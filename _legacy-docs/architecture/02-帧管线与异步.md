# 02 · 帧管线与异步

## 1. 一句话

一帧按 `src/Rendering/FrameStage.php` 的 `ORDERED` 跑**九段**：
`pumpIo → pumpTasks → pumpTimers → tickAnimations → placeOverlays → settle
→ tickLateMount → focusCollect → pumpSemantics`。
`layout / paint / beginFrame / present` 是 `TIMED_ONLY` 四段，只计时、不参与顺序校验。
所有"后台结果 / 动画推进"都必须在 `settle` **之前**，让 `setState()` 标脏被同帧的 settle 消费
（否则 "loading→ready" 闪一帧空）。帧时钟**自适应**：`wantsFrame()` 只读 `Pipeline` 的
`frameRequests > frameServed` 一个计数器，变更现场自己调 `scheduleFrame()` 举手；
欠账清零即停摆、CPU 归零。

## 2. `Application::frame()` 的实际顺序（`src/App/Application.php`）

段名与顺序的唯一真相源是 `src/Rendering/FrameStage.php`（`FrameStageTest` 守表完备性）：

```
pumpIo           // ① 非阻塞 IO 先到；回调里 setState 的脏标记由本次 settle 消费
pumpTasks        // ② 后台结果取出；必须在 settle 前 ⇒ 同帧生效
pumpTimers       // ③ 延时回调；跑到 settle 之后则要等下一帧
tickAnimations   // ⓸ 推进动画；在 settle 前
placeOverlays    // 浮层布局段（逐层无界自尺寸 + 钉锚点 + 翻转/夹进客户区）
Frame::run(...)  // 核心管线：settle → layout → paint → present（后三段只计时）
tickLateMount    // ⓹ 迟到挂载补 tick：刚挂上的页 State 在 ⓸ 时还不在树里
focusCollect     // 每帧重建焦点链（settle 可能换了子树 ⇒ 旧链握死节点）
pumpSemantics    // 语义树推给 UIA（无 sink ⇒ 不建，零开销）
```

★ `Frame::run()` 内部是 `settle → layout → paint → present`，其中 `layout / paint / present`
与壳侧 `beginFrame` 一起登记为 `FrameStage::TIMED_ONLY`：有耗时、无跨段顺序约束
（详见 [01](01-三层树与身份.md) 的 settle、[03](03-布局与渲染盒.md) 的 layout、
[04](04-绘制与双后端.md) 的 paint、[10](10-平台端口与-Win32-壳.md) 的 present）。
★ 别按「五段 / 六段」数 —— 那是把有序九段、只计时四段与 `STAGE_BUDGET_MS` 的
**预算分组**混成了一套口径。

### 2.1 零视口帧（最小化 / 桌面临时切走）

`tight(0,0)` **不是**"内容放不下"，而是**"没有像素可画"**。拿它去布局时 `Text` 只能
每字一行（宽 0 ⇒ 换行），而可用高度同样是 0 ⇒ `RenderText 实际 0.0 × 86.4，
最多只能用 0.0 × 0.0`，当场 C6 Fatal（用户 2026-10-25 实测：最小化即崩）。

判据放在 `frame()` 里、**泵全部跑完之后**、`placeOverlays` 之前：

| 段 | 零视口时 | 理由 |
|---|---|---|
| `pumpIo` / `pumpTasks` / `pumpTimers` / `tickAnimations` | **照跑** | 最小化期间动画与 `after()` 必须继续推进，否则还原时一下跳好几秒 |
| `placeOverlays` + `Frame::run` | **跳过** | 布局/绘制/present 都没有意义；表面因此**一帧都不起** |

★ 根盒**保持最后一次有效尺寸**（不被 0 覆盖）—— 这是"还原能正常重排"的前提；
还原时系统必发新的 `WM_SIZE`（带真实尺寸）⇒ 走正常帧。夹具断言的就是这三件事：
帧被**计数跳过**、表面**不起帧**、根盒**保持旧宽**（`Smoke\App\ZeroViewportApplication`）。

★ 为什么不做"缓存上次视口继续画"：画进不可见 surface 纯属浪费，而且会让
`Screen::viewport()` 撒谎 —— 它应当诚实反映客户区（0 就是 0）。判据放在**框架**
而不是平台端口，是因为任何端口都可能给 0（离屏、折叠屏、远程桌面），
框架早退一次就全覆盖；`repaintForResize()` 用同一条判据直接 return（它本来不跑泵）。

## 3. 动画驱动（§17.4.9）

- `State::tickFrame(float $timestampMs): bool`（`src/Widget/State.php`）由 `tickAnimations` 段在
  settle 前遍历树调用；返回值只回答"这段动画还活着吗"，**不是** `wantsFrame()` 的判据。
  欠帧由变更现场调 `Pipeline::scheduleFrame()` 记账，`Application::wantsFrame()` 只读
  `frameRequests > frameServed`（`src/Core/Pipeline.php`）—— 别在这里加枚举判据。
- `State::markDirty()`（`src/Widget/State.php`）是写入口；`tickFrame()` 里 `setState` 只标脏，由紧随的 settle 消费。
- **同帧幂等**：`tickFrameStamped(ts, serial)`（`src/Widget/State.php`）用每帧自增 `frameSerial`
  识别"本帧已推进过的状态"，迟到挂载补 tick 不会把动画快进一帧。
- 原语：`AnimationController`（`src/Widget/AnimationController.php`，0..1 单值驱动器）+ `Curve`
  （`src/Widget/Curve.php`，`int $kind` + `===` 链分 4 条二次曲线，**不用 `switch`**——见
  `src/Widget/Curve.php` 注释：tpc 给 `switch($this->kind)` 生成属性读不加 `php::toInt()` ⇒ C2440）。

## 4. 异步三问（先问"你在等什么"）

- `TaskHost` 接口（`src/App/TaskHost.php`）：**三条后端**——`ProcessTaskHost`（子进程，跨语言/
  防卡帧）、`ThreadTaskHost`（线程）、`SyncTaskHost`（同线程，快路径）。
- 作业：`Job`（`src/App/Job.php`）、`NamedJob`（`src/App/NamedJob.php`）。
  ★ `SlicedJob`（分片任务）**已于 2026-10-31 删除** —— 它的入口只在 `Application` 上，
  页面（`State`）架构上拿不到，且与 `TaskHost` 重复七件事；见
  `docs/ASYNC-ARCH-2026-10-31.md` §12 与 `docs/_archive/DESIGN-v2-2026-10-14.md` §17.4.3。
- `IoPoller`（`src/App/Io/IoPoller.php`）+ `ProcessWorker`（`src/App/ProcessWorker.php`）：非阻塞 IO 与子进程管理。
- ★ 不依赖 `Swoole\Thread`：上游修复实测只到半效。异步结果**回贴**走 `setState` ⇒ 同帧 settle 消费。

### 4.1 取消能停到哪：三档能力声明

`cancel()` 的文档写的是"尽力而为"。**"尽力"在各后端差得很远**，而且这个差异以前只活在
一份分析稿里 —— 应用想知道"按了停止之后后台还在不在烧 CPU"，只能去读三个后端的实现。
现在它是 `TaskHost::cancelSupport(): CancelSupport`（`src/App/CancelSupport.php`），
新增后端**编译期强制**回答：

| 档位 | 后端 | `cancel()` 之后实际发生什么 | 省 CPU？ |
|---|---|---|---|
| `QueuedOnly` | `ProcessTaskHost` | 还在**排队**的：从队列摘掉，永远不会开始；已发给 worker 的只"不交付" | **能**（排队那部分） |
| `DetachedOnly` | `ThreadTaskHost` | 只能"不交付"——任务已交给 C++ worker，摘不回来 | 不能 |
| `AlreadyDone` | `SyncTaskHost` | `submit()` 里 `run()` 已跑完，没有对象可取消（不是"不支持"） | 不适用 |

★ 与渲染侧 `CanvasCapabilities` 是**同一条设计语言**：能力声明只回答"能不能"，不回答
"做得怎么样"；界面据此决定要不要显示停止按钮、要不要提示"仍在后台运行"
（文案用 `CancelSupport::describe()`，别在界面里再拼一遍）。
★ 三条用法结论：**别指望 `cancel()` 省 CPU**（除进程池排队那部分）；**`cancel()` 永不产生
`error` 态**（取消不是失败，`catch()` 不会被调到）；**取消是剪枝**（一条根 Future 只该有
一个主人，`AsyncCommand::make()` 的契约）。

### 4.2 失败分三档：谁的错决定怎么处置

`Failure::codeOf()` 是全链路唯一的分类提取点（跨进程的 `code` 也在这里归一）。框架自己的
失败给稳定 code，应用**不该靠消息文字分辨**：

| code | 谁给的 | 含义 | 该不该重试 |
|---|---|---|---|
| `drift/timeout` | `ProcessTaskHost::sweepTimeouts()` | 跑过任务声明的（或 Host 兜底的）墙钟上限，worker 已被杀 | 可以 |
| `drift/worker-died` | `ProcessTaskHost::reap()` | worker 进程自己没了（崩溃 / 被外部杀） | 可以 |
| `drift/host-unavailable` | `ThreadTaskHost` | 池起不来、递不进去（环境问题） | 可以 |
| `drift/job-rejected` | `ProcessTaskHost` / `ThreadTaskHost` | 不是 `NamedJob` / 参数转不了 JSON / 注册表里没有 | **不行**（装配写错了） |

★ 超时与"任务自己抛异常"在 UI 上是两种处置（前者可重试、后者要改代码）。没有 code 时
它们只能靠消息文字区分 —— 而 `codeOf()` 对裸 `RuntimeException` 归一成 `''`，等于把这条
信息丢在边界上（2026-11-16 之前就是这样）。

### 4.3 进度：只喂根任务

`Future::reportProgress()` 不沿 `chain()` 传递；`onProgress()` 挂在派生节点上会留一条
`progress/derived-chain` 诊断。⇒ 要进度就订阅 `submit()` 返回的那条（或用
`AsyncScope::await($root, $onProgress)`）。

★ `AsyncCommand` 转发进度时会先看 `Future::isDerived()`：派生链**不挂**（收不到），
所以走 `submit()->then(…)` 形态的命令不会留噪音诊断 —— 框架自己不该制造这类诊断，
否则真正的"应用挂错链"会被淹掉。

### 4.4 跨进程线协议：`FIELDS` 一份名单，两个方向

跨进程只能传**名字 + 数组**，所以每个值对象都要被描述两遍（写出去一遍、读回来一遍）。
两遍手写 = 两份会分叉的信息，而分叉是**静默**的：键名对不上时两侧一起退化成默认值，
UI 一切正常，只有真机 worker 里跑的是错数据。

⇒ `Wire` trait（`src/App/Wire.php`）让一份名单驱动**摊平**方向，读回方向留给业务
（形状不规则，塞不进名单 —— 见下方否决表）：

```php
final class FetchRowsJob implements NamedJob
{
    use JobArgs;                    // JobArgs use Wire：参数侧多出 args()/fromArgs()/name()

    public const NAME = 'showcase.rows';

    /** 顺序 == 构造参数顺序 */
    private const FIELDS = ['page', 'perPage', 'mode', 'baseUrl'];

    public function __construct(
        private readonly int $page = 1,
        private readonly int $perPage = 20,
        …
    ) {
    }

    public function run(): mixed { … }
}

final class SignInfo
{
    use Wire;                       // 结果侧只有 toArray() + 收窄原语

    private const FIELDS = ['account', 'policy', 'signature', 'directoryPath', 'accessAddress', 'expireTime'];

    public function __construct(public readonly string $account, …) {}

    public static function fromArray(mixed $data): ?self { … }   // ← 业务兜底自己写
}
```

| 方向 | 谁给 | 怎么来 |
|---|---|---|
| 摊平（`args()` / `toArray()`） | trait | 从**同名属性**读（构造器提升保证"参数名 == 属性名"） |
| 读回（`fromArgs()`） | `JobArgs` | 按 `FIELDS` 顺序**位置**填（`new self(...$values)`） |
| 读回（`fromArray()` / `fromPayload()`） | **业务** | 逐字段收窄；用 `wireString()` / `wireStrings()` 省掉 `is_array` 样板 |

★ 契约：**`FIELDS` == 构造参数名集，且顺序相同**。漏字段 ⇒ 跨进程丢值；顺序错 ⇒
`fromArgs()` 把两个同类型参数装反（没有 `TypeError`）。两条判据都拿**反射的构造器签名**
比（拿名单比名单永远发现不了自己漏字段）：`NamedJobContractTest`（参数侧）、
`WireContractTest`（双向，按目录发现，新增值对象自动纳入）。
★ 加一个异步动作 = **两个文件两处**：`Jobs/XxxJob.php`（`NAME` + `FIELDS` + 构造器 +
`run()`）、`JobRegistry` 加一行。漏登记由同一条判据咬。

**为什么读回那一侧不让 trait 生成**：

| 方案 | 否决理由 |
|---|---|
| 按 `FIELDS` 位置 `new self(...$values)` 也用于结果 | 返回值形状不规整：状态码可能是 int 也可能是数字字符串、缺字段要退化成默认值、有的缺一个就整份作废。这些是**业务判断**，硬塞进通用映射只会逼出一个没人看得懂的迷你 schema |
| 反射（`ReflectionClass` 取构造参数） | AOT 下 Reflection 元数据 **Partial**；而 `args()` 恰恰在 **AOT 二进制**里被调（`ProcessTaskHost::submit`），反射跑不起来 |
| `#[\Arrayable]`（tpc 编译期 attribute） | **只在 AOT 生效**。本仓是双形态：phpunit 与 `drift dev` 跑解释器，那时 `args()` 根本不存在 |
| `new $class(...$args)` / `get_object_vars` | 全仓零用例、无 AOT 验证记录 —— 不赌 |
| codegen 持续派生映射 trait | 7 个任务的规模撑不起「生成器 + `--check` 判据 + 生成物入库」；这是"为低频场景上新机制" |

★ 两条形态都走 tpc 正规路径：属性读生成 `attr(Get)`（按槽读，不经 Zend 可见性检查），
重建生成 `appendUnpacked` + `newObject`。真机验证见 §8。

## 5. 三条错误通道（先问"这是谁的错"）

`Errors`（判决器，`src/Errors.php`）与 `ErrorBoundary`（节点级兜底，`src/Widget/ErrorBoundary.php`）
职责分得清，但**入口没有类型**：写应用时没人告诉你什么时候 `throw`、什么时候
`Errors::report()`、什么时候包一层边界。按"错在谁"三行判完：

| 谁错了 | 用什么 | 现场表现 | 为什么不是另外两条 |
|---|---|---|---|
| **框架契约 / 不变式被破坏**（封存后 `mutate()`（`src/Widget/Widget.php`）、容器上 `overflow(Overflow::Scroll)`、尺寸超出上界（C6，`src/Layout/RenderBox.php`）） | `Errors::report($msg, Errors::FATAL)`（`src/Errors.php`，默认就是 FATAL） | 写 `Errors.log`（错误 + 栈 + 最近 100 条 Diagnostic）→ 原生错误框 → `exit(3)` | 继续跑必然得到错误结果 ⇒ 降级没有意义；交给 `ErrorBoundary` 会把"框架坏了"画成一个占位块，**看起来像应用自己的 bug** |
| **用户输入 / 数据让某一子树渲染失败**（一条记录缺字段、插件页面炸了） | `ErrorBoundary::make($subtree)`（`src/Widget/ErrorBoundary.php`） | 该子树换成 `ErrorPlaceholder`（消息原文显示给用户），**其余照常** | 这类错不该让整个窗口死；捕获只写 `DIAGNOSTIC`，**不用 `RECOVERABLE`**——它在 debug 下整局中止，与"只坏那一块"直接矛盾 |
| **外部 IO / 慢操作**（读文件、跑子进程、网络） | `Job` + `after()`（真异步 `ProcessTaskHost` / 快路径 `SyncTaskHost`，见 §4） | 结果回贴 UI 线程后 `setState`，同帧 settle 消费 | 既不是契约破坏也不是渲染失败；**在 UI 线程里同步等**才是这里的错（`SyncTaskHost` 就在 UI 线程执行作业，卡帧） |

★ 三条纪律：
- **不要用 `throw` 当错误报告**：没人接的异常冒到 `Frame` 走 Fatal 序列 ⇒ 整个窗口中止。
  要么 `Errors::report()`，要么把这段渲染放进 `ErrorBoundary` 子树里。
- **`ErrorBoundary` 不是 `try/catch` 的替代品**：它只兜渲染期三层（`ErrorBoundaryElement::rebuild()`
  / `settle()` / `RenderErrorBoundary::performLayout()/paint()`）；`Job` 回调里的异常**不在**它的
  捕获范围内（那里该自己 `Errors::report()` 或走应用自己的失败态）。
- **占位 UI 本身就是痕迹**（消息原文给用户看）；额外 `Errors::report(DIAGNOSTIC)` 的理由只是
  让 `recentDiagnostics()` 能断言，不是"多记一条更保险"。

## 6. 自适应帧时钟（`FrameClock`，`src/App/FrameClock.php`）

- 壳的消息泵是**阻塞**的（`GetMessageW`）：没输入事件就一直睡。所以"后台任务还在跑 /
  有流在监听 / 动画没跑完"必须由框架主动说出口，壳才知道起定时器把循环叫醒 ——
  **这是修缺陷，不是优化**。说出口的方式是变更现场调 `Pipeline::scheduleFrame()`，
  不是让 `wantsFrame()` 去枚举谁还活着。
- `FrameClock::advance($app, $ts, $constraints)` 跑一帧并推进时钟；`nextWaitMs($app, $now)`
  决定下一次醒来的时间。公共面还有 `stallCount()` / `worstGapMs()`，**没有** `pace()` / `tick()`。
- `Pipeline` 欠账清零 ⇒ `wantsFrame()` 为 false ⇒ 帧时钟停摆、CPU 归零。

## 7. 轻量重绘（拖动 resize，`Application::repaintForResize()`）

与 `frame()` 唯一区别：**不碰帧外东西**（不 pump/不推进画/不重建焦点链/不推语义）。平台壳在
`WM_SIZE`（模态循环内）同步调回（C→PHP 重入），能碰的状态越少越安全；松手后主循环恢复跑完整帧收尾。

零视口（最小化时 `WM_SIZE` 的 lp 就是 0×0）与 `frame()` 用**同一条判据**，但它不跑泵 ⇒ 直接
return（§2.1）。不早退的话，最小化瞬间这条重入路径就是第一个撞 C6 的地方。
