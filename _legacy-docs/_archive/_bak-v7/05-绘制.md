# 05 绘制

> 本册回答：**绘制产出什么形状、后端怎么插拔、局部重绘靠什么、golden 怎么分层。**

---

## 1. 两个不同的东西：`Painter` 与 `Canvas`

Drift 把两者混在一个 `Canvas` 接口里，结果"每条绘制命令过一次桥"。
本方案拆开：

| | `Painter` | `Canvas` |
|---|---|---|
| 在哪 | PHP 侧 | 后端（C++ / PHP 软光栅） |
| 做什么 | **追加 op** 到缓冲 | **消费整段 op 流**，出像素 |
| 调用频率 | 每 op 一次（纯 PHP，无跨界） | **每帧一次** |
| 有状态 | 有（当前缓冲、变换栈） | 有（画布、裁剪栈） |

```php
final class Painter
{
    public function rect(float $x, float $y, float $w, float $h, int $paintId): void;
    public function roundRect(float $x, float $y, float $w, float $h, float $r, int $paintId): void;
    public function text(int $paraId, float $x, float $baselineY): void;
    public function glyphRun(int $runId, float $x, float $y): void;
    // …每个 op 一个方法，全部只往 $this->buf 追加
}

interface Canvas            // 后端
{
    public function capabilities(): int;                       // ★ 能力位掩码，启动时查一次
    public function begin(int $w, int $h, float $dpr, int $bg): void;
    public function draw(OpBuffer $buf, int $count): void;      // ★ 一帧只跨一次边界
    public function end(): string;                              // 返回 RGBA 像素
}
```

★ **"一帧一次跨界"是本方案相对 Drift 的实质改进**：
Drift 的 Skia 桥是"每条 `drawRect` 过一次 C++ 边界"（`php_drift_skia_draw_rect`），
本方案整帧一次。代价是 C++ 侧要遍历 op 流——但那本来就是它要干的事。

★ **`Painter` 无跨界** ⇒ `CustomPaint` 可以在 PHP 里随便追加几百条 op，不产生桥开销。

## 2. op 流形状

固定槽位，每条 op = **1 个 opcode + 6 个数值槽 + 1 个资源索引**：

| 槽 | 含义 |
|---|---|
| `op` | opcode（int 常量） |
| `a b c d` | 几何（float，含义随 op） |
| `e` | 数值参数（半径 / 线宽 / 透明度量化） |
| `f` | 资源索引（`paintId` / `paraId` / `runId` / `imageId`），无则 -1 |
| `node` | 所属节点 id（局部重绘与调试用） |

★ **资源走索引，不进 op**：`Paint`（颜色/描边/渐变）、`Paragraph`、`GlyphRun`、`Image`
都存在各自的表里，op 只带 `int` 索引。这样 op 定长、可 memcpy、可哈希。

★ **容器只能是 packed PHP array**（不是"待实测"）：op 段是**节点的属性**，
而 Std 容器不能嵌入属性（赋给属性会被 `toArray()` 拷贝）⇒ **V9 已被约束解掉，不用量了**。
op 是纯数值（int / float）而不是对象 ⇒ packed array 正是合适形态。

★ 唯一还值得量的是**追加开销**：2000 次 `$arr[] = $v`。
若成为瓶颈，退路是"每节点预分配定长数组 + 游标"（避免反复扩容），**而不是换容器**。

## 3. 19 个 op，三层能力

| 层 | op | 要求 |
|---|---|---|
| **Core（10）** | `RECT` `ROUND_RECT` `ELLIPSE` `LINE` `TEXT` `GLYPH_RUN` `SOLID` `STROKE` `DRAW_CHILD` `CLIP_RECT` | **所有后端必须实现**；缺一个 = 启动即 Fatal |
| **Extended（4）** | `LINEAR_GRADIENT` `RADIAL_GRADIENT` `DASH` `CLIP_PATH` | Skia 必须；软光栅可近似（渐变→分带，虚线→实线） |
| **Optional（5）** | `PATH` `IMAGE` `LAYER` `SHADOW` `BLUR` | 仅 Skia 级后端；软光栅报 `E-OP-UNSUPPORTED` 并**降级为矩形占位** |

★ **为什么 Core 缺一个就 Fatal**：Core 是"能画出界面"的下限。
缺了它，界面会静默变成空白——比崩溃更难查。**宁可启动就炸，不要跑到一半缺块。**

★ **为什么 Optional 不 Fatal 而降级**：它们只影响"好不好看"。
软光栅（golden 后端）画不了阴影，就画个半透明矩形占位——golden 依然可比（占位是确定的）。

### 3.1 能力矩阵是数据文件，不是散文

```
build/capabilities.php     ← 构建期由后端声明生成
[
  'raster' => Canvas::CORE,
  'skia'   => Canvas::CORE | Canvas::EXTENDED | Canvas::OPTIONAL,
]
```

`Application` 启动时读一次，写入 `AppCapabilities`。`CustomPaint` 与控件据此决定降级路径。
★ 这样"某个平台支持什么"是**可查询的**，不是靠文档记忆（UDA 的 SupportLevel 思路）。

## 4. 局部重绘：段属于节点

### 4.1 段的分配

每个节点持有自己的 `OpBuffer $seg`（一条 op 段）。`paint` 阶段：

```
for each node in 脏绘制集合（按 depth 升序）:
    node.seg->reset()
    node->paint($painter)         // 追加自己的 op
    for each child:               // 递归，但子节点若有缓存段则直接引用
        $painter->drawChild(child.id)
```

★ **`DRAW_CHILD` 是唯一的结构 op**：父不复制孩子的 op，只记"这里要画 id 为 N 的子树"。
最终上屏时由后端按 id 解析（或由 PHP 侧在 present 前展开成线性流）。

### 4.2 为什么这样能局部重绘

改一个 `Text` 的文本 ⇒ 只有它的 `seg` 重录；兄弟节点的 `seg` **完全不动**（连 memcpy 都不需要）。
上屏时按树序拼装——拼装是引用拼接，不是内容拷贝。

★ 对比 Drift：Drift 是每帧全树 `paint($canvas)` 重画（4.5ms 光栅 / 29.9ms Skia）。
局部重绘的收益在**大树 + 局部高频变化**（编辑器、表格）时才明显；首版不追这个，
但**结构先留好**，否则以后改不动。

### 4.3 `RepaintBoundary`：缓存整棵子树的段

```php
final class RepaintBoundary extends Node
{
    private OpBuffer $cached;       // 子树拼好的段
    private bool $cacheValid = false;
}
```

跳过条件：子树无 `DIRTY_PAINT` 且自身无 `DIRTY_STRUCT`。
★ 与 `LayoutBoundary` 成对使用：`LayoutBoundary` 省布局，`RepaintBoundary` 省绘制。
**大多数场景只需要 `LayoutBoundary`**（绘制本来就便宜，除非有渐变/模糊）。

## 5. 变换与裁剪

```php
$painter->save();                 // 压栈
$painter->translate(10, 20);
$painter->clipRect(0, 0, 100, 100);
... 画 ...
$painter->restore();
```

★ **变换栈与裁剪栈是两条独立栈**（Drift 的 W8 结论）：`save()` 同时压两条，`restore()` 同时弹。
但**深度分别计数**，任一超限各自报错——否则"裁剪栈溢出"会被误报成"变换栈溢出"。

★ **变换只允许平移与缩放**（首版）。旋转/斜切不进 op 流：
一旦支持旋转，命中测试、裁剪矩形、文本基线全部要重写。**明确不做，比做了再砍便宜。**

## 6. 两个后端

| 后端 | 用途 | 实现 | 关键约束 |
|---|---|---|---|
| **`RasterCanvas`** | golden / 无头测试 / 预览 | 纯 PHP 软光栅 | **确定性**：同一 op 流必出同一像素；不读系统字体 |
| **`SkiaCanvas`** | 生产 | C++ 桥 + Skia 静态库 | 逐字形绘制（不用 SkParagraph），字体走随包目录 |

★ **确定性是 RasterCanvas 的唯一价值**，所以它必须拒绝一切"不确定"的东西：
不做抗锯齿（或做固定规则的），不做亚像素定位，不查系统字体，不用时间戳。

★ **SkiaCanvas 不用 SkParagraph**：一旦让 Skia 自己塑形，步进换成 HarfBuzz 的度量，
与 Drift 的度量对不上 ⇒ 断行、光标、命中三处同时错。**字形逐个画，位置由 PHP 给。**

---

## 7. golden 分两层

| 层 | 比什么 | 抓什么 bug | 速度 |
|---|---|---|---|
| **op golden** | op 流的哈希（`md5(codes . nums)`） | 布局、绘制顺序、裁剪、颜色 | 极快，不用光栅化 |
| **像素 golden** | 光栅化后的 PNG md5 | 光栅器本身、字形、抗锯齿 | 慢 |

★ **先跑 op golden，失败再看像素**。绝大多数回归在 op 层就能定位到"哪个节点多画了一条"。
只有 op 相同但像素不同时，才是光栅器的 bug——这时候看像素图有意义。

★ op golden 需要 op 流**稳定**：资源索引必须按确定顺序分配（不能按对象地址）。
索引表用"创建顺序 + 帧末重置"，且在 golden 模式下断言两次运行索引一致。

## 8. 性能预算

| 场景 | op 数 | 目标 |
|---|---|---|
| 静态页 | ~800 | paint < 3ms |
| 列表滚动一帧 | ~600（视口内） | paint < 2ms |
| 全屏渐变背景 | ~10（但填充面积大） | 光栅 < 6ms |
| 1000 字符段落 | ~40（`GLYPH_RUN` 合批） | paint < 2ms |

★ **`GLYPH_RUN` 是文本性能的关键**：一个字一个 `TEXT` op 会产生 1000 条 op；
合成一个 run（字形 id 数组 + 位置数组，走侧表）只需 1 条 op。Drift 是逐字形桥调用，这里必须合批。

## 9. 绘制实现细节（v6 补齐）

> 前面八节是"op 流与后端"，这一节是"帧内怎么省钱"。
> v7 第一版只提了 `RepaintBoundary`，没有层判据、没有脏区、没有动画分级——
> 那三条决定了"能不能 60fps"。

### 9.1 层的开关判据（P2）

| 情形 | 开层？ | 理由 |
|---|---|---|
| `opacity < 1` | **开** | 半透明必须整组先合成再统一乘 alpha（否则子节点重叠处叠两次） |
| 非矩形裁剪（圆角 + 内容） | **开** | 需要一次 mask |
| 混合模式（非 `src-over`） | **开** | 需要隔离背景 |
| **变换（translate / scale / rotate）** | **不开** | ★ 变换只是改矩阵，子树 op 一条都不用重录 |
| **阴影** | **不开** | 阴影是绘制内容（画在子树下面），不是合成操作 |

★★ **"变换不开层"是最值钱的一条**：500 节点子树整体位移，成本 = 位移一个矩形。
开了层就要"离屏渲染 + 重新合成" ⇒ 成本 = 整棵子树重画。

★ 判据：**"这一组孩子需要互相作用吗？"** 需要（半透明叠加、混合、整体裁剪）⇒ 开层；
不需要（只是整体移动/缩放）⇒ 不开。

### 9.2 脏区 damage（P3 / P4）

```
damage = ∪(旧 bounds, 新 bounds)
       → 经变换到屏幕坐标
       → 外扩（阴影半径 / 模糊半径 / AA 1px / 描边宽度）
       → ∩ 视口
若 damage 面积 > 视口 40% ⇒ 全刷
```

★ **必须 ∪ 旧和新**：只算新的会留残影（元素缩小/移走后原位置没被重画）。这是必踩的坑。

★ **外扩是必须的**：AA 在边界外半像素出墨，阴影/模糊在边界外几十像素出墨。
不外扩的症状是"元素边缘有一圈没擦干净的旧像素"。

★ **> 40% 全刷**：脏区太多时逐个裁剪的开销超过整屏重画。40% 是经验值（Qt/Flutter 同量级），实测再调。

★★ **脏区在 C++ 算，不在 PHP 算**（P4）：PHP 只有节点级 bounds，而脏区需要 **op 级**精确 bounds
（大节点里改一个小字，节点级算出来是整块）。所以 PHP 只提供"哪些段脏了"，C++ 用 op 的 bounds 求 damage。

### 9.3 扁平 `drawList` + `transformIndex`（P5）

```php
// PHP 侧：段属于节点（§4），局部坐标
$node->ops = [...];

// C++ 侧：整帧消费一次，展开成扁平列表
// struct DrawOp { int type; float x,y,w,h; int transformIndex; ... };
```

★ **`transformIndex` 是矩阵栈的索引，不是每节点一个矩阵**：
滚 1000 项不是 1000 次矩阵乘法，而是 1000 次"读同一个 index"。
只有变换真的变化处（§9.1 的层边界）才压栈。

★ **`DIRTY_PAINT` 只换段，`drawList` 不动**：扁平列表按段边界切片，
某节点重录只替换它那一段（memcpy），兄弟节点连搬都不用搬。这是 I5"段属于节点"的直接收益。

### 9.4 动画三档（P6）

| 改什么 | 脏位 | 成本 | 例子 |
|---|---|---|---|
| 变换 / 不透明度 | `DIRTY_COMPOSE` | ~3µs | 淡入、滑入、缩放 |
| 颜色 / 圆角 / 文字内容 | `DIRTY_PAINT` | ~60µs | 高亮、悬停 |
| 尺寸 / 位置（参与布局） | `DIRTY_LAYOUT` | ~300µs | 展开/折叠（高度动画） |

★ **三档差 100 倍**，所以"这个动画能不能 60fps"在**设计时**就能回答：
- 淡入淡出、位移、缩放 ⇒ 一定能（compose 档）。
- 高度展开 ⇒ 只有小范围能（layout 档，每帧重排该子树）。
- 高度展开 + 长列表 ⇒ **不能**，必须换成"淡入 + 内容直接出现"。

★★ **Tween 按字段静态类型分派，不做 `interface Tween { lerp(mixed $t): mixed }`**：
`mixed` 在 AOT 下是 `Var`，每字段每帧一次装箱。
做法是 `FloatTween` / `ColorTween` / `IntTween` 三个具体类 + `switch ($node->kind)`（同 L3）。

### 9.5 七条绘制不变量（P7）

| # | 不变量 | 违反的症状 |
|---|---|---|
| 1 | 段内 op 用**局部坐标** | 节点移动后 op 要重录（失去"只改矩阵"的收益） |
| 2 | 只有**属主节点**能重录自己的段 | 别人的段被改 ⇒ 局部重绘的边界失效 |
| 3 | `ops` **只写不读**（除后端消费） | 有人读 ⇒ 段不能安全替换 |
| 4 | **帧内不分配** | GC 停顿落在帧中间 ⇒ 偶发卡顿 |
| 5 | 录制中**不改状态** | 段内容依赖录制顺序 ⇒ 不可复现 |
| 6 | `opacity < 1` **必有层** | 子节点重叠处叠两次 alpha |
| 7 | 段生命周期**跟随节点** | 节点没了段还在 ⇒ 画出幽灵 |

★★ **第 4 条"帧内不分配"是 60fps 的前提**：靠 `Recorder` **预分配缓冲 + 游标覆写**实现。
每次 `paint` 不 `new` 数组、不 `array_push`（超出预分配才扩容，且扩容次数可统计）。
判据：`FrameStats` 记"本帧分配次数"，> 0 就该查。

### 9.6 分数量化在光栅前（P8）

```
所有几何 → 乘 DPR → 四舍五入到整物理像素 → 光栅
```

★ **相邻盒必须共享像素边**：A 的右边界与 B 的左边界要落到**同一个**物理像素边界，
否则两盒交界处各亮半行，出现**接缝**（1px 亮线，深色背景上特别明显）。

★ 做法：`round($x * $dpr)` 统一在光栅前做一次，**不在布局里做**。
布局保持浮点（逻辑像素），光栅器只认整数物理像素——**量化是单点，且只有一个点**。
