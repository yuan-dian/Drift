# 19 控件 API 语法

> 本册回答：**同一件事为什么只能有一种拼法、命名参数什么时候带、响应式四个入口各收什么、
> 菜单为什么必须是数据。**
> 来源：v6 第 11 / 12 轮（D-33 / D-34）。v7 第一版完全没有这一层——
> 于是"框架对了，但开发者每天要猜三种写法"。

---

## 0. 一句话

**同一个动作只能有一种拼法；一条规则如果没有 lint，它就只是建议。**

前一句管可读性，后一句管可持续性。两句话合起来是这一册的全部：

| 只管前一句 | 后果 |
|---|---|
| 规则写在文档里，没有 lint | 三个月后新增 10 个控件，其中 3 个不遵守，且没人发现 |
| 规则太抽象（"尽量用命名参数"） | 每个人理解不同，等于没规则 |

★ 所以本册的每条规则都必须是**能被示例检验的谓词**——
写规则时拿文档里所有示例回代一遍；回代不过就说明规则写错了，不是示例写错了。

## 1. `make()` 只收一个本质输入

```php
Text::make('保存')                       // ✅ 本质输入 = 文本
Button::make('保存')->onTap($fn)          // ✅ 本质输入 = 标签
Image::make('logo.png')->decodeSize(w: 80, h: 80)   // ✅ 本质输入 = 路径
```

**判据（机械）**：**去掉它，这个控件还存在吗？** 不存在 ⇒ 本质输入；还在 ⇒ 链式。

| 控件 | 本质输入 | 为什么其余不是 |
|---|---|---|
| `Text` | 文本 | 颜色/字号是修饰 |
| `Button` | 标签 | 回调不是"按钮之所以是按钮" |
| `Image` | 路径 | 尺寸来自布局（见 §3.3） |
| `Row` / `Column` | **无** | 容器没有本质输入 ⇒ 只用 `->children([...])` |
| `TextField` | **无**（空字段合法） | 初值可空 ⇒ `->value()` / `->defaultValue()` |

★ **`make()` 收 2 个以上参数就是设计错误**，不是风格问题：
它意味着"这个控件的身份由两个东西共同决定"，而那两件事里必有一件该被链式覆盖。

### 1.1 例外一：子节点用数组形参

```php
Column::make()->children([$a, $b, $c]);      // ✅
Column::make($a, $b, $c);                    // ❌ 变参
```

★ 理由不是偏好：**变参在循环里累积会撞 AOT 编译器的 bug**。
`->children(array)` 是唯一安全形态，且它让"孩子列表"变成可构造、可传值的一等数据。

### 1.2 例外二：框架命令的第 1 个"目标"用位置

```php
traySetMenu($trayId, items: [...], onResult: $fn);   // ✅ 目标位置 + 其余命名
```

★ 判据：**"目标"是这条命令的作用对象**（没有它命令没有意义），其余都是配置。

## 2. 命名参数的机械规则

> **从左往右数，第一个实参之后，只要还有实参，就都得带名字。**

这句话同时覆盖四类调用，不用分类记忆：

```php
Text::make('保存')                                  // 1 个 ⇒ 位置
Button::make('保存')->onTap($fn)                     // 1 个 ⇒ 位置
->animate(200, curve: Easing::OUT)                   // 第 1 个之后还有 ⇒ 全命名
$c->local('open', init: fn() => false)               // 同上
->range(min: 0, max: 100)                            // 没有"第一个" ⇒ 全命名
```

★ **治理范围**：只管**应用会写的调用**。
`Platform::paintSet(...)` 这类 ABI 直通、`Spec::layout($this, $c)` 这类内部方法**不管**——
参数名对调用者没有意义，强行命名只是噪音。

★★ 这条规则的初版是"≥2 参数一律命名"，然后被文档里自己的
`->menu($items, onResult: ...)` 证伪了（它是"第 1 个位置 + 其余命名"）。
**规则被自己的示例推翻，说明规则写错了。** 改成上面那句可机械执行的话之后，四类调用全部通过。

## 3. 响应式四个入口，每个只收一种类型

| 入口 | 收什么 | 用于 |
|---|---|---|
| `make(值)` | 标量 / 值对象 | 静态内容 |
| `of(Closure)` | 闭包，**读即订阅** | 内容依赖共享态 |
| `dynamic(Closure)` | 闭包，**局部重建** | 内容依赖本地态且结构会变 |
| `value(Cell)` | **`Cell`**（不包闭包） | 受控值（输入框、开关） |

★ 一句话记法：**`Cell` 不用包，`Closure` 要包。**
四种入口各收一种类型 ⇒ 选错是**编译期/类型错误**，不是运行期怪现象。

★ **为什么不做"三种写法选一种"的灵活性**（v6 明确否掉过）：
选择的成本 × 每天 50 次 = 比省下的代码贵得多。

### 3.1 受控值的类型必须与回调对称

```php
// ✅ 进出同一个类型
$field->value($cell)            // Cell<TextEditingValue>
      ->onChanged(fn(TextEditingValue $v) => ...);

// ❌ 值存 string、回调给 TextEditingValue
```

★★ **不对称会逼出两个必须手工同步的入参**：
`->value($cell)` + `->selection($cell2)`，而它们一旦不同步就是"光标跳到行首"这类 bug。
**同一个值进出必须是同一个类型。**

### 3.2 受控值不能是"半受控"

★ 判据：**这个值在"输入过程中"有没有第二个读者？** 有 ⇒ 受控（[16](16-应用分层.md) §5）。
但"受控"必须是完整的：值、选区、组字态三者一起受控，不能只受控值。

### 3.3 `Image` 的解码尺寸默认来自布局

```php
Image::make('logo.png')                    // ✅ 默认取 lastBox 的逻辑尺寸 × DPR
Image::make('logo.png')->decodeSize(w: 80, h: 80)   // 只在要覆盖时写
```

★ **理由**：布局跑完才 `paint`，那时尺寸一定已知 ⇒ 让 `make()` 收尺寸是**提前要一个还没算出来的值**。
这同时消掉了一个 3 位置参数的 `make()`（见 §1）。

## 4. 菜单：内容必须是数据，不能是 View 树

**三个消费者决定了这件事**：自绘菜单、Win32 `HMENU`、macOS `NSMenu`。
后两者**没有 View 概念** ⇒ 只有数据能同时喂三家。

```php
Menu::make([
    MenuItem::item('save', label: '保存', shortcut: 'Primary+S'),
    MenuItem::separator(),
    MenuItem::submenu('recent', label: '最近打开', menu: $recent),
    MenuItem::checkbox('wrap', label: '自动换行', checked: true),
]);
Menu::lazy(fn() => $this->buildMenu());     // 打开时求值一次
```

### 4.1 `lazy` 而不是 `of`

★★ **`of` 是读即订阅（§3），菜单是短暂对象，打开时求值一次。**
理由不是省事：**原生菜单是快照**（`HMENU` 建好不会自己变）。
自绘若实时重建，就会出现"菜单开着时后台同步完成 ⇒ 自绘多一项、原生不变"，
而 **golden 抓不到这种差异**（两个平台各跑各的）。

> **同一个 API 在两种实现下必须看起来一样，否则它就不是一个 API。**

★ 推论：`Menu` 不需要相等性比较——它不在每帧协调路径上，顺带避开"闭包每帧新建 ⇒ 永不相等"。

### 4.2 五条硬规则

| # | 规则 | 违反的症状 |
|---|---|---|
| 1 | **`id` 整棵菜单（含子菜单）唯一** | 两级同名 ⇒ 回调只有一个参数，无法区分（`E-MENU-ID-DUP`） |
| 2 | **`checked` 不自动翻转** | 自动翻转 = 双向绑定，与受控纪律冲突 |
| 3 | **`shortcut` 只是标签，不注册** | 两处注册 = 双分发源（菜单点一次、快捷键又一次） |
| 4 | **无界列表不进菜单** | 原生菜单无虚拟化 ⇒ 要长列表就 `custom` 一个列表控件，并接受它不能给托盘用 |
| 5 | **`custom` 必须显式构造** | 让"这个菜单能不能给托盘用"变成可判定；`flatten()` 遇到 custom 报 `E-MENU-NATIVE`，**不静默跳过** |

★ 第 5 条的"不静默跳过"是重点：静默跳过的后果是**托盘少一项，发布后才发现**。

### 4.3 能力边界

| 项类型 | 自绘 | 原生（HMENU / NSMenu） |
|---|---|---|
| `item` / `separator` / `submenu` | ✓ | ✓ |
| `checkbox` / `radio` / `header` | ✓ | ✓ |
| **`custom`（任意控件）** | ✓ | **✗** |

★ **托盘菜单必须原生**（可能出现在任务栏角落，没有 Surface 承载自绘菜单）
⇒ 给托盘的菜单 API **只能收声明式数组**，这是类型层面的约束，不是文档提醒。

## 5. 规则必须配 lint

一条 API 规则如果没有 lint，它就只是建议。三条 fixture（`E-API-SHAPE`）：

| 规则 | 检查 | 报什么 |
|---|---|---|
| `make()` 至多 1 个位置实参 | 数位置实参个数 | `E-API-SHAPE make() 收了 2 个位置实参` |
| 第一个实参之后必须全命名 | 扫调用参数列表 | `E-API-SHAPE 第 2 个实参缺参数名` |
| 响应式入口的类型 | `of` 收闭包 / `value` 收 `Cell` | `E-API-SHAPE value() 收到闭包` |

★ lint 只管**框架自己的 30 个类**。业务组件不管：
`TaskRow::__construct(...)` 是应用自己的构造函数，爱怎么写怎么写——
**框架管得住自己，管不住用户的一万个类。**

---

## 6. 方法：规则怎么被验证

| 做法 | 为什么 |
|---|---|
| 把文档里所有示例抽出来回代 | 规则与示例打架时，先怀疑规则 |
| 规则写成谓词（能数、能匹配） | "尽量""优先"这类词无法执行 |
| 一条规则配一条 lint | 否则它会在三个月内静默失效 |
| 例外必须写"为什么" | 不写理由的例外会扩散成常态 |

★ 本册第 2 节的规则就是被自己的示例证伪过一次才定稿的。
**这不是瑕疵，这是唯一可行的定规则方式**——先写，再回代，再改。
