## 4. 逐项分析

---

### D-01 动作缝（命令）的机制

**问题本质**：`handleCommand(string $name, int $arg = 0): bool` 全篇只出现 **1 次**（§11.4 的样例），而方案**同时要了两件互相排斥的事**：

- §11.4 裁决 2 要"**跨树复用**、一个 handler 管一列"（⇒ 需要**应用级注册表**）
- §11.4 样例要"**页面就近接管**"、改的是 `$this->result`（⇒ 需要**树内 handler**）

而注册在哪 / 谁派发 / 找不到 handler 怎么办 / 多个 handler 谁先 / `arg` 为什么只能是 `int` —— **全部未定义**。更微妙的是：`handleCommand(): bool` 这个**返回值本身**暗示了"冒泡链"，但方案从没解释过 `bool` 是什么意思。

**争议度：中**（方案自己已经写了一半，只是没接上）

#### 方案

**A. 只有页面 handler（最简）**
命令必须由"命中 Element 的 `State`"实现 `handleCommand`；跨树复用靠继承基类或每个页面各写一遍。

**B. 只有应用级 `CommandRouter`**
组合根注册 `->on('user.del', UserCommands::class)`；控件 `command()` 只发字符串。

**C. 冒泡链 + 应用级注册表（两段）**
```
① 命中 Element 的 State::handleCommand($name, $arg)   → 返回 true ⇒ 停止冒泡
② 祖先 State（直到 Root）                              → 同上
③ CommandRouter（应用级注册表）                        → 同上
④ 都没有 ⇒ Errors::report（Diagnostic 级）—— 不静默
```

#### 得失对照

| 维度 | A 只有页面 handler | B 只有注册表 | **C 冒泡链 + 注册表** |
|------|------------------|-------------|---------------------|
| 满足 §11.4 裁决 2（跨树复用） | ❌ 做不到 | ✅ | ✅ |
| 满足 §11.4 样例（页面就近接管） | ✅ | ❌ 页面私有命令必须提到应用级 | ✅ |
| `bool` 返回值 | ❌ 变成死代码（没人接） | ❌ 变成死代码（没有链） | ✅ **"我处理了，停止冒泡"** —— 方案写出来的 `bool` 在这里才成立 |
| 新概念数 | **0** | 2（`CommandRouter` + handler 类型） | 3（`CommandRouter` + `CommandHandler` + `CommandArg`） |
| 可枚举 / 可单测 | ❌ 分散在 N 个页面 | ✅ 注册表可列举 | ✅ 同上 + 页面局部可单测 |
| lint（死命令 R5） | 树内可达性（= GUI 仓现成能力） | 注册表 vs 控件发出的命令集 | **两张表都要查**（树内 + 注册表） |
| 页面独立预览（§12.2 附带收益） | ✅ | ❌ 预览时命令跑不了 | ✅ 局部命令照跑；应用级命令退化为 Diagnostic |
| 与 §9.1 路由链的关系 | 无 | 无 | ✅ **同族复用**（"从命中点向上找接管者"正是 §9.1 键盘/指针路由的形态） |
| `arg` 传 string id | ❌ `int $arg` | ❌ 同 | ✅ `CommandArg` 值对象 |
| 落地成本 | 最低 | 中 | 中（1 接口 + 1 值对象 + 派发循环） |

#### 参考推荐：**C**

四条理由：
1. **方案自己已经要了两件互斥的事**（裁决 2 的跨树复用 + 样例的就近接管）⇒ 只有"链"能同时满足。选 A 或 B 等于**放弃方案已经写下的一条裁决**。
2. **`bool` 返回值是方案已经写出来的东西**。A/B 都让它成为死代码 —— 而 §10.2 第 4 条明写"**声明了但从未被读的 API 比不提供更糟**"（A1 反模式）。⇒ 选 A/B 会让方案**自己犯自己的反模式**。
3. **链的两段都是既有机制的复用**：第 ① ② 段是 §9.1 路由链的同族（同一形态，不同对象）；第 ③ 段是 §12.1 第 5 条"跨树引用"的落地。**不是新发明**。
4. **它顺带解决 `arg` 的类型问题**：`CommandArg`（值对象）取代裸 `int` —— 现在 `arg(1)` 传不了 string id，而 §11.5 的样例 `->arg($u->id)` 一旦 id 变成 UUID 就崩。

#### 待你补裁的子问题

**handler 用闭包还是类？** 推荐**类**（`interface CommandHandler { public function handle(string $name, CommandArg $arg): bool; }`）。理由：闭包**不可枚举**（devtools 列不出来）、**不可单测**（§16.1 的"死命令 lint"需要静态可达性）、且与 §10.2 第 6 条"糖只转发"的精神一致（注册表是数据，不是闭包堆）。

#### 落地成本

- 新公共类型 2 个：`CommandRouter`（`Drift\Routing` 或 `Drift\State`）、`CommandArg` + `CommandHandler`（`Drift\Widget` 或 `Drift\State`）⇒ **要进 §10.1 的公共面**（与 D-02 有交互）
- §11.4 的 `handleCommand(string, int)` 签名要改 ⇒ 只有 1 处样例
- lint 扩一条：`CommandRouter` 注册的命令集 vs 全树 `command()` 发出的命令集（双向：死命令 + 死注册）

### D-02 公共面：按命名空间还是按标注

> **★ 本项在用户提示后做了第二轮深挖**（"这个框架应该是一个 SDK / composer 包 / 跟着项目一起编译" + "还可以看一下 `-m lib` 模式"）。
> 结论比第一轮**更强**：不只是"换成标注"，而是**三个面分开 + 两种分发形态**。详见 D-02.b / **D-02.d（GUI 仓实证 + 上游已修复）**。

#### D-02.a 问题本质

§10.1 定义公共面 = 5 个命名空间 + lint 判据"`apps/` 不得引用任何 `@internal` 类型"。但方案**自己给出的必写文件**全在清单之外：

```php
// §5.1：apps/hello/bin/bootstrap-win32.php —— 组合根
$app = new HelloApp(new \Drift\Platform\Win32\Win32Platform());   // ← 不在 5 个之内
// §4.5：apps/<app>/src/<App>Application.php
class HelloApp extends Application { ... }                        // ← Drift\App 不在
// §12.2：Root 里
->center(PageHost::make()->source(...)->table($this->routeTable())) // ← Drift\Routing 不在
```

⇒ **按方案自己的 lint，样板代码第一行就违规**。而且这不是"清单少写几个"——**组合根必须引用平台实现**，这是 §5.1"平台类名只出现在组合根"的必然结果。

★ 更根本的证据：§10.1 已经为 `seal()` 开了一个**豁免**（"`@internal` 判定以**标注**为准，不以命名空间为准"）—— 说明"命名空间 = 可见性"这个模型**已经被方案自己打破过一次**。

**争议度：中**（改一行也能跑，但会反复撞）

#### D-02.b ★ 深挖：SDK 模型下其实有"三个面"

用户点出前提："**框架是一个 SDK，业务引用它，或作为 composer 包在当前项目中一起编译**"。这个前提下必须先把**三件事**拆开 —— 它们**互不重合**，且**各自只有一种可行的表达手段**：

| 面 | 定义 | 唯一可行的表达手段 | 能强制吗 |
|----|------|-----------------|---------|
| **① 物理边界** | 哪些文件属于框架包 | **composer PSR-4 前缀**（`Drift\` → `src/`） | ✅ 工具强制 |
| **② 架构分层** | 包内**谁能依赖谁** | **命名空间 + §4.3 依赖规则 lint** | ✅ lint 强制 |
| **③ 公共契约面** | **承诺不破**的签名 | **`@api` 标注** + `api-surface.json` | ✅ lint 强制 |

**上一版把 ① 当成 ③ 来用。** 这在 PHP 里必然失败：

1. **组合根必须引用平台实现** —— §5.1 的必然结果 ⇒ `Drift\Platform\Win32` **必须**对应用可见。不是"清单漏了"，是**清单这条路本身走不通**。
2. **PHP 没有"包内私有"** —— `@internal` 是**文档约定**，不是语言强制（`internal` 关键字是 **namespace 级**，不是包级）。用户技术上能 `use` 包内**任何** public 类型 ⇒ **"命名空间 = 可见性"在 PHP 里根本不成立**。
3. **方案自己已经为 `seal()` 开了豁免** —— 同一个模型错两次，就该换模型，而不是再补一次清单。

★ 而 **① 和 ② 其实都已经有机制了**：① 是 `composer.json` 的 `autoload.psr-4`；② 是 §4.3 的依赖规则 lint。⇒ §10.1 拿命名空间做第三遍，纯属多余。

#### D-02.c ★★ `-m lib` 模式（用户提示，改变了答案）

`tpc` 有第三种模式 **`-m lib`**（手册 §4；权威细节 `typephp/docs/zh-cn/MIXED_CPP_PHP.md` §3）。**它给"物理隔离"提供了一个编译器强制的机制**，这是第一轮分析里完全没有的。

**实测事实**（读手册 + tpc 源码得出，非推测）：

| 事实 | 出处 |
|------|------|
| 产物 = 自动生成的 `<target>.stub.php`（带 `/** @import-library */`）+ Windows `.dll` + 导入库 `.lib`；Linux `.so` | `MIXED_CPP_PHP.md` §3 · `Translator.php:1010/1017` |
| **库名由 stub 文件名推导**（`drift.stub.php` ⇒ 库 `drift`） | 同上 |
| 消费侧只把 stub 放进 `sources` ⇒ **tpc 自动追加 `linkLibs`**（不用手写 `link-libs`） | `Preprocessor.php:478-480` |
| **stub 是"声明汇总"**：函数体清空、类方法体清空、**property hook 的 `get/set` 保留声明、移除实现**；保留 `TraitUse` / `ClassConst` / `EnumCase` / 属性 | `LibraryImportStubGenerator.php:126-170` |
| **`#[NoExport]`** 排除出公开 ABI；**类注解级联到全部方法**；单个方法可独立标；声明**仍参与本库编译**，只是不加导出修饰 | `MIXED_CPP_PHP.md` §3 |
| `#[NoExport]` **只在根命名空间**（其他命名空间必须 `#[\NoExport]`） | 同上 |
| **`#[Native]` 类不能通过库 stub 导出** ⇒ 必须标 `#[NoExport]` | `LibraryImportStubGenerator.php:107-114` |
| 自动生成的 stub **放宽类型要求**（无类型 ⇒ `php::Var`），而**手写本地 stub 必须显式 ABI 类型** | `Preprocessor.php:1396-1398` |
| **传递导入不会被再导出** ⇒ 若 Drift 的库自己也导入别的库，消费方必须**另外**提供 | `LibraryImportStubGenerator.php:40-42` |
| 库构建仍**需要 PHP 运行时与 PHPX**（`php8ts.lib` 或 `php8.dll`；**`phpx.lib` 链接期 + `phpx.dll` 运行期**）⇒ **不是完全自包含产物** | `Platform/Windows.php:183-230` |

**⇒ 这把"物理隔离"拆成了两套机制，按分发形态选**：

| 层 | 形态 A：源码同编（`-m bin`） | 形态 B：`-m lib` 共享库 |
|----|---------------------------|----------------------|
| **物理隔离**（能不能调到） | ❌ 无 ⇒ 退化为 **lint**（`internal-leak`） | ✅ **`#[NoExport]` + 编译器生成的 `.stub.php`**（**链接期**强制） |
| **契约承诺**（承诺不破） | `@api` + `api-surface.json` | 同左，**且 `api-surface.json` 可从 `.stub.php` 派生** |
| **应用侧 `project.yml`** | 要 Skia include/link 路径 + 全部 `link-libs` | **只加一行 stub** ⇒ **不需要 Skia 工具链** |

★ **形态 B 的最大收益**：应用侧**完全不需要 Skia 头文件与那 20 个 `link-libs`**（全烘进 `.dll`）⇒ §16.4 那份庞大的 `project.yml` 对第三方应用会缩到几乎为空。**这是"框架作为 SDK 交给第三方"唯一现实的形态。**

★ **形态 B 的代价（必须诚实写清）**：
1. **失去跨模块内联** —— `layout()` / `paint()` / `mutate()` 这些**热路径**在同编下能被内联；跨 `.dll` 只剩一次间接调用。**§15.3 实测的 0.92 µs/节点是同编下测的** ⇒ 形态 B 的性能退化**幅度未测** ⏳。
2. **部署变成多文件** —— 单 exe 的"一个文件"优势没了。
3. **版本/CRT 矩阵** —— §16.4 已踩过 `LNK2038`（`/MT` vs `/MD`）⇒ `.dll` 与宿主必须同 CRT、同 PHP 版本。
4. ~~闭包跨 `.dll` 边界未验~~ ⇒ **✅ 已验**（见 D-02.d）。★ 但"跨 `.dll` 的**异步/跨线程**闭包"仍未验。
5. **`#[Native]` 类在库模式下对应用不可见**（硬约束）⇒ 若想用 `#[Native]` 加速热路径对象，形态 B 下应用拿不到。

### D-03 `ForEach` 的 key

**问题本质**：`ForEach` 无 key 约定（`keyBy` 全篇 **0 次**）。按位置 diff ⇒ 删掉第 2 行后，第 3..n 行的 Element **左移继承**前一行的 `State`。对纯 `Text` 无害，但只要行内有**焦点 / 展开 / 滚动 / 编辑中**任一状态，用户就会看到"我删了 A，结果 B 的展开态跑到 C 上了"。

★ **这不是假想**：§12.3 自己把"选中项 / 展开状态 / 编辑中的草稿"列为**必须跨回收存活的 UI 态** —— 说明这些状态确实存在于列表项里。

**争议度：低**（§16.1 已经写了"key 是结构事实 ⇒ 构建期校验"）

#### 方案

**A. 可选 `->keyBy(fn)`**（有则用，无则按位置）

**B. 必填，进 `make()`**
```php
ForEach::make(fn(User $u): int => $u->id)     // key 是必填，不是可选修饰
    ->items($store->rows(), fn(User $u): Widget => ...)
```

**C. B + 给"索引 key"一个短入口**（`ForEach::indexed()` 作为 `make(fn(_,$i)=>$i)` 的纯转发别名）

#### 得失对照

| 维度 | A 可选 | **B 必填** | C 双入口 |
|------|--------|-----------|---------|
| 静默 bug（删除中间项串位） | ❌ **默认就是错的** | ✅ 结构上不可能漏 | ✅ |
| G1 判据（"编译器知道列表项有身份吗？"） | ❌ 不查 | ✅ **知道** —— `fn(User $u)` 的类型就在签名里 | ✅ |
| 与 §16.1 已有裁决的关系 | 弱（只是"能查"） | ✅ **就是那条裁决的落地**（原文"key 唯一 / 稳定 ⇒ 构建期校验（key 是结构事实）"） | ✅ |
| 纯展示列表的样板长度 | 短 | **长一行** | 短（`indexed()`） |
| 能用于字符串数组 `['a','b']` 吗 | ✅ | ⚠️ **不能**（没有 `id`）⇒ 需 `fn($item, int $i): int => $i` 显式声明"用位置当身份" | ✅ |
| 与 §21 A12（糖自造状态路径） | — | — | ⚠️ 两个入口 = 两条路径（但 `indexed()` 是**纯转发**，可接受） |
| 落地成本 | 0 | 小（改 `make()` 签名 + 一处样例） | 小 + 一个别名 |

#### 参考推荐：**B**（必填，且 key 函数的第二参数是 `int $i`）

四条理由：
1. **默认值错了的东西不该有默认值。** A 的致命伤：位置 diff **只在"纯展示 + 无状态"时安全，而这一点无法静态判定** ⇒ 忘了写 = 静默 bug，且**只在删除中间项时才现形**（最难查的一类）。
2. **G1 判据成立**：`fn(User $u)` 的类型就在签名里 ⇒ **编译器知道**列表项有身份 ⇒ 按 §16.1"编译器知道 ⇒ 构建期做"，这该是必填。
3. **它是 §16.1 已有裁决的必然落地**，不是新决定（原文："key 唯一 / 稳定 | 运行期位置匹配 → **构建期校验（key 是结构事实）**"）。
4. **`fn($item, int $i): int => $i` 把"按位置"从默认变成显式选择** ⇒ 静默 bug 消失，纯展示列表只多写 7 个字符。⇒ C 的收益被 B 的这一个参数吃掉大半，**C 可以后加**（纯转发，不破坏 B）。

#### 待你注意的一条限制

`ForEach` 的 item 必须能给出稳定 key ⇒ **`ForEach` 不能直接用于"标量数组"**（`['a','b','c']` 没有 id）。B 的解法是 `fn(string $s, int $i): int => $i`（显式）。若你觉得这个限制不可接受，那就退到 C（给 `indexed()` 一个短入口）。

### D-04 三态：string 约定 vs backed enum

**问题本质**：§11.5 用 `private string $status = 'idle'` + `match(...){ 'loading'=>…, 'error'=>…, default=>… }`，与 §12.1 第 2 条**自己的建议**矛盾：

> ★ `match` 编译成跳转表；需要枚举时换 backed enum + **无 `default`** 的 `match`（漏一支 = `UnhandledMatchError`）。

而且 `default => rows` 意味着**任何未来新增的状态都会静默显示数据行**（正是 §21 A7"状态语义只写进某个 else 分支"）。

**争议度：低**（方案自己的 §12.1 已经给了答案）

#### 方案

**A. 保持 string**

**B. backed enum + 无 `default` 的 `match`**
```php
enum LoadStatus: int { case Idle = 0; case Loading = 1; case Ready = 2; case Error = 3; }
```

**C. enum + `default` 兜底**（折中）

#### 得失对照

| 维度 | A string | **B enum + 无 default** | C enum + 兜底 |
|------|----------|------------------------|--------------|
| 拼错状态名 | ❌ **静默**（落进 `default` ⇒ 显示数据行） | ✅ 编译错误 | ✅ |
| 新增一个状态 | ❌ 静默走 `default` | ✅ **`UnhandledMatchError`**（响亮失败） | ❌ 静默走 `default`（**= A7 反模式**） |
| 与 §12.1 第 2 条 | ❌ 违反自己的建议 | ✅ 一致 | ❌ |
| 与 §15.2 纪律 4（哨兵三档定则） | ❌（枚举语义 ⇒ 应加显式 case） | ✅ | ⚠️ |
| AOT 可用性 | ✅ | ✅ **§2.1 已探针验证 backed enum 可用** | ✅ |
| 样板长度 | 最短 | +1 行（enum 声明） | +1 行 |
| Store 的依赖 | 零 | 引一个 enum（**建议业务层自己定义**，不是 `Drift\State`） | 同 |

#### 参考推荐：**B**，且 **enum 定义在业务层**（`SignupForm` 旁边的 `LoadStatus`）

三条理由：
1. **三态是"语义"，不是"字符串"** —— §15.2 纪律 4"哨兵三档定则"的原话："枚举语义 ⇒ 加显式 enum case"。三态正是枚举语义。
2. **无 `default` 的 `match` 是 G2 的正面样板**：漏一支立刻响，而不是静默显示数据行。
3. **enum 归业务层**（不是 `Drift\State`）：三态的**取值集合**是业务知识（有的 Store 只有 idle/ready 两态），把它塞进框架的公共面等于**用框架的枚举约束业务的表达**。

#### 成本

- §11.5 的样板改 3 行（Store 加 enum、`status()` 返回类型改、`match` 去掉 `default`）
- **与 D-05 耦合**：若采用 `select()`，`match` 的输入就是 `select` 的返回值 ⇒ **建议 D-03 / D-04 / D-05 一起改 §11.5 的样板**（一次改完，不反复动同一段）

### D-05 订阅粒度：`select()`

**问题本质**：订阅粒度 = **整个 `Subject`**。一个 Store 有 10 个字段 + 10 个 `SubjectBuilder` ⇒ 任一字段变，10 个全重建。

方案靠 §12.2 的"每个切片自己是一个 Subject"（`statusLine()` / `currentPage()`）绕 —— 但那让 **`Store` 必须暴露 N 个 `Subject`**，而且**隐含依赖"每次调用返回同一个实例"**（这一点方案没写、也无法 lint）。

★ 所以现状**不是"没做"，而是"做了个坏版本"**（= §18 从 Flutter 学来的要避开的 "provider soup"：业务反向依赖 UI 的关切）。

**争议度：中高**（决定 Store 形态，越晚改越贵）

#### 方案

**A. 不做**（保持现状）

**B. 每个切片一个 `Subject`**（`Store` 显式暴露 N 个 Subject，即 §12.2 的形态）

**C. `SubjectBuilder::select()`**
```php
SubjectBuilder::make($store)
    ->select(fn(UserStore $s): array => $s->rows())        // 只关心这一个切片
    ->builder(fn(array $rows): Widget => ...)
```

#### 得失对照

| 维度 | A 不做 | B 每切片一个 Subject | **C `select()`** |
|------|--------|---------------------|-----------------|
| 订阅粒度 | ❌ 整个 Subject | ✅ 细 | ✅ 细 |
| `Store` 是否要暴露 N 个 Subject | 不用（但**现状已经在用**） | ❌ **要**（业务反向依赖 UI 关切） | ✅ **不用**（纯函数式） |
| 实例身份问题 | — | ❌ 依赖"同一实例"（不可 lint） | ✅ **不存在** |
| 相等门控 | ❌ 无 | ✅（各 Subject 自己门控） | ✅ **落在 `select` 返回值上**（复用 §11.3 RT-4 的 `===`，不引第二套） |
| 可 lint（G1） | ❌ | ⚠️ 弱 | ✅ **`select` 闭包里的属性集 = 该订阅者真正依赖的字段集 ⇒ 编译期可生成依赖清单** |
| 与 §16.1"远期编译期推导" | 无关 | 无关 | ✅ **就是它的第一步** |
| 新概念 | 0 | 0（复用 Subject） | 1（`select` 的语义 + 返回值相等规则） |
| 每帧成本 | — | — | 一次闭包调用（**可忽略**） |
| `builder` 签名兼容性 | — | — | ⚠️ 需要两个变体（`builder(fn(): Widget)` / `builder(fn($v): Widget)`） |
| 消灭 §12.2 的 `statusLine()` 歧义 | ❌ | ❌ | ✅ |

#### 参考推荐：**C**

四条理由：
1. **现状不是 A，是 B 的坏版本** —— §12.2 的样板已经在用 `statusLine()`（= B），而 B 的两个硬伤（业务反向依赖 UI、实例身份不可 lint）**已经在方案里现形**。⇒ 这不是"要不要新增"，而是"要不要把已有的坏形态换成好形态"。
2. **`select` 的相等门控复用 RT-4**（`===`），不引入第二套相等机制 —— 与 §11.3"四件事"的口径一致。
3. **lint 收益是独有的**：`select` 闭包出现的属性集合 = 依赖清单 ⇒ **编译期可推导**。这正是 §16.1 里那条"哪个 State 变了 ⇒ 更新哪棵子树 | 运行期（订阅点下移）+ **远期编译期推导（spike）**"的入口。B/A 都拿不到。
4. **失的三条都可控**：① 相等语义写清（**`select` 必须返回标量或不可变值对象，否则门控失效** —— 数组 `===` 是逐元素严格比较，对象是同一实例）；② 闭包成本可忽略（一次函数调用/帧）；③ `builder` 用两个重载解决。

#### 必须写进契约的两句话

- **`select` 的返回值必须是标量或不可变值对象**（否则 `===` 门控失效，退化成"每次都不等"⇒ 每帧重建）。
- **`select` 闭包不得有副作用**（它每帧都会跑，且可能被 lint 用来推导依赖）。

### D-06 表单绑定：`Bound` + property hooks

**问题本质**：§11.4 每个字段要写三件事 ⇒ **字段名出现 3 次**：

```php
TextField::make('name')                                    // ① 字符串键
    ->value((string) $form->get('name'))                   // ② 字符串键 + 显式转换
    ->onChanged(fn(string $v) => $form->set('name', $v));  // ③ 字符串键 + 手写闭包
```

**10 个字段 = 30 个字符串字面量**（每个都是 typo ⇒ 静默失败）+ 10 个闭包 + 10 次 `(string)` 转换。而 §2.1 明写 **property hooks 可用**且是"**受控属性的物理基础**"—— **能力在手却没用**。

★ **本决策的真正难点**：撞上 §10.2 第 6 条 —— "**糖只转发**：删掉全部糖，框架契约与测试原样完整"。而 `bind()` 引入"订阅"这一**新行为**，按现纪律它**不允许存在**。

**争议度：中**（收益最大，但撞纪律）

#### 方案

**A. 不做**（保持手写）

**B. 只上 property hooks**（不做 `Bound`）
```php
final class SignupForm extends Subject {
    public string $name = '' { set (string $v) { $this->name = $v; $this->notifyChanged(); } }
}
// 页面：字段名从"字符串键"变"属性"
TextField::make('name')->value($form->name)->onChanged(fn(string $v) => $form->name = $v);
```

**C. B + `Bound` 订阅控件**
```php
TextField::bind($form->name)->label('姓名')     // 一行取代三件事
// 等价展开（契约层，糖删掉后仍在）：
Bound::make($form->name, fn(string $v): Widget =>
    TextField::make('name')->label('姓名')->value($v)->onChanged(fn(string $x) => $form->name = $x))
```

**D. C + 把 `bind()` 定位成 `Bound` 的变体工厂**（纪律不动）
`Bound` 进 `Drift\State`（与 `SubjectBuilder` 同族，"专职订阅控件"）；`TextField::bind($cell)` = `Bound::make($cell, fn($v) => TextField::make(...))` 的**薄壳别名** ⇒ 按 §15.4"变体工厂 = `make()` 的薄壳别名"的定义，它**是**纯转发（只是转发到 `Bound` 而不是 `TextField`）。

#### 得失对照

| 维度 | A 手写 | B 只上 hooks | C + `Bound` | **D + `Bound` 且纪律不动** |
|------|--------|-------------|-------------|--------------------------|
| 字段名出现次数（单字段） | **3** | 2（`'name'` + `$form->name`） | **1** | **1** |
| 10 字段的字符串字面量 | **30** | 10 | 0（全变属性） | 0 |
| 手写闭包数（10 字段） | 10 | 10 | **0** | 0 |
| `(string)` 转换（10 字段） | 10 | **0**（属性已带类型） | 0 | 0 |
| 拼错字段名 | ❌ 静默 | ✅ 编译错误 | ✅ | ✅ |
| 还要记得包 `SubjectBuilder` | ❌ **要**（A-P0-3a 的根因） | ❌ 要 | ✅ **不用**（`Bound` 自带订阅） | ✅ |
| 撞 §10.2 第 6 条 | — | ✅ **不撞** | ❌ **撞**（引入新行为） | ✅ **不撞**（变体工厂=纯转发） |
| 新公共类型 | 0 | 0 | 1（`Bound`） | 1（`Bound`） |
| 依赖 D-10（"专职订阅控件"判据） | — | — | ✅ 需要 | ✅ 需要 |
| 落地成本 | 0 | **极低**（只改 Store 写法） | 中 | 中 |

#### 参考推荐：**D，分两步落地**

**第一步（M2，必做，零风险）—— 上 property hooks（方案 B）**
这条**其实不需要裁决**：§2.1 已经证明 property hooks 可用，且方案自己称它是"受控属性的物理基础"——**方案却没用它**，属于"能力在手却没用"。收益：字段名从字符串变属性（拼错 = 编译错误）、消掉 `get/set` 两个方法、`(string)` 转换消失。**成本：只改 Store 的写法，框架零改动。**

**第二步（M3，随 D-01 动作缝一起）—— 上 `Bound` + `bind()`（方案 D）**
四条理由：
1. **收益是心智负担的最大单点**：§B.4 的 12 个概念里，"`SubjectBuilder` 必须包在哪一层"这一条（3 个"没有使用时机"的概念之一）**直接消失**。
2. **纪律冲突有"不修改纪律"的解法**（D）⇒ 不需要"为了糖改纪律"。这很重要：§10.2 第 6 条是**方案里最硬的一条纪律**（"删掉全部糖，框架契约与测试原样完整"），为它开一个例外会削弱它。
3. **它结构性地消灭了 A-P0-3a**：§11.4 样板缺订阅的根因是"要记得包 `SubjectBuilder`"，而 `Bound` **自带订阅** ⇒ 这个错误不再可能发生。
4. **`Bound` 与 `SubjectBuilder` 同族**（都是"专职订阅控件"）⇒ 复用 §11.3 的订阅袋 / 异常隔离 / 相等门控四件事，**不新增运行期机制**。

#### 待你补裁的子问题

**`TextField::make('name')` 的第一个参数（字段名）在 `bind()` 形态下怎么给？**

| 选项 | 写法 | 得失 |
|------|------|------|
| ① | `TextField::bind($form->name)->name('name')` | 字段名只在需要时给（无障碍/测试定位）；**推荐** |
| ② | `TextField::bind('name', $form->name)` | 保留现状顺序，但字段名仍 2 次 ⇒ typo 风险回来 |
| ③ | 从 `$form->name` 的**属性名**自动推导（`ReflectionProperty::getName()`） | 最优雅，但 **AOT 下能否反射属性名要探针** ⏳ |

### D-07 派生值（computed）的落点

**问题本质**：`fullName = first + ' ' + last` 放哪？

- 放 Store getter ⇒ **每帧重算**，且**订阅者无法只跟它**（订阅整个 Store ⇒ 改了 `first` 会重建所有订阅者，包括只关心 `fullName` 的）
- 放页面 `build()` ⇒ 每帧重算

§18 明说借了 Vue 的"计算缓存 + 版本跳过（**形状**）"，但 §11 里**没有这个原语**。

**争议度：低**

#### 方案

**A. 不做原语，Store 里写普通 getter**

**B. Store 里的"缓存 getter"**（自己写脏标记）
```php
private ?string $fullNameCache = null;
public function fullName(): string {
    return $this->fullNameCache ??= $this->first . ' ' . $this->last;
}
// 改 first/last 时：$this->fullNameCache = null;
```

**C. `Computed` 原语**（进 `Drift\State`，与 `Cell` 同族；版本跳过）

**D. 依赖编译器推导**（§11.6 的"长期方向"，Svelte 路线）

#### 得失对照

| 维度 | A 普通 getter | **B 缓存 getter + lint** | C `Computed` 原语 | D 编译器推导 |
|------|--------------|------------------------|------------------|-------------|
| 每帧重算 | ❌ 是 | ✅ 否 | ✅ 否 | ✅ 否 |
| 手写脏标记 | — | ⚠️ **要**（忘了清 = 静默旧值，**正是 A9 形态**） | ✅ 不用 | ✅ 不用 |
| 可单独订阅 | ❌ | ❌（但可由 D-05 的 `select` 缓解） | ✅ | ✅ |
| 新原语 | 0 | 0 | **1 + 依赖追踪机制** | 0 |
| 与 §11.6"不做运行期自动追踪" | ✅ 不冲突 | ✅ 不冲突 | ⚠️ **张力**：不带自动追踪 ⇒ 要**手写依赖清单**，而"手写依赖清单"与 B 的"手写脏标记"**是同一类风险**（忘了 = 静默旧值），C 还多一个原语 | ✅ 就是 §11.6 的方向，但**方案自己说"以 spike + kill criteria 推进，不承诺"** |
| 可被 lint 守 | — | ✅ **可以**（"Store 里有 `??=` 缓存字段 ⇒ 所有会改依赖字段的方法里必须有清缓存语句"；字段集编译期已知） | ⚠️ 难 | — |
| 落地成本 | 0 | 极小 | 大 | 很大 |

#### 参考推荐：**B（现在）+ D-05 的 `select`（组合）**，C 留作"有实测痛点再说"

四条理由：
1. **§11.6 明确不做运行期自动依赖追踪** ⇒ C 若不带自动追踪，就要**手写依赖清单**。而"手写依赖清单"与 B 的"手写脏标记"**是同一类风险**（忘了 = 静默旧值），但 C 多一个原语 + 一套版本号机制。⇒ **C 的收益不抵它的成本**，除非能自动追踪。
2. **B 的成本可控且可被 lint 守**：`??=` 一行 + 清缓存一行；lint 判据是静态可判的（Store 的字段集是编译期已知的，`??=` 的缓存字段也是）。★ 这条 lint 要**新增**并记进 §16.6.3。
3. **有了 D-05 的 `select`，C 更不必要**：`select(fn($s) => $s->fullName())` ⇒ 门控落在**返回值**上 ⇒ `fullName` 没变就不重建。⇒ C 的"可单独订阅"收益被 `select` 拿走，C 只剩"省一次重算"，而 B 已经省了。
4. **诚实边界**：B 只解决"重算"，不解决"订阅者只跟它"—— 后者交给 `select`。

#### 落地成本

- Store 写法（业务层）
- `drift-lint` 新增一条：**缓存字段清空检查**（`Store` 里出现 `??=` 赋值的属性 ⇒ 所有会修改其依赖字段的方法里必须有 `$this->xxx = null`）

### D-08 `notifyChanged` 的线程断言

**问题本质**：§5.3 第 3 条只断言 `setState()` / 树变更在非 UI 线程调用 ⇒ Fatal。但线程池（§17.2.2）落地后，**最可能踩的路径不是"直接改树"，而是"在 worker 里改 Store 然后 notify"**：

```
worker 线程：$store->setRows($data); $store->notifyChanged();
   ⇒ 订阅者回调在 worker 线程上执行 ⇒ setState ⇒ 树变更 ⇒ 数据竞争
```

`notifyChanged()` 本身不是"树变更"，所以按现口径**不触发断言**。而探针 E 已经证明线程池**物理可行** ⇒ M4 就会有人这么写。

**争议度：低**

#### 方案

**A. 不加**（只守 `setState`）

**B. 断言点在 `Subject::notifyChanged()` 入口**（"通知必须在 UI 线程发出"）

**C. B + 让 `notifyChanged()` 自动 marshal**（worker 线程调用时自动 post 到 UI 线程，不报错）

#### 得失对照

| 维度 | A 只守 `setState` | **B + `notifyChanged` 入口** | C 自动 marshal |
|------|------------------|----------------------------|---------------|
| 错误在**发出点**响（栈干净） | ❌ 在订阅者回调里响（栈里看不到"哪个 notify 引起的"） | ✅ | — |
| 覆盖**非控件订阅者**（纯业务订阅者不会 `setState`） | ❌ **真漏口**（worker 上跑业务回调，无任何断言，而业务回调可能改别的 Store ⇒ 静默竞争） | ✅ | ✅ |
| 单线程阶段（M1–M3）的成本 | 0 | 一次整数比较（**可忽略**） | — |
| 与 §11.1"业务层零 GUI 依赖" | ✅ | ✅ **可兼容**：`Subject` 只依赖 `Drift\State` 内部的 `ThreadAffinity::assertUi()`，业务层仍不知道 GUI 是什么 | ✅ |
| 破坏同步语义 / 顺序确定性 | — | — | ❌ **会**：`notifyChanged()` 从同步变"可能异步"，而 §11.5 的"帧末一次重建"依赖同步（两次 notify 同栈 ⇒ 一次重建）；marshal 后**顺序不保证** |
| 与 G2 / G3 | ✅ | ✅ | ❌ **违反 G2**（本该报错的静默修好）+ G3（顺序不确定） |

#### 参考推荐：**B**

四条理由：
1. **成本可忽略**（一次整数比较），而 **A 有一个真漏口**：非控件订阅者在 worker 线程上跑，**无任何断言**。
2. **"错误在发出点响"**：栈干净 —— 一眼看到"谁在 worker 里 notify"，而不是在订阅者回调的深处。
3. **与 §11.1 的"业务层零 GUI 依赖"可兼容**：`Subject` 依赖的是 `Drift\State` 内部的线程亲和检查器（一个静态方法 + 一个缓存的 `int` tid），**不是 `Platform`**。业务层仍然不知道 GUI 是什么。
4. **C 虽然对开发者最友好，但破坏同步语义与顺序确定性** ⇒ 与 G3 / G2 冲突 ⇒ **不做**（它把"线程错用"从响亮错误变成隐式行为，代价是顺序不确定）。

#### 落地时机

**与 M4 的线程池同时落地**（M1–M3 单线程，B 永远成立 ⇒ 是纯开销）。⇒ **可以先批、后实现。**

#### 与未验项的关系

与 §17.2.2 的"**闭包跨线程调用未验**"（⏳）有关：若闭包跨线程调用不可行，则"worker 里 notify"这条路本身走不通，B 的优先级降低。⇒ 但 **B 的成本太低，仍然建议批**（先验后用，不亏）。

### D-09 反模式 A16 + lint：`build()` 里读 Subject 但不在订阅者内

**问题本质**：`build()` 里读了 Subject 的值、但该子树**不在任何订阅者内** ⇒ **永远不更新，且不报错**（最难查的一类）。

方案只在 `Root` 上加了 lint 判据（§12.2："`Root` 的 `build()` 里出现 `$store->某方法()` 形态的取值调用 = 违规"），**页面级没有判据**，反模式表里也没有对应条目。

★ 这是 §21 A4（build 期订阅）的**镜像反模式**：A4 是"订了但订错时机"，A16 是"该订没订"。**两个都要有。**

**争议度：低**

#### 方案

**A. 只加反模式条目 A16，不加 lint**

**B. 加 A16 + 页面级 lint**（把 §12.2 的 Root 级判据**推广到全部 `build()`**）

**C. B + 运行期兜底**（`build()` 期记录"读了哪些 Subject"，帧末若发现"读过但无订阅者" ⇒ `Errors::report`）

#### 得失对照

| 维度 | A 只加条目 | **B 加条目 + 页面级 lint** | C + 运行期兜底 |
|------|-----------|--------------------------|---------------|
| 抓到静默 bug | ❌ 反模式表是给人看的，静默 bug 是给机器查的（G1） | ✅ | ✅ |
| G1 判据（编译器知道吗？） | — | ✅ **知道** —— `$this->store` 的声明类型是 `UserStore extends Subject`，编译期就有 | ✅ |
| 误报风险 | — | ⚠️ 要判"是否位于订阅控件内" ⇒ 需**树结构分析**（`drift-lint` **已有能力**：GUI 仓的 R1/R2 就是父子关系分析） | 无 |
| 运行期成本 | 0 | **0** | ❌ 每次读 Subject 要记账 |
| 与 §11.6"不做运行期自动追踪" | ✅ | ✅ | ⚠️ **张力**（虽目的不同：§11.6 是"用它刷新"，C 是"用它报错"，但机制是同一套） |
| 落地成本 | 1 行 | 1 条 lint 规则（依赖 D-10 的判据） | 中 |

#### 参考推荐：**B**（加 A16 + 页面级 lint），**C 作为 M3 的 dev-only 可选增强**（`debug` 构建开、release 关）

三条理由：
1. **G1 判据成立**：类型在编译期就有 ⇒ 该在构建期查。
2. **`drift-lint` 已有树结构分析能力**（R1 `flex-parent` / R2 `positioned-parent` 就是父子关系分析）⇒ **不需要新机制**。
3. **C 与 §11.6 有张力，且是运行期成本** ⇒ 只该在 dev 构建里做（而且 C 可以做得便宜：`Subject` 加一个 `int $readCount`，`build()` 前后 diff ⇒ **只加计数，不做依赖图**）。

#### 待写进反模式表的原文

> **A16 | `build()` 里读 Subject 的值，但该子树不在任何订阅者内 ⇒ 静默不更新**
> 后果：改了数据界面不动，且不报错（最难查的一类）
> 正确做法：把读值的那层包进 `SubjectBuilder` / `Bound`（**`Bound` 自带订阅，见 D-06**）
> **lint**：`build()` 体内出现对 `Subject` 类型字段的方法调用 ⇒ 该 `build()` 必须是订阅控件（D-10 的判据）或位于订阅控件内

### D-11 `DisplayList` 是否总是录制

**问题本质**：§7.2 第 2 条说"`paint()` 的产物**不是**'立即画到屏上'，**而是**录制成命令序列，由 surface 执行"；但 §7.2 第 1 条又把 `SkiaCanvas` 标为"**生产路径**（转发 Skia 桥接、直接画到离屏 bitmap）"，§7.3 说 M1 是"Skia CPU 光栅 + 位块传送"。**两者不能同时为真。**

若**只在 dev / golden 录制** ⇒ **golden 与生产走两条路** —— 而 §20 第 1 条"量具双向自检"要防的正是这个。

**争议度：中**

#### 方案

**A. 总是录制**（生产也走 `DisplayList`；`SkiaCanvas` 变成**回放器**）

**B. 只在 dev / golden 录制**

**C. 总是录制 + 一个关闭开关**（`DRIFT_NO_DISPLAYLIST`）

#### 得失对照

| 维度 | **A 总是录制** | B 只 dev 录制 | C 总是 + 开关 |
|------|--------------|--------------|--------------|
| golden 与生产同一条路（§20 第 1 条） | ✅ | ❌ **两条路** ⇒ golden 过 ≠ 生产对 | ❌（开关一开就等价于 B，还多一个配置面） |
| §14.1 第 2 条"渲染是纯函数 ⇒ 录制成 DisplayList" | ✅ 生产上也成立 | ❌ 生产上**无法验证**（没录制就没法比对） | ⚠️ |
| 每帧成本 | ⚠️ 多一次间接（录制 + 回放 = 两遍遍历） | ✅ 0 | ⚠️ |
| 缓冲复用（零分配）后成本 | **可控**（复用同一块缓冲） | — | — |
| 为将来铺路（脏矩形 / 重放 / 远程 Inspector / 多线程光栅） | ✅ 免费 | ❌ 要做时得改生产路径 | ⚠️ |
| 与 §18 的"每帧全画"事实 | ✅ 一致（本来就没有"跳过绘制"的机会 ⇒ DisplayList 只是把"直接画"变"先记再画"） | — | — |
| 量级 | 一条命令 ~16–32 字节，一帧几千条 ⇒ 几十 KB/帧（**可复用同一块缓冲**） | — | — |

#### 参考推荐：**A（总是录制）**，并把"**缓冲复用（每帧零分配）**"写成契约

三条理由：
1. **§14.1 第 2 条已经承诺**"渲染是纯函数 ⇒ 录制成 `DisplayList` ⇒ 可重放、可 golden 比对" —— **只在 dev 录制让这条承诺在生产上不成立**。
2. **§20 第 1 条"量具双向自检"的核心就是"量具与生产走同一条路"** —— B 直接违背它。
3. **成本可控**：§18 已记 GUI 仓的教训是"**每帧全画**"（不取 Flutter 的 `shouldRepaint`，"本框架每帧全画"）⇒ 本来就没有"跳过绘制"的优化可损失；`DisplayList` 只是把"直接画"变成"先记录再画"，**多出的成本是内存 + 一次函数调用转发**，缓冲复用后为零分配。
4. **与 §7.3 的分期不冲突**：M1 可以"录制 + 立即回放"（`RecordingCanvas` → `DisplayList` → `SkiaCanvas` 回放），M5 再加脏矩形按需重放。

#### 连带要改的措辞

§7.2 第 1 条的"`SkiaCanvas` —— **生产路径**"要改成"**回放器**（`DisplayList` 的执行后端）"，把"生产路径"这个标签交给 `RecordingCanvas`。
