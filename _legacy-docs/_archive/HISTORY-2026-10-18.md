**三条探针纪律**（探针 E 沉淀，复用价值高）：

1. **worker 用自旋不用 `sleep`** —— `sleep` 会让"主线程其实被阻塞"伪装成通过。
2. **两边各放一个进度计**，都 > 0 才算并发成立。
3. **输出落文件、每行一次 open/write/close** —— 后面有一步会掀掉进程，前面证据必须已在盘上。

★ **探针必须测量"设计的真实形态"**（F2/F3 的根因）：测简化替身会得出方向相反的结论。

## 4. 可复用手法：假编译器拿生成物

只想要代码生成、不想要真编译时：

```bash
mkdir -p /tmp/fakecl
printf '#!/bin/bash\nexit 0\n' > /tmp/fakecl/cl.exe      # ★ Windows 下必须有 .exe 后缀
printf '#!/bin/bash\nexit 0\n' > /tmp/fakecl/link.exe
PATH=/tmp/fakecl:$PATH \
PHPX_HOME='D:/TypePHP/.phpx-dllhost' \
PHPRC='D:/TypePHP/typephp-windows-x64' \
  tpc project.yml -m lib
# 编译"失败"（假编译器不产 .obj），但 build/ 下 .cc 已生成 ⇒ 拿到明文产物可 diff / grep
```

- **不需要真编译器、不需要提权、秒级。**
- `tpc` 在 `Translator->prepare()` 阶段就因找不到 `cl` 而 Fatal ⇒ 假编译器是绕过该前置检查的钥匙。
- `--dry` 仍要求 `cl.exe` 可发现（只跳过编译链接，不跳过工具链探测）。
- `build/` 缓存会让 `--dry` 的 `.cc` 陈旧 ⇒ 改完源要 `rm -rf build` 或加 `-f`。

## 5. 环境坑（一次踩完，别再踩）

| 坑 | 症状 | 解法 |
|----|------|------|
| `tpc.exe` **不加载**同目录 `php.ini`（`php.exe` 会） | `Fatal: Failed to startup module [typephp_tpc]`（缺 `mbstring`） | ① `export PHPRC=<发行版根>` ② 该 ini 的 `extension_dir` 改**绝对路径**。★ 0.9.0 不要求、**0.9.4 起强制** ⇒ 升级发行版即破坏既有脚本 |
| 已验证**无效**的尝试 | 同上 | `tpc -d extension=mbstring` / `tpc -c php.ini` / 只改 `extension_dir` 不设 `PHPRC` |
| `PHPRC` 两个用途混用 | 构建期 vs 运行期 exe | 构建期指向**发行版根**；运行产物 exe 时才用"关 opcache"的那个 ini |
| `php.exe` 拒收 Git Bash 风格路径 | `/d/...` 被拒 | 传 Windows 风格 `D:/...` |
| 本环境 PowerShell 工具不回传输出 | 构建脚本拿不到 stdout | 一律走 Bash + 直接 `export INCLUDE/LIB` |
| `cl.exe` 被沙箱拦 | 构建失败 | 构建须提权；`LNK1104`（锁自家 exe）= 有残留进程，先 `taskkill` |

### 7.7 实现纪事：TaskHost 线程池被探针 K 判死（2026-10-16 晚）

**这一节的主题是"一个已经写进方案 4 处的『【实测】可用』是怎么被推翻的"。**

★ **§17.2 后端 A（C++ 线程池执行 PHP 任务）在方案里被标了 4 次"【实测】可用"**
（§2 表第 15 行 · §2 能力表 · §11.x 第 2 条 · §17.2 架构图），依据是探针 E。
但探针 E 的 ⑤ 只跑了三个函数：`thr_php_add`（整数算术）/ `thr_php_sum`（标量循环）/
`thr_php_concat`（循环拼字符串）—— **从没碰过类 / 对象 / 属性**。
⇒ "worker 能跑 PHP"这句话成立的范围，**比它被引用时假设的范围小得多**。

★ **探针 K（`probes/taskhost_tsrm/`）补的正是 §17.2.2 点名的那一枪**，做法上两个关键点：
① **`threads=1` 是关键对照列** —— 它把"并发竞争"与"worker 线程本身就缺东西"分开。
   结果是后者：**碰类/对象/属性的 mode 在 1 个 worker 线程上就 SIGSEGV**（3/3 稳定）。
② **C++ 侧 `trace()` 文件追踪**（`fopen/fprintf/fclose`，每行一次 open/close）——
   崩在 PHP 里时 `file_put_contents` 已经不可用，只有 C++ 侧的证据留得下来。
   它把崩溃点定到了行：`mode=0 req=2` 崩在 **`zm_activate_*` 内部**；
   `mode=4 req=1` 崩在 **`php::request_init()` 之后的 mode 调用里**。

★ **根因是读生成的 C++ 读出来的**（不是猜的）：`build/extension-taskhost_tsrm.cc` 里
`static THREAD_LOCAL php_request_cache_storage *php_request_cache = nullptr;`
**只在模块 RINIT 里被 `new`**，而 `get_class()` / `get_property_cache()` / `get_method()` /
`get_method_call_cache()` / `get_function_resolution_cache()` 全走它 ⇒
**没跑过 RINIT 的线程上全是空指针解引用**。`typephp_read_property_cached(…, get_property_cache(…))`
在生成的 `main.cc` 里出现 **32 次**（读枚举 `->value` 就要请求级属性缓存）。
★ 顺带解释了一个"看起来像并发"的现象：mode 1（类静态属性）在 `threads=1` 也崩、但
**主线程先摸一遍就好了** —— 因为 `get_persistent_class` 是 `std::atomic` + CAS 的**持久**缓存，
主线程填上以后 worker 直接命中，**不再需要在自己线程上做类名解析**。

★ **两条"给 worker 补请求上下文"的路都断了**（这是本轮唯一"想救但救不了"的部分）：
- `php::request_init()`（**公开 API**）可调、安全（`mode=0 req=1` 完整跑通），
  但它**不建 `php_request_cache`** ⇒ 类/对象访问照样崩；
- 完整 RINIT（`zm_activate_*`）**自己就 SIGSEGV** —— 它的最后一步是
  `php::eval("main();")`，把"建请求上下文"与"启动 main()"**绑死了**。
⇒ 结论：**后端 A 在当前 tpc 运行时下不可实现**；需要 tpc 提供一个"每线程进入请求"的入口
（分配请求缓存 + `php::request_init()`，**不启动 main()**），最省事的等价做法是把 RINIT 的
前两步与最后那一步拆开各自导出。⇒ **M1–M3 只上后端 B（`SyncTaskHost`）**，
端口契约不变，tpc 补上钩子即可接入（页面/Store/`Job` 零改动）。

★ **顺带抓到两个"永不匹配的 mangling"式 `LNK2019`**（`obj` 里明明有符号）：
① 生成的模块钩子**在命名空间里** —— 真实符号是
   `typephp_project_taskhost_tsrm::zm_activate_typephp_taskhost_tsrm`（命名空间名 =
   `typephp_project_<project.name>`）。在全局作用域写声明就永远匹配不上。
② **`INIT_FUNC_ARGS` 是 `int type, int module_number`**（`zend_modules.h:27`），
   **不是** `zend_module_entry*`。写成指针签名同样匹配不上。

★ **一条量具缺陷**（自己踩的，写下来防复发）：mode 0 第一版返回"本线程推进的步数"——
而"共享静态量 + 线程恰好串行"时**每线程步数也是 `$rounds`** ⇒ 判据恒真、什么都测不到。
改成返回**绝对值**才成立（每线程独立 ⇒ `min=max=rounds`；共享 ⇒ `max=threads*rounds` 且 `distinct>1`）。
**"量具必须带反例自检"的又一例。**

### 7.8 实现纪事：单屏 100% DPI 把"糊"藏住了（2026-10-16 深夜）

**这一节的主题是"开发机的环境恰好掩盖了一个真实缺陷，而文档把它写成了『无差别』"。**

★ **背景**：§19 M1 的出口判据里有一句"**分数缩放下不糊**"，而实现一直只跑在**单屏 100% DPI**
的机器上 ⇒ 这句话从没被检验过。方案侧只在 M1 行末尾留了一句"仍未验"，没说它会怎么坏。

★ **缺陷是读代码读出来的，不是跑出来的**：`cpp-src/win32/drift_win32.cc` 的 `php_drift_win_create()`
调的是 `SetProcessDPIAware()` —— 那是 **system-DPI-aware（V1）**，**不是** per-monitor。
而 `php_drift_win_dpi()` 的注释把它论证成"无所谓"：

> 「用 `GetDeviceCaps(LOGPIXELSX)` 而不是 `GetDpiForWindow`：后者要 `_WIN32_WINNT >= 0x0A00`……
>  代价：拿到的是**系统** DPI —— **对 M1 无差别**，因为跨屏拖动时系统会发 `WM_DPICHANGED`」

**这句话里两个断言都是错的**：
1. `WM_DPICHANGED` **只发给 per-monitor 感知的进程** —— V1 进程跨屏时**收不到**，
   所以 `g_dpi` 永远停在系统 DPI，§6 的"跨屏 = scale 变更 = 布局事件"整条落空；
2. V1 进程跨屏时系统把窗口内容**整体位图拉伸** —— 那正是"糊"本身。

⇒ 于是"为一个 DPI 查询不值得抬 `WINVER`"这个**成本判断**也站不住：正解不是抬宏，是
   `GetProcAddress` **动态取**（`SetProcessDpiAwarenessContext` / `GetDpiForWindow` /
   `AdjustWindowRectExForDpi` 三个都这么取），**一个编译宏都不用碰**。

★ **为什么它能在开发机上"过"**：单屏 + 100% DPI 时，V1 与 V2 的**可观测行为完全相同**
（系统 DPI == 显示器 DPI，且没有"跨屏"这个动作）。⇒ **"本机跑得好"对这类缺陷零信息量。**
这条比 §7.7 那条更狠：§7.7 是"探针没测那一面"，本节是"**环境恰好让那一面不存在**"。

★ **修法与判据**（判据必须直接断言**配置**，而不是断言它的后果）：
- 进程感知升到 **Per-Monitor V2**（三级回退：`SetProcessDpiAwarenessContext` →
  shcore `SetProcessDpiAwareness` → `SetProcessDPIAware`）；必须在**建窗 / 取 DC 之前**设
  （Windows 在那时锁定感知级别）。
- `drift_win_dpi` 改 `GetDpiForWindow`（每显示器）；退 `GetDeviceCaps` 是**降级**不是等价。
- 外框改 `AdjustWindowRectExForDpi`（老的 `AdjustWindowRectEx` 按系统 DPI 算边框厚度 ⇒
  客户区对不上请求的逻辑尺寸）；建窗后按 `GetDpiForWindow` 再纠正一次
  （`CW_USEDEFAULT` 可能把窗口放到另一块 DPI 的屏上）。
- ★ **探针加断言**：`python tools/probe-window.py users` 现在读
  `GetWindowDpiAwarenessContext` + `AreDpiAwarenessContextsEqual(…, PER_MONITOR_AWARE_V2)`，
  **判据 = 感知级别 == PER_MONITOR_AWARE(2) 且 == V2**。
  **反例自检**已跑过（`SetProcessDPIAware()` 之后同一条判据给 `False`）⇒ 旧的 V1 实现会被判 FAIL。
- 分数 dpr 的**量化算术**另有一层：smoke 里 `Scale::fromDpi(120)`（1.25）/ `quantize(10.0)`
  / `quantizeRect`（1.5，相邻盒共享像素边）/ `dpr=2` 设备分辨率光栅都有断言
  —— 这两层合起来才叫"分数缩放下不糊"。

★ **仍未验**：真·跨屏拖动（本机单屏，没有第二块不同 DPI 的显示器）⇒ 只验了"感知级别正确"，
**没验**"跨屏后的实际画面"。已登记 §24.2 #11。

### 7.6 滚动两缺口收尾（2026-10-17）

用户报两点：① 没有滚动条 ② 可以滚动但不跟手。先出架构分析（链路：`WM_MOUSEWHEEL` → 桥 → `pump`(÷dpr、÷120 收"格") → `ScrollEvent` → `Application::scrollAt` → `ScrollViewState::scrollBy` → `RenderScrollView`），再落地。

**① 滚动条 = 纯视觉层**（不动滚动机制）：`RenderScrollView::paint()` 在**视口坐标系**画胶囊形 thumb —— 长度 = 视口占比（最短 24、超长夹进轨道）、位置 = 偏移/maxScroll × 可走距离、`maxScroll==0` 不画、纵向贴右 / 横向贴底，画在内容之上（裁剪区内）。★ **抓到真 bug**：thumb 起初画在内容的 `translate` 之后 ⇒ 被滚动偏移带走 —— offset=max 时整条飞出视口被裁干净（"该贴底时什么都没有"）。offset 小的用例有墨 ⇒ 单看一条会误判成位置公式错；是 smoke 的 sv2（offset 9999）当场暴露的。修法：`save/restore` 包住内容的 translate，thumb 在 restore 之后画。

**② "不跟手"根因 = 步长，不是缺插值动画**：`pump` 把 WHEEL_DELTA ÷120 收成"格"，而消费侧把"格"直接当像素用 ⇒ **一格 notch 只滚 1px**。修法：`Application::WHEEL_NOTCH_PX = 48`（3 行 × 16px 行高，与 Windows 默认 `SPI_GETWHEELSCROLLINES=3`、浏览器每格 ~40–53px 同量级），在 `dispatchInput()` 的 ScrollEvent 分支换算（**格→像素只发生一次**，策略归框架、量化归平台）。★ **不做插值动画**：滚轮输入本离散，48px/格后与浏览器同量级；惯性/平滑是新机制（要帧循环驱动动画态），留给真有消费者的 M4（触摸拖动）。这条判断写进文档：避免后人把"离散跳变"当 bug 又加一层动画。

★ **tpc 比 PHP 严（新 AOT 纪律）**：可选参数排在必选参数之前，**解释器只发 Deprecated**（`php -l`/smoke/lint 全绿），**tpc 预处理器直接 Fatal**（"optional parameter cannot be declared before required parameter"）⇒ `RenderScrollView($offset, $thumb, $vertical = true)` 换序。解释器三门全绿也过不了 codegen，再次印证"AOT 只在更大用法面上才喊"。

★ **刻意不做**（避免"没有消费者就发明机制"）：通用 Fiber 调度器（`Awaitable::read()`）、

### 7.12 P3：ProcessTaskHost 常驻子进程（2026-10-18）

**为什么是进程**（§17.2.5–17.2.6 实测的结论）：线程跑 AOT 代码当前不可行（worker 线程缺 Zend
上下文，裸线程 / Swoole + FFI 两枪 SIGSEGV）；进程**天然隔离**（崩了只丢一个任务），且 worker
**跑的是同一份 AOT 代码** —— 不像 Swoole 线程只能 `require` 源码解释执行（慢 55–95×）。

**落地**：
- `NamedJob`：`name()` + `args()` —— 跨进程只能传"名字 + 参数数组"（对象图没有稳定的序列化格式，
  且 `serialize()` 在 AOT 下没验过）。注册表两侧一致是硬约束。
- `ProcessWorker::serve($registry)`：`php://stdin/stdout` 上的 JSON Lines，一行请求一行回复；
  **任何异常都变 `{ok:false}`**，不许打死 worker（进程隔离的价值就在这）。
- `ProcessTaskHost($command, $registry)`：**懒启动 + 常驻 + 串行**；`drain()` 每帧非阻塞读
  stdout **和 stderr**（不读 stderr 的话管道满了 worker 会阻塞在 warning 上 —— 真正的死锁来源）；
  `reap()` 检测进程死亡 ⇒ 在途任务走 `onError` + 下一帧自动重启。

**实测**（本地 php.exe）：首次 spawn + 往返 **256ms**，热态**往返 23.5ms**。
对比"每任务一进程"的 275ms/次 ⇒ 常驻池的价值就在这个数上。

**判据（smoke +12，真进程真管道）**：懒启动 / 真进程算对（跨进程跑 `SumJob`）/ 串行排队
（在途 1、队列 1）/ 任务失败 ⇒ `onError` 且 worker 活着 / `exit 9` 崩死 ⇒ `onError`（"后台进程退出
（exit=9）"）且 worker 停 / 崩溃后自动重启并跑完新任务 / `shutdown()` 收工。

★ **两处踩坑（都是"判据自己的 bug"）**：
1. `$pump` 的 drain 回调直接读 `$c->value`，**没调 `onDone`** ⇒ 断言期望 `a1` 拿到 `1`。
   改成走**生产路径**（`$onDone` / `$onError`）—— 测端口就要测"回调真的被调了"。
2. `static fn(): bool => $sink !== []` **按值捕获创建时的空数组** ⇒ `$until` 恒 false ⇒
   每次 pump 等满 10 秒 deadline（smoke 从 10s 涨到 78s）。判据闭包必须**收参数**。
   修完 30s（真进程测试本身的成本 ~3s）。

**两条必须说清的代价**：
① **异常类不可还原**：worker 把 `RuntimeException: 消息` 拼成字符串，UI 侧收到的是一个新的
`RuntimeException`（跨进程没有"同一个异常对象"这回事）。
② **串行**（在途 ≤ 1）：第一版形态。并行要"多 worker + 空闲挑选 + 任务重派"（并发调度器），
等真有需求再把 `$worker` 变成数组，结构不用改。

★★ **AOT 运行面仍未验**：`users` 没有真实后台需求，所以"同一份 AOT 产物带 `--drift-worker` 分支"
只到**翻译层**（codegen 210 全翻译 + `users.exe` 链接通过）。补法很明确：组合根加一次
`$_SERVER['argv']` 分流（探针 ⑦ 已验可行）+ 让某个应用真用上 —— 留给 M4 的 `HttpUserSource`。

**验证**：smoke **720 ok / 0 FAIL**（+12）· lint **317 文件 0/0** · codegen **210 全翻译 0 skip** ·
`drift-build users` 构建通过 + 真机 OK。DESIGN：§4.2 数字 **183 / 158 / 105 = 103 + 2 / 未点名 80**、

| 后台（`ProcessTaskHost`）| `attach` **116ms** 回事件循环；此后 `frame()` **4.24ms/帧**、`drain()` **0.013ms** |

**② 但第一次量出来 `drain()` 是 29ms、`frame()` 是 34.5ms** —— 界面上就是稳定 30fps 掉帧。
根因不在架构，在**句柄类型**（Windows 专属）：

| `proc_open` 句柄 | `stream_select(..., 0)` | 非阻塞 `fread` |
|---|---|---|
| `['pipe','w']` | **13.654 ms/次** | **411.189 ms/次**（"非阻塞"等于没用）|
| `['socket']` | **0.008 ms/次** | **0.001 ms/次** |

Windows 的 `select()` 只吃 socket，PHP 对 pipe 走"逐句柄猜"的退化路径。⇒ 全部换 `['socket']`，
12 条 P3 判据仍全绿（worker 的 `php://stdin` 照常工作）。

**③ curl 在 AOT 产物里可用**（探针 `[L]` 段）：
```
[L1] curl_init=yes curl_exec=yes allow_url_fopen=1
[L2] curl → code=200 body={"ok":true} err=
```
⇒ `drift-build` 的运行时 ini 从"仅 mbstring"改为 **`mbstring + openssl + curl`**
（之前"不拖 curl"是保守选择，不是能力限制）；`FetchUsersJob` 改用 curl ——
连接超时/总超时分离（5s/10s）、能拿 HTTP 状态码（4xx/5xx 不再混成"解析失败"）、
HTTPS 证书校验是一等公民。
