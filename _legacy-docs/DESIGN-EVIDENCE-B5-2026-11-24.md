# B5 · 重开的忠实性：`--loop` 到底在测什么

> 前置：B2（S-live 自走宿主）、B3（S6 干预）、B4（S5 消费者）均已落地。
> 本文档只回答一件事：**多加一个命令之前，先把"重跑"这个词的含义钉死。**

## 一、这一期要买什么

一句话：**证明"把关掉这一页再打开"是等价的**。

不是"多跑几次看看稳不稳"。是：`Application` 实例可被丢弃重建，重建后的因果与结构必须与第一次**逐值相同**。这是框架可测试性的地基 —— 现在没有任何判据钉住它，而所有"单例忘了清"、"静态缓存跨页残留"、"卸载不干净"的 bug 都藏在这条缝里。

分期表上它排在 S5 之后、S2 之前，理由也在这里：S2 的常驻黑匣子要"崩溃后重开同一页看能不能复现"，那条能力的地基就是本文档这一条。

## 二、先证伪四件事

写代码前先打掉四个想当然。前两个是我自己上一轮的判断，后两个是实现时会踩的坑。

### 2.1 「`Recorder::reset()` 没清节点号」——已过时，且本轮用不上

B2 §5.4(a) 断言 `reset()` 只清帧、不清 `$seq` / `$tag`，于是重跑后节点号从 365 起、`stats.nodes` 报一个越来越大越来越假的数。我上一轮据此把"修 reset"列为本轮前置。

**读代码即可证伪**：`Recorder::reset()`（`src/Debug/Session/Recorder.php:1159`）已经把 `$nodes` / `$boxless` 清空、`$seq` 归零、`$tag` 换新。B2 §九第 0 条当时就顺手落地了。

更要紧的是：**这条路径在本轮根本用不到**。正解是"每轮重建应用"（§三），而重建应用必然伴随新会话、新录制器；`reset()` 复用同一个录制器的路子在 loop 里不存在。

⇒ 上一轮说"前置是修 reset"是错的。本轮不做这件事，也不该在文档里留一个已经修完的待办。

### 2.2 「重跑 = 把脚本再放一遍」——实测咬人，而且咬得很难看

复用同一个 `Application` 实例，只重开会话，跑同一份脚本（`async-table`，`resolve` + `click` + `wheel`）：

| 轮 | digest |
|---|---|
| 1 | `97cddecda950` |
| 2 | `4702c810ffeb` |
| 3 | `4702c810ffeb` |

第 2、3 轮**彼此相同** —— 这才是要命的地方。一个"跑 3 轮，看后两轮一致就收工"的实现会恒绿，而它漏掉的正是"第一轮把页面推到了另一个状态"。

相同的理由在落地时才查清：这份脚本里有 `wheel`，而滚动位置**会饱和**——第 2 轮再滚同样的 240 格时已经到底，第 3 轮更是原地不动。所以"后两轮相同"不是"稳定了"，是"撞墙了"。这个细节比差异本身更有教育意义：**一致性的形状可以是假象**，而它偏偏长得像"跑两次就收敛了"。

状态在树里，不在脚本里。`Replay` 的注释早就写着"回放是从第一帧重跑到第 N 帧，不是跳回第 N 帧"——但那只在**应用是新的**时候成立。

⇒ 判据必须从第 1 轮开始比，**不许丢 warmup**。这是与基准测试的分歧点，理由见 §四。

### 2.3 「进程内重建会残留」——现在测不出来，除非采样点强制 GC

同一进程、每轮新建应用、连跑 50 轮：

| 采样方式 | 读数 |
|---|---|
| 裸 `memory_get_usage()` | 145 → 283 → 159 → 297 → 159 MB（锯齿） |
| `gc_collect_cycles()` 之后 | 20.832 → 20.834 MB（20 轮共 +2KB） |

裸读数那串数字看起来像"每轮漏 3MB、攒到 GC 周期才收"，而它测的是 **PHP 什么时候想起来回收**，不是**有没有东西留下来**。用它做判据会恒红，且红得毫无意义 —— 修不了，因为那不是 bug。

⇒ 内存判据的采样点必须是 `gc_collect_cycles()` 之后。这是"看起来像泄漏"与"真的泄漏"的分界线。

### 2.4 「两轮 digest 相同，说明重建是对的」——不，可能根本没重建

如果 `Target::app()` 里有静态缓存，两轮拿到的是同一棵树，digest 相同**毫无信息量**。所以判据自己也要能自证"这不是在骗我"：

| 轮 | `spl_object_id(app)` | 根节点 `debugId#tag` | 节点号区间 |
|---|---|---|---|
| 1 | 69 | `10#1` | 1..21 |
| 2 | 623 | `10#2` | 1..21 |
| 3 | 1027 | `10#3` | 1..21 |

⇒ 报告里必须打出每轮的**会话令牌**与**节点号区间**。少了这两列，"两轮相同"随时可能是"两轮是同一棵树"。

## 三、裁决一：重跑的单位是「应用」，不是「脚本」

三个粒度：

| 粒度 | 实现 | 代价 | 能测什么 | 漏什么 |
|---|---|---|---|---|
| A 只重放脚本（复用 `Application`） | 最省，0 | 脚本可重放 | **状态延续**（§2.2 实测咬人） |
| **B 重建 `Application`，同进程** | 每轮 `Runner::open` | 一次 mount | **跨会话残留**、结构一致、成本稳定 | 进程级残留 |
| C 每轮一个子进程 | `--remote` 跑 N 次 | N × 进程启动 | 一切 | **什么都测不出来**（新进程本来就干净） |

选 B。理由不是折中，是**只有 B 的观测区间别人盖不住**：

- A 把"残留"和"状态延续"混成同一个 digest 差异，分不开，修复动作相反；
- C 每轮都是新进程，残留被操作系统清掉了 —— 它证明的是"进程干净"，不是"页面干净"；
- B 恰好落在中间：**同一个 PHP 进程、同一份静态状态、同一个堆，但应用是新的**。

所有"单例忘了清"、"静态计数器跨页漂"的 bug 只在这个区间显形。Android 的 Activity 重建（同进程、新 Activity）、Flutter 的 hot restart（同进程、新 isolate）、Chrome 的 `Page.reload`（同进程、新文档）暴露的正是同一类问题。

## 四、裁决二：两类指标，两套采样纪律

| | 正确性 | 性能 |
|---|---|---|
| 指标 | `digest` / 节点数 / 帧数 | `mountMs` / 帧耗时 |
| 采样 | **每一轮都算，从第 1 轮起** | 报中位数与极差，不参与判定 |
| 为什么 | 应用语义：第一轮就是真相 | 机器语义：单次读数没有意义 |
| 抄谁 | React StrictMode 的双渲染 | Lighthouse `--runs` 取中位数 |

两条纪律不能合并。合成一个"稳定性分数"的后果是：「这次机器慢」与「这一页有残留」用同一个数字说话，而修复动作完全相反（换机器 vs 改代码）。

**为什么正确性不丢 warmup**：Lighthouse / 各类基准丢第一轮，是因为 CPU 频率爬升、JIT 预热 —— 那是机器状态，第一轮不代表后续。而这里的差异来源是**应用状态**，第一轮恰恰是唯一没有被任何前置轮污染的那次。丢掉它等于丢掉基准。

## 五、裁决三：新出口，不给现有出口加 `--loop`

给 `brief` / `network` / `node` 加 `--loop=N` 看起来最省，但立刻产生一个无解的问题：**报告给第几轮的**？

- 给第一轮 ⇒ 后几轮白跑，只剩"验证"这一个用途；
- 给最后一轮 ⇒ 前几轮成了 warmup，与 §四 冲突；
- 给中位数 ⇒ 给不了，报告不是数字。

所以 `--loop` 的产物形态与其它十一个出口根本不同：别人产出「一次运行的某份证据」，它产出「多次运行的对比」。**产物不同就该是不同出口。**

命令：`drift debug loop --runs=N`（老称呼沿用 B2 与 `Cursor` 注释里的 `--loop`，参数名用 `--runs` 与 Lighthouse 对齐）。

## 六、裁决四：比较要指出「第一处不同」，不是报一个哈希不等

`Digest::of()` 已经给了三层：`frames`（每帧一个哈希）、`nodes`（节点表哈希）、`digest`（整体）。比较器因此可以分层报：

```
✗ 第 2 轮与第 1 轮不同
    整体   97cddecda950 ≠ 4702c810ffeb
    节点表 21 个节点，哈希相同          ← 结构没变
    帧     第 1 帧起不同                 ← 因果变了
```

这比"两次 digest 不一样"有用一个数量级：**结构相同而因果不同**指向"状态被带进来了"，**结构不同**指向"重建顺序变了"，两者修复动作完全不同。

## 七、裁决五：`--out` 导出首轮

给了 `--out` 就导**第 1 轮**。它是唯一没有被任何前置轮影响的那次，也是判据的基准。导出末轮等于把"验证"当"取样"，而两者取的东西不一样。

`--out` 与 `--remote` 的互斥是既有规则（`Source` 里已有），loop 不引入新规则 —— 也因此 loop **不支持 `--remote`**：`--remote` 每轮会起一个新进程，那是粒度 C，与 §三 相悖。

## 八、形状

### 8.1 输出

```
$ drift debug loop --page=async-table --runs=3 --resolve --frames=2

重开 3 次 · async-table · 每轮 2 帧

  轮  会话          digest        节点  帧   挂载    首帧
   1  d4b63e17…     97cddecda950   21   2   3.1ms   0.42ms
   2  8a021c55…     97cddecda950   21   2   2.8ms   0.39ms
   3  5f190a2b…     97cddecda950   21   2   2.9ms   0.41ms

  ✓ 3 轮因果与结构逐值相同

  挂载   中位 2.9ms   极差 0.3ms
  首帧   中位 0.41ms  极差 0.03ms
  内存   20.832 → 20.834 MB（GC 后，+0.01%）

  会话令牌各不相同 = 确实重建了三次；节点号每次都从 1 起。
```

不一致时：

```
  ✗ 第 2 轮与第 1 轮不同
      整体   97cddecda950 ≠ 4702c810ffeb
      节点表 相同（21 个节点）
      帧     第 1 帧起不同
  其余 1 轮与第 1 轮相同 —— 一致性只在第 1 轮断，说明有状态被带进了第一轮的终点。
```

### 8.2 文件落点

| 文件 | 职责 |
|---|---|
| `tools/Debug/Reopen.php` | 跑 N 轮、逐层比较、给结论。不碰排版，不碰 argv |
| `tools/debug-loop.php` | 出口：参数解析 + 调 `Reopen` + 排版 |
| `tools/Debug/View/LoopReport.php` | 排版（`lines()` / `json()`） |
| `bin/drift` | 注册 `loop` verb |
| `tests/Feature/Tools/Debug/LoopTest.php` | 判据 1–7 |

`Reopen` 吃的是一个**会话工厂**（`fn(int $round): array{session, mountMs}`），不是 `Runner`。这样它不依赖"怎么造这一页"，测试才能喂一个"复用同一个应用"的假工厂来证明判据有牙（判据 5）。

## 九、判据

| # | 判据 | 防的是 |
|---|---|---|
| 1 | 同一脚本跑 N 轮，`Digest::of()['digest']` 逐轮相同；不同时报出**第一处不同**（整体 / 节点表 / 第几帧） | 重建不忠实 |
| 2 | 每轮 `spl_object_id(app)` 不同、会话令牌不同、节点号区间都是 `1..K` | 根本没重建，判据 1 白给 |
| 3 | 每轮录下的脚本 `script()->digest()` 与源脚本相同 | 重放丢步 / 多步 |
| 4 | 内存（`gc_collect_cycles()` 后）首末轮差 < 5%，且不单调上升 | 跨会话泄漏 |
| 5 | 喂一个"复用同一应用"的假工厂，判据 1 **必须红**（用 §2.2 的脚本做固定夹具） | 判据自己是恒绿的 |
| 6 | `--runs=1` 只报一轮并明说"没有可比对象"，不假装通过 | 单轮也打勾 |
| 7 | `--out` 导出的是第 1 轮；`--remote` 与 loop 互斥并给出理由 | 导出末轮 / 每轮起进程 |

判据 2 是判据 1 的前提：没有它，判据 1 可能在"两次都是同一棵树"时恒绿。判据 5 是判据 1 的变异测试，用真应用而不是 mock —— mock 编不出"状态被带到下一轮"这种只有真树才有的行为。

## 十、落点

顺序按依赖排，每步都能单独验：

1. `Reopen`：会话工厂 + N 轮循环 + `try/finally` 关会话（中途抛异常时录制器不能残留，否则下一轮 `open` 直接抛"已有录制器"）。
2. 比较器：`frames` 逐帧 → `nodes` → `digest`，产出一个 `{same: bool, firstDiffAt: ?array}`。
3. `LoopReport`：表 + 结论 + 性能段 + 内存段。
4. `debug-loop.php` 出口 + `bin/drift` 注册。
5. 测试（判据 1–7）。
6. verify：`behavior` 层加一条（`--assert` 模式跑 table 页 3 轮，非 0 退出即红）。

`--runs` 上限 100（手滑 `--runs=100000` 要跑半天，而它不会给出比 100 更多的信息）。

## 十一、不做

| 不做 | 理由 |
|---|---|
| 进程级隔离重跑（粒度 C） | 它是"跑两次命令"，不需要新能力；且会掩盖跨会话残留（§三） |
| `--watch` 自动重跑 | 前置是 supervisor（监视 mtime → 重启宿主 → 观察者重连），是 S-live-b |
| 快照 / 恢复现场 | A38 已裁决：PHP 序列化不了 State，AOT 没有稳定地址。这条路在本项目是死的 |
| 把 loop 挂进 `serve` | `serve` 是常驻可干预，`loop` 是一次性批量；挂进去会让"会话能不能被替换"变成一个新问题 |
| 给用户开"复用应用"的开关 | 那是给人挖坑：省一次 mount，拿到的是假结论（§2.2） |

## 十二、后续

本轮之后，"重开"这条链上还剩两处欠账：

1. **`--remote` 的会话状态没人标 `finished`**（B4 §11）：宿主在子进程，本进程管不到。修法是在协议里加一个"脚本跑完了"的通知，属于协议变更，不与 loop 同批。
2. **驱动词表四处各一份**（`brief` / `network` / `serve` / `web`）：加 `loop` 就是第五份。它已经越过"复制一次是省事"的线，下一轮该收成一个解析器 —— 但那是重构，不是本文档的落点。
