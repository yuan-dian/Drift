# 组合根「双角色」暴露面 Review · 对照成熟 GUI 框架与 PHP 约束的方案推演

> 日期：2026-11-22 · 类型：**只读分析，未改任何代码 / 配置**
> 基线：HEAD `f88aea9`（A23/A24 已提交，未 push）。
> 起因：`WorkerProcess::executable()` / `SWITCH` 的设计被评价为"不好理解"，追问成熟框架怎么做。
> 相关：[REVIEW-异步DX对照成熟GUI-2026-11-16](REVIEW-异步DX对照成熟GUI-2026-11-16.md)、
> `docs/decisions/README.md` 的 A23、`docs/start/app-anatomy.md`。
> 定位一律用类名 / 方法名，不写 `file:line`。

---

## 0. 结论先行

1. **机制不用改。** 单个 exe + 命令行开关认进程角色，是 Chromium / CEF / Electron 的
   标准做法；PHP 没有"能跑 PHP 代码的用户态线程"，跑业务逻辑的后台**只能是进程**。
   这条路不是凑合，是约束下的最优解。
2. **位置也对。** 角色分流发生在 `Bootstrap::run()` 第一行，与 Android 在
   `Application.onCreate()` 判进程名、CEF 在 `main()` 判 `--type` 是**同一层**。
3. **错的是暴露面。** 上面两个框架都把这个判断**封装在框架模板里**，业务作者看不见；
   Drift 把它摆在应用作者面前，而且是**两行、分属两个对象**（`WorkerProcess::serveIf`
   与 `AppScope::useBackgroundJobs`）。用户觉得绕，绕在这一层，不在机制本身。
4. **可回收的只有"两行→一行"这一步**，但要付一个代价：`AppBoot::enter()` 返回
   `?AppScope` 的 null 语义。更彻底的收口（零行 / 自动装配）会撞 tpc 入口约定与
   "显式优于隐式"的纪律，**不建议做**。
5. **真正消掉心智负担的是脚手架**：`drift create` 生成带这行的组合根并标注"业务不用改"，
   把概念关进生成代码。这比再抽一层 API 更有效。

## 1. 现状：到底暴露了什么

### 1.1 三份组合根的逐字重复面

watermark / users / showcase 三份 `Bootstrap::run()` 的**开头与中段**拥有同一段骨架：

```
if (WorkerProcess::serveIf(<App>\Jobs\JobRegistry::make())) { return; }   // ① 角色分流
...
$scope = AppScope::make()->...->useBackgroundJobs(<App>\Jobs\JobRegistry::make());  // ② 建池
```

`hello` / `tutorial` 没有后台，这两行都不写 —— 它们的组合根只有建窗 + `open` + `run`，
干净得像 Flutter 的 `runApp()`。

### 1.2 真实业务矩阵（决定"能不能统一"）

| 应用 | Job 数 | workers | 预热 | 其它应用语义 |
|---|---|---|---|---|
| watermark | 5 | 1 | 是（进窗就取签名） | Dialog 端口 |
| users | 1 | 1 | 是（首屏取数） | Restoration、无边框、材质 |
| showcase | 1 | **3** | 是 | 双窗、Inspector、材质、剪贴板 |
| hello / tutorial | 0 | — | — | 无 |

**重复的只有 ①②**；`workers` / 预热 / Dialog / 恢复 / 双窗都是差异。A23 的边界判断
（只收逐字重复的进程角色与后台装配）是对的。

### 1.3 暴露的成本（按开发者要理解的概念算，不按行数）

| 要理解的东西 | 为什么绕 |
|---|---|
| `--drift-worker` 是什么 | 应用作者从不需要知道 exe 有两种角色 |
| 为什么 `serveIf` 要 return | "我可能是个 worker、跑完就该退出"这个形态很陌生 |
| 为什么 `useBackgroundJobs` 要在 `attach` 之前 | 端口被 `PumpHost` 取走的时序契约 |
| `AppScope` 和 `WindowSet` 谁先谁后 | 两个对象都要配，且顺序有坑 |

前两条是**角色概念**，后两条是**装配时序**。都属框架职责，却写在应用文件里。

## 2. 成熟框架怎么处理（借鉴什么 · 排什么坑）

### 2.1 Chromium / CEF / Electron —— 同构，且证明可行

- **做法**：Windows / Linux 是**单个可执行文件**处理所有进程类型，靠 `--type=renderer`、
  `--type=gpu-process` 等命令行标志重新调用同一个二进制。主进程（browser）决定进程拓扑，
  renderer / GPU / utility 各自从 `main()` 最早期读 `--type` 走不同初始化。
- **借鉴**：机制与 Drift 同构；"主进程决定拓扑、子进程只认角色"正是 Drift
  `ProcessTaskHost` + `ProcessWorker` 的分工。
- **排坑**：
  - **macOS 不是单 exe**：Apple 的沙箱与签名要求子进程从 `.app` 包内的独立 helper
    可执行文件启动。"单 exe"是平台相关的最优解，不是普适真理 —— Drift 在 macOS 上
    若要做，同样得准备 helper 产物。
  - 角色判断在**框架启动代码**里，不在应用的 `CefApp` handler 里。应用 handler 根本
    不知道自己是哪个角色。这是 Drift 与它的**唯一结构性差距**。
- **对 Drift 的意义**：机制无可指摘；差距在"谁来做这个判断"。

### 2.2 Android —— 最接近"声明式分流"的范式

- **做法**：跨进程在 manifest 写 `android:process=":remote"`，系统负责 fork；代码侧在
  `Application.onCreate()` 里判当前进程名，`if (isMainProcess) initUI() else initRemote()`。
- **借鉴**：**声明与实现分离** —— 拓扑是配置，代码只判"我是谁"。Drift 的
  `JobRegistry` + `workers: N` 已经有"声明"的味道，缺的是把判断收成固定模板。
- **排坑**：
  - `:remote` 进程**静态变量不共享**，单例各自一份；`Application.onCreate` 会为每个
    进程各跑一次。Drift 的 `serveIf` 提前 return 正是同一件事 —— 位置对。
  - Binder 跨进程有 ~1MB 事务上限（`TransactionTooLargeException`）。Drift 的
    JSON Lines + `READ_CHUNK` 分片读，等价问题已被处理。
- **对 Drift 的意义**：**Drift 的位置是 Android 同款，不是野路子**；Android 之所以不
  让人觉得绕，是因为它长在框架生命周期里，开发者抄模板不思考。

### 2.3 Flutter —— API 形态最值得抄，机制抄不了

- **做法**：单进程 + isolate（独立内存、消息传递、运行时托管）。开发者只写
  `Isolate.run(fn)` / `compute(fn, arg)`，零进程概念。
- **借鉴**：**消费侧 API 形态** —— 一个函数入口，参数是任务，返回是结果。
- **排坑**：
  - isolate **不共享任何可变状态**（连全局变量都不共享），通信只能复制消息。
  - isolate 崩溃会带崩整个进程，**没有 OS 级隔离** —— Drift 的多进程在"崩溃隔离"
    上其实强于 Flutter。
  - `compute()` 在 web 上退化为同步执行。平台能力差异必须显式。
- **对 Drift 的意义**：机制抄不了（PHP 没有可跑 PHP 的用户态线程），但
  "一个入口函数"的形态可以借。

### 2.4 Qt —— 全局池的形态可借

- **做法**：`QThreadPool::globalInstance()` + `QRunnable`；`QtConcurrent::run(fn)` 一行；
  跨线程回 UI 靠 `QueuedConnection` 信号槽。
- **借鉴**：**全局单例池**，应用不自己 new 池。
- **排坑**：`QObject` 有线程亲和性（对象属于创建它的线程，跨线程访问未定义）；
  `DirectConnection` 跨线程会出事。任务里不能碰 GUI 是不成文规则。
- **对 Drift 的意义**：`AppScope` 已经是"进程一份"的作用域，形态对；但池必须带
  `registry`（跨进程重建任务），这是 Qt 没有的负担，也是 Drift 必须保留的复杂度。

### 2.5 .NET WPF / WinForms —— "回调必回 UI 线程"已对齐

- **做法**：单进程 + `Task.Run` + `Dispatcher.Invoke`；`SynchronizationContext` 保证
  回调回 UI 线程；`IProgress<T>` 一等公民。
- **排坑**：`async void` 的异常直接崩进程；`ConfigureAwait(false)` 用错会死锁。
- **对 Drift 的意义**：`TaskHost::drain()` 只在 UI 线程的帧内调用、回调必在 UI 线程，
  这条契约 Drift 已经**机制化**（不用像 WPF 那样靠 `Dispatcher` 纪律），是领先处。

### 2.6 横向结论

| 框架 | 拓扑决策归属 | 角色判断位置 | 业务看见什么 |
|---|---|---|---|
| Chromium/CEF | 框架（browser 进程） | 框架 `main()` | 什么也看不见 |
| Android | 声明（manifest） | 框架 `Application.onCreate` | 一行不写，抄模板 |
| Flutter | 框架（isolate 运行时） | 不存在 | `compute(fn)` |
| Qt | 应用（可全局池） | 不涉及进程 | `QtConcurrent::run` |
| .NET | 框架（线程池） | 不涉及进程 | `Task.Run` |
| **Drift** | **应用（组合根）** | **应用 `Bootstrap::run`** | **两行 + 两个概念** |

**共性是：拓扑决策与角色判断都属于框架，且被封装。Drift 唯一越界的是"这一层漏在应用文件里"。**

## 3. PHP / TypePHP 的硬约束（决定方案上限）

| 约束 | 后果 |
|---|---|
| PHP 没有能跑 PHP 代码的用户态线程（`ThreadTaskHost` 只跑 C++ IO，不跑 PHP） | 跑业务逻辑的后台**只能是进程**，无法像 Flutter/Qt 那样"一行起线程" |
| tpc 入口固定为 `-m bin` → `Bootstrap::run()` | 角色分流**无法上移到框架**，最早就只能在 `Bootstrap::run()` 第一行 |
| 跨进程只能传 JSON 标量/数组 | `Job` 必须 `NamedJob` + `FIELDS`，`registry` 必须两侧一致 |
| 每个 worker = 一整套 AOT 运行时（几十 MB） | 进程数必须受控，池必须懒扩张；不能"每次任务起一个进程" |
| AOT 无完整反射（Partial） | 不能靠"扫类找 registry"做自动装配；`class_exists` 类魔法有坑 |
| 闭包是 AOT 的已知税 | 收口 API 不应新增闭包层 |

⇒ **方案上限**：可以在应用文件里把"两行 + 两个概念"压成"一行 + 一个概念"，
**不能压到零行**，除非改 tpc（上游，不可控）。

## 4. 方案推演

### 方案 A：维持现状（两行原语）

- 收益：0。
- 代价：0。
- 评价：显式、可读、无魔法，但认知负担留在应用作者身上。**不是错误答案，是不做功的答案。**

### 方案 B：`Desktop::boot()` 装配器（返回可链式装配器）

```
$desk = Desktop::boot('watermark', JobRegistry::make(), workers: 1);
if ($desk === null) return;
$desk->platform(new Win32Platform())->window(...)->minSize(...)->run();
```

- 收益：两行 → 一行 + null 判；`platform` / `scope` / `WindowSet` 全被收进一个对象。
- 代价：
  - **撞 `app-bootstrap-loop` 判据**（要求组合根出现 `new WindowSet(`）；
  - `Desktop` 成为上帝对象，`$scope` 的取得路径改变，所有应用构造器签名受影响；
  - `beforeRestore` / `beforeAttach` / 双窗这些应用语义要塞进链式 API，反而更难读。
- 评价：**收益中等、代价偏大**，不推荐。

### 方案 C：只改名（`AppScope::background()`）

```
$scope = AppScope::background(JobRegistry::make(), workers: 3);
```

- 收益：语义从"装配后台"变成"声明后台"，但**还是一行**，角色分流那行没动。
- 评价：换汤不换药。

### 方案 D：约定式自动装配（零行）

- 设想：`AppScope::make()` 自动按应用命名空间找 `Jobs\JobRegistry`，自动装池。
- 致命问题：
  - AOT 无完整反射，靠 `class_exists` / 字符串拼类名有坑；
  - 隐式魔法违反本仓"显式优于隐式"的纪律（也是历史多次事故的教训来源）；
  - 应用名 → 命名空间是隐式映射，改名即静默失效。
- 评价：**不做**。

### 方案 E（推荐）：`AppBoot::enter()` 单行门面

```
// 第一行：既是角色分流，也是建作用域 + 装后台；返回 null = 我是 worker，已收工
$scope = AppBoot::enter(JobRegistry::make(), workers: 1);
if ($scope === null) {
    return;
}

$platform = new Win32Platform();
$dialog   = ...;                       // 应用语义仍在这里
$scope->setDialog($dialog);

$set = new WindowSet($platform, 'watermark');
$set->open(...)->setMinSize(...)->onSemantics();
$set->run();
```

- `AppBoot::enter()` 内部顺序（只写一处，顺序契约由它保证）：
  1. `WorkerProcess::isWorker()` → true 则 `ProcessWorker::serve()` 并返回 `null`；
  2. `WorkerProcess::executable()` → 空则 `setTaskHost(null)`；
  3. 否则 `new ProcessTaskHost([exe, SWITCH], registry, workers)` + `prewarm()` + `setTaskHost()`；
  4. 返回装配好的 `AppScope`。
- 收益：
  - 两行 → 一行；概念从"双角色 + 两块装配"降为"**进入应用 / 返回 null**"；
  - 顺序契约（预热与 `setTaskHost` 必须早于 `attach`）由**一个地方**保证，应用无法写错；
  - **不破坏 `new WindowSet(` 判据**；不改应用构造器签名；`$scope` 形态不变。
- 代价：
  - 引入 `null` 返回值语义（但 `serveIf()` 的 `bool` 也一样要判断，成本没增加）；
  - `AppBoot` 是新类（AOT 需一次全量，属已知一次性成本）。
- 评价：**收益/代价比最好**，且完全落在现有判据框架内。

### 方案 F：改 tpc 加前置钩子（零行）

- 需要上游 tpc 在调 `Bootstrap::run()` 之前提供一个"应用可注册的早期钩子"。
- 不可控、收益归一，**不做**；仅作为"若将来能改上游"的备选记录。

## 5. 推荐落地顺序

1. **P0（本轮可做）**：把 `serveIf` + `useBackgroundJobs` 合成 `AppBoot::enter()`，
   三份组合根各减一行；`worker-argv` lint 不变；补一条 `AppBootTest`
   （UI 角色返回 scope、worker 角色返回 null、无 exe 时 scope 无端口）。
2. **P1（DX 杠杆最大）**：`drift create` 脚手架生成带 `AppBoot::enter()` 的组合根，
   模板注释写明"这一行是框架要求的角色分流，业务不用改"。**把概念关进生成代码**，
   业务作者永远不需要理解 `--drift-worker`。
3. **P2（可选）**：`app-anatomy.md` 把这一行定位成"框架要求的固定前缀"（类比 C 的
   `int main`），而不是"你需要理解的双角色"。文档措辞改变认知负荷。

## 6. 不建议做的事（排坑清单）

- **不要试图把角色分流上移进框架**：tpc 入口固定，除非改上游，否则做不到；半吊子方案
  只会多一层间接。
- **不要做自动装配（方案 D）**：AOT 反射不全 + 隐式映射，静默失效风险高于收益。
- **不要为"统一"把双窗 / 材质 / 恢复 / Dialog 塞进配置对象**：它们是差异不是样板，
  A23 已裁决过；塞进去只是把负担换个地方放。
- **不要改 `Bootstrap` 里 `new WindowSet(` 的形态**：`app-bootstrap-loop` 判据护的是
  三次真实事故（手写循环漏接线、静态钩子不卸导致关窗崩），不能为省一行让路。
- **不要照搬 Flutter 的 `compute()` 命名**：Drift 的 `enter()` 返回作用域，不是"跑一个
  函数"，语义不同；照搬名字会让读者误以为是 `Isolate.run` 那种一次性任务。
