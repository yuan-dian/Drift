# 技术债审计与重构裁决（2026-11-02）

> 输入：`src/` 374 文件 / 27,831 行 · `apps/` 6 个应用 16,243 行 · `PITFALLS.md` 188 条
> **项目年龄：18 天**（首个提交 2026-10-15，628 次提交，平均每天 35 次）
> 上游：`ANALYSIS-watermark-dx-2026-11-02.md`（DX 视角） · `arch-v2/12-Application拆分.md`（十步拆分记录）
> 本文视角：**结构债**。DX 那篇讲"用起来累"，这篇讲"为什么会累、以及怎么让它不再累"。
> 约束：**兼容性可破坏**（用户已授权）。所以每条方案都按"最优形状"给，不按"最小改动"给；
> 需要迁移的地方给机械迁移路径，而不是留兼容层。

## 0 结论

### 0.1 一句话

**这个框架的问题不是"设计得不好"，而是"没有扩展点"。**

每一次新增能力，框架里唯一可用的落点是"再加一条判据 / 再加一个兼容方法 / 再加一个静态计数器"。
于是 18 天后我们看到：`needsFrameNow()` 有 8 条判据、`Application` 有 89 次提交、38 个
进程级静态可变字段、269 个 `@api` 类里有一半没有真实用户。

`arch-v2/12` 拆了十步（TextEditingBridge / InputRouter / OverlayManager / PumpHost…），
方向完全正确，但**拆的是代码位置，不是职责边界** —— 所以 Application 从 1,919 行变成 2,061 行，
净增 142 行（+7.4%），提交频率仍是第二名的 3 倍。

**该做的不是再拆一次，是补上缺的那几个"扩展点"**，让"新增能力"有地方可去、有类型可依、
漏了会报错。

### 0.1b 为什么是现在（这条决定"要不要做"，而不是"怎么做"）

**18 天 / 628 次提交 / 27,831 行** —— 平均每天 35 次提交。这个速度下，"补丁式演进"
不是设计失误，是**必然**：结构决策需要停下来想，而停下来就意味着当天少 30 次提交。

反过来说，这是偿还成本最低的时刻，之后每过一天都更贵：

| 现在（18 天） | 再等 3 个月 |
|---|---|
| 6 个应用，全在你手上，破坏性变更一次改完 | 可能有外部应用 / 同事在用，破坏一次要协调 N 方 |
| 471 条 smoke 是**你自己的**测试，跟着改就行 | 测试被当成"规格"，改测试等于改契约 |
| 所有设计意图还在你脑子里（注释可以自由重写） | 注释成了唯一信源，删改要考古 |
| `PITFALLS` 188 条还能逐条判断"哪些该变 lint" | 变成 500 条，没人读 |

★ 更关键的一点：**这 18 天的产物质量远高于"赶工"的常态** —— 471 条 smoke、1,125 条单测、14 项闸门、
确定性软光栅、订阅者异常隔离、版本号缓存。所以问题不是"要不要重写"，是"要不要补上
那 3 个缺失的扩展点"。**补扩展点 ≠ 重写**，两者成本差一个数量级。

### 0.2 三条不要动（先说这个，避免重构把好东西拆掉）

| 项 | 为什么是对的 | 证据 |
|---|---|---|
| **Widget / Element / RenderBox 三棵树** | 与 Flutter 同构，被十年工业实践验证；不可变 Widget + 正交 Element 是"参数整体换新 ⇒ 不存在字段半同步"的结构保证 | `Element::update()` 注释；`PITFALLS` 里没有一条是"三棵树结构错了" |
| **拉取式 `Computed` + `Versioned` 版本号** | 一次事务改两个字段，中间态无人可见（glitch 结构上不存在）；不需要拓扑排序 | `Computed` 类注释；`03` §4.2 |
| **订阅者异常隔离** | 一个订阅者抛异常不会饿死其余订阅者，且延迟到通知完成后才上报 | `Subject::notifyChanged()`；§11.3 RT-3 |

顺带一个反直觉结论：**`Computed` 设计对，但没人用**（全仓 1 处使用）。所以"对"不等于"该留"，
见 D7。

## 1 债务的生成机制

不谈机制只谈清单，改完这一批会长出下一批。以下四条是**可测的生成机制**，不是感慨。

### 1.1 机制一：新增能力没有"扩展点"，只能落在中枢

`Application` 是唯一同时持有 Element 树、FocusManager、OverlayManager、PumpHost、
FrameClock 的地方。所以"某个新特性需要一帧"这件事，除了往 `needsFrameNow()` 里加一条判据，
**没有第二种写法**。

于是它长成这样：

```php
public function needsFrameNow(): bool         // src/App/Application.php:1225
{
    if ($this->focusRingTarget() !== $this->paintedFocus) return true;   // 第 7 判据（焦点环）
    if ($this->frame?->hasPendingPaint()) return true;                   // 第 8 判据（像素脏）
    return $this->overlayLayout->panelsLagBehind();                      // 第 6 判据（面板落后）
}
```

注释自己写着每条判据对应的真机症状：

```text
第 6：远程搜索结果到了、数据也对，面板却永远停在旧内容
第 7：键盘 Tab 换焦点后，环要等下一次鼠标移动才出现
第 8：悬停零反馈 / 滚动条淡出从不发生
```

**这三条的形态完全一样**：某个东西欠一次重绘，但没人告诉帧时钟。补法也一样：加一条 `||`。

这不是"补得不好"，这是**接口缺失**。Flutter / Qt / WPF 里同一件事是一个动词：

| 框架 | "我要一帧" |
|---|---|
| Flutter | `SchedulerBinding.instance.scheduleFrame()` / `requestLayout()` / `markNeedsPaint()` |
| Qt | `QWidget::update()`（可合并）、`updateGeometry()` |
| WPF | `InvalidateVisual()` / `InvalidateMeasure()` |
| Compose | `Recomposer` + snapshot 失效 |

它们都是**推**：谁脏谁喊。Drift 是**拉**：调度器每轮挨个问 8 个问题。

推和拉的差别不是性能，是**扩展性**：推的模型加新特性时不需要改调度器；拉的模型每加一个特性
就要改调度器的判据列表。所以判据只会继续长。

### 1.2 机制二：量具与实现绑死，重构即改测试

`State` 上有 6 个进程级静态计数器（`pendingDirty` / `markedCount` / `buildingState` /
`rebuiltCount` / `mountedThisFrame` / `frameWantedCount`），`Frame` 上有 4 个，`RenderBox`
上有 4 个 —— 全仓 **38 个静态可变字段**。

其中约 20 个是**只给测试读的量具**（`settleRunCount` / `paintSkipCount` / `pairChecks`…）。
它们的存在本身是好事（"让复杂度成为可断言的东西"这条纪律很对），但它们写在**生产类的私有静态字段**上，
于是：

- 想给 `Application` 换一个实例，得先动 38 个字段；
- 想并发跑两个 Application（多窗口 / 一个进程里跑两个根），**结构上不可能**；
- 想改一个内部实现，读计数器的 smoke 用例会红 —— 而它们红的理由不是"行为变了"。

### 1.3 机制三：API 表面按"想象的需求"预留

269 个 `@api` 类（分布在 313 个文件里），`apps/` 实际 import 了其中 137 个（**50.9% 触达率**）。
其中两个原语是彻底的零使用：

| 原语 | 设计意图 | 真实使用 |
|---|---|---|
| `Cell`（单值门控） | "设同值不重建" | **0 处**（`src` + `apps` 全无调用；只有 `M2.php` 里的同名无关类） |
| `Computed`（派生值） | 拉取式缓存 | **1 处**（`UserStore::visible()`） |

`Cell` 里甚至有一个恒为 `true` 的字段，注释说"留着是为了让未绑定这件事在类型系统里有位置"：

```php
/** @internal 恒为 `true`。★ 看着多余，它留着是为了让"未绑定"这件事在类型系统里有位置 */
private bool $bound = true;
```

**这是死代码**。它不会有第二条创建路径，因为那条路径（`Store` 里要一个不标脏的 `Cell`）
至今没有被需求证明过。

每个"预留"的代价不是行数，是：要写在 `API-SURFACE.md`、要有 smoke、要进累加器、
后来的人读它时要判断"这个能不能用"。**API 的维护成本随表面积线性增长，与使用量无关。**

### 1.4 机制四：正确用法靠文字承载，不靠结构约束

```text
PITFALLS.md              188 条 / 4,222 行 / 302 KB
src 里 "★" 出现          3,440 次
"旧" 出现 213 次 / "之前" 192 次 / "兜底" 76 次 / "上一版" 11 次
docs/*.md                22 篇 19,080 行 + arch-v2 13 篇 12,717 行 = 31,797 行
src/*.php                27,831 行
```

**文档行数 > 代码行数（1.14 倍）。**

其中最能说明问题的是这条坑（`PITFALLS` 第 319 条）：

> `$this->application()` 不存在 —— **照抄自己的 docblock 把真机打崩**

也就是说：**注释可以撒谎，而且撒过谎**。当一个框架的正确用法必须靠 3,440 个 ★ 来传递时，
说明这些约束中至少有一部分**本该是类型、本该是编译错误**。

举个已经做到的正面例子（说明"能变成结构"）：

```php
// Widget::mutate() —— 封存后再写直接 Fatal，不靠注释提醒
if ($this->sealed) { Errors::report('已封存的 Widget 不能再改：' . ...); }
```

这条就是"把纪律变成机制"的范式。**D1–D7 的每一个方案，最终判据都是"能不能变成这类断言"。**

### D1 · 帧调度：从"拉"改成"推"

#### 症状

`needsFrameNow()` 8 条判据，`wantsFrameRhythm()` 2 条，`nextDeadlineMs()` 1 条。三处互不
知晓，谁也不敢删。

更糟的是**两套"要一帧"机制并存且不相交**：

```php
// 路径 A：State::requestFrame() —— 全仓只有 1 个调用点（AnimatedOpacityState）
public function requestFrame(): void { self::$frameWantedCount++; }   // 只 ++

// 消费点：Application::frame() 内部，帧**已经跑起来之后**
$frameWanted = State::frameWantedCount();
if ($frameWanted !== $this->lastFrameWanted) { $this->animating = true; }
```

`requestFrame()` **不能让帧时钟醒来**。它只能在"下一帧恰好有人叫"时起作用。注释指望的
"settle 期间起飞的动画"能对上，是因为那时候通常还有别的东西欠帧。这是**巧合正确**。

#### 证据

| 位置 | 内容 |
|---|---|
| `Application.php:1225-1241` | 8 条判据，注释逐条标注对应真机症状 |
| `State.php:493-497` | `requestFrame()` 只 `++` 一个计数器，不触碰帧时钟 |
| `State.php:493` 全仓调用点 | 1 处（`AnimatedOpacityState.php:48`） |
| `FrameClock.php:168-171` | 决策 = `wantsFrameRhythm() ? 16ms : ∞` + `nextDeadlineMs()` |

#### 成因

调度器没有"请求"这个概念，只有"状态询问"。所以每个新局面都得教会调度器问一个新问题。

#### 参考

| 框架 | 机制 | 关键性质 |
|---|---|---|
| Flutter | `scheduleFrame()` + `SchedulerPhase` | 请求可合并、可在任意 phase 发 |
| Qt | `update()` / `updateGeometry()` | 请求可合并，**重复请求不叠加成本** |
| WPF | `InvalidateVisual()` / `InvalidateMeasure()` | 同一帧内多次失效只重跑一次 |

三者共同的形状：**一个单调递增的"欠帧"序号，任何人可以 +1，帧末归零。**

#### 方案

```php
// 新增 src/App/FrameScheduler.php（~120 行，含诊断）
final class FrameScheduler
{
    private int $requested = 0;   // scheduleFrame() 每调一次 +1
    private int $served    = 0;   // 每帧结束 = 当帧开始时的 requested
    private bool $inFrame  = false;

    /** 唯一入口：任何人想"下一帧再画一次"就调它。幂等（同一帧内多次调用成本 = 一次自增）。 */
    public function scheduleFrame(): void
    {
        $this->requested++;
    }

    public function wantsFrame(): bool
    {
        return $this->requested > $this->served;
    }

    /** 帧末由 Frame::run() 调；顺便做"欠了但没人消费"的诊断（见下） */
    public function frameServed(): void
    {
        $this->served = $this->requested;
    }
}
```

然后**删掉 `needsFrameNow()`**，把 8 条判据改成 8 个调用点 —— 落点就在"变化发生的现场"：

| 原判据 | 新调用点 | 为什么这里不会漏 |
|---|---|---|
| 焦点环目标变 | `FocusManager::setFocus()` / `hoverTo()` | 改目标的唯一入口 |
| 像素脏 | `RenderObject::markNeedsPaint()`（已有） | 标脏的唯一入口 |
| 面板落后 | `OverlayLayout::markPanelStale()` | 面板内容更新的唯一入口 |
| 动画在跑 | `AnimationController::forward()` / `tickFrame()` 有进展时 | 起飞的唯一入口 |
| 异步在途（轮询） | `PumpHost::drain()` 后 | drain 的唯一调用点 |
| 定时器到点 | `after()` 注册 / 触发处 | 定时器的唯一入口 |

**"push 会不会变成另一种静默？"**（必须回答，否则方案不成立）

会，但失败形态不同，而且可以变成断言：

| | 拉（现在） | 推（方案） |
|---|---|---|
| 漏了 | 该动的东西不动，**没人知道为什么** —— 要查 8 条判据 | 该动的东西不动，**故障点就在那个功能里** |
| 可检测性 | 只能靠人眼发现"某处不刷新" | 可加闸门：连续 3 帧 `wantsFrame()==false` 但 `State::pendingDirty()>0` 或 `Frame::hasPendingPaint()` 为真 ⇒ **FAIL** |

最后这条是关键：它把"漏调 `scheduleFrame()`"从静默缺陷变成**可断言的矛盾**
（"有脏活但没人要帧"是不可能状态）。这就是 §1.4 说的"把纪律变成机制"。

#### 破坏面

- 删除 `Application::needsFrameNow()`（`@api`，但只有测试在用）→ 改 3 处 smoke。
- `State::requestFrame()` 语义改为"真的叫醒帧"（现在是上膛）→ 调用点只有 1 处，且语义变强。
- `wantsFrameRhythm()` 保留（轮询节奏是另一件事：**多久问一次** vs **要不要问**），但它不再是"欠帧"判据。

#### ★ 与 D3 的依赖：先用静态门面过渡，别等

`RenderObject::markNeedsPaint()` 是 **static**，而 `FrameScheduler` 要的是实例
（`scheduleFrame()` 得知道是哪个应用的帧）。两者直接对接会撞上 D3②（把静态变实例，
排在期三），若严格按依赖序，D1 就得挪到 D3② 之后 —— 那等于把收益最大的一条压到最后一期，
**不可接受**。

裁决：D1 用一层**静态门面**过渡。

```php
// src/App/FrameRequest.php —— 唯一的静态入口（~40 行）
final class FrameRequest
{
    private static ?FrameScheduler $scheduler = null;

    /** @internal Application::attach() 里绑一次 */
    public static function bind(FrameScheduler $s): void { self::$scheduler = $s; }

    /** 任何人想"下一帧再画一次"就调它 —— 静态上下文（RenderObject）也能调 */
    public static function schedule(): void { self::$scheduler?->scheduleFrame(); }
}
```

代价与它换来的东西：

| | 静态门面（现在） | 纯实例（D3② 之后） |
|---|---|---|
| 多实例 | ❌ 只有最后 bind 的那个收到 | ✅ 天然隔离 |
| 收益 | D1 可以在期二就落地，不用等整个 D3 | —— |
| 迁移成本 | `FrameRequest::schedule()` 的调用点全在框架内部（约 15 处） | 一次 `grep` 换完 |

★ **这不是"兼容层"**（第 4 节的纪律禁的是"旧 API 留壳"）：`FrameRequest` 是一层
**有明确退役条件的显式过渡**，退役条件写在类注释里 —— "D3② 落地后删除本类，
调用点改 `$this->pipeline->scheduler()->scheduleFrame()`"。留一个 `@deprecated` 的旧 API
让调用方二选一，和留一个"只有一个实现、但先把调用点统一"的门面，是两件事。

#### 验收

1. `needsFrameNow()` 不存在，`grep` 为 0。
2. 新增闸门项：`pendingDirty > 0 && !wantsFrame()` 连续 3 帧 ⇒ FAIL。
3. 现状 8 条判据对应的 8 个真机场景（焦点环 / 悬停 / 滚动条淡出 / 远程面板 / 动画起飞 /
   异步轮询 / 定时器 / 尺寸变化）在 smoke 里各有 1 条用例，删除判据后仍绿。

### D2 · 补上"节点形状"抽象层

#### 症状

加一个**最简单的容器控件**（`Padding`）要写 3 个方法 + 关联 1 个 Element 类：

```php
final class Padding extends RenderBoxWidget
{
    public function expandChildren(): array { return [$this->kid]; }        // ① 声明子
    public function createRenderObject(BuildContext $c): RenderBox { return new RenderProxy(); } // ② 造盒
    public function createElement(): Element { return new ProxyElement($this); }  // ③ 指定 Element
}
```

而 Flutter 的等价物是：

```dart
class Padding extends SingleChildRenderObjectWidget {
  @override
  RenderPadding createRenderObject(BuildContext context) => RenderPadding(padding: padding);
}
```

**一个方法**。因为 `SingleChildRenderObjectWidget` 已经承诺了"我恰好一个子节点"，
Element 的管子逻辑（`adoptBoxes` / 子盒挂接 / 顺序）由 `SingleChildRenderObjectElement` 统一实现。

#### 证据

```text
function createRenderObject      37 处
function createElement           23 处
function expandChildren          13 处
function adoptBoxes               9 处
Element 子类                     13 个（其中 10 个只为覆写 expand()/adoptBoxes() 而存在：
                                 Proxy / Flex / Stack / Wrap / Table / SegmentedControl /
                                 AppBar / Dock / ErrorBoundary / ThemeScope）
```

23 处 `createElement()` 里，绝大多数返回的是 `ProxyElement` 或另一个通用 Element ——
**重复的是"管子"（把子盒收进自己），不是逻辑**。

#### 成因

`Element` 是一个通用类，它用"基类空实现 + 容器覆写 `adoptBoxes()`"表达"我有子节点"。
于是每个容器都要自己实现一次管子。这是**用继承的空实现代替形状分类**。

Flutter 的解法是把"形状"提升为类型：Widget 三分类 → Element 三分类 → 一一对应。
形状在类型里，"我有几个子"这件事就变成了**编译期事实**，不需要每个控件重新声明。

#### 方案

```php
// src/Widget/SingleChildRenderObjectWidget.php
abstract class SingleChildRenderObjectWidget extends RenderBoxWidget
{
    private ?Widget $child = null;

    public function child(Widget $c): static { $this->mutate(); $this->child = $c; return $this; }
    public function childWidget(): ?Widget { return $this->child; }

    final public function expandChildren(): array
    {
        return $this->child === null ? [] : [$this->child];
    }

    final public function createElement(): Element
    {
        return new SingleChildElement($this);
    }
}

// src/Widget/SingleChildElement.php —— 管子逻辑只写一次
// ★ API 照抄现有的 ProxyElement::adoptBoxes()（它已经是这个形状的雏形）
final class SingleChildElement extends Element
{
    #[\Override]
    protected function expand(): array
    {
        /** @var SingleChildRenderObjectWidget $w */
        $w = $this->widget;
        $kid = $w->childWidget();

        return $kid === null ? [] : [$kid];
    }

    #[\Override]
    protected function adoptBoxes(): void
    {
        $box = $this->renderObject();
        $kid = $this->childAt(0)?->effectiveBox();
        if ($box instanceof RenderProxyBox && $kid !== null) {
            $box->setChild($kid);   // setChild() 收非空 ⇒ 空子不调（与现有 ProxyElement 一致）
        }
    }
}
```

★ 顺手一处对称性缺口：`RenderProxyBox` 有 `setChild()` 但**没有** `clearChild()`，
而多子容器有 `clearChildren()`。单子容器今天靠"子永远非空"回避了这个问题
（`Padding`/`Center` 都要求必填子），所以它不是 bug；但形状上该补齐，否则将来第一个
"可空子"的容器会踩到"旧子盒没摘"。

多子版本同形，只是挂子用 `clearChildren()` + `addChild()`（`FlexElement::adoptBoxes()` 已经是这么写的）：

```php
final class MultiChildElement extends Element
{
    #[\Override]
    protected function adoptBoxes(): void
    {
        $box = $this->renderObject();
        if ($box === null) { return; }

        $box->clearChildren();
        foreach ($this->children as $child) {
            $b = $child->effectiveBox();
            if ($b !== null) { $box->addChild($b); }
        }
    }
}
```

**效果**：`Padding` 从 77 行 → 约 30 行；`createElement()` 覆写从 23 处 → 5 处以内
（只剩 `StatefulWidget`/`StatelessWidget`/`Offstage` 这类形状特殊者，以及 `AppBar`/`Dock`
这类"子盒种类不同"的容器）；`adoptBoxes()` 覆写从 **9 处** → 3 处以内。

★ 注意 `ProxyElement` 今天是 `Padding`/`Center`/`Align` 等十几个容器的共用 Element，
**它本来就是 `SingleChildElement` 的雏形** —— 这一步不是发明新东西，是给已有的东西一个正确的名字
并把 `expand()` 的管子逻辑收进去。

#### 破坏面

- `Padding::child()` / `Center` 等已有的"取子"方法可能与基类 `child()` 冲突 → 基类用
  `child()` 存、`childWidget()` 取，命名错开。
- 13 处 `expandChildren()` 改为继承 —— 但签名不能变（`final` 会拦住那些形状不规则的：
  `ForEach` / `Spacer` / 条件节点）。所以**只对真正单子/多子/叶子的控件启用**，
  形状不规则者继续直接继承 `RenderBoxWidget`。**这是有意的：抽象只覆盖 90%，不追求 100%。**

#### 验收

1. `grep -c "function createElement" src/Widget` ≤ 5。
2. `grep -c "function adoptBoxes" src` ≤ 3（三个形状各一次）。
3. 现有 471 条 smoke 全绿（这是纯等价重构，行为必须零变化）。
4. 新增一条"教程式"判据：`apps/tutorial` 里加一个自定义单子控件，行数 ≤ 40（现在约 90）。

### D3 · 把 38 个静态字段收进实例

#### 症状

```text
src/Widget/State.php        6 个（pendingDirty / markedCount / buildingState / rebuiltCount / mountedThisFrame / frameWantedCount）
src/App/Frame.php           4 个（settleRunCount / settleSkipCount / paintRunCount / paintSkipCount）
src/Layout/RenderBox.php    4 个（layoutEpoch / layoutCount / paintCount / replayCount）
src/Layout/RenderObject.php 1 个（paintEpoch）
其余散落                     23 个
------------------------------------------------------------
合计                        38 个 private static 可变字段
```

后果不是"脏"，是**能力边界**：

- 一个进程只能有一个应用实例（`State::$pendingDirty` 是全局的，两个根会互相清计数）；
- 一个进程只能有一个窗口（`RenderObject::$paintEpoch` 同为全局）；
- 测试之间必须串行且严格复位（`PITFALLS` 已有"smoke 插新用例必须恢复现场"一条）。

`docs/MULTI-WINDOW-2026-10-30.md`（783 行）已经在设计多窗口，而**这 38 个字段是它的硬阻塞**。

#### 成因

早期为了"零成本计数"（一条 `add`）和"测试能读到"（静态最省事）做了这个选择。
在单窗口 + 单应用 + 串行测试的前提下，它是正确的。前提变了，它变成债。

#### 参考

- Flutter：`RenderObject` 的 `_layoutCount` 之类**不存在**；`PipelineOwner` 持有脏列表，
  binding 是实例（`WidgetsFlutterBinding` 可多引擎）。
- Qt：`QPaintDevice` 的 `paintEngine` 在实例上；`QWidget::update()` 走 `QApplication` 的
  事件队列，但**脏区域在 widget 上**。

#### 方案

分三层搬，每层可独立验收（不要一次搬 38 个）：

| 层 | 字段 | 搬到 | 风险 |
|---|---|---|---|
| **① 量具**（~20 个） | `settleRunCount` / `paintSkipCount` / `pairChecks` / `layoutCount`… | `AppMetrics` 实例，经 `Application::metrics()` 取 | 低：只被测试读，改测试即可 |
| **② 帧/布局控制**（~12 个） | `pendingDirty` / `buildingState` / `paintEpoch` / `layoutEpoch` | `Pipeline` 实例（`Frame` 持有，`Element`/`RenderBox` 经树根反查） | 中：`Element` 要能拿到 `Pipeline`；这是"树上的静态 → 树外的实例" |
| **③ 真单例**（~6 个） | `Errors::$ring` / `Errors::$logPath` / `LayoutTolerance::$noted` | 保留静态，但**显式标注 `@process-singleton`** 并在文档里说明理由 | 无 |

第 ② 层的技术要点：`Element` / `RenderBox` 目前**没有**任何指向 `Application` 的引用
（§4.3 禁止 Widget → App）。所以不能直接塞 `Application`。

两条候选：

```php
// 候选 A：树根反查（无新引用，O(深度)）
//   Element::pipeline() 沿 parent 走到根，根持 pipeline。缺点：热路径上多跳。

// 候选 B：构造时注入（一个引用，O(1)）
//   Element::mount(..., ?Pipeline $p) —— 但 mount 签名会变，碰 471 条 smoke。
```

**裁决：选 A，且只在"低频入口"用**（帧边界 / 挂载 / 标脏）。理由：标脏虽是热路径，
但它已经是"一次方法调用 + 一次比较"，多一跳父引用可接受；而 B 会改 `mount()` 签名，
破坏面远大于收益。**这是"破坏性变更"里也要讲性价比的一处。**

#### 破坏面

- 所有读 `State::markedCount()` 之类静态方法的测试要改成 `$app->metrics()->markedCount()`。
  这类调用点集中在 `tools/smoke.php` 与 `tools/frame-*-probe.php`，估计 40~60 处，**机械替换**。
- `RenderObject::markNeedsPaint()` 是 `static` → 变实例方法。调用点全在 `RenderBox` 内部及其子类，
  约 15 处。

#### 验收

1. `grep -c "private static [a-z]* \$" src` ≤ 8（只剩真单例）。
2. 新增一条用例：**同一进程里构造两个 Application，各自跑 3 帧，计数互不干扰**。
   （今天这条会直接失败 —— 它就是这个债的判据。）
3. `MULTI-WINDOW` 的下一步不再被静态字段阻塞。

### D4 · Application 的最后一段路

#### 症状

拆了十步之后：

```text
2026-10-25  arch-v2/12 记录：Application 现 1919 行
2026-11-02  实测：            2061 行    (+142, +7.4%)
```

同期提交数 89（第 2 名 `Widget.php` 30 次，第 3 名 `RenderBox.php` 29 次）。

拆出去的五片都活得很好（`InputRouter` 1,015 / `OverlayManager` 726 / `OverlayLayout` 415 /
`PumpHost` 377 / `TextEditingBridge` 255），但 Application 本身**没瘦**。

#### 成因

**拆分是"搬家"，不是"定界"。** 搬走的每一片都通过一个 `*Host` 接口回调 Application
（`OverlayHost` / `InputHost` / `PumpHostHost`），于是：

- 片的逻辑出走了，但"片要读的宿主状态"还在 Application 上；
- 新功能仍然需要一个"能同时看到所有片"的地方 —— 那个地方只能是 Application。

`arch-v2/12 §4i` 的裁决甚至明说了这一点：

> 裁决：方案二（B 异步泵拆 `PumpHost`，A/C 留壳）
> 为什么 C 簇（语义 / 动画）不拆：读 `$this->animating` / `focus` / `root` 等宿主状态
> ⇒ host 口子 10+，与前 8 步"host 只摸应用状态、2-6 个口子"背离

也就是说：**"片"被设计成"只能通过宿主访问状态"，于是宿主永远是中心。**
这是 ten-step 拆分的天花板 —— 它天然停在"宿主 + N 个片"。

#### 参考

Flutter 的 `WidgetsBinding` 也是中心，但它用的是**另一条路**：不是"片向宿主回调"，
而是**分层 mixin 叠起来**：

```text
GestureBinding → RendererBinding → SchedulerBinding → SemanticsBinding
→ PaintingBinding → ServicesBinding → WidgetsBinding
```

每一层**只依赖下面的层**，不回调宿主。`GestureBinding` 要重绘就调 `RendererBinding`
的方法（在同一个对象上，但按层次约定）。关键是**层之间是"我调你"，不是"我问你"**。

Qt 的解法更彻底：`QApplication` 只持有事件循环与全局表，窗口状态全在 `QWidget` 上，
**没有"应用级状态"这个东西**。

#### 方案

不再继续"搬"，而是**问一个问题**：Application 上剩下的哪些字段，其实属于"某一帧"或"某一棵树"？

| 现在住 Application 的 | 真正的归属 | 搬走后 Application 剩什么 |
|---|---|---|
| `$root` / `$frame` / `$focus` | 一棵树的运行时 | 一个 `Scene`（树 + 焦点 + 覆盖层 + 语义） |
| `$animating` / `$paintedFocus` / `$lastFrameWanted` | 一帧的运行时 | 一个 `FrameState`（帧内可变，帧末重建） |
| `$frameCost` / `$worstFrame` / `$zeroViewportFrames` | 量具 | `AppMetrics`（D3 的①层） |
| `$semantics*` | 一个语义快照 | `SemanticsSnapshot` |

引入 **`Scene`**（Flutter 的 `PipelineOwner` + `BuildOwner` 的合并体，但更小）：

```php
final class Scene
{
    public function __construct(
        public Element $root,
        public FocusManager $focus,
        public OverlayManager $overlays,
        public SemanticsTree $semantics,
    ) {}
}
```

`Application` 保留：`buildRoot()` / `title()` / `theme()` / `commands()` / `attach()` / `frame()`。
**目标 ≤ 800 行。**

★ 这一步与 D3 是**互锁的**：`Scene` 要能持自己的 pipeline，就必须先把静态字段变实例。
所以顺序是 **D3 → D4**，反过来做会返工。

#### 破坏面

- `Application` 上约 20 个 `@api` 方法变更归属（`overlays()` / `focus()` / `metrics()`…）。
  应用侧调用点：`apps/` 里 `$app->overlays()` 之类的直接用很少（多数经 `BuildContext`），
  实测可机械迁移。
- 4 个 `*Host` 接口（`TextEditingHost` / `InputHost` / `OverlayHost` / `PumpHostHost`）
  可以合并为 2 个（`SceneHost` + `PumpHost`）。

#### 验收

1. `wc -l src/App/Application.php` ≤ 800。
2. `Application` 的 `public function` ≤ 30。
3. 同上两个 Application 实例用例（D3 的验收 2）通过。
4. **判债不判数**：新增一条"Application 不得直接持有绘制/布局状态"的 lint
   （字段白名单 + 前缀），防止它再长回去 —— 这才是长期有效的部分。

### D5 · 双渲染后端：能力不对等才是债，"有两个"不是

#### 症状

```text
RasterCanvas   1,964 行   软光栅，纯 PHP，CI/golden 用
SkiaCanvas       768 行   真机用，经 C++ 桥
RecordingCanvas  165 行   录制命令流
```

**`RasterCanvas` 必须存在**（`php.exe` 里没有真 Skia，`drift_skia.stub.php` 只是签名桩），
所以"删掉一个后端"不是选项。债在别处：

```php
// apps/watermark/src/Widgets/UploadCard.php:82
// ★★ 虚线的效果**只在真机上看得见**：软光栅（`RasterCanvas::drawRect`）把
//    虚线降级成实线
```

也就是说：**golden 测试跑的是 A 后端，用户看的是 B 后端，而 A 后端明确不具备某些能力。**
凡是"只在 B 上正确"的渲染特性（虚线、模糊、抗锯齿质量、渐变插值、字形 hinting），
**golden 一律验不出来**。

这与本轮会话早先那次"六条判据全绿却错色"是同一个病根的两个例子：**量具与被测对象不是同一个。**

#### 成因

历史选择"确定性优先 → 自研软光栅"。这个选择本身没错（否则 golden 不成立）。
错在**做完之后没有补上"两个后端是否等价"的判据**。

#### 参考

- Flutter：`flutter test` 的 golden 用**同一个引擎**的 CPU 后端（`SkSurface::MakeRaster`），
  所以"测过的像素"与"画出来的像素"是同一份代码。
- Qt：`QPixmap` 的 `grab()` 走同一 `QPainter`，只是 paint device 不同。

**共同点：后端可以换，但"渲染语义"只有一份实现。** Drift 有两份实现。

#### 方案（三步，按收益/成本排）

**① 建"语义一致性"判据（最便宜，先做）**

不需要后端等价，只需要**能力矩阵显式化 + 差异化断言**：

```php
// src/Rendering/CanvasCapabilities.php 已有能力位 —— 扩展成"每个能力位两后端都必须回答"
CanvasCapabilities::DASH     // Raster: false（降级为实线）  Skia: true
CanvasCapabilities::BLUR     // Raster: false                Skia: true
```

然后：

- golden 用例按 `capabilities()` **自动跳过**后端不支持的能力（今天靠人写注释）；
- 每个能力位有一个"两后端都跑"的用例，断言**差异在容许范围内**（虚线：Raster 断言实线；
  Skia 断言虚线间距）—— 这样"Raster 降级"从**注释里的知识**变成**测试里的判据**。

**② 补一份"真机渲染回归"（中等成本，解决"用户看到的东西没人测"）**

真机截图 → 与 golden 比对（容许阈值）。这条链已经有一半（`tools/golden-raster.php`、
真机探针），缺的是"自动化 + 进闸门"。做成 `php tools/gate.php --device`（可选，不阻塞 CI）。

**③ 长期：评估让 Raster 退化成"Skia 的确定性替身"，而不是"第二份实现"**

`drift_skia.cc` 能不能编出个 `php_drift_skia.dll`，让 `php.exe` 里也能跑 Skia CPU surface？
如果能，`RasterCanvas` 就能降级为"极端兜底"（连 DLL 都没有时），`src` 少 1,964 行，
两份实现的同步成本归零。

★ **这一条必须先做 30 分钟的可行性探测再立项**（不是直接干）：确认 Skia 静态库能否编译成
PHP 扩展、CPU surface 的 `readPixels` 输出是否稳定。若成立，这是全篇收益最大的一条；
若不成立，①② 就是终点。

#### 破坏面

① 改 `CanvasCapabilities` 的语义（从"后端能力查询"变成"后端能力契约"）→ 3 个实现各加一个方法。
② 新增工具，不动 src。

#### 验收

1. `grep -c "只在真机上看得见"` = 0（这类知识全部进能力位与用例）。
2. 每个能力位都有一条"两后端并跑"的用例。
3. `--device` 闸门能在真机上抓到一次人为改坏的渲染（先自己种一个 bug 验证它咬人）。

### D6 · 控件：从"全功能单体"到"能力组合"

#### 症状

```text
TableState.php   2,825 行
Table.php          636 行
```

`TableState` 的私有字段清单（节选）：

```text
laneY / laneX                 滚动
focusedRow / focusedCol       焦点
hasFocus
resizeStartX / resizeLastWidth / resizeMoved    列宽拖拽
dividerHoverKey / dividerDragKey                分隔线拖拽
hoverKey / anchor / dragAnchor / dragTo / dragStartY   单元格拖选
editingRef / draft / draftOrigin                行内编辑
revealScrollInFlight
```

**六类交互耦合在一个 State 里**。后果不是"文件大"，是**不可组合**：

- 想要"能滚动但不要列宽调整" → 做不到（除非再写一个控件）；
- 想要"表格放进一个已有的滚动容器" → 冲突（`Table` 自带滚动）；
- 想复用"列宽拖拽"到别的控件 → 拿不出来。

#### 参考

| 框架 | 分解方式 |
|---|---|
| Flutter | `DataTable` **不带滚动**（外部套 `SingleChildScrollView`）；列宽调整、行内编辑都在第三方包 |
| Qt | `QTableView` 用 Model/View：数据、代理、视图三者独立；滚动由 `QAbstractScrollArea` 提供 |
| WPF | `DataGrid` 内置全部，但每项都能关（`CanUserResizeColumns=false`），且通过依赖属性暴露 |

**共同点**：要么"拆成能力"（Flutter/Qt），要么"每项可关"（WPF）。
Drift 现在两条都没做 —— 全都有，且都不能关。

#### 方案（P2，但设计要现在定，因为它影响 D2 的形状）

把"交互能力"提升为可独立的 trait/组件，`Table` 退化为组合：

```php
// 能力（每个 ~150-300 行，可被任何控件复用）
trait ScrollableState      { /* laneX/laneY + glide + ensureVisible */ }
trait FocusGridState       { /* focusedRow/Col + handleFocusKey */ }
trait ResizableColumnsState{ /* resizeStartX… + hitTest */ }
trait CellDraftState       { /* draft + commit/cancel */ }
```

然后：

```php
final class Table extends MultiChildRenderObjectWidget
{
    use ScrollableState, FocusGridState, ResizableColumnsState, CellDraftState;
}
```

★ **不要一次全拆**。先拆 `ScrollableState`（因为 `LazyList` 已有独立实现，
拆完两处合一，立刻能验证"能力真的可复用"）。如果第一刀拆不出复用，说明抽象错了，
**及时停**——这比拆完四刀才发现方向错要好。

#### 破坏面

`Table` 的公共 API 不变（`use` 进去的 trait 方法仍是实例方法，D6 与 Widget trait 拆分同形，
那次已用反射快照验证过签名不变）。

#### 验收

1. `TableState` ≤ 1,200 行。
2. `LazyListState` 与 `Table` 共用同一份滚动实现（`grep` 只有一个 `glideByAxis` 定义）。
3. 关掉列宽调整（不加 `resizableColumns()`）时，代码路径里不出现 `RESIZE_HANDLE_W`。

### D7 · 状态原语：4 个减到 2 个

#### 症状

```text

Future.php            848 行   一次性结果 + 取消       使用：广泛
```

四个"状态原语"（`Cell` / `Subject` / `Computed` / `AsyncCommand`）+ 两个异步类型。
其中 `Cell` 零使用、`Computed` 一处使用。

#### 成因

这是"设计时想全，实现后没验证"的典型：§11.3 的状态体系是按"理想数据流"设计的，
但真实应用（6 个）只走了其中两条路。

#### 参考

- Compose：一个原语 `mutableStateOf` + 一个派生函数 `derivedStateOf` + 快照系统。
  **没有"Cell vs Subject"之分** —— 门控由快照系统统一处理。
- Riverpod：一个 `Provider` 家族。
- Qt：`QObject` + signal/slot，一个模型通吃。

成熟框架的共性：**一个可写原语 + 一个派生原语 + 一套失效机制。** 原语多了就是负担。

#### 方案

**减到两个：`Subject`（可写、可广播）+ `AsyncCommand`（异步四态）。**

```text
保留  Subject            已有，广泛使用
保留  AsyncCommand       已有，3 个应用
删除  Cell               零使用；需要"设同值不重建"时用 State::setState 的比较
降级  Computed           → @internal，只作为 SubjectBuilder 门控的实现细节
合并  AsyncValue         → AsyncCommand 内部的私有值对象（现在是公开类型，但应用不直接造）
```

`Cell` 的"设同值不重建"需求怎么满足？两种（按现状选）：

1. `State::setState()` 里做**浅比较**（只有 1 个字段时够用）—— 但这要求 State 知道"哪个字段变了"，
   不现实；
2. `SubjectBuilder::select()` **已经**做了相等门控（`if ($value === $this->selected) return;`）。
   ⇒ **用 `select` 就够，`Cell` 是它的另一种写法。**

结论：`Cell` 解决的问题已被 `select` 覆盖。删掉它，`SubjectBuilder` 的 `select` 文档里
加一句"这就是 `Cell` 的替代"。

#### 破坏面

`Cell` 是 `@api`，README/教程里若有提及要改（`grep` 一下，估计 0~2 处）。
删 `Computed` 的公共面会碰 `UserStore` 1 处（改成 `SubjectBuilder::select`）。

#### 验收

1. `src/State/` 只剩 `Subject` / `SubjectBuilder` / `Subscription` / `AsyncCommand`（+ `SubscribingWidget`）。
2. `API-SURFACE.md` 的类数下降 ≥ 3。
3. `apps/users` 的 `visibleComputed` 改动后，行为不变（smoke 绿）。

## 7 一句话收尾

`arch-v2/12` 那句"instanceof 是知识泄漏，接口是接缝"是对的，只是它只回答了**代码怎么搬**，
没回答**新东西该往哪放**。

补上 D1（要一帧的动词）和 D2（节点形状的类型），框架就有了"新东西该往哪放"的答案；
补上 D3（把静态变实例），才有多窗口；D4/D5/D6/D7 是让这个答案**撑得住**的部分。

**判断标准始终是同一个：这个约束能不能从注释里搬进代码。** 搬得进去的，债务就还清了；
搬不进去的，写进 `PITFALLS`，别再写进 `arch-v2`。

### 8.2 勘误一：D3 的"搬家"只搬了一半（已补）

报告 §D3 的方案是"字段搬到 `Pipeline`"，验收是"`grep -c 'private static' ≤ 8`"。
那条验收**过了**，但债没还完 —— 每个类上还留着一行转发：

```php
public static function rebuiltCount(): int { return Pipeline::current()->rebuiltCount(); }
```

22 个。危害不是行数，是**同一份数据有两个名字**：新代码继续用旧名字，而旧名字
还在骗人（`State::boxEpoch()` 读的是渲染树的全局序号，与"某个 State"无关）。

修法是**一个 trait + 一条 lint**：

```php
trait PipelineAccess { protected function pipeline(): Pipeline { return Pipeline::current(); } }
```

- 树内对象（`State` / `Element` / `RenderObject` 及子类）→ `$this->pipeline()->…`
  —— 语义是"**我的**账本"，多窗口时改成读节点上的引用，**调用点一行不改**（这才是扩展点）
- 树外（`Application` / `FocusManager` / 测试 / 探针）→ `Pipeline::current()->…`
  —— 语义是"**当前**账本"，观察者视角

`static-pipeline-facade` 守住不回流（反例自检：手造一个门面 ⇒ 当场报错）。

### 8.3 勘误二：D7 的论据是错的，结论仍然成立

报告说"`Cell` 解决的问题已被 `SubjectBuilder::select()` 覆盖"。

**这条不对。两者门控在完全不同的层**：

| | 门控什么 | 效果 |
|---|---|---|
| `select()` | **订阅侧**：值没变就不重跑 builder | `build()` 已经跑完了，只是少一次子树重建 |
| `Cell` | **重建侧**：值没变就不标脏 | 连 `build()` 都不进 |

所以 `Cell` 不是 `select` 的另一种写法，它是 Compose 的 `mutableStateOf`。

**那为什么还是删了**：判据换成"**样板量 vs 概念成本**"。它省的样板是两行 `if`，
代价是一个类型 + 一个创建方法 + 一套"绑定属主"的概念 + 文档里三次"什么时候用它、
什么时候不用"（`ComboBox` / `Select` / `Subject` 各写过一段解释"为什么不用 `Cell`"——
**三处解释本身就是这条债的症状**）。

门控现在写在调用点，且性质有回归保护：`tests/Unit/State/EqualGateTest.php`
（判据是"同值写不触发 `build()`"，`build()` 自己不读那个值 ⇒ 不自证）。

**`Computed` 不降级**：报告建议"降为 `@internal`"，但唯一的用户 `UserStore::visible()`
是**应用代码** —— 应用要用的东西标 `@internal` 是自相矛盾。它是 Compose `derivedStateOf`
的对等物，保留 `@api`。

### 8.4 勘误三：D6 的第一刀已经被 `ScrollLane` 悄悄做掉了

报告 §D6 的方案是"拆 `ScrollableState` trait，因为 `LazyList` 已有独立实现，拆完两处合一"。

实际上 2026-10-27（A 批第 1 项）已经把**滚动状态机**抽成了 `ScrollLane`
（偏移 + 动画 + 淡出 + 条），`LazyListState` 与 `TableState`（两个 lane）都在用它。
现在两处真正重复的只剩 3~5 行的"轴对不对"转发：

```php
public function glideByAxis(Axis $axis, float $delta): void
{
    if (($axis === Axis::Vertical) !== $this->view()->isVertical()) { return; }
    $this->lane()->glide($delta);
}
```

trait 只能共享这几行，**收益抵不上一个新抽象**。报告的验收条件 2（"grep 只有一个
`glideByAxis` 定义"）是**判据选错了**：它数的是方法名，不是重复的逻辑。

⇒ D6 剩下的真问题不是"滚动不能复用"，而是 `TableState` 里**六类交互仍耦合**（选择 /
编辑 / 列宽 / 焦点网格 / 滚动 / 构建）。裁第一刀应该裁**编辑**（`TextEditingHost`
协议已经存在，边界清楚），而不是滚动。

### 8.5 勘误四：D4 的验收条件与它的方案不匹配

报告 §D4 的方案是"把字段按归属搬进 `Scene` / `FrameState` / `AppMetrics`"，
验收是"`Application` ≤ 800 行、`public function` ≤ 30"。

但搬字段**不会减方法数**。现状 72 个公共方法里，约 25 个是**纯转发**
（`showMenu` / `closeMenu` / `showModal` / `showSnackbar` / `drag()` 一族）。
它们存在的原因是 `BuildContext` 只有主题与度量，**没有服务定位**
（Flutter 的 `Theme.of(context)` / `ScaffoldMessenger.of(context)` 一族）——
应用侧没有第二种写法，所以只能堆在 `Application` 上。

⇒ 顺序应该反过来：**先给 `BuildContext` 补服务定位，转发方法才有地方退役**。
这是一条**架构红线**（§4.3 禁止 Widget → App），要先设计再动手，不是"再拆一次"。

## 9 期三：键位映射收口，以及 §8.6 候选①的**撤回**（2026-11-02）

### 9.1 先撤回一件事：`BuildContext` 服务定位是**伪需求**

§8.6 把它排在第一位，理由是"72 个 public 里约 25 个是纯转发，根源是
`BuildContext` 没有服务定位"。这条推理**错了**，三处证据：

1. **`BuildContext` 的类注释第 ③ 条明令禁止**：「无向上查找 —— 无 `of()` /
   `find()` / `maybeOf()`（§18 已否决 Flutter 的 provider soup）」。我上一轮
   提的方案直接撞在这条已记录的架构裁决上。
2. **消费者不在应用侧**。`apps/` 里对 `Application` 的调用只有 4 处
   （`router` / `windowDrag` / `frame` / `attach`，都是入口胶水）。`showMenu` /
   `overlays` / `drag` 这些的调用点全是 `$this->…`（Application 与
   `InputRouter` / `OverlayManager` 内部）或 `$app->…`（**测试与 Application 子类
   里**，`$this` 就是 Application）。
3. **Widget 侧根本不该弹东西**。§5.1 裁决 1 的原话是"Application 管生命周期与落位，

## 11 期五：按词跳/扩选，以及一个"从来没生效过"的键位（2026-11-02）

### 11.1 为什么 `Ctrl+←/→` 是个洞

`TextKeymap` 有 12 条映射，其中方向键四个（`←/→/Home/End`）与 `Shift+` 四个。
`Ctrl+←/→` **一条都没有**。`KeyChord::is()` 是全字段比较 ⇒ `Ctrl+Left` 不命中
`KeyChord::left()` ⇒ 落到末尾 `return null` ⇒ 按键**被放行**。放行的后果不是
"按了没反应"，而是这个键流到上层：在表格里落到 `handleFocusKey()` 的
`else return false`，再往上可能被加速键吃掉（"Ctrl+← 切上一条"那种）。

⇒ 缺的不只是功能，是一个**按键归属**问题：它必须有人认领。

### 11.2 语义选择：Windows 风格，不是 readline 风格

两种成熟做法：

| | `hello world` 从 0 按 `Ctrl+→` | 使用者 |
|---|---|---|
| **readline / Emacs**（`forward-word`） | 5（当前词**尾**） | 终端、shell |
| **Windows Edit / 浏览器 / GTK** | 6（下一个词**首**） | 桌面 GUI |

选 Windows 风格：本仓的控件都是桌面 GUI 控件，用户在输入框里对
"按两下跨过两个词"有肌肉记忆。readline 的"先到词尾"在 `world` 中间会让人
觉得"少跳了一下"。

**从词中间按 `Ctrl+→` 直接到下一个词首**（不停在当前词尾）—— 三个平台一致。

### 11.3 落在哪一层：`TextBoundary` 加两个纯函数

```
TextBoundary::previousWordStart(string $text, int $offset): int
TextBoundary::nextWordStart(string $text, int $offset): int
```

- 与 `wordAt()` 共用 `classOf()`：**双击选中的词**与 `Ctrl+←/→` 跳过的区间
  一定是同一个。两套独立分类器 = "双击选中 `用户`、`Ctrl+→` 却跳进 `1`"。
- 两步/三步的顺序不可换，两条都在注释里写了反例：
  · `previousWordStart` 若先跳词再看非词 ⇒ `用户 1|` 停在空格前（差一个字节）
  · `nextWordStart` 若把"跳非词"和"停在词首"合并 ⇒ `abc, def` 停在 `,` 上
- `TextDraft` 只加两个**委托**（`previousWordStart()` / `nextWordStart()`）：
  调用方不该自己取 `text()` 再算偏移，否则"插入符口径"会漏到调用方。

`TextKeymap` 加 4 条：`Ctrl+←/→` 移插入符、`Ctrl+Shift+←/→` 扩选。
**收口键仍然不动**（`Enter` / `F2` / `↑` / `↓` / `Esc` 各控件自己的答案）。

⇒ 输入框与表格**同时**获得这 4 条，因为它们共用一个 `TextKeymap`（上一棒的收口）。

### 11.4 顺手挖出一个真 bug：`Ctrl+A` / `Ctrl+C` 在真机上从来没生效过

写这一棒时对照 `TableState` 的键位，发现它写的是
`KeyChord::make('a', ctrl: true)` —— **小写**。而壳的 `keyNameFromVk()` 对
`VK_A`–`VK_Z` 给的是**大写** `"A"`（大小写信息在 `$shift` 位里，不在键名里）。

`KeyChord::is()` 全字段比较 ⇒ 这两个分支**永远不命中**。也就是说：

> 表格的"全选"和"复制"从 2026-10-26 落地那天起，在真机上一次都没成功过。

**为什么九个月的测试全绿**：`CellSelectTest::testCtrlASelectsWholeGridAsOneRange`
构造事件也用小写。实现与测试**同源** ⇒ 谁也不是独立判据。这与 §10.2 的
`M4::$pumpKeys`（`placeMenu` 不存在）是同一族：**一个名字两种拼法，其中一种是死的。**

修法**不是**"把两处都改成大写"就完 —— 那样下次还会有人写小写。改成：

1. `KeyChord::make()` 把单字母键名归一成大写；`ctrl()` / `alt()` / `shift()`
   改走 `make()`（原先各自 `new self(...)`，绕过了归一）。
2. `TableState` 两处改成 `KeyChord::ctrl('A')` / `ctrl('C')`，与其余
   4 处消费者一致（`TextKeymap` / `TextEditingBridge` / `TextField::claimKeys()`）。

⇒ "两种写法"从此**不存在**，这类错不再是"要小心"的事。

★ 判据（进 `07`）：**当一处配置有两种等价写法时，要么归一，要么删掉一种；
不要靠"大家都记得"**。同 §10 的段名表、上一棒的键位表 —— 这是第三次同一形态。

### 11.5 变异自检

| 变异 | 期望落点 | 实测 |
|---|---|---|
| `nextWordStart` 不跳非词 | `abc, def` 停在标点 | **红 8**（`TextBoundaryTest` 6 + `TextKeymapTest` 2） |
| `previousWordStart` 不跳非词 | `用户 1` 差一个字节 | **红 9** |

## 12 期六：按词删，以及"删到哪儿"这个不能靠对称猜的问题（2026-11-02）

### 12.1 为什么是它，不是 D7

§11.7 排的两条：①按词删 ②D7 复核（`Cell` 仍 0 处使用）。

选①的理由不是"功能好听"，是它属于**同一族正在发作的债**：§11 修的是
"`Ctrl+←` 没人认领 ⇒ 按键静默穿过编辑器 ⇒ 被加速键吃掉"。`Ctrl+Backspace`
正是同一个洞的下一个成员 —— 它在**所有** Windows 应用里都是"删一个词"，
用户的手指会自己按下去。按了没反应（或触发了应用的"删除行"）不是"少个功能"，
是**按键归属错了**。

D7 是删 0 使用的代码，收益是"少一个类"，风险是"它可能是 `Computed`/`Subject`
的结构前提"（§10.6 已记）。收益/风险比明确更差，排后面。

### 12.2 裁决一：`Ctrl+Delete` 删到**词尾**，与 `Ctrl+→` 到**词首**不冲突

这是这一棒唯一需要"参考成熟框架"的地方，而且**对称直觉在这里是错的**：

| 键 | `hello |world` 上的效果 |
|---|---|
| `Ctrl+→` | 插入符到 6（`w`）—— 词**首** |
| `Ctrl+Delete` | 删掉 ` world` —— 到 11，词**尾** |

三家一致：Win32 通用编辑控件、GTK `delete-from-cursor(WORD_ENDS)`、
浏览器的 `deleteWordForward`。它们把"移动"和"删除"当作两件事：
移动要停在**能开始打字**的位置（词首），删除要吃掉**整个词**（到词尾）。

⇒ 新增 `TextBoundary::nextWordEnd()`，**不能**复用 `nextWordStart()`。
后者的失败形态极隐蔽：`hello |world` 上按 `Ctrl+Delete` 只删掉一个空格，
`world` 还在 —— 代码看着完全正常，用户只觉得"这键有点怪"。

两条分支（`ab|c def` 删 `c`；`abc| def` 删 ` def`）在方法注释里各写了反例。

### 12.3 裁决二：删除逻辑只有一份，落点是参数

`TextDraft::deleteBackward()` 原本是 15 行（判选区 → 找边界 → 改 buffer → 定插入符）。
"按词删"与它的差别**只有一个函数**（`previousBoundary()` vs `previousWordStart()`）。

这是本仓第三次撞上"逐字同义"（前两次：`TableState::editKey` 抄
`TextFieldState::handleKey`；`M4::$pumpKeys` 抄 `SurfaceAction` 名单）。所以这次
**不抄**，改成：

```
deleteBackward()            → deleteBackwardTo(previousBoundary())
deleteForward()             → deleteForwardTo(nextBoundary())
deleteBackwardTo(int $start)    // 有选区 ⇒ 删选区；否则删 [start, caret)
deleteForwardTo(int $end)       // 有选区 ⇒ 删选区；否则删 [caret, end)
```

调用方（`TextKeymap`）只负责算落点。签名里带 `To` 是为了让"这是区间删除"一眼可见
—— `deleteBackward(6)` 读起来像"向后删 6 个"。

★ 参数方向错的防御：`$start >= caret` / `$end <= caret` ⇒ `TextChange::None`。
不是"夹一下继续删"—— 越界区间说明调用方算错了，**静默做一半**比不做更糟。

### 12.4 顺带：`KeyChord::make('Left', true, false, true)` 的四个位置布尔

上一棒新写的 4 条映射用了位置参数，读出来是 `true, false, true` —— 看不出是
`Ctrl+Shift` 还是 `Ctrl+Alt`（写错一格不报错，与 §11.4 的 `'a'`/`'A'` 同族）。
改成命名参数 `make('Left', ctrl: true, shift: true)`；单修饰的直接用 `ctrl()`。
**没有加 lint 规则**：`make()` 在 `Win32Platform` 那处传的是三个变量（本来就清楚），
禁掉位置参数会逼它拆成四次三元判断，得不偿失。

### 12.5 明确**不**做的两件

1. **不把 `TextKeymap` 的 21 条 `if` 改成表驱动。**
   表驱动会让"顺序"从代码可见变成运行时数据 —— 而 §10 的 `FramePhase` 裁决刚立过
   相反的判据：**顺序是正确性约束时，不要造运行时机制。** 这里更微妙：除了
   `isText()` 必须在最后，其余条目的顺序**无关**（全字段比较），所以表也带来不了
   什么；而 `KeyChord` 不是常量表达式，表只能在方法里现建。收益 ≤ 成本。

2. **不加 `Ctrl+Home` / `Ctrl+End`。**
   单行里它们是 `Home`/`End` 的别名，加了等于"白送两个键位"。但一旦有 `TextArea`，
   `Home` 该是**行首**、`Ctrl+Home` 该是**文档首** —— 那时这两条别名都得改，
   且"改哪一条"取决于多行支持怎么落地。现在加上去，是把未来的改动面扩大一倍，
   与 §10.1（D6 撤回）同一条判据：**不为未到的场景造结构。**

### 13.2 真正的债：四行绘制写了 **10 份**

按前几棒验证过的判据（"同一件事有几个名字/几份"）扫全仓，这次扫到的不是名字，
是**四行代码**：

```php
$canvas->save();
$canvas->translate($child->offsetX(), $child->offsetY());
$child->paintComposed($canvas);
$canvas->restore();
```

| 文件 | 处 |
|---|---|
| `RenderFlex` / `RenderStack` / `RenderWrap` / `RenderSegmentedControl` | 各 1 |
| `RenderDock`（槽） / `RenderProxyBox`（单子基座） | 各 1 |
| `RenderScrollView` / `RenderPopupPanel` | 各 1 |
| `RenderTable`（header / body） | 2 |

**10 处逐字相同。** 用正则在 `src/` 全扫，`->translate($X->offsetX(), $X->offsetY())`
命中 10 次，全部是这一形状。

#### 为什么这不只是"重复"

它的失败形态是**静默的**，而且错得很贵：

| 写错的方式 | 报错吗 | 现象 |
|---|---|---|
| 漏 `restore()` | `DisplayList::assertBalanced()` 报，但帧已画完 | 只知道"某处漏了" |
| `translate` 写在 `save` 之前 | **不报**（栈是配平的） | 后面**所有兄弟**整体偏移 |
| 漏 `translate` | **不报** | 全叠在盒左上角 |
| 少一个 `save` 但保留平移 | **不报** | 平移累积，越往后越偏（像布局错） |

后三种不会让任何一道闸门变红：栈配平、命令合法、像素只是"不对"。**错的那块代码
完全正确，偏的是别人的位置** —— 定位成本是"逐盒二分"。

这与本仓前三次是同一族：段名五份、键位表两份、键名大小写两种。共同点不是"重复
难看"，是**错了不响**。

#### 顺带清掉一对多余的 `save/restore`

`RenderFlex::paintContent()` 外面还包了一层 `save()` / `restore()`，中间没有任何
`translate` / `transform` / `pushClip` —— 纯多两次调用。收口时一并删掉。

### 13.3 修法：`RenderBox::paintChildAt()`

```php
final protected function paintChildAt(Canvas $canvas, RenderBox $child): void
```

10 处改成一行。**只收"平移后画"这一步，没收 kids 容器**：

- `$kids` 的访问方式每个类都不同（`Flex`/`Wrap` 按行区间、`Dock` 是命名槽、
  `Table` 是 header/body 两个字段、`ProxyBox` 是单个 `$child`）；
- 遍历序也不同（`Flex` 主轴序、`Wrap` 按 run、`Dock` 按槽名固定序、`Stack` 层叠序）。

共有的只有这四行。**多抽一层就是给不同的东西造同一个壳**（§10.1 D6 撤回的同一条
判据）。这也回答了"要不要做一个 `RendersKids` trait"：不要，它得先假设 kids 的
形状是统一的，而事实不是。

★ 它同时是 **M5 脏矩形的唯一插入点**：将来"与脏区域不相交就跳过"只在这里加一次；
散在 10 处就得改 10 次，漏一处 = 那类容器在脏矩形模式下画错且不报错。

### 13.4 让"第 11 份"长不回来：`paint-shift` lint

收口解决的是"现在有 10 份"，没解决"明天又有人抄一份"。而抄一份是最自然的动作 ——

几何快照**。"这一格在哪"是选址、命中、滚动、绘制、键盘 reveal 的**同一个问题**，
拆成五个对象之后要么各存一份（第二个真相），要么互相回调（等于没拆）。

⇒ **D6 是长度债，不是结构债。** 2,767 行里 46% 是注释/空行，剩下 1,442 行代码
分给 82 个平均 15 行的方法 —— 这个类**已经拆得很细了**，再按职责切是搬家。

### 14.2 成熟框架拆的到底是什么

| 框架 | 拆的东西 | 为什么是这条缝 |
|---|---|---|
| Qt `QTableView` | view / model / **delegate** / selectionModel / **headerView** | model 是**用户提供的外部对象**（Drift 的数据本来就在 widget 上）；delegate 拆出去因为**要被替换**；headerView 拆出去因为它是**独立 widget**（自己的事件与绘制） |
| AG Grid | cell / header **renderer**、editor、filter | 全是**可替换插件**；内部状态仍是一个 core |
| Flutter | `State` 从 `Element` 拆 | **生命周期**（Element 被回收，State 跟着走） |

★ 共有的判据只有两条：**可替换点**、**每实例生命周期**。都不包括"职责种类多"。

★ 而**生命周期**这条本仓 §12.3 早就在用（"承载它的 Element 会不会被回收"），
它的结论是：行会被回收 ⇒ 草稿外置到 `TableState`；表自己不会被回收 ⇒ 状态住表上。
**同一条判据推不出"再拆一层"。**

⇒ 新判据（进 `07`）：**一个类里绝大多数方法都 ≤40 行时，它的债是"流水线太长"
而不是"类太大"。** 前者靠拆函数还，后者才靠拆类。混为一谈会把一个健康的类
拆成一堆互相引用的碎片。

### 14.3 真债在这儿：一个模式四段手写，而测试侧早就是一张表

`ConfigFailureTest` 的抬头原话：

> ① **受控声明必须接上报**（`selection` / `sortable` / `resizable` / `editable`）——
> 四个实例是同一个模式，故用一张表驱动，而不是抄四遍（`controlledCases()`）。

**测试侧收口了，生产侧没收。** 生产侧是：

```
build() 里 selection 一段（9 行）
build() 里 ……
assertInteractivityDeclared() 里 editable / resizable / sortable 各一段（各 9 行）
+ 一个三重循环，为这三种能力各取"第一个声明它的列"（同一个动作写三遍）
```

四段措辞各不相同（"编辑是受控的" / "列宽是受控的" / "排序是受控的"），
但结构逐字同形。失败形态是本仓最贵的那一族：

> 加第五种受控能力（例如列序拖拽）时，忘了写检查 ⇒ **声明了能力、点下去没反应、
> 界面完全正常**；而测试侧那张表会照常要求加 case —— 于是 case 有了、检查没有。

### 14.4 修法：`TableContract` —— 能力名单 + `match` 穷尽性

`src/Widget/TableContract.php`（新，204 行）：一张能力名单 + 一个 `match`。

```php
public static function capabilities(): array
{
    return ['selection', 'sortable', 'resizable', 'editable'];
}

private static function read(string $capability, Table $view, array $columns): array
{
    return match ($capability) { /* 每种能力：声明? / 声明者 / 上报? / 缺的话怎么改 */ };
}
```

★ **加能力的第一步是改 `capabilities()`**：`match` 没有对应分支 ⇒ `UnhandledMatchError`
（当场响，不是静默跳过）。这是本仓偏爱的"表驱动 + 穷尽性"组合（`FrameStage` 同款）。

★ **测试反向锁**：`ConfigFailureTest::testEveryCapabilityHasAFatalCase()` ——
契约表里的每种能力都必须有一个 fatal case，缺哪个就点名哪个。两边少一个都藏不住
（漏实现 ⇒ 静默；漏 case ⇒ 漏掉的是"这条静默失败永远测不到"，更难发现）。

★ 文案统一成一句模板，但**保留 `去掉 ->xxx()` 这条退路**（测试钉着）：只喊"你缺
上报"而不给"纯展示就别声明"的出口，会逼用户写一个空闭包 —— 那是静默坑的另一种写法。

顺带搬进来的还有 `keyOf` 必填、`cell()` 列不能 editable、`sort()` 指向不存在的列
—— 它们不是"受控声明"，但都是"挂载期就该喊"的同一件事：**契约检查**。

### 14.5 `build()` 229 行 → 30 行，`headerRow()` 9 参 → 3 参

拆成五段，每段一个方法名就是它做的事：

```
TableContract::assert($view, $columns)   // 校验
$this->prepareEditor($ctx)               // 量宽 + 编辑会话存活检查
$this->settleGeometry(...)               // 算几何 + 夹偏移 + 夹光标（写回活字段）
$this->headerRow(...) / buildBody(...)   // 表头 + 行区
TableBox::make(...)                      // 装盒
```

★ **`headerRow()` 原先收 9 个参数**：`widths / contentW / headerH / spacing /
colFirst / colEnd / colLeading` —— 这 7 个**全是 `TableGeometry` 的公有字段**。
把它拆成散参数传，等于给同一份快照造第二个表达：调用点要按正确的顺序摆 7 个数，
而其中三个都是 `float`、两个都是 `int`（`colFirst` 与 `colEnd` 写反了也不报错）。
现在收 `(BuildContext, array $columns, TableGeometry $g)`。

★ `buildBody()` 里那 56 行代码是**行循环本体**，故意没再往外拆：它的输入是
"整份数据 + 这一帧的几何 + 三个交互开关"，拆出去要么 10 个参数，要么先造一个
参数对象 —— 而后者就是 §13.3 否掉的"给不同的东西造同一个壳"。

★ 同样的位置参数风险在 `TableBox::make`（6 个连续 float）也存在，本轮**没动**：
它是 internal 盒描述，唯一调用点就在 `build()` 里、紧挨着几何快照；改成"收
`TableGeometry`"能让它少 6 个参数，但会把一个纯 float 的盒描述**绑死在表格的
几何类型上** —— 收益是注释性的，成本是一层新依赖。**记录在案，不修。**

### 15.4 修法：`SurfaceProfile::time()` + `Application::stage()`

```php
// Rendering 层（Platform 与 App 都能用）
public static function time(string $stage, \Closure $body): mixed

// App 层（多推一个 trace 段名）
private function stage(string $stage, \Closure $body): mixed
```

四个决定：

1. **住 `Rendering` 不住 `App`**：`Platform/Win32` 的三段（`beginFrame` / `present`）
   也要计时，而 `Platform` 不能依赖 `App`（§4.3）。选址理由同 `SurfaceProfile` 本身。
2. **`try/finally` 而不是"正常路径才记"**：抛异常的那一段也花了时间。写成正常路径
   才记账时，异常帧的成本会凭空消失 —— 而排查"卡住"时最需要的恰恰是那一帧。
3. **`settle` 不走 `stage()`**：它是**标记**不是真段。计时在 `Frame::run()` 内部，
   跨越整段 settle 且夹着 try/catch 与早退（`$box === null` 直接 `return false`），
   包不进闭包。⇒ 它是唯一保留裸 `$trace[] =` 的段，并在注释里写明理由。
4. **trace 从局部变量提成属性**（`private ?array $frameTrace`）：推段名的动作进了
   `stage()`，而 `stage()` 是另一个方法。

★ **闭包开销实测**（A/B，同机同树，各跑 5 次）：

| | 稳态帧 5 次 | 最小 |
|---|---|---|
| 改前（局部 `$trace` + 四行样板） | 899.6 / 1110.6 / 948.4 / 1005.3 / 958.2 | **899.6µs** |
| 改后（8 次闭包/帧） | 939.1 / 915.3 / 970.1 / 1098.7 / 974.5 | **915.3µs** |

组内波动 899→1110（23%），组间差 1.7% ⇒ **在噪声内**。而这一档里 `tickAnimations`
占 99%，成本结构没变。

### 15.5 判据：三条，且靠"名单驱动"自动覆盖未来

`tests/Feature/App/FrameStageAccountingTest.php`（4 个用例 / 28 断言）：

| # | 判据 | 挡住什么 |
|---|---|---|
| ① | `FrameStage::all()` 每段都必须有计时 | 漏一段（本轮的 `tickLateMount` 就这一条） |
| ② | 计时里不许有名单外的段 | 段名拼错被静默吞掉 / `stage()` 被调两次 |
| ③ | 每段**每帧只记一次** | 我给一段包两层 `stage()` |
| ④ | `time()` 四条契约（透传 / 开记 / 关不记 / **异常也记**） | 去掉 `finally` |

★ ③ 不能省，而且判的是**次数**不是平均：`perCall()` 是平均值，包两层时分子分母
同时翻倍，**平均看不出翻倍**。

★ **为什么不需要 lint 挡第 9 份**：判据是名单驱动的 —— 新段一旦进 `FrameStage::ORDERED`
（`selfTest()` 要求每个常量都进表），① 自动覆盖它；反过来，在 `frame()` 里补一个裸
`$trace[] =` 会让该段每帧记两次 ⇒ ③ 红。两个方向都闭了，加规则是多余的。

| **路径 B**：只走表 | 其余每一帧 ⇒ O(在动的节点)，通常 0–5 |
| **起飞点** | `State::markDirty()` · `State::requestFrame()` · `AnimatedValue::toward()` · `AnimationController::start()`（外加 `Pipeline::bumpStructure()`） |

四个决定的理由：

1. **表里存 `Element` 不存 `RenderBox`**：盒每次重建被换新（§13.2），Element 才是跨重建
   稳定的那个，而 `element->renderObject()` 永远指向当前盒 ⇒ 表项不会变成"tick 一个死盒"。
2. **一帧只走一条路径**（`if / return`，不是两个 `if`）：`RenderObject::tickAnimations()`
   没有帧戳（`State` 有），同一帧推两次就是动画快进一帧。
3. **全扫"重写"表而不是"并入"**：它在帧内的某一刻看得到整棵树，它给出的才是完整答案；
   并入会让"已经停了但这一帧没被问到"的旧项永远留着。
4. **标记位 `Element::$animationActive` 只由收表 / 出表写**，登记方只入队。第一版在
   `markDirty()` 里顺手置了 true，收表时"已在表里就跳过"正好把自己跳过 —— 表永远是空的。

### 16.3 三个坑，全是静默的

### 17.3 设计：一份 `$items`，两种渲染，退出码只有一个来源

| 元素 | 内容 |
|---|---|
| `CheckItem` | `id` / `ok` / `text` / `data` / `skipped`，三态由 `status()` 一个函数给出 |
| `CheckReport` | `tool` + `list<CheckItem>` + `summary`；`text()` / `json()` / `line()` / `emit()` |
| 退出码 | **只有** `CheckReport::exitCode()`（`ok() ? 0 : 1`），调用方不许再算 |
| 跳过 | `skipped = true`，`ok()` 仍为真（它没失败），但正文印 `skip`、JSON 给 `status:"skip"` |

四条构造期不变量，都是"静默绿壳"的形状，**在构造函数里炸**：

| # | 不变量 | 挡的是 |
|---|---|---|
| ① | `$items` 不能为空 | 「0 项全过」= 没有扫描的假绿（`frame-tax` 判据③ 的教训） |
| ② | `$id` 不能重复 | 同一件事被报两遍（§16.3 那处多余的 `requestAnimationScan()`） |
| ③ | 元素必须是 `CheckItem` | 传三元组不会报错，只会渲染成 `Array` —— 更糟 |
| ④ | `$tool` 不能为空 | JSON 里读不出是哪份报告 |

两个刻意的取舍：

1. **`text()` 与 `json()` 都不带业务话术**。全过时印什么由 `summary` 给（各工具话术不同：
   `6 项判据全过（500 行 / 30 帧）` / `GOLDEN OK（60 场景）` / `1 项全过（334ms）`），
   失败时**统一**成 `--- FAIL（n / m 条）---` —— 否则「全过」与「失败」两句话可能同时出现。
2. **失败收尾带总数**（`n / m`）。471 行的 smoke 日志里只有失败数等于没信息，
   人还得自己数正文。这条是改 smoke 时顺手发现的，回填进了 `CheckReport`。

### 19.1 开工核账：为什么这一棒不接着做工具链

§18.8 列了六条，逐条核完 —— **六条全是工具链**（`smoke --json` / `gate --json` 的失败
路径 / `probe-*` 文档 / `method-map` 的 21 个方法 / `--script` 截图 / M5 复核）。
前两期（§17 判据账本、§18 M2 尺子）也都是工具链，连着三期了。

本轮指令是「**优先核心能力与能力缺口**」。按这条重排，工具链该让位。

### 19.2 怎么找到"能力缺口"：三类差距先分层，再量

`docs/ANALYSIS-watermark-dx-2026-11-02.md` §3.2 已经把差距分过类，这个分法
直接决定"哪些抱怨是白抱怨"：

| 类别 | 含义 | 能不能消 |
|---|---|---|
| 阶段性 | 生态、控件数、文档、DevTools | 会随时间收敛，**不值得现在投** |
| 结构性 | 无热重载（AOT）、无共享内存（进程池）、静默失败（PHP 动态） | **消不掉，只能补偿** |
| **设计债 / 能力缺口** | 今天就能改 | **该做这个** |

候选与量法：

| 候选 | 是真缺口吗 | 消费者 | 成本 | 结论 |
|---|---|---|---|---|
| **撤销 / 重做** | `grep -rn "undo\|redo" src/` = **0 处** | 每个 `TextField` + 表格单元格 + `ComboBox` | 小 | **本棒** |
| 状态订阅自动化（MobX 式） | 半（能写，但易错） | watermark 21 处 `SubjectBuilder` | 中-大 | 留 |
| 表单绑定 `bind()` | 半（省 8 行/字段） | watermark | 中 | 留 |
| 布局边界（`RelayoutBoundary`） | 是（绘制侧有 `LayerCache`，布局侧没有） | 大树 | 大 | 留 |
| 交互视觉回归（`--script`） | 是（golden 只比静态帧） | 测试 | 中 | 留（§18.8 第 5 条） |

选撤销的三条硬理由：

1. **完全缺失**（不是"能写但别扭"）—— 这是"能力缺口"的字面意思；
2. **消费者确定且已在树上**：`TextField` / 表格单元格 / `ComboBox` 三处都持有
   `TextDraft`，**一处收口三处受益**；
3. **有教科书参照**：Qt 的 `QUndoStack` / `QUndoCommand`、WinUI 的 `UndoManager`、
   浏览器的 `input.value = x` 重置 undo —— 每个设计问题都有现成裁决可抄。

### 19.3 症状：不是"按了没反应"，是**静默穿过**

`TextKeymap` 的注释自己写过这个形状：

> 缺了它们的现象不是"按了没反应"，而是按键**静默穿过**编辑器。

`Ctrl+Z` 在按下时的实际走向：`TextKeymap::apply()` 不认识它 ⇒ 返回 `null` ⇒
调用方"放行" ⇒ 落到 `AcceleratorTable`。于是两种结局：
- 应用没绑 `Ctrl+Z` ⇒ 什么也不发生（用户以为坏了）；
- 应用绑了（比如"撤销删除行"）⇒ **在输入框里按 Ctrl+Z，撤销的是表格里别的东西**。

第二种比第一种难查得多，而且不报错。

### 19.4 设计：六个裁决

| # | 问题 | 裁决 | 理由 |
|---|---|---|---|
| ① | 快照还是逆操作 | **快照**（`[文本, 插入符, 锚点, 活动端]`） | 逆操作要知道"删了几个码位、每个几字节"，IME 组合期更要知道整条组合串。200 字符 × 100 步 ≈ 20 KB；写错的逆操作是"撤销之后文本坏了" |
| ② | 栈住哪层 | **`TextDraft`** | 它是唯一收口点（`applyText()` 注释原话："所有改文本的路径都收口到这里"）。放 `TextFieldState` 就要给表格再写一份 —— 正是 `TextKeymap` 注释骂过的"两处并存"形状 |
| ③ | 怎么合并 | **同类且连续**，不按时间窗 | §14 硬纪律"不读环境时钟"。纯逻辑则可测；且顺手解决 IME 组合期（组合串每更新一次都是一次 `insert`，全是 `'type'` 且连续 ⇒ 自动并成一步，不会"撤销一次只退一个拼音字母"） |
| ④ | 外部推值（`setText`） | **不进栈，且清空两个栈** | 进了栈 ⇒ 受控组件每帧灌值把历史淹没；只"不进栈"却不清 ⇒ 撤销会退到**已被外部数据取代**的文本上。浏览器对 `input.value = x` 也是重置 |
| ⑤ | 栈空时按键的返回值 | `TextChange::None`（**不是** `null`） | `null` = "这键不归编辑管" ⇒ 静默穿过（见 19.3）。栈空只是"没得撤"，键仍归编辑 |
| ⑥ | 上限 | 100 步，超了丢最旧 | 一页几十个输入框，每字段一份无限栈是**隐蔽的内存增长** |

收口之后**只有一个入栈点**（`applyText()`），四个"文本会变"的动作
（`insert` / `replaceSelection` / `deleteBackwardTo` / `deleteForwardTo`）全部经过它
⇒ 加新的编辑动作时不会漏掉入栈（漏掉的表现是"打字能撤、粘贴不能撤"，不报错）。
`applyText()` 的 `$kind` **不给默认值**，逼每个调用点表态"它该和谁合并"。

打断合并共 5 处（`moveCaret` / `selectAll` / `clearSelection` / `extendSelectionTo` /
`selectRange`），另加 `replaceSelection()` 那条"替换成同一段文本"的早退分支。

★ `clearSelection()` 那处是**对不变量的防御**，造不出"只靠它才不合并"的现场
（要有选区必然先经过上面三条之一）。这一点在文档里写明，而不是假装它也有一条判据。

**已知代价（诚实版）**：只有两个 kind ⇒ **连续两次粘贴会并成一步**（都算 `'type'`）。
要分开就得让 `replaceSelection()` 每次独立入栈，但那样 IME 组合期（若走的是
`replaceSelection`）就会每步一步 —— **组合期的正确性优先于粘贴的粒度**。
实际手感上"粘贴两次撤一次回到粘贴前"不算错，只是粗。等真的有人抱怨再拆 kind。

★ `canUndo()` / `canRedo()` 当前**没有生产消费者**（没有"撤销按钮置灰"那种 UI）。
留着是因为它们与 `undo()` / `redo()` 是同一组接口，且测试用它表达"栈里有没有东西"
比 `assertNotSame(null, $draft->undo())` 清楚得多（后者还会**真的撤一步**）。

## §20 二十期：`claimKeys` 的正确答案是删掉它 —— 键归「处理者」不归「声明」（2026-11-03）

### 20.1 开工核账：量完发现缺口比记录的小，而病比记录的大

§19.8 第 1 条的原话是「`claimKeys` 需要能跟着编辑态变」，并留了一句
「★ 先量 `FocusNode` 的不可变值对象形态要不要破」。量了三件事：

| 量到的 | 结论 |
|---|---|
| `FocusManager::claims()` 每次都实时读 `$this->focused?->widget()->focusNode()`（不是快照） | **不需要**"进编辑补声明、退出撤掉"这套动态机制 |
| `TableState::build()` 返回 `TableBox::make(...)`，**不是**新的 `Table` 实例 | ⇒「在 `build()` 里按编辑态重新 `claimKeys`」**不可行**：`Table` 是 `StatefulWidget`，`State` 换不掉自己的宿主 Widget |
| `TableState::handleFocusKey()` 在**非编辑态**处理 `Ctrl+A`/`Ctrl+C`，而 `Table` 从未声明 `claimKeys()` | ⇒ 应用只要绑了这两个键，表里就是**死码** —— 一直如此，没人发现 |

第三条是决定性的。白名单是**逐键列举**的：每个控件都得自己想一遍"我要抢哪些键"，
想漏一个就静默失效，而且"只在编辑时才抢"这种**动态让位**它根本表达不了。

### 20.2 决定性的反证：本仓自己写过正确答案

`TextEditingBridge::dispatchEditCommand()` 的注释（2026-10-21）逐字写着：

> ★ `V` 不经 `claimKeys` 声明独占：声明了就得有人接，没人接就是死键；
>   这里的"环在加速键之前"已经达到同一优先级，且门控不满足时自动让位。

这就是"**谁处理谁赢**"。所以本仓不是没有正确答案 —— 是**同一个问题有两套答案**：
剪贴板族走"环在前 + 门控回落"，其余控件走"静态白名单 + 让位判断"。
§19.8 第 1 条真正该做的不是给白名单加动态能力，而是**让白名单消失**。

### 20.3 裁决：把「编辑命令优先」推广成「焦点优先」

`InputRouter::dispatch()` 的键分支从
`Esc ⇒ 剪贴板 ⇒ 加速键 ⇒ 焦点链 ⇒ 激活`
改成
`Esc ⇒ 剪贴板(⓪) ⇒ **焦点链(①)** ⇒ 加速键(②) ⇒ 激活(③)`。

| 参照 | 顺序 | 它怎么解决同一个问题 |
|---|---|---|
| WPF / WinForms | **焦点优先** | `PreviewKeyDown` 先到控件，再冒到窗体 `InputBindings` |
| Flutter | **内层优先** | `Shortcuts` 是树上的 widget，离焦点近的赢 |
| Qt | 加速键优先 | 靠 `Qt::WidgetShortcut` **上下文**表给特例开洞 —— 与本仓原先的白名单同形，同一个漏法 |

两个主流都是焦点优先，**Qt 那条路本仓已经走过并且撞墙了**，所以改。

三条理由：

1. **不需要声明，也就不会漏**：控件认得就吃、返回 `false` 自然落给加速键。
   `Table` 的 `Ctrl+A`/`Ctrl+C`/编辑态 `Ctrl+Z` 三处死键一次全活。
2. **动态让位是天然的**：非编辑态返回 `false` ⇒ 应用收得到；进编辑 ⇒ 吃。
   这正是 §19.8 想要的"补声明/撤声明"，但一行状态机都不用写。
3. **概念数减少**：`claimKeys()` / `FocusNode::claimedKeys` / `claiming()` /
   `FocusNode::claims()` / `FocusManager::claims()` 五处一起删。

### 20.4 边界（诚实版）

- **焦点优先 ≠ 焦点通吃**：控件若"认得却不该认"就会吞掉全局快捷键。本仓所有键表
  都是显式白名单（`TextKeymap` / 各 `keyboard()`），没有"吞所有键"的实现 ⇒ 风险收敛在
  "这些键本来就该归控件"。判据第 2 条专门盯这个（控件认不得的键必须放行）。
- **`activateFocused` 仍在最后**：应用把 `Enter` 绑成"提交"时要能覆盖按钮的默认激活。
- **`Ctrl+Space` 一类的平台隐患没修**：壳在 `Ctrl` 按住时仍可能发 `WM_CHAR`
  （`AltGr` 会同时置 `Ctrl` 与 `Alt` ⇒ "按 Ctrl 就丢 char" 是错的），
  于是应用若把 `Ctrl+Space` 绑成命令、而焦点在输入框，会打进一个空格。
  这是**既有**问题（与顺序无关），修法在平台侧，本轮不动。登记在 §20.9 第 3 条。
- 顺序是 `InputRouter` 的内部契约，全仓只有那一处写；没有第二个"三环表"。

## §21 二十一期：多行输入 —— 排版层早就做好了，缺的是「编辑几何」（2026-11-03）

### 21.1 开工核账：为什么这一棒接着做能力，不回去做工具链

§20.9 列了五条，四条是尾巴（`Ctrl+C` 连续动作判据 / `Ctrl+Space` 平台隐患 /
文档级撤销栈 / §18.8 与 §16.7 的残留），一条是 M5 复核。上一期刚做完键路由，
回到工具链就是连着两次"内部整备"—— 本轮指令仍是「**优先核心能力与能力缺口**」。

| 候选 | 量的结果 | 判决 |
|---|---|---|
| **多行输入** | `RenderTextField` 注释自陈「多行输入属 M3」；`grep -n "TextArea"` 全仓**零实现**；`InlineEditorBox` 也写死单行 | **本棒** |
| 暗色主题 | `ThemeData::dark()` / `forSystem()` / `SystemTheme` / `ThemeChangedEvent` 全在 | 已有，划掉 |

选多行的三条硬理由（与 §19 选撤销同构）：

1. **完全缺失**：不是"能写但别扭"，是根本不存在 —— 表格的备注列、表单的描述、
   任何 JSON/日志/多行文本场景都没法写；
2. **消费者在树上且已预告**：`EditableText` 接口注释写着「将来的 `TextArea` /
   `CodeEditor`」，`TextKeymap` 注释写着「第三方要写第三个可编辑控件（`TextArea`）」，
   `RenderTextField` 注释写着「多行输入属 M3」—— 三处各自留了门，门后是空的；
3. **有教科书参照**：Flutter `TextField(maxLines: null)` / WinUI `TextBox`
   `AcceptsReturn + TextWrapping` / Qt `QPlainTextEdit` / Web `<textarea>`。

### 21.2 关键发现：**排版层早就能多行**，缺的只有编辑几何

这条决定了成本量级，必须先量再动手：

| 能力 | 现状 |
|---|---|
| `\n` 硬断行 | ✅ `TextLayout::breakLines()` 里就有 `LINE_FEED` 分支 |
| 按宽软换行（贪心 + 断点） | ✅ 同一处，CJK 处处可断、拉丁只在词间断 |
| 行高 / 基线 / 行框 | ✅ `TextLine` 有 `top` / `baseline` / `height` / `offsetX` / `textStart` |
| 二维命中 `(x,y) → 偏移` | ✅ `Paragraph::indexAt()` |
| **偏移 → `(行, x)`** | ❌ **缺**（这是多行插入符的全部难点） |
| 垂直滚动 | ✅ `ScrollLane` + `RenderScrollView` 的模式可复用 |
| 滚轮路由 | ✅ `Scrollable` 接口（"沿命中链找最近滚动目标"） |
| 撤销 / 按词跳 / 选区模型 | ✅ 全在 `TextDraft`，**与行数无关** |

所以本棒不是"实现多行文本"，是"补 4 个缺口点 + 把已有的接上"。

### 21.3 三个裁决

| # | 问题 | 裁决 | 理由 |
|---|---|---|---|
| ① | 新控件还是 `TextField(maxLines)` | **新控件 `TextArea`** + 新盒 `RenderTextArea` | `RenderTextField` 的几何前提就是单行（插入符 x 用 `advance(前缀)` 一次量得、选区一个矩形、高度恒一行）。塞进去会让**单行**也背上分支，而单行是绝大多数输入框。Qt（`QLineEdit`/`QPlainTextEdit`）与 Web（`<input>`/`<textarea>`）也是两个；Flutter/WinUI 能合成一个，是因为它们的盒本来就是多行几何 |
| ② | 插入符几何算在哪 | **`Paragraph::caretX()` / `lineRect()` / `selectionRects()`** | 类注释已写「光标位置的唯一入口（§8.2 坑 7）」—— `indexAt()` 是反查，这是正查，必须在同一处。放到渲染盒里就是第二个答案 |
| ③ | State 怎么不复制 | 抽 **`EditableTextState`** 抽象基类 | `TextFieldState` 除 `build()` / `caretRect()` 外 90% 与行数无关（焦点 / 通知 / 动作转发 / `Esc` 收口）。不抽就得抄一份，而抄出去的第一份就会漂（现象：多行框 `Esc` 顺手触发按钮、或只挪插入符也发 `onChanged`） |

另有两个小裁决值得记：

- **`Enter` = 换行，`Ctrl+Enter` = 提交**。让 `Enter` 兼两职就没法在段落里换行。
  没有接 `onSubmitted()` 时 `Ctrl+Enter` **不吞**（放给加速键）—— 与 §20「认得就必须处理，
  认不得必须放行」同一条：没有消费者的组合被控件截走 = 死键。
- **只做 `minLines`，不做 `maxLines`**。多行框的高度 99% 由外层给（`SizedBox`/`Expanded`）；
  而 `maxLines` 在本仓已经是"排版截断 + 省略号"（`TextStyle::maxLines`），
  两个同名不同义的东西迟早被混用。

### 21.4 顺手修掉的两个真 bug（都是"写的时候才发现"）

| bug | 现象 | 根因 |
|---|---|---|
| `Paragraph::lineIndexAt()` 认不出空行 | 空行上的插入符跳过该行、直接画到下一行 | 判据是 `offset < textStart + textLength`，而空行 `textLength == 0` ⇒ 恒假。改成「**最后一个行首 ≤ offset 的行**」 |
| `RenderTextArea::maxScroll` 恒 0 | 内容超出视口却滚不动（`revealCaret` 把偏移设成 252，盒夹回 0） | 自然高写成 `insets + max(行高, minHeight)`，漏了**段落高**；`maxScroll` 跟着算成 0 |

第二个是探针抓的（`maxScroll=0` 但 `caretTop=323`），第一个是单测抓的。
**两个都不会报错**，只会表现为"看起来怪"。

### 21.5 边界（诚实版）

- **不画滚动条**：多行框的滚动条本仓尚无设计（`ScrollBarHost` 属于 `ScrollView`）。
  插入符跟随已经保证"打字看得见" —— 不假装有。
- **`revealCaret()` 在 `build()` 里做，用上一帧的盒**：那一帧的插入符位置正是用户
  看见的位置，所以"越界了吗"判断是准的。文本刚变的情形会在**下一帧**被重新判断 ——
  每帧都查所以不会漏，一帧延迟在 60fps 下无感。
- **上下移行用上一帧的段落几何**：上下移不改文本 ⇒ 那份几何仍然有效。真要让几何
  每键重排，就得在事件里跑一次排版（得不偿失）。
- **IME 组合区间跨行没验**：`caretRect()` 给的是当前行的插入符，组合串跨软换行时
  候选窗跟着哪一行没测过（§24.2 #32 ③ 的真机键盘限制仍在）。
- **`Ctrl+Space` 一类的平台隐患不变**（§20.9 第 2 条，与本期无关）。

## §22 多行输入的滚动条 + `lines()` 固定框高（2026-11-03，对应 §21.10 第 2 条）

### 22.1 先量账：DEBT 那两行已经过期了

§21.10 第 2 条写的是"要做就得先把 `ScrollBarHost` 从 `ScrollView` 解耦"。
开工前 grep 了一遍：**`ScrollBarHost` 早就是接口**（2026-10-27 阶段 5 轴化），
`RenderTable` 已是第二份实现，`ScrollInputRouter` 的 thumb 命中 / 拖动映射、
`ScrollBarFade` 的淡出，全部只认接口 —— **解耦这件事根本不存在了**。

真正存在的是两件小事：

1. 条的**绘制**（alpha 折算 + 胶囊圆角）在 `RenderScrollView` / `RenderTable`
   各抄了一份（15 行 × 2）。第三份抄下去就是"三处公式同源、圆角各写一次"。
2. `RenderTextArea` 已有垂直滚动（§21），只差"实现接口 + 画出来"。

⇒ 本轮的真实成本从"先解耦再实现"降到"抽一份绘制 + 实现接口"。

### 22.2 三个裁决

**① 条栏宽常驻预留，不按"这一帧溢出了吗"决定扣不扣。**
折行宽度在布局期就要定，而"溢出了吗"是布局的**结果** —— 按结果决定输入是
循环依赖，临界点上会抖一帧。浏览器 `<textarea>` / Win32 `EDIT` /
Qt `QPlainTextEdit` 全是常驻占位，同一裁决。预留量 = `THICKNESS + MARGIN`（9px），
从文本可用宽度里扣。

**② 框高固定用 `TextArea::lines()`，不叫 `maxLines`。**
`lines(n)` 定的是**布局高度**（`<textarea rows>` / `QPlainTextEdit` 的语义：
框高是布局决定，内容短也不缩）；`maxLines` 在本仓已经属于
`TextStyle::maxLines`（折行画省略号）—— 同名不同义迟早被混用。
没有 `lines()` 的后果不是"少个选项"：`Column` 里的 `TextArea` 会被内容撑到
自然高 ⇒ `maxScroll` 恒 0 ⇒ **滚动条永远不出现**（§21 做的滚动条等于零消费者）。

**③ 条浮在内容之上、不随偏移平移** —— 与既有两个盒完全一致
（`RenderScrollView` 2026-10-17 踩过"offset=max 时整条飞出视口被裁干净"）。
TextArea 的条画在 `restore()` 之后。

顺带一条观察（没改代码）：给 `TextArea` 套 `.height(96)` 修饰被框架直接
Fatal（"声明了修饰但不产渲染盒"，`Errors::report` 硬中止）。**这是既有契约
在正确地工作** —— 但它也逼出了 `lines()`：多行框的高度必须由自己的 API 表达。
