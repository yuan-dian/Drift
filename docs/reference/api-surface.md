# 公开 API 面

> 说明什么算 `@api`、什么算 `@internal`，以及如何用唯一事实源生成清单、审查公开面的变化。

## 为什么要有这条线

Drift 分两层使用者：应用开发者和框架维护者。公开 API 面就是"应用开发者可以依赖什么"的边界。标成 `@api` 的是承诺稳定的公共面，可以放心调用；标成 `@internal` 的是框架实现细节，随时可能改。把这条线写清楚，应用才不会建在会动的沙子上。

这条线靠代码里的标注维护，不靠一份手写的清单文档。

## 标注的口径

只认 docblock 里的**独立标注行**，两种写法：

- 多行 docblock 中独占一行，形如 ` * @api` 或 ` * @internal`；
- 单行 docblock，形如 `/** @api ... */` 或 `/** @internal ... */`。

判断靠的是"这一行以 `*` 加 `@api` / `@internal` 开头"，或者"整个单行 docblock 以 `@api` / `@internal` 开头"。

**行内描述性提及不算标注。** 像"它本身是 `@internal` 的实现细节"这种写在句子里的字样，只是文字，不构成一条标注。按 `grep` 数字面数量会把这类提及一起算进去，得到的是错的——这正是不能手抄清单、必须用生成器的原因。

## 默认 internal

**没有标注就默认不进公共面。** 只有显式标了 `@api` 的成员才算公开；没标的、标了 `@internal` 的，都按内部处理。新增一个成员却不标注，它不会自动变成公开承诺——这是刻意的保守默认。

有一条配套防线：`internal-leak` lint 规则。它的口径是：

- **类型级**：非 `Drift\` 前缀的代码引用 `@internal` 类型，默认报 error；若该类型带了 `@internal-use-allowed:` 说明，降为 warn。
- **方法级**：调用框架类的 `@internal` 方法报 warn；它绝不按方法名猜测，只解析静态可确定的接收者。

这条防线让"内部面被外部依赖"在 lint 阶段就能被发现，而不是等到公开面被破坏。

## 唯一事实源：`lint --api`

公开 API 面清单由 `php tools/lint.php --api` 生成，这是唯一事实源。它扫描 `src/`，排除 fixtures、build、`_build`、`.git`、`vendor`、`node_modules`——夹具和产物不是 API 面。

生成器的几条保证：

- 按 `@api` / `@internal` 分组、按层列出，可以直接当文档看。
- 要求 docblock 与声明紧邻；遇到无法归属到声明的标注会记成 `unmatched`，自检断言它为 0。漏解析一种声明形态会被当成错误抓出来，而不是静默少算。
- 输出里不带行号锚点，避免清单随代码挪动就失效。

composer 侧没有单独的 API 脚本，直接用 `php tools/lint.php --api`。命令入口见[命令速查](./cli.md)。

## 不要手抄快照

不要在文档里维护一份 `@api` 清单的拷贝，也不要抄某次生成的数量。原因有三：

- 清单随 `src/` 的标注变化，手抄会立刻过期；
- 按关键字数出来的字面数量包含大量描述性提及，口径本就是错的；
- 现行的验证计划已经不设 API 文档闸门，清单只作为给人看的产物存在，没有"拿文档和代码对账"这一层——所以手抄错了也没人报红，只会误导读者。

需要知道当前公开面时，重新跑一次 `php tools/lint.php --api`，以那次输出为准。

## 公开面变化怎么审查

改动公开面要当作破坏性变更对待，按下面的顺序过一遍：

1. **确认是不是真的要公开。** 新成员默认 internal；确实要给应用用，才加 `@api` 独立标注行。能用现有 `@api` 表达的就别新增。
2. **确认标注写对形式。** 独立标注行或单行 docblock；写在句子里的字样不算，别以为标了其实没标。
3. **跑生成器看差异。** `php tools/lint.php --api`，对比改动前后 `@api` 面有没有多出或消失的条目，`unmatched` 必须为 0。
4. **跑 lint 看内部面有没有泄漏。** `php bin/drift lint`，重点看 `internal-leak` 有没有新报。
5. **按分层验证。** 公开面变化通常改的是 `src/`，按[协作流程](../contributing/workflow.md)要走 T2 重编译，不能只靠 dev 壳。

移除或改签名一个已有 `@api`，等于破坏对外承诺，要按发布层面的破坏性变更处理，不能只当普通重构。
