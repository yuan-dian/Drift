## 3. 三个新发现（本次复评的实质内容）

### 3.1 ★★ D8（measure/place）不是"待做"，是"已判 no-op"

`26` §6.4 与 §7 的结尾写着：

> present 的 1.11 ms 已是驱动拷贝…**下一步轮到 `25` §4 判据的 measure/place 分支**：
> 先只拆两个容器（滚动场景），拆完量一次再决定剩下的 21 个。

**这条行动项已经过时，必须划掉。** 完整链条是：

```
layout() 本就位置无关（§14.1 规则 1）
  ⇒ measure/place 分离本身不产生收益（只是把一次遍历拆成两次）
  ⇒ 要收益就必须有"尺寸缓存"（place 时复用上次 measure 结果）
  ⇒ 缓存层需要失效逻辑（脏位 + 边界）
  ⇒ GUI 上游对同一问题已裁决：布局缓存层不做
      （为个位数百分比预算造一整套失效逻辑，不划算）
  ⇒ 分离 = no-op，缓存 = 不做 ⇒ 整条线关闭
```

★★ **更硬的证据：v7 想解决的问题已经被另一条路解决了，而且更彻底。**

v7 D8 的动机原文是"**定位是 O(子数) 的加法，重量是 O(子树)**"——滚动不该重排整棵树。
Drift2 现在的答案是**虚拟化**（`LazyColumn` + `RenderScrollView` 的 `virtualExtent`/`sliceOrigin`）：

| 方案 | 滚动时的成本 | 实测 |
|---|---|---|
| v7 的 place-only | O(可见孩子数) 次 **加法**（仍要遍历整棵已建树） | 未实现，无数据 |
| Drift2 的虚拟化 | O(可见孩子数) 次**布局**，不可见孩子**根本没被建** | 10000 行单帧 96 ms → **0.2 ms** |

⇒ 虚拟化连"不可见孩子的节点"都不存在，比 place-only 少一整层；而它已经落地并有消费者
（`BigListPage`）。**D8 的目标达成度：虚拟化 100%，place-only 只在其上再加一点。**

★ 因此 `13` 册 D8 的**推翻条件写错了方向**：它只写了"若 `place` 里出现需要重新量孩子的需求"，
没写"若分离本身是 no-op"。后者才是真正发生的推翻理由 —— 建议补进 D8 的推翻条件。

### 3.2 ★★ M1 的"给 Render 层加定型"与 C6 冲突，应降级为**不做**

`25` §4 的分支表写着：

> **M1 已测：`toObject` 比动态分派便宜**（0.72–0.83）⇒ 给 Render 层加定型 —— 独立优化，与重写无关 · **2–3 天**

两条理由说明它不该做：

**① 算术上不值。** `toObject` 的净成本是 **56 ns/节点**（动态分派）vs 37 ns（定型），
省 19 ns。而真实 layout 每节点是 **5.7–12.4 µs**（`26` §3.1）：

```
19 ns / 5 750 ns ≈ 0.33%   （参数化树）
19 ns / 12 400 ns ≈ 0.15%  （showcase）
```

即使按"每个孩子 measure+place+paint 三次调用"放大三倍，也只有 **layout 的 0.5–1%**，
端到端 **0.02–0.05%**。M1 测的是**相对成本**（一次定型 vs 一次分派），
被误读成了"一处值得修的绝对开销"。

**② 语义上是地雷。** `11` 册 C6：**虚方法在静态类型已知时会被去虚化、静默走基类实现**。
`src/Layout/` 现有 **18 个 `performLayout()` 覆写**。今天它们能生效，恰恰是因为
`RenderFlex::$kids` 是裸 array ⇒ `$kid->layout()` 走**动态分派** ⇒ 绕开了 C6。
一旦加 `toObject(RenderBox::class)` 定型，18 个覆写会**静默失效** ——
这正是 v7 D4（`int $kind` + `switch`）要解决的问题。

⇒ **"2–3 天的独立优化"实际上等于"先重写分派层"**。而重写分派层的收益上限仍是 layout 的 1%。
**结论：这条分支从"待做"改为"不做"**，除非将来因为别的原因（序列化 / AI 驱动）重写分派。

### 3.3 int 命令的开放问题有答案了：15 个

`24` §5.3 说 int 命令"收益真实，但**要先数命令数**：30 个以内不值得，300 个以上值得。现在没人算过"。

实测（`grep -rho "'[a-z]+\.[a-z.]+'" apps/ src/`）：

| 指标 | 数 |
|---|---|
| 不同命令字符串 | **15** 个 |
| 出现总处数 | **52** 处 |
| 最高频 | `users.refresh` ×14 |

⇒ **15 < 30 ⇒ 明确不值得**。D3 的双路径裁决（常规交互闭包 / 可回放走命令 ID）也不必改：
现在两个应用都是"闭包为主 + 少量字符串命令"，正是 D3 的形态，只是命令侧没上 int。

★ 这条要回填 `24` §5.3 与 `13` D3，把"没人算过"换成数字 —— 否则下一个人还会再问一次。

## 7. 下一步：性能线关闭，转能力面

### 7.1 为什么不再挖性能

```
端到端 3.14 ms（60fps 预算 16.6 ms ⇒ 5.3× 余量）
├─ surface 链 0.81 ms —— present 1.11 ms 是 GDI 驱动拷贝，PHP/C 侧无油水
└─ PHP 逻辑 2.3 ms —— layout 0.87、settle 0.08、paint 记录 0.36，其余是 Skia 调用 + pump
```

- 剩下的最大单项是"Skia 逐 op 调用"（D6 未做的那一半）—— 要做整帧回放，改动面覆盖整个 Rendering 层。
- 而**真实应用的瓶颈已经不是帧时间**：showcase 6 个页面在 3.14 ms/帧下无任何掉帧症状。

⇒ 性能线**关闭**，只保留 DESIGN §13.5 的三条重估触发（中位 > 8 ms / 最差 > 30 ms / 高分屏 > 12 ms）。

### 7.2 能力面的缺口（按"用户能感知"排序）

| 优先 | 缺什么 | 现状 | 备注 |
|---|---|---|---|
| **1** | **表单控件** | Checkbox / Radio / Switch / Slider / Select / DatePicker **全零** | 55 个 widget 文件里一个都没有；这是"能不能写业务界面"的分水岭 |
| **2** | **Image / Icon / Divider / Progress / Tooltip** | 全零 | `drawImage`（P4）刚打通，Image 现在**可以真做**了；Icon 可走 `drawPath` 矢量表 |
| **3** | **文本编辑三件套** | 选择 / 复制粘贴 / 撤销 全缺 | `Clipboard` 端口空（D17）；没有它 `TextField` 只是"能打字" |
| **4** | **动画** | 无过渡 / 无插值 | 前提是**层合成**（`pushLayer` 已有，但无 RepaintBoundary 语义） |
| **5** | 平台线两个前置 | `SupportLevel` · 壳拆分 | 只有真要上第二个平台才值得 |

★ 顺序理由：1 和 2 是**纯增量**（新控件 + 现有原语），不碰热路径、不动架构；
3 需要先补 `Clipboard` 端口（一个 C 函数 + 一个类）；4 需要先想清层合成语义（v7 `20` 册有判据可借）。

## 8. 推翻条件（新增，写下来免得再讨论一遍）

| 结论 | 什么情况下重新考虑 |
|---|---|
| 不重写（D1） | 出现"同一份 UI 要在两个渲染后端复用同一棵树"的强需求 |
| 不做 measure/place（D8） | 出现"必须复用上次尺寸"的场景且虚拟化覆盖不到（如可变高度瀑布流 + 频繁滚动） |
| 不做 Render 层定型（§3.2） | 分派层因别的理由重写（如要做序列化/AI 驱动）—— 那时定型顺手做 |
| 不做 int 命令（§3.3） | 命令数 > 100（当前 15），且需要撤销栈 / 跨进程回放 |
| 不做脏矩形 | DESIGN §13.5 三条触发任一成立，且**必须与 relayout 脏边界成对做** |
| 不挖性能（§7.1） | 端到端 > 8 ms，或出现 10000 节点以上的真实应用页面 |
