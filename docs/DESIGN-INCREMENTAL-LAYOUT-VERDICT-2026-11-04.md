# 增量布局立项裁决：12k 节点三数与「更优方案」（2026-11-04）

> 权威待办：`docs/DEBT-2026-11-02.md` §27 ①。
> 方法：先跑量具 → 按 `DESIGN.md` §13.5 / `RESEARCH-ALIGN-2026-11-03.md` §3.2 判定 →
> 五维评估「直接立项是不是最优解」→ 参考成熟 GUI 借机制、排结论 → 再动代码。
> 口径声明：全部数字来自 **PHP 8.5.11 解释器 + 软光栅**（合成档视口 400×300），
> **不是 AOT 生产**。这一条决定了下面所有结论的适用边界，见 §7。

## 0. 结论先行

| # | 结论 | 性质 |
|---|---|---|
| 1 | 12k 档三数已出：**12,003 节点 / 首布局 1,026.4ms / 稳态帧 8.7µs / 全量重排 49.8ms** | 实测 |
| 2 | 按 §3.2 的 8,000µs 线，全量重排**触线 6.2×**；但按 §13.5 的**生产**触发条件与 `--pages --check` 的 27 个真实页复核，三条**均未成立**（最重 `TablePage` 1,531.7µs，余量 5.2×；**11-04 晚 AOT 口径复量为 3,474.9µs / 余量 4.8×**，见 §4.3 门 2） | 两个分母 |

| 4 | 兼容性：不动框架、不动布局协议；探针新增独立 `--scale` 档，`--check` 默认行为一字不改 | 克制 |

「可破坏兼容」是授权不是义务。这一棒没有证据表明动布局协议的收益大于成本，所以**不用这张牌**。

## 1. 事实底座（五档实测，非估计）

```text
  rows    nodes   cold(us)   perFrame(us)   layout(us)   paint   skip
    10       43    29327.4           12.7        262.2       0     50
    50      203    15512.6           11.3       1011.2       0     50
   200      803    57198.0            8.2       3089.1       0     50
   500     2003   153665.6            9.5       8847.1       0     50
  3000    12003  1026417.7            8.7      49841.1       0     50
```

三条读得出来的结构事实：

1. **稳态帧与规模无关**（8.2–12.7µs）。`RESEARCH-ALIGN` §2.3 那条「2000 节点 1.04ms ⇒ 外推 12k 是 ~6ms」
   已经**过期** —— 它量的是全树 `tickSubtree`，§16 的 active set 落地后固定税只剩几百纳秒。
   12k 实测 8.7µs 就是证据。**不能用旧外推去论证今天的立项**。
2. **全量重排随节点线性**：16–19µs/行 ≈ **4.15µs/节点**。线性意味着当前确实是「整棵树重排」，
   没有隐藏的跳过 —— 这是判定「增量布局有没有得省」的前提，也是判据 ⑤ 要钉住的东西。
3. **稳态 paint 0 画 / 50 跳**：`LayerCache`（RepaintBoundary 等价物）生效。
   ⇒ 绘制侧有边界、布局侧没有，`RESEARCH-ALIGN` §3.3 的不对称在 12k 档上依然成立。

首布局 1.03s 非线性上翘，主要是建 12k 个对象 + 首次 shaping + GC，不在本棒裁决范围内。

## 2. 三个分母，才是之前吵不清的原因

| 出处 | 分母 | 数字 | 回答的问题 |
|---|---|---|---|
| Raven `14-Raven研读.md` §1.11 | 12,000 widget / 27,800 图元，**C11 Release** | 首布局 2–3ms；改一处 0.03–0.05ms | 工业实现的天花板 |
| `DESIGN` §13.5 复核（11-03） | **27 个真实页面**，最重 `TablePage` | 全量重排 1,531.7µs | 今天的产品要不要做 |
| 同上，**AOT 口径**（11-04 晚） | 同样 27 页，`probes/frame_tax_aot` | 全量重排 3,474.9µs（2.15×） | 生产上还够不够 |
| 本棒 12k 合成档 | 12,003 节点，**PHP 解释器** | 全量重排 49,841µs | 目标规模变大后要不要做 |

前两者不是同一棵树，第三个又引入了「解释器 vs AOT」这**第三重口径**。
⇒ 绝对 µs 在这里不能跨行比较。归一化之后才是一把尺子：

- Drift2 全量重排 **4.15µs/节点**；
- Raven 增量布局 0.03–0.05ms / 12,000 = **2.5–4.2ns/节点**；
- 比值约 **1,000×**，且不受机器快慢影响。

这个比值说明「增量布局理论上能省很多」，**但不说明今天该做**：它省的是「有节点变脏的那一帧」，
而 §1 的稳态帧（占绝大多数帧）已经是 8.7µs。

## 3. 五维评估：为什么「直接立项增量布局」是更差方案

| 维度 | 评估 |
|---|---|
| **结构** | `DESIGN` §13.3 与 `EVAL-design-v7` §261 要求**脏矩形与 relayout 脏边界成对做**，单独补一半只是把瓶颈搬到对面。绘制侧已有 `LayerCache`，布局侧缺对称那一半是真问题，但补它必须同时动绘制。 |
| **实现** | Flutter 的答案是「三 pass 各自脏集合 + `markNeedsLayout` 沿父链上传 + 按深度排序」（`01-Flutter.md` §2）；Raven 是脏子树。两者都要求 `RenderBox` 持有 parent 与 boundary 标记。而 `540b55e` **刚改过** `Frame::run()` 的布局时序（帧内约束收敛、上限 4 轮），脏路径会与 `constraintRounds()` / `LayoutBuilder` 的反馈直接交互 ⇒ 风险叠加，不是干净切口。 |
| **扩展性** | 当前 `performLayout()` 的隐含契约是「每次调用都重排整棵子树」。引入脏路径要重审 `src/Widget` 134 个文件里的自定义盒；`--pages --check` 判据 ④ 正是钉住这条契约的哨兵，实现一改判据必须同步改。 |
| **易用性（DX）** | 新增「boundary 要声明在哪」的概念，开发者要理解并放对位置 ⇒ 与 §26.9「先找消费者，不要先找框架」以及本仓当前 DX 主线相悖。目前 **零真实消费者**，形状只能凭空设计 —— §24.1 拒 `pollUntil` 用的就是这条（A15 老账：第二个消费者一出现就得改签名）。 |
| **维护性** | 量具与实现会互相追：判据 ④ 会红、要改；`--pages` 的分母会变、要重刷；归一化基线要重建。而收益只落在「未来某个 10k 节点页面」上。 |

⇒ **不是能力不够，是症状没到**。§13.5 的「等症状」门禁继续有效，只是把触发条件写清（§4.3）。
`14-Raven研读` §3-B 的「增量布局是生死线，**Drift 必须补**」是**结论不是证据**：它用的是
12k C11 Release 分母；照抄会重演 `RESEARCH-ALIGN` §1 记下的「调研的现状描述会腐烂」。

## 4. 更优方案：把尺子做对

### 4.1 量具升级（`tools/frame-tax-probe.php`）

1. **补齐第三数的真实口径**：§3.2 要的是「**改一个 label 后的布局**」，现有 `layout(us)` 列量的是
   「同一棵树暖缓存全量重排」—— 两者不是一回事。报告增印 `rebuild` 三段（settle/layout/paint）。
2. **加 `us/节点` 归一化列**：跨规模、跨语言可比，不随机器抖动；§2 那个 1,000× 才有依据。
3. **新增 `--scale` 独立档**：跑 `[500, 3000]` 两档（500 作同量纲基线），出三数 + 判据，
   **不拖慢现有 `--check`（仍 500 行 / 30 帧 / 6 条）**。
4. **判定线内建但只作信息输出**（8,000µs / 8ms / 16.7ms），**不作红判据** ——
   `gate.php` 头注已经否过「绝对耗时进闸门只会变成一台随机失败的机器」。
5. **`--json` 输出三数 + 归一值**：agent 可直接消费，不必正则刮 stdout（呼应 §17）。

### 4.2 判据：只认自证 / 比值 / 结构事实

| # | 判据 | 能红的真实事故 |
|---|---|---|
| ① | `nodes ≥ 10,000` | 12k 档被改小 / 建树失败 ——「没扫到」冒充「没有」（本仓硬判据） |
| ② | 四数（`cold/perFrame/layout/rebuild.layout`）全 > 0 | 量具某段没计时却报了个 0 |
| ③ | 归一值自洽：`(layout/nodes)@3000` 与 `@500` 之比 ∈ [0.5, 2.0] | 量具污染自己（重建帧 GC 混入）、或单位换算 1000× |
| ④ | 稳态帧 ≤ 8ms（`DESIGN` §13.5 的产品要求，非机器速度） | 每帧固定税退化 —— 实测 8.7µs，余量约 900×，不会误红 |
| ⑤ | `rebuild.layout ≥ layoutUs / 2` | 钉住「layout 仍是全量」这个前提；哪天真做了增量布局，这条会**主动报红**提醒同步改判定（与页面档 ④ 同构） |

★ 五条里**没有一条**引入新的墙钟绝对阈值作红（④ 是产品要求，不是「这台机器快不快」）。

### 4.3 立项三道门（写进 `DEBT` §28，以后不用重新吵）

1. **真实消费者**：出现 ≥10k 节点的真实页面/应用，或 `--pages --check` 最重页全量重排 > 8,000µs。
   合成档触线**不算**。
2. **AOT 口径**：在 AOT 产物上复量同一份归一化值，确认触线不是解释器独有。
   ~~当前 49.8ms 是 `php.exe` 读数；layout 是纯 PHP 递归，AOT 编成 C++ 后大概率快数倍。~~
   > ★ **2026-11-04 晚已复量，上面那句被推翻**：`probes/frame_tax_aot/` 同规模实测
   > **88.4ms**（不是更快，是 **1.73× 更慢**），归一化 7.368 us/节点。
   > ⇒ 这道门**已通过且结论更硬**：触线不是解释器独有，AOT 下倍数从 6.4× 变成 **11.1×**。
   > 量账见 `DEBT` §34 / `AOT-CONSTRAINTS.md` §2.5。
   >
   > ★ **2026-11-04 更晚：真实 27 页也复量了**（`--pages` 换成显式清单 `ShowcasePages`，
   > AOT 编得过）。最重页 `TablePage` **3,474.9µs**、27 页 `layout` 合计 15,360.9µs，
   > AOT ÷ 解释器 = **2.24×**（比合成档的 1.73× 更大 —— 树越"碎"越吃亏）。
   > ⇒ 真实页还剩 **4.8×** 余量（原解释器口径 10.3×）：**门 1 仍未触，但余量砍了一半，
   > 页面重量翻一倍就触线**。量账见 `DEBT` §35 / `AOT-CONSTRAINTS.md` §2.6。
   >
   > ★ **同日深夜：减速的成因也拆开了。** 13 级阶梯（`DEBT` §36 / `AOT-CONSTRAINTS.md` §2.7）
   > 显示**不是装箱**：虚调用 1.96×、闭包创建 2.04×、值对象分配 1.79×；
   > 而算术在 AOT 下快 15–20×、`mixed` 拆箱快 2.3×，只是布局本来不吃算术。
   > ⇒ **没有哪个单一成分值得优化**（最贵的闭包在 12k 量级上占比不到 2%），
   > 真要改善只能改「每节点 2–4 次小对象分配」，那是扁平化渲染树级别的重构 ——
   > **余量 4.8× 时做这个是浪费**。裁决不变，且现在它建立在归因上，不是猜上。
3. **成对**：脏矩形 + relayout 边界同时做（§13.3 / `EVAL-design-v7` §261）。

三条全过才立项；任一不过就继续驻留，但尺子每次都能给出新数据。

## 5. 成熟框架：借什么、排什么坑

**借机制（可跨版本复用）**

- Flutter：三 pass 各自处理脏集合、按 Element 深度排序保证父先于子（`01-Flutter.md` §2）。
  这是将来真做时的入口形状，不是今天要抄的代码。
- Raven / nanoui：「谁在工作要显式登记，不要每帧问全树」。本仓 §16 已落地，§1 的 8.7µs 是验收证据。
- Raven 的 `ns/widget` 归一化思路：把绝对耗时换成结构量，才让 C11 与 PHP 两个数能同桌比。

**排坑（防止照抄结论）**

| 候选 | 为什么否 |
|---|---|
| Raven「必须补增量布局」 | 结论绑在 12k C11 Release 分母上；先过 §4.3 三道门 |
| Raven「并行绘制」 | 它自己 §1.11 实测 2 核提升甚微；别把并行当银弹 |
| nanoui「CPU == GPU 逐像素一致」 | 与 2026-11-01 裁决冲突，`RESEARCH-ALIGN` §4.1 已论证；跨后端只比设备几何 |
| 判定线用绝对 µs 做红判据 | `gate.php` 头注：墙钟数随机器浮动，会变成随机失败的机器 |
| 直接改 `--check` 让它跑 12k | 闸门要快；且 6 条既有判据的前提是「静止的 500 行合成树」，换分母会把判据一起换掉 |

## 7. 边界（诚实版）

- ~~三数是**解释器 + 软光栅**；AOT 下 layout 会更快，6.2× 这个倍数会缩小，**不能当生产结论**。~~
  > ★ **2026-11-04 晚修正**：AOT 复量结果是**更慢**（12k 全量重排 51.1ms → **88.4ms**，
  > 1.73×）。所以「AOT 会更快、倍数会缩小」不成立，真实倍数是 **11.1×**。
  > 「不能当生产结论」这半句仍然对 —— 但现在的正确结论是「解释器数字**偏乐观**」。
- 合成档是 `ScrollView(Column(Row(3 Text)))`，真实页面形状不同；Raven 的 12k widget 也非同构。
  归一化比值只用于自洽与跨规模比较，不是产品性能指标。
- 本棒**不改框架语义**，所以「增量布局最终该不该做」没有被永久判死 —— 只是把判定条件写清、
  把尺子交出去。~~第 2 道门（AOT 复量）尚未做，需要真机构建时补。~~
  > ★ **2026-11-04 晚已做**（`probes/frame_tax_aot/`，5 条判据双侧同构、变异双侧咬住）。
  > ~~仍未做的是 **`--pages` 27 个真实页的 AOT 复量** —— 那档靠 `new $class()` 反射扫页，
  > AOT 静态编译走不通，要改成显式页面清单（`DEBT` §34.9 第 1 条）。~~
  > ★ **同日更晚也做完了**：显式清单 `tools/Bench/ShowcasePages.php`（一份数据，
  > 名字是键、构造闭包是值），解释器与 AOT 共用；「加页忘填清单」由判据 ⑤ 兜住，
  > 另补 ⑥「页面真建起来了」。**这一档的口径欠账清零**，见 `DEBT` §35。
  > ★ **正确性口径也补上了**（`DEBT` §36.8）：27 页 / 2278 个 `RenderBox` 的几何
  > 两侧**逐值相同**（`tools/geom-fingerprint.php` 对 `PROBE_SECTION=geom` 做 diff）。
  > 这道检查顺带抓到了 tpc 的 `int / int` 整数除法（`AOT-CONSTRAINTS.md` §1.2）——
  > 框架没踩，但那是**静默**错误，以后动 AOT 先跑它再谈性能。
- `rebuild.layout` 是「整页换一棵等价新树」的成本，比「改一个 label」更重；它是上界，
  不是 Raven 那个 0.03–0.05ms 的等价物。这一条必须写清，免得下次有人拿它俩直接相减。
