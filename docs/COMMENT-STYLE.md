# 代码注释规范

> 注释回答**「这条约定不这样写会怎样错」**，不记录「我们是怎样走到这里的」。
> 设计论证、变更史、技术债编号属于 `docs/` 与本仓的 git 历史，不属于代码。

## 一、判断标准

一条注释值不值得留，只问一句：**删掉它，下一个改这段代码的人会不会踩坑？**

- 会 ⇒ 留，并且**只留"会怎样错"**，不留推导过程。
- 不会 ⇒ 删。哪怕它是对的、写得挺好。

反例（当前代码里的典型形态，都要删）：

```php
// ★★ 为什么不做成 pushBackdropBlur()/popBackdropBlur() 一对：
//    那样"层里到底该有什么"就有歧义 —— 子内容画在层里会被一起模糊…
//    ★ 2026-10-17 修复记录：SkiaCanvas 第一版只发 round(pen × dpr)，
//      offset 被丢（今天生产者 offset 恒 0 ⇒ 潜伏；M4 真塑形时会活）。
```

正例：

```php
// 一次性操作，不是栈：模糊只作用于调用前已画的背景。
```

## 二、保留什么

| 类别 | 写法 | 例 |
|---|---|---|
| 类职责 | 1 句 + 关键不变量 | `// 绘制目标。父级已 translate 到盒原点，`paint` 以 (0,0) 为盒左上角。` |
| 契约 | 参数里非显然的语义、null 的含义、副作用、抛什么 | `// `$src` 为 null ⇒ 整幅缩放` |
| 真坑 | 违反后**不报错、只是行为错**的那一类 | `// 不可 return null：null = 这层不存在 = 穿透` |
| 来源 | 常量/魔法值从哪来 | `// WIC 的 BGRA 序，不是 RGBA` |
| 标记 | `@api` / `@internal` / `@deprecated` / capability-gap 指令 | 闸门依赖，**一字不改** |

## 三、删掉什么

1. **日期与技术债编号** —— `（2026-11-02，D1）`、`（技术债 D3①）`。
2. **章节引用** —— `§7.2 裁决 3`、`见 DESIGN §17.4.2.1`。设计文档在 `docs/`，代码不指路。
3. **"为什么不用另一种方案"的论证** —— 移 `docs/` 或 commit message。
4. **变更史** —— "原来是 X / 现在改成 Y / 第一版只发 Z / 此前用于 W"。
5. **复述代码** —— `// 遍历子节点`、逐字段解释字段名。
6. **重复强调** —— 同一约束在类头说了、方法上再说一遍。
7. **过程性旁白** —— "本次"、"这一棒"、"又咬一次"、"血"。

## 四、格式

- 类头 ≤ 8 行；方法 docblock ≤ 5 行（**有真坑可到 10 行**，但要能一眼看出坑在哪）。
- 并列约束 ≤ 3 条才用项目符号；超过 3 条说明该拆方法，不是该写注释。
- `★` 只标**违反会静默出错**的条目，全文件通常 ≤ 3 处。它不是"重要"的装饰。
- 中文、句号结尾、不用感叹号、不写"注意！"。

## 五、硬约束

- **只改注释，不改任何代码 token**（含空行归属、字符串、注解）。
- `php -l`、`php tools/lint.php`、`phpunit` 必须全绿。
- 校验方式：`git diff -U0 -- <file>` 的每一条新增行 **必须**以 `*`、`//`、`/*`、`*/` 开头或为空行；
  出现别的形态说明改到了代码，立即回退。
