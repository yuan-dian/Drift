## 0. 一句话结论

**框架本身健康，债务主线（D1–D7）已基本偿还，性能余量 4.8×，没有需要推倒重来的结构问题。**
当前真正的风险不在"代码架构"，而在**知识架构**——47 份 review/design/decision 文档 +
9802 行债务清单 + 最近 7 天 85 份 md 变更，结论靠人肉"重 grep 订正"维持，
每新一轮 review 都要重新踩一遍上一轮踩过的过期坑。这已是本项目最大的隐性成本。

据此给出两层建议：
- **代码层**：只做三件小而实的事（图片缓存上限、`cacheKey`、扇出诊断升级为运行时 ownership），
  不碰已裁决的结构，不为闭包/readonly 这类"听起来该优化"的伪问题动刀。
- **知识层**（本轮新提，优先级最高）：给文档体系补一个**活索引 + 裁决失效条件机检**机制，
  把"重 grep"从人肉纪律变成判据。

## 2. 跨轮次的系统性问题（本轮核心发现）

四个模式在近几轮反复出现，单独看都合理，合起来指向同一个根因。

### 2.1 模式一：过期结论反复触发返工

本日至少四次踩到"文档结论已过期"：

- `?Obj` 退化：`PITFALLS` 顶条还写着"一律值+bool"，但 11-11 已解禁（#183/#184）。
- readonly "零开销"：`AOT-CONSTRAINTS §2.1` 的实测是 10-22 旧编译器（走 `read_property_cached`），
  #186 后已走 `read_property_scoped`。
- 示例整合：`PLAN-NEXT-STEPS-11-11` 的计划项被 `DEBT §9330` 降级（"可做但不该先做"）。
- tutorial.md："19 个页面"实际 35 个。

项目**已经认知**到这点——`DEBT` 里明写"清单会腐烂是本项目反复验证过的"、
"先重 grep 再动手"。但对抗手段仍是**每轮人肉重复 grep + 事后写订正注**。
这是流程缺口，不是纪律问题：没有人会每次都记得所有可能过期的结论。

### 2.2 模式二：静态 lint 的能力边界被反复触碰

lint 已有 34 条规则（含 `callback-arity`、`await-scope`、`cancel-guard` 等 AOT 专项），
但本日的三件事都落在它的边界外：

- 扇出取消（同一 Future 被两个命令持有）——静态分析追踪不了两个闭包运行时返回同一对象，
  最终只能做运行时诊断。
- 两层闭包性能——静态规则管不着调用频率。
- readonly 退化——生成物形状问题，lint 扫的是 PHP 源码。

**判断**：这是工具定位问题，不是缺陷。lint 擅长"结构性、文本可判"的纪律（它守得很好），
不该强求它覆盖运行时/编译器层。真正该做的是**给运行时与编译器层也配机制**
（见 §3.3），而不是往 lint 里塞更多规则。

### 2.3 模式三：成熟度陷阱——"成熟框架有，我们也该有"

多轮裁决都在抵制这个陷阱，且都做对了：`i18n/RTL`（零消费者）、`fling/长按`（无触控输入）、
`BuildContext::of()`（明文否决）、Flutter `updateRenderObject()`（字段级半同步是倒退）、
`AsyncResourceState` 基类（`AsyncValue::fold()` 四态穷尽是优势，改可覆写反而丢编译期保障）、
闭包改接口（L09 1.96× vs L10 2.04×，净收益为负）。

**判断**：这套"有消费者 + 错了静默 + 决定交付"的三条判据是本仓最值钱的资产之一，
应继续作为默认防线。但它目前只活在 DEBT/REVIEW 正文里，**没有机检**——
§4 建议把它做成一条可执行的 checklist 判据。

### 2.4 模式四：文档膨胀与导航缺失

47 份 REVIEW/DESIGN/DECISION/PLAN 文档，最近 7 天 85 份 md 变更。文档本身质量高，
但**读者无法判断"哪份是现行结论、哪份是历史快照、哪份裁决已失效"**。
本轮只读这些文档就花了大量 token 做交叉验证；开发者日常只会被淹没。
`docs/00-README.md` 是索引，但索引的是"文档分类"，不是"结论状态"。

## 3. 需要修改或优化的点（按优先级）

### P0（知识层，本轮新提）—— 裁决索引 + 失效条件机检

**问题**：§2.1 + §2.4 的根因是同一件事——结论有了，但"何时失效"没有机器可读的落点。
`?Obj` 解禁和 readonly 退化都是编译器升级触发的，若当时有一张"依赖编译器版本的裁决表"，
升级时就能自动提示"这些裁决需要重评"，而不是等用户提醒才发现。

**建议方案**（成本中低、纯工具链）：
1. 建一份 `docs/DECISION-INDEX.md`，表格三列：`裁决 | 现行结论 | 失效条件`。
   从本轮已知的裁决先填起（`?Obj` 形参已解禁 / 字段层不变、readonly 不迁移的 #188 失效条件、
   apps 不改名、示例不整合、不建 AsyncResourceState、闭包不换接口）。
2. 加一条 lint/doc 判据：每个 `DECISION-*` / 关键 `AOT-CONSTRAINTS` 结论必须带
   `失效条件:` 字段；缺失即 warn。让"写裁决时想失效条件"成为结构约束，不靠自觉。
3. 上游编译器版本变化时（`DRIFT_TPC_ENTRY` / tpc HEAD 变更），codegen 报告附一段
   "受影响裁决清单"提示——最低成本是把编译器版本写进生成物头注释并让一个 test 比对。

**为什么排 P0**：它不改变产品行为、零风险，但直接消除本日反复出现的返工模式，
且随文档增长收益递增。这是"补扩展点"而非"再拆一次代码"——正合 DEBT §0.1 的原始洞察。

### P1（代码层，小而实）—— 三项异步资源缺口

review 里提过但一直未落地的三件（本轮已复核仍是空白）：

1. **图片内存缓存加字节上限 + LRU**（`ImageLoader::$cache` 现在只增不减，
   `clear()` 是唯一出口）。理由：本仓有 1792×2390 图解码成 17MB 的 OOM 前科；
   2048 上限只挡单图解码，挡不住多图累积。
2. **`asset()` 加可选 `cacheKey()`**。理由：签名 URL（带 token/时间戳）现在会
   `md5(url)` 每次落新文件，磁盘缓存形同虚设。
3. **`classify()` 升级为来源解析器注册表**。理由：现在硬编码 `http/https/盘符/reject`，
   加 `data:` / `file://` / 自定义 scheme 要改核心方法。优先级最低（无真实消费者）。

前两项有真实风险与 DX 收益，第三项归入 P2。

### P1（机制层）—— 扇出取消诊断升级为运行时 ownership

本日已落地 `future/fanout-cancel` 诊断（`c087b3b`），但它只在 `cancel()` 时按 links 数报，
是"事后提醒"。更彻底的形态是给 Future 根记录 owner（`spl_object_id`，AOT 已验证支持），
认领/取消时校验"一根一主"，把风险在**持有那一刻**变红而非取消那一刻。
成本中，需改 `AsyncCommand`/`AsyncScope` 认领点。建议**等出现第二个真实踩坑再动**——
目前诊断已足够覆盖，别为完备性增加机制（§2.3 纪律）。

### P2（能力层）—— ITextProvider / WM_POINTER 保持待命

两项都有明确裁决和失效条件（§1.2）。**不主动开工**，等真实消费者：
- ITextProvider：读屏/政企无障碍采购出现时升级为硬阻断。
- WM_POINTER：触控输入场景出现时，与 fling/长按一次性评估。

## 5. 后续方向（给下一棒的行动建议）

```
第一步（P0，本轮新提）：补知识层扩展点
  └─ DECISION-INDEX + 失效条件 lint + 编译器版本指纹
     收益：把"重 grep 订正"从人肉变机制，阻断本日反复出现的返工模式

第二步（P1，有真实风险）：异步资源三缺口的前两项
  └─ 图片缓存 LRU + cacheKey
     判据：变异"去掉 LRU 淘汰"红、签名 URL 两次命中同一磁盘文件

第三步（按需，有失效条件）：ITextProvider / WM_POINTER / ownership
  └─ 等真实消费者出现再启动，不提前铺摊子

不做：闭包/readonly/结构重写/应用目录 —— 见 §4
```

**一句话方向**：代码架构已经到"够用且健康"的阶段，下一阶段的杠杆在**知识架构**——
让结论不会腐烂、让裁决能自动失效、让 47 份文档变成可导航的现行知识，
而不是再给一个已经 4.8× 余量的框架加功能或抠性能。
