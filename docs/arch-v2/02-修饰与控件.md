## 1. 现状：同一件事写了两遍

### 1.1 重复一：修饰是一个节点

```php
// apps/users 与 smoke 里共 157 处这种写法
Padding::make(16)->child($card)
SizedBox::make(width: 240.0, height: 32.0)->child($input)
Center::make()->child($spinner)
```

每个修饰都是 **Widget + Element + RenderBox 三件套**：

| 修饰 | Widget | Element | RenderBox | RenderBox 行数 |
|---|---|---|---|---|
| `Padding` | `Padding.php` | `ProxyElement` | `RenderPadding` | 61 |
| `SizedBox` | `SizedBox.php` | `ProxyElement` | `RenderSizedBox` | 135 |
| `Center` | `Center.php` | `ProxyElement` | `RenderCenter` | 35 |
| `Expanded` | `Expanded.php` | `ProxyElement` | `RenderFlexible` | 46 |
| `Card` | `Card.php` | `ProxyElement` | `RenderCard` | 145 |

代价不是"多了 5 个文件"，是**每个修饰都在重复实现同一件事的两遍**：

```php
// src/Layout/RenderPadding.php 的两条独立实现（节选语义）
protected function performLayout(BoxConstraints $c): Size
{
    $inner = $c->deflate($this->insets);              // ① 约束内缩
    $child->layout($inner);
    $child->setOffset($this->insets->left, $this->insets->top);
    return $inner->constrain(...)->inflate($this->insets);   // ② 尺寸加回
}

public function intrinsicWidth(float $height): float
{
    return $child->intrinsicWidth($height - $this->insets->vertical()) + $this->insets->horizontal();
}
```

**这两段必须手工保持一致**，编译器不查。`SizedBox` 更糟：它要处理
`width/height` 各自"设了/没设"的四种组合，`performLayout` 与 `intrinsicWidth`
各写一遍那四种组合。

### 1.2 重复二：有态控件要造一个"盒 Widget"

```php
// src/Widget/SpinnerBox.php:15-19 自己写明了原因
★ **为什么存在**：相位在 `State` 里，而 `StatefulWidget` 自己不产盒
  （`Element::syncBox()` 只认 `RenderBoxWidget`）⇒ 有态的控件与有盒的控件
```

⇒ 每个有态的**叶子**控件都要三个类：`Spinner` + `SpinnerState` + `SpinnerBox`（164 行）。

**每个 State 抄一遍，抄的是"框架不变量"，不是业务**。

已重复的四组：`TextField`(919) / `ScrollView`(213) / `Spinner`(164) / `LazyColumn`(287)。
第 5、6、7 组（`Slider` / `Select` / `DatePicker`）正在等。

## 2. 判据：什么时候该是一个节点

借 v6 `07` §3，一句可机械执行的判据：

> **它要不要自己的 `measure()`？**
> 要 ⇒ 节点（`Scroll` / `Stack` / `Aspect` / `Virtual`）。
> 不要 ⇒ 字段（`padding` / `width` / `background` / `radius` / `opacity` / `translate`）。

用这条判据逐个过现有的修饰类：

| 类 | 要自己的 `measure()` 吗 | 判定 |
|---|---|---|
| `Padding` | 不要 —— 内缩约束 + 尺寸加回，**所有容器都一样** | 字段 |
| `SizedBox` | 不要 —— 收紧约束 | 字段 |
| `Center` | 不要 —— 就是 `align` | 字段 |
| `Expanded` / `Flexible` | 不要 —— 就是 `grow` / `shrink` 份额 | 字段 |
| `Card` | 不要 —— 背景 + 圆角 + 边框 + 阴影 + 内距 | **样式预设**（字段组合） |
| `Spacer` | 不要 —— 就是 `grow(1)` 的空盒 | 字段 |
| `ScrollView` | **要** —— 视口约束主轴无界、偏移进子盒 | 节点 |
| `LazyColumn` | **要** —— 只物化可见区间 | 节点 |
| `Dock` | **要** —— 五区布局 | 节点（算法） |
| `AppBar` | 不要 —— `Row` + 样式 | 组合 |

★ 这条判据的好处：**它不是"我觉得该合并"**，是"内缩约束 + 尺寸加回"这件事
只有一份实现，放在基类；任何容器都不该重写它。

## 3. 修饰值对象 `Modifier`

### 3.1 形状

```php
namespace Drift\Widget;

/**
 * 修饰字段的集合（**值对象**：不可变、按值比较、可共享）。
 *
 * ★ 为什么是一个对象而不是 Widget 上的十几个属性：`Element::syncBox()` 只需把
 *   **一个** 引用递给盒（同 `setCursor()` 的形状），不必为每个修饰加一条传递路径。
 *   12 处抄同一句、漏抄不报错 —— 那是 `Element::syncBox()` 注释里已经写明的问题。
 *
 * ★ 为什么字段是 `private` + 读方法而不是 `public`：`private` 在类外同样不可访问，
 *   但**保留完整的优化能力**（官方 `best_practice.md` §7 原话）；读方法可以用 `#[\Getter]`
 *   生成（**不用手写 20 个方法**，`10` §2 A3/A5），也可以换成 `public`（一次改动、调用点不变）。
 *   ★★ **但类内一律直读 `$this->padLeft`，绝不走 `getPadLeft()`** —— `#[\Getter]` 生成的是
 *   一次**方法调用**：M0-1 实测它比属性读贵 **+22 ns/read**（`docs/AOT-CONSTRAINTS.md` §2.1）。
 *   "编译期零成本"要理解为**"不用手写"**，不是**"运行时免费"**。布局数学全在类内 ⇒ 这条决定
 *   A3 的收益成不成立。
 *
 * ★ **类上不标任何注解**：`#[\Immutable]` 挂不到类上，也挂不到属性上 —— 它只作用于
 *   **实例方法**（该方法内 `$this` 只读）与**参数**（含 `const &` 语义）（`10` §2 A3）。
 *   所以"不可变"在这里靠两件事：① 字段全 `private`，外部改不到；② 每个 `withX()` 里
 *   `clone $this` 写克隆再返回（`clone` 的结果是**可变的新对象**，写它合法）。
 *   ★ 也不能改回 `readonly`：`#[\With]`/`#[\Setter]`/`#[\Native]` 都不支持 `readonly`
 *   （`10` §2 A3/A5）⇒ 用 `readonly` 会把这三条路全堵死。
 *   ★★ **2026-10-21 更正（M0-1 实测）**：原稿这里还写了"且密集访问慢 10×+"，**那句是错的**。
 *   `apps/bench` 三组实测（`docs/AOT-CONSTRAINTS.md` §2.1）：readonly 直读 65 ns/read、
 *   非 readonly 的 `public` 直读 66 ns/read ⇒ **`readonly` 自身零 Hook**（差 −2ns，噪声内）；
 *   真正贵的是 getter（`private`+`v()` 87 ns/read，比属性读贵 +22ns）。
 *   ⇒ 不用 `readonly` 的理由**只剩"不堵 `#[\With]` 等三条路"这一条**，与性能无关。
 *   ⇒ 连带结论：全仓 32 个 `final readonly class` / 187 处 `readonly` **不做性能迁移**。
 */
final class Modifier
{
    // ── 布局维（D_LAYOUT）──
    private float $padLeft = 0.0;
    private float $padTop = 0.0;
    private float $padRight = 0.0;
    private float $padBottom = 0.0;

    /** NAN = 未设（用内容的自然尺寸） */
    private float $width = \NAN;
    private float $height = \NAN;

    // ── 绘制维（D_PAINT）──
    // ★ **不用 `?Color`**：可空对象在编译期退化为 `php::Var`（`10` §2 A2）
    //   ⇒ 用"值 + bool"，与 `03` §3.2 的 `Cell`（`State $owner` + `bool $bound`）同一条判据。
    //   `Color` 没有属性初始化器能用的常量（只有 `Color::black()` 静态方法）
    //   ⇒ 在 `__construct` 里初始化。构造期写入永远合法：`#[\Immutable]` 管的是
    //   **方法内的 `$this`**，而 `__construct` 本来就不能标它（`10` §2 A3）。
    private Color $background;
    private bool $hasBackground = false;
    private Color $borderColor;
    private bool $hasBorder = false;
    private float $borderWidth = 0.0;
    private float $radius = 0.0;
    private float $shadow = 0.0;

    // ── 合成维（D_COMPOSE，见 `05` §5.4）──
    // ★ 这 3 个是**初值**，不是"当前值"：`RenderBox::setMods()` 读一次去初始化
    //   `composeOpacity/composeDx/composeDy`，此后动画走 `setCompose()` 直接写盒，
    //   不再回到这里。`05` §10 #9（rebuild 后"回到 Widget 声明的值"）依赖的正是这条
    //   ⇒ 所以它们**不能删**（删了 `->opacity(0.5)` 只在第一次 layout 生效）。
    private float $opacity = 1.0;
    private float $translateX = 0.0;
    private float $translateY = 0.0;

    // ── 布局意图（见 `04` §2）──
    private int $grow = 0;
    private int $shrink = 0;
    private float $basis = \NAN;
    private int $alignSelf = 0;      // ALIGN_* 常量

    public function __construct()
    {
        $this->background = Color::black();    // 占位：hasBackground 为假时值无意义
        $this->borderColor = Color::black();
    }

    public function hasPadding(): bool;      // 四边全 0 ⇒ false（省一次 save/translate）
    public function hasVisual(): bool;       // 无背景/边框/阴影 ⇒ false（省一次 paintBehind）
    public function hasCompose(): bool;      // opacity==1 && translate==0 ⇒ false
}
```

★ **原稿列为"待真机确认"的那条，官方文档已经回答了**：`immutable.md` 的禁止清单里
"`clone` 的结果是**可变的**"是明写的允许项 ⇒ `withX()` 里 `clone $this` 再写克隆字段**合法**，
不需要退到"全参构造"。`#[\Immutable]` 约束的是 `$this`，不是这个类的所有实例。

★ 但**本类不标 `#[\Immutable]`**（类上标不了）。将来若把读方法改成方案 ③（手写 +
`#[\Immutable]`，`10` §2 A3），`withX()` 照写不误；唯一互斥的是 `#[\Getter]` ——
它生成的是普通方法，而 `#[\Immutable]` 方法里**不能调未标 `#[\Immutable]` 的方法** ⇒
读方法**要么** `#[\Getter]`、**要么** 手写 `#[\Immutable]`，不能兼得。本册选 `#[\Getter]`
（**20** 个字段，手写 20 个方法不值）。

### 3.2 `NAN` 作哨兵，不用 `null`

理由（v6 `13` §1 约束 C）：对象属性是固定类型槽，**`?float` 是可空标量**。
v6 的 V-1 明确"`?int`/`?string` 不退化是**推断**，待实测"。而 `float` + `NAN`
是**确定不退化**的写法。

★ 判据：**`width` 的"未设"与"设为 0"必须是两件事**。
`SizedBox(width: 0)` 是"宽 0"（合法的退化），`SizedBox()` 是"不约束宽"。
用 `0.0` 当哨兵会把两者混成一件事 —— 这正是 `BoxStyle` 现有的 `null/0 = 未设` 问题
（`DESIGN.md` §24.2 #26 的遗留）。用 `NAN` 一次解决。

### 3.3 链式写法

```php
// Widget 上的修饰器（全部返回 static，链式永远在同一个控件上）
public function padding(float $all): static
public function paddingOnly(?float $left = null, ?float $top = null, ...): static
public function size(?float $width = null, ?float $height = null): static
public function width(float $w): static
public function height(float $h): static
public function background(Color $c): static
public function border(Color $c, float $w = 1.0): static
public function radius(float $r): static
public function shadow(float $elevation): static
public function opacity(float $o): static
public function translate(float $dx, float $dy): static
public function align(int $align): static
public function grow(int $weight): static
public function shrink(int $weight): static
public function basis(float $b): static
```

每个方法内部三件事（与 `Widget::cursor()` 同形）：

```php
public function padding(float $all): static
{
    $this->mutate();                 // 封存后写 ⇒ Fatal（既有守卫）
    $this->mods = $this->mods->withPadding($all, $all, $all, $all);  // 值对象，换新不就地改
    return $this;
}
```

★ **值对象换新而不是就地改**：`Modifier` 不可变 ⇒ "同一个 `Modifier` 被两个 Widget 共享"
是安全的（`Column::make()->children([$a, $a])` 合法，同 `Widget::seal()` 的注释）。

★ **`$this->mods` 不能是 `?Modifier`**：`Widget` 是不可变描述，`?Modifier` 会退化成
`Var`（若 V-2 实测成立）。⇒ 构造时就 `new Modifier()`，永远非 null。
**代价**：每个 Widget 多一个对象分配。要不要改成"首次 `padding()` 时才建"取决于
M0 实测（`08` §3 V-4：一帧内 `new` 空对象的成本）。**默认取"总是有"**（简单、无分支）。

### 3.4 装饰绘制：`paintBehind()`

签名 `public function paintBehind(Canvas $canvas, Size $size): void`，
由 `RenderBox::paint()`（§4.2）在画内容**之前**调一次。

**顺序不能反**（阴影在盒外 ⇒ 先画，否则会被底盖掉）：

```php
public function paintBehind(Canvas $canvas, Size $size): void
{
    $rect = new Rect(0.0, 0.0, $size->width, $size->height);

    // ① 柔和阴影：三层递减外扩
    //    外扩 3px · alpha × 0.35 / 外扩 2px · alpha × 0.60 / 外扩 1px · alpha × 1.00
    //    ★ 单层实心矩形看起来像描边（第一眼的判断就是"生硬"），三层叠出过渡带才像影子。
    //      代价 = 每张卡片多 3 次 drawRect（软光栅下可忽略）。
    //    ★ 阴影画在盒外 ⇒ 父布局不会为它留白，卡片之间要留 ≥ 4px 间距，否则邻块底色盖掉它。
    if ($this->shadow > 0.0) {
        $base  = (int) \round(255.0 * \min(1.0, $this->shadow));
        $steps = [3 => 0.35, 2 => 0.60, 1 => 1.00];

        foreach ($steps as $grow => $weight) {
            $alpha = \max(1, (int) \round($base * $weight));
            $canvas->drawRect(
                new Rect(-$grow, -$grow, $size->width + 2 * $grow, $size->height + 2 * $grow),
                Paint::fill(new Color(0, 0, 0, $alpha)),
                $this->radius + $grow,
            );
        }
    }

    // ② 底
    if ($this->hasBackground) {
        $canvas->drawRect($rect, Paint::fill($this->background), $this->radius);
    }

    // ③ 边框
    if ($this->hasBorder && $this->borderWidth > 0.0) {
        $canvas->drawRect(
            $rect,
            Paint::stroke($this->borderColor, $this->borderWidth),
            $this->radius,
        );
    }
}
```

★ **为什么这个方法住在 `Modifier` 而不上移到 `RenderBox`**：它要读 7 个字段
（`background` / `hasBackground` / `borderColor` / `hasBorder` / `borderWidth` / `radius` / `shadow`）。
住 `Modifier` ⇒ 同类内 `private` **直读 0 次方法调用**；住 `RenderBox` ⇒ 每帧每盒
**7 次 `#[\Getter]` 方法调用**。而"类内直读、绝不走 getter"是 §3.1 的纪律本身。

★ **只用 Core op**：`drawRect`（带圆角）属 Core/Extended 层，`RasterCanvas` / `SkiaCanvas` /
`RecordingCanvas` 三后端都支持。**不要**为了阴影去用 `drawPath` / 模糊 mask ——
那是 Optional 层，软光栅会报 `E-OP-UNSUPPORTED`（MEMORY 已记）。

★ **来源**：这段逐字搬自 `src/Layout/RenderCard.php` 的 `paint()`（145 行那个类在 W5 被删，
`RenderCard::performLayout` / `intrinsic*` 由 §4 的基类接管，只剩这 10 行阴影需要新家）。

## 4. `RenderBox` 基类接管三处

### 4.1 `layout()`：内缩 → 量内容 → 加回

```php
// src/Layout/RenderBox.php   改造后的 layout()
final public function layout(BoxConstraints $constraints): Size
{
    $m = $this->mods;

    // ① 尺寸修饰收紧约束（width/height 设了就变成紧的那一轴）
    if ($m !== null) {
        $constraints = $m->tighten($constraints);
    }

    // ② padding 内缩：给子类的约束是**内容盒**的
    $inner = $constraints;
    if ($m !== null && $m->hasPadding()) {
        $inner = $m->deflate($constraints);
    }

    // ③ 子类量内容（**契约变了**：返回内容尺寸，不是盒尺寸）
    $measured = $this->performLayout($inner);

    // ④ padding 加回
    if ($m !== null && $m->hasPadding()) {
        $measured = $m->inflate($measured);
    }

    // ⑤ C6 检查（原样保留）
    if (($measured->width > $constraints->maxWidth || $measured->height > $constraints->maxHeight)
        && !LayoutTolerance::$previewing) {
        Errors::report(...);
    }

    $this->size = $constraints->constrain($measured);

    // ⑥ **子节点整体平移 padding**（唯一一处需要遍历子节点）
    if ($m !== null && $m->hasPadding()) {
        $dx = $m->padLeft();
        $dy = $m->padTop();
        $this->visitChildren(function (RenderObject $c) use ($dx, $dy): void {
            if ($c instanceof RenderBox) {
                $c->setOffset($c->offsetX() + $dx, $c->offsetY() + $dy);
            }
        });
    }

    return $this->size;
}
```

★ **第 ⑥ 步是整个设计的关键**，也是它为什么可行的原因：

`performLayout()` 收到的是**内容盒约束**，所以容器把子节点摆在
"内容盒原点"坐标系里 —— 这与它们现在的写法**完全一致**（容器本来就是从 (0,0) 开始摆）。
基类量完之后把子节点整体平移 `(padLeft, padTop)`，就从"内容盒坐标系"换到了"边框盒坐标系"。

⇒ **20 个容器的 `performLayout` 一行都不用改。** 这是"用坐标变换代替 20 处改动"。

★ 代价：`visitChildren` 一次 O(子数) 的指针写。与同帧的 `layout()` 同阶，可忽略。

★ 边界：**`setOffset` 是 `protected`**。基类调子类的 `protected` 方法在 PHP 里合法
（同类层级），在 tpc 下也合法（字段偏移查运行时类）。但**不要**改成 `public` —— 那会破坏
C1「父定位子，子不自定位」的可见性约束。

### 4.1.1 ★ 两个坐标系：`absoluteOrigin` 给的是**边框盒**原点

§4.1 的 ⑥ 步把 padding 从"祖先盒"搬进了**同一个盒**，于是同一个盒上出现了两个原点：

```
边框盒原点 ──(padLeft, padTop)── 内容盒原点
```

| 坐标系 | 谁在这个系里 | 谁给 |
|---|---|---|
| **边框盒** | `absoluteOrigin()` 的返回值、`$box->size()`、`hitTest()` 的入参 | `RenderBox::absoluteOrigin()` |
| **内容盒** | `performLayout()` 的入参约束、`paintContent()` 的绘制坐标、`caretRect()` / `offsetAt()` 的期望入参 | 基类 ⑥ 步之前的一切 |

★ **W5 之前这两者是同一个**（padding 是祖先盒，所以 `absoluteOrigin(TextFieldBox)` 已经含了 pad）。
W5 之后它们差一个 `(padLeft, padTop)`。凡是"内容盒坐标 → 窗口坐标"的地方**都要补上 pad**。

`paint()` 那条路是对的（§4.2 已经 `translate(padLeft, padTop)` 再调 `paintContent()`），
但**不走画布的那些路径不会被 translate 覆盖**。逐条核对全部 `absoluteOrigin` 调用点：

| 位置 | 用法 | W5 之后 |
|---|---|---|
| `Application.php:793` `imeCaretRect()` | `origin + caretRect()` —— `caretRect()` 是**内容盒**坐标（`RenderTextField.php:38` 原注"盒内坐标（含内边距）"） | ★ **错**：候选框偏 `(padLeft, padTop)` |
| `Application.php:863` / `:888` 文本选区点击 | `$box->offsetAt($x - $origin)` —— `offsetAt()` 自己减 `$insets->left`，即它要的是**内容盒** x（`RenderTextField.php:184-186`） | ★ **错**：插入符落点偏右 `padLeft` ⇒ 点到的是后面几个字 |
| `Application.php:553` 菜单锚点 | `origin + $box->size()->height` —— 只用盒尺寸，不掺盒内坐标 | 对（边框盒底边就是要的位置） |
| `Application.php:1632` 滚动条拇指命中 | `origin + thumbRect()` —— `thumbRect()` 用 `$this->size` 算，是**边框盒**坐标 | 对（两边同系） |
| `SemanticsBuilder.php:81` UIA `BoundingRectangle` | `origin + 盒尺寸` | 对 |

⇒ **两处要改**（`:793` / `:863` / `:888` 共三条语句），三处不用改。
改法统一：**"内容盒 → 窗口"的地方显式加 `$m->padLeft()` / `$m->padTop()`**，
并在这三处各写一行注释指向本节（否则下一个人会以为多加了）。

★ 为什么这条容易漏：**插入符自己画得是对的**（走 `paint()` 的 translate），
只有 IME 候选框和点击落点错；而候选框是**独立原生窗口**，不在应用截图里
⇒ `09` §7 那四类"只有真机能抓"的失败模式**一条也抓不到它**。只能靠无头几何断言（§7.2 M2-2b）。

### 4.2 `paint()`：装饰 → 平移 → 内容

```php
final public function paint(Canvas $canvas): void
{
    $m = $this->mods;
    $size = $this->size;

    // ① 背景 / 边框 / 圆角 / 阴影（画在自己身上，子节点之上）
    if ($m !== null && $size !== null && $m->hasVisual()) {
        $m->paintBehind($canvas, $size);
    }

    // ② 内容：有 padding ⇒ 平移后画
    if ($m !== null && $m->hasPadding()) {
        $canvas->save();
        $canvas->translate($m->padLeft(), $m->padTop());
        $this->paintContent($canvas);
        $canvas->restore();

        return;
    }

    $this->paintContent($canvas);
}

/** 子类只实现这一层（原 `paint()`，20 个文件改名） */
abstract protected function paintContent(Canvas $canvas): void;
```

★ **为什么 `paint()` 也做成 `final`**：`layout()` 早就是 `final`（`RenderBox.php:88`），
理由写在它的注释里 —— "约束检查（C6）只该有一处"。现在多了"装饰 + padding 平移"，
**同一个理由成立**：装饰只该画一处。

★ **为什么改名而不是加一个 `paintDecorated()` 让父容器调**：父容器调的话，
"每个容器都要记得调"就是 12+ 处抄同一句、漏抄不报错 —— 正是 `syncBox()` 注释里
点明的那类问题。做成 `final` + `abstract` 让**编译器强制**：漏改名 = "抽象方法未实现" = Fatal。

★ **`translate()` 的坑**：它只改 PHP 侧 `offsetX/offsetY`，从不调 Skia（MEMORY 记载）。
所以 `save()` 必须真的保存/恢复这个偏移。这一点**要在 M0 里验一条**（`08` §3 V-5）：
`RecordingCanvas` 的 `saveDepth` 与 `RasterCanvas`/`SkiaCanvas` 的偏移栈是否一致。
若不一致 ⇒ `paintBehind` 与 `paintContent` 会画错位，且只在某一个后端上错。

### 4.3 `intrinsicWidth/Height`：也由基类接管

```php
final public function intrinsicWidth(float $height): float
{
    $m = $this->mods;

    // ① 显式宽度 ⇒ 直接是它（不再问内容）
    if ($m !== null && !\is_nan($m->width())) {
        return $m->width();
    }

    // ② 内容的内禀 + padding
    $h = $height;
    if ($m !== null && $m->hasPadding()) {
        $h -= $m->padTop() + $m->padBottom();     // 内容盒可用高度
    }
    $w = $this->contentIntrinsicWidth($h);

    if ($m !== null && $m->hasPadding()) {
        $w += $m->padLeft() + $m->padRight();
    }

    return $w;
}

abstract protected function contentIntrinsicWidth(float $height): float;
```

⇒ **"`width` 设了就问它、没设就问内容 + padding"这件事只有一份实现。**
`SizedBox` 的那四种组合、`Padding` 的加回、`Center` 的转发，全部消失。

★ 这解决 P4 的**一半**：修饰类不再有"两套实现必须手工一致"的问题。
剩下的一半（控件自己的 `performLayout` 与 `contentIntrinsic*` 仍可能不一致）
由 `04` §5 的 `verifyLayout()` 用全量重算当 oracle 来**证明**。

## 5. 八原语

改完之后，`RenderBox` 的具体子类从 **21 → 16**（少 4 个纯修饰盒 + 1 个样式预设盒 `RenderCard`），
再往下压需要合并语义相近的。目标形态（借 v6 `08` §1 的"八种原语"）：

| # | 原语 | 算法 | 现有对应 | 状态 |
|---|---|---|---|---|
| 1 | `Box` | `leaf` | 无（修饰字段直接落在任何控件上） | **新增（无渲染逻辑，只是"有修饰的叶子"的基类）** |
| 2 | `Flex` | `column` / `row` | `RenderFlex` | 已有（`Row`/`Column` 共用） |
| 3 | `Stack` | `stack` | **无** | **新增** |
| 4 | `Scroll` | `scroll` | `RenderScrollView` + `LazyColumn` | 已有（虚拟化是它的模式） |
| 5 | `Dock` | `dock` | `RenderDock` | 已有 |
| 6 | `Text` | `leaf` | `RenderText` | 已有 |
| 7 | `CustomPaint` | `leaf` | `RenderCustomPaint` | 已有 |
| 8 | `TextField` | `leaf`（自己排版） | `RenderTextField` | 已有（暂不并入 `Text`） |

其余（`Button`/`Card`/`Toggle`/`Progress`/`Divider`/`MenuItem`/`PopupPanel`/`AppBar`）
全部是"原语 + 样式预设"，不再各自持有布局算法。

### 5.1 `Stack` 是唯一真缺的布局原语

```bash
ls src/Widget/ | grep -i "stack\|align\|wrap\|grid"    # 空
```

**为什么现在必须补**：改完修饰字段之后，剩下三类需求无处表达：

1. 浮层里的层叠（`01` 的模态面板是"居中 + 层叠"）
2. 徽标 / 覆盖提示（一个角标压在图标上）
3. 骨架屏（占位块压在内容上）

用 `Dock` 表达不了（它是五区），用 `Flex` 表达不了（它不重叠）。

★ **本册只回答"它该不该存在"（§2 的判据：要不要自己的 `measure()` ⇒ 要）。
形状、`StackFit`/`StackAlign` 两个枚举、两遍布局、命中顺序全部以 `04` §4 为准**
（`09` §1 冲突 3 已裁决：一个原语只定义一次，归 `04`）。
★ 上一版这里曾写过 `->align(Align::TopRight)` —— **那是错的**：本仓没有 `Align` 这个类型，
`04` §4 定的是 `->alignment(StackAlign::TopRight)` + `->fit(StackFit::Loose)`。

★ **不引入 `zIndex`** 的理由（v6 `04` §7 原话）：两套顺序必然打架，
且"同 z 值时谁在上"需要稳定排序规则，规则一复杂就没人记得住。`z` 序 = 子数组顺序。

### 5.2 不做 `Wrap` / `Grid`

| 原语 | 为什么不做 |
|---|---|
| `Wrap` | 需要 S2 两遍布局（先量所有子的固有宽才知道一行放几个）。Drift2 的 `RenderFlex` 是单遍。**没有消费者之前不引入两遍布局** —— 它会让"布局是纯函数"从结构保证退化为纪律 |
| `Grid` | 同上 + 需要 `span` 意图字段 |

★ 触发条件写死：**出现"标签云"或"图片墙"的真实页面**再做，且届时必须同时引入
`04` §5 的自校验（两遍布局是缓存最容易出错的地方）。

## 6. 控件产盒：消灭"三件套"

### 6.1 现状的病根

```php
// src/Widget/Element.php:106-116
protected function syncBox(): void
{
    $this->box = $this->widget instanceof RenderBoxWidget
        ? $this->widget->createRenderObject($this->context)
        : null;
    $this->box?->setCursor($this->widget->cursorShape());
}
```

`StatefulWidget` 不是 `RenderBoxWidget` ⇒ 没有盒 ⇒ 必须再包一层 `*Box`。

### 6.2 解：`StatefulWidget` 可以直接产盒

```php
// src/Widget/StatefulWidget.php 新增一个钩子
/**
 * 直接从 State 产渲染盒（可选）。
 *
 * 返回 null（默认）⇒ 走 `build()` 那条路：本控件是"组合"，子层由 State 描述。
 * 返回盒 ⇒ 本控件是"叶子"，不再有子节点，`State::build()` 不会被调用。
 *
 * ★ 为什么是钩子而不是让 `StatefulWidget extends RenderBoxWidget`：
 *   后者会让"有态"与"有盒"强制绑定，而 `TextField` 恰恰两者都要（有态、有盒、
 *   且有子 —— label 与输入框是两个盒）。钩子允许"三选一"。
 */
public function createRenderObjectFromState(BuildContext $context, State $state): ?RenderBox
{
    return null;
}
```

```php
// src/Widget/StatefulElement.php 改造
/** @internal 本节点的盒是不是 State 直接产的（决定 rebuild 走哪条路） */
private bool $boxFromState = false;

protected function syncBox(): void
{
    $box = null;
    if ($this->state !== null && $this->widget instanceof StatefulWidget) {
        $box = $this->widget->createRenderObjectFromState($this->context, $this->state);
    }

    if ($box !== null) {
        $this->box = $box;
        $this->boxFromState = true;
        $this->box->setCursor($this->widget->cursorShape());

        return;
    }

    $this->boxFromState = false;
    parent::syncBox();
}

public function rebuild(): void
{
    $this->state?->consumeDirty();
    if ($this->state === null) {
        return;
    }

    // 叶子：只换盒，不产子
    if ($this->boxFromState) {
        $this->syncBox();

        return;
    }

    $this->updateChildren([$this->state->build($this->context)]);
}
```

`Spinner` 改造后：

```php
final class Spinner extends StatefulWidget
{
    private float $diameter = 24.0;

    public function createState(): State { return new SpinnerState(); }

    public function createRenderObjectFromState(BuildContext $ctx, State $state): ?RenderBox
    {
        /** @var SpinnerState $state */

            $this->diameter,
            $state->step(),
            $ctx->color(ColorToken::Accent),

```

**`SpinnerBox` 删除（45 行），`SpinnerState::build()` 与 `spinner()` 删除（约 25 行）。**
164 行 → 约 95 行，且不再有"为什么要有第三个类"的解释。

### 6.3 `State::build()` 从抽象改成有默认实现

```php
// src/Widget/State.php
/**
 * 描述子层。
 *
 * ★ 默认实现**只为"直接产盒"的控件存在** —— 它们的 `build()` 永远不会被调用
 *   （`StatefulElement` 看到 `createRenderObjectFromState()` 非 null 就不走这条路）。
 *   返回零尺寸而不是抛异常：抛异常会把"忘记 override"变成 Fatal，而那个遗漏
 *   本身无害（返回值没人读）。
 *
 * ★ 为什么不做成"`build()` 与 `createRenderObjectFromState()` 二选一必填"：
 *   PHP 无法表达"抽象方法二选一"，AOT 更不行（无反射）。默认实现是唯一可编译的形态。
 */
public function build(BuildContext $ctx): Widget
{
    return SizedBox::make(0.0, 0.0);
}
```

★ 这是一处**契约弱化**，诚实标注：写错的代价是"控件不显示"，不是"编译失败"。
防线：`createRenderObjectFromState()` 返回非 null 的控件，smoke 里加一条
"它的 `build()` 未被调用"的断言（用 `Errors::report` 打桩或计数器）。

### 6.4 不做的：`TextField` / `ScrollView` 保留三件套

两者都**有子**（`TextField` 的 label + 输入框、`ScrollView` 的内容），
`createRenderObjectFromState` 的"不产子"语义不适用。
⇒ 保留 `TextFieldBox` / `ScrollViewBox`，但**在注释里写明它们是"有子"的特例**，
不是"框架要求"。这样下一个写控件的人知道"叶子不用三件套"。

### 6.5 落地实况（2026-10-23 ✅）

§6.2/§6.3 的形状**一字未改**地落地，`Spinner` 改造完成、`SpinnerBox` 删除
（45 行）。实际落地与册子有三处出入，都是册子没想到的：

## 7. 迁移

### 7.1 四类 shim（应用侧零改动）

```php
// src/Widget/Padding.php 改造后（保留类名，不再是可挂载的 Widget）
/**
 * @deprecated 用 `$x->padding(8)`。本类保留只为迁移：`->child()` 直接转成修饰器。
 */
final class Padding extends Widget
{
    private float $all;

    public static function make(float $all): self { ... }

    /** ★ 返回**子控件本身**（已带上 padding），不是 Padding 实例 */
    public function child(Widget $child): Widget
    {
        return $child->padding($this->all);
    }

    public function createElement(): Element
    {
        Errors::report(
            '`Padding::make(8)` 没有接 `->child(...)`，它已经不是可挂载的控件了。'
            . '两条修法：① 直接写 `$x->padding(8)`；② 检查是不是漏了 `->child($x)`。'
        );

        return parent::createElement();
    }
}
```

六个 shim：`Padding`（→ `padding`）/ `SizedBox`（→ `size`）/ `Center`（→ `align`）/
`Expanded`（→ `grow`）/ `Flexible`（→ `shrink`）/ `Spacer`（→ `grow(1)` 的空 `Box`）。

`Card` **不是 shim** —— 它变成"样式预设"，且形态是 **`StatelessWidget`**（不是 shim 那种"`child()` 直接转发"）：

```php
final class Card extends StatelessWidget
{
    public function build(BuildContext $ctx): Widget
    {
        $theme = $ctx->theme();

        // ★ clone：Card 的语义是"包一层"，不是"给这个控件加样式"。
        //   Widget 可共享（`children([$a, $a])` 合法，§3.3）⇒ 就地 mutate 会把样式漏给另一处引用。
        $kid = clone $this->kid;

        $style = $this->box ?? BoxStyle::none()
            ->withBackground($theme->color(ColorToken::Surface))
            ->withBorder($theme->color(ColorToken::Border), 1.0)
            ->withRadius(2.0);

        return $kid->background($style->background)
            ->border($style->borderColor, $style->borderWidth)
            ->radius($style->radius)
            ->shadow($this->shadow)
            ->padding($this->padding);
    }
}
```

★ **为什么必须是 `build(BuildContext)` 而不是 `child()` 直接转发**：`Card` 的默认样式要取
主题 token（`ColorToken::Surface` / `Border`），而主题只能从 `BuildContext::theme()` 拿。
`child()` 的签名里没有 context ⇒ 只能硬编码颜色。`StatelessWidget::build()` 是这个仓里
唯一"有 context 又只做组合"的位置（`AppBar` / `Dock` / `Flex` / `ThemeScope` 都是这个形状）。

★ **必须同时给 `Widget` 加 `__clone()`**（3 行）：

```php
// src/Widget/Widget.php
/** ★ 克隆 = 复制一份"可再配置的描述" ⇒ 封存位必须归零，否则 clone 出来的东西写不了 */
public function __clone(): void
{
    $this->sealed = 0;
}
```

理由：`$sealed` 是 `private int`，`clone` 会**连它一起复制** ⇒ 克隆一个已封存的 Widget，
得到的也是封存的，紧接着 `->background()` 里的 `mutate()` 直接 Fatal。
本仓今天没有任何 `__clone`（`grep -rn __clone src/` 空），这条从来没被验过。

★ **`Card` 不再继承 `BoxWidget`**（`BoxWidget extends RenderBoxWidget`，"有方法 ⇒ 必须是那个类型"）。
它自己持有一个 `?BoxStyle $box`（`BoxStyle` 当值容器复用，不复制实现），并保留
`->background()` / `->border()` / `->radius()` 三个 setter 的既有语义：
**调了任何一个 ⇒ 整套默认让位**（`Card.php` 头注释 §15.7 纪律 3）。
`BoxStyle` 本身不动 —— `Button` / `PopupPanel` 仍产 `RenderButton` / `RenderPopupPanel`，仍吃它。

| M2-5 | 删除五个 RenderBox 类（`RenderPadding`/`RenderSizedBox`/`RenderCenter`/`RenderFlexible`/`RenderCard`）+ 对应 Widget 的 `createRenderObject`；`Card` 改 `StatelessWidget`（§7.1）+ `Widget::__clone()`；**删掉 `ProxyElement::expand()` 的 `instanceof Card` 分支** | `grep -c "RenderPadding\|RenderSizedBox\|RenderCenter\|RenderFlexible\|RenderCard" src/` = 0；`grep -c "instanceof Card" src/Widget/ProxyElement.php` = 0 |

★ **M2-2 是唯一有"全局改名"的一步**（20 个文件 `paint` → `paintContent`）。
用 PHP 脚本一次应用（带断言：每个文件必须命中 1 次 `function paint(`），
不要手改 —— 手改 20 个文件必漏。

★ **M2-3 与 M2-4 的顺序不能反**：先让旧类改成"纯内容"语义，再让 shim 生效。
反过来的话，`Padding::make(8)->child($x)` 已经变成 `$x->padding(8)`，
而 `RenderPadding` 还在做内缩 ⇒ **padding 被应用两次**（视觉上内距翻倍，
且不报错）。这是本册最容易踩的一步。

## 8. 备选方案与否决

| 备选 | 否决理由 |
|---|---|
| **保留包装节点，只把内禀尺寸统一** | 只解 P4 的一半，扩展性零收益（加修饰器仍要写三件套） |
| **Compose 式 `Modifier` 链（`->padding(8)->background()` 返回 `Padding` 对象）** | 顺序有语义（`padding` 两次结果不同）、返回类型会变、AOT 下链式退化为动态分派（v6 `07` §3） |
| **让 `Padding` 继承 `Widget` 但共享一个 `RenderDecorated` 盒** | 只把 4 个盒合成 1 个，节点数不变（还是每修饰一层）⇒ 布局次数不变 |
| **`paint()` 保持抽象，父容器调 `paintDecorated()`** | 12+ 处抄同一句、漏抄不报错（`syncBox()` 注释已写明这类问题） |
| **`Modifier` 用 `?Modifier` 字段** | 可空对象退化 `Var`（若 V-2 成立）；且"有没有修饰"多一个分支 |
| **`width` 用 `0.0` 当"未设"哨兵** | 与"宽 0"混为一谈（`BoxStyle` 现有的问题，`DESIGN.md` §24.2 #26） |
| **`StatefulWidget extends RenderBoxWidget`** | 强制"有态 ⇒ 有盒"，`TextField` 两者都要且有子，表达不了 |

### 推翻条件

| 决策 | 什么情况下应推翻 |
|---|---|
| 修饰是字段 | 若出现"必须在任意节点插入一个改变布局**阶段**的修饰"（如 `baselineAlign`），引入**布局参与型修饰**作为显式节点，**不恢复通用链**（v6 `11` D-05 原话） |

## 11. W5 动工前的五条裁决（2026-10-22，全部有实测依据）

> 本节推翻上面若干处原稿。**写代码时以本节为准**，上面的段落保留原样只为看出"改了什么、为什么改"。

### 11.1 ★★★ `#[\Getter]` / `#[\With]` 在 `src/` 里**不可用** —— 它们只在 tpc 编译期存在

**实测**（`_build/getter_probe.php`，5 行）：

```php
final class Probe { #[\Getter] private float $padLeft = 1.5; }
echo (new Probe())->getPadLeft();
// php.exe ⇒ Fatal error: Uncaught Error: Call to undefined method Probe::getPadLeft()
```

官方 `typephp-docs/zh-cn/getter.md` 原文确认：「Getter 方法在**编译期静态生成**……
**运行时不解析 Attribute**、不使用反射」。`with.md` 同形。

⇒ 而 `smoke.php` / `lint.php` / `M2Conformance` / `drift-preview` / `selftest` **全部跑在 `php.exe` 上**。
⇒ 用 `#[\Getter]` ⇒ **1000 条 smoke 断言在 M2-1 第一步就全 Fatal**，而 T2 的 AOT 构建照样绿
—— 这正是最坏的一类失败：**闸门本身跑不起来，但看起来"编译通过"**。

**裁决：`Modifier` 不标任何编译期注解**，21 个字段手写**按用途成形**的读写方法
（不是 21 个 `getXxx()` 样板）。分组见 §11.6 末尾的表。

三条理由：
① **双后端等价** —— `src/` 的既有判据是"解释器能跑、AOT 也能跑"。编译期注解只满足后者。
② **按用途成形 ⇒ 9 个 `with*` 而不是 21 个**：`background` 必须同时写 `hasBackground`，
   `padding` 要同时写四个边，`border` 要同时写颜色与宽度 —— 单字段 `withXxx()` **一个都不够用**，
   `10` §A5 自己也写了"多字段的 6–8 个方法仍然手写"。
③ `02` §3.4 担心的"每帧每盒 7 次 getter 方法调用"**不存在**：`paintBehind()` / `tighten()` /
   `deflate()` / `inflate()` 全在 `Modifier` 类内直读字段，外部只剩 `RenderBox` 的
   `hasPadding()/padLeft()/padTop()/hasVisual()/hasCompose()` 五次。

**连带作废**：`09` §出口判据里的 `grep -c '#\[\\Getter\]' = 20`、`grep -c '#\[\\With\]' = 20`。
改成：

```bash
grep -cE '#\[\\\\(Getter|With|Setter)\]' src/   # 0
grep -c  'public function '  src/Widget/Modifier.php   # 21（读 12 + 写 9）
```

★ **并升级为长期判据**：`src/` 里只许用 **PHP 原生**注解（今天只有 `#[\Override]`，62 处）。
tpc 独有的编译期注解（`Getter`/`Setter`/`With`/`Constructor`/`NoExport`）**一律不进 `src/`** ——
它们会让"解释器闸门"与"AOT 产物"看到两个不同的类。

### 11.2 `padding` 的签名冲突 —— `Widget::padding()` 必须收 `EdgeInsets`

`02` §3.3 原写 `padding(float $all)`。实测：`padding(EdgeInsets $v)` **已经存在于 5 个控件**
（`Flex` / `LazyColumn` / `PopupPanel` / `Card` / `Padding`），且 `apps/` 里有 **13 处**
`Column::make()->padding(EdgeInsets::all(20.0))`。

`Widget::padding(float)` 与子类 `padding(EdgeInsets)` **参数类型不兼容 ⇒ 类声明期 Fatal**（LSP 检查），
不是"跑起来才发现"，而是**整个 `src/` 装载不起来**。

**裁决**：

```php
public function padding(EdgeInsets $insets): static      // 主形态
public function paddingAll(float $all): static           // 糖（这个名字在 Card/Flex 上已存在）
public function paddingOnly(?float $l = null, ?float $t = null, ?float $r = null, ?float $b = null): static
```

- 13 处调用点 **零改动**；
- `Flex::padding/paddingAll`、`Card::padding/paddingAll`、`Padding::padding` **直接删**（继承即生效）；
- `LazyColumn::padding`、`PopupPanel::padding` **保留覆写** —— 它们的内距参与**滚动虚高 / 面板自身**的布局，
  不进 `mods`。签名与基类一致 ⇒ 覆写合法；`mods` 保持默认 ⇒ **不会双算**。
- `Padding::make(8)->child($x)` shim ⇒ `$x->padding(EdgeInsets::all(8.0))`。

★ 这一条同时解掉 `Card` 在 M2-5 改成 `StatelessWidget` 之后 `Card::padding(EdgeInsets)` 与基类冲突的死结
（否则 M2-5 会撞一个"要么改 13 处调用点、要么给 Card 换个方法名"的两难）。

### 11.3 `Center` 不是 `align`：加第 21 个字段 `center`，`RenderCenter` 照删

`02` §2 与 §7.1 把 `Center` 判成"就是 `align`" ⇒ `Modifier::$alignSelf`。**这条是错的**：

`alignSelf` 只在 `RenderFlex::placeChildren()` 里被消费。而 `Center::make()` 有 **3 处是页面根**：

| 位置 | 用法 |
|---|---|
| `apps/hello/src/HelloApplication.php:31` | `return Center::make()->cursor(...)->child(...)` —— **整页根** |
| `tools/Preview/ShellPage.php:52` | 内容区根 |
| `tools/Preview/M2LayoutPage.php:62` | 内容区根 |

根上没有 Flex 父 ⇒ `alignSelf` 是**死字段**，`hello` 会从"居中的一句话"变成"左上角"。

**裁决**：`Modifier` 加 `bool $center`，由基类 `layout()` 的**第 ⑥ 步**消费 —— 与 padding 是同一处，
因为两者是同一类操作：**"把直接子盒整体平移"**，只是 padding 的位移是常量、center 的位移由
`(自身尺寸 − 内容尺寸)` 算出：

```php
// ⑥ 后置平移直接子盒
$dx = $m->padLeft();
$dy = $m->padTop();

if ($m->hasCenter()) {
    $dx += \max(0.0, ($this->size->width  - $m->padLeft() - $m->padRight()  - $contentW) / 2.0);
    $dy += \max(0.0, ($this->size->height - $m->padTop()  - $m->padBottom() - $contentH) / 2.0);
}
```

**并且 `hasCenter()` 为真时 `$inner = $inner->loosen()`** —— `RenderCenter` 今天正是给子
`loosen()`（`RenderCenter.php:25`）。不补这一句，`Center` 在 `Stretch` 的 Flex 里会退化成
"子被拉满、居中失效"；而 `apps/hello` 的根**恰好吃紧约束**，这条一定会被真机抓到。

⇒ `RenderCenter` 照删，`Center` 的 11 处调用点零改动，**"5 个 RenderBox 消失"的目标保住**。

### 11.4 §4.1 第 ⑥ 步的可行性：16 处 `setOffset` 全部自身起算 —— 已逐点核对

```bash
grep -n "setOffset(" src/Layout/*.php      # 16 处
```

| 文件:行 | 起算 |
|---|---|
| `RenderFlex:329/331` | `$pen` 从 `$this->padding->top/left` 起 —— **它自己的**内距，与 `mods` 是两个来源 |
| `RenderCard:74` / `RenderPadding:35` / `RenderMenuItem:106` / `RenderPopupPanel:83` | `$this->padding/insets`，同上 |
| `RenderDock:113-117` / `RenderCenter:28` / `RenderSizedBox:97` / `RenderScrollView:149/151` / `RenderModalHost:68` / `RenderButton:62` / `RenderToggle:90` | 纯 `(0,0)` 或自身尺寸派生 |

**没有任何容器把父偏移算进子 offset** ⇒ ⑥ 步的"整体平移"对 19 个 `performLayout` **一律成立**，
不需要逐个确认起算约定。

★ 顺带：`RenderFlex::$padding` 这个字段在 M2-3 之后**必须删除**（连同 `performLayout` 里的
`+ $this->padding->horizontal()` 与 `placeChildren()` 里的 `$pen` 起点），否则
`Column()->padding(...)` 会走 `mods`（基类施加）**且** `RenderFlex` 自己再加一遍 —— 内距翻倍、不报错。
`PopupPanel`/`MenuItem`/`LazyColumn` 的内距**保留**（它们是控件自身的几何，不是用户修饰）。

#### ★★★ 缺口：`StatefulWidget` / `StatelessWidget` 上的修饰**无处可去**

```
   laid out size = 41.0 x 24.8      ← 加了 pad 尺寸一点没变
```

**裁决**：`syncBox()` 在"没有自己的盒、但 mods 非默认"时**响亮失败**（FATAL，与

落地后补。当前由"真机三帧 `ink` 逐像素不变"（M2-1 与 M2-2 都是 `10.6`）守 §4.1.1 的修正不回归。

### 11.8 M2-3 实况（2026-10-22）—— 第 ⑦ 步被推翻，第 ⑤ 步要夹一次

#### ① 第 ⑦ 步不能平移 padding（原 §4.1 的写法会双重平移）

§4.1 原本把 padding 的位移也放进第 ⑦ 步（"子盒改住边框盒坐标"），理由是
`hitTest()` / `absoluteOrigin()` 都按边框盒坐标算。**这条被 M2-3 推翻**：

| 谁 | 需要子盒 offset 住哪 |
|---|---|
| `paint()` | 基类已经 `translate(padLeft, padTop)` ⇒ 子盒再带 padding 就**画偏一个 padding** |
| `hitTest()` / `absoluteOrigin()` | 要边框盒坐标 ⇒ 要么子盒带 padding，要么这两处补 |

两边都要，且不能同时满足 —— 除非其中一处补。**裁决：子盒 offset 住内容盒坐标**
（与 19 个 `performLayout` 原本的写法一致），换算在 `paint()` 的 `translate()` 与
新增的 `RenderBox::contentOriginX/Y()` 里各补一次：

```
绘制：save → translate(padLeft, padTop) → paintContent → restore
几何：hitTest(x − padX − child.offsetX) / absoluteOrigin 每上一层补父的内容原点
```

⇒ `performLayout()` **与** `paintContent()` 一行都不用改（19 个容器、8 个测试盒）。

★ 为什么 M2-2 没暴露：当时**没有任何生产控件**把 padding 写进 `mods`（`Flex` /
`Card` / `Padding` / `LazyColumn` / `PopupPanel` 全都覆写 `padding()` 写自有字段）
⇒ `paint()` 的 `translate` 一次都没触发。M2-3 把 `Padding` 接上 `mods` 之后它才生效。

#### ② 第 ⑤ 步要**先夹进约束**再交给 ⑥

`Padding::all(250)` 塞进 200 高的槽，W5 之前的 `RenderPadding` 返回的是
`constrain(inflate(child))` ⇒ 静默裁剪。新写法在 ⑤ 加回 padding 后直接交给 C6，
`500 > 200` ⇒ **FATAL**（smoke 在 `Flex · 弹性内容比视口长` 那条上当场炸）。
修法：⑤ 加回后立刻 `$constraints->constrain(...)`。内容自己超约束（`SolidBox(500)`
塞进 100 宽）仍由 ⑥ 响亮报 —— 那才是 C6 要抓的东西。

#### ③ 三个盒收敛成 `RenderProxy`，`Padding` / `SizedBox` 改走 `mods`

| 原类 | 现在 |
|---|---|
| `RenderPadding` | **删**；`Padding::createRenderObject()` → `new RenderProxy()`，内距进 `mods` |
| `RenderSizedBox` | **删**；`SizedBox::width/height` 直接继承 `Widget`（写 `mods`），`Modifier::tighten()` 是原来逐轴夹取的逐行同构 |
| `RenderCenter` | **留到 M2-4**（见 ④） |
| `RenderFlexible` | 不动：`performLayout` 本来就是纯转发，份额仍住构造器 |
| `RenderCard` | **留到 M2-5**（见 ④） |

#### ④ 两条刻意留后的

- **`Center`**：`RenderCenter` 按 `constraints->maxWidth` 算居中偏移（loose 约束下
  会把子推到**盒外** —— 盒尺寸仍是子尺寸），基类按 `size − measured` 算。两者只在
  **父给紧约束**时一致。改它是一次**语义修正**，不该混进"零行为变化"的一步。
- **`Card`**：默认样式（`Pane` / `Border` / 圆角 2）在 `createRenderObject()` 里用
  `$context->theme()` 解析，而 `Element::syncBox()` 递的是 `widget->mods()`（不含
  主题派生默认值）⇒ 需要一个 `Widget::renderMods(BuildContext)` 那一层。它属于
  "`BoxWidget` 的 `BoxStyle` 与 `mods` 合一"那一步。

#### ⑤ 连带修：夹具里的 `boxOrigin()` 必须委派

`tools/smoke.php` 的 `boxOrigin()` 手抄了一遍"沿父链累加 offset"——正是 ① 说的
第三份副本。`Padding::all(24)` 的字段盒因此算成 `(0,0)`，**7 条框选/光标断言全红**
（`caret=3` 而不是 0、`IBeam` 退化成 `Default`）。修法：`return RenderBox::absoluteOrigin($box);`。
同一批还修了浮层项点击（`boxOrigin` 已是绝对值，再叠 `menuOrigin()` 就加两遍 ⇒
点落面板外、静默不生效）。

### 11.9 M2-4 实况（2026-10-22）—— 居中的口径，以及一条断言语义反转

#### ① `center` 的偏移按**可用空间**算，不是按盒尺寸

M2-2 写的第 ⑦ 步是 `(size − measured) / 2`。它在**紧**约束下与旧 `RenderCenter`
一致（`size` 被 `constrain()` 顶到上限），但在**松**约束下不同：

| 约束 | `RenderCenter`（旧） | `size − measured`（M2-2 写法） |
|---|---|---|
| `tight(100)` | 盒 100、偏移 (100−子)/2 | 盒 100、偏移 (100−子)/2 ✅ 同 |
| `loose(100)` | 盒 = 子、偏移 (100−子)/2 | 盒 = 子、偏移 **0**（等于没居中） |

M2-4 的判据是「删 `RenderCenter` 而**零行为变化**」⇒ 采用旧口径：

```php
$dx = $inner->hasBoundedWidth() ? max(0.0, ($inner->maxWidth - $measured->width) / 2.0) : 0.0;
```

★ **这个口径 2026-10-23 已修正**（`Center` 的松约束缺陷）。原口径有两处错：

1. **松约束下孩子被推到盒外**：盒 = 孩子尺寸，偏移却按上限算 ⇒ 孩子落在盒右/下边界
   之外。画面"看起来居中"，但 `hitTest` 按小盒判定（点不到），`Modifier::clip`
   （2026-10-23 起真裁）会把它**裁掉**。
2. **有 padding 时完全不居中**：`$measured` 在 ⑤ 步已加回 padding（是**盒**尺寸），
   而 `$inner->maxWidth` 是**内容区**宽 ⇒ `(内容区 − 盒宽) / 2 < 0` ⇒ 被
   `max(0.0, …)` 夹成 **0**。

现在的口径（`RenderBox::layout()` ⑦）：

```php
$dx = max(0.0, ($boxSize->width - padding - $content->width) / 2.0);
```

`$content` 是 `performLayout()` 的**原始返回**（内容尺寸），在 ④ 步单独留住 ——
`$measured` 在 ⑤ 步会变成盒尺寸，不能拿来算居中。

★ **为什么不用 Flutter `Align` 的"有界轴撑满"**（这是本次唯一否决的方案）：
Drift 的 `RenderFlex::childConstraints()` 给**非弹性子有界主轴**（`0..$mainMax`），
而 Flutter 给的是 `0..INF`。撑满会在 `Row` 里占满整行、把兄弟挤出去 —— 实测
`AccelApplication` 当场 C6 Fatal（子项共需 264.8，可用 240.0）。
而**"松约束下不居中"不是 bug**：盒就是内容那么大，没有空间可居中（Flutter 在同样
前提下也收缩）。要撑满请让父给 tight —— `Dock` 的 `center` 槽、`Stack(Expand)`、
应用根都是这么做的。

★ 零像素变化的依据：`constrain()` 本来就会把 **tight 的下界**提上来 ⇒ tight 父下盒
早已撑满，本修正对它们无作用。现有 4 处 `Center` 调用点的父全是 tight。

#### ② `Expanded` / `Spacer` 的份额搬进 `mods`，`RenderFlexible` 删除

份额的住处从「`RenderFlexible` 的构造器」改成「`mods.grow`」，
`RenderBox::setMods()` 接上 `setFlexIntent()`：

```php
$this->setFlexIntent($mods->flexGrow(), $mods->flexShrink(), $mods->flexBasis(), $mods->flexAlign());
```

★★ **M2-1 的那条硬约束在 M2-4 语义反转**：M2-1 时 `setMods()` **必须不碰**
`setFlexIntent()`（那时份额还住在 `RenderFlexible` 构造器里，按 mods 默认值再写一次
会清零 ⇒ `Expanded` 全失效、不报错）；M2-4 删掉那个类之后，`mods.grow` 成了份额的
**唯一**来源，`setMods()` **必须**写。smoke 里那条断言因此从
「setMods 不清掉 `RenderFlexible` 的份额」改成「setMods 把 mods 的弹性意图写到盒上」
+ 新增「mods 里没有份额 ⇒ 盒上归零（没有第二个来源可以"留着"）」。

★ `RenderMenuItem` 内部那个 `new RenderFlexible(1)`（chord 前的撑开项）改成
`RenderProxy` + 直接 `setFlexIntent(1, 0, NAN, ALIGN_INHERIT)` —— 它不经 Element，
没有 `setMods()` 这一步。

#### ③ `flex < 1` 的守卫跟着搬家

`RenderFlexible` 构造器里那条 `flex 份额必须 ≥ 1` 搬到 `Expanded::flex()` 与
`Spacer::flex()`。★ 没有放进 `Widget::grow()`：`grow(0)` 对**通用修饰**是合法值
（"这一轴不参与放大"），只有 `Expanded` / `Spacer` 这两个"承诺了要分空间"的控件
才该响亮失败。smoke 的 `--case=flexvalue` 因此从 `new RenderFlexible(0)` 改成
`Expanded::make(...)->flex(0)`。

#### ④ 五个修饰盒只剩一个

| 原类 | 删于 |
|---|---|
| `RenderPadding` / `RenderSizedBox` | M2-3 |
| `RenderCenter` / `RenderFlexible` | **M2-4** |
| `RenderCard` | 待 M2-5（主题派生默认样式要先能并进 `mods`） |

| 档 | 结果 |
|---|---|
| smoke | 1024 → **1025 ok / 0 FAIL**（一条拆两条：份额写入 + 归零） |
| lint | 416 → **414 个文件 / 0 error / 0 warn**（删 2） |
| lint `--selftest` | 18/18 |
| T2 `users` | **99.7s / 8.8 MB** |
| 真机 | `client=983x491`、三帧 `ink=10.6`（与 M2-1/M2-2/M2-3 **逐字一致**）、`closed=1`、无残留 |

### 11.10 M2-5 实况（2026-10-22）—— W5 收口，五个修饰盒全消失

#### ① `Card` 变成"样式预设"，不再是盒

`RenderCard` 删除。`Card` 改 `StatelessWidget`，`build()` 用 `$ctx->theme()` 解析
默认样式（`Pane` / `Border` / 圆角 2），再把「底 / 边 / 圆角 / 阴影 / 内边距」写成
**子控件的 `mods`** —— 与 `Text::make('x')->paddingAll(8)->background($c)` 走同一条路。

三件值得记住的事：

- **盒尺寸仍是"内容 + 内边距"**，内禀尺寸也含它（基类 ②⑤ 步 + `intrinsicWidth/Height`）；
- **内容原点仍是 `(padLeft, padTop)`**，只是换算点从"父盒平移子盒"变成
  `contentOriginX/Y()` —— 所以 IME / 命中测试一行没改（`02` §4.1.1）；
- **裁剪矩形变大了一个内边距**：以前 `RenderCard` 是外层盒、子盒是内容区；现在内边距
  属于子盒自己 ⇒ 子盒的 `Overflow` 按含内边距的矩形裁剪。这与 `Padding` 在 M2-3 的
  收敛是同一条语义，不是新偏差。

★★ **`build()` 里的 `clone $kid` 不能省**：`Card` 的语义是"包一层"，不是"给这个
控件加样式"。`Widget` 可共享（`children([$a, $a])` 合法，§3.3）⇒ 就地 `mutate` 会把
卡片样式漏给另一处引用。`Widget::__clone()` 清封存位，否则克隆出来的写不了
（这条在 M2-1 就加好了，M2-5 第一次真的用上）。

★ **诚实的边界**：`build()` 是"给子控件加样式"，不是真的再包一层 ⇒ 若子控件自己是
`BoxWidget`（`Button` / `PopupPanel`），它的 `background()` 写自己的 `BoxStyle`，
卡片的底/边会**覆盖**它而不是垫在它下面。今天所有调用点传的都是结构节点 / `Text` /
`ScrollView`（走 `mods`）；要真"垫一层"得等 `Stack`（W6 第 34 步）。

#### ② `Card` 不再继承 `BoxWidget`

自持一个 `?BoxStyle $box`，`background()` / `border()` / `radius()` 三个 setter 的
语义逐字不变：**调了任何一个 ⇒ 整套默认让位**（§15.7 纪律 3）。
`BoxStyle` 本身不动 —— `Button` / `PopupPanel` 仍产 `RenderButton` /
`RenderPopupPanel`，仍吃它。

#### ③ 五个节点壳仍在 —— **shim 化不做**（2026-10-23 裁决）

`Padding` / `SizedBox` / `Center` / `Expanded` / `Spacer` 现在都是"壳"：各产一个
`RenderProxy`，几何全在 `mods`。W5 当时把"再往前一步是 shim"留作独立一步、等 API
形状裁决。**裁决结论：不做。** 三条理由都不是成本问题，是"做了会错"：

**① 合并规则三类不一致。** shim 要求 `make()` 直接返回子控件，那 `mods` 只能有一份：

| 字段 | 现在（两层盒各施加一次） | 合并后必须 |
|---|---|---|
| `padding` | `Padding::make(Text::make('x')->paddingAll(4))->all(8)` = **12** | **相加** |
| `width` / `height` | `SizedBox::make($x->width(100))->width(200)` = **200**（外层赢） | **覆盖** |
| `grow` / `center` | 外层赢 | **覆盖** |

没有统一的"合并 mods"规则；今天靠"两层各施加一次"天然正确。

**② `Center::make()` 无参 + 链式 `child()` 决定了必须有 builder。** shim 后 `make()`
返回子控件，`->child()` / `->cursor()` 无处可挂 ⇒ 那是个**不是 `Widget` 的新类型** ⇒
与 `children([...])` 的类型约束冲突（册子 §7.1 自己点出的死结）。

**③ 成熟框架的分界线一致：按「要不要参与 layout」切，不是按「能不能省节点」切。**

| 框架 | `Padding` / `SizedBox` / `Center` | `Expanded` / `Flexible` |
|---|---|---|
| Flutter | `SingleChildRenderObjectWidget` —— **各有自己的 RenderObject**（`RenderPadding` / `RenderConstrainedBox` / `RenderPositionedBox`） | `ParentDataWidget` —— **不产 RenderObject**，只往子的 parentData 写一个值 |
| Compose | `Modifier.padding()` 不产节点（由 `Layout` 节点统一处理） | `Spacer` 是 `Layout` 子类 |
| SwiftUI | `padding()` 是 modifier | `Spacer` 是独立 view |

本质：**只写"父数据"的可以 shim（`Expanded`），要改子约束或改自己尺寸的不行。**

★ 而 Drift 已经比 Flutter 更进一步：W5 之后**没有任何"只为施加修饰而存在的
`RenderBox` 子类"**，几何全在 `RenderBox::layout()` 的 ①②③⑤⑦ + `Modifier` 里。
剩下的 `RenderProxy` 是**实例开销**（一次虚调用 + 一次 constrain），不是逻辑重复。

**替代改进（真正有收益的那一半）**：`ProxyElement::expand()` 原来有 **7 个
`instanceof` 分支**（`Padding` / `Center` / `Expanded` / `ScrollViewBox` /
`PopupPanel` / `ModalHost` / `SizedBox`）—— 每新增一个单子控件都要回来改这一处，
漏了就是"子不挂载、静默空白"（§24.2 #25）。已搬到 `Widget::expandChildren()`
（默认 `[]`，各壳覆写），`ProxyElement::expand()` 变成一行转发。**开放-封闭，
零行为变化。**

| 判据 | 结果 |
|---|---|
| `grep` 五个类名在 `src/` 的非注释命中 | **0** |
| `grep -c "instanceof Card" src/Widget/ProxyElement.php` | **0** |
| 157 处旧写法不改也能过 smoke | ✅（`apps/` 与 `src/` 一行未改） |
| smoke | 1020 → **1025 ok / 0 FAIL** |
| lint | 417 → **413 文件 / 0 error / 0 warn** |
| T2 `showcase` | **120.4s / 8.7 MB** |
| 真机 | `client=1920x1017`，与 W5 之前的 `showcase-w2s4d-home.png` **逐像素 diff=0**（跳过左侧 8 列窗口边框抓取物），首屏 `ink=50.3%` 与历史记录一致 |

★ 为什么这一波的真机判据用 `showcase` 而不是 `users`：`apps/users` **一张 Card 都没有**
（`grep -rc "Card::make" apps/users/src/` 全 0）⇒ 用 users 验 M2-5 等于没验。
★ 那次"左侧 8 列纯黑"是**抓图物**（窗口边框），不是渲染差异：跳过 x<8 后
`diff=0`、`bbox=none`，且 x=8 起的颜色与旧图逐列相同。

### 11.11 方案外独立项：`Modifier::clip` —— `Overflow::Clip` 从"不报错"变成"真的裁"（2026-10-23）

#### ① 缺口：声明与行为不一致

`RenderAppBar` 的构造器注释从 2026-10-19 起就写着：

> `Overflow::Clip`（原 `Report`）：顶条的宽度**随窗口变化** …… 裁剪语义：右侧导航项被裁掉

而 `RenderFlex::handleOverflow()` 的 `Clip` 分支是 `null`（注释"自己夹住"）—— **只夹尺寸，不裁绘制**。
`Overflow::Clip` 在真机上的实际效果是"不弹 Fatal"，内容照样画到盒外。
`grep pushClip src/` 只命中三处（`RenderScrollView` 视口矩形 / `RenderTextField` 盒矩形 / `Canvas`
接口本身），全是**手写**；`Modifier` 里没有这个字段。

⇒ 这不是"少一个功能"，是"契约查询说 `Clip`、行为是 `Report`"—— 与 `RenderFlex::overflow()`
覆写注释里点名的同一类问题（"查询说 Clip、行为是 Report，W4 的判定面整体说谎"）。

#### ② 为什么放在 `RenderBox::paint()`，而不是各容器自己写

`paint()` 已经 `final`，三段各只有一处：装饰（`paintBehind`）→ **裁剪** → 内容（`paintContent`）。
让容器各自在 `paintContent()` 里 `pushClip` 就是 12+ 处抄同一句、漏抄不报错 —— `paint()` 的
docblock 当初否决 `paintDecorated()` 用的正是这条理由。

#### ③ `clipsOverflow()` 的默认值**故意**与 `overflow()` 不一致

| | `overflow()` | `clipsOverflow()` |
|---|---|---|
| 默认 | `Clip`（乐观假设："不会超的容器"） | `false` |
| 语义 | 布局期 C5 策略（放不下：报错还是夹住） | 绘制期"画的时候裁掉" |
| 代价 | 零 | 每帧 `save/pushClip/popClip/restore` |

默认 `false` 有两个作用：① 不裁的盒不付代价；② **新容器忘了覆写 ⇒ 行为与加钩子之前完全一致**
（默认 `true` 会让"忘记覆写"变成静默改变像素）。

| 覆写者 | 判据 | 说明 |
|---|---|---|
| `RenderFlex` | `$this->overflow === Overflow::Clip` | 含 `RenderAppBar`（构造器固定传 Clip） |
| `RenderDock` | `$this->policy === Overflow::Clip` | `apps/users` 根 Dock 声明了它 |
| `RenderTextField` | `true` | 文本比盒宽是常态 |

`RenderScrollView` **不覆写** —— 它的 `paintContent()` 已按视口矩形手写裁剪（内容要平移、滚动条
要画在视口坐标系），再覆写就是双重压栈。

#### ④ `RenderTextField` 的手写裁剪一并收敛

它原来在 `paintContent()` 里 `pushClip($rect)` / `popClip()`，`$rect = (0,0,size)` —— 与基类要压的
矩形**完全相同** ⇒ 删掉手写版、改成覆写 `clipsOverflow(): true`，视觉零变化（1083 条 smoke 一条
没红就是这条等价性的证据）。

#### ⑤ 三条实现纪律

- **装饰在裁剪之外**：阴影按 `-grow` 起画（`paintBehind()` 里 `new Rect(-$grow, …)`），裁了等于把
  影子切掉。夹具用"盒在 (10,10)、影子在 (8,20) 还在、墨在 (35,35) 被裁"**同一帧**验这两件事。
- **装饰有两处，不止 `Modifier`**：自持 `BoxStyle` 的容器（`AppBar` / `TextField`）是在
  `paintContent()` 里画背景/边框的 ⇒ 裁内容会把描边跨在盒边界上的那一半切掉。第一版就踩了：
  真机 `users` 顶条底部那条 1px 灰线（`#ebeef1`）整行消失，diff **983 像素**。修法 = 基类加
  `paintOwnChrome()` 钩子（在 `paintBehind()` 之后、`pushClip()` 之前），两个容器把 chrome 搬进去。
  ★ 这条只能用**命令顺序**验（`drawRect` 的索引 < `pushClip` 的索引）：描边是**内描边**
  （盒宽 10、描边 2 ⇒ 像素 9 有墨、10 没有），靠像素分不出"被裁"与"本来就不画"。
- **走统一出口**：原 `paint()` 的"有 padding"分支中途 `return`。裁剪若跟着分支走，早退分支就漏
  `popClip` ⇒ `DisplayList::assertBalanced()` 会抓（`clipDepth` 归不了零），但真机表现是
  "后面整棵子树全被裁"且不报错。
- **`Modifier::isDefault()` 必须计入 `clip`**：漏了 ⇒ `Element::syncBox()` 的"声明了修饰、但这个控件
  不产盒"守卫失效（§11.7），修饰被静默丢掉。

#### ⑥ 夹具：`BleedBox`（墨比盒大）

`SolidBox` 的墨与盒同尺寸 ⇒ **裁与不裁像素完全相同**，是恒真断言。新夹具
`tools/Smoke/Layout/BleedBox.php`：盒 = `constraints.constrain($ink)`，墨 = `$ink` 原尺寸 ⇒
盒 10×10、墨 40×40，裁不裁在 (20,20) 上分得清。

★ **`performLayout()` 必须自己 `constrain()`**：基类 ⑥ 步对"返回尺寸超出上界"报 C6 Fatal（那意味着
"我要画到盒外面去"）—— 而本夹具要的是**盒不超、墨超**。这两件事必须分开，第一次写成 `return $ink`
就撞了 C6（smoke 静默停在上一行，没有 Fatal 文本）。

10 条断言：装置基准（未裁时溢出）/ `Widget::clip()` 写进 mods / `clip(false)` 可关 / `isDefault()`
计入 / 裁后盒外是背景 / 盒内仍有墨 / Flex 声明 `Clip` 真裁 / `Report` 不裁 / 阴影不被裁 /
同一帧墨被裁 / `clipsOverflow()` 口径。smoke 1083 → **1093**。
