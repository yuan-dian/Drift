## 1. 为什么需要这一册：跨册的七处冲突

各册的迁移节都是在自己册内自洽的。**把它们并排放，就有七处打架。**

| # | 冲突 | 出处 | 本册裁决 |
|---|---|---|---|
| **1** | `settle()` 被两册**分别改签名** | `03` §5.1 写 `final public function settle(): void` + 拆 `settlePass()`；`05` §8 写"返回值从 `void` 变 `bool`" | **合并成一次改造**：`final` + 返回 `bool` + 拆 `settlePass`，归入 W2 |
| **2** | `dispatchPointer` 被两册分别改 | `01` §6.1（浮层栈命中）vs `06` §5（`captureNode`） | **同批**（W3） |
| **3** | `Stack` 被两册**各排了一步** | `02` §7.2 **M2-6**「加 `Stack`」vs `04` §9 **L4-4**「`Stack` 三件」 | **只在 W6 做一次**（按 `04` §4 的形状）；`02` 的 M2-6 划掉 |
| **4** | 自校验在 `04` 自己的序里排第 5，但 `05` 说它是硬前置 | `04` §9 原序 `L4-1→L4-2→L4-3→L4-4→L4-5`（自己已改成 `L4-5` 提前）vs `05` §9「**L3-0 是硬前置**」 | **提前到 W0** |
| **5** | `FramePhase` 断言在 `00` §7 排"第 5 步穿插"，但 `06` §8 说"排最前" | `00` §7 vs `06` §8 | **提前到 W0** |
| **6** | `02` 的 `Expanded`/`Flexible` shim 需要 `RenderBox::grow/shrink`，而那两个字段写在 `04` §2 | `02` §7.1 vs `04` §2.1 | **`04` 的 L4-1 提前到 W0** |
| **7** | 各册的 lint 累计数按 `03→04→05→06→07` 的**写作顺序**算 | `03` §11.3「16 条」/ `05` §12.1「16→18」/ `07` §11.1「15→18」 | 终值一致（**19**，含 W0 新增的 `attribute-unqualified`）；中间值随执行序变，本册 §5 给唯一口径 |

### 1.1 从这七处冲突里提炼的判据（进 MEMORY）

> **同一个方法 / 同一个函数被两册分别改造 ⇒ 必须先合并成一次改造。**
>
> 分两次不是"多一个提交"，而是"第二次要在第一次的废墟上重新推演一遍"。
> 冲突 1 的具体代价：`05` 的 `settle(): bool` 如果先落地，`03` 再把它改 `final`
> 并拆 `settlePass()` 时，`ErrorBoundaryElement` 那一处覆写要**改两次名 + 改一次返回类型**，
> 而中间那次如果忘了 `return parent::settlePass()` 就变成 `bool` 恒 `null`
> ⇒ 跳过 layout 的判据永远为真 ⇒ **动画帧永不重排**（画面冻结在旧布局，不报错）。

> **一个原语只在一个地方定义。** 冲突 3 的代价：两处都写 `Stack` ⇒ 两份 `StackFit`
> 常量值可能不同（一个 `LOOSE=0`，一个 `LOOSE=1`）⇒ 序列化 / 日志 / 断言里对不上。

## 3. 八个波次

### 3.0 为什么是这个串行序

| 相邻对 | 为什么这么排（而不是反） |
|---|---|
| W0 最先 | 它零行为改动。`04` §5 / `06` §2 / `07` §8 各自都把自己册的"断言/量具"排在第一位 —— 四册独立得出同一结论，说明这是结构性的 |
| W1 在 W2 之前 | W1 是"纯增量 + 补 bug"（新增 3 个 op，没人调用），风险最低。且它的真机验收会重跑 `probe-grab` / `pnglook` / `p4-crop` 整条量具链，为后面所有真机验收热身 |
| W2 在 W3 之前 | W2 破坏面**零**（生产 `Cell` 消费者 0）。先清掉零风险的一块，后面每个阶段少一个未知数。且 `01` §7.2 的"锚点消失自动 pop"要在 settle 期读树，多轮 settle 更稳 |
| W3 在 W4 之前 | 两册都改 `Frame::run`（W3 加浮层栈参数、W4 加跳过分支）。相邻做，少开一次同一个文件 |
| W4 在 W5 之前 | 两册都改 `RenderBox`（W4 加 3 个合成字段 + `setCompose`，W5 加 `spec` + 接管 `layout`/`paint`）。同样是为了少开一次 |
| W5 在 W6 之前 | 硬边，见 §2 |
| W6 在 W7 之前 | W7 的 `L5-2/3/4` 改帧预算与挂载表，要在 W0 的阶段断言与 W6 的布局稳定之后收口 |
| W7 在 W8 之前 | W8 是产品功能，本方案不给它排期 |

**第 17 步是本册最需要解释的一步**

`03` §5.1 的示例写的是 `final public function settle(): void`，`05` §8 要求返回 `bool`。
两个需求都成立（多轮收敛要知道"这一遍有没有脏"；跳过 layout 要知道"整帧有没有 rebuild"），
**但一次只能改一次签名**。合并后的形状（**`03` §5.1 已同步改成这一版**）：

```php
// src/Widget/Element.php
/**
 * @return bool 本次 settle **是否重建过任何节点**。`05` §5.4 的"跳过 layout"用它。
 *
 * ★ **必须 final**：唯一覆写点是 `ErrorBoundaryElement`，它的语义是"包住子树的异常"。
 *   如果允许覆写 `settle()` 本身，多轮收敛的第 2 轮就会绕过边界 ⇒ 错误边界从"到节点"
 *   退化成"到整帧"，**且不报错、不崩**。
 */
final public function settle(): bool
{
    $before = State::rebuiltCount();

    for ($round = 1; $round <= self::SETTLE_ROUNDS; $round++) {
        if (State::pendingDirty() === 0) { break; }
        $this->settlePass();
    }

    if ($round > self::SETTLE_ROUNDS) {
        Errors::report('一帧内 rebuild 了 ' . self::SETTLE_ROUNDS . ' 轮仍未收敛…（E-FLUSH-CYCLE）');
    }

    return State::rebuiltCount() > $before;
}

/** 签名一个字不动，只是从 `settle()` 改名 */
protected function settlePass(): void { /* 原 settle() 的单遍后序 */ }
```

```php
// src/Widget/ErrorBoundaryElement.php
protected function settlePass(): void          // ← 只改名，签名不变
{
    try {
        parent::settlePass();
    } catch (\Throwable $e) {
        $this->capture($e);
    }
}
```

★ **为什么 `settlePass()` 保持 `void`、用计数器差值判"有没有 rebuild"**：

| 理由 | 说明 |
|---|---|
| **AOT 风险** | 让 `settlePass()` 返回 `bool` 就必须在 `visitChildren` 的闭包里用 `use (&$rebuilt)` 聚合。**按引用捕获的闭包在 AOT 下没有实测过**；`private static int` 至少是"读一个静态字段"（`08` §4 V-5 已列为待实测项） |
| **覆写面最小** | `ErrorBoundaryElement` 只需改名。若改成返回 `bool`，它还得 `return parent::settlePass()` —— 多一处可漏的地方 |
| **免费** | `rebuild()` 里本来就要 `State::noteRebuilt()`（`03` §5.3），计数器不需要新机制 |

★ **漏改 `ErrorBoundaryElement::settlePass` 的后果是静默的**：`settle()` 已经是 `final`，
所以编译器**不会**报"抽象方法未实现"，也不会报"覆写 final 方法"（因为名字不同）。
它只是变成一个**永远不会被调用的方法**（PHP 对未调用的 `protected` 方法零警告）。

⇒ **W0 第 8 步（`#[\Override]` 批量标注）就是为这一处买的保险**（`10` §2 A1）：
标了 `#[\Override]` 的 `settlePass()` 一旦不再覆写任何东西，**编译期当场报错**。
这条把 W2 从"编译器兜不住的静默失效"降级为"编译错"——**本方案里唯一一处这样的降级**。

**★ S2 与 S3 之间不能插别的**（`03` §8.1）

`Cell` 构造私有化之后，"写值的时机面"变大了（更多人会用 `Cell`），
`settle()` 多轮收敛是它的安全网。中间插别的 ⇒ 有一个窗口期"陷阱已除、安全网未装"。

### 6.1 每波的回滚动作

| W6 | 5 | revert | **低**（五步正交） |
| W7 | 7 | revert | **零**（不动产品代码） |

### 6.2 三条回滚纪律

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **每波一个提交序列，序列内不再夹别的** | 否则 `revert` 要挑着挑（`git revert` 只能整段或单个） |
| 2 | **W5 必须逆序整段 revert** | 只 revert M2-5 ⇒ 5 个类回来但没人实例化（死代码）；只 revert M2-3 ⇒ 基类接管 + 子类也内缩 ⇒ 内距翻倍 |

### 6.3 不可回滚点：**没有**

本方案**没有一处**需要"回滚后还要修数据"：

- 没有持久化格式变更（`apps/users` 的内存 Store，无磁盘）
- 没有协议变更（单进程 GUI，无 IPC 契约）
- 没有配置文件格式变更（`build/m4.on` / `build/layout.check` 都是"文件存在即开"）

★ 这是本方案的一个结构性优点，要写下来：**它让"每个波次独立可回滚"从口号变成事实。**
反例：如果 W2 改了 `UserStore` 的持久化格式，回滚就要写迁移脚本。

### 6.4 半回滚（部分保留）的三个安全点

有时候不想全回滚，只关掉某个新行为。三个现成的开关：

| 开关 | 关掉什么 | 怎么关 |
|---|---|---|
| `build/layout.check` 不存在 | 布局自校验 | 删文件（`LayoutSelfCheck::$on` 默认 `false`） |
| `build/frame.trace` 不存在 | 段顺序断言 | 删文件（`FramePhase` 的 dev 开关） |
| `Frame::run` 的跳过分支 | 跳过 layout | 改一个 `if`（不删代码） |

★ 这三个都是**文件开关**，不读环境变量（`nano-hygiene` 禁 `getenv`）。

## 9. 与 `00` §7 的差异（七条顺序调整的理由）

`00` §7 的原序是：
