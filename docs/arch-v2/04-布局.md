## 0. 一句话

**布局的算法是对的，缺的是三个意图字段、一个原语、一条可证明性。**

| 已有的（不动） | 缺的（本册） |
|---|---|
| 三阶段 flex（问自然尺寸 → 分剩余 → 定位） | **`shrink` / `basis` / `alignSelf`** —— 现在只有 `grow`，内容超了只能报错或裁剪 |
| C1 父定位子（`setOffset`）、C3 内禀两轴、C4 无界量自然尺寸、C5 溢出必选、C6 超上界即报 | **`Stack`** —— 唯一的布局原语缺口 |
| 单遍布局、每帧全量重排、虚拟列表固定行高 O(1) 窗口 | **"纯函数"的可执行断言** —— `RenderBox::layout()` 的 docblock 写着"同样输入 ⇒ 同样输出"，零断言 |
| `ScrollView` 上界在盒里夹、滚动条自绘 | **锚点保持** —— 内容变短时可见行整体跳走 |
| `Dock` 五槽外壳 | `ensureVisible` —— 键盘导航的前提，现在没有 |

**明确不做**（`00` §5 已判，这里只记落点）：measure/place 两遍拆分（no-op）、
布局缓存层（收益个位数百分比、失效逻辑要造自校验来兜）、`Wrap`/`Grid`（需要两遍布局）。

## 1. 现状：全部实测

### 1.1 已有的六条不变式（先承认，免得改坏）

| # | 不变式 | 证据 |
|---|---|---|
| **C1** | 父定位子（`setOffset`），子不读父 | `RenderFlex::placeChildren()` `:316-334`；`RenderDock` 偏移全由自己算 |
| **C3** | 内禀值必须带另一轴（比例盒要用） | `RenderBox::intrinsicWidth(float $height)` `:128` |
| **C4** | 量自然尺寸那遍给弹性子**无界主轴** | `RenderFlex::performLayout()` `:139` `!$mainBounded ? INF : …` |
| **C5** | 会超的容器**必须显式声明**溢出策略（无默认值） | `RenderFlex::__construct` 的 `$overflow` 无默认值 `:55`；`RenderDock::__construct(Overflow $policy)` 必填 |
| **C6** | 只有超出上界才算违反（下界提升不是） | `RenderBox::layout()` `:91-108` |
| **W4** | 查询（`overflow()`）必须与实际行为一致 | `RenderFlex::overflow()` `:73-76` 覆写 —— 不覆写则"查询说 Clip、行为是 Report" |

★ 这六条是本册的**地基**，一条都不能破。下面所有改动都在它们之内。

### 1.2 只有 `grow`：内容超了只能报错或裁剪

`RenderBox::flex()` 返回 `int`，语义只有"份额"（`RenderBox.php:132-139`）：

```php
/** 主轴弹性份额（`RenderFlex` 读它；§13.1 C4）。0 = 不参与弹性分配 */
public function flex(): int
{
    return 0;
}
```

`RenderFlex` 第二遍的分配公式（`:160-174`）：

```php
$free  = $maxMain - $fixedMain - $gap;      // 剩余空间
$space = max(0.0, $free);                    // ★ 溢出 ⇒ 无空间可分
$share = $space * $flex / $totalFlex;        // 纯比例 grow
```

⇒ 当 `$free < 0`（非弹性子已经把主轴占满）时，弹性子拿 **0**，然后走 C5：

| 容器声明 | 结果 |
|---|---|
| `Overflow::Report`（默认） | **Fatal**：`"放不下：子项共需 X，可用只有 Y"` |
| `Overflow::Clip` | 自己夹到可用主轴，超出部分被裁掉 |

**没有第三条路。** 而真实 UI 里最常见的就是第三条路：**让子项缩一点**。
现在只能靠应用自己算——例如把 `Expanded` 的 `flex` 调小，但 `flex` 是**分剩余**不是**压缩**，
`flex = 0` 就完全不参与 ⇒ 调小没有任何压缩效果。

### 1.3 `Expanded` 是一个代理盒，只为装一个 `int`

调用链：

```
Expanded(Widget)  →  RenderFlexible(RenderProxyBox)  →  flex() 返回 $flexValue
RenderFlex 读 $kid->flex()
```

`RenderFlexible` 全文 50 行，做的事只有两件：存一个 `int`、转发 `layout()`。

| 成本 | 说明 |
|---|---|
| 1 个 `Element`（`ProxyElement`） | 每帧 `settle` 多一个节点 |
| 1 个 `RenderBox` | 每帧 `layout` 多一层（`performLayout` 转发） |
| 1 遍 `measure` | `RenderFlexible::performLayout` 调 `$child->layout($constraints)` 再 `constrain` |
| 1 份 `intrinsic*` | 走 `RenderProxyBox` 的转发 |

★ **关键观察**：`RenderFlex` 读的是 `$kid->flex()` —— **一个 `RenderBox` 上的方法**。
所以把份额搬到 `RenderBox` 的字段上，`RenderFlex` 的 `performLayout` **一行都不用改**。
`RenderFlexible` 是纯粹的载体开销。

### 1.4 没有 `Stack`

```bash
ls src/Widget/ | grep -i "stack\|align\|wrap\|grid"    # 空
```

22 个 `RenderBox` 子类里（21 具体 + 1 抽象）没有一个做"多个子叠在同一区域"。
现有唯一的"叠"是 `Dock`（五槽，各占一块，不重叠）和浮层（`Application` 手算坐标 + `Frame` 里 `translate`）。

⇒ 后果（`02` §5.1 已说，这里记布局侧的理由）：

| 需求 | 现在怎么做 | 代价 |
|---|---|---|
| 角标（badge）叠在图标右上 | 不可能 | — |
| 进度条叠在内容上 | `RenderProgress` 自绘在同一个盒里 | 只能用自绘，不能用任意 Widget |
| 骨架屏叠在真内容上 | 不可能 | — |
| 浮层的"居中"方向（`CENTER`） | `Application::placeModal()` 手算 | 浮层自己的布局逻辑，与树无关（`01` §4） |

### 1.5 "纯函数"是注释，没有断言

`RenderBox::layout()` 的 docblock（`:85`）：

```
* 两阶段之一（§13.1）：约束 → 尺寸，**同时定位子节点**。
*
* 纯函数（§14.1）：同样输入 ⇒ 同样输出。所以它**不参与**脏判定 —— 由调用方
* 决定何时重排（§13.3：Render 层全树重排）。
```

**这句话从来没有被验证过。** 而它一旦为假，症状是"某个盒子显示上一帧的尺寸"——
正是 `LazyColumnState` 那句注释里说的形态：

> 弹性子按"现在剩多少"量，flex 分配就建立在错误分母上（图形比例会随兄弟数量漂移）

现状**没有任何机制**能发现"某个 `performLayout` 读了 `$this->size`（上一帧的值）"。
`LazyColumnState::viewportEstimate()`（`LazyColumnState.php:105-118`）**就是**在读上一帧盒尺寸——
它在 `build()` 里读，所以布局仍"纯"；但这条边界没有守卫，谁在 `performLayout` 里
抄一句 `$this->size?->width` 就破了。

### 1.6 `Overflow::Scroll` / `Wrap` 在容器上是未实现的

`Overflow` 枚举四个值（`Overflow.php`），但 `RenderFlex::handleOverflow()`（`:337-358`）：

```php
Overflow::Clip   => null,
Overflow::Report => LayoutTolerance::$previewing ? null : Errors::report(...),
Overflow::Scroll, Overflow::Wrap => Errors::report('溢出策略 X 尚未实现（M2 只有 Clip / Report）'),
```

`RenderDock` 的注释同样写"`Scroll` / `Wrap` 未实现（M3 只有 Clip / Report）"。

★ 这是**诚实的未实现**（响亮失败，不是静默），不是缺陷。但 `Overflow::Scroll` 的语义
与 `ScrollView` 重叠 —— 记在 §13 的否决里（不做，让 `ScrollView` 一个机制承担）。

## 2. 弹性份额住哪：搬到 `RenderBox` 的四个字段

### 2.1 形状

```php
// src/Layout/RenderBox.php
/**
 * 主轴弹性意图（§13.1 C4 扩展）。
 *
 * ★ 住 `RenderBox` 而不是"一个代理盒"：`RenderFlex` 本来就是读 `$kid->flex()`，
 *   把四个意图放在同一层，代理盒就没有存在理由了（`02` §7 已把 `Expanded` /
 *   `Flexible` 改成 shim）。
 *
 * ★ **NAN = 未设**：`basis` 的"未设"（用自然尺寸）与"设为 0"必须两件事
 *   （同 `02` §3.2 的 `width` 判据）。
 */
private int $grow = 0;        // 0 = 不参与放大
private int $shrink = 0;      // 0 = 不参与压缩
private float $basis = \NAN;  // NAN = 用自然尺寸
private int $alignSelf = self::ALIGN_INHERIT;

public function setFlexIntent(int $grow, int $shrink, float $basis, int $alignSelf): void
public function grow(): int
public function shrink(): int
public function basis(): float
public function alignSelf(): int
```

★ **`flex()` 保留为 `grow()` 的别名**，一个提交周期的兼容层：

```php
/** @deprecated 用 `grow()`；保留到 `apps/showcase` 全量改名之后 */
public function flex(): int
{
    return $this->grow;
}
```

### 2.2 为什么 `RenderFlex::performLayout` 一行都不用改

`RenderFlex` 里所有对弹性子的判断都是 `$kid->flex()`（`:108` `:120` `:156` `:165`）。
`flex()` 改成读 `$this->grow` 之后：

- `$kid->flex() > 0` ⇔ `$kid->grow() > 0` ✅ 行为不变
- `$share = $space * $flex / $totalFlex` ✅ 公式不变
- 第二遍的 `$tight = $this->tightMain($inner, $share)` ✅ 不变

⇒ **`02` §7.1 的 `Expanded` shim 只要把 `flex` 写进 `Modifier::$grow`，`RenderFlex` 完全不动。**
这是"形状优先于补丁"的一个直接兑现：改的是数据的**住处**，不是算法的**写法**。

### 2.3 `grow` / `shrink` / `basis` 的语义（与 CSS Flexbox 对齐，逐条标差异）

| 字段 | 语义 | 与 CSS 的差异 |
|---|---|---|
| `grow` | 有剩余空间时按份额放大 | 同 `flex-grow`（但整数，不是小数） |
| `shrink` | **空间不足时按加权份额压缩** | 同 `flex-shrink`，但**下限是 0**（CSS 的 `min-width: auto` 不做，见 §3.4） |
| `basis` | 分配前的起始主轴尺寸 | 同 `flex-basis`；`NAN` = 用第一遍量出的自然尺寸 |
| `alignSelf` | 覆盖父容器的交叉轴对齐 | 同 `align-self` |

★ **为什么 `grow` 是 `int` 而不是 `float`**：`RenderFlex` 现有公式用整数份额
（`$space * $flex / $totalFlex`），整数除法在 `float` 上做没有问题；
改成 `float` 会引入"0.3 + 0.7 ≠ 1.0"的浮点尾差，让 `totalFlex` 为 0 的判定变脆。
**不动。**

### 2.4 `alignSelf`：四个值 + `INHERIT`

```php
public const ALIGN_INHERIT = 0;   // 跟父容器的 crossAlign
public const ALIGN_START   = 1;
public const ALIGN_CENTER  = 2;
public const ALIGN_END     = 3;
public const ALIGN_STRETCH = 4;
```

★ **用 `int` + `===` 比较链，不用 enum**：`FlexAlign` 已是 enum（`RenderFlex::$crossAlign`），
但 `alignSelf` 要表达"未设"（`INHERIT`），而 enum 没有"未设"这个 case —— 加一个
`Inherit` case 会让 `placeChildren()` 的 `match` 多一条"不该走到"的分支。
`int` 哨兵 0 是唯一"不可能与真值混淆"的写法。

`placeChildren()` 的偏移计算（`:319-325`）改成：

```php
$align = $kid->alignSelf() === RenderBox::ALIGN_INHERIT
    ? $this->crossAlign
    : self::toFlexAlign($kid->alignSelf());
```

### 2.5 为什么不做 `order` / `absolute`

v6 `04` §1 有六个意图字段，我们只抄四个。否决两个：

| 字段 | v6 有 | 我们不做的理由 |
|---|---|---|
| `order` | 有（改绘制与布局顺序） | ① Drift2 的 `children()` 顺序就是语义，应用要排序就在 `build()` 里排（`Each` + LIS 已经给了最小移动）；② `order` 会让"树顺序 ≠ 布局顺序"，破坏 C1 的"父定位子"直觉；③ 一个 `int` 字段换来一类新的失效模式（`key` 与 `order` 冲突时谁赢？） |
| `absolute` | 有（脱离流，按 left/top 定位） | 这正是 **`Stack`** 要解决的事。`absolute` 是"在一个流式容器里开一个绝对定位的口子"，而 `Stack` 是"一个专门的容器"。前者把复杂度塞进每个容器，后者只塞进一个 |

★ 判据（进 `07`）：**能用一个新容器解决的，不要给所有容器加一个字段。**

## 3. `shrink` 的算法（本册最需要推演的地方）

### 3.1 与"第一遍跳过弹性子"直接冲突

`RenderFlex` 现在有一个**刻意的优化**（`:123-135`）：

```php
// ★★ 弹性子**不在第一遍量**（主轴有界时）：它的尺寸要等"份额"定下来才有意义…
//   ⇒ 等于让整棵弹性子树每帧白排一遍 —— showcase / users 的外层
//   `Row[导航, Expanded(ScrollView(页))]` 正是此形态。
//   GUI 上游同款实测：这笔浪费接近整帧布局开销的一半（layout 620→310µs）。
if ($flex > 0 && $mainBounded) {
    $mains[$index] = 0.0;   // 占位：第二遍回填
    continue;
}
```

**`shrink` 需要弹性子的自然尺寸**（压缩的起点是"它本来要多大"）。所以：

| 场景 | 第一遍能跳过弹性子吗 |
|---|---|
| 全部 `shrink = 0`，全部 `basis = NAN`（现状，纯 grow） | ✅ 能（保住 620→310µs） |
| 任一子 `shrink > 0` | ❌ **不能** —— 要知道它本来多宽才能压缩 |
| 任一子 `basis` 有效 | ✅ 能 —— 起始尺寸直接取 `basis`，不用量 |

⇒ 判据写进代码：

```php
$needsNatural = false;
foreach ($this->kids as $kid) {
    if ($kid->shrink() > 0 && \is_nan($kid->basis())) {
        $needsNatural = true;
        break;
    }
}
```

★ **这条判据保住了现有快路径**：不用 `shrink` 的应用（当前 100%）行为与性能**逐字节不变**。
`02` §7.1 的 shim 把 `Expanded` 映射成 `grow=1, shrink=0` ⇒ 仍然走快路径。

### 3.2 压缩公式（加权 + 冻结迭代）

```
输入：overshoot = fixedMain + Σbasis − maxMain（> 0 才需要压缩）
每轮：
  1. 对每个未冻结的弹性子 i：
       scaled_i = shrink_i × basis_i
     若 Σscaled == 0 ⇒ 全部冻结，跳出（没有可压缩的子）
  2. 每个未冻结的子压缩：
       cut_i = overshoot × scaled_i / Σscaled
       new_i = basis_i − cut_i
     若 new_i < 0 ⇒ new_i = 0，标记冻结，把它的 basis_i 从 overshoot 里扣掉（少压一点）
  3. 若本轮没有新冻结 ⇒ 收敛，跳出
上限 3 轮；3 轮后仍有未冻结的子 ⇒ 用当前值（不再压）
```

★ **上限 3 轮**，理由：每轮至少冻结一个子，否则收敛。子数 ≥ 轮数时才可能超过 3 轮，
而"同一行里 4 个以上子同时被压到 0"是布局已经不可用的状态 —— 那时再压也没有意义，
交给 C5 的溢出处理。**3 轮之后不再压，让 `mainSize > maxMain` 走 C5** ⇒ 用户看到
`"放不下：子项共需 X，可用只有 Y"`，而不是"所有子都变成 0 宽"。

★ 3 这个数字与 v6 `04` §2 的"S3 仲裁 ≤3 轮"一致 —— 两处独立得出同一上限，是个好信号。

### 3.3 与 C5 的关系：`shrink` 优先，溢出兜底

| 顺序 | 做什么 | 若失败 |
|---|---|---|
| ① | `grow` 分剩余 | 剩余 < 0 ⇒ 进 ② |
| ② | `shrink` 压缩（≤3 轮） | 压完还超 ⇒ 进 ③ |
| ③ | C5 溢出策略 | `Report` ⇒ Fatal；`Clip` ⇒ 夹住 |

★ **`shrink` 不是"另一种溢出策略"**，它是分配公式的一部分。这个区分很重要：
`Overflow` 表达"装不下时怎么舍弃"，`shrink` 表达"装不下时先试试缩小"。
把 `shrink` 塞进 `Overflow` 枚举会得到一个第五个值 `Overflow::Shrink`，
而它与其他四个不是同一层的东西（前四个决定"画到盒外怎么办"，`shrink` 决定"尺寸算多少"）。

### 3.4 下限是 0，不做 `min-content`

CSS 的 `flex-shrink` 默认不会把元素压到 `min-content` 以下（`min-width: auto`）。
我们不实现这一条，**下限就是 0**。理由：

| 要做 `min-content` 需要什么 | Drift2 有吗 |
|---|---|
| `Text` 的 min-content 宽度（最长不可断词） | ❌ `DeterministicMetricsProvider` 只提供 `advance`（max-content）与 `layout(maxWidth)` |
| 每个被压子的额外一次测量 | 会抵消 §3.1 保住的那 310µs |
| `Image` 的最小尺寸语义 | ❌ 没有 `Image`（`02` §5.2） |

⇒ **诚实的边界**：`shrink > 0` 的子可能被压到 0 宽（内容不可见，但不报错）。
要保底就设 `width`（`Modifier::$width` 会与 `shrink` 的 `tightMain` 取 max）。

★ 这一条要写进 `Flex` / `Expanded` 的 docblock，否则用户会以为它像 CSS 一样有保底。

## 4. `Stack` 原语

### 4.1 为什么它是唯一真缺的

八个原语的判据（`02` §5）是"它要不要自己的 `measure()`"。`Stack` 需要：

- **尺寸** = 所有子的**最大**尺寸（不是和、不是最后一个）
- **定位** = 每个子按 `alignment` + `fit` 算偏移（不是顺序累加）
- **绘制** = 按 `children` 顺序（绘制顺序即层叠）

这三件没有一件能由现有容器表达。`Dock` 最接近，但它是**五槽不重叠**。

★ **命中不在这张表里**（2026-10-22 评审修正）：`RenderBox::hitTest()` 的实现就是
`foreach (array_reverse($children) as $child)` ⇒ **所有容器**的命中都从后往前，
`Stack` 继承基类即得，一行不用写。上一版把"命中从后往前（与 `Flex` 的从前往后相反）"
列为 `Stack` 的特殊性，是**错的** —— `Flex` 的命中同样从后往前。§12.2 #8 那条夹具
仍要留，但它守的是**基类契约**（防止有人改 `hitTest` 的遍历方向），不是 `Stack` 的实现。

### 4.2 形状

```php
// src/Widget/Stack.php
Stack::make()
    ->alignment(StackAlign::TopRight)     // 默认 TopLeft
    ->fit(StackFit::Loose)                 // Loose（默认）/ Expand / PassThrough
    ->children([$background, $badge])
```

```php
// src/Layout/RenderStack.php
final class RenderStack extends RenderBox
{
    protected function performLayout(BoxConstraints $constraints): Size
    {
        // ① 每个子拿"松约束"（或按 fit）
        // ② 记下每个子的尺寸
        // ③ 本盒尺寸 = max(子宽) × max(子高)，再 constrain
        // ④ 每个子按 alignment 算偏移（相对**本盒尺寸**，不是约束上限 ——
        //    与 RenderFlex 的交叉轴居中同一条纪律，见 :194-198）
    }
}
```

| `StackFit` | 给子的约束 | 本盒尺寸 | 用途 |
|---|---|---|---|
| `Loose`（默认） | `0..max` 两轴松 | `constrain(max(子))` | 角标、覆盖层 —— 子按自己大小 |
| `Expand` | 有界轴 `tight(max)`、无界轴 `0..INF` | 有界轴 = `max`，无界轴 = `max(子)` | 背景铺满 —— 子强制拉到容器大小 |
| `PassThrough` | `$constraints` 原样 | `constrain(max(子))` | 罕见；需要"子自己决定容器多大"时 |

★★ **`Expand` 的本盒尺寸不来自子**（2026-10-22 评审修正）：上一版写"`Expand` 给子
`tight(本盒尺寸)`"，而本盒尺寸又是 `max(子)` ⇒ **循环依赖**。上一版用"两遍布局"解，
但两遍布局正是本册 §5.3 与 `02` §5.2 否决 `Wrap` 的理由 —— 同一册里不能一处否决、
一处采用。正确口径：`Expand` 的**有界轴**直接取 `constraints.biggest`（父给了多少就
拉满多少），无界轴退化为 `Loose`（绝不产生 `INF` 尺寸）。这样单遍就够，而且"背景铺满"
的语义才成立 —— 按 `max(子)` 铺的话，父给了 500 而子只要 100 时就只铺 100。

★ **`Loose` 是默认值的理由**：`Stack` 最常见的用法是"主内容 + 一个角标"，
主内容应该按自己大小、角标按自己大小。若默认 `Expand`，主内容会被强制拉满 ——
那是最不常见的用法当默认值。

★ **`③` 的 `max(子宽)` 要在所有子都 layout 完之后才能算**，而 `④` 的偏移又依赖
`③` 的结果 —— 但这是**同一遍里的两个阶段**，不是两遍 layout：量完所有子（每个子
只 layout 一次）→ 求 max → 算偏移。**`Stack` 的每个子在整个过程中只被 layout 一次。**
（上一版写"`Expand` 才需要第二遍 layout"，那是在给循环依赖打补丁，已按上表口径取消。）

**`RenderStack` 必须实现的五个方法**

`RenderBox` 有四个抽象方法、`RenderObject` 有一个，上面的骨架只覆盖了第一个：

| 方法 | `Stack` 的口径 |
|---|---|
| `performLayout()` | 见上面的 ①–④ |
| `contentIntrinsicWidth($height)` | `max(子的 intrinsicWidth($height))` |
| `contentIntrinsicHeight($width)` | `max(子的 intrinsicHeight($width))` |
| `paintContent()` | 按 `children` 顺序 `translate` + `paintComposed` |
| `visitChildren()` | 按 `children` 顺序（= 绘制顺序 = 层叠顺序） |

★ 内禀值是 **`max`** 而不是和 —— 与尺寸同口径（`RenderFlex` 的**主轴**是求和，这里不是）。

**`StackAlign`：九个值，容器级**

```
TopLeft     TopCenter     TopRight
CenterLeft  Center        CenterRight
BottomLeft  BottomCenter  BottomRight
```

默认 `TopLeft`（与"主内容在左上、角标压右上"的常见形态一致）。

★ **不支持"每个子单独对齐"**：`alignSelf`（§2.4）的语义是"覆盖父容器的**交叉轴**对齐"，
而 `Stack` 两轴都自由、没有交叉轴概念 ⇒ 那个字段对 `Stack` 的子**无效**（静默不生效，
不是报错）。要每子对齐就嵌套一层 `Stack`。这是**已知的能力缺口**，记账在这里。

**不做 `Overflow` 参数**（2026-10-22 评审修正）

`09` 上一版要求"`Stack` 的 `Overflow` 必填（C5 同纪律）"。实测两条理由都不成立：

1. **`Overflow::Clip` 今天不真裁**：`src/Rendering/` 里没有任何裁剪 API
   （`grep 'function clip'` 只命中 `DisplayList::clipDepth` 与 `RasterCanvas` 的私有
   row span 辅助），`RenderBox::paint()` 里也没有裁剪 ⇒ `Clip` 的实际效果只是
   "布局期把盒尺寸夹进约束"，**绘制期子照画到盒外**。
2. **`Stack` 的 `Report` 永不触发**：它的 `mainSize = max(子)`，子顺从约束时必然
   ≤ `maxMain`。

⇒ 加一个必填 `Overflow` 会得到一个"两个值都不生效"的参数，比不加更糟 ——
读者看到 `overflow(Overflow::Clip)` 会以为角标被裁掉了，实际没有。

★ 真要裁剪（角标出血、骨架屏圆角），正确落点是 **`Modifier::clip(bool)`**：
裁剪是修饰（字段），不是容器参数 —— 与 W5 的"修饰是字段不是节点"同一条判据。
**未排期**，记为 W8 之后的一项。

### 4.3 不做 `zIndex`

绘制顺序 = `children` 顺序（后画的在上）。要改层叠就改 `children` 顺序。
与 `01` §5 的"绘制顺序即层叠，不引入 z-index"是同一条裁决。

★ 命中测试从后往前是**基类**的行为（`RenderBox::hitTest()` 里 `array_reverse($children)`），
`Stack` 不用自己写。§12.2 #8 那条夹具守的是这个基类契约 —— 写反了就是"角标在右上但点
右上命中背景"，且只在有重叠时才暴露 ⇒ 仍进 §11 失败模式。

### 4.4 不做 `Wrap` / `Grid`

| 原语 | 为什么不做 |
|---|---|
| `Wrap` | 需要**两遍布局**：先量所有子的自然尺寸，再按可用宽分行。而"分几行"决定容器高度，容器高度又可能改变子的宽度（如果子依赖父宽）⇒ 需要 `layout` 迭代。**v6 `04` §2 的 S2/S3 策略就是为这类容器准备的，Drift2 没有那套** |
| `Grid` | 同上，且需要"跨列"的约束传播（`columnSpan` 要回溯） |

⇒ 需要流式换行的场景，用 `Column` 套多个 `Row`（应用自己决定怎么分行，等于把
"分几行"这件事从框架挪到应用）。**这是有意的取舍**：`Wrap` 的正确实现要引入
布局迭代，而迭代的失效模式（不收敛、尺寸抖动）比"应用自己分行"难查得多。

★ 推翻条件：出现"子项数量运行时才知道 + 必须自动换行"的真实需求（例如标签云）。
那时按 v6 `04` §2 的 S3 仲裁实现，且**只给 `Wrap` 一个容器开这个口子**。

## 5. 布局可证明性：把"纯函数"变成断言

### 5.1 现状：一句话声明，零断言

见 §1.5。`RenderBox::layout()` 的 docblock 说"纯函数（§14.1）：同样输入 ⇒ 同样输出"，
而**没有任何机制验证它**。

★ 注意这条声明的重要性：它是 `00` §5 "不做布局缓存"的**唯一前提**。
如果布局不纯（读了上一帧的 `$this->size`），那么"不做缓存"就是错的 ——
因为那时候连"重算"都不保证正确。⇒ **先证明纯，才有资格说不缓存。**

### 5.2 自校验：同约束连排两次，逐字节比

```php
// src/Layout/LayoutSelfCheck.php
final class LayoutSelfCheck
{
    /** @var bool dev 开关（`build/layout.check` 文件存在时为 true，同 `SurfaceProfile::$on`） */
    public static bool $on = false;

    /** 每 16 帧抽一帧 */
    private const SAMPLE_EVERY = 16;

    public static int $checks = 0;
    public static int $mismatches = 0;
    /** @var list<string> 最近 8 条不一致的描述（类名 + 哪个字段） */
    public static array $recent = [];

    public static function maybeCheck(RenderBox $root, BoxConstraints $constraints, int $frameSerial): void
    {
        if (!self::$on || $frameSerial % self::SAMPLE_EVERY !== 0) {
            return;
        }

        $snapshot = self::snapshot($root);      // [类名, size, offset, 每个子的…]
        $root->layout($constraints);            // ★ 用同一约束再排一次
        $again = self::snapshot($root);

        self::$checks++;
        if ($snapshot !== $again) {
            self::$mismatches++;
            // 记第一条差异：类名 + 字段 + 两个值
            Errors::report(sprintf(
                '布局不是纯函数：%s 用同一约束排两次，结果不同（%s）。'
                    . "\n" . '修法：在 performLayout() 里读的必须是约束与子树，不能读 $this->size 等上一帧留下的值。',
                $diff['class'],
                $diff['field'],
            ), Errors::DIAGNOSTIC);
        }
    }
}
```

`snapshot()` 是**扁平化**的：深度优先遍历，每个盒取 `[class, size.w, size.h, offsetX, offsetY]`，
拼成一个 `list<string>`。逐字节比 —— 不做容差。

★ **为什么不做容差**：浮点误差在纯函数里也应该是确定的（同样输入 ⇒ 同样的浮点运算顺序 ⇒
同样的结果）。加容差就等于允许"轻微不纯"，而"轻微不纯"在布局里就是"偏移差 0.5px"，
那正是要抓的东西。

### 5.3 为什么不做布局缓存

`00` §5 已判（引用 `EVAL-design-v7-2026-10-21.md` §7.1）。这里补三条**本册视角**的理由：

| # | 理由 |
|---|---|
| ① | `layout()` 位置无关（父给约束、子返回尺寸、父 `setOffset`）⇒ measure/place 拆分是 no-op；要做缓存必须有"尺寸缓存"，而尺寸依赖约束 + 子树 + 主题 + 字体缩放，失效键的组合数远大于收益 |
| ② | 虚拟化已经用**另一条路**达成同一目标：10000 行 96ms → 0.2ms（只造可见行）。这比"缓存布局结果"彻底得多 |
| ③ | 缓存错了的**检测成本**高于缓存本身 —— §5.2 的自校验就是为了兜"缓存失效漏了"，而我们连缓存都没有，就不需要兜 |

★ **判据（进 `08` §10）**：只有当"单帧 layout 稳定 > 4ms"时才考虑缓存。
现在的量级：M4 真机端到端 3.1ms（含 settle/layout/paint/present）⇒ **远未到**。

### 5.4 计数器与开关

| 项 | 值 |
|---|---|
| 开关 | `build/layout.check` 文件存在（与 `build/m4.on` 同一种"文件开关"，不读环境变量 —— `nano-hygiene` 禁 `getenv`） |
| 采样 | 每 16 帧一次（v6 `04` §3.2 同频率） |
| 计数器 | `LayoutSelfCheck::$checks` / `$mismatches` / `$recent` |
| **报告文件** | `build/layout.check.out`（与开关同目录同前缀，`getcwd()` 相对）—— 内容 `frames` / `checks` / `mismatches` + 最近 8 条差异 |
| 出口 | smoke 夹具跑 64 帧后断言 `$mismatches === 0`；真机读报告文件（`php tools/probe-frame-gates.php`） |
| 生产 | 默认关（`$on = false`），**dev 与 CI 开** |

★ 采样 1/16 的代价：一次全量重排 ≈ 0.3–0.8ms（2200 行的树），摊到 16 帧 ≈ 0.05ms/帧。
可接受。若将来树大到重排 > 4ms，改成 1/64。

★★ **为什么必须有报告文件**（W0 落地时补的，原方案漏了）：`Errors::report(DIAGNOSTIC)`
只进**进程内**环形缓冲，而真机上 `users.exe` 是独立进程 ⇒ 外面一条都读不到 ⇒
"`mismatches === 0`"**无法验证，只能选择相信**。那是 G2「绝不静默」的反面：
断言输出了，但没有人看得见。⇒ 开着时每帧把计数器刷进 `build/layout.check.out`。

★ **报告每帧刷，不只采样帧刷**：`frames` 要表达"当前跑到第几帧"。只在采样帧刷
会让它比真实帧数少 0–15，真机上看着像"丢帧"（实测 `143 vs 128`，128 = 8×16）。
★ 开关与报告同在 `build/` ⇒ `is_file()` 能找到开关时目录一定存在，写不会因目录
缺失而静默失败。
★ `boot()` 一翻开开关就落一份 `checks 0` ⇒ "没有文件"与"跑过且干净"分得开。

### 5.5 已知的"不纯"：`build` 期读上一帧

`LazyColumnState::viewportEstimate()`（`:100`）读上一帧盒尺寸：

```php
$box = $this->element()?->effectiveBox();
if ($box instanceof RenderScrollView) {
    $size = $box->size();
    if ($size !== null && $size->height > 0.0) {
        return $size->height;
    }
}
return max(0.0, $ctx->height);   // 首帧兜底
```

★ **它不违反布局纯函数**（在 `build` 期，不在 `performLayout` 里），但它是
"帧与帧之间的状态依赖" —— 同类隐患的另一半。本册**不动它**，理由：

| 为什么保留 | 说明 |
|---|---|
| 布局结果在 `build` 期拿不到 | `build → settle → layout` 的顺序决定了这一点（`LazyColumnState` 类注释已写明） |
| 首帧的兜底是上界 | `ctx->height` 是任何嵌套视口的上界 ⇒ 首帧一定造多不少，**不会白** |
| 代价只是一次多余的 `buildItem` | 首帧可能多造十几行，第二帧就修正 |

★ 但要加一条**断言**：`viewportEstimate()` 返回的值必须 ≥ 0 且 ≤ `ctx->height × 2`
（超过 2 倍窗口高说明上一帧的盒尺寸是错的，例如窗口刚从小变大）。超出 ⇒ `Errors::report`
DIAGNOSTIC。这比"什么都不查"好，比"改成两遍布局"便宜。

## 6. 滚动

### 6.1 现状：偏移是构造参数，上界在盒里夹

坐标链（`RenderScrollView.php:18-24`）：**滚动偏移进子盒的 `offsetX/offsetY`**，
不是 `paint` 期 `translate`。理由同 `RenderFlex::placeChildren()` 的 padding ——
`hitTest()` 与 `absoluteOrigin()` 必须看到与绘制一致的坐标。

夹取分两处，**职责分明**：

| 谁 | 夹什么 | 为什么在这 |
|---|---|---|
| `ScrollViewState::scrollBy()` | **下界 0** | 只有一处写入口 ⇒ 不会出现"两处各自夹、边界不一致" |
| `RenderScrollView::appliedOffset()` | **上界 `maxScroll`** | 只有布局后才知道内容多长 |

★ `appliedOffset()` 是"读时夹"而不是"写时夹" ⇒ 内容变短时**下一帧自动回弹**，
不需要谁记得复位。这是对的形状，别改。

### 6.2 嵌套滚动：保持"只滚最近的"，不做 delta 传递

`Application::dispatchInput()` 的 `ScrollEvent` 分支（`:1552-1562`）注释：

> ★ **命中一次、就滚那一个**：指针停在哪个视口里就滚哪个 —— 多个滚动容器各自滚动，
>   外层的视口不吞内层的事件（scrollAt 只找最近的）。

v6 `04` §5.3 的做法相反：内层滚到头之后，**剩余 delta 传给外层**。

**裁决：保持现状（不传递）**，理由三条：

| # | 理由 |
|---|---|
| ① | 可预测：滚轮只影响指针下的那个视口，不会"滚到底之后页面突然开始动" |
| ② | 实现简单：`scrollAt()` 找到最近的一个就返回，不需要"内层返回消费了多少"的协议 |
| ③ | 当前零需求：生产代码里没有 `ScrollView` 套 `ScrollView` 的场景（`apps/users` 的 `ScrollView` 里是 `Column`，`LazyColumn` 里是行） |

★ **推翻条件**：出现真实的嵌套滚动需求（例如页面级 `ScrollView` 里放一个横向 `ScrollView`
的表格）。那时加的是"内层返回消费量"的协议，不是"框架猜"。

### 6.3 `ensureVisible`：键盘导航的前提（W6 L4-6 已落地，见 §14.4）

落地前：`grep -rn "ensureVisible" src/` 是 **0**。

后果：Tab 键把焦点移到一个**滚出视口**的控件上时，焦点环画在视口外 ⇒ 用户看不到焦点在哪。

这是无障碍的硬要求（v6 `15` §5「键盘可达性硬要求」），也是 `07-可检查性.md` 的
`TestApp` 做键盘导航测试的前提。

**形状**：

```php
// src/Widget/Scrollable.php
interface Scrollable
{
    public function scrollBy(float $delta): void;

    /** 把**内容坐标**里的矩形滚进视口，四周留 `$margin` 边距 */
    public function ensureVisible(Rect $target, float $margin = 8.0): void;
}
```

★ **算术不写在 State 里**（原方案写在 `ScrollViewState`，落地时改了）：两个实现
（`ScrollViewState` / `LazyColumnState`）要算的是**同一件事**，各写一遍必然漂 ——
一处按视口高、一处按窗口高，而两边都不会报错。所以几何只有一处：

```php
// src/Layout/RenderScrollView.php —— 只有它知道视口多长、往哪个轴滚
public function revealDelta(Rect $target, float $margin, float $base): float
{
    $viewport = $vertical ? $size->height : $size->width;   // 横向看宽
    $offset   = $base;
    $start    = $vertical ? $target->top    : $target->left;
    $extent   = $vertical ? $target->height : $target->width;

    if ($extent + $margin * 2.0 > $viewport) {          // 目标比视口高 ⇒ 对齐上沿
        return $start - $margin - $offset;              //   且这条是幂等的
    }
    if ($start - $margin < $offset) {
        return $start - $margin - $offset;              // 在上方 ⇒ 负增量
    }
    if ($start + $extent + $margin > $offset + $viewport) {
        return $start + $extent + $margin - $offset - $viewport;   // 在下方
    }

    return 0.0;                                         // 已可见 ⇒ 不动（不标脏）
}
```

State 侧只剩"找自己的盒 → 转交"（两个实现**逐字同构**）：

```php
$box = $this->element()?->effectiveBox();
if (!$box instanceof RenderScrollView) { return; }      // 还没挂盒 ⇒ 不动
$delta = $box->revealDelta($target, $margin, $this->offset);
if ($delta !== 0.0) { $this->scrollBy($delta); }
```

★ `revealDelta()` 的两个浮点参数**都必填**：`$margin = 8.0` 有默认而 `$base` 没有
⇒ tpc 直接 Fatal（optional parameter before required，2026-10-17 踩过）。
⇒ `margin` 的默认值只留在 `ensureVisible()` 一处。

三条落地判据（原方案没写，写代码时才发现不这么写就错）：

| # | 判据 | 不这么写会怎样 |
|---|---|---|
| ① | `$base` 传 **State 自己待生效的偏移**，不传盒的 `appliedOffset()` | 同一帧连按两次 Tab（输入泵一次取多条消息）时盒还没按新偏移重排 ⇒ 第二段增量按旧基准再算一遍（8 之后再要 48 会滚到 56） |
| ② | 目标比视口高 ⇒ **上沿对齐** | 上下两个条件不可能同时满足 ⇒ 连着调两次会在两端来回跳（每次翻一次方向） |
| ③ | 找盒失败 ⇒ **什么都不做** | 猜一个默认视口高 ⇒ 滚到错的位置，比不滚更坏 |

★ **边距 8px**（v6 `04` §5.4 同值）：0 边距会让目标贴边，视觉上像"被切掉"。

**调用点**：`Application::dispatchInput()` 的键盘分支 —— `dispatchKey()` 返回 true
**且焦点 Element 变了** ⇒ `revealFocused()`。判据是"焦点变了"而不是"按的是 Tab"：
输入框吃掉 Tab 时焦点没动，那时滚一下就是用户没要求的位移。

★ `revealFocused()` 把焦点盒的**绝对原点之差**换算成内容坐标、再加回 `appliedOffset()`
—— **不自己沿父链累加偏移**。`absoluteOrigin()` 已经含滚动量（偏移住子盒的
`offsetX/Y`），手抄累加是 M2-3 那一族"算两次"的 bug。

★ 原稿写的"调用点：`activateFocusedWidget()` 之后 —— 见 `06` §5"**两处都错**：
`activateFocusedWidget()` 是 Enter/Space 激活（指针按下也走它），与焦点移动无关；
`06` §5 是**指针捕获**，不是输入通道。

### 6.4 惯性滚动：本册不做

v6 `04` §5.2 的惯性是**物理积分**：

```
offset += v · dt
v *= exp(-k · dt)
v < 5px/s 停
新按下 v = 0（不改 offset）
```

Drift2 现在**没有触摸输入**（只有滚轮 + 键盘），所以惯性没有消费者。
`ScrollViewState::scrollBy()` 是纯位移，`WHEEL_NOTCH_PX` 把"格"换成像素。

⇒ **不做**。推翻条件：触摸/触控板手势输入落地时（那是 `06` §5 的输入通道扩展），
惯性按上式的三步实现，常数 `k` 与停止阈值**先用 v6 的值**（`k = 8.0 /s`、`5px/s`），
真机测完再调。

### 6.5 滚动条

`RenderScrollView::paint()` 自绘 6px 胶囊（`BAR_THICKNESS = 6.0` / `BAR_MARGIN = 3.0` /
`BAR_MIN_THUMB = 24.0`），`maxScroll == 0` 不画。**纯视觉层**：不新增状态、不改夹取、
不碰命中。本册不动。

★ 唯一要说的一点：它用的是 `drawRect` + 圆角（Core/Extended op），所以
`RasterCanvas` 能画 ⇒ preview/golden 里有滚动条。若哪天改成路径描边，
`05` §4 的能力等价断言会当场抓住。

## 7. 虚拟列表：一万行滚动为什么跳

### 7.1 现状：固定行高 ⇒ O(1) 窗口（这是优点，别改）

`LazyColumnState::build()`（`:60` `:67-68`）：

```php
$total    = $insets->top + $count * $extent + $insets->bottom;
$viewport = $this->viewportEstimate($ctx);
$offset   = min(max(0.0, $this->offset), max(0.0, $total - $viewport));

$first = (int) floor(max(0.0, $offset - $overscan - $insets->top) / $extent);
$last  = (int) ceil (max(0.0, $offset + $viewport + $overscan - $insets->top) / $extent);
```

**窗口是除法算出来的，不是累加出来的** ⇒ O(1)。这是 10000 行 96ms → 0.2ms 的全部原因。

★ **不做 Fenwick 树**（v6 `04` §6.2 用的前缀和）：Fenwick 解决的是"**行高不固定**时
如何 O(log n) 求前缀和"。而 `LazyColumn` 的 `itemExtent` 是**必填参数**
（`$view->itemExtent()`），行高固定 ⇒ 前缀和 = `index × extent`，一次乘法。
**引入 Fenwick 等于给一个不需要的数据结构付 O(n) 的构建成本。**

⇒ 判据（进 `08` §10）：**只有当 `LazyColumn` 支持变高行时，才需要 Fenwick。**
而支持变高行需要"不建节点就知道高度"（v6 `04` §6.1 的三个前提之一），
Drift2 没有这个能力（`buildItem` 必须真造 Widget 才知道多高）⇒ **两层都不到，不做。**

### 7.2 跳的真原因：无锚点保持

**"一万行滚动跳"不是滚动本身跳，是内容变了之后跳。** 三种触发：

| 触发 | 现在发生什么 |
|---|---|
| 搜索框输入 ⇒ `rows` 变少 | `total` 变小 ⇒ `offset` 被 `min(...)` 夹小 ⇒ **可见行整体换了一批** |
| 删除一行 | 同上，且被删的行在视口上方时，视口内容整体上移一格 |
| 数据刷新（`applyPage`）⇒ 行内容全换 | 行号不变但内容变了 ⇒ 不跳（key = 绝对行号，`LazyColumnState.php:74-79` 已正确） |

第一种最刺眼：用户滚到第 500 行，一输入搜索词，列表跳回顶部附近。

★ 注意 `offset` 的夹取是**正确的**（不夹会让窗口算到列表外，造出空白，
`LazyColumnState` 类注释已写明）。问题不是夹错了，是**夹的依据错了**：
夹的时候假设"用户关心的是 offset 这个数字"，而用户关心的是"我正在看的那些行"。

### 7.3 锚点保持的形状

```php
final class LazyColumnState extends State implements Scrollable
{
    private float $offset = 0.0;

    /** ★ 锚点：视口顶部那一行的**绝对行号**，以及滚过了它多少（0..1） */
    private int $anchorIndex = 0;
    private float $anchorFrac = 0.0;

    public function scrollBy(float $delta): void
    {
        // …（不变）
        $this->rememberAnchor();   // ★ 每次真的滚了就更新锚点
    }

    /** @internal `didUpdateWidget` 时调：内容变了 ⇒ 从锚点反算 offset */
    private function restoreAnchor(float $extent, int $count): void
    {
        if ($count === 0) {
            $this->offset = 0.0;
            return;
        }

        // 锚点行还在（行号没超界）⇒ 回到它；否则夹到最后一个可完整显示的行
        $index = min($this->anchorIndex, max(0, $count - 1));
        $this->offset = $index * $extent + $this->anchorFrac * $extent;
    }

    private function rememberAnchor(float $extent = 0.0): void
    {
        // offset = anchorIndex × extent + frac × extent
        $index = (int) floor($this->offset / $extent);
        $this->anchorIndex = $index;
        $this->anchorFrac = ($this->offset - $index * $extent) / $extent;
    }
}
```

★ **固定行高让锚点保持变成 O(1)**（一次除法 + 一次乘法）。这是 §7.1 的"不做 Fenwick"
换来的第二个好处：v6 需要 Fenwick 才能做锚点保持（它要"第 k 行的 y 坐标"），
我们一次乘法就有。

★ 但**行号变了怎么办**？搜索把 10000 行筛成 30 行时，锚点行 500 不存在了。
`restoreAnchor()` 的 `min($this->anchorIndex, $count - 1)` 会夹到第 29 行 ⇒
**跳到列表末尾**，这比跳回顶部更糟。

⇒ 正确的做法要**按内容身份**保持，不是按行号：

```php
/** 锚点行的 key（`LazyColumn::keyOf()`）；null ⇒ 按行号夹 */
private ?string $anchorKey = null;
```

`restoreAnchor()` 先在 `items` 里找 `anchorKey` 的位置（`O(n)` 一次，只在内容变时跑）；
找不到 ⇒ 退回 `offset = 0`（顶部）。

★ **`O(n)` 一次是可接受的**：它只在 `didUpdateWidget`（内容变）时跑，不在滚动时跑。
10000 行的线性扫描 ≈ 0.1ms，而内容变本身就是一次全量数据替换。

### 7.4 `LazyColumn` 需要 `keyOf`

现在 `LazyColumn` 的 key 是绝对行号（`$rows[] = … ->key($i)`）。要按身份保持锚点，
需要 `LazyColumn::make(...)->keyOf(fn($item): string|int)` —— 与 `Each` 的 `key` 参数同形。

| 现状 | 之后 |
|---|---|
| `LazyColumn::make(items, itemExtent, buildItem)` | 加**可选** `keyOf`；不给 ⇒ 用绝对行号（行为与现在逐字节一致） |

★ 不给 `keyOf` 时锚点保持退化为"按行号夹" —— 搜索场景仍会跳。这是**诚实的边界**：
框架不能凭空知道"两批数据里哪一行是同一行"。

## 14. 落地实况（W6）

> 与 §3 / §12 的偏差、只在实现时才暴露的坑、以及册子数字对不上的地方。
> 口径：**代码为真相**，本节记"为什么与上面不同"。

### 14.1 L4-2 `shrink`（第 32 步）

#### 偏离 1：`basis` 有效时**不一定**能跳过第一遍

§3.1 的表格第三行写"任一子 `basis` 有效 ⇒ ✅ 能跳过"。实现里的判据更窄：

| 情况 | 第一遍跳过弹性子？ | 为什么 |
|---|---|---|
| 有子 `shrink > 0` 且 `basis` 未设 | ❌ 不跳 | 压缩起点 = 自然尺寸，不量就不知道 |
| 所有要压缩的子都有 `basis` | ✅ 跳 | 起点直接取 `basis` |
| 纯 `grow` 子（`shrink = 0`、`basis` 未设） | ✅ 跳 | 起点是 0，与老公式等价 |

```php
$skipFlex = $mainBounded && !$needsNatural;   // $needsNatural = 有 shrink 子没声明 basis
```

★ 与表格**实质一致**，但表格容易被读成"只要有 `basis` 就跳"—— 混合场景
（部分子有 `basis`、部分子要压缩）跳不过，因为要压缩的那些还是得量。

#### 偏离 2（§3.1 没写、但决定 `shrink` 能不能用）：`$needsNatural` 时弹性子必须拿**无界主轴**

§3.1 只说了"不能跳过"。不跳之后给什么约束？给 `0..$maxMain` 的话：
**内容比容器长的弹性子第一遍就撞 C5**（`Flex` 的 `Overflow` 默认 `Report`），
而"内容比容器长"正是要用 `shrink` 的场景 ⇒ **`shrink` 永远用不上**。

⇒ 第一遍必须给 `INF` —— 这正是 C4 契约的原文（"量自然尺寸那遍给弹性子无界主轴"），
只是在此之前它没有可观察的后果：

```php
$elasticNatural = $needsNatural && ($flex > 0 || $kid->shrink() > 0);
$childMainMax = ($mainBounded && !$elasticNatural) ? max(0.0, $maxMain) : INF;
```

★ **`$flex > 0` 单看不够**：`flex()` 只是 `grow()` 的别名，而"要压缩的弹性子"恰恰是
`grow = 0, shrink > 0` 的那种。第一版漏了 `|| $kid->shrink() > 0`，夹具当场抓到
（`第一遍 maxWidth=100.0`，应为无界）。这条**不是**真机暴露的，是夹具拦下的。

#### 推翻 §3.4：「要保底就设 `width`」不成立

§3.4 原文：`shrink > 0` 的子可能被压到 0 宽；要保底就设 `width`（`Modifier::$width`
会与 `shrink` 的 `tightMain` 取 max）。

实测不成立：`Modifier::tighten()` 是把 `width` **夹进**父给的区间
（`if ($w > $maxW) { $w = $maxW; }`），而被压到 0 的子拿到的是 `BoxConstraints(0, 0, …)`
⇒ `width(60)` 一起被夹成 0。`shrinkoverflow` 夹具的初版就是这么写的，压到 0 之后**零保底**。

⇒ **今天 `shrink` 压到 0 就是 0，没有保底手段。** 真要有下限得等 `min-content`
（§3.4 已否决，理由不变）。§13 的推翻条件（"出现压到 0 导致不可用的真实投诉"）
因此更容易被触发 —— 这是**已知代价**，不是遗漏。这条写进了 `Widget::shrink()`
与 `RenderFlex::allocateAdvanced()` 的 docblock。

#### 推翻 §12.2 #3 / #4 的夹具数字

| # | 册子写的 | 按 §3.2 的公式实际算出 |
|---|---|---|
| 3 | 一个子 `basis` 200 `shrink` 1，容器 100 ⇒ 该子 **0**，容器报 C5 | 压到 **100** 就正好装满（`cut = overshoot = 100`），不冻结、不报 C5 |
| 4 | A `shrink` 1 `basis` 10、B `shrink` 10 `basis` 200，容器 100 ⇒ A 先到 0 | A 分到 `110 × 10/2010 ≈ 0.55` ⇒ 收敛在 **9.45 / 90.55**，没有冻结 |

两条都差在"加权份额"这一层：`scaled = shrink × basis`，A 的份额要**够大**才会被压到 0。
落地夹具按真实能触发的数字写：

- #4 改成 A `shrink` 100 `basis` 10 ⇒ 第 1 轮 A 冻结到 0、B 到 126.67；第 2 轮 B 到 100。
- #3 改成"间距 20×2 + 两个固定 40 的子"（`shrink` 压不动间距与固定子），
  弹性子压到 0 后总量仍 120 > 100 ⇒ 真的报 C5。

★ **#3 顺带证明了一件事**：`shrink` 路径下 C5 几乎不可达 —— 压缩公式总会把总量压到
`maxMain`，除非**压不动的东西**（间距 / 固定子）自己就超了。册子写成"压到 0 就报 C5"
会让读者以为 C5 是这条路径的常态。

#### §3.2 的"把 `basis` 从 `overshoot` 里扣掉"改成每轮重算总账

原文："若 `new_i < 0` ⇒ `new_i = 0`，标记冻结，把它的 `basis_i` 从 `overshoot` 里扣掉
（少压一点）"。

实现里**不维护 overshoot 修正量**，每轮从当前 `$sizes` 重算 `total` 与 `overshoot`。
冻结子的 `shrink × size` 已经自然归 0，重算比维护修正量少一处状态
（少一处状态 = 少一处"某一轮忘扣"的静默错）。两者数学等价。

#### 与 §12.1 / §12.2 的数字

| 指标 | 册子"之后" | 实况 |
|---|---|---|
| 纯 `grow` 场景的 layout 遍数 | 1 | **1**（`$needsNatural` 为假 ⇒ 老路径；`C4 弹性子只在份额定下后量一次` 仍绿） |
| `RenderBox` 具体子类 | 18 | 18（本步不加不减） |
| smoke | 977 → 990 | 1025 → **1033**（+8） |

★ 新增的 8 条夹具：无界主轴 1 / 量两次 1 / 加权压缩 1 / 冻结迭代 1 / `basis` 优先 1 /
`basis`+`grow` 增量 1 / C5 退出码 1 / C5 消息 1。

（`$elasticSpy->firstSeen === $elasticSpy->lastSeen`）。

#### 两条路径为什么不会漂移

| 判据 | 走哪条 | 公式 |
|---|---|---|
| 没有子声明 `shrink` / `basis`（今天 100% 的用法） | 老路径（原代码一字未改） | 份额 = `剩余 × grow / Σgrow`，**从 0 起算** |
| 有子声明了（`$advanced`） | `allocateAdvanced()` | `start + 剩余 × grow / Σgrow`，**起点之上加增量** |

纯 `grow` 子的起点是 0 ⇒ 两条公式逐字节等价。所以同一容器里混用不会漂移，
老路径也不必为了"统一"而改 —— 它是 620→310µs 那条快路径的载体。

### 14.2 L4-3 `alignSelf`（第 33 步）

#### 册子只说了 `placeChildren`，实现必须改三处

§2.4 给的只有 `placeChildren()` 的偏移计算。但 `ALIGN_STRETCH` 要**真的拉满交叉轴**，
而尺寸是在另外两处定下来的：

| 处 | 改什么 | 不改的后果 |
|---|---|---|
| `childConstraints()` | `Stretch` ⇒ 交叉轴紧约束 | 非弹性子不拉满 |
| `tightMain()` | `Stretch` ⇒ 交叉轴紧约束 | **弹性子**不拉满（同一行里高度参差） |
| `placeChildren()` | 偏移按解析后的 `align` 算 | 偏移不对 |

只在 `placeChildren()` 里解析的话，`ALIGN_STRETCH` 会变成"偏移算成 0、尺寸没变" ——
一个**看起来实现了、实际没生效**的分支（G2）。夹具专门守这一条：
`alignSelf(STRETCH) 真的拉满交叉轴（子高 10 ⇒ 40，不是只改偏移）`。

#### `resolveAlign()` 是三处的唯一入口

```php
private function resolveAlign(RenderBox $kid): FlexAlign
{
    $self = $kid->alignSelf();
    if ($self === RenderBox::ALIGN_INHERIT) {
        return $this->crossAlign;
    }

    return match ($self) {
        RenderBox::ALIGN_CENTER  => FlexAlign::Center,
        RenderBox::ALIGN_END     => FlexAlign::End,
        RenderBox::ALIGN_STRETCH => FlexAlign::Stretch,
        default                  => FlexAlign::Start,
    };
}
```

★ `tightMain()` 因此多了一个 `RenderBox $kid` 形参（两个调用点：老路径与新公式）。
默认 `ALIGN_INHERIT` ⇒ 返回值恒等于 `$this->crossAlign` ⇒ **零行为变化**。

#### `default` 不是"兜底"而是"非法值退化为 `Start`"

`alignSelf` 是 `int` 哨兵（§2.4），非法值可以从 `setFlexIntent()` 直接写进来
（绕过 `Widget::alignSelf()`）。`match` 的 `default` 让它退化为 `Start`，与"未设"同义 ——
比抛异常合理，因为这里是**布局期**，抛异常等于整个界面不画。

#### 夹具（4 条）

| 夹具 | 守什么 |
|---|---|
| `alignSelf(END)` 覆盖父的 `Center` | 覆盖生效（30 而非 15） |
| `alignSelf(CENTER)` 在 `Start` 容器里 | 覆盖是双向的（不只是"更靠后"） |
| `alignSelf(STRETCH)` 子高 10 ⇒ 40 | **尺寸**真的拉满（防"只改偏移"） |
| 未设 ⇒ 跟容器 | `INHERIT` 不改变现有行为 |
