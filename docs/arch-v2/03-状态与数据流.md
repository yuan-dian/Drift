## 0. 一句话

**状态层不缺机制，缺消费者。**

`src/State/` 417 行、5 个文件、5 条专用 lint —— 而 `Cell` 在**生产代码里的消费者是 0**
（唯一用到它的是 `tools/Smoke/State/HoverWidget.php` 这个测试夹具）。
`UserStore` 每个写点要手工做三件事（改字段 / 清派生缓存 / 通知），四个写点四份样板。
`Element::settle()` 单遍后序，脏的传播方向与遍历方向相反 ⇒ 结构上收不住。

三处改动，**加起来比 `02` 小一个数量级**：

| 落点 | 改什么 | 为什么值得 |
|---|---|---|
| **`Cell` 去掉那个陷阱** | `__construct` 转 `private`；`?State` → `State` + `bool` | 最自然的写法现在是**运行期 Fatal**，正确写法要多一行且读点带 `?` ⇒ 用户选 `setState` |
| **`Computed` 把派生值变成机制** | 新 `Drift\Core\Versioned` 接口 + `Computed` | 派生值现在是"手工 `??=` + 记得复位"，靠一条有边界的 lint 兜 |
| **`settle()` 改多轮收敛** | `Element::settle` + `State` 加两个静态计数器 | 单遍在"子标脏祖先"时慢一帧；而 `Cell` 去陷阱后写的时机面会**变大** |

★ 本册**不动** `Subject` / `SubjectBuilder` / `PageHost` / `TaskHost` —— 那四件的形状是对的
（`Subject` 不认识 GUI 是结构事实，`select` 门控比的是两次输出，异步三件已跑通）。
本册只改"`Cell` 用不了"和"派生值靠纪律"两件事。

### 1.2 为什么没人用：最自然的写法是个陷阱

`Cell` 要标脏，就必须知道标哪个 `State`（`Cell.php:24-25`）：

```php
/** @internal 标脏要靠它；由 `State::cell()` 绑上 */
private ?State $owner = null;
```

于是"创建"必须发生在**能拿到 `$this` 的地方**。逐条推演三条创建路径：

| 写法 | 结果 | 判定 |
|---|---|---|
| **A** 属性初始化器 `private Cell $hovered = new Cell(-1);` | 编译期就能写（`new` 在初始化器里合法），但 `owner` 是 `null` ⇒ **第一次 `setIfChanged()` 当场 Fatal**（`Cell.php:61`） | ❌ **陷阱**：错在"最自然的写法"，且只在写值时才炸 |
| **B** 构造函数 `__construct() { $this->hovered = new Cell(-1); }` | 同样 `owner = null` ⇒ 同样 Fatal | ❌ 同 A |
| **C** `initState()` 里 `$this->hovered = $this->cell(-1);` | 正确 | ✅ 但要额外一行 + 属性声明只能写 `?Cell` |

★ **A 和 B 都能过 lint、过静态分析、过 `php -l`**，只在运行期写值那一刻炸。smoke 里那条
`(new Cell(1))->setIfChanged(2)`（`tools/smoke.php:295`）测的就是这条 Fatal ——
**它测的是一个用户必然会踩的坑，而不是一条框架不变式**。

再算第三笔成本：因为属性只能声明成 `?Cell`，每个读点要写成

```php
$this->hovered?->value()
```

对比用户实际选的那条路：

```php
// 现状（14 处 setState 之一，apps/showcase/src/Pages/ButtonsPage.php:92）
$this->setState(function (): void { $this->hovered = $i; });
```

**一行、无 `?`、无绑定。** 代价是 `setState()` 不比较值（`State.php:64-65` 明写
"不比较值：想设同值不重建就把那个值用 `Cell` 装"）⇒ 鼠标在同一行反复移动时每帧重建。

⇒ 结论：**`Cell` 省下的是重建次数，付出的是"每个读点一个 `?` + 一次显式绑定 + 一条会炸的错路"。**
在"只有一个消费者、且那个消费者是测试夹具"的现实下，这笔交易不划算。

### 1.4 `settle()` 单遍后序：两条性质，一条是坏的

`src/Widget/Element.php:282-296`：

```php
public function settle(): void
{
    if ($this instanceof StatefulElement && $this->state()?->needsBuild()) {
        $this->rebuild();                       // ① 先重建自己（内部 consumeDirty）
    }
    $this->visitChildren(function (Element $child): void {
        $child->settle();                       // ② 再下沉子节点
    });
    $this->adoptBoxes();                        // ③ 后序挂盒
}
```

**当前节点先 rebuild，再下沉子节点。** 两条性质：

| # | 性质 | 好坏 |
|---|---|---|
| **A** | 父 rebuild 造出的**新**子节点，在同一遍里就会被 settle ⇒ 新子树当帧生效 | ✅ 这是"一次 setState 当帧可见"的物质基础 |
| **B** | 子节点在 settle 期间标脏了**祖先**，那个祖先已经 settle 过 ⇒ 本帧不重建 ⇒ **慢一帧** | ❌ |

B 的触发路径有三条，逐条判"当前会不会炸"：

| 路径 | 谁在 settle 期写 | 会炸吗 |
|---|---|---|
| 后台任务回调 `applyPage()` → `notifyChanged()` | 任意 `State` | **不会**：`Application::frame()` 的 pumpTasks 段在 `Frame::run()` **之前**（`:1001-1093` 九段） |
| `tickAnimations` → `tickFrame()` → `setState()` | 任意 `State` | **不会**：同上，在 settle 之前 |
| `OffstageElement::rebuild()` 里 `$parked->settle()` | 被唤醒的隐藏子树 | **不会**：子树在本节点**之下**，同遍能收 |
| `Element::applyContext()` → `markDirty()` | 子节点 | **不会**：子节点在下沉路线上 |
| **`build()` 里调 Store 的写方法** → `notifyChanged()` | 任意 `State`（可能在树的**另一支**） | **会**：这是唯一真实路径，且只发生在"页面在 build 里改 store"这种写法下 |

⇒ 诚实的结论：**R3 是"还没炸"，不是"不存在"。** 而 `Cell` 去陷阱（§3）之后，
"写"的时机面会**变大**（不再需要 `initState()` 才能建），所以 §5 必须与 §3 同批落地。

### 1.5 `SubjectBuilder` 的门控注释对**数组**是错的

`src/State/SubjectBuilder.php:29-31`：

> ② 返回值该是"代表变化的最小值"（摘要），返回每次新建的对象/数组 ⇒ `===`
>   永不相等 ⇒ 退化成每帧重建

**这句话对数组是错的。** PHP 的 `===` 对数组是**逐键值严格比较**（键序 + 类型 + 值），
`[1, 2] === [1, 2]` 为 `true`。只有**对象**才是身份比较。

实测反证：`apps/users/src/Pages/UsersPage.php:92`

```php
->select(static fn(UserStore $s): array => $s->visible())   // 每次都是新数组
```

`visible()` 每次返回 `array_values(array_filter(...))` 的**新数组**（`UserStore.php:74-82`），
门控照样生效 —— 因为元素是同一批 `User` 实例，`===` 逐项为真。

⇒ 该注释要改成"返回每次新建的**对象**（非 `readonly`）⇒ `===` 永不相等"。
而这条恰好是 lint `select-purity` 在守的（返回类型必须是标量 / enum / readonly class，
`User` 是 `final readonly class`）。

★ 顺带一条判据（进 `07-可检查性.md`）：**注释里写的"机制原因"也会腐烂**。
这条注释从写下起就是错的，而它守着的机制（`select-purity`）是对的 ——
于是没人会去验证注释，因为代码一直工作正常。

## 2. 根因三条

| # | 根因 | 证据 | 后果 |
|---|---|---|---|
| **R1** | **`Cell` 的创建时机被绑定方式锁死**，最自然的写法是陷阱 | §1.2 三条路径表 | 生产消费者 0 |
| **R2** | **派生值是手工缓存**，框架知道依赖（`select` 闭包里）但没把它变成机制 | §1.3 四写点十二行 | 靠一条有边界的 lint 兜 |

三条的共同形状与 `00` §0 完全一致：**"只有一个消费者时，把'记得做'当成了'不需要机制'"**。

- R1：`Cell` 唯一的消费者是 smoke 夹具 ⇒ 绑定时机的不便**没人报怨**，于是没修
- R2：`UserStore` 只有一个派生值 ⇒ 手工清缓存看着很便宜
- R3：所有写都发生在 settle 之前（`frame()` 九段的顺序）⇒ 单遍**够用**

⇒ **本册三处改动，都是"第二个消费者已经出现（或即将出现）"的兑现。**
不是"设计错了"，是"设计的形状只覆盖了一个消费者"。

## 3. 落点一：`Cell` 去掉那个陷阱

### 3.1 逐笔消成本

§1.2 算出三笔成本，逐笔判"能不能消"：

| 成本 | 能不能消 | 怎么消 |
|---|---|---|
| **绑定**（必须 `initState()` 里调 `cell()`） | ❌ 消不掉（PHP 语言限制：属性初始化器拿不到 `$this`） | 保留，但让它**不再是陷阱** |
| **`?Cell` 读点**（`?->value()`） | ✅ 能消 | 允许声明**非空** `Cell` 属性；未初始化时读 ⇒ 响亮 `Error`（不是静默 null） |
| **`?State` 动态分派**（每次写走 `Var`） | ⚠️ 形参层能消，**字段层无性能收益** | `?State $owner` → `State $owner` + `bool $bound` |

★ 第二笔 2026-10-21 按 M0-2 改了口径（原写"✅ 能消"）。实测：`?Obj` 的退化
**只发生在形参/返回值层**（`Frame::run` 同一签名里 `Element $root`→`php::Object`
而 `?Element $popup`→`php::Var`）；**字段存储层两种形态相同**（tpc 不给普通类生成
C++ 结构体字段，都走 PHP 属性表），读点层 `?State` 付一次空检查、`State`+`bool`
付一次布尔检查 —— **都是一次比较，无量级差**。且非空字段上的属性访问仍是
`typephp_read_property_cached`（单态内联缓存），**不是静态偏移读**。
⇒ 这个改动的收益是**人因**（读点不写 `?->`），不是性能。仍然要做，但理由要写对。
证据：`docs/AOT-CONSTRAINTS.md` §2.2。

★ 第一笔消不掉是**诚实的边界**，不要假装能消。§3.3 推演了三条"看起来能消"的路，全否决。

### 3.2 形状

```php
final class Cell
{
    private mixed $value;

    // ★ 非空：读点不写 `?->`（人因）。**不要以为是性能**：M0-2 实测字段存储层
    //   `?State` 与 `State` 同形态（都走 PHP 属性表），读点各付一次比较；
    //   且非空字段上的属性访问仍是 typephp_read_property_cached（内联缓存），
    //   **不是静态偏移读**。`?Obj` 真退化只发生在**形参/返回值层**（→ `php::Var`）。
    //   证据：docs/AOT-CONSTRAINTS.md §2.2
    private State $owner;
    private bool $bound = false;

    /** ★ private：唯一入口是 `State::cell()` —— 让"错的写法"写不出来 */
    private function __construct(mixed $initial)
    {
        $this->value = $initial;
    }

    /** @internal 只有 `State::cell()` 调得到（构造函数私有 ⇒ 外部造不出未绑定的 Cell） */
    public static function makeFor(State $owner, mixed $initial): self
    {
        $cell = new self($initial);
        $cell->owner = $owner;
        $cell->bound = true;

        return $cell;
    }

    public function value(): mixed
    {
        return $this->value;
    }

    public function setIfChanged(mixed $value): bool
    {
        if ($value === $this->value) {
            return false;              // === 相等 ⇒ 什么都不做（§11.3.1 门控）
        }

        $this->value = $value;
        $this->owner->markDirty();     // 非空引用 ⇒ 无 ? 检查、无 null 分支

        return true;
    }
}
```

★ **`bool $bound` 现在恒为 `true`**，看着多余 —— 它留着是为了让"未绑定"这件事
在类型系统里**有位置**：将来若有第二条创建路径（比如 `Store` 里要一个不标脏的 `Cell`），
`bound = false` 就是那个开关，而不是又加一个可空属性。

`State::cell()` 相应改一行：

```php
public function cell(mixed $initial): Cell
{
    return Cell::makeFor($this, $initial);
}
```

### 3.3 为什么不做"懒分配"（三条写序推演）

v6 的做法是 `Tracker::$stack`（读即订阅）：`Cell::get()` 时从静态栈顶拿"当前正在 build 的
`State`"。这条路能让 `new Cell(-1)` 直接写在属性初始化器里，看起来最省事。**否决**，推演如下：

| 写序 | 情形 | 懒分配结果 |
|---|---|---|
| ① | `initState()` 里写（`$this->hovered->setIfChanged($i)`） | 栈空（不在 build 期）⇒ **绑不上** ⇒ 只能"先读后写" ⇒ 要求 `initState` 里先 `get()` 一次 |
| ② | `build()` 里读 | 栈顶 = 当前 `State` ⇒ 绑上 ✅ |
| ③ | 事件回调里写（无 build 上下文） | 栈空 ⇒ 绑不上 ⇒ 若 ① 没做过"先读"，这次写**静默无效** |

⇒ **懒分配把"必须显式绑定"换成了"必须先读后写"** —— 后者违反起来是**静默的**
（写了一个没人订阅的 `Cell`，值变了界面不动），前者违反起来是**响亮 Fatal**。

按 `00` §2 P1 与 G2「绝不静默」：**用响亮换省事，不划算。**

★ 还有第二条否决理由：`Tracker::$stack` 是**带类型的静态属性**（v6 `03` §3），
而 AOT 下静态属性的读写成本是 v6 自己的待验证项 V-5。为一条"省一行"的便利引入
一个未验证的机制，不值。

### 3.4 不做分型（推翻 `00` §6 的原计划）

`00-总纲.md` §6 原写"`State/IntCell.php` 等 5 个"。**本册把它降级为条件性改动**，
理由是先算账再决定。

分型的收益**不在"省一次装箱"** —— `Cell` 现在用 `mixed` + `===`，`IntCell` 用 `int` + `===`，
比较语义完全一样。真正的收益在 tpc 侧：

| 形态 | tpc 生成 | 每次读 |
|---|---|---|
| `private mixed $v` | `php::Variant` | `php::toInt()` / `php::toObject()` |
| `private int $v` | `int` | `Z_LVAL_P` 直取 |

判据写死，免得反复讨论：

```
M0 实测两条：
  C_mixed = Cell<int> 经 mixed 存取一次（写 + 读）的端到端成本
  C_int   = IntCell 经 int 存取一次的端到端成本

每帧 Cell 写次数的上界 N ≈ 鼠标移动事件数 ≈ 60–200（HoverWidget 那类场景）

判据：(C_mixed - C_int) × N × 2 < 0.1ms  ⇒ 不分裂
```

代入估数：若 `C_mixed - C_int = 200ns`，`N = 200` ⇒ `200ns × 200 × 2 = 80µs` ⇒ **不分裂**。
若差到 1µs（即 `Variant` 每次读写要 1µs，明显不合理）⇒ `400µs` ⇒ 才值得分裂。

⇒ **本册的默认结论是"不分裂"**，只在 M0 实测超出判据时执行 `00` §6 的五个文件。
`09-迁移路线.md` 把这条写成"第 4 步的一个分支"，不是一个独立步骤。

★ 这也回应了 v6 自己的自我怀疑（`11` §7 第 2 条）：
「`Cell` 按类型分裂……`IntCell`/`StrCell` 的收益可能不足以抵消'选哪个'的成本」。
我们的判据直接量化了"什么情况下收益够"。

### 3.5 兼容

| 现状 | 之后 | 破坏 |
|---|---|---|
| `new Cell(-1)` 可用（但写值即 Fatal） | **不可用**（构造函数私有 ⇒ `Error: Call to private Cell::__construct()`） | 无生产影响（0 消费者）；smoke 夹具 `smoke.php:295` 改成断言这条 `Error` |
| `State::cell()` | 保留，签名不变 | 无 |
| `Cell::value()` / `setIfChanged()` | 保留 | 无 |
| `Cell::bindTo()` | **删除**（只有 `State::cell()` 一个入口） | 无（`@internal`，无外部调用） |

★ 唯一"破坏"是把一个**运行期 Fatal** 换成**更早的 `Error`**。这是净收益：
错得更早、更近出错点、堆栈更短。

## 4. 落点二：`Computed`（派生值从纪律变机制）

### 4.1 现状代价

`UserStore::$visibleCache` 的三个问题：

| # | 问题 |
|---|---|
| ① | **复位点分散**：4 个写点各一行，加第 5 个写点就多一处要记得 |
| ② | **lint 有边界**：只扫 `*Store`、只认字段级槽（§1.3） |
| ③ | **缓存是"先到先得"**：`visible()` 第一次被谁调就按当时的依赖算；若某个写点漏了复位，**第一次读到的旧值会被永久缓存**（`??=` 不会自己失效） |

③ 是最狠的：漏一次复位不是"这一帧显示旧数据"，是**直到下一次复位之前都显示旧数据**。

### 4.2 拉取式为什么天然无 glitch（三种写序）

场景：`full = first . ' ' . last`，一次事务里先改 `first` 再改 `last`。

| 机制 | 改 `first` 之后 | 改 `last` 之后 | 中间态会被看到吗 |
|---|---|---|---|
| **推送式**（订阅/回调，改一个就算一遍） | 立刻算出 `full = "A oldLast"` 并写出去 | 再算出 `full = "A B"` | **会** —— 这就是 glitch。要消它必须批处理 + 拓扑排序 |
| **拉取式**（`Computed`，改只置脏） | 只置脏，不算 | 只置脏，不算 | **不会** —— 重算发生在两次写**之后**（同一帧的 settle 里） |

⇒ 结论：**拉取式不需要批处理，也不需要拓扑排序。** 脏只是一个 `bool`/版本号，
"什么时候算"由**读**决定，而读一定发生在写之后。

### 4.3 为什么不需要拓扑排序（以及它的前提）

拓扑排序要解决的问题：`A` 依赖 `B`、`B` 依赖 `C`，`C` 变了要按 `C → B → A` 重算。
拉取式把"顺序"变成"递归"：`A.get()` → `B.get()` → `C.get()`。**调用栈天然是拓扑序。**

★ 前提：**求值过程中不能再写。** 若闭包里有写操作 ⇒ 递归中嵌套置脏 ⇒ 可能死循环。
守卫：

```php
public function get(): mixed
{
    if ($this->evaluating) {
        Errors::report('Computed 闭包必须是纯函数：求值期间又触发了自己的求值（E-COMPUTED-CYCLE）');
    }
    $this->evaluating = true;
    try {
        // … 版本和没变就直接返回缓存
        return $this->value;
    } finally {
        $this->evaluating = false;
    }
}
```

★ 这条守卫与 `SubjectBuilder` 的"`select` 闭包不许有副作用"是同一条纪律，
但**它现在是注释，之后是运行期守卫**（`00` §2 P6：逃生口要难看）。

### 4.4 真冲突：业务层不许依赖 State 层 ⇒ `Versioned` 接口

这是本册唯一一处**需要裁决**的地方，v6 没有这个问题（它的 `Store` 与 `Cell` 同层）。

**冲突**：
- `visible()` 是**业务派生值**（过滤结果），逻辑上属于 `Store`
- `Computed` 若要读 `Cell` 的版本，就得住 `Drift\State`
- 而 `Subject.php:11-16` 明写：

  > ★ **不认识 GUI**：子类（`Store`）住在应用包的 `store/` 目录，依赖的只有本类 ——
  >   "业务层零 GUI 依赖"因此是**结构事实**，不是纪律承诺。
  > ★ ……**不要**为了门控把 `Store` 的每个字段都换成 `Cell` —— 那会让业务层依赖 State 层类型。

**三个选项**：

| 选项 | 做法 | 判定 |
|---|---|---|
| A | `Computed` 住 `Drift\State`，`Store` 依赖它 | ❌ 破坏结构事实 |
| B | 业务层继续手工缓存 + lint（现状），`Computed` 只服务 UI 层 | ❌ 真正需要它的地方（`UserStore`）用不上 |
| **C** | **把"依赖有没有变"抽象成一个 `int` 接口，`Computed` 住 `Drift\Core`** | ✅ 选这个 |

```php
namespace Drift\Core;

/**
 * "我有版本号"（§11.3.4）。
 *
 * ★ 只有一件事要说：**我变了没有**。不提 Cell、不提 Subject、不提 State ——
 *   于是业务层与 UI 层可以各自实现，`Computed` 谁都不认识。
 *
 * ★ 版本号是**单调递增**的：写一次 +1。不要求连续、不要求可比较大小之外的语义。
 */
interface Versioned
{
    public function version(): int;
}
```

- `Cell` 实现它（`setIfChanged()` 里 `$this->version++`）
- `Subject` 实现它（`notifyChanged()` 里 `$this->version++`）
- `Computed` 自己也实现它（求值成功时 `$this->version++`）⇒ **可以嵌套**

于是 `Computed` 的形状：

```php
namespace Drift\Core;

final class Computed implements Versioned
{
    private mixed $value = null;
    private bool $hasValue = false;
    private int $version = 0;
    private int $seenSum = -1;        // 上次求值时的依赖版本和
    private int $depth = 0;           // 嵌套深度（构造时算）
    private bool $evaluating = false;

    /** @var list<Versioned> */
    private array $deps;

    /**
     * @param callable(): mixed $fn 必须纯（不许写任何 Versioned）
     * @param list<Versioned>   $deps 依赖
     */
    public function __construct(private $fn, array $deps, int $depth = 0)

    public function get(): mixed
    {
        $sum = 0;
        foreach ($this->deps as $dep) {
            $sum += $dep->version();     // O(依赖数)，上界 5
        }

        if ($this->hasValue && $sum === $this->seenSum) {
            return $this->value;         // 没变 ⇒ 直接给缓存（无脏时成本 = 一次加法）
        }

        // … evaluating 守卫 → 求值 → 更新 seenSum / value / version
    }

    public function version(): int
    {
        return $this->version;
    }
}
```

★ `Computed::get()` 的**无脏成本**是 `O(依赖数)` 次 `version()` 调用 —— 依赖数上界很小
（`visible()` 的依赖是 `UserStore` 一个），所以是"一次加法 + 一次比较"。

### 4.5 `UserStore` 改造后的样子

```php
final class UserStore extends Subject      // ★ Subject 已实现 Versioned ⇒ 本类不用再写
{
    private Computed $visible;

    public function __construct(...)
    {
        // 依赖 = $this（Subject 的版本号）⇒ 任何 notifyChanged 都重算
        $this->visible = new Computed(
            fn(): array => $this->query === ''
                ? $this->rows
                : array_values(array_filter($this->rows, fn(User $u): bool => str_contains($u->name, $this->query))),
            [$this],
        );
    }

    public function visible(): array
    {
        /** @var list<User> */
        return $this->visible->get();
    }

    public function setQuery(string $q): void
    {
        if ($q === $this->query) {
            return;
        }
        $this->query = $q;
        $this->notifyChanged();      // ★ 删掉 `$this->visibleCache = null`
    }
    // load() / remove() / applyPage() 同样删掉那一行
}
```

**4 处 `$this->visibleCache = null` 全部删除，`private ?array $visibleCache` 字段删除。**
`stale-derived` 这条 lint 从此对 `UserStore` 无事可做（它守的槽不见了）。

### 4.6 精确依赖 vs 粗依赖：一个明确的取舍

`[$this]` 是**粗依赖**：`status` 变了 `visible` 也会重算，而 `visible` 并不读 `status`。
精确依赖要写成 `[$this->queryCell, $this->rowsCell]` ⇒ 要求 `Store` 字段 `Cell` 化 ⇒
违反 §4.4 的结构事实。

**裁决：用粗依赖。** 理由与 `UserStore.php:106-107` 的既有裁决逐字一致：

> 多一次全表过滤换掉一整类静默陈旧值。

★ 但粗依赖有一个**必须写下来的上界**：`visible()` 是一次 `O(rows)` 的过滤，
每次 `notifyChanged()` 后**第一次读**会重算一次。`UserStore` 的 `notifyChanged()` 每帧
最多几次（加载三态切换 + 输入），`rows` 是 200 条 mock ⇒ 单次 ≈ 20µs ⇒ 可忽略。
**若某个 Store 的派生值超过 1ms，就不该用粗依赖** —— 那时该拆 Store（派生值单独一个 `Subject`），
而不是给 `Computed` 加精确依赖。

### 4.7 嵌套深度上限

`Computed` 依赖 `Computed` 是允许的（都实现 `Versioned`）。深度上限 **8**：

```php
if ($depth > 8) {
    Errors::report('Computed 依赖链超过 8 层：这不是派生值，是没拆开的 Store（E-COMPUTED-DEPTH）');
}
```

★ 8 这个数字不是拍脑袋：正常派生链是"字段 → 过滤/聚合 → 格式化"三层，
留一倍余量。超过 8 层的派生值，正确的修法是拆 Store，不是加深链条。

## 5. 落点三：`settle()` 多轮收敛

### 5.1 算法

```php
// src/Widget/Element.php
/**
 * 收敛整棵子树的脏。
 *
 * @return bool 本次 settle **是否重建过任何节点**。`05` §5.4 的"跳过 layout"用它。
 *
 * ★ 返回值是**与 `05` 合并**的结果（`09` §1 冲突 1）：本册原写 `: void`，
 *   `05` §8 要 `: bool`。两个需求都成立，但**一次只能改一次签名** ⇒ 合并成这一版。
 *   分两次的代价：中间态 `bool` 恒 `null` ⇒ 跳过 layout 的判据永真
 *   ⇒ **动画帧永不重排，且不报错**（画面冻结在旧布局，没有任何告警）。
 */
final public function settle(): bool
{
    $before = State::rebuiltCount();

    for ($round = 1; $round <= self::SETTLE_ROUNDS; $round++) {
        if (State::pendingDirty() === 0) {
            break;                        // ★ O(1) 提前退出：绝大多数帧走这里
        }
        $this->settlePass();
    }

    if ($round > self::SETTLE_ROUNDS) {
        Errors::report(sprintf(
            '一帧内 rebuild 了 %d 轮仍未收敛：有 State 在 build() 里改了会标脏的东西（E-FLUSH-CYCLE）',
            self::SETTLE_ROUNDS,
        ));
    }

    return State::rebuiltCount() > $before;
}

protected function settlePass(): void
{
    if ($this instanceof StatefulElement && $this->state()?->needsBuild()) {
        $this->rebuild();
    }

    $this->visitChildren(function (Element $child): void {
        $child->settlePass();
    });

    $this->adoptBoxes();
}
```

★ **为什么"有没有 rebuild"用计数器差值，而不是让 `settlePass()` 返回 `bool`**：

1. **AOT 风险**：让 `settlePass()` 返回 `bool` 就必须在 `visitChildren` 的闭包里聚合，
   而聚合只能靠 `use (&$rebuilt)`（按引用捕获）。**按引用捕获的闭包在 AOT 下没有实测过**，
   而 `State::rebuiltCount()` 是一个 `private static int`（`08` §4 V-5 已列为待实测项，
   但它至少是"读一个静态字段"，不是"造一个引用环境"）。
2. **`ErrorBoundaryElement` 的覆写面最小**：它只需要**改名**，签名一个字不动。
   若改成返回 `bool`，它还得 `return parent::settlePass()` —— 多一处可漏的地方。
3. **差值天然正确**：`rebuild()` 里本来就要 `State::noteRebuilt()`（§5.3），
   计数器是免费得到的，不需要新机制。

⇒ `settlePass()` 保持 `void`，`settle()` 用 `State::rebuiltCount()` 的前后差。

#### `settle()` 必须 `final`：唯一覆写者的形状

实测 `grep -rn "function settle" src/` = **2 处**：

| 文件 | 干什么 |
|---|---|
| `Element.php:282` | 基类（本册拆成 `settle` + `settlePass`） |
| `ErrorBoundaryElement.php:45` | **覆写** `settle()`，`try { parent::settle(); } catch { capture(); }` |

★ **如果只拆基类，这个覆写会静默坏掉**：`settle()` 变循环、`settlePass()` 变单遍，
而 `ErrorBoundaryElement` 覆写的仍是 `settle()` ⇒ 它包住的只是**第一遍**，
第 2 遍的异常绕过边界直接冒到 `Frame::run()`（`Frame.php` 的 settle 段 catch 会把
整帧降级成一条 `Errors::report`）⇒ **错误边界的粒度从"到节点"退化成"到整帧"**，
且**不报错、不崩**，只在真出错那天才看得见。

⇒ 处置两条：

1. **`settle()` 改 `final`** —— 循环归基类所有，子类无法再用"覆写整遍"的方式绕过收敛
2. `ErrorBoundaryElement` 的覆写**改名** `settlePass()`：

```php
// src/Widget/ErrorBoundaryElement.php
public function settlePass(): void          // ← 原 `settle()`
{
    if ($this->caught !== null) {
        return; // 已坏：占位不参与帧末重建，不会二次抛
    }

    try {
        parent::settlePass();
    } catch (Throwable $e) {
        $this->capture($e);
    }
}
```

★ 这正是 `00` §2 P1 想要的形状：**"想让忘写变成写不出来"** —— `settle()` 一 `final`，
"覆写 settle 但只包住一遍"这个错误**在语法层面不可达**。

配合 `State` 里**两个静态字段**：

```php
/** @internal 未消费的脏 State 数 —— 收敛循环的 O(1) 提前退出条件 */
private static int $pendingDirty = 0;

/** @internal 本帧序号 —— `noteRebuilt()` 用它识别"同帧第二次"（§5.3） */
private static int $frameSerial = 0;

/** @internal 由 `Application::frame()` 每帧调一次，紧跟 `$this->frameSerial++` */
public static function beginFrame(int $serial): void
{
    self::$frameSerial = $serial;
}

public function markDirty(): void
{
    if ($this->dirty) {
        return;                  // ★ 已经脏 ⇒ 不重复计数
    }
    $this->dirty = true;
    self::$pendingDirty++;
}

public function consumeDirty(): bool
{
    $dirty = $this->dirty;
    if ($dirty) {
        $this->dirty = false;
        self::$pendingDirty--;
    }

    return $dirty;
}

/** @internal 收敛循环的提前退出条件 */
public static function pendingDirty(): int
{
    return self::$pendingDirty;
}
```

★ **`pendingDirty` 是"要不要再扫一遍"的 O(1) 判据。** 没有它，每帧要无条件扫两遍树；
有了它，正常帧只扫一遍（第一遍之后计数为 0 ⇒ 立即 return）。

### 5.2 为什么"重复整遍"等价于"按树深度升序"

v6 `03` §5.2 的 flush 是**按树深度升序**处理一个扁平脏列表。我们不需要显式排序，理由：

`settlePass()` 是**前序**遍历（先自己、再子节点）。前序保证：**同一遍里，祖先一定先于后代被处理。**

- 脏在"祖先 → 后代"方向传播（父 rebuild 造出新子节点）：**同一遍收住**（性质 A）
- 脏在"后代 → 祖先"方向传播（子在 settle 期标脏祖先）：祖先已在**本遍**处理过 ⇒ 落到**下一遍**
- 而下一遍仍是前序 ⇒ 祖先先 rebuild、随后它的整棵子树在本遍内被重新下沉

⇒ **只需要两遍**就能收住任何单方向的链；两遍之后再产生脏，只可能是"build 期又写了"
（活锁，见 §5.3）。所以上限 16 是**防御性**的，不是预期路径。

★ 这是对 v6 的一处**简化**：v6 需要显式深度排序，因为它的 flush 拿的是一个"脏集合"；
我们拿的是"树 + 一个计数器"，前序遍历已经把深度序免费给了。

### 5.3 build 期写：从静默活锁变当帧报错

现状：`build()` 里调 `setState()` 是允许的（`State::setState()` 没有守卫）。
后果推演：

```
帧 N   : settle → needsBuild=false → 不 rebuild
帧 N+1 : 父 rebuild 造出新子节点 → 子 mount → rebuild → build() → setState → dirty=true
帧 N+2 : settle → needsBuild=true → rebuild → consumeDirty(false) → build() → setState → dirty=true
帧 N+3 : 同上 …… 每帧重建一次，永远不停，不报错，不崩
```

⇒ **一个静默的每帧重建**，CPU 占用上去，没人知道为什么。

多轮收敛之后，同一个写法变成：

```
轮 1 : rebuild → build() → setState → pendingDirty=1
轮 2 : rebuild → build() → setState → pendingDirty=1
……
轮 16: 抛 E-FLUSH-CYCLE（当帧，带 State 类名）
```

★ 更好：**在第二轮就报**，不必等到 16。做法是 `State` 记一个"本帧已 rebuild 过的帧号"：

```php
private int $rebuiltFrame = -1;

/** @internal `StatefulElement::rebuild()` 的第二句调它（第一句是 consumeDirty） */
public function noteRebuilt(): void
{
    if ($this->rebuiltFrame === self::$frameSerial) {
        Errors::report(sprintf(
            '同一帧内 %s 被 rebuild 了两次：build() 里改了会标脏的东西（E-FLUSH-CYCLE）',
            get_class($this),
        ));
    }
    $this->rebuiltFrame = self::$frameSerial;
}
```

调用点在 `StatefulElement::rebuild()`（`StatefulElement.php:43-52`）：

```php
public function rebuild(): void
{
    $this->state?->consumeDirty();
    $state = $this->state;
    if ($state === null) {
        return;
    }

    $state->noteRebuilt();                              // ★ 新增这一句
    $this->updateChildren([$state->build($this->context)]);
}
```

★ **帧序号不需要新造**：`Application::$frameSerial` 已经在（`Application.php:227-228`，
`:1016` 每帧 `++`），`State::tickFrameStamped()` 用它做同帧幂等（`State.php:116-124`）。
本册只是把它**同步一份到 `State` 的静态**，让 `rebuild()` 拿得到：

```php
// Application::frame() 里，紧跟现有的 $this->frameSerial++;
State::beginFrame($this->frameSerial);
```

★ 为什么不用参数往下传（`settle(int $serial)` → `settlePass(int $serial)` → `rebuild()`）：
`rebuild()` 是 `public`，`mount()` 也调它（`Element.php:72`），传参要改两处签名并让
"mount 期没有帧号"变成一个新分支。**静态一份、一处写入**，改动面最小。

⇒ **一次 build 期写 = 当帧 Fatal，带类名。** 这是本册最直接的一处"静默变响亮"。

### 5.4 与 `Frame::run` 的接缝

`Frame::run()` 的 settle 段只改一处：

```php
try {
    $root->settle();
    $popup?->settle();     // 第二棵树（浮层）—— 它有自己的根，计数是同一份静态
}
```

★ `pendingDirty` 是**静态**的 ⇒ 两棵树共用一份计数。这是**对的**：
若浮层的 build 标脏了主树的 State，主树的 `settle()` 会看到非零计数并多跑一遍。
`00` §6 说浮层栈落地后 `Frame::run` 签名改成 `array $overlays`，那时循环体变成：

```php
foreach ($overlays as $entry) { $entry->element?->settle(); }
```

★ **静态计数器在 AOT 下**：`private static int` 的读写成本是 v6 的待验证项 V-5。
若实测显示静态属性访问比实例属性慢，退路是把计数挂到 `Element` 的根节点上
（`$root->dirtyPending`），代价是 `State::markDirty()` 拿不到根 ⇒ 需要再想办法。
**这条写进 `08` §3 的 V-5，与 `Cell` 分型共用同一次 M0 实测。**

### 5.5 落地顺序：§3 与 §5 必须同批

| 若先做 §3（`Cell` 去陷阱） | 若先做 §5（settle 收敛） |
|---|---|
| `Cell` 可以在构造函数里建 ⇒ **写时机面变大** ⇒ 单遍 settle 的"慢一帧"从罕见变常见 | 收敛循环上线，但没有 `Cell` 消费者 ⇒ 收益为 0，只多了一个 O(1) 检查 |

⇒ **同批**。`09-迁移路线.md` 把这两件合并成"第 4 步"的一个提交序列。

## 6. 分层：Domain ← Store ← Ui

### 6.1 现状：三层已经成立，且是**结构事实**

`apps/users/src/Store/` 全部 5 个 import（实测）：

```
2 × use Drift\State\Subject;
1 × use Drift\App\TaskHost;
1 × use Drift\Theme\SystemTheme;      ← 枚举，不是 UI 类型
1 × use App\Users\Jobs\FetchUsersJob;
```

**没有一行 `use Drift\Widget\...`、没有一行 `use Drift\Layout\...`、没有一行 `use Drift\Rendering\...`。**

⇒ "业务层零 GUI 依赖"不是纪律承诺，是**依赖方向的结构事实**。
`Subject.php:11-16` 那段注释说的是实话，本册的任务是**别把它破掉**（§4.4 选项 C 就是为此）。

★ `Drift\Theme\SystemTheme` 是 `enum`，`Drift\App\TaskHost` 是异步端口 —— 两者都不是
"UI 类型"，依赖方向仍然成立。但**这条边界值得一条 lint**，见 §6.3。

### 6.2 状态放哪：四处判决表

抄 v6 `16` §2，按 Drift2 的类型名落地：

| 状态 | 放哪 | 判据 | Drift2 里的例子 |
|---|---|---|---|
| **业务数据**（要落库/要跨页/要被测试断言） | `Store`（`extends Subject`） | 换个 UI 它还得在 | `UserStore::$rows` `$status` |
| **跨页共享的 UI 偏好** | `Store` | 两个页面都要读 | `AppStore::$systemTheme` `$currentPage` |
| **单页 UI 态**（展开/选中/滚动位置） | `State` | 换个页面就该没了 | `FormPage` 的 `$on`、`ButtonsPage` 的 `$hovered` |
| **高频、可能重复设值的 UI 态** | `State` 里的 `Cell` | 同值反复写会白白重建 | 鼠标在行间移动的 hover |
| **派生值** | `Computed`（住 `State` 或 `Store` 均可，靠 `Versioned`） | 能从别的状态算出来 | `UserStore::visible()` |

★ 第五行是新增的：**派生值不该有"自己的存储"**，只该有"自己的求值函数 + 依赖列表"。
现状把两者混在一起（`$rows` 是真存储，`$visibleCache` 是派生），于是"复位"变成手工动作。

### 6.3 新增一条 lint：`store-imports-ui`

| 项 | 内容 |
|---|---|
| **代号** | G1 |
| **判据** | `apps/*/src/Store/**` 里的文件不许 `use Drift\Widget\` / `Drift\Layout\` / `Drift\Rendering\` / `Drift\App\Application` |
| **为什么现在加** | 现状 0 违规（§6.1 实测），但**没有任何机制守着**。`internal-leak` 只查 `@internal` 类型，查不到"业务层用了 UI 层类型" |
| **允许的例外** | `Drift\State\*`（`Subject` / `Subscription`）、`Drift\Core\*`（`Versioned` / `Computed`）、`Drift\App\TaskHost`（异步端口）、`Drift\Theme\SystemTheme`（枚举） |
| **误报风险** | 低：Store 的 import 面很小（5 个），判据是白名单 |

### 6.4 附带发现：`markDirty()` 的 `@internal` 已经漏了

`State::markDirty()` 标 `@internal`（`State.php:79`），但**应用代码直接调了 5 次**：

```
apps/showcase/src/Pages/MotionPage.php:88, :116, :122, :128, :134
```

用法是 `tickFrame()` 里改完值之后标脏：

```php
if ($busy) {
    $this->markDirty();
}
return $busy;
```

这是**合法需求**（`tickFrame` 里已经改完值，用 `setState(fn() => null)` 裹一层空闭包很别扭），
但**没有 `@api` 入口**。`internal-leak` 只查类型、不查方法 ⇒ 漏了。

**处置**：`markDirty()` 升为 `@api`，并在 docblock 里写清它与 `setState()` 的分工
（"值已改完 ⇒ 用 `markDirty()`；值还没改 ⇒ 用 `setState()`"）。

★ 这是"标记与用法打架"的典型：不是代码错了，是**标记错了**。发现它的唯一办法是
"把 `@internal` 的方法被外部调用的地方数一遍" —— 这条也进 `07-可检查性.md` §4。

## 9. 边界情况

| # | 情形 | 期望行为 |
|---|---|---|
| 1 | `Cell` 的初值是 `null`，`setIfChanged(null)` | `===` 相等 ⇒ 返回 `false`，不标脏 |
| 2 | `Cell` 存 `NAN` | `NAN === NAN` 为 `false` ⇒ 每次写都标脏。**已知，写进 docblock**（`NAN` 不是合法 UI 值） |
| 3 | `Cell` 存对象，两次写同一实例 | `===` 为真 ⇒ 不标脏（**正确**：对象内部可能被改了，那是可变对象的责任，不是 `Cell` 的） |
| 4 | `Cell` 存数组，两次写内容相同的不同数组 | `===` 为**真**（数组逐项严格比较）⇒ 不标脏 ✅ |
| 5 | `Computed` 依赖一个永不变化的 `Versioned` | 首次求值后永不重算 ✅ |
| 6 | `Computed` 依赖自己（自引用） | `evaluating` 守卫 ⇒ Fatal `E-COMPUTED-CYCLE` |
| 7 | `Computed` 依赖链 9 层 | Fatal `E-COMPUTED-DEPTH` |
| 8 | `Computed::get()` 在 `build()` 里调 | 正常（拉取式就是为此设计） |
| 9 | `Computed::get()` 在事件回调里调 | 正常，但会同步求值（可能是一次 `O(n)` 过滤）⇒ docblock 提醒 |
| 10 | 一帧内两个 State 互相标脏 | 第 2 轮收住（前序保证）；第 3 轮不会再脏 |
| 11 | 一帧内同一个 State 被 rebuild 两次 | Fatal `E-FLUSH-CYCLE`（§5.3） |
| 12 | 浮层的 build 标脏主树的 State | 静态计数共用 ⇒ 主树多跑一遍 ✅ |
| 13 | `Offstage` 唤醒隐藏子树时子树内有脏 | `$parked->settle()` 内部走同一套多轮逻辑 ✅ |

## 10. 失败模式

| 失败 | 表现 | 防线 |
|---|---|---|
| 在 `build()` 里调 Store 的写方法 | 单遍 settle 下每帧重建一次（静默）；多轮收敛下当帧 Fatal | §5.3 `noteRebuilt()` |
| `Computed` 闭包有副作用 | 求值顺序依赖读的顺序 ⇒ 结果不稳定 | §4.3 `evaluating` 守卫 + `07` 的 `computed-purity` lint（可选） |
| `Computed` 依赖漏写 | 永远不重算 ⇒ 显示陈旧值 | **无自动防线**：依赖是构造参数，漏写等于"没依赖它"。⇒ 契约：`Computed` 只在**同一文件内**用（构造与 `get()` 相隔不超过 50 行） |
| `Store` 手工缓存漏复位 | 陈旧值被 `??=` 永久缓存 | 现状靠 `stale-derived`（有边界）；改 `Computed` 后消失 |
| `Cell` 未绑定就写 | 运行期 Fatal | §3.2 构造私有化 ⇒ 编译期就造不出未绑定的 `Cell` |
| `settle()` 收敛 16 轮不收敛 | 当帧 Fatal | §5.1；16 轮是防御上限，正常 ≤2 |
| `pendingDirty` 计数漂移（漏减） | 每帧都扫两遍（性能退化，不报错） | smoke 夹具：跑 100 帧后断言 `pendingDirty() === 0` |
| `Computed` 粗依赖 + 大 `rows` | 每次 notify 后第一次读 `O(n)` | §4.6 上界：派生值 > 1ms 就拆 Store |

## 12. 备选方案与否决

| 备选 | 否决理由 |
|---|---|
| **`Tracker` 静态栈做"读即订阅"**（v6 形态） | 把"显式绑定"换成"必须先读后写"，后者违反是静默的（§3.3） |
| **`Cell` 分型五类（无条件做）** | 收益需要 M0 实测才成立；判据写死（§3.4），默认不做 |
| **`Computed` 住 `Drift\State`，`Store` 直接依赖** | 破坏"业务层零 GUI 依赖"的结构事实（§4.4） |
| **精确依赖（`Store` 字段 `Cell` 化）** | 同上；且 `Subject` 的设计意图就是"无门控、整批通知" |
| **`settle` 显式按深度排序脏列表**（v6 形态） | 前序遍历已经把深度序免费给了（§5.2）；多一个排序 = 多一个失效点 |
| **`settle` 无条件跑两遍** | 用 `pendingDirty` 做 O(1) 提前退出，正常帧仍是一遍（§5.1） |
| **`Computed` 做成推送式（订阅 + 回调）** | 会出 glitch，消 glitch 要拓扑排序（§4.2） |
| **给 `State::setState()` 加值比较** | 比较什么？`setState` 收的是闭包，闭包改了哪些字段不可知（这是 `Cell` 存在的理由） |
| **`State` 静态计数器改实例字段** | `State::markDirty()` 拿不到根节点（§5.4） |

### 推翻条件

| 裁决 | 什么情况下推翻 |
|---|---|
| `Cell` 不分型 | M0 实测 `(C_mixed - C_int) × N × 2 ≥ 0.1ms` |
| `Cell` 构造私有 | 出现"`Store` 里也需要 `Cell`（不标脏）"的真实需求 ⇒ 那时加 `Cell::detached()`，而不是放开构造 |
| `Computed` 粗依赖 | 某个派生值的单次求值 > 1ms ⇒ 拆 Store，不是加精确依赖 |
| 静态计数器 | M0 的 V-5 实测显示 AOT 下静态属性访问显著慢于实例属性 ⇒ 改挂根节点 |
| 收敛上限 16 | 出现真实需要 >2 轮的场景（目前推演不出） ⇒ 先查是不是 build 期写 |
