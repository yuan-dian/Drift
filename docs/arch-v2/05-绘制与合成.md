## 0. 一句话

**分级与双后端是对的，缺的是"让动画不必重排"的那条路，和"分级该按谁在用"的一次重划。**

| 现状 | 问题 | 本册 |
|---|---|---|
| 9 个能力位 × 3 档（Core / Extended / Optional），两个后端 | `drawPath` 被放在 **Optional**，而"控件自绘"正需要它 ⇒ 位置放错，不是能力缺失 | 把 `drawPath` **提到 Extended**，Raster 补实现 |
| `RasterCanvas` 6 个 op 响亮失败 | 其中 `pushClipPath` 是 Extended ⇒ **Extended 层不该有缺口** | Raster 补 `pushClipPath` |
| `AnimationController` 每 tick 都 `markDirty()` | rebuild → `syncBox()` **造新盒** → 全树重排 → 全树重绘 | 一条"只改合成参数、不重建"的路 |
| `RenderBox::layout()` 声明纯函数但零断言 | "跳过 layout" 没有理论依据 | 由 `04` §5.2 的自校验**兑现**这条依据 |
| Optional 层的消费者只有 1 个 demo 页 | 分层不是按"谁在用"划的 | 允许 Optional 一强一弱，但**控件必须先查能力位**（加 lint） |

**明确不做**：retained 命令段（v6 的 `ops` packed array）、脏区光栅、图标矢量路径、
图片预算、字体子集（`00` §5 / §4.2）。

## 1. 现状：全部实测

### 1.1 能力分级与位掩码

`CanvasCapabilities`（102 行）九个叶子位，三档：

| 档 | 位 | 谁必须实现 | 现状 |
|---|---|---|---|
| **Core** | `CAP_ELLIPSE` `CAP_LINE` | 所有后端，缺一个即缺陷 | Skia ✅ / Raster ✅ |
| **Extended** | `CAP_GRADIENT` `CAP_DASH` `CAP_CLIP_PATH` | Skia 级必须；Raster **可降级近似** | Skia ✅✅✅ / Raster ✅✅❌ |
| **Optional** | `CAP_PATH` `CAP_IMAGE` `CAP_SHADOW` `CAP_LAYER` | 仅 Skia 级 | Skia ✅✅✅✅ / Raster ❌❌❌❌ |

`RasterCanvas` 的六个响亮失败点（`:424-449`）：

| 行 | op | 报的档 |
|---|---|---|
| `:424` | `drawPath` | **Optional** |
| `:429` | `drawImage` | Optional |
| `:434` | `drawShadow` | Optional |
| `:439` | `pushLayer` | Optional |
| `:444` | `popLayer` | Optional |
| `:449` | `pushClipPath` | **Extended** |

★ **第 6 行是矛盾**：`pushClipPath` 被标为 Extended（"Raster 允许降级近似"），
但 Raster 的 `capabilities()`（`:221-228`）**没有置** `CAP_CLIP_PATH`，且实现在
`:449` 直接报 `E-OP-UNSUPPORTED` ⇒ **Extended 层有一个硬缺口**。

这不是"没做完"，是**分档与实现不一致**：档位说"可以近似"，实现说"完全不支持"。

### 1.2 Optional 层的消费者只有 1 个，而且是 demo 页

```bash
for op in drawPath pushClipPath drawImage drawShadow pushLayer drawEllipse drawLine; do
  grep -rn -e "->$op(" --include=*.php src/ apps/ | grep -v "Rendering/" | wc -l

```

| op | 生产（`src/`）调用 | 应用（`apps/`）调用 |
|---|---|---|
| `drawEllipse` | 6 | 1 |
| `drawLine` | 6 | 1 |
| `drawPath` | **0** | **1**（`CustomPaintPage.php`） |
| `pushClipPath` | **0** | **1** |
| `drawImage` | **0** | **1** |
| `drawShadow` | **0** | **1** |
| `pushLayer` | **0** | **1** |

⇒ **Optional 五个 op 的全部消费者是 `apps/showcase/src/Pages/CustomPaintPage.php` 一个 demo 页。**
`src/` 里零消费者。

★ 这条事实决定了两件事：
1. **不能把 Optional 当成"已交付的能力"** —— 它是"Skia 侧跑通、有 demo 证明"的能力
2. **分级该按"谁在用"重划**：`drawPath` 是"控件自绘"的需要（下一个消费者已经在门口），
   其余四个是"某个控件将来的需要"（`Image` 控件、阴影装饰、透明度动画）

### 1.3 `translate()` 只改 PHP 侧偏移，从不调 Skia

这是 P4 踩过的坑，值得写成**绘制契约**（`Canvas.php:44` 的 docblock 已有，但太轻）：

```php
public function translate(float $dx, float $dy): void;
```

**它的语义是"改 PHP 侧的偏移累加器"，不是"给 Skia 发 translate 命令"。**
所以每个 draw 方法必须**自己**把偏移加进坐标：

| 方法 | 怎么用偏移 |
|---|---|
| `drawLine` | 手加（`$x1 + $this->offsetX`） |
| `drawRect` / `drawEllipse` | 走 `toDevice()` 转矩形 |
| `drawPath` | ★ **必须逐点平移后再打包**（P4 踩过：照"几何走画布 translate()"写 ⇒ 落在画布原点、被盒裁掉 ⇒ 真机完全无墨而解释器全过） |

★ **本册新增的 `drawPath` 在 Raster 上不涉及这个问题**（Raster 是纯 PHP 软光栅，
`translate()` 就是改自己的偏移），但 **Skia 侧已有实现必须复核**：`SkiaCanvas::drawPath`
是否逐点平移了。这是 §8 破坏清单里的一条"必须查"。

### 1.4 每帧全量重录

`RenderSurface::beginFrame()` 每次返回的画布状态是**新的一帧**：

- `RasterCanvas` 每次清屏 + 逐 op 画
- `SkiaCanvas` 每次 `sk_canvas_clear` + 逐 op 转 Skia 调用
- `DisplayList` 被 `RenderText` / `RenderTextField` 复用（`$this->list ??= new DisplayList(); $this->list->reset();`）
  —— **只在这两处**，其余 op 直接进画布

⇒ 现状是 **immediate mode**：没有 retained 命令段，每帧重新录。

### 1.5 动画：每 tick 一次 `markDirty()`，走完整重建

`AnimationController` 的 docblock 示例（`:19-29`）：

```php
public function tickFrame(float $timestampMs): bool
{
    $busy = $this->fade->tick($timestampMs);
    if ($busy) {
        $this->markDirty();
    }
    return $busy;
}
```

一次 tick 的完整链路：

```
markDirty → settle: rebuild → build() 造新 Widget
          → updateChildren: 同类型同 key ⇒ 复用 Element，调 update()
          → Element::update(): syncBox() 造**新盒**（:196 "新描述 ⇒ 新盒"）
          → 全树 layout（§13.3：Render 层全树重排）
          → 全树 paint（每帧重录）
```

★ **`syncBox()` 那句注释是整条链的关键**：`Element::update()`（`:192-199`）

```php
$this->widget = $newWidget;
$this->widget->seal();
$this->syncBox(); // §13.2：新描述 ⇒ 新盒
$this->didUpdateWidget($newWidget);
$this->rebuild();
```

⇒ 一次动画 tick = **一个新 `RenderBox` 对象** + 一次全树重排。
动画的每一帧都在做"结构变更级别"的工作，而它实际改的只是**一个 float**。

### 1.7 W8（栈配平断言）有两个盲区

`DisplayList::assertBalanced()`（`:142-153`）是 W8 的落地：录制结束时
`saveDepth` 与 `clipDepth` 都必须为 0。它守住了 `save/restore` 与 `pushClip/popClip`。

但计数点只有四处（`record()` `:95-104`）：

```php
if ($op === self::OP_SAVE)            { $this->saveDepth++; }
elseif ($op === self::OP_RESTORE)     { $this->saveDepth--; }
elseif ($op === self::OP_PUSH_CLIP)   { $this->clipDepth++; }
elseif ($op === self::OP_POP_CLIP)    { $this->clipDepth--; }
```

| 盲区 | 后果 |
|---|---|
| **`OP_PUSH_CLIP_PATH` 不计数** | `pushClipPath()` 后漏 `popClip()` ⇒ `clipDepth` 仍为 0 ⇒ **W8 抓不到**，后续全部被裁 |
| **`OP_LAYER_PUSH` / `OP_LAYER_POP` 完全不计数** | 层深不配平 ⇒ 下一帧复用缓冲时带上未闭合的层（`Canvas.php:131` 明写"W8 的配平断言**不**覆盖层深"） |

★ 第二个盲区现在是**不可达**的（`pushLayer` 只在 `CustomPaintPage` 里用一次且配对），
第一个盲区在 `pushClipPath` 落地（§4）之后**立刻可达**。

⇒ 本册把这两个计数补上（§8）。这是"补一个新 op 时，必须同时补它的**记账**"这条纪律的
直接兑现 —— 新 op 不只是 `RasterCanvas` 里多一个方法。

## 2. 两个后端要不要一样强

### 2.1 "一强一弱"的三种坏法

| 坏法 | 症状 | 现在会发生吗 |
|---|---|---|
| **① 静默丢像素** | 真机上"矩形全对、内容没了" | ❌ 不会（`E-OP-UNSUPPORTED` 响亮失败） |
| **② 产品表现力迁就测试工具** | 控件为了能在 Raster 上跑，只用 `drawRect` 拼形状 | ✅ **正在发生**（`02` §1 的"控件自绘被锁死在 Core"） |
| **③ 测试与真机走不同代码路径** | golden 在 Raster 上过、真机是另一套 | ✅ 部分（Extended 的渐变：Raster 逐像素实渐变 vs Skia 真渐变） |

② 是真正要解决的问题。③ 已有缓解（golden 只用 Core，P3/P4 用结构 golden）。

### 2.2 判据

> **同一份生产代码，在两个后端上要么产出同样的像素，要么同样响亮失败。**
> 不允许"一个画出来、一个不画"；也不允许"为了能画出来，代码里写 `if (Raster)`"。

★ 这条判据的三个推论：

| # | 推论 |
|---|---|
| 1 | **控件代码里不许出现 `instanceof RasterCanvas`** —— 那是 ② 的直接形态。加 lint（§2.5） |
| 2 | **Extended 层不许有缺口**（现在是它有的：`pushClipPath`） |
| 3 | **Optional 层允许缺口，但控件必须先查能力位并给出替代呈现**（不是"报错给用户"） |

### 2.3 分级要按"谁在用"重划

| op | 现在的档 | 谁需要它 | 应该的档 |
|---|---|---|---|
| `drawEllipse` | Core | 6 处 `src/` | Core（不变） |
| `drawLine` | Core | 6 处 `src/`（勾选标记就是两条线段） | Core（不变） |
| `GRADIENT` | Extended | `CustomPaintPage` + `Paint::withGradient` | Extended（不变） |
| `DASH` | Extended | `CustomPaintPage` + `Paint::withDash` | Extended（不变） |
| `pushClipPath` | Extended | 圆角之外的任意形状裁剪（`Stack` + 圆形头像） | Extended（不变，**但 Raster 必须补**） |
| **`drawPath`** | **Optional** | **控件自绘**（图标、勾、箭头、任意形状）—— `02` §5 的八原语里 `CustomPaint` 是唯一出口 | **Extended**（★ 提档） |
| `drawImage` | Optional | 将来的 `Image` 控件（现在没有） | Optional（不变） |
| `drawShadow` | Optional | 卡片阴影（现在 `RenderCard` 用 `drawRect` + 圆角模拟） | Optional（不变） |
| **`LAYER`** | **Optional** | **`Opacity` 动画（§5）** —— 它已经是 `Modifier` 的合成维字段，消费者就是下一批控件 | **Extended**（★ 提档） |

★ **`drawPath` 提档的理由**：Extended 的定义是"Skia 级必须、Raster 可降级近似"。
`drawPath` 没有"近似"的余地（路径就是路径），所以它不能是 Extended。
但它的**消费者已经是控件自绘**，所以它也不能是 Optional（Optional 的定义是"仅 Skia 级"）。

⇒ 三档不够用。**真正的分档判据是"缺了它，控件能不能只用别的 op 画出来"**：

| 判据 | 档 |
|---|---|
| 缺了它，任何控件都画不出来 | **Core** |
| 缺了它，某类控件只能退化成难看的替代（勾用两条线段代替路径），或某类**动画效果**根本做不出 | **Extended** |
| 缺了它，某类控件根本不存在（没有 `Image` 控件就没有 `drawImage` 的消费者） | **Optional** |

按这条判据：`drawPath` 属 **Extended**（勾、箭头、图标都能用线段拼，但难看）。
`pushClipPath` 属 **Extended**（圆角矩形能拼，圆形裁剪拼不出）。
`LAYER` 属 **Extended**（没有它，`opacity` 只能靠"改每个 `Paint` 的 alpha"——
那是控件自己算，等于每个控件重写一遍层语义；而 Raster 用"alpha 乘数栈"**能近似**）。
`drawImage` / `drawShadow` 属 **Optional**（没有 `Image` 控件；阴影能用边框 + 圆角拼）。

### 2.4 Raster 补什么、不补什么

| op | 补吗 | 理由 |
|---|---|---|
| `drawPath` | **补**（§3） | 提到 Extended ⇒ Extended 不许有缺口；且它是控件自绘的出口 |
| `pushClipPath` | **补**（§4） | 已在 Extended ⇒ 现在有缺口，是缺陷 |
| `pushLayer` / `popLayer` | **补**（§5.6） | 提到 Extended；实现是 **alpha 乘数栈**（约 20 行），近似而非真离屏 |
| `drawImage` | **不补** | Optional；没有 `Image` 控件 ⇒ 没有消费者。补了就是"为一个不存在的控件写 800 行" |
| `drawShadow` | **不补** | Optional；W5 之后阴影走 `Modifier::paintBehind()` 的三层递减圆角矩形（`02` §3.4，逐字搬自 `RenderCard::paint`），Core 层 `drawRect` 就够 |

★ **不补的两个 op 必须"两边行为一致地响亮失败"吗？** 不。它们的消费者在 `src/` 里是 0，
所以"一强一弱"没有现实后果。但**必须满足判据的三个推论**：
- 推论 1：控件不许 `instanceof RasterCanvas` ⇒ lint
- 推论 3：控件要画阴影/图片时，先查能力位，没有就换一种呈现

### 2.5 新增两条 lint

| 代号 | 判据 | 为什么 |
|---|---|---|
| `backend-branch`（G2） | `src/Widget/**` 与 `src/Layout/**` 里不许出现 `RasterCanvas` / `SkiaCanvas` / `RecordingCanvas` 的类型名 | 判据推论 1；现在是 0 违规，但没人守 |
| `optional-op-guard`（G2） | 发起 Optional 层的 op（`drawImage` / `drawShadow`）之前，同一个方法体内必须出现 `capabilities()` 调用 | 判据推论 3；防止"在 Raster 上跑控件就炸" |

★ `optional-op-guard` 的**误报风险**是"跨方法查能力位"（在 `init()` 里查一次、
在 `paint()` 里用）。处置：判据放宽到"**同类内**出现过 `capabilities()`"，
不做跨方法数据流。宁漏不误响。

## 3. `RasterCanvas::drawPath`（扫描线填充 + 描边）

### 3.1 为什么是扫描线，不是泛洪

`RasterCanvas` 已有两套像素化算法：`rasterize()` 的区间法（矩形 / 圆角矩形）与
`drawEllipse` 的逐行谓词法。路径没有解析式谓词 ⇒ 只能：

| 方案 | 代价 | 判定 |
|---|---|---|
| **扫描线**（按 y 求与路径边的交点，排序后成对填区间） | `O(边数 × 行数)`，且**每行只填连续区间** ⇒ 与矩形同一条填色路径 | ✅ |
| 泛洪填充（从种子点扩散） | 需要"判断点在多边形内"的谓词 + 会漏（细长形状） | ❌ |
| 逐像素射线法 | `O(宽 × 高 × 边数)` —— 1080p 下 200 万 × 边数，不可接受 | ❌ |

★ 扫描线的实现要点：**边表按 y 排序 + 活性边表**，避免每行重扫全部边。
`Path` 的 verbs 已经是一条条 `MOVE/LINE/QUAD/CUBIC/CLOSE`（`Path.php` 104 行），
先**扁平化成线段表**（贝塞尔按固定段数采样），再做扫描线。

### 3.2 奇偶 vs 非零环绕

| 规则 | 语义 | 选它吗 |
|---|---|---|
| **奇偶**（even-odd） | 射线穿越次数为奇 ⇒ 内部 | ✅ 默认 |
| **非零环绕**（nonzero） | 环绕数 ≠ 0 ⇒ 内部 | 需要方向信息 |

**选奇偶**，理由：`Path` 现在**不记录方向**（verbs 只有点位，没有 winding）。
非零环绕需要"每个子路径的方向 + 交叉计数"，那要改 `Path` 的数据格式 ⇒ 破坏面变大。
而奇偶对 99% 的实际路径（图标、箭头、勾）结果相同。

★ 写进 `Path` 的 docblock：**"重叠子路径按奇偶规则"**。要"挖洞"就用两个反向子路径
（奇偶天然支持），不要指望非零环绕。

### 3.3 抗锯齿：不做

现有 `drawRect` / `drawEllipse` 都是**硬边**（像素中心谓词，无覆盖率）。
`drawPath` 保持一致 ⇒ 三个形状在同一张图上边缘风格统一。

★ 做抗锯齿的正确位置是**整个光栅层的超采样**（2× 渲染再降采样），不是单个 op 的
边缘羽化。那是 `05` 之外的事（属性能优化），记在 §13。

### 3.4 描边：路径偏移，不是"画粗线"

| 方案 | 做法 | 判定 |
|---|---|---|
| **路径偏移**（stroke → 填充） | 每条边向外/向内偏移 `w/2`，接缝按 join 类型补 | ✅ 与 `drawRect` 的"外减内收半宽"同口径（`drawEllipse` 注释已写明） |
| 画粗线（沿路径逐段画 `w` 宽的矩形） | 接缝处会重叠 / 有缝 | ❌ 斜接处视觉错 |

★ **只实现 `Miter` join + `Butt` cap**（最简单、无接缝）。`Round` / `Bevel` 记在 §13 不做。
理由：`drawPath` 的第一批消费者是图标（勾、箭头），它们的拐角都是尖的。

### 3.5 成本上界

| 输入 | 估算 |
|---|---|
| 一个 24×24 的勾（3 段线段） | 24 行 × 3 边 = 72 次交点计算 ≈ 微秒级 |
| 一个 200×200 的复杂图标（100 边） | 200 行 × 100 边 = 2 万次 ≈ 0.2ms |
| 一个 1000×1000 的装饰图形（500 边） | 50 万次 ≈ 5ms ⇒ **超帧预算** |

⇒ **加一条上界检查**：`边数 × 行数 > 200_000` ⇒ `Errors::report` DIAGNOSTIC
（"这个路径的扫描线成本超预算，考虑简化路径或用 `drawImage`"）。不中止（Raster 是测试后端，
慢一点可以接受），但要留痕。

## 4. `RasterCanvas::pushClipPath`（每行 x 区间掩码）

### 4.1 与 `pushClip(Rect)` 的区别

| | `pushClip(Rect)` | `pushClipPath(Path)` |
|---|---|---|
| 语义 | 矩形裁剪 | 任意形状裁剪 |
| 实现 | **矩形求交**（`$this->clip = $this->clip->intersect($rect)`） | **每行 x 区间表** |
| 代价 | O(1) | O(行数) 构建 + O(1) 每像素查表 |
| 类比 | Skia 的 scissor（免费） | Skia 的 clipPath（要开层，贵 100×） |

★ 这就是 `CanvasCapabilities` 注释里说的"`CLIP_RECT` 与 `CLIP_PATH` 故意分开
（scissor 免费 vs 开层贵 100×）"。

### 4.2 掩码方案

```
pushClipPath($path):
  ① 扁平化路径 → 线段表
  ② 对裁剪区内的每一行 y：求交点，排序成对，得到 list<[x0, x1]>
  ③ 存进栈（与 clip 一样是栈：pushClipPath / popClip 配对）
  ④ 之后每个 fill 的每行像素：先与 ② 的区间求交，再填
```

★ **复用 §3.1 的扫描线**：`drawPath` 求出的区间表和 `pushClipPath` 的掩码是**同一个函数**。
一次实现，两处用 —— 这是"提档 `drawPath`"的附带收益。

### 4.3 栈的配对

`Canvas` 接口的栈语义是 `save/restore` + `pushClip/popClip` **两套**。
`pushClipPath` 必须与 `popClip` 配对（不是新的 `popClipPath`），与 Skia 的 `save/restore` 一致。

★ **配对错误是静默的**（多 push 一次 ⇒ 后面全被裁）。`RecordingCanvas` 已经有栈深度检查？
若没有，本册加一条：`restore()` 时栈深 < 0 ⇒ `Errors::report`（不是静默 return）。

## 5. 合成与动画：让动画不必重排

### 5.1 动画改的是什么

| 动画 | 改的字段 | 需要重排吗 |
|---|---|---|
| 进度条数值 | `Progress::$value` → 盒子尺寸变化 | **要**（尺寸变了） |
| 淡入淡出 | `opacity` | **不要**（几何没变） |
| 滑入滑出 | `translateX/Y` | **不要**（几何没变，只是偏移） |
| 展开/收起 | 高度 | **要**（尺寸变了） |
| 颜色过渡 | `Paint` 的颜色 | **不要**（几何没变） |

⇒ **四类动画里只有两类需要重排**。而现状是**五类全都要**（因为都走 `markDirty → rebuild`）。

### 5.2 三个脏位的代价差

抄 v6 `05` §3 的量级（它是实测值，我们没有同等精度的数，但**比例关系**是可推的）：

| 脏位 | 改了什么 | 需要做的事 | 相对代价 |
|---|---|---|---|
| `D_PAINT` | 颜色 / 画笔 | 重录这一棵子树 | 1× |
| `D_COMPOSE` | 矩阵 / 不透明度 | 重录 + 重新合成 | **~3×** |
| `D_LAYOUT` | 尺寸 / 间距 | 重排 + 重录 + 合成 | **~100×** |

★ 为什么 `D_LAYOUT` 是 100×：一次 `layout()` 会**递归整棵子树**（`O(节点数)`），
而重录一个叶子是 `O(1)` 条命令。100 这个数来自"平均子树规模"。

★ 为什么 `D_COMPOSE` 是 3× 而不是 1×：`opacity < 1` 要**开层**（离屏缓冲 + 合成），
那是"分配一块像素 + 两次 blit"。

### 5.3 现状：`opacity` / `translate` 都走 `D_LAYOUT`

`02` 的 `Modifier` 已经有 `opacity` / `translateX` / `translateY` 三个字段（合成维）。
但在现状的"新描述 ⇒ 新盒"下：

```
Modifier 变了（值对象换新）→ 新 Widget → Element::update() → syncBox() 造新盒 → 全树 layout
```

⇒ **值对象式修饰 + "新描述 ⇒ 新盒" = 动画仍然换盒。** 这是 `02` 与 `05` 之间的一个真接缝，
必须在这里说清。

### 5.4 `D_COMPOSE` 路径的形状

三步，缺一不可：

**第一步：动画参数住盒上的可变字段，不住 Widget。**

```php
// src/Layout/RenderBox.php
private float $composeOpacity = 1.0;
private float $composeDx = 0.0;
private float $composeDy = 0.0;

/**
 * 就地改合成参数（**不重建盒、不重排**）。
 *
 * ★ 为什么允许"可变字段"破坏 `02` 的值对象纪律：值对象管的是**描述**
 *   （Widget 层，不可变），这里管的是**每帧都在变的动画量**（Render 层）。
 *   两者的失效频率差三个数量级 —— 让动画量走值对象，等于每帧造一个新盒。
 */
public function setCompose(float $opacity, float $dx, float $dy): void
{
    $this->composeOpacity = $opacity;
    $this->composeDx = $dx;
    $this->composeDy = $dy;
    $this->composeDirty = true;      // ★ 只置合成脏，不置布局脏
}
```

**第二步：`State` 直接写盒，不经过 rebuild。**

```php
// 应用代码（淡入）
public function tickFrame(float $timestampMs): bool
{
    $busy = $this->fade->tick($timestampMs);
    if (!$busy) {
        return false;
    }

    // ★ 不 markDirty()：直接改盒的合成参数
    $this->element()?->renderObject()?->setCompose($this->fade->value(), 0.0, 0.0);

    return true;
}
```

**第三步：`Frame::run` 跳过 layout。**

```php
$didRebuild = $root->settle();          // ★ settle 返回"本帧有没有 rebuild 过"
$popup?->settle();

if ($didRebuild || !$constraints->equals($this->lastConstraints)) {
    $box->layout($constraints);
    $this->lastConstraints = $constraints;
}
// 否则：盒的 size 与子 offset 还是上一帧算的，且没东西变 ⇒ 跳过（§5.5 证明这是对的）
```

★ **第三步的正确性依据是 `04` §5.2 的布局自校验**：它证明了 `layout()` 是纯函数
（同样输入 ⇒ 同样输出）。所以"没 rebuild + 约束没变 ⇒ 跳过 layout"**等价于**重算。
`04` 说"先证明纯，才有资格说不缓存" —— 这里兑现。

★ 若将来某个 `performLayout` 破了纯（读了 `$this->size`），自校验会在 64 帧内抓到，
而"跳过 layout"会**放大**那个错误（从"轻微漂移"变成"完全不更新"）。
⇒ **自校验必须先于跳过 layout 上线**（迁移顺序见 §9）。

### 5.5 为什么变换不开层、`opacity < 1` 自动开层

| 情形 | 开层吗 | 理由 |
|---|---|---|
| `translate(dx, dy)` | **不开** | 平移是**坐标加法**，把 `dx/dy` 加进每个 draw 的坐标即可。开层是"分配一整块像素"，为一次加法付这个代价不划算 |
| `opacity < 1` | **开** | 不透明度是**逐像素乘法**，必须在"子树已经画完"之后才能乘（否则子与子重叠处会被乘两次） |

★ 这条与 `01` §5 的"绘制顺序即层叠"是同一套推理：**能靠坐标解决的，不靠层**。

### 5.6 `opacity` 在 Raster 上怎么办：alpha 乘数栈

`pushLayer` / `popLayer` 提到 Extended（§2.3）⇒ Raster 必须实现。**不做真离屏**，做乘数栈：

```php
// RasterCanvas
/** @var list<float> 层不透明度栈；栈顶 = 当前生效的乘数（空栈 ⇒ 1.0） */
private array $layerAlpha = [];

public function pushLayer(float $opacity): void
{
    $top = $this->layerAlpha === [] ? 1.0 : $this->layerAlpha[count($this->layerAlpha) - 1];
    $this->layerAlpha[] = $top * max(0.0, min(1.0, $opacity));
}

public function popLayer(): void
{
    if ($this->layerAlpha === []) {
        return;   // 未配对：W8 的 layerDepth 断言负责（§1.7）
    }
    array_pop($this->layerAlpha);
}
```

之后每个 fill / stroke 在算颜色时把 `$a` 乘上栈顶值。

| 项 | 真离屏（Skia） | 乘数栈（Raster） |
|---|---|---|
| 代码量 | 已有 | **约 20 行** |
| 重叠子 | 先合成再乘一次 | **每个 draw 各乘一次** ⇒ 重叠处更透 |
| 内存 | 一块离屏缓冲 | **零** |
| 判定 | 正确 | **近似**（正是 Extended 的定义） |

★ 写进 docblock："Raster 的层不透明度是**逐 draw 乘 alpha**，重叠子之间会重复相乘，
视觉上更透明；Skia 是真离屏合成。" 并在 smoke 里把这条差异**钉住**（§12.2 #9）。

★ **为什么不做真离屏**：纯 PHP 里一块 1080p 的 RGBA 缓冲是 `array<int,int>`（约 200 万个
元素）⇒ 内存与 GC 压力远超这 20 行的收益。而"重叠子更透"在 90% 的动画里看不出来
（动画通常是整块淡入淡出，内部没有重叠子）。

## 6. 每帧全量重录：取舍写清楚

### 6.1 现状

immediate mode：每帧从 `beginFrame()` 开始重录所有 op。

| 项 | 现状 |
|---|---|
| 命令段 | 不存在（没有 retained 结构） |
| 重录范围 | 全树 |
| 光栅范围 | 全屏（`SetDIBitsToDevice` 一次拷贝） |
| 端到端 | **3.1ms**（M4 真机，含 settle/layout/paint/present） |

### 6.2 为什么不做 retained 命令段

`00` §5 已判。补本册视角的三条：

| # | 理由 |
|---|---|
| ① | v6 的 `ops` packed array 前提是"命令段长期住在节点上"（retained mode）。Drift2 的 Widget 每帧新建、盒每帧可能换新 ⇒ 命令段的宿主不存在 |
| ② | 3.1ms 有 5.3× 余量（60fps 预算 16.7ms）。**余量足够时优化是负收益**（复杂度换不来用户可感知的改善） |
| ③ | retained 的失效逻辑正是 v6 要造自校验来兜的那一类（"哪条命令该重录"）。我们连脏位系统都没有，加 retained 等于同时加两套失效逻辑 |

★ **触发条件写死**：单帧 > 8ms 连续 10 帧 ⇒ 才考虑。这条与 `00` §5 一致。

### 6.3 脏区光栅也不做

同上。理由：`SetDIBitsToDevice` 已经是驱动侧的整块拷贝，脏区只能省 CPU 的绘制部分，
而 3.1ms 里绘制部分不是大头（present 才是）。**先把 present 之外的部分压到 2ms 以下再说。**

| 10 | `setCompose` 不触发 layout | 调 `setCompose` 后 `layout` 调用计数不变 |

| 12 | 纯动画帧跳过 layout | 一帧只有 `setCompose` ⇒ `layout` 调用 0 次，`paint` 仍执行 |

★ 第 9 条是**记录近似**，不是断言正确 —— 它的价值是"把这个已知差异钉住"，
将来有人改 Raster 的 opacity 实现，夹具会提醒他这条差异是有意的。

★ 最后一条是关键：**`CustomPaintPage` 现在只能在 Skia 上跑**（`drawPath` 等 5 个 op 全失败）。

`optional-op-guard` 要抓的（demo 页可以豁免，但要有 `capabilities()` 判定）。

## 13. 备选方案与否决

| 备选 | 否决理由 |
|---|---|
| **retained 命令段（v6 `ops` packed array）** | §6.2 三条；触发条件写死 |
| **脏区光栅** | §6.3；present 才是大头 |
| **Raster 补 `drawImage`** | 没有 `Image` 控件 ⇒ 没有消费者（§2.4） |
| **Raster 的 `pushLayer` 做真离屏缓冲** | 纯 PHP 里是 `array<int,int>`（1080p 约 200 万元素），内存与 GC 压力远超收益；用 alpha 乘数栈近似（§5.6） |
| **`drawPath` 用非零环绕** | `Path` 不记方向（§3.2） |
| **`drawPath` 做抗锯齿** | 与 `drawRect`/`drawEllipse` 硬边不一致；正确位置是整层超采样（§3.3） |
| **`Round` / `Bevel` join** | 第一批消费者是图标，拐角都是尖的（§3.4） |
| **给 Raster 加 `Degraded` 档** | `ARCH-REVIEW` A3 已否决：那是"产品表现力迁就测试工具"（§2.2 坏法 ②） |
| **控件里 `instanceof RasterCanvas` 分叉** | 判据推论 1；lint `backend-branch` 守 |
| **`Frame::run` 无条件跳过 layout** | 必须有"无 rebuild + 约束没变"两个条件（§5.4 第三步） |

### 推翻条件

| 裁决 | 什么情况下推翻 |
|---|---|
| 不做 retained 命令段 | 单帧 > 8ms 连续 10 帧 |
| 不做脏区光栅 | 同上，且 present 已压到 1ms 以下 |
| Raster 不补 `drawImage` | 出现 `Image` 控件 ⇒ 那时按同一套扫描线思路补（图片不需要扫描线，是逐像素 blit） |
| `opacity` 用乘数栈近似 | 出现"重叠子透明度必须准确"的真实需求 ⇒ 那时才把 Raster 的 `pushLayer` 改成真离屏 |
| `drawPath` 奇偶规则 | 出现"必须挖洞且奇偶做不到"的路径 ⇒ 那时才给 `Path` 加方向 |
| 跳过 layout | `04` 的自校验在真机上抓到 `mismatches > 0` ⇒ **立即回退这一步** |
