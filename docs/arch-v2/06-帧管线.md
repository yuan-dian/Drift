## 0. 一句话

**九段的分组是对的，但那条分组只写在注释里；"超预算先牺牲什么"完全没做。**

| 现状 | 判定 |
|---|---|
| `Application::frame()` 九段，注释里写清了"顺序不重要，都在 settle 之前才重要" | ✅ **判据是对的** —— 本册把它变成机制 |
| 三组（前置产脏 / 核心消费 / 后置观察新树） | ✅ 已经存在，只是没名字 |
| `SurfaceProfile` 分段计时 | ✅ 有，默认关 |

| **降级顺序** | ❌ 没有（连文档都没有） |

## 1. 现状：九段的真实形状

### 1.1 顺序表（`Application::frame()` `:1001-1093`）

| # | 段 | 行 | 作用 | 会产脏吗 |
|---|---|---|---|---|
| 0 | `assertUiThread('frame')` | `:1010` | 帧必须在 UI 线程 | — |
| 0b | `$this->frameSerial++` | `:1016` | 帧序号（`tickFrameStamped` 幂等 + `03` 的 `noteRebuilt`） | — |
| **①** | `pumpIo()` | `:1023` | 非阻塞 IO 回调 | **会** |
| **②** | `pumpTasks()` | `:1033` | 后台任务结果 | **会** |
| **③** | `pumpSliced()` | `:1043` | 分片任务完成 | **会** |
| **④** | `tickAnimations()` | `:1052` | 推进动画 → `$this->animating` | **会** |
| **⑤** | `placeMenu()` | `:1058` | 浮层布局（无界自尺寸 + 钉锚点 + 夹客户区） | 不产脏（只排盒） |
| **⑥** | `Frame::run()` | `:1062` | settle → layout → paint → present | **消费脏** |
| **⑦** | 迟到挂载补 tick | `:1079` | 第二次 `tickAnimations()` | **会**（但同帧幂等） |
| **⑧** | `focus->collect()` | `:1086` | 重建焦点链（含浮层第二棵树） | 不改树 |
| **⑨** | `pumpSemantics()` | `:1092` | 语义树推 UIA | 不改树 |

★ 加上 `Frame::run()` 内部四步，一共 **12 个动作**。`00` 说的"9 个泵"是 ①–⑨ 的口径。

### 1.2 唯一真正的不变式

代码自己的注释（`:1041-1042`）：

> 顺序（结果 → 分片 → settle）不重要，**都在 settle 之前**才重要。

这句是**对的**，而且它比"九段顺序"重要得多。展开成三条：

| # | 不变式 | 违反的症状 |
|---|---|---|
| **I1** | 所有**会产脏**的段都在 `settle` **之前** | 慢一帧。`loading → ready` 会闪一帧空（注释 `:1029-1031` 写明） |
| **I2** | 所有**观察新树**的段都在 `settle` **之后** | 焦点链握着已被移除的 Element ⇒ 按键静默丢给死节点（`:1083-1085` 写明） |
| **I3** | `present` 是本帧**最后一个**动屏幕的动作 | 半帧画面 |

⇒ **九段的相对顺序里，只有跨过 `settle` 的那条界线是硬约束。**
①–④ 之间、⑦–⑨ 之间可以任意换序。

### 1.3 三条被注释守着的约束（无机制）

| 约束 | 守它的东西 |
|---|---|
| ①–④ 必须在 `Frame::run()` 之前 | 一句 `★` 注释 + 调用位置 |
| ⑧⑨ 必须在 `Frame::run()` 之后 | 同上 |
| `tickSubtree()` **不许短路**（`:1229-1231`：否则多个 Spinner 只有一个转） | 一句 `★` 注释 |

⇒ 任何人把 `pumpTasks()` 挪到 `frame->run()` 之后，**编译过、lint 过、smoke 过**
（因为 smoke 手动驱动帧序列，不测"段顺序"），只在真机上表现为"慢一帧"。

★ 这是 `07-可检查性.md` 的第一类问题的典型：**"忘写"没法用 lint 抓，因为它是"挪了一行"。**

### 1.4 `tickAnimations()` 每帧走两遍全树

`tickAnimations()`（`:1209-1224`）遍历主树 + 浮层树。调用点两处：

```php
// ④ 第一次：settle 之前
$this->animating = $this->tickAnimations($timestampMs);

// … Frame::run() …

// ⑦ 第二次：settle 之后
$this->animating = $this->animating || $this->tickAnimations($timestampMs);
```

**为什么需要第二遍**（`:1064-1077` 的注释，2026-10-20 修的真实框架洞）：

> ④ 在 settle **之前**跑，而页面挂载发生在 `Frame::run()` 的 settle 段 —— 于是
> "这一帧刚挂上的页"的 State 在 ④ 时还不在树里、从未被 `tickFrame()` 访问 ⇒
> `$animating` 当帧永远是 false ⇒ `wantsFrame()` 返回 false ⇒ 帧时钟不重新上膛 ⇒
> **之后没鼠标事件就永远静止**（Spinner / 自绘页同病，真机探针抓到）。

⇒ 这是一个**结构性必需**的补丁（不是懒），但它用"再走一遍全树"实现，
代价是 **每帧 2 × O(节点数)** 的指针追逐。

| 项 | 现状 |
|---|---|
| 每帧 `tickSubtree` 调用次数 | 2 ×（主树 + 浮层树） |
| 每次的节点数 | 树规模（`apps/users` 约 300–800） |
| 真实收益的调用 | **只在"这一帧有 State 刚挂载"时**才有 |
| 浪费 | 其余 99% 的帧，第二遍**什么都没做**，只是走了一遍 |

### 1.5 `pumpSemantics()` 每帧全量

`:1199-1207`：

```php
private function pumpSemantics(): void
{
    $sink = $this->semanticsSink;
    if ($sink === null) {
        return;                    // ★ 无 sink ⇒ 不建，零开销
    }
    $tree = SemanticsBuilder::build($this->root, $this->focus?->focused());
    ($sink)($tree->toArrays()['nodes']);
}
```

★ 前半句是好的（无 sink 零开销）。后半句是问题：**有 sink 时每帧全量构建 + 全量序列化 + 全量推送**。
`SemanticsBuilder::build()` 是 O(树)，`toArrays()['nodes']` 造一个巨大的 PHP 数组。

⇒ 这是九段里**唯一一段"省了不影响正确性"的**（只影响读屏实时性）。降级的唯一落点就在这（§3.4）。

### 1.6 没有帧预算，只有测量

| 有什么 | 缺什么 |
|---|---|
| `SurfaceProfile::$on`（默认关）+ `add($key, $elapsedNs)` | 没有"本帧总耗时"的聚合 |
| `FrameClock::stallCount()` / `worstGapMs()`（卡顿观测） | 卡顿只能**事后**看，不能**当帧**降级 |
| `SlicedJob::step(int $budgetMs)`（框架给分片任务预算） | 帧本身没有预算 |

⇒ 现状是"**测得很细，但超了什么都不做**"。

★ 这**不算缺陷**：M4 真机端到端 3.1ms，60fps 预算 16.7ms ⇒ **5.3× 余量**。
但"超预算时牺牲什么"是一个**设计决策**，必须在需要它的那一天之前定下来，
否则那天会在压力下随手砍掉不该砍的东西。

### 1.7 量化

| 指标 | 实测 |
|---|---|
| `Application::frame()` 行数 | 约 92（`:1001-1093`） |
| 段数 | **9**（含两次 tick） |
| 硬约束 | **3 条**（I1/I2/I3），全部靠注释守 |

## 2. 阶段表：把注释变成机制

### 2.1 三组九段

```
┌─ 组 A：产脏（必须在 settle 之前） ────────────────────────┐
│  ① pumpIo   ② pumpTasks   ③ pumpSliced   ④ tickAnimations │
└───────────────────────────────────────────────────────────┘
                          ↓
┌─ 组 B：核心（消费脏） ─────────────────────────────────────┐
│  ⑤ placeMenu   ⑥ Frame::run(settle → layout → paint → present) │
└───────────────────────────────────────────────────────────┘
                          ↓
┌─ 组 C：观察新树（必须在 settle 之后） ─────────────────────┐
│  ⑦ 补 tick   ⑧ focus.collect   ⑨ pumpSemantics            │
└───────────────────────────────────────────────────────────┘
```

| 组 | 组内顺序 | 组间顺序 | 依据 |
|---|---|---|---|
| **A** | **任意** | 必须全在 B 之前 | I1 |
| **B** | **固定**（placeMenu → settle → layout → paint → present） | 在 A 之后、C 之前 | `Frame::run()` 的四步本身是硬序 |
| **C** | **任意** | 必须全在 B 之后 | I2 |

★ **为什么 A 组内可以任意**：四个泵都只做"调回调"，回调里只 `setState`/`markDirty`
（不读树、不读布局）。它们之间没有数据依赖 —— `pumpIo` 的回调不会读 `pumpTasks` 的结果，
因为两者写的是不同的 `State`。

★ **为什么 C 组内可以任意**：三个都只读新树，互不写。
`focus.collect` 与 `pumpSemantics` 之间有顺序（语义树要带焦点），但那是**数据**依赖
（`pumpSemantics` 读 `$this->focus?->focused()`）⇒ 保持 ⑧ 在 ⑨ 之前。

### 2.2 阶段表的形状

```php
// src/App/FramePhase.php
/**
 * 帧的阶段声明（§5.2）。
 *
 * ★ 为什么需要它：九段的顺序里只有"跨过 settle"是硬约束，其余可以任意 ——
 *   而这句话现在只写在注释里。声明成一张表之后，dev 期可以断言"谁越界了"。
 */
final class FramePhase
{
    /** 必须在 `Frame::run()` 之前（会产脏） */
    public const BEFORE_SETTLE = [
        'pumpIo', 'pumpTasks', 'pumpSliced', 'tickAnimations',
    ];

    /** 必须在 `Frame::run()` 之后（观察新树） */
    public const AFTER_SETTLE = [
        'tickLateMount', 'focusCollect', 'pumpSemantics',
    ];
}
```

★ **它不是调度器**（§2.3 否决了调度器）。它只是**一份可以拿来断言的名单**：
dev 期每帧记下"实际执行了哪些段"，帧末比对名单，缺一段或多一段 ⇒ `Errors::report`。

### 2.3 为什么不做"通用调度器"

| 方案 | 代价 |
|---|---|
| 把九段改成"注册进一个数组，按优先级排序执行" | ① 顺序从**代码可见**变成**运行时数据**（读代码看不出顺序）；② 一次间接调用（闭包）比直接调用贵；③ 调度器本身要测 —— 而它解决的问题是"顺序可能被写错"，那是**一次写对就不用管**的问题 |
| **保持九段直写 + 一张断言名单** | 顺序仍然肉眼可见；名单只在 dev 期跑 |

★ 判据（进 `07`）：**能靠"一次写对 + dev 断言"守住的，不要造运行时机制。**
调度器的收益是"顺序可配置"，而帧阶段顺序**不该可配置**（它是正确性约束，不是偏好）。

### 2.4 阶段断言（dev）

```php
// Application::frame() 首尾
$trace = FramePhase::$on ? [] : null;
// …每段执行前： if ($trace !== null) { $trace[] = 'pumpIo'; }
// …帧末：
if ($trace !== null) {
    FramePhase::assertOrder($trace, $settleIndex);
}
```

`assertOrder()` 检查三件事：

| 检查 | 失败消息 |
|---|---|
| A 组成员的下标都 < settle 的下标 | `"pumpTasks 在 settle 之后跑了 —— 它的 setState 会慢一帧（loading→ready 会闪一帧空）"` |
| C 组成员的下标都 > settle 的下标 | `"focusCollect 在 settle 之前跑了 —— 焦点链可能握着已被移除的节点"` |
| 名单里的每一段都出现了 | `"本帧没跑 pumpSemantics —— 读屏会停在上一帧"` |

★ **开关**：`FramePhase::$on`，由 `build/frame.trace` 文件控制（与 `build/m4.on` 同一种
文件开关，不读环境变量 —— `nano-hygiene` 禁 `getenv`）。默认关。

★ 开销：关的时候是 `$trace = null` + 9 次 `if ($trace !== null)` ⇒ 可忽略。

★★ **报告文件**（W0 落地时补的，原方案漏了）：`build/frame.trace.out`，与开关同目录
同前缀（`getcwd()` 相对），开着时每帧刷一次，内容 = `frames` / `violations` +
最近 8 条一行摘要。**为什么必须有它**：`Errors::report(DIAGNOSTIC)` 只进**进程内**
环形缓冲，而真机上 `users.exe` 是独立进程 ⇒ 外面一条都读不到 ⇒ "0 条段顺序违规"
**无法验证，只能选择相信**。那是 G2「绝不静默」的反面：断言输出了，但没有人看得见。
跑法：`php tools/probe-frame-gates.php 14 1`（W0 实测 1219 帧 / violations 0）。
★ 整份重写而不是追加：报告表达"**当前**状态，进程被杀时留下的最后一份恰好就是
当时的真实状态。
★ `boot()` 一翻开开关就落一份 `frames 0` ⇒ "没有文件"与"跑过且干净"分得开。

## 3. 帧预算与降级顺序

### 3.1 现状

| 项 | 值 |
|---|---|
| 真机端到端（M4） | **3.1ms** |
| 60fps 预算 | 16.7ms |
| 余量 | **5.3×** |
| 帧预算机制 | `noteFrameCost()` + `overBudget`（连续 10 帧）+ D1 语义节流（第 37/38 步） |

### 3.2 六阶段预算分配

抄 v6 `08` §3.4 的分法，按我们的段名重排（16.7ms 预算）：

| 阶段 | 预算 | 现状占比 | 说明 |
|---|---|---|---|
| **A 组（四个泵）** | 1.0ms | 小（回调通常只 setState） | 含 IO 轮询与任务结果取回 |
| **settle** | 1.0ms | 0.2–0.5ms | rebuild + adoptBoxes |
| **layout** | 2.0ms | 0.6–1.2ms | 全树重排 |
| **paint（录制 + 光栅）** | 4.0ms | 0.8–1.5ms | 每帧全录（`05` §6） |
| **present** | 5.0ms | 约 1ms | `SetDIBitsToDevice` 驱动拷贝 |
| **余量** | 3.7ms | — | 给"某帧突然多 200 个节点" |
| **合计** | **16.7ms** | **3.1ms** | |

★ 这张表的作用**不是"按它分配 CPU"**，而是**回答"超了先砍谁"**。
没有这张表，超预算时的第一反应通常是"砍 paint"（错误）或"降帧率"（更错误）。

### 3.3 降级顺序

> **宁可少一帧动画，不可少一次刷新。**
> **宁可少一次读屏更新，不可少一次画面更新。**

按这个顺序砍，**从下往上**：

| 档 | 砍什么 | 影响 | 现在实现吗 |
|---|---|---|---|
| **D0** | 什么都不砍 | — | ✅ 现状 |
| **D1** | 语义推送降到**每 4 帧一次**（焦点变化时立即推） | 读屏延迟 3 帧（约 50ms），用户察觉不到 | ✅ **本册实现**（3 行） |
| **D2** | 动画 `tickFrame` 降到**每 2 帧一次**（动画变 30fps） | 动画变卡，但画面仍然响应输入 | ❌ 写死，不实现 |
| **D3** | 关掉 `LayoutSelfCheck` 的采样（`04` §5.4） | 失去自校验（只影响可诊断性） | ❌ 写死 |
| **D4** | 滚动的惯性/平滑（我们没有） | — | — |
| **D5** | **不砍**：layout / paint / present | 画面不更新 = 应用假死 | ❌ **永不** |

★ **D5 是"不可砍"的边界**，写在这里是为了防止将来有人为了"保住 60fps"去砍 layout。
砍 layout 等于"画面不更新" —— 那比掉帧严重一个数量级。

### 3.4 D1 的实现（唯一现在做的降级）

#### 帧耗时在哪量

`FrameClock::tick()` —— 它本来就是"谁在管时间"的那一层：

```php
$startedNs = \hrtime(true);
$app->frame($timestampMs, $constraints);
$app->noteFrameCost((float) (\hrtime(true) - $startedNs) / 1e6);
```

★ 量的范围 = `frame()` 全段（四个泵 + settle + layout + paint + present），正是 §3.2
那张表的合计口径。一对 `hrtime` 约 60ns，与一帧 3.1ms 相比可忽略。
★ **应用不自己读钟**（G3：帧的输入只有约束与树）：`noteFrameCost()` 只收一个数字。

#### 唯一的预算机制

```php
public const BUDGET_MS = 16.7;              // 60fps
public const OVER_BUDGET_FRAMES = 10;       // 单帧超不算"真超"
public const STAGE_BUDGET_MS = [            // 六阶段预算（§3.2）
    'A 组（四个泵）' => 1.0, 'settle' => 1.0, 'layout' => 2.0,
    'paint' => 4.0, 'present' => 5.0, '余量' => 3.7,
];

public function noteFrameCost(float $milliseconds): void
{
    if (!\is_finite($milliseconds) || $milliseconds < 0.0) { return; }   // 量坏了不立标志
    // …记 frameCostMs / worstFrameMs
    if ($milliseconds <= self::BUDGET_MS) { $streak = 0; $overBudget = false; return; }
    $streak++;
    $overBudget = $streak >= self::OVER_BUDGET_FRAMES;
    if ($streak === self::OVER_BUDGET_FRAMES) { /* 报一条 DIAGNOSTIC */ }
}
```

★ **`overBudget` 用"连续 10 帧"而不是"单帧"**：单帧超预算通常是垃圾回收或系统抢占，
连续 10 帧才是真问题。这与 `00` §5 的"单帧 > 8ms 连续 10 帧"是同一个口径。

★ **只在刚立起来的那一帧报**（`=== OVER_BUDGET_FRAMES`）：环形缓冲只有 100 条，
每帧报一条会把它刷满，别的诊断全被挤掉。

★ **一帧回到预算内就复位**（不是"要连续 10 个好帧"）：偶尔一帧慢就把降级锁死很久，
那是把"短暂抖动"放大成"长期降级"。

★ `STAGE_BUDGET_MS` 是**降级顺序的依据**，不是 CPU 分配表 —— 诊断文案从它生成
（数字只有一个来源）。超了先砍语义推送；`layout` / `paint` / `present` **永不砍**（D5）。

#### D1：语义推送每 4 帧一次

```php
private function pumpSemantics(): void
{
    $sink = $this->semanticsSink;
    if ($sink === null) { return; }

    $focused = $this->focus?->focused();
    $focusChanged = $focused !== $this->semanticsFocused;   // ★ 判据是"焦点 Element 变了"

    if ($this->overBudget && $this->semanticsFrameSkip > 0 && !$focusChanged) {
        $this->semanticsFrameSkip--;
        return;
    }

    $this->semanticsFrameSkip = $this->overBudget ? 3 : 0;
    $this->semanticsFocused = $focused;
    ($sink)(SemanticsBuilder::build($this->root, $focused)->toArrays()['nodes']);
}
```

★ **焦点变化永不节流**：读屏用户靠焦点提示知道"我移到哪了"。延迟 3 帧（约 50ms）能忍，
漏一次不能忍。这正是"宁可少一次读屏更新，不可少一次画面更新"的另一半 ——
**画面**永不节流，**读屏**只允许"慢一点"，不允许"少一条关键事件"。

★ **判"焦点变了"用 Element 身份比较，不给 `FocusManager` 加计数器**：计数器是新增状态
（要维护"什么时候归零"），而身份比较是零状态的 —— 代价是"Element 被重建"时会多推一次，
方向是**多推**而不是漏推，可以接受。

★ 没有 sink ⇒ 整段早退（不建语义树），节流也就无从谈起。诊断文案因此说的是
"语义推送降到每 4 帧一次"，而不是"帧率降了"。
### 3.5 不做"自适应帧率"

| 方案 | 否决理由 |
|---|---|
| 掉帧时把帧间隔从 16ms 拉到 33ms | 那是"主动变卡"，用户对"稳定 30fps"的接受度远低于"偶尔掉一帧的 60fps"。而且它掩盖问题 —— 开发时看不出超预算 |
| 按负载动态选 30/60 | 同上，且引入"帧率切换时的抖动" |
| 用 `wantsFrame()` 精确控制"只在有活时跑" | ✅ **已经在做**（4 条判据） |

★ `wantsFrame()` 的 4 条判据（`:1154-1173`）是**正确的省电机制**，本册不动。
它解决的是"没活干时 CPU 归零"，与"有活干时超预算"是两件事。

## 4. `tickAnimations()` 两遍 → 一遍

### 4.1 为什么必须两遍（重述）

见 §1.4。核心矛盾：

- `tickFrame()` **必须**在 settle 之前（否则动画慢一帧）
- 挂载**必然**发生在 settle 期间（rebuild 造新 Element）
- ⇒ 新挂载的 State 在第一次 tick 时**还不在树里**

### 4.2 改成"挂载登记表"

```php
// State（`03` 已经加了两个静态字段，这是第三个）
/** @var list<State> 本帧挂载的 State（`callInit()` 时登记，帧末清空） */
private static array $mountedThisFrame = [];

public function callInit(): void
{
    if ($this->initialized) {
        return;
    }
    $this->initialized = true;
    self::$mountedThisFrame[] = $this;      // ★ 登记
    // … 原有逻辑
}

/** @internal `Application::frame()` 帧末消费 */
public static function takeMountedThisFrame(): array
{
    $list = self::$mountedThisFrame;
    self::$mountedThisFrame = [];
    return $list;
}

/** @internal smoke 用：登记表必须被清空 */
public static function mountedCount(): int
{
    return count(self::$mountedThisFrame);
}
```

`Application::frame()` 的第 ⑦ 段改成：

```php
// ⑦ 只 tick 本帧新挂载的 State（不再走全树）
foreach (State::takeMountedThisFrame() as $state) {
    if ($state->tickFrameStamped($timestampMs, $this->frameSerial)) {
        $this->animating = true;
    }
}
```

★ **正确性**：第二次 tick 的目的**只有一个** —— 让"这一帧刚挂上的 State"有机会
声明"我还要下一帧"。全树里**其他** State 已经在本帧第一次 tick 时被访问过
（`tickFrameStamped` 会跳过重复），所以遍历它们**纯属浪费**。

★ **`tickFrameStamped` 的帧戳还要吗**？要 —— 因为 `takeMountedThisFrame()` 返回的
State 可能已经在本帧被第一次 tick 访问过（如果它是"在 settle 之前就挂上"的，
例如 `placeMenu()` 期间）。帧戳保证不重复推进。

### 4.3 省多少

| 项 | 现状 | 之后 |
|---|---|---|
| 每帧 `tickSubtree` 全树遍数 | **2** | **1** |
| 帧末的额外调用 | O(树) 次 `tickFrameStamped`（每个都查一次帧戳） | O(新挂载数)（通常 0–5） |
| 树 800 节点时 | 800 次虚方法调用 + 800 次整数比较 | 0–5 次 |

★ 粗估：800 次调用 ≈ 20–40µs。占 3.1ms 的 **1%**。不大，但它是**纯浪费**，
且随树规模线性增长 —— 而 `tickAnimations` 的第二次本来就不该存在。

★ 更重要的一条：**`$mountedThisFrame` 的登记点是 `callInit()`**，而它已经在
`StatefulElement::onMount()` 里被调（`State.php:193-206`）⇒ 不新增调用点，只加一行。

## 5. 指针捕获：`captureNode`

### 5.1 现状：没有捕获，已经有**两套**私有的指针跟踪

**第二套：`$thumbDrag`**（`Application.php:123`，一个 `?array`）


⇒ 缺的不是"捕获这个想法"，是**"捕获"这个机制**：

| 需求 | 现状 | 需要的 |
|---|---|---|

| **表格列宽拖动** | ❌ 没有 | 第五套 |

★ 判据（`00` §0 的同一条形状）：**"按下后持续收 move"这件事已经被实现了两遍，
第三遍就会开始走样** —— 因为每遍都要自己处理 up/leave/卸载/浮层/失焦。

### 5.2 形状

Stored above.

```php
// src/App/Application.php
/** @var null|Element 捕获指针的节点（拖动/滑动的物质基础） */
private ?Element $captureNode = null;

/** @internal 由控件的 pointerDown 处理里调 */
public function capturePointer(Element $node): void
{
    $this->captureNode = $node;
}

/** @internal 释放（指针抬起 / 捕获者卸载 / Esc） */
public function releasePointer(): void
{
    $this->captureNode = null;
}
```

`dispatchPointer()` 的路由改成：

```
若 $captureNode !== null：
    → 事件只发给 $captureNode（不再命中测试）
    → 指针抬起（UP/CANCEL）⇒ 发完之后 releasePointer()
否则：
    → 正常命中测试（含浮层优先，见 01 §6.1）
```

★ **捕获期不做命中测试**，这是捕获的全部意义。但要保留一条：**捕获者卸载时自动释放**。
做法与 `01` §7.2 的 `owner` 清扫同路 —— 在 `Application::frame()` 的 ⑧ 段之后检查
`$captureNode` 是否还在树里（`$captureNode->isMounted()`），不在就释放 + DIAGNOSTIC。

### 5.3 为什么不做"每个 Element 自带 capture 状态"

| 方案 | 代价 |
|---|---|
| `Element::$capturing` 字段 | 一次捕获要改一个 Element 的字段，而"谁是捕获者"是**全局唯一**的事实 ⇒ 分散在 N 个对象上 |
| **`Application::$captureNode` 一个字段** | 与 `DragController` 同形（它也是全局单例），且"同一时刻只有一个捕获者"是**输入系统的物理事实**（只有一个鼠标） |

★ 触摸输入落地后会有多个指针 ⇒ 那时改成 `array<int, Element>`（按 pointerId）。
**现在不做**：没有触摸输入，加数组就是"为一个不存在的场景造结构"。

### 5.4 `DragController` / `$thumbDrag` 与 `captureNode` 的关系

**不合并。** 三者职责不同：

| | `DragController` | `$thumbDrag` | `captureNode` |
|---|---|---|---|
| 管什么 | **拖放的业务语义**（谁是源、谁是目标、能不能放） | **滚动条的一步位移公式** | **指针事件的送达**（move 发给谁） |
| 有几个 | 一个（全局拖放） | 一个（一个 thumb） | 一个 |
| 谁用 | `Draggable` 控件 | `RenderScrollView` 的 thumb | `Slider` / 文本选择 / 表格列宽 / 将来的 thumb |

★ **本册只加 `captureNode`，不改前两个。** 它们的行为是对的，只是各自手写了一遍
"怎么持续收 move"。`captureNode` 落地之后，`$thumbDrag` 应该重写成
"down 时 `capturePointer()` + move 时算 delta + up 时自动释放"——
那是 `09-迁移路线.md` 的一件独立小事，**不在本册范围**（改它要动 `dispatchPointer`，
而本册已经要和 `01` 同批改它了，再加一件会让回滚粒度变粗）。

## 10. 失败模式

| 失败 | 表现 | 防线 |
|---|---|---|
| 把 `pumpTasks` 挪到 settle 之后 | 慢一帧（`loading → ready` 闪一帧空） | `FramePhase` 断言（§2.4） |
| 把 `focus.collect` 挪到 settle 之前 | 按键丢给已被移除的节点 | 同上 |
| `tickSubtree` 加了短路 | 多个 Spinner 只有一个转 | 断言名单不覆盖这条（它是**方法内**的约束）⇒ 只能靠注释 + 一条 smoke 夹具（两个 Spinner 都转） |
| 超预算时砍 layout | 应用假死（画面不更新） | §3.3 的 D5「永不」 |
| 降级顺序写错（先砍 paint） | 画面更新变慢，但动画流畅 —— 用户感知更差 | §3.3 的顺序表 |
| 语义推送节流但焦点也节流了 | 键盘导航时读屏跟不上 | "焦点永不节流"（§3.4） |
| `$mountedThisFrame` 登记后不清空 | 内存泄漏 + 每帧 tick 越来越多的 State | `takeMountedThisFrame()` 里清空；smoke 断言跑 100 帧后 `count === 0` |
| `captureNode` 忘记释放 | 之后所有指针事件都发给一个死节点 | UP 自动释放 + 卸载清扫 + 失焦释放（§9 #10/#11） |
| `captureNode` 与浮层同时存在 | 点浮层外不关闭 | 捕获期不命中测试 ⇒ 浮层的"点外面关"失效。**处置**：捕获期若浮层打开，先释放捕获（`01` §6.1 的浮层优先规则） |

★ 最后一条是真冲突，要写进 `01` 的协调项：**捕获优先于浮层**还是**浮层优先于捕获**？
裁决：**浮层优先**。理由：浮层是"模态性"的（用户必须先处理它），而捕获是"我在拖"。
用户拖到一半时浮层弹出来（例如 Toast），继续拖是对的；但用户主动点浮层时，
那次 down 应该先关浮层。⇒ 具体规则：**捕获期，浮层外的 down 先释放捕获 + 关浮层，不转发给捕获者**。

## 12. 备选方案与否决

| 备选 | 否决理由 |
|---|---|
| **通用调度器（九段注册进数组按优先级排）** | §2.3：顺序从代码可见变运行时数据；间接调用更贵；调度器本身要测 |
| **自适应帧率（超预算拉到 33ms）** | §3.5：主动变卡，且掩盖问题 |
| **超预算砍 layout / paint** | §3.3 D5：画面不更新 = 假死 |
| **`tickAnimations` 保持两遍** | §4：第二遍 99% 的帧纯属浪费，且随树规模线性增长 |
| **`Element::$capturing` 每节点自带** | §5.3：捕获者是全局唯一事实 |
| **`captureNode` 做成 `array<int, Element>`（按 pointerId）** | 没有触摸输入 ⇒ 为不存在的场景造结构 |
| **把 `DragController` 合并进 `captureNode`** | §5.4：一个管业务语义、一个管事件送达，职责不同 |
| **统一事件总线** | §6：五条入口的上游差异大，统一成带 type 的大 struct 更难读 |
| **`pumpSemantics` 改成增量** | 属 `07` 的三档推送（full/delta/coalesce），本册只做 D1 节流 |

### 推翻条件

| 裁决 | 什么情况下推翻 |
|---|---|
| 不做调度器 | 段数增长到 15+ 且需要"按配置开关某些段" |
| D2/D3 不实现 | 真机出现连续超预算且 D1 不够 ⇒ 按 §3.3 顺序往上砍 |
| `tickAnimations` 一遍 | 出现"settle 期之外新挂载"的路径（例如某段在帧末造子树） |
| `captureNode` 单指针 | 触摸输入落地 ⇒ 改 `array<int, Element>` |
| 浮层优先于捕获 | 出现"拖到一半必须继续拖"的真实场景（例如拖动中被 Toast 打断）⇒ 改成"捕获优先，浮层只画不拦" |
