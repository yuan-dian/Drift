### W8-2 · 叶子控件（解锁、低风险，建立范式）
- ✅ **2026-10-24 完成**：Slider / Select / ComboBox / Segmented / Tooltip / Snackbar /
  Menu / Checkbox / Radio / Toggle / Progress / Spinner（`src/Widget/` 可查；逐项的
  裁决与踩坑见附二~附十）。
  **未做**：DatePicker / Pagination / Breadcrumb / Timeline / Upload / Badge / Chip ——
  七个都没有真实消费者。
- 逐控件：Widget(+State) + RenderBox + 语义 + smoke（含反例自检）+ 真机一图。顺序：
1. **TabBar / SegmentedControl**（tap + 受控选中，复用 focus/activate，无浮层）—— 先立范式。
2. **Slider**（受控值 + drag；drag 复用/最小扩展 `Application` 派发，**改前先出方案**）。
   - **2026-10-23 裁决（已落地 `7f0b536`）**：**否掉"复用 `Draggable`"**。三个硬理由：
     ① 点轨道不跳值（arena 把激活推迟到 up、拖动推迟到 6px 阈值，而 Slider 的标准语义是
     "按下即跳到该位置"）；② `DragController::drop()` 会派发 `DragTarget::onAccept`
     ⇒ 拖放区里的 Slider 松手会被当成"投放"；③ 拖动中 `hoverTo` 会刷新拖放区高亮。
   - 改走 **两条输入缝**（`Widget::pointer($h, ownsPress: true)` / `Widget::keyboard($h)`），
     见下节。**新控件一律走这两条缝，不要再往 `Application::activateFocusedWidget()` 的
     `instanceof` 塔里加分支。**
3. **Tooltip**（hover 回调 + `OverlayStack`；无新手势）。
   - **2026-10-23 裁决（已落地）**：**否掉"应用写 hover 回调 + 自己 `showTooltip()`"**，
     改走 **`Widget::tooltip(string)` 声明 + 框架托管浮层**。三个硬理由：
     ① **hover 回调拿不到锚点**（签名 `\Closure(bool)`），加第二个参数在 PHP 侧无害，但
     tpc 生成的 C++ 侧闭包 arity **没有验证过** —— 不值得为一个可选能力赌编译器；
     ② 应用侧代码量：回调式每个控件 3 行（记 entry / show / hide）+ 自己写对"相邻控件
     先关再开"的时序，声明式一行，时序只在一处；
     ③ 同族一致性：`semantics()` / `pointer()` / `keyboard()` 都是"控件属性"，Tooltip
     **不产生布局、不产生绘制** ⇒ 做成包裹 Widget 反而要透明 `RenderProxy` +
     `expandChildren()`（纯开销），还会插进 `hoverOwner()` 的父链判定。
   - **顺带补掉的三处结构性缺口**（都是"承诺了没实现"）：
     - `Application::after(ms, cb): int` / `cancelAfter()` —— **通用一次性延时**，
       全仓此前没有（`TimerHost` 只有周期定时器且只给帧时钟用）。走**帧时钟轮询**
       （`FRAME_MS=15`），不新增 `TimerHost` id：15ms 精度对"人的反应时间"无感，
       换来零平台改动。**Snackbar 的定时消失会复用同一条**。
     - `wantsFrame()` 第 5 条判据"有定时器待触发" —— **结构前提**，不是优化：
       消息泵是阻塞的，没人叫醒定时器永远不响。反面代价是停留期帧时钟保持上膛
       （500ms ≈ 33 帧空转），可接受。
     - `FramePhase::ALL` 加 `pumpTimers`（组 A，settle 之前）。
   - **`OverlayEntry` 三处新增**：
     - `hitTest = true`（`false` = 指针看不见这一层，对应 Win32 `WS_EX_TRANSPARENT`）。
       ★★ **没有它就会闪烁死循环**：提示面板一出现在指针附近 ⇒ `dispatchPointer()` 的
       浮层段命中它 ⇒ `hoverTo(面板里的元素)` ⇒ 锚点悬停丢失 ⇒ 隐藏 ⇒ 指针又命中锚点
       ⇒ 再显示。`barrier=false` 只解决"没命中时穿透"，解决不了"命中了就不放"。
       真实后果还有一条：提示盖住某个按钮时，`barrier=false` 的命中分支会**吞掉那次
       down** ⇒ 用户点不动下面的按钮。
     - `maxWidth`（`INF` = 不限）—— `placeEntry()` 给非居中层的是**无界**约束，而
       `RenderPopupPanel` 只在约束有界时才夹宽，⑤ 的夹紧**只挪 x 不改宽** ⇒ 长文案
       右边溢出。Tooltip 设 320。
     - `BELOW_CENTER = 6` / `ABOVE_CENTER = 7` —— 锚点中心对齐。落位算法在
       `originFor()` 里（应用拿不到夹紧后的 `maxW`），所以方向必须是**语义**而非坐标。
   - **`FocusManager::onHoverChanged(\Closure(?Element))`** —— 悬停**原始命中**的变化口。
     与 `hoverHandler` **不同源**：那个找"有 `hover()` 的控件"，Tooltip 的声明者可能
     没有 `hover()`。收原始命中而不在这里解析，是为了不把"Tooltip 是什么"的知识漏进
     焦点层。默认 `null` ⇒ 逐字节不变。
   - ★ **`OverlayEntry::$owner` 此前零消费**（`01` §7 承诺"owner unmount ⇒ 自动 pop"）
     —— 本次在 `placeOverlays()` 里补上。死字段比缺失更贵：读代码的人会以为防线已在。
   - ★ `pushOverlay()` 会快照 `restoreFocus`（菜单/模态要的"焦点回锚"）⇒ Tooltip 必须
     **在 push 之后**把 `restoreFocus` 覆盖成 `null`，否则关闭提示会把焦点从用户刚点的
     地方抢走。
   - ★ 时序：进入 ⇒ `after(500)`；离开 ⇒ cancel + 立即 hide；**已显示时移到相邻声明者
     ⇒ 立即换**（Windows 手感：一排图标不该每个都等 500ms）。
   - ★★★ **AOT 坑（2026-10-23 真机抓到的，解释器侧全绿）**：`BoxConstraints::INFINITY`
     作为**外部类常量引用**（`new BoxConstraints(0, $w, 0, BoxConstraints::INFINITY)`）
     在 tpc 生成的 C++ 里求值成 **0** ⇒ `maxHeight = 0` ⇒ 面板 `w=h=0`。
     现象极具欺骗性：`showTooltip` 被调、文字正确、`placeEntry` 的 `x/y` **完全正确**
     （`x=268 y=161.6`）、`ink_all_pct` 只从 9.4 变 9.5（一个 88×30 的面板占整窗
     0.13%，而墨量精度是 0.1% ⇒ **单看墨量会误判成"没变"**），画面一丝不变。
     ⇒ 修法：**走类内工厂** `BoxConstraints::capWidth($w)`（内部用 `self::INFINITY`，
     与 `unbounded()` / `loose()` 同一条已被验证的路径）。
     **判据纪律**：AOT 特有的静默失败，smoke 一条都抓不到 ⇒ 这类改动只能靠
     T2 真机图；且真机判据要**看 md5 与图**，不要只看墨量百分比。
4. **Snackbar**（`OverlayStack` + 定时消失 —— 复用上面那条 `after()`）。
   - **2026-10-23 裁决（已落地）**：**`Snackbar` 是纯描述对象（`final class`），不是
     Widget**。三条理由：
     ① **动作按钮要能关掉自己**，而 Widget 一旦 seal 就拿不到 `Application`
     （§4.3 禁 `Widget → App`）⇒ 只能由 `Application` 组面板时把 dismiss 闭包
     **注入**进去（`SnackbarPanel::make($snackbar, $onDismiss)`）；
     ② **生命周期一次性**（显示 → 消失 → 丢弃），没有 diff 复用需求 —— `Modal` 做
     Widget 是因为"内容变了要复用盒"，Snackbar 不会；
     ③ **队列里排着的那几条还没挂载**，本来就不该是 Widget。
     ⇒ 与 `OverlayEntry`（也是纯描述 `final class`）同形。
   - **`Application::showSnackbar()` / `dismissSnackbar()` / `hasSnackbar()` /
     `snackbarQueueLength()` / `snackbarEntry()`**：第一条立即显示、其余 **FIFO 排队**
     （不排队的话"连续保存三次"只看得到最后一次 —— 那正是通知最容易失职的场景）。
     `duration(0)` = **永不自动消失**（错误提示要用户确认），走哨兵三档定则。
   - **`OverlayEntry` 两处新增**：`BOTTOM_CENTER = 8`（贴底居中，**不做翻转** ——
     通知没有"上面放不下就翻到下面"这种语义）+ `inset`（离底留白，Snackbar 用 24）。
     落位 `x=(maxW−w)/2`、`y=maxH−h−inset`，放不下由 `placeEntry()` ⑤ 的夹取兜住。
   - ★★ **`hitTest` 与 Tooltip 相反**：Snackbar 保持 `true`（动作按钮要能点），
     Tooltip 是 `false`（指针看不见它）。**这两个需求正好相反**，改任何一个之前
     先想清楚是哪一类。
   - ★★ **`MIN_WIDTH = 220` 不是审美，是必须的**：`RenderPopupPanel` 用
     `max(minWidth, child->intrinsicWidth(INF))` 定内容宽，而 `Button` 在**无界高度**
     下的 `intrinsicWidth()` 会失真（返回远小于实际）⇒ 内容宽被算成正文那行字的宽
     （42），布局时动作按钮要 50 ⇒ `RenderFlex 放不下：子项共需 50.0，可用只有 42.0`
     **直接中止**（smoke 退出码 3、零输出，`Errors.log` 里才有那句话）。
     长文案不受影响：`max(220, 全文宽)` 后被 `MAX_WIDTH=480` 夹住 ⇒ 正文换行。
   - ★★★ **示例台接线踩到的坑（2026-10-23，真机进程直接崩、smoke 全绿）**：
     `$this->application()` **不存在** —— `State` / `Widget` 上都没有这个访问器。
     我在 `Application::showSnackbar()` / `Modal.php` / `Snackbar.php` 的 docblock
     和示例台里都写成了那个形态（`docs/examples.md` 更早就写着），**照抄即崩**。
     后果：真机点一下按钮 → 未定义方法 → AOT 侧直接退出、5 秒内进程消失、**没有
     `Errors.log`**（那不是 `Errors::abort` 的路径）。
     ★ 两条连带教训：
     - **tpc 不校验 `$this->不存在的方法()`** ⇒ `drift-build` 照样成功（9.4 MB，
       0 error）⇒ **AOT 构建本身不是这条的闸门**；
     - **smoke 的夹具拿着 `Application`**，走的是另一条路 ⇒ 全绿。
       **示例台是这条 API 唯一的真实消费者** ⇒ 凡"只给应用用的 API"，判据必须在
       示例台上做。
     ⇒ 合规写法只有两条：**组合根接线**（`ShowcaseApplication::buildRoot()` 把
     `fn(Snackbar $s) => $this->showSnackbar($s)` 递进 `ShowcaseRoot` → 页面，
     `Menu::onOpen` 同款）或**框架托管**（`Widget::tooltip()` 那种声明式）。
     ★ 闭包参数**不可空**（`?\Closure` 在 AOT 侧退化 `php::Var`）。
   - ★ 真机五档判据（`_build/probe-snackbar.php`）：`sb-page` = `sb-gone`（**逐字节
     相同** `9e06ac88…` ⇒ 4s 到点真的自动走了）、`sb-on` 不同（通知出现）、
     `sb-act` 不同（带「撤销」按钮 ⇒ **AOT 侧注入的闭包被接受、面板建起来了**）、
     `sb-undo` 不同（点完通知收掉 + 页面「已撤销 0 次」→「1 次」）。
   - ★★ **起窗探针的子进程 stdout/stderr 必须落文件**（`['file', ...]`）：
     `stream_set_blocking()` 对 Windows 管道**无效**，想在运行中抽干管道会永久阻塞
     （探针只打印了 `pid=` 就卡死，看着像"起窗卡住"）；而崩溃信息是唯一线索。
5. **Select/Dropdown**（tap + `OverlayStack` + 列表 + 受控选中）。
   - **2026-10-23 裁决（已落地）**：**不写 `RenderSelect`，用 `Button` + 一条
     声明式浮层缝组合出来**。理由：新渲染盒是本仓最贵的改动面（内禀失真 /
     offset 双重平移 / AOT 常量折叠，每一条都出过真机 bug），而"一个有边框的、
     点了浮面板的按钮"用现成 `Button` **完全表达得出来** —— 焦点、激活、光标、
     语义、命中全白送。真机实测 `Button` 被 `width()` 定宽后标签**靠左**（与示例台
     侧栏导航同一条路径）⇒ 正好是选择框的形态，连对齐都不用额外处理。
   - ★★★ **新增第三条声明式缝 `Widget::overlayPanel(\Closure $factory)`** ——
     形参是"收掉这一层"的 `dismiss` 闭包，返回面板内容。三个关键点：
     - **为什么需要它**：`pointer()` / `keyboard()` 这两条输入缝把事件交给**控件
       自己的闭包**，而"开浮层"要 `Application`（§4.3 禁 `Widget → App`）⇒
       闭包够不着。声明式让框架在**激活**那一个入口统一处理。
     - **为什么工厂只收一个参数**：tpc 生成的 C++ 侧**闭包 arity 没有系统验证过**
       （`Menu::onOpen` 的 2 参形态至今没被示例台消费过）。要往工厂里塞"锚点宽度"
       这类信息，宁可给 `OverlayEntry` 加字段，**不要加形参**。
     - **为什么由 `Application` 注入 dismiss**：与 `SnackbarPanel::make($s, $onDismiss)`
       是**同一条**已被真机验证过的路（`119cfd7`）。
   - ★★ **`activateFocusedWidget()` 里只有一条按"能力"判的通用分支**
     （`$widget->overlayPanelValue() !== null`），**排在最前**、**没有 `instanceof`**
     ⇒ 以后 DatePicker / ComboBox 不用再改这里一行。优先级：声明了面板 ⇒ 开面板，
     不走 `onPressed` / 命令（"浮一个面板"比"按一下"更具体）。
   - ★★ **面板参数三处最容易搞反的**：
     | 字段 | 值 | 为什么 |
     |---|---|---|
     | `barrier` | **true** | 这是 `dismissOnTapOutside` **唯一**生效的路径 —— `dispatchPointer()` 里"点在条目盒外"整支包在 `if ($e->barrier)` 里，`false` 的条目直接穿透 |
     | `owner` | **锚点自身** | 页面走了没关下拉 ⇒ `placeOverlays()` 的 owner 清扫收尸 |
     | `restoreFocus` | **保留快照**（不置 null） | 与 Tooltip / Snackbar **相反**：那两个是悬停 / 定时器触发的，打开时焦点不在锚点上，快照下来是错的；这里打开它的就是锚点自己 ⇒ 快照天然正确，收面板时焦点回到控件上（否则"选完一项焦点就丢了"） |
   - ★ **不靠字段记"谁开着"**：直接扫栈里 `owner === $anchor` 的条目。字段会在
     `dismissOnTapOutside` / `closeMenu()` / owner 清扫这些**不经过本类**的移除路径上
     变陈旧（Snackbar 的 `snackEntry` 就是靠 `closeMenu()` 手动复位兜的）。
   - **`Option` 值对象**（`label` + `value`）：`label` 是给人看的字，`value` 是**身份**。
     ★ 与 `SegmentedControl`（`list<string>` + 下标）**刻意不同**：分段控件的段是
     "几个平级的视图"，位置本身就是语义；Select 的列表会被重排 / 过滤 / 分页，
     下标就不是身份了。两条纪律各自的理由都写在这两处，**别为了统一而统一**。
   - ★ **能力边界**：方向键换值（要"面板随控件重建"，否则选中高亮会
     停在旧值上 —— 宁可不做也不做自相矛盾的）/ 下拉箭头（`Button` 标签位只收字符串）/

#### W8-2 附二 · PopupPanel 限高 + 浮层 settle 顺序（2026-10-24）

**动机**：`Select` 的面板是"超高就永远点不到"—— 30 项的面板高 ~1000px，
超出客户区的部分既点不到也看不见。这不是 Select 特有的洞：`Menu::panel()` /
`ContextMenu.php` 到今天仍用 `PopupPanel::make(Column...)` **不设上限**
（**同一个洞，留作独立一步**，`PopupPanel::maxHeight()` 的 docblock 已写明）。

**一、`PopupPanel::maxHeight(float)` + `RenderPopupPanel` 限高**

- **算法（"超长才滚、够短就贴着"）**：先按**无界高**排一遍量自然高，超过上限才按上限
  重排（内容变成可滚视口），否则按自然高贴着。
  ```php
  $roomH = max(0.0, $constraints->maxHeight - 2.0*$e - $this->padding->vertical());
  $cap   = $this->maxHeight;                       // 0 = 不限（旧行为逐字节不变）
  if ($cap > 0.0 && $cap > $roomH) { $cap = $roomH; }   // 上限不超过约束允许的内容高
  $natural = $child->layout(new BoxConstraints($innerW, $innerW, 0.0, INF));
  if ($natural->height + $this->padding->vertical() + 2.0*$e > $cap) {
      $child->layout(new BoxConstraints($innerW, $innerW, 0.0, $cap - 2.0*$e - $this->padding->vertical()));
  }
  ```
  ★ **`RenderBox::layout()` 没有"已排过"守卫** ⇒ 双重 `layout()` 安全（已核验）。
- ★ **"贴着还是滚"必须由面板用实测自然高判，不能按条目数猜**：
  `RenderScrollView` 的视口语义是 `is_infinite($mainMax) ? $contentMain : $mainMax`
  （有界填满、无界贴内容）⇒ 内容矮时**不会**自己滚，也不需要面板替它决定。
- ★ **AOT 纪律**：本文件用**裸 `INF`**（PHP 内建常量）而非 `BoxConstraints::INFINITY`
  —— 后者是**外部类常量引用**，tpc 下会折叠成 0（Tooltip 那次 `w=h=0` 的根因）。
  **判据：不在 `Geometry` 之外手写 `BoxConstraints::INFINITY`。**
- `Select` 侧：`PANEL_MAX_HEIGHT = 260.0`，`panelFactory()` 内容套
  `ScrollView::make(Column...)` + `->maxHeight(self::PANEL_MAX_HEIGHT)`。

**二、★★★ 浮层的重建必须早于浮层的布局（本轮最贵的发现）**

`Application::frame()` 里 `placeOverlays()`（浮层 layout）跑在 `$frame->run()`
（内含 settle）**前面** ⇒ **settle 换上的新盒这一帧没排过**（`size` 为 null、
offset 为默认值）⇒ `paintContent()` 第一句"没排过 ⇒ 无墨"早退 ⇒ **面板空白一帧**。

- **首个暴露者**：`Select` 面板里的 `ScrollView` 滚一格换一次盒、空白一格
  （`ScrollView` 是三段式：`ScrollView` → `ScrollViewState`（持 offset）→
  `ScrollViewBox`；`scrollBy()` → `setState` → `update()` → **新 `RenderScrollView`**）。
- **这不是 Select 特有的洞：任何浮层里的有态控件都中招**（模态里放 `TextField`，
  每敲一键空白一帧）—— 只是以前没有浮层装过会自重建的内容。
- **定位手法**：`spl_object_id()` 打快照 ⇒ 面板盒不变、选项盒全不变、
  **只有 ScrollView 盒换新且没排过**。别被"dy 只有 8px"骗成渲染偶发抽风。
- **修法**：`placeOverlays()` 开头先 settle 所有浮层（放在方法内而非调用点 ——
  `frame()` / `repaintForResize()` 两个调用点都要这条顺序）；`Frame::run()` 里原有的
  浮层 settle 保留（幂等）。
- **修后实测**：滚一格 option[0] 位移 **8.00 → 48.00**（正好 `WHEEL_NOTCH_PX`），
  `appliedOffset` 同帧 0→48→96。

#### W8-2 附三 · Menu / ContextMenu 面板限高（2026-10-24）

`PopupPanel::maxHeight()` 立起来之后的**同一个洞**：`Menu::panel()` / `ContextMenu::panel()`
都是 `PopupPanel::make(Column...)` 不设上限 ⇒ 超长菜单被夹成整个客户区高、超出部分被裁
⇒ **第 N 项之后点不到**（Tab 也走不到 —— 焦点环画在视口外，用户看不见焦点在哪）。

- **落地**：两个 `panel()` 都改成 `PopupPanel::make(ScrollView::make(Column...))`
  + `->maxHeight(self::PANEL_MAX_HEIGHT)`（`320`）。
- ★ **为什么这一步只是"接上现成 API"、没有新语义**：
  - `MenuItem extends Button` ⇒ 每一项都可聚焦；
  - `Application::revealFocused()` **已经**挂在焦点变化上（`04` §6.3 键盘可达性硬要求）
    ⇒ Tab 在长菜单里走会自动把焦点项滚进视口，**一行接线都不用加**。
- ★ **`320` 是策略圆整数，不是布局计算**：菜单行约 26.8px、分隔线 7px ⇒ 约 10 行。
  "贴着内容还是滚动"由 `RenderPopupPanel` 按实测自然高决定 ⇒ 短菜单不会因为上限大就
  凭空变长，也不会因为上限小就无故滚。
- ★ **常量各放自己类上**（`Menu::PANEL_MAX_HEIGHT` / `ContextMenu::PANEL_MAX_HEIGHT`）：
  两个类的 `panel()` 本就是同一形态，而文档明说"它与 `Menu` 不对称是本质的不对称"
  ⇒ 不引进 `ContextMenu → Menu` 的依赖。
- **夹具设计**：长菜单（30 项 + 6 条分隔线）**刻意不进 `MenuBar`** —— 菜单栏自然宽有
  既有断言（"标题 + 3 个导航 + 菜单 ≈ 327"），加一个标题会把它顶翻。照 `fileMenu()`
  的用法直接 `showMenu($m->panel())`（绕开焦点状态）。
- ★★ **两个量具陷阱（都是本步新踩的）**：
  1. **客户区必须取高视口（320×900）**：`RenderPopupPanel` 的上限会与"约束允许的内容高"
     取小，沿用菜单那段 320×240 的矮视口会把面板夹成视口高 ⇒ 分不清"被 `PANEL_MAX_HEIGHT`
     限"还是"被客户区限"，用例白写。
  2. **每滚一次必须重取 `RenderScrollView`**：`scrollBy()` → `setState` → `update()`
     会换一个新渲染盒。探针在滚轮前抓了盒、滚完在**旧盒**上读 `appliedOffset()`
     ⇒ 恒为 0，"极像滚轮没生效"（与浮层 settle 那条同源：盒在重建时换新）。
- **实测（解释器）**：长菜单面板 **140×320 = 上限恰好**；视口 120×300；
  自然内容高 = 24 行 × 26.8 + 6 分隔 × 7.0 = **685.2** ⇒ `maxScroll = 385.2`；
  滚一格 = **48**、两格 = 96。短菜单（3 项）面板 140×80.6、`maxScroll = 0`（贴着）。
- **smoke +10（1261 → 1271）**：长菜单面板高 = 上限 / 反例"自然高远超上限" / 有滚动
  视口且视口比盒矮 / `maxScroll = 自然高 − 视口`（推导）/ 最后一项在面板下沿之外 /
  滚一格 = 48、两格 = 96 / 滚后面板仍在且高度仍是上限；反例短菜单高 < 上限且 `maxScroll = 0`。
- **反向自检**：临时拿掉 `->maxHeight(...)` ⇒ **6 条立刻红**，且报出的数字精确复现洞
  （面板高 705.2 而非 320、`maxScroll=0` 滚不动、appliedOffset=0）。
- **真机（`users.exe`，AOT 131.1s / 9.4 MB）**：`users` 是菜单的真实消费者
  （`UsersRoot` 的 MenuBar）。点「文件」⇒ 菜单浮出（刷新 / 新建 / 退出）；
  点「刷新」⇒ 菜单收起 + 状态栏「加载失败」→「**已刷新**」⇒ 命令真的分发了。
  ★ **如实记录覆盖边界**：`users` 的菜单只有 4 项 ⇒ 真机走的是**短菜单（贴着）**路径；
  **没有哪个真机应用渲染过"长而滚动的菜单"**。长路径的那部分代码
  （`RenderPopupPanel` 限高 + `ScrollView`）已由 Select 在 `showcase.exe` 上真机验过
  （滚到第 30 项），菜单自己新增的只是"哪几个 Widget 在 `panel()` 里组合"。

#### W8-2 附四 · `keyboard()` 沿父链解析（2026-10-24）

三条声明式输入缝此前**不同构**：`pointer()`（`dispatchToCapture` / `pointerOwner`）与
`contextMenu()`（`openContextMenu`）都沿父链找"最近的声明者"，唯独 `keyboard()` 只读
焦点控件自己的 widget ⇒ **包裹式控件的声明是死的**。`Widget::keyboard()` 的 docblock
一直写着"任何控件都能挂"—— 文档承诺了代码没做到的事。

- **洞**（为 ComboBox 补前置时发现的）：`ComboBox` 包一个 `TextField`，焦点落在
  `TextField` 上；外层要拦 Enter / 方向键 / Esc 驱动过滤浮层，声明永远收不到键。
- **落地**：`FocusManager::dispatchKey()` 改成从 `$this->focused` 起沿父链走，
  第一个 `keyHandlerValue() !== null` 的节点上；它吃掉 ⇒ `return true`；
  它让位（返回 false）⇒ **不再往上找**（更远的祖先更不具体，与另两条缝同口径）。
- ★ **对现有代码可证明是加性**：全仓三处声明（`Slider` / `Select` / `PressLabApplication`）
  都挂在"自己就是焦点控件"的 widget 上 ⇒ 父链第一跳就命中，行为逐字节不变
  （改完全量 smoke 1271 → 0 FAIL 印证）。
- **夹具**（`tools/Smoke/App/KeyAncestorApplication.php`）：外层 `Column` 声明
  `keyboard()`、内放可聚焦 `TextField` 的最小两件套；`fieldState()` 暴露
  `text()` / `caretOffset()` 供判据读。
- **smoke +3（1271 → 1274）**：① 焦点在 TextField 上时外层 handler 也收到键；
  ② 外层吃掉 Backspace ⇒ 焦点控件的文本不被改；③ 外层让位 ⇒ 键落到
  `TextFieldState`（删掉插入符前一个字符）。
- ★★ **量具教训（新踩）**：第 ③ 条的期望值**不能写死**。探针点的是输入框中部
  ⇒ 插入符落在 'a'/'b' 之间，Backspace 删掉的是**前面的** 'a' ⇒ 结果是 `'b'`，
  这是**正确行为**；写死 `'a'` 会把正确行为判成 bug。期望值从 `caretOffset()`
  **现推**：`substr($before, 0, $caret - 1) . substr($before, $caret)`。

#### W8-2 附五 · ComboBox（可编辑下拉 + 输入过滤，2026-10-24）

`Select` 的能力边界里写着"可编辑（输入过滤）没有 —— 那是 `ComboBox`"。这一步补上它。

- **形状**：`Column(keyboard)` → `SizedBox(width)` → `TextField(overlayPanel)`。
  **没有新渲染盒**（与 `Select` 同一条裁决：新盒是本仓最贵的改动面）。
- ★★ **`keyboard()` 声明在 `Column` 上、不是 `TextField` 上** —— 这是附四那条
  父链修复的**第一个真实消费者**。`Select` 把 `keyboard()` 挂在 `Button`（自己
  就是焦点控件）上，所以它当年不需要父链；`ComboBox` 需要：焦点落在里面的
  `TextField` 上，外层声明靠父链才收得到键。将来若在框右边加下拉箭头按钮
  （它也会是焦点目标），外层声明照样有效。
- ★★ **面板必须自己订阅**（本仓**第一个住进浮层树的 `StatefulWidget`**）：
  浮层是第二棵根渲染树 ⇒ 主树重建**不带动**它。查询词住在一个
  `ComboBoxQuery extends Subject`，面板 `State` 在 `initState()` 里 `watch()` 它
  ⇒ 打字 → `notifyChanged()` → `markDirty()` → 帧末 `placeOverlays()` 的 settle
  段重建面板。`OverlayEntry::$panel` 的字段注释早就写着这条设计
  （"是 Widget 不是 Closure：StatefulWidget 自己订阅状态自己重建"），本控件是
  它的第一个兑现者。
  - **为什么不用 `Cell`**：`Cell::setIfChanged()` 只标脏**它自己的属主**（同一个
    `State`）⇒ 跨不了树。`Cell` 的类注释也明说它"住在 `State` 里"。
  - **为什么不用手写注册表**：那要在 `dispose()` 里配对注销，漏一次就是永久泄漏；
    `watch()` 的订阅袋（`State::dropSubscriptions()`）已经把这件事故结构性地
    做掉了。`State` 子树本来就豁免 `subscriber-mark` 那条 lint（订阅账簿归 `State`）。
- **字段的两个状态**（`$editing`）：显示态 = 已选标签；编辑态 = 查询词（可为空）。
  切换点只有两个：**打开面板**（⇒ 编辑态 + 清空）与**面板关闭**（⇒ 显示态）。
  - 打开时**必须清空**：不清空的话打字会**追加在标签后面**（现象：选中"北京市"
    再打开、打"上" ⇒ 字段成了"北京市上"、一项都匹配不到）。这一条是写代码时
    想到的，解释器探针第一版就复现了。
  - 但清空**只在字段还显示标签时**做：用户可能在面板关着时就打了字（Tab 进来
    直接打 / Esc 之后接着改），那时点开面板不该把他的字吃掉。
- ★ **关闭路径只有一个汇合点**：`onPanelClosed()`（面板 `State::dispose()`）。
  Esc / 选中 / **点面板外** / **owner 清扫**四条路都走到那里；只在 `closePanel()`
  里复位会漏掉后两条（它们不经过控件任何代码）。
- **键盘模型（v1）**：
  - Enter 取**过滤后的第一项**（面板关着时让位 ⇒ 框架把面板开起来）。
  - 面板开着但**无匹配**时 Enter **吃掉**（不关面板、不回调）—— 否则会走到
    `toggleWidgetPanel()` 把面板关掉，用户以为自己选中了什么。
  - Esc 在面板开着时收起；关着时让位给 `TextFieldState`（清选区，既有行为）。

#### W8-2 附六 · 选项表形态（`Option::normalize()`，2026-10-24）

**动机**：`Select::make()` / `ComboBox::make()` 原先只收 `list<Option>`，而从 DB /
HTTP 拿到的数据**天生就是** `id => name`。每个调用点手写一遍 `array_map` 是纯粹的
噪音，`Option::make()` 的壳还把"值在前还是标签在前"变成一个要反复翻文档的问题。

**两种形态**（`Option::normalize()` 统一收口，两个控件共用一处）：

| 形态 | 写法 | 身份（`value`） | 显示名（`label`） |
|---|---|---|---|
| 显式对象 | `[Option::make('北京市', '110000')]` | 第二参 | 第一参 |
| 映射 | `['110000' => '北京市']` | **键** | 值 |

**为什么映射形态不违反"label/value 必须分开"**：那条裁决反对的是"**下标**当身份"
（`list<string>` 的 0/1/2，重排后指错人）。映射的**键就是身份** ⇒ 恰好满足它。
此前 `Option` 类头把"反对下标当值"写成了"反对数组形态"，是把两件事混了。

**两条 PHP 坑（不是设计选择，是语言事实）**：

1. ★★ `['110000' => '北京市']` 的键被 PHP 转成 `int 110000`（`'01'` 却仍是
   `string`）。`Option::$value` 是 `string` ⇒ 不收口就**根本装不进去**（严格类型下
   `Option::make()` 抛 TypeError，而错误信息指向 `make()`，与应用写的东西对不上）。
   所以 `(string) $key` 是必需的，且**不依赖调用方的严格类型兜底** —— AOT 的类型
   退化表不保证与解释器同形。
2. ★★ `[0 => 'x']` 与 `['x']` 在 PHP 里是**同一个数组** ⇒ "值 0"与"标签列表"在
   语言层面无法区分。所以 list 形态**只收 `Option`**，裸值一律 **Fatal**
   （`Errors::report()` 的默认级别）。不猜的理由：猜错的后果是"选中了错的人"且
   全程无报错，比启动即崩贵得多。要"值 = 显示名"写 `Option::of('北京')`。

**第三种入口：行数组（`Option::fromRows()`）**

DB 的 `fetchAll` / HTTP 的 JSON 解出来是 `list<array>`，键在**列**里而不在数组键上，
映射形态表达不了：

```php
// $rows = [['id' => 110000, 'name' => '北京市'], ...]
Select::make(Option::fromRows($rows, 'name', 'id'))->value($this->city);
```

对应 WPF `DisplayMemberPath` / `SelectedValuePath` 与 antd `fieldNames`。
**区别在失败形态**：那两家字段名拼错是**静默**的（整列空白），这里缺字段直接 Fatal
并报出「哪一行、缺哪个字段、现有哪几列」。挂在 `Option` 而不是 `Select` 上，是因为
它产出 `list<Option>`，`ComboBox` 与以后的控件都能直接用。

**反例（都进 smoke，子进程断言 exit=3 + 日志文案）**：`['甲','乙']`（裸值）、
`['' => '请选择']`（空键与 `value('')` 这个"未选"哨兵冲突）、行里缺字段、行不是数组。

**未做（明确记下，别当缺陷报）**：

- **值域泛型**：全仓 0 处泛型类，AOT 会把泛型参数退化成 `php::Var` ⇒ `value` 只能
  是 `string`，int id 由应用自己转。Flutter `DropdownButton<T>` / Qt `QVariant` /
  WPF `object` 都能装任意类型，这条**学不了**。
- **远程三态**（loading / 空 / 错）：~~补法是两个受控属性，**不需要新机制**~~ ——
  **这句被自己推翻了，见附七**。当时 `Select` 还是 `StatelessWidget`，面板的
  Widget 建一次就永不重建 ⇒ 光加两个受控属性，面板**收不到**新值。

#### W8-2 附七 · `Select` 有态化（三态 + 方向键 + 跨树重建，2026-10-24）

**破坏性变更**：`Select` 从 `StatelessWidget` 改为 `StatefulWidget`。应用侧
`options / value / onChanged` 三个方法**一个字没变**，新增 `onOpen()` 与三态。

> **2026-10-24 晚更新**：三态的三个 setter（`loading()` / `emptyText()` / `errorText()`）
> 已收成**一个** `status(OptionStatus)` —— 见附九。下面凡提到"三态"的地方，
> 机制不变，只是表达从"三个字段 + 优先级"变成"一个互斥的值"。

**为什么一件事要动三件**（三态 / 方向键 / `onOpen` 是同一个前置的三张脸）：

| 需求 | 卡在哪 | 谁负责 |
|---|---|---|
| 三态跟着受控值变 | 面板是**第二棵根渲染树**（`OverlayEntry::$panel`），主树重建不带动它 | `didUpdateWidget()` 比对签名 ⇒ `Subject` publish |
| 方向键移高亮 | 高亮是控件私有态，主树**一个字都不用变** | 同一个 `Subject`（`moveHighlight()` 故意不 `setState()`）|
| `onOpen` 打开才取数 | 只有"开面板那一刻"这个时机 | `overlayPanel` 工厂是唯一触发点 |

★ 上一版方案写的是"三态只加两个受控属性即可、**不需要新机制**"——**错**。那时
面板的 Widget 建一次就永不重建，受控属性根本送不进去。

**★★★ 坑一（本步最贵）：覆写 `didUpdateWidget()` 必须调 `parent::`**

> **2026-10-24 晚更新**：这条坑已经**收进框架**了（`Widget::overlaySignature()`，
> 见 `01-覆盖层.md` §7.3 与附八）。`Select` 现在不覆写 `didUpdateWidget()`，
> 受控值的传播由 `Application::syncPanelSignatures()` 负责 ⇒ 坑**结构上不存在**。
> 下面这段保留，是因为它解释"为什么值得为这件事动框架"，以及"忘了 parent 时
> 现象长什么样"（排查老代码还会遇到）。

`State::didUpdateWidget()` 的**唯一职责**是 `$this->widget = $widget;`。漏掉
parent ⇒ `widget()` 永远返回**旧**对象 ⇒ 签名恒等 ⇒ 面板永不更新，而
`didUpdateWidget()` 看起来被调了、不报错、不写日志（实测 `didUpdate=2 /
published=0`，三态 6 条用例红、方向键 3 条绿）。
**反向自检**：摘掉那一句 ⇒ 恰好红 6 绿 3。用例守的就是这条缝。

**★★ 坑二：帧序 ⇒ 用例必须跑两帧**

`Application::frame()` 是 ①`placeOverlays()`（先 settle 浮层 + 布局）→
②`Frame::run()`（settle 主树）。受控值一变，主树重建发生在 ②，面板的
`markDirty()` 也在 ② —— 此时浮层的布局段**已经跑完** ⇒ 新盒这一帧没排过，
下一帧才显示。60fps 下不可见（16ms），但用例按一帧写就会把"晚一帧"误判成
"没生效"。`tools/smoke.php` 里 `$ssSettle` 闭包跑两帧就是这条。

**★★ 坑三：`commit()` 先收面板、再回调应用**

反过来的话，应用的 `setState` 会先让面板带着新值重建一帧、随后才被收掉 ——
现象是"点一项，列表闪一下"。先收面板则 `$this->dismiss = null` 已经落地，
`notifyChanged()` 即使被触发也没人听（`OptionPanelState::dispose()` 已退订）。

**能力边界（如实记录）**

- **方向键 = 高亮 + Enter**，不是"移焦点"。后者要新开一条"复合控件内方向键"
  的框架缝（控件闭包拿不到 `FocusManager`），而焦点/手势是本仓出过最多 bug 的
  地方。鼠标点行与 Enter 提交走**同一个** `commit()`。
- **ESC 仍返回 `false`**（面板开着也一样）：交给浮层的 `dismissOnEsc`，自己关
  会与框架的关闭路径重复。
- **面板关着时 `keyHandler()` 一律 `false`**：`dispatchKey()` 跑在
  `activateFocused()` 之前，返回 `true` 就把"Enter 开面板"那条路堵死（现象：
  鼠标点得开、键盘打不开）。
- **没有选中值时，打开面板第一行就是 Primary** —— 那是**光标位置**，不是"已选"。
  内置字模缺 U+2713（`✓`）⇒ 两者只能同形。

**真机判据（`showcase.exe`，AOT）**：⑦ 段四态（空 / 加载中 / 失败 / 3 项）
逐个截图 + `onOpen` 计数 1→2→3→4；`--vk=28,0D` ⇒ 310000→440100、
再 `--vk=28,0D` ⇒ 环绕到 110000、`--vk=26,0D` ⇒ 环绕回 440100（两张图 md5
逐位相同，正是环绕对称）；面板关着时 `--vk=0D` ⇒ 面板打开且高亮停在当前值。

#### W8-2 附八 · 受控值 ⇒ 面板重读收进框架（`overlaySignature()`，2026-10-24）

**动机（不是"想重构"，是两个消费者已经不一致）**：

| | 受控值（Widget 上）变了 ⇒ 面板重读 | 私有态（State 上）变了 ⇒ 面板重读 |
|---|---|---|
| `Select` | `didUpdateWidget()` 比对签名 ⇒ `Subject` | 同一个 `Subject`（高亮）|
| `ComboBox` | **没有** ← 潜在缺陷 | `Subject`（查询词）|

`ComboBox::panelContent()` 读的是 `matches()`（过滤 widget 的 `options`）⇒ **面板开着
时应用换掉选项表，面板纹丝不动、不报错**。远程搜索要做的第一件事就是这个动作。

**形状**（`Widget::overlaySignature(\Closure(): string)`，与 `pointer()` / `keyboard()` /
`tooltip()` 同一族 —— 一条声明一个方法，**不给 `overlayPanel()` 加形参**）：

```php
->overlayPanel($this->panelFactory())
->overlaySignature(fn (): string => $this->contentSignature())
```

框架侧在 `placeOverlays()` 的 settle 段**之前**跑两道闸：① 锚点 Widget 换了没（`===`
比实例，`Widget` 不可变）；② 签名变了没。两道都过才 `markNeedsBuild()` 面板根。
细则与"为什么必须早于 settle / 为什么晚一帧"见 `01-覆盖层.md` §7.3。

**为什么不用"`State` 上加 `panelSignature()` 虚方法"**：`Widget.php` 的 `semantics()`
注释记着 tpc 有全程序去虚化缺陷（"基类默认 + 子类覆写"会被静默忽略）。虽然
`initState` / `didUpdateWidget` 证明 State 覆写是通的，但这条历史包袱不值得为省一个
参数去赌。**声明式字段是仓里已被真机验证过三遍的形态。**

**闸门**：smoke 1321 → **1324**（+3：ComboBox 换表基线 / 换表生效 / 同内容不重建）；
lint 462 文件 0/0；T2 AOT 27.5s。

**两条反向自检（形状不同，缺一不可）**：

1. 关掉 `syncPanelSignatures()` ⇒ **红 7**：`Select` 三态 5 + `Select` 跨树 1 +
   `ComboBox` 跨树 1。（"同内容不重建"那条仍绿 —— 不传播当然不重建，所以它单独
   证明不了闸②，必须有第 2 条。）
2. 去掉签名比对（锚点一换就标脏）⇒ **红 1**：`ComboBox 跨树 · 换的是同样的内容 ⇒
   面板不重建`（`rebuilt=yes`）。这条钉的是"应用每次重建都造新 `Option` ⇒ 面板
   每帧重建 ⇒ 滚动位置回顶部"。

**★ 一条假绿教训（值得单列）**：第 2 条用例第一稿写成
`$before = $app->optionButtons()[0]; ... $before->widget() === $after->widget()` ——
`Element::widget()` 是**活动访问器**，而 `Element::update()` 只换里面的 Widget、元素本身
复用 ⇒ 拿 Element 再读 `widget()` 拿到的永远是**当前**那个 ⇒ 断言恒真。反向自检
当场抓到（去掉签名比对仍然全绿）。**捕获实例，不要捕获访问器。**

**真机判据（`showcase.exe`，AOT）**：⑦ 段四态整条流程（开面板 / 空 / 加载中 / 失败 /
3 项 / 点选）**每一步的 PNG md5 与重构前逐位相同** —— 传播路径换了，用户看到的一个
像素都没变。方向键那一轮（`--vk`）md5 同样逐位相同。

#### W8-2 附九 · 三态收成一个值（`OptionStatus`，2026-10-24）

**动机**：下一步 `ComboBox::onSearch` 也要带三态（远程搜索必然有加载中 / 失败 / 空）。
而三态当时是 `Select` 的**私有实现**：三个字段 + 一条优先级规则
（`loading > errorText > 空表 emptyText`）。复制过去 ⇒ 规则两份实现 ⇒ 漂移，
而它是**用户可见行为**（同一个 App 里两个下拉的空态长得不一样）。

**为什么不是"共享可变对象 + 三个 setter"**：那样单一实现有了，但**优先级规则还在**
—— 仍要回答"同时成立时显示谁"，仍要靠文档 + 用例守。

**形状**：不可变值 + 静态工厂 + `int` 常量 + `===` 链（与 `OverlayEntry::BELOW`
同一条纪律：tpc 对 `switch` 生成 C2440，四个子类会引入多态派发）。

```php
OptionStatus::ready()                        // 默认
OptionStatus::loading()                      // 文案固定"正在加载…"（事实，不是文案）
OptionStatus::empty('没有匹配的城市')          // 应用声明的空态
OptionStatus::error('连接超时')
```

| 成员 | 作用 |
|---|---|
| `showsOptions()` | 面板该画选项行吗 |
| `row(): ?Widget` | 面板里那一行（`ready` ⇒ `null`） |
| `signature()` | 面板内容签名的那一段（两个控件**共用**） |

**结构性收益**：**优先级规则消失了**。"重试时 error 与 loading 都真"在类型上不存在
—— 设了 `loading()` 就没有错误态可言。旧版专门有一条 smoke 守"loading 优先于
error"，现在那条用例被删掉，换成"error 之后设 loading ⇒ 只剩正在加载（值替换）"。
★ 也因此**没有** `setLoading(false)`：要回正常态就 `ready()`；有"关"的开关就又能
拼出"不在加载、也没错、但也不正常"的第三种含糊状态。

**内置兜底 ≠ 声明的空态**（这条容易混）：

| 情形 | 谁给文案 |
|---|---|
| `options === []` 且状态是 `ready()` | **控件内置**（`Select` = "没有可选项"，`ComboBox` = "无匹配项"）|
| `OptionStatus::empty('…')` | **应用**给 |

两者语义不同（"没东西可选" vs "搜不到"），所以兜底留在各自控件里，只有"应用主动
声明这是空态"才走 `empty()`。

**破坏面**：三个 setter（`loading()` / `emptyText()` / `errorText()`）取消 ——
它们是一天前刚加的，消费者只有示例台与 smoke。

**闸门**：smoke 1324 → **1325**（删 1 条优先级用例、加 2 条）；lint 462 → **463**
（+1 文件）；T2 AOT 30.3s。

**反向自检**：把 `OptionStatus::signature()` 改成恒返回 `''` ⇒ **红 5**（三态驱动的
那几条）。而"空表 + ready ⇒ 内置文案"**仍绿** —— 它靠签名里 options 那一段，
正好说明两段签名彼此独立。

**真机（AOT）**：⑦ 段 9 步里 **8 步 md5 与收口前逐位相同**；唯一变的是"初始空态"
那一步 —— 文案从"没有匹配的城市"改成"还没取数"（有意为之：取数之前说"没有匹配的
城市"是错的）。

#### W8-2 附十 · `ComboBox` 远程搜索（`onSearch` + `status`，2026-10-24）

`ComboBox` 一直是"候选表就在手上"的本地过滤。远程搜索是另一套：**打字 ⇒ 问服务端
⇒ 换选项表**。三个加性方法：`status(OptionStatus)` / `onOpen()` / `onSearch()`。

**四条决定**（每条都对应一处会静默出错的写法）：

| # | 决定 | 不这么做会怎样 |
|---|---|---|
| 1 | `onSearch` 挂在**用户输入**上，不挂在"查询词变了"上 | 查询词有三个写入点（打字 / 开面板清空 / 关面板复位），后两个是控件自己的状态管理 ⇒ 每次开关面板都发一次"搜索空串"请求 |
| 2 | 声明了 `onSearch` ⇒ **本地过滤让位** | 服务端可能按拼音 / 按 value 匹配，本地再按标签子串筛一遍是**二次收缩**：服务端返回 8 条、面板只显示 2 条，而它看起来像服务端的问题 |
| 3 | Enter 跟着三态闭（`!showsOptions()` ⇒ 吃掉） | 加载中面板里没有选项行，但应用**很可能还留着上一批 `options`**（不清旧数据以免闪烁）⇒ Enter 选中一个用户根本没看见的项 |
| 4 | **不做去抖**，契约是"每改一次词回调一次、且带上当时的词" | 控件侧去抖要定时器，而定时器只有 `Application::after()` 有（§4.3 禁 `Widget → App`）|

第 2 条的判据用"有没有声明回调"，**不另加一个开关**：两个旋钮又能拼出"声明了搜索
但本地也筛"这种含糊状态（与附九同一条纪律）。

第 4 条不是省事，是分工：控件报告**时机与事实**，调度归应用（`Job` + 请求序号丢弃
过期响应）。与 `Select::onOpen` 同一条线 —— 控件从不猜"取数该怎么做"。

**顺带修掉的静默缺陷（`onSearch` 一上就必然踩到）**：

`fieldText()` 靠"在当前 `options` 里找 `value`"得到标签。远程搜索会把选项表整个换掉
⇒ 选中"北京市"之后搜"上"，表里已经没有 `110000` ⇒ **框变空白，用户看到的是"值丢了"**。
修法：`ComboBoxState` 记最后一次**真见过**的 `(value ⇒ label)`，表里找不到且值相同
时用它兜底；**值不同不冒充**（没见过的值仍返回空串，让 placeholder 出来）。

**闸门**：smoke 1325 → **1338**（+13 条）；lint 463 文件 0/0；T2 AOT 32.5s + selftest。

**六条反向自检**（每条都恰好红在该红的地方）：

| 自检 | 结果 |
|---|---|
| 去掉 `matches()` 的让位 | 红 1（`rows=[北京市]`，服务端给的"上海市"被本地筛掉）|
| 把 `onSearch` 接到开面板的查询词清空上 | 红 2（"内部清空不触发" + 后续 `searched=[,北]`）|
| 去掉 Enter 的三态闸 | 红 2（加载中 Enter 选中了、面板被关）|
| 去掉标签记忆 | 红 1（字段 `text=''`）|
| 去掉 `wantsFrame()` 第六条判据 | 红 1（`wantsFrame=false`）|
| `after()` 基准改回只取"上一帧" | 红 1（`fired=1`，+100ms 就触发了）|

**量具教训**：打字之后必须跑**两帧**。`onSearch` 的回调把 status 改成 `loading`，而面板
内容读的是"锚点当前那个 Widget" —— 它要等主树 settle 之后才换。第一帧面板还会用**旧**
Widget 重建一次（`$query` 广播带出来的），第二帧框架的签名闸才看到新 Widget。只跑一帧
⇒ 现象是"面板还是 4 个城市"，看起来像三态没生效。

### 附十·续 · 真机暴露的两个框架缺陷（2026-10-24）

这两条都是 **smoke 全绿、真机不对**，而且都只有"示例台真的点一遍"才能抓到 ——
它们是本步最有价值的产出，不是 ComboBox 的 bug。

#### ① 面板内容永远停在旧值：`wantsFrame()` 缺"面板落后"判据

`syncPanelSignatures()` 跑在 `placeOverlays()` 里，而主树在它**之后**才 settle
⇒ 那一帧它看到的锚点还是**旧** Widget，只能等下一帧。

- smoke 里"跑两帧"是**显式写的**（`$cbSettle` / `$ssSettle`）⇒ 从来看不出问题；
- 真机上**没有下一帧** —— 应用处理完一次 `setState` 就静默了（`wantsFrame()` 前五条
  判据全假），帧时钟不上膛 ⇒ 面板永远停在旧内容。

实测证据：`deliver()` 的日志明明 `q='北' n=2`，面板还列着旧的 4 项。

修法：`wantsFrame()` 加**第六条判据** `panelsLagBehind()` —— 有浮层的锚点 Widget
换了、但还没同步 ⇒ 必须再跑一帧。**自终止**：`syncPanelSignatures()` 无论签名变没变
都会更新 `seenAnchor` ⇒ 下一帧判据即为假，不空转。

#### ② `after()` 的基准在空闲应用上是错的 ⇒ 延时不生效

`after()` 用"上一帧时间戳"当基准（G3：框架不自己读钟）。但 `after()` 常被**帧外**
的回调调用（指针点击 → `onOpen`），而空闲应用的"上一帧"可能是几百毫秒前 ⇒ `due`
落在过去 ⇒ **定时器当场触发**。实测：远程搜索的"正在加载…"一帧都没出现过。

修法：**由壳把输入时刻带进来**（`dispatchInput($event, $platform->now())`），
`after()` 的基准取 `max(上一帧, 上一次输入)`。

- 为什么不是"在 `pumpTimers()` 里发现 `due` 已过期就重算"：那条**分不清**
  "应用空闲"与"用例把时钟直接跳过去了" —— 现有的延时用例正是后者（帧戳 2000 → 2100
  一步跨 100ms），重算会把它们全打红。试过，红 5。
- 为什么不是"给 `Application` 一个时钟"：`Platform::now()` 是实例方法，而
  `Application` 按 §5.1 不持平台。让壳在**派发输入时**顺手递一个时间戳，是这条
  约束下唯一不破边界的做法。
- ★ 第 2 参不传 ⇒ 基准退回"上一帧"，与改动前**逐字节相同** ⇒ smoke 的 1336 条
  既有断言一条都不用改（这正是它可被接受的理由）。

**真机（AOT，`_build/probe-p16.php`，7 步 7 个不同 md5）**：

| 步 | 画面 | md5 |
|---|---|---|
| open（+200ms）| 面板「正在加载…」 | `9fd113bc…` |
| open（+900ms）| 面板 4 项（北京市/上海市/广州市/北京南站）| `f9d6e197…` |
| 打「北」（+200ms）| 字段「北」、面板「正在加载…」| `1e585c7c…` |
| 打「北」（+900ms）| 面板 2 项（北京市/北京南站）| `db124270…` |
| 点第一项 | 字段「北京市」、当前值 `110000`、"onSearch 已收到 2 次" | `c6920631…` |

**量具纪律（这一轮踩到的）**：`--click-wait` 默认 600ms > 模拟的 400ms 延时 ⇒
默认参数下**永远**抓到结果态、看不到加载态。要抓中间态必须把它压到 200ms。

#### W8-3 附十一 · `Grid` / `LazyGrid`（2026-10-24）

W8-3 原计划四件：`Grid`/`LazyVGrid`、`Wrap`、`AspectRatio`、`LazyRow`。动手前先做了一次
方向核对，结论改了其中一件的做法、否了另一件。

**① `Wrap` 不做 —— 而且不该按原计划"兑现 `Overflow::Wrap`"**

`04` §4.4 明确否决过 `Wrap` / `Grid`，理由是"需要两遍布局 + 布局迭代"。但那条否决把
两件事并列了，**并列是错的**：

| 原语 | 一行放几个 | 要什么 |
|---|---|---|
| `Wrap` | **量完才知道**（按子项自然宽贪心累加）| 两遍布局；"分几行"决定容器高 |
| `Grid` | **应用给的**（`columns`）| 一个除法：`(可用宽 − 间距) / 列数` |

而那个除法 `Row` + `Expanded` 已经做了。所以 `Grid` 不触碰否决，`Wrap` 仍然触碰。
另有一条更硬的：`Overflow` 的语义是**舍弃方式**（Clip / Report 都是"装不下怎么办"），
`Wrap` 不是舍弃而是**重排** ⇒ 塞进这个枚举是类别错误（`Overflow::Wrap` 在 `RenderFlex`
和 `RenderDock` 里各躺了一个"尚未实现"的死分支，正是这个错误的证据）。`04` §4.4 的
推翻条件（"出现子项数运行时才知道 + 必须自动换行"的真实需求）今天没有满足 —— 唯一
消费者会是示例台自造的标签云，拿合成需求推翻一条布局纯函数性的取舍不划算。

**② `Grid` 是纯组合：零新渲染盒、零新 Element、零布局迭代**

`build()` 只做两件事：切块（`Grid::chunk()`）、每块造一个 `Row`（`Grid::rowOf()`）。
格子是 `Expanded` 包住的子控件 ⇒ 命中测试 / 裁剪 / 内禀尺寸 / diff / AOT 全部沿用
既有路径。**它补的洞只有一个**：末行不满时 `Expanded` 会把剩余宽度均分给**剩下的**
格子 ⇒ 末行卡片变宽。这个错很安静（画面"只是有点不对"），只在最后一行不满时出现，
而数据量恰恰经常让它不满。所以 `rowOf()` 给末行补 `Spacer`（= 没有孩子的 `Expanded`）。

**③ `LazyGrid` = `LazyColumn` 套 `Grid`**

items 先切块，每块一行交给 `LazyColumn` ⇒ 视口计算 / 锚点恢复 / `overscan` / `keyOf` /
滚动全部继承，本类只做分块。两条纪律：
- **行节距含行距**（`格子高 = 节距 − 行距`），与 `itemExtent` 同口径 —— `LazyColumn`
  也没有独立的行间距参数；
- **分行规则与全量版共用**（`Grid::rowOf()`）：同一批数据在"全量"与"懒"之间切换，
  格宽必须逐像素一致，两处各写一遍就一定会漂移。

**④ 能力边界**：不做跨列（`columnSpan` 要回溯约束 —— 那才是 §4.4 否决的那条）、
不做自动列数（那是 `Wrap` 的语义）、不做竖向网格（无消费者）。

**闸门**：smoke 1338 → **1348**（+10）；lint 465 → **466 文件 0/0**；T2 AOT 36.0s + selftest。

**三条反向自检**（每条都恰好红在该红的地方）：

| 自检 | 结果 |
|---|---|
| 去掉 `rowOf()` 里补 `Spacer` 的 while | 红 3（末行格宽 162 而不是 104）|
| `LazyGrid::cellHeight()` 不扣行距 | 红 2（格子 96 而不是 84；"行距 ≥ 节距"守卫也不再触发）|
| `chunk()` 的切块宽度改成 `columns − 1` | 红 3（5 项变 3 行）|

**两条量具教训**：

- **`Errors::report` 走 `abort()` ⇒ 真的 `exit(3)`，进程内 `try/catch` 接不住**
  （`exit()` 不是异常）。第一稿把"列数 0 ⇒ 响亮失败"写在进程内 ⇒ smoke 在那一行
  **静默截断**：无汇总行、无 FAIL、退出码还是 0（管道吃掉了子进程的退出码）。
  正确形状是本仓既有的 `runCase(__FILE__, 'case名', null)` + 断言 `code === 3`。
- **`offsetY()` 是相对父盒的**：`LazyColumn` 把每个 item 包在 `SizedBox(height: 节距)`
  里 ⇒ 行盒的 `offsetY()` 恒 0（它相对那个 `SizedBox`）。行节距要用
  `RenderBox::absoluteOrigin()`。同理"格子高"要量子盒 —— 行盒自己被紧约束撑成节距。

**真机（AOT `showcase.exe`，页 17）**：页面正常建出（`ink=12.8`），LazyGrid 滚轮生效
（格 1 → 格 9 → 底）。② 段的末行宽度是**量出来的**，不是看出来的：首行「一」x=219、
「二」x=790；末行「四」x=219、「五」x=790 —— 逐像素相同。
★ 第 3 次滚轮 md5 与上一张相同，是**合法状态**（已经到底），不是"滚动坏了"。

#### W8-3 附十二 · `AspectRatio`（2026-10-24）

**方向核对改了一件事**：原计划写的是"需要一个约束→尺寸映射的渲染盒"。核对后**不需要
渲染盒** —— 比例与 `width` / `height` 是同一类修饰（"约束 → 约束"），只是联动两轴。

**形状（三层，零新原语）**：

| 层 | 落点 | 职责 |
|---|---|---|
| 几何 | `BoxConstraints::applyAspect(float $ratio)` | 纯函数：约束 → 紧约束 |
| 修饰 | `Modifier::aspect(float $ratio)`（`NAN` = 未设） | 与 `width` / `height` 同族；`tighten()` 在显式尺寸**之后**调上一行 |
| 控件 | `Widget::aspect()` + `AspectRatio` 便捷壳 | 任意控件可贴；壳与 `Center` 同构（`RenderProxy`） |

**求解口径**（`applyAspect()`）：两轴都紧 ⇒ 原样（比例无自由度）；一轴紧 ⇒ 另一轴
按比例推（**显式尺寸优先**）；都松 ⇒ 先铺满有界那轴、超界回退；都无界 ⇒ 原样。
末尾 `min/max` 夹取可能不严格 —— 父的下界优先（与 `tighten()` 同一条）。

**比例作用于盒（含 padding）**：先解比例、再内缩内边距 ⇒ `->aspect(2)->paddingAll(10)`
是"外框 2 : 1，内容区比外框小 20"。

**闸门**：smoke 1348 → **1353**（+5：铺满宽 / 高不够回退 / 显式 width 优先 /
两轴定死 / 含 padding）；lint 466 → **468 文件 0/0**；T2 AOT（增量 33–42s）。

**反向自检**：`applyAspect()` 恒返回入参 ⇒ 红 4（"两轴定死"那条仍绿 —— 它验证的
正是"比例无效"）。

**真机（页 18）发现的一个 AOT 坑**：`AspectRatio::make(16 / 9, ...)` 真机画出近正方形
（约 640×640），而 smoke 断言 640×360 全绿 —— tpc 把常量 `16 / 9` 生成成 C++ 的
`int / int` ⇒ 1。判据是页面里那行诊断文字：真机显示 `16 / 9 = 1；16.0 / 9.0 =
1.7777777777778`。**比值一律写浮点字面量**（`16.0 / 9.0`）。

#### W8-5 附十三 · `RichText` / `Span`（2026-10-24）

**方向核对**：最直觉的落点是"把颜色塞进 `TextStyle`"（CSS 同构）。核对 §8.1 后否掉：
`TextStyle::cacheKey()` 是**排版缓存键**，纪律是"凡是影响排版的输入都必须在 style 里"；
反过来同样成立 —— **不影响排版的输入不该进键**。颜色放进 `TextStyle` 会让"只换颜色"
也整段重排，且把 style 从"排版输入"污染成"排版 + 绘制"混合体。

**落点（颜色跟着 span 走，`TextStyle` 零改动）**：

| 层 | 改动 |
|---|---|
| `TextSpan`（新） | `(text, TextStyle, int argb=-1)` —— `int` 而非 `?Color`（AOT 可空对象退化） |
| `GlyphRun` | 加 `int $argb = -1`、`withColor()`、`shifted(offset)` |
| `TextLayout` | 抽 `layoutRuns()`；新增 `layoutSpans()`（span 各自整形 + cluster 抬到全文偏移）；`breakLines` / `measure` / `sliceRuns` 改用 **run 自己的** `letterSpacing` |
| `Paragraph` | 新增 `keyForSpans()` —— **不含 argb** |
| `TextMetricsProvider` | 接口加 `layoutSpans()`（唯一实现同步） |
| Canvas ×2 | 按 run 取色 / 字号（`RecordingCanvas` 只记录，不改） |
| 控件 | `RichText` + `Span`（fluent 增量：color / bold / size） |

**关键词**：`sliceRuns()` 本来就在按 `$flat[$i]['r']` 分组切 run ⇒ 多 span 只需要
"shaper 吃多段 + 偏移 + 行高按最大字号"，**不是重写排版**。

**行高**：`layoutSpans()` 把段落 style 的 size 抬到 **max span size** ⇒ 32pt 的数字
不会被 14pt 的行高压扁。单段 `layout()` 不走这条路径。

**兼容性**：`TextStyle` 零改动、`GlyphRun` / `Glyph` 只加默认参数、单段路径读到的
run style 就是传入的 style ⇒ **逐字节不变**。闸门：smoke **1353 → 1357**（+4）；
lint 468 → **472 文件 0/0**。

**反向自检**：

| 自检 | 结果 |
|---|---|
| `layoutSpans()` 不调 `shifted()` | 红 1（后段 cluster=0） |
| `keyForSpans()` 把 argb 拼进键 | 红 1（两键不同） |

**续作：行内链接 + 下划线（同日，`Span::tag` / `onSpanTap`）**

- `Span::tag('retry')` + `RichText::onSpanTap(fn(string $tag))` ⇒ 点击命中。
  命中走 `Paragraph::tagAt(x, y)`（`indexAt()` 的字节偏移 → 覆盖它的 run 的 tag），
  **不另算 pen**；`RenderRichText::tagAtClient()` 只做一次 `absoluteOrigin` 换算。
- 事件复用既有的 **`pointer()` 缝**（`ownsPress=true`）⇒ 按下被控件接管、move/up
  直达同一回调，**不引入第六个手势状态**；`Application` 不认识 `RichText`。
- 下划线在**盒内**画（`RenderRichText::paintContent()` 用 `RecordingCanvas` 画 1px
  矩形），随 DisplayList 一起 replay ⇒ Raster / Skia 后端一行不改。
- 真机（页 19 ⑤）：点「重试」两次 ⇒ 计数 0→1→2；点旁边文字 ⇒ 画面 md5 **不变**。

**续作二：盒级光标（`RenderObject::cursorAt()`）**

手型光标原来的阻塞点是"光标只能整段声明"（`Widget::cursor()` 沿命中链生效）。解法不是
给 `RichText` 开后门，而是把光标解析下沉一层：

- `RenderObject::cursorAt(float $x, float $y): ?CursorShape`（默认 `null` = 不表态）；
  坐标是**盒局部**，与 `hitTest()` 同口径。
- `RenderRichText` 覆写：`tagAt(x, y) !== ''` ⇒ `PointingHand`，否则 `null`。
- `Application::cursorFor($hit, $x, $y)` 收成**唯一入口**：先问盒（位置比控件更具体），
  不表态才回落 `FocusManager::cursorOf()`；原先 4 处 `cursorOf` 全部走它。
- 探针 `probe-grab --cursor=x,y` 现在额外输出 `cursor_shape=hand|arrow|...`
  （壳用 `LoadCursorW(NULL, IDC_*)`，系统预定义光标句柄跨进程可比较）。

真机（页 19 ⑤）：悬停「重试」⇒ `cursor_shape=hand`；悬停旁边「加载失败，」⇒ `arrow`。

**续作三：背景色（`Span::background`）**

- `TextSpan` / `GlyphRun` 加 `background`（ARGB，`-1` = 无）；`Span::background(Color)`。
- 背景高度 = 该 run 的**字体内容区**（`baseline − ascent .. baseline + descent`，
  按 run 自己的字号），**不是整行高** —— 大字号 span 的背景贴着字，不会把行距也涂上。
- 绘制抽成 `RenderRichText::paintRunDecorations()`：一个循环处理"背景 + 下划线"，
  顺序是**装饰 → 字形**（背景必须垫在字下面）；仍在盒内画，后端零改。
- 缓存键不含 `background`（与颜色同一条纪律）：改背景不重排。
- 真机（页 19 ⑥）：`_build/measure-color.php` 量出浅绿 83×16、浅黄 44×16，
  同一行 `y=492..507`（= 内容区高 16，不是行高 19.2）。

**续作四：`State::didChangeFocus()` + 键盘可达**

键盘可达原来卡在"焦点变化没有通用出口"：`FocusManager::enter/leave` 里只有
`instanceof TextFieldState` 的特例 —— 框架认识一个具体控件，别的控件想知道
"我被聚焦了吗"没有路。

- `State::didChangeFocus(bool)`：焦点进出的**唯一钩子**（默认空）。
  `FocusManager::enter/leave` 只调它；`TextFieldState` 覆写它（进出编辑态），
  `FocusManager` 里的 `instanceof` 特例**删掉**。
- 为什么是 `State` 而不是 `Widget` 上的闭包：焦点态必须存在**跨重建存活**的地方。
  实测过"把 `$focused` 放盒里"——`syncBox()` 每次 `setState` 都造新盒，状态立刻丢。
- `keyboard()` 的 handler 补第二个参数 `Element`（与 `pointer()` / `hover()` 同形）：
  原来只传 `KeyEvent`，控件拿不到盒就没法按"盒上的状态"决定行为。老的单参写法
  在 PHP 里忽略多余参数，AOT 也编过（实测 102s 通过）。
- `RichText::onSpanTap()` 顺带 `markFocusable()` + `keyboard`（Enter ⇒ `firstTag()`）。

真机（页 19 ⑤）：点普通文字把焦点落到 `RichText`（计数不变）⇒ 按 Enter 两次 ⇒
计数 0→1→2。

**能力边界（两条，都是这次实测出来的）**：

- **没有焦点高亮**：全仓还没有焦点视觉（`Button` / `Slider` 也没有）。给 `RichText`
  单独加会需要 State 级状态，是另一个议题。
- **多链接的 Tab 细分未做**：需要"一个 Element 内多个焦点停靠点"（焦点组），
  是焦点链结构级改动。当前语义是"整段一个焦点点 + Enter 触发第一个链接"。

**续作五：焦点视觉（焦点环，全仓级）**

键盘用户此前**完全看不见焦点在哪**（`Button` / `Slider` / `TextField` 都没有焦点视觉）。
这不是 RichText 的问题，是全仓缺口。

- 落点：`Frame::run()` 加 `?\Closure $afterPaint`（树与浮层都画完、`endFrame` 之前），
  `Application::paintFocusRing()` 在里面画 —— **零控件改动**，任何可聚焦控件自动有环。
- 样式：**2px 外扩**描边（`drawRect` 只有填充 ⇒ 四条边拼），主题 `Accent` 色；
  直角、不跟随控件圆角（MVP）。
- 为什么不做成 `Modifier` / 控件自绘：要么每个盒都得知道"我在焦点上"（盒状态跨
  重建会丢），要么给 `RenderObject` 注入焦点查询 —— 都比这一处多。
- **`wantsFrame()` 加第七判据**：`focused() !== $paintedFocus` ⇒ 再画一帧。
  焦点环是应用级叠加、不经过任何 `setState` ⇒ 没有这条，换焦点后环要等**下一次
  鼠标移动**才出现。有界：画完记录 ⇒ 立刻回落 `false`。

闸门：smoke 1366 → **1370**（+4：wantsFrame 真/回落、无焦点不画、像素 `#0969DA`）；
lint 473 文件 0/0。真机（页 19 ⑤）：点链接 ⇒ `RichText` 外围出现 2px 蓝色描边。
反例：`paintFocusRing` 直接 `return` ⇒ 像素断言红（`rgb=255,255,255`）。

**续作六：`:focus-visible`（指针操作不显示环）**

续作五的环"只要有焦点就显示" ⇒ 每次点按钮都闪一圈蓝框（Windows 里不是这样）。

- 输入模态：`Application::$keyboardFocusVisible`，在 `dispatchInput()` **最前面**更新
  （`KeyEvent` ⇒ 真；`PointerEvent` / `ScrollEvent` ⇒ 假）。初值 `false` ⇒ 启动时
  第一次点击不该看到环。
- **`focusRingTarget(): ?Element`** 纯函数收口两处消费者：`paintFocusRing()` 画它、
  `wantsFrame()` 比对它。★ 这条很关键：若 `wantsFrame()` 仍比 `focused()`，
  "点击隐藏环"会被判成"没变化" ⇒ 环要等下次输入才消失。
- 真机（页 19）：点链接 ⇒ **无环**（`p19-3-tap1.png`）；按 Enter ⇒ **有环**
  （`p19-8-enter1.png`，与续作五那张逐字节相同）。

闸门：smoke 1370 → **1372**（+2：点击后隐藏、隐藏也请求一帧）；lint 474 文件 0/0。
反例：`focusRingTarget()` 忽略模态 ⇒ 红 2（环仍画、`wantsFrame` 为假）。

**仍未做**：圆角跟随、焦点环滚出视口时的裁剪（当前直接按绝对坐标画）。

**仍未做**：行内图标（object replacement + 图片 run）、删除线（加一个字段 + 一个分支即可）。

#### W8-2 附 · 两条输入缝（2026-10-23，Slider 立的范式）

| 声明 | down 归谁 | 说明 |
|---|---|---|
| `pointer($h, ownsPress: true)` | **本控件** | 框架捕获它、把 `down` 交过去、**跳过** `activateFocusedWidget()`；焦点照旧落上去（键盘可达）|
| `pointer($h)`（默认） | 框架激活 | 只在捕获期被调（`OverlayLab` 的锚点按钮就是这个用法）|
| `Draggable` | GestureArena 裁决 | 过阈值才算拖 |
| 都没有 | 框架激活 | A15 行为 |

- `keyboard(\Closure(KeyEvent): bool)`：返回 `true` = 吃掉。**沿焦点控件的父链找
  "最近的声明者"**（2026-10-24 之前只读焦点控件自己的 widget ⇒ 包裹层的声明是死的，
  见附四）；找到的那个在 `TextFieldState` 之前调。方向键调值 / 上下选 / 翻页都走它。
- ★ 两者都是**加性**（默认 `false` / `null` ⇒ 既有控件逐字节不变）。
- ★★ `ownsPress` 复用 `$captureNode` ⇒ **不引入第六个手势状态**，四条收口路径
  （抬起 / 卸载 / 失焦 / 浮层外按下）全部现成。**不要**给控件再写一套手写拖动状态
  （`$thumbDrag` 已是第二套，第三套必然走样）。
- ★ `pointer()` 分支必须排在 `Draggable` **之前**：它是"我自己处理指针"的最深声明，
  比祖先的拖放更具体（否则"可排序列表里放一个 Slider"会被祖先抢走按下）。
- ★ 命名是 `keyboard()` 不是 `key()` —— 后者已被 diff 身份 `key(Key)` 占用。

## 2. 通用纪律（承 arch-v2，不因是新功能而松）
- 每控件一次 T2（建 `showcase`，它有 `CustomPaintPage`/`Stack` 演示；`users` 缺控件消费者）。
- **smoke 全绿 ≠ 真机正确**：每个交互控件必须真机看图/驱动。
- 新增"产 `RenderProxy` 的单子控件"必须同时加 `Widget::expandChildren()`（漏了 = 子不挂载、静默空白）。
- 有态+有盒+无子走 `createRenderObjectFromState()` 叶子路径；有子的走 `build()`+`*Box`。
- 受控值（值住应用 State，控件只回调），不自持"任务语义"。
- 双后端能力必须等价（都支持或都响亮失败）；新 draw op 过 T2。
