# 异步 API 的开发者手感评估（2026-10-30）

> 问题：**当前异步接口对开发者友好吗？心智负担大吗？对比成熟 GUI 有没有优化空间？**
>
> 这一份的判据是**可数的事实**（要掌握几个概念、要写几行样板、要记住几条隐性纪律），
> 不是"感觉还不错"。凡是"可以更好"的地方，都给出落点与代价。

---

> ★ **2026-10-30 第二轮（同日，接 §5）**：上面两处负担里的"一次请求的生命周期"
> 已经收成 `AsyncCommand`（P1 落地），而且它是**替换不是加法** —— `AsyncCommand`
> 是 `FutureBuilder` 的超集，所以 `FutureBuilder` **已删除**，UI 侧不再有专用异步
> 控件（见 §5.1）。"穿参"那一处经复核**不做**沿树查找（`BuildContext` 三条边界
> 与 §18 已否决），改成组合根打包（§5.3）。
>
> ★★ **2026-10-31 第三轮（收敛到一套）**：`AsyncCommand` 从"只能住 `State`"改成
> **`extends Subject`（宿主无关）** ⇒ 跨页共享那条路用上了同一个类，`apps/users`
> 的 `UserStore` 里那份**手写状态机被删除**（连带 `LoadStatus` 枚举）。
> 页面侧的入口收成 `State::asyncCommand()`（与 `State::cell()` 同一条路），
> 而且**连 `dispose()` 都不用写了** —— 卸载时由框架统一停掉在途任务。

## 0. 一句话结论

**"怎么画"这一层已经和 Flutter 平手；负担全在"Future 从哪来"和"一次请求的生命周期"两处。**

- `FutureBuilder` + `AsyncValue` 的用法与 Flutter `FutureBuilder` + `AsyncSnapshot` **同构**
  —— 一个 future、一个四态 builder，没有额外概念。
- 但 Drift 多出两笔 Flutter 没有的开销：
  ① **依赖靠手写闭包穿参**（同一个能力从组合根递到页面要改 **6 处**）；
  ② **"一次请求"没有任何对象承载**（`?Future` 字段 + `load()` + `dispose()` 取消
     + 去重判断，每页重写约 15 行纯代码 / 50 行含注释）。
- 再加一笔**架构必然的税**：`Job` / `NamedJob` / `args()` —— 进程隔离必须可序列化，
  `await api.fetch()` 这种写法在这里不存在。这笔税**只能付在组合根**，页面不该感知；
  目前恰好是这样（页面只认 `\Closure(int): Future`），这点做对了。

## 1. 换算成开发者的账

### 1.1 一个"进页面就加载、失败可重试、能翻页"的表格页要写什么

`apps/showcase/src/Pages/AsyncTablePage.php`（本仓的真实接入示例，303 行）的构成：

| 段落 | 行数 | 其中纯代码 | 是否"异步特有" |
|---|---|---|---|
| 类注释（讲清数据来源、为什么整页进 builder） | ~30 | 0 | 一次性，可复用为模板 |
| 页面壳：`__construct` / `make` / `createState` | ~20 | ~14 | 否（所有 StatefulWidget 都要） |
| **异步簿记**：`?Future $future` + `load()` 去重 + `dispose(){cancel}` | **~50** | **~15** | **是 —— 每页重写** |
| `build()` + `toolbar()` + `bodyOf()`（四态画法） | ~105 | ~70 | 部分是（四态分支 ~30 行是必要的） |
| `columns()` 等纯业务 | ~27 | ~20 | 否 |

⇒ **异步簿记的纯代码只有 ~15 行，但要理解它得读 ~50 行注释** —— 这正是"心智负担"
的形态：不是打字多，是**每次都要重新确认"我要不要 cancel / 要不要去重"**。

★ 行数按 303 行版本数（2026-10-30 改完后）。"纯代码"= 去掉注释与空行，是估算。

### 1.2 要掌握的概念数（写页面的人必须懂）

| # | 概念 | 不懂会怎样 |
|---|---|---|
| 1 | `Future`（`pending` / `resolved` / `rejected`） | 不知道 `rejected` 没人接会走 Fatal |
| 2 | `AsyncValue` 四态 | 漏一态落进 `else` ⇒ 画空白 |
| 3 | `AsyncCommand`（`run()` / `value()` / `retry()`；`FutureBuilder` 已被它取代，见 §5.1） | 以为还能"把 Future 交给控件去投影" |
| 4 | `State` 生命周期：`initState` 订阅 / `didUpdateWidget` / `dispose` / `setState` 只标脏 | 在 `build()` 里订阅 ⇒ 逐帧增长 |
| 5 | 闭包穿参（同一个能力 6 处） | 加能力时漏改一处 ⇒ 页面拿到旧闭包 |
| 6 | `Job` / `NamedJob::args()`（只有真跑后台才需要） | 忘了 `args()` ⇒ worker 侧重建时参数丢失 |
| 7 | AOT 纪律（`?->`、枚举、外部常量、`parent::__construct()`） | 解释器能跑，AOT 真机 exit=255 |

**Flutter 同等任务是 3 个概念**（`Future`、`AsyncSnapshot`、`FutureBuilder`）+ 1 个依赖查找。
**WPF 是 3 个**（`Task`、`INotifyPropertyChanged`、`IAsyncRelayCommand`）+ DI 容器。

⇒ Drift 多出来的是 **5（穿参）**、**6（Job）**、**7（AOT）**。
其中 6 是架构必然、7 是编译器约束，**只有 5 是框架设计可以改的**。

## 2. 与四家成熟 GUI 的逐项对照

同样是"表格取数 + loading + 错误 + 重试 + 翻页"：

| 维度 | Flutter | WPF | Qt | React Query | **Drift（本轮之前）** |
|---|---|---|---|---|---|
| 异步值类型 | `Future<T>` | `Task<T>` | `QFuture<T>` | `Promise` | `Future` ✅ |
| 状态快照 | `AsyncSnapshot<T>` | 手写 `IsBusy`+`Error` | `QFutureWatcher` 状态 | `{data,isLoading,error}` | `AsyncValue` ✅ |
| UI 绑定 | `FutureBuilder` | `IAsyncRelayCommand` + 绑定 | `finished` 信号 | `useQuery` | `FutureBuilder` ✅ |
| **取消** | 靠 `Future` 无法取消，用 `CancelableOperation` | `CancellationToken` | `QFuture::cancel()` | `AbortSignal` | `Future::cancel()`（两档语义）✅ |
| **去重 / 重入** | 手写 | 手写 | 手写 | **内建**（同 key 共享） | **手写**（本页靠 `$force`）⚠️ |
| **重试** | 手写 | 手写 | 手写 | **内建**（`retry: 3`） | **手写** ⚠️ |
| **超时** | `.timeout()` | `CancellationTokenSource` | `QTimer` | **内建** | **无** ❌ |
| **依赖注入** | `Provider` / `ref.watch(ctx)` | DI 容器 | 手动 / `qApp` | `Context` | **手写穿参 6 处** ❌ |
| **异步值的"从哪来"** | 直接 `await api.x()` | `await api.x()` | `QtConcurrent::run` | `queryFn` | **`Job` + `NamedJob` + `args()`** ⚠️（进程隔离的税） |
| 回调线程保证 | 单 isolate | `Dispatcher` 亲和 | 对象亲和 | JS 单线程 | UI 线程帧内 ✅ |
| **同帧重绘** | 否（下一帧） | 否（`Normal` 优先级在 render 之后） | 否 | 视调度 | **是**（泵在 `settle` 之前）✅ |

**读表要点**：

- ✅ 的四行说明**核心机制不落后**，其中"同帧重绘"和"取消两档语义"比 Flutter 更明确。
- ⚠️/❌ 集中在**"重复劳动"**（去重 / 重试 / 超时 / 注入）—— 这四件恰好是 React Query
  一个 `useQuery` 全包的，而 Drift 要每页手写。
- `Job` 那行是 ⚠️ 而不是 ❌：它不是缺能力，是**换了一种付法**（组合根付一次，页面零感知）。

## 3. 本轮查出的五处真负担

按"会咬人程度"排序。

### Q1 `didUpdateWidget()` 要求覆写者调 `parent::` —— **框架自己能做的事推给了每个开发者**

**证据**：`State::didUpdateWidget()` 原本只有一行 `$this->widget = $widget;`，
而它是 `$widget` 字段（`private`）**唯一**的更新点。于是覆写者必须记得：

```php
public function didUpdateWidget(Widget $widget): void
{
    parent::didUpdateWidget($widget);   // 漏了 ⇒ $this->widget 停在旧值
    ...
}
```

本仓四处覆写**全都老实写了**这一句（`AnimatedOpacityState` 的注释甚至写着"第一句必须"）。
纪律守住了，但**不该让纪律存在**：漏写的症状是"改了筛选条件，结果没变"，
**不报错**、极难归因。

**Flutter 怎么做的**：framework 在调 `State.didUpdateWidget(oldWidget)` 之前就把
`state._widget` 换成新的 —— 覆写者从来不需要 `super.didUpdateWidget()`。

**已修**（见 §4.1）。

### Q2 依赖靠手写闭包穿参 —— **6 跳**

**证据**：`fetchRows` 这个能力从组合根到页面，经过：

```
ShowcaseApplication::buildRoot()        闭包定义          ← 1
  → ShowcaseRoot::__construct()         参数              ← 2
  → ShowcaseRoot::make()                参数              ← 3
  → ShowcaseRoot::createState()         传递              ← 4
  → ShowcaseState::__construct()        参数              ← 5
  → NavEntry 的工厂闭包                  捕获              ← 6
```

`ShowcaseRoot` 的构造器已有 **6 个参数**（`$notify` / `$delay` / `$showModal` /
`$dialog` / `$setCloseConfirm` / `$fetchRows`），**每加一个能力就要动 6 处**。

这是**扩展性上最大的瓶颈**：不是"难写"，是"每加一个功能都要改一条链"。
`BuildContext` 目前只有 `theme()` / `metrics()` / `color()` / `metric()` / `textSize()` /
`textColor()` —— **没有任何依赖查找能力**，也没有 `InheritedWidget` 等价物。

**为什么没在本轮改**：需要 `InheritedWidget`（沿 Element 树查找 + 依赖订阅 + 变更通知），
是**重构级**改动，牵连 `Element` 的生命周期。见 §5 P3。

### Q3 "一次请求的生命周期"没有任何对象承载

每个异步页面都要自己写：

```php
private ?Future $future = null;                  // ① 承载
private function load(int $page, bool $force)    // ② 提交点 + 去重
{
    if (!$force && $this->future !== null && $target === $this->page) return;
    $this->setState(fn() => $this->future = $fetch($target));
}
public function dispose(): void                  // ③ 卸载时取消
{
    $this->future?->cancel();
    parent::dispose();
}
```

**React Query `useQuery` 一行**就给出 `{data, isLoading, error, refetch, isFetching}`，
且同 key 自动共享去重。Drift 这 ~15 行纯代码每页重写（读懂要 50 行注释），且**漏一处就出问题**：
漏 ③ ⇒ 离开页面后 worker 白跑；漏 ② 的去重 ⇒ 转圈时连点排队几条请求。

**为什么没在本轮改**：需要一个新类（`AsyncCommand`），且它天然是"超时 / 重试"的落点
（正好覆盖已记录的 G3 / G4）。单独一轮更稳。见 §5 P1。

### Q4 `AsyncValue::idle()` 在生产代码里**零消费者**

**证据**：`grep AsyncValue::idle()` 只命中 `tests/Unit/Async/AsyncValueTest.php`。
原因：`FutureBuilder` 的 `$future` 不可空、快照恒从 `loading` 起 ⇒ `idle` 永远产生不了
⇒ `isIdle()` 是死判据，`AsyncTablePage` 只能自己写一层
`$future === null ? Center('准备中…') : FutureBuilder(...)`。

四态名义、三态实际 —— **多一个必须理解但没有场景的态**，是纯负担。

**已修**（见 §4.2）：`FutureBuilder::make(?Future $future, ...)`，`null` ⇒ `idle`
（对应 Flutter `FutureBuilder(future: null)` 的 `ConnectionState.none`）。

### Q5 `FutureBuilder` 的 builder 拿不到 `BuildContext`

**证据**：签名是 `\Closure(AsyncValue): Widget`。想在 builder 里读主题
（`$ctx->theme()` / `$ctx->color(...)`），只能在外层 `build($ctx)` 里把 `$ctx`
捕获进闭包。`AsyncTablePage` 恰好没用到主题，所以这处不便**没有暴露**，
但它是隐式要求 —— 而 Flutter 的签名是 `(BuildContext, AsyncSnapshot)`。

**没有本轮改**：破兼容（2 处调用点 + 测试），收益中等。见 §5 P2。

## 4. 本轮落地的

### 4.1 `State::adoptWidget()` —— 覆写 `didUpdateWidget()` 不再需要 `parent::`

`src/Widget/State.php` 新增：

```php
/** @internal 只有 StatefulElement::didUpdateWidget() 调它 */
public function adoptWidget(Widget $widget): void
{
    $this->widget = $widget;
}
```

`src/Widget/StatefulElement.php` **顺序**改成：

```php
$this->state?->adoptWidget($newWidget);   // ① 框架先落新描述
$this->state?->didUpdateWidget($newWidget); // ② 再交用户钩子
```

`State::didUpdateWidget()` 里的赋值**保留作幂等兜底** ⇒ 三件事同时成立：

| 覆写者的写法 | 结果 |
|---|---|
| 调 `parent::didUpdateWidget()` | 无害（重复赋同一个值） |
| **不调** | 无害（框架已落）← **修复点** |
| 不覆写 | 与原来完全一致 |

**零破坏**：没删任何方法、没改签名，四处覆写一行都不用动。

**为什么不干脆把 `$widget` 改 public**：那是用一个封装漏洞换一个纪律问题 ——
封装成本不该转嫁给调用方。

**变异验证**：注释掉 `adoptWidget()` 那行 ⇒ `StateAdoptWidgetTest` 立刻红，
实际读到 `'a'`（旧值）。这是本仓少见的"测**错误写法不再出错**"的用例 ——
既有四处覆写全调了 parent，常规用例永远碰不到这一支。

### 4.2 `AsyncValue::fold()` + `idle` 有了真实语义

**`fold()`**：一次调用写完四支，缺键**当场抛**。

```php
$label = $value->fold([
    'idle'    => static fn(): string => '尚未请求',
    'loading' => fn(): string => '正在加载第 ' . $this->page . ' 页…',
    'error'   => static fn(): string => '加载失败（可重试）',
    'data'    => fn(): string => '第 ' . $this->page . ' 页 / 共 ' . $pages . ' 页',
]);
```

为什么值得：手写 `if/elseif/else` **只有三个出口**，`idle` 会落进 `else` 被当成"有数据"
⇒ 显示「第 1 页 / 共 0 页」。`AsyncTablePage` 的 `toolbar()` 原来就是这个形状 ——
`idle` 一出现，那个 `else` 就成了 bug。

为什么"缺键当场抛"而不是"用到才抛"：后者要等真的走到缺的那一态才炸，而"失败时空白"
正是缺 `error` 的症状 —— 那等于把错误推迟到最难复现的时刻。宁可第一次调用
（几乎必然是 `loading`）就抛，让问题停在开发期。

**`idle` 的真实语义**：`FutureBuilder::make(null, ...)` ⇒ `idle`。
于是 `AsyncTablePage` 少了一层 `$future === null ? 占位 : FutureBuilder(...)`
—— 那层分支只为"首帧前一瞬"存在，属于纯噪音。

> ★ 诚实说明：`AsyncTablePage` 在 `initState()` 里就 `load(1)`，所以它的首帧是
> `loading` —— **`idle` 分支在这个页面上走不到**。`idle` 的价值在"点按钮才加载"
> 的页面（不调 `initState` 加载就是 idle）。本轮验证的是"能力成立"，不是
> "这个页面用到了它"。

### 4.3 `fold()` 原来的混合签名是个 AOT-only 陷阱 —— 已改掉

第一版 `fold()` 是混合签名：`idle` / `loading` 零参、`data` 收值、`error` 收消息。
`toolbar()` 里 write 成：

```php
'data' => fn(): string => '第 N 页 / 共 M 页',   // ← 零参，但 fold 会给它传值
```

- `php -l` ✅ · `phpunit` 932 tests ✅ · `lint` ✅ · `gate` 8 项 ✅
- **AOT 真机**：`Fatal: AsyncTablePageState::{closure}() expects exactly 0 arguments, 1 given`

原因：**PHP 解释器允许"多传实参"（忽略掉），AOT 严格校验参数个数**。
而且它只在**真的走到 `data` 态**才炸 —— 失败态、加载态都正常，所以"点一下就崩"
看起来像随机故障。

**修法不是"文档里写清哪支收什么"，而是让这种错写不出来**：四支签名统一
`\Closure(AsyncValue): mixed`。代价是 `data` 分支多写一次 `->value()`；收益是
**一整类"解释器全绿、真机才崩"的故障从语法层消失**。

⇒ **这条是整份文档里最好的"心智负担"论据**：AOT 的严格性本身就是一笔开发者税，
而它**只在真机暴露** —— 再好的注释也拦不住，只能靠**让错误的写法不成立**。
这也正是为什么"减少必记事项"比"写清必记事项"更值钱。

## 5. 第二轮：收敛（P1–P4 全部处理完，且是替换不是加法）

| 优先级 | 原计划 | 结果 |
|---|---|---|
| **P1** | 新增 `AsyncCommand`，让 `FutureBuilder` 接受它 | **做成"替代"**：`AsyncCommand` 是 `FutureBuilder` 的**超集** ⇒ `FutureBuilder` 删除（§5.1） |
| **P2** | builder 给 `BuildContext` | **消失了**：没有 builder 了，`build()` 本来就有 `$ctx`（§5.2） |
| **P3** | 依赖查找（`InheritedWidget` 等价物） | **否决（有据）**，改做组合根打包（§5.3） |
| **P4** | `Button` 禁用态 | **已做**（§5.4），页面里的 `$force` 兜底随之删除 |

### 5.1 为什么是"删 `FutureBuilder`"而不是"两套并存"

`FutureBuilder` 的入参是一个 **`Future`**，而 `Future` **无主**：谁发起的、还能不能
重跑、旧的那条要不要取消，控件一概不知道 ⇒ 这三件事全摊给页面（每页 ~15 行纯代码、~50 行注释）。
`AsyncCommand` 是它发起的那条 `Future` 的**唯一持有者**，于是：

| 事 | `FutureBuilder` | `AsyncCommand` |
|---|---|---|
| 请求从哪来 | 页面存 `$this->future` + 自己 `load()` | `run($arg)` |
| 旧请求 | 页面记得"换 Future 触发重订阅" | `run()` 内部作废 + **真的 `cancel()`** |
| 迟到的旧结果 | 控件另配"订阅代号"（它不敢取消共享的 Future） | `cancel()` 之后 `Future` **永不结算** |
| 重试 | 页面把提交再写一遍 | `retry()`（记得上次参数） |
| 去重 | 页面自己判"同页且在途" | `run()` 内建（同参数在途 ⇒ 忽略） |

⇒ **凡是 `FutureBuilder` 能表达的，`AsyncCommand` 都能**（"一次性提交" = `run()` 一次；
"投影别人给的 Future" = `fn() => $thatFuture`）。两套并存只会让每个新页面先问一句
"这里该用哪个"。**能替代就只留一套。**

**UI 侧因此不再有专用异步控件**：命令住在页面 `State` 里，值一变就 `markDirty()`
（与 `Cell` 同一条路），`build()` 直接读 `$cmd->value()`。

### 5.2 P2 自然消失

`FutureBuilder` 要 `BuildContext` 是因为它的 builder 在控件内部、拿不到外层的 `$ctx`。
现在画四态的就是页面自己的 `build()` ⇒ `$ctx` 本来就在手上。

### 5.3 P3 否决：不做"沿树查找"，改做组合根打包

复核后的结论比我上一轮写的更硬 —— **不只是"成本高"，是已经被架构否决过**：

- `BuildContext` 的类注释三条边界里第 ②③ 条明写：**无业务数据**、**无向上查找**
  （`of()` / `find()` / `maybeOf()` 一律不开），理由是 §18 已否决 Flutter 的
  provider soup（"`$ctx` 后面藏着读值和订阅 ⇒ `dead-subscription` 的判据被绕过）。
- 而框架**已经有**完整的响应式设施：`Subject` / `Cell` / `State::watch()` /
  `SubjectBuilder`。再开一条"沿树查找"就是第二套依赖传播机制。

**真正做了的替代**：把示例台组合根的那 6 个能力收成一个 `ShowcaseCapabilities`
值对象（`apps/showcase/src/ShowcaseCapabilities.php`）。

- 收益：加第 7 个能力时**只改 1 处**（原为改 3 处签名 + 2 处装配点）；
  "示例台到底要接几样"有了可读的地方。
- **诚实边界**：它降的是噪音（每跳携带的参数个数），**不是跳数** ——
  页面拿到能力仍然由组合根显式递进，跳数一处没少。这是有意的。

### 5.4 P4 已做：`Button::enabled()`

`ToggleBase` 早就有 `enabled()` / `paintsDisabledLook()`，`Button` 只是没接 ——
现在补上（`enabled()` + `activate()` 早退）。框架侧三件事全是现成的：
不激活、外观变淡（`RenderBox` 按 `Modifier::$disabled` 叠 alpha）、不进 Tab 序 +
语义上报 disabled（`FocusManager` / `SemanticsBuilder` 已经读 `mods()->disabled()`）。

⇒ 异步表格页的「上一页 / 重试 / 下一页」现在用**禁用态**表达边界（`isRunning()`
直接就是判据），页面里那段"同页 / 在途就 `return`"的 `$force` 兜底**删除**了 ——
静默拒绝（点了没反应）换成了看得见的"现在不能点"。

### 明确不做（不变 + 一条新增）

- **`async` / `await` 语法糖**：PHP AOT 无法真正挂起调用栈。
- **通用 DI 容器**：见 §5.3。
- **把 `Job` 层藏掉**：进程隔离要求可序列化，税付在组合根是对的。
- **新增：命令内建超时 / 自动重试 N 次** —— 超时需要计时端口，而 `Async` 层只认
  `Errors`（依赖方向），计时端口属于 `App`（`TimerHost`）。要超时就让任务侧管
  （`ProcessTaskHost` 的 worker 超时是后端职责）。重试策略是业务决定（哪些错误值得
  重试），框架默认重试会把"幂等性假设"藏进基础设施。**不做半个。**

## 8. 第三轮：为什么"命令该住哪"这个问题的答案是"都不住"

第二轮结束时有个残留：命令构造收 `State` ⇒ 它**只能服务某一个页面**，于是跨页
共享的异步数据仍然要手写一遍状态机。当时我把它记成"两条路，各管一段"。

复核后那不是两条路，是**同一个状态机被写了两遍**：

| `AsyncCommand::start()` | `UserStore::load()`（旧） |
|---|---|
| `abandon()` 取消旧的 | `$inflight` + `cancel()` |
| `emit(loading())` | `$status = Loading; notifyChanged()` |
| `then/catch` | `then/catch` → `applyPage()` |
| — | `LoadStatus` 枚举 + `$rows` + `$error` 三个字段 |

⇒ 修法不是"给 Store 再造一个命令类"，是把**"值变了 ⇒ 通知谁"从命令里拿掉**。
命令改成 `extends Subject`：它只负责"四态 + 一次请求的生命周期"，通知走本仓既有的
订阅设施（`Subject` / `State::watch()` / `SubjectBuilder` / `Subscription`），
一个字节的新机制都没加。

| 谁持有 | 怎么收到通知 | 生命周期谁收 |
|---|---|---|
| 页面 `State` | `State::asyncCommand()` 内部 `watch()` → `markDirty()` | 框架 `unmount()` → `dropCommands()` |
| 跨页 `Store` | 构造器里 `subscribeFor($this, …)` → `notifyChanged()` | 应用自己 |

成熟 GUI 的同一形状：Riverpod 的 `AsyncNotifier` 在页面内 `autoDispose` 与全局共享
是**同一个类型**的两种寿命；React Query 的 `useQuery` 本地与缓存共用一份机制。
**寿命不是类型的一部分** —— 这正是上一版把 `State` 钉进构造参数所违反的。

### 顺带消失的两条"必记事项"

- **页面不用写 `dispose()` 了**：`State::dispose()` 是**可覆写**的，"忘了
  `parent::dispose()`"正是 A4 点名的失败模式 —— `Subscription` 的注释把这条原则
  写得很清楚（"把兜底放在用户侧就是文档承诺了、机制守不住"）。命令是同一类资源，
  于是同样由框架在 `unmount()` 时统一停掉。
- **`emit()` 里那句"宿主还在树上吗"删了**：卸载时命令已被 `dispose()`，迟到的结算
  根本到不了订阅回调 ⇒ 那是个**不可达分支**，而不可达的分支没有测试能消费
  （本仓纪律：未消费的分支 = 未实现）。留着它，读者还得替它想象一个场景。

### 用户的四态：从枚举换成值对象

`LoadStatus`（`Idle/Loading/Ready/Error`）与 `AsyncValue` 表达的是同一件事，而
`AsyncValue` 多带两样东西：**载荷**（`data` 态的值）与**消息**（`error` 态的原因）。
旧写法把这三样散在三个字段里，"失败时 `rows` 还是上一次的"这种语义只能靠
`applyPage()` 的注释守着。现在它是一条 `if ($value->hasData())`。
| **真机抓到的 bug** | `fold()` 混合签名 ⇒ AOT `expects exactly 0 arguments, 1 given`（解释器/gate 全绿）⇒ 已改为统一签名，见 §4.3 |

## 9. 第四轮：超时 —— 借 PHP-FPM 的形态，落在本仓的进程池上

### 9.1 为什么"客户端超时"是错的落点

前两轮我都把超时记成"待办，落点应是 `TaskHost` 的 per-job 超时"。这一轮做掉它，
先把"为什么不能放在 `AsyncCommand` 里"讲清楚 —— 这是本轮唯一的架构判断：

| 做法 | 谁提供 | 能停掉 worker 吗 | 成熟对照 |
|---|---|---|---|
| **客户端计时**（到点把 `Future` 判失败） | `AsyncCommand` 自己 | **不能** —— 进程还在跑、坑还占着，**且完全不报错** | .NET 6 `Task.WaitAsync(timeout)`：原任务**继续跑** |
| ** cooperative 取消**（带 deadline 的令牌） | 任务自己配合 | 只在任务真的查令牌时 | `CancellationTokenSource.CancelAfter` / gRPC deadline |
| **墙钟上限 + 杀进程**（本轮做的） | 握着进程句柄的那一层 | **能** | PHP-FPM `request_terminate_timeout` |

⇒ 握着 `proc_open` 句柄的只有 `ProcessTaskHost`。**放在别处都是半个。**
（客户端计时的那个"半个"尤其坏：它让 UI 看起来恢复了，实际池的有效容量悄悄掉
一格 —— 没有任何信号。）

### 9.2 从 FPM 借了什么

FPM 那条指令的形态几乎可以逐条照搬，因为两边是同一个形状（一个 master + 一组
PHP 子进程）：

| FPM | 本仓（`ProcessTaskHost`） |
|---|---|
| 池级指令 `request_terminate_timeout`（pool.d） | 构造参数 `$requestTerminateMs` |
| **墙钟**，从 master 把请求交给 worker 那一刻起算 | `hrtime`，从 `send()` 派发那一刻起算 |
| 到点 `SIGTERM`（必要时 `SIGKILL`），master 补一个 | `proc_terminate()`，下一帧 `flush()` 自动补 |
| 失败以 502 回给客户端 | `Completion(error)` ⇒ `Future` 判失败 ⇒ `AsyncCommand` 落 `error` 态 |

三条刻意跟着 FPM 走的决定：

1. **墙钟而不是 CPU 钟**。FPM 的文档把这件事讲得很透：PHP 的
   `max_execution_time` 只对 CPU 时间计时（`setitimer(ITIMER_PROF)`），
   `sleep()` / 慢查询 / 卡住的 curl **一律不计**。本仓的任务同样可能卡在 IO 上。
2. **默认开（30s）而不是默认关**。FPM 的默认值 `0`（关）被运维界叫作
   *the dangerous default*。本仓默认关更糟：worker 卡住 ⇒ `AsyncCommand`
   永远 `isRunning()` ⇒ 翻页 / 重试**全禁用** ⇒ **用户没有任何出路**，只能杀程序。
3. **计时从派发开始，不从提交开始**。排队等空闲 worker 不是"卡住"，是正常等待；
   而卡住的 worker 会被杀、池会补，所以排队不会饿死。

### 9.3 没借什么（诚实边界）

- **per-job 覆盖**：FPM 也只有池级一条。两条取数任务都在 1s 量级，一个池级上限
  足够。真出现"有的任务就是慢"再按需求加 —— 不提前铺。
- **慢日志**（FPM 的 `request_slowlog_timeout`）：需要一条独立的诊断通道与采样
  策略。超时消息里带**任务名**已经够定位。
- **`SyncTaskHost` / `ThreadTaskHost` 不提供这道闸**：同步后端里任务是 inline 跑完
  的，**不存在"卡住的 worker"这个对象**（真慢的话 UI 已经卡了，问题在别处）；
  线程后端杀不掉线程。⇒ 超时是**进程池这个后端的能力**，不是端口契约的一部分
  —— 与 `needsPolling()` 同类：后端声明"我能不能叫醒你"，调用方不猜。
- `State → Platform` 那条边**仍然没人走**：命令因此不需要计时端口。

### 9.4 顺带修掉的三处"说了不该说的话"

- `UserCommands::refresh()`：`load()` 返回后立刻 `say('已刷新')` —— `handle()`
  是**同步**的，它不可能知道异步结果。改成只说"正在刷新…"；"完成了没有"由
  `AsyncValue` 那四态回答（那才是真的状态）。
- `DESIGN.md` §11.5 仍以已删的 `LoadStatus` 手写三态为范例 —— 加了"不要再照它写
  新代码"的更新块 + 当前形态。
- `Spinner` 的类注释仍写 `LoadStatus::Loading => …`。

## 10. 第五轮：界面上的两个谎言 —— "载荷被扔掉" 与 "浇筑时的快照"

第四轮把"超时"落到了进程池上，async 这条线看起来收完了。这一轮**又抓出两个**
问题，它们的形状不同，病根是同一句话：**界面没有如实反映异步状态**。
一个在类型层（载荷活不下来），一个在读法层（会变的值没在订阅里读）。

### 10.1 谎言一：刷新 / 翻页时内容整块消失

`AsyncCommand::start()` 发的是 `AsyncValue::loading()` —— **不带载荷**。于是：

| 动作 | 上一版的画面 | 用户读到的 |
|---|---|---|
| 点「下一页」 | 表格 → 整块转圈 → 新表格 | "卡了一下" |
| 点「刷新」 | 列表 → 一个转圈 → 列表 | "我刚才看的东西呢" |
| 刷新失败 | 列表 → 错误 | 内容丢了（值随 `loading` 一起被扔掉） |

`fold()` 的 `loading` 支被**强制**画成转圈，因为那一态里**没有东西可画**。
这不是页面写错了，是**类型表达不了**"同时有旧数据 + 正在取新的"。

### 10.2 为什么"加一个 `refreshing` 状态"是错的

最直觉的修法是加第五态。但它把两个不同的问题混成一个：

| 问题 | 是"状态"吗 |
|---|---|
| 请求在不在途 | 是（`loading`） |
| 手上有没有值 | **不是**，是载荷的归属 |

"刷新中"= 在途 **且** 有值 —— 它是两个维度的**组合**，不是第三个维度。加成第五态
的直接代价：`fold()` 多一个键，而"漏写一支 ⇒ 静默画空白"的失败模式跟着翻倍
（`fold()` 的注释专门讲这一类）。

成熟 GUI 全都是两维：

| 框架 | 形状 | "刷新中"怎么表达 |
|---|---|---|
| Flutter `AsyncSnapshot` | `(ConnectionState, data, error)` | `waiting` + 有 data |
| Riverpod 2 | `AsyncValue` + `copyWithPrevious()` | `isRefreshing` / `isReloading` |
| React Query / SWR | `status` + `data` | `keepPreviousData` / `isFetching` |

⇒ 本仓选**两维**：四个名字不变，**载荷可以跨状态存活**；`fold()` 的分支选择按
"**现在该画哪一块**"走 —— `loading` **且带旧值** ⇒ 走 `data` 支。这就是 Riverpod
`when(skipLoadingOnRefresh: true)` 的默认行为（默认就对了，页面才不用每处手写）。

### 10.3 落地（替换，不是新增机制）

| 处 | 改了什么 | 一句话理由 |
|---|---|---|
| `AsyncValue` | 新增 `$hasValue` 字段、`carriedFrom()`、`hasValue()`、`isRefreshing()` | 载荷与状态分开；"有没有值"不能用 `$value !== null` 判（`data(null)` 是合法值） |
| `AsyncValue::dataOr()` | 判据从 `state === DATA` 改成 `hasValue` | 刷新中照旧画得出来 —— 消费点不必各写一份 `hasData() ? … : $last` |
| `AsyncValue::fold()` | `loading` **且有值** ⇒ 路由到 `data` 支 | 四支的名字描述"画哪一块"，`loading` 因此被收窄成**首屏** |
| `AsyncCommand::start()` | `loading()->carriedFrom($this->value)` | 一处发出，所有消费点自动受益 |
| `AsyncCommand::land()` | 结算统一 `$next->carriedFrom($this->value)` | `data` 自带载荷（不动），`error` 继承旧值 ⇒ "失败说得出来、旧内容也还在" |
| `AsyncCommand::cancel()` | 有旧值 ⇒ 回 `data`，没有 ⇒ `idle` | 取消是"我不等了"，不是"把看到的东西也扔掉" |
| `AsyncTablePage` | 标题在 `isRefreshing()` 时说"正在加载第 N 页…" | 那时表格里还是**上一页**，写"第 2 页"就是在说没有依据的话 |
| `AsyncTablePage` | `loadingLabel()` 一处 | 两处各写一份 ⇒ 改文案必然只改一处 |
| `UsersPage` | 见 §10.4 | 另一个谎言 |

### 10.4 谎言二：`enabled()` 是浇筑那一刻的快照（真机抓到的）

`UsersPage` 是 `StatelessWidget` —— `build()` 只在这棵子树被造出来时跑一次。而本应用
**进页面就取数**，所以：

```php
Button::primary('刷新')->enabled(!$this->store->page()->isRunning())   // ← 旧写法
```

那一次 `isRunning()` 必然是 `true` ⇒ 按钮**永久灰掉**。真机探针（手动结算的后端）：

```
enabled(loading)=false isRunning=true      ← 首帧：对
enabled(settled)=false isRunning=false rows=1  ← 数据到了，按钮还是灰的（bug）
enabled(reload)=false  isRunning=true
```

上一轮刚把"禁用态"当成边界表达的正解（§5.4），却忘了**它得跟着状态走**。
修法不是"再想个办法刷新按钮"，是把那段包进 `SubjectBuilder`（切片 = `isRunning()`
一个布尔），并顺手把"刷新中"的信号补上（列表不消失之后，界面否则看起来像
"点了没反应"）。

**为什么一个布尔就够**：`AsyncCommand` 维持一条不变式 —— *`isRunning()` 的每次
变化都伴随一次值变化*（`start()` 里先置 `pending` 再 `emit(loading)`；`land()` 里
先清 `pending` 再 `emit(结果)`）。所以"值变了"就是"按钮该重算了"，不需要给
`isRunning()` 单开第二条通知通道 —— 两条通道迟早会不同步。

⇒ 提炼成一条页面层纪律（已写进 `UsersPage` 的类注释）：
**页面里任何读 Store 的地方都必须落在某个 `select` 之内，否则它就是快照。**

### 10.5 没做的（诚实边界）

- **`error` 不路由到 `data`**：带旧值的失败照样进 `error` 支（与 Riverpod
  `skipError: false` 一致）。失败必须被看见 —— 否则就是"静默不刷新"，用户以为
  数据是新的。想在错误条下面继续画旧内容，就在 `error` 支里读 `$v->dataOr()`。
- **不做缓存 / `staleTime`**：与 §9 的边界同 —— 缓存键策略是上层课题。
- **不做每键 debounce**：本仓的搜索是本地过滤（同步），没有真实需求。
- **per-job 超时 / 慢日志**：仍未借（同 §9.3）。
- **"手感"仍无人眼验证**：本轮新增的「刷新中…」提示同样只有断言（文字在树上、
  旧行仍在），**不证明**好看。

## 11. 第六轮：全量复审 —— 三个真缺陷、两处说错的话，以及一次逐项对照

前五轮都是"沿着一个具体症状往下挖"。这一轮换方向：**把异步这条线的全部实现读一遍**
（`Future` / `AsyncValue` / `AsyncCommand` / 三个 `TaskHost` / `PumpHost` 的预算与
`State` 的生命周期），再逐项对照成熟 GUI，问一个问题：**这套东西现在有几处是"只说
对了一半"的？**

结论先说：**结构不用改**（下面 §11.1 那五层各自只有一份，没有平行实现），但挖出
**三个真缺陷**，全部属于"一条路做对了、另一条路漏了"这一类 —— 而且都不是新功能，
是把已有承诺补齐。

### 11.1 现状盘点：五层，各一份

| 层 | 类型 | 职责（唯一） | 复用者 |
|---|---|---|---|
| 结果 | `Future` | 组合（`then`/`catch`/`all`/`race`/摊平/取消） | 三个后端 + 应用 |
| 状态 | `AsyncValue` | 四态 + 载荷（两维） | 页面 / Store |
| 生命周期 | `AsyncCommand` | 发起 / 去重 / 作废旧请求 / 重试 / 广播 | 页面（`State::asyncCommand()`）· Store（`subscribeFor`） |
| 执行 | `TaskHost` ×3 | 同步队列 / 子进程池 / C++ IO 池 | 组合根一行切换 |
| 时序 | `PumpHost` | 帧内交付 + 每帧预算 + 轮询判据 | 帧循环 |

★ 复审里**没有找到第二份实现**：`LoadStatus`、`FutureBuilder`、`applyPage()` 那三套
已经在第二～四轮删干净了。这是本轮唯一可以称为"通过"的部分。

### 11.2 缺陷一：聚合体把失败吞了（G2 的破口在"组合"这一层）

`Future` 的契约写得很直白：*结算为失败时若**没有任何** `catch()`，直接走 Fatal 序列*。
但 `all()` / `race()` 造出来的聚合体是 `new self()` —— `$task = false`。于是：

```php
Future::all([$api->get('/u'), $api->get('/o')])->then(fn (array $r) => …);  // 忘了 catch
```

两条子任务的失败被 `all` 内部的 `catch` 接住 → 转成 `$all` 的失败 → `$all` 没有
`catch`，但它是"值" ⇒ **不喊** → `then` 的下游继承 `false` ⇒ 一路静默。结果就是
**界面永远转圈、日志里一个字都没有**，正是 G2 要杀的东西。

根因是上一轮给"值不喊"加的豁免用得太宽：`rejected()` / `resolved()` 确实是"构造即
结算，那一刻调用方还来不及挂 `catch`"，但**由任务组成的聚合体不是值**。

修法（`Future::all()` / `race()`）：

| 步 | 做什么 | 为什么 |
|---|---|---|
| ① | 遍历入参时记 `$anyTask = $anyTask \|\| $future->task` | 聚合体的"任务性"来自入参，不是自己 |
| ② | 接线（`then`/`catch`）**之后**才 `$all->task = $anyTask` | 若入参早就失败，聚合体会在 `all()` 里当场结算 —— 那一瞬 `all()` 还没返回，调用方**不可能**挂过 `catch` ⇒ 此时立标记就是误报 |
| ③ | 纯值入参（`Future::rejected()`）仍然不喊 | 保持 `testRejectedValueAndAllOverItDoNotTripTheUnhandledGuard` 的语义 |

★ ②是这一条的全部难点：**"该不该喊"取决于"失败发生在谁还能接住的时候"**。所以标记
不能和构造同时立，必须错开一个"接线已完成"的时刻。

判据落在**退出码**上（`abort()` 不是异常，`try/catch` 接不住）：新增冒烟用例
`allerr`。修复前 `exit 0`（静默），修复后 `exit 3` —— 同一个用例两个结果，这就是
"这条判据有牙"的证据。

### 11.3 缺陷二：取消聚合体不传播（"能停就停"的承诺打了折）

`cancel()` 的文档说它"① 调后端的取消钩子（能停就停）；② 标记结果不要了"。对单条
`submit()` 这是真的（`ProcessTaskHost` 摘排队项）。但对聚合体：

```php
$this->rows = $this->asyncCommand(fn ($p) => Future::all([
    $host->submit(new FetchRowsJob($p)),
    $host->submit(new FetchStatsJob($p)),
]));
```

换页时 `AsyncCommand` 会 `cancel()` 上一次那条 Future —— 那是**聚合体**。旧实现只把
聚合体标记成"不要了"，两个子任务**照旧跑完**：worker 占着、结果回来被 `resolve()`
的第一句丢弃。用户看到的是"翻页了"，机器上跑的是两份没人要的请求。

修法：聚合体构造时带一个 `onCancel` 钩子，把取消转给全部入参（`all` / `race` 各一处）。
这与"失败时取消其余"是同一件事的两面，现在共用同一条路径。

★ 顺带补了一条**契约**（写在 `AsyncCommand::make()` 上）：`$task` 每次必须返回**新的、
归本命令独有**的 Future。反例很自然 —— "同页在途就复用上一条 Future"，而本类换参数
时会 `cancel()` 它 ⇒ **误伤另一个持有者**，症状是"别的地方莫名其妙不再更新"，
比"多跑一次"难查一个量级。

### 11.4 缺陷三：`$task` 同步抛出会穿透事件循环

`AsyncCommand::start()` 原来的写法是 `$future = $task($arg);`。而 `$task` 是应用写的：

```php
fn (int $p): Future => $src->fetchPage($p)->ok ? Future::resolved(...) : Future::rejected(...)
```

`fetchPage()` 在同步路径上会**抛**（PDO / 连接失败 / 超时）。这条异常于是：
`run()` → `UserStore::load()` → 命令 handler → `CommandRouter::dispatch()` →
`Application::dispatch()` → 平台消息循环。这一段**没有任何 `try/catch`**
（`src/App` 里 grep 得到 0 个 catch，`Frame::run()` 只兜 settle / paint）。

后果分叉得很刺眼：**同一次取数失败**
- 异步后端 ⇒ `Job::run()` 抛出 → `Completion.error` → `catch()` → `AsyncValue::error` → 界面画"加载失败"；
- 同步后端 ⇒ 异常穿透 → 中止序列 / 平台层未定义行为，界面停在上一次的样子。

修法：`start()` 把 `$task($arg)` 包进 `try/catch (\Throwable)`，转成
`AsyncValue::error($e->getMessage())->carriedFrom($this->value)`（旧值仍然保留），
`pending` 由 `abandon()` 保证已是 `null` ⇒ `isRunning()` 为假，按钮能再点。
**不额外 `Errors::report()`**：异步路径的 `Job::run()` 抛出也不喊 Fatal，两条路要一致。

判据三层：① 值是 `error` 且消息原样；② `isRunning()` 为假；③ **画出来的字是 error**
（`fold()` 真选了那一支）。变异自检：去掉 `try/catch` ⇒ 用例以 `RuntimeException` 报错
（证明异常真的会冒到调用栈）。

### 11.5 两处"说了不该说的话"

| 处 | 原文 | 事实 |
|---|---|---|
| `AsyncCommand::run()` 注释 | "`SyncTaskHost` 下 `$task()` 返回的 Future 已经结算 ⇒ 首帧就是 `data`，不会白闪一帧 loading" | **不成立**。`SyncTaskHost::submit()` 只入队（§17.4.2 的统一语义），结算发生在下一帧 `drain()` ⇒ 首帧仍是 `loading`。真正"当场 data"的只有 `$task` 返回**已结算** Future 的场合（基准 / 快照里的 `Future::resolved`） |
| `ProcessTaskHost::$queue` 的 `@var` | `array{id, line, future}` | 实现里还写了 `name`（`send()` 的类型注释是对的）⇒ 类型注释漏字段，静态分析会放过"少写一个键"的真错 |

★ 第一条是同一个坑的第二次现身：**把"同步后端"与"立即结算的 Future"混成一回事**。
上一轮它出现在 `enabled()` 的推演里（"首帧 `isRunning()` 必然 true"—— 那句是对的），
这一轮它出现在注释里。**结论**：说"首帧"时必须问清是哪种后端 + 哪种 Future。

### 11.6 逐项对照成熟 GUI（这一次问的是"缺哪一维"）

| 维度 | Flutter | Riverpod 2 | TanStack Query | Compose | 本仓 |
|---|---|---|---|---|---|
| 状态形状 | `AsyncSnapshot(ConnectionState, data, error)` | `AsyncValue`（`value` + `isLoading` + `error`） | `status` + `fetchStatus` + `data` | 无内建（`State` + `LaunchedEffect`） | `AsyncValue` 四态 + `hasValue`（**两维**） |
| 旧值保留 | ✗（换 future 就没了） | `copyWithPrevious()`（refresh 默认保留） | `placeholderData: keepPreviousData` | 手写 | `carriedFrom()`（`run()` 自动） |
| 发起 | 换 `future` 字段 | Notifier 方法 / `ref.refresh` | `refetch()` | `LaunchedEffect(key)` | `run($arg)` |
| 去重 | ✗ | ✗ | `dedupe` | 手写 | 同参数在途 ⇒ 忽略 |
| 取消 | `CancelableOperation`（手动） | `ref.onDispose` / `autoDispose` | `AbortSignal` | 协程 cancellation | `cancel()` + 框架在 `unmount()` 兜底 |
| 超时 | `Future.timeout`（客户端） | `.timeout()`（客户端） | ✗ | `withTimeout`（客户端） | **后端墙钟**（`ProcessTaskHost`，FPM 形态） |
| 重试 | ✗ | ✗ | `retry` + 指数退避 | 手写 | `retry()` 手动 |
| 键 / 缓存 | ✗ | `family` / provider 身份 | `queryKey` + 缓存 | ✗ | **✗**（一个命令 = 一个键） |
| 错误载荷 | `snapshot.error`（Throwable） | `AsyncError(error, stack)` | `error` 原对象 | 异常 | **只有消息字符串** |

★ 读法：本仓在"状态 / 旧值 / 去重 / 取消"四维与成熟框架**同形**（不是"类似"，是同一
组判断），差异集中在**三处刻意的减法**：超时挪到后端（客户端超时停不掉 worker，
§9.1 已论证）、重试归业务、错误只留字符串（AOT 的可空对象字段会读成 `php::Var`，
而界面要的本来就是一句能画的话）。这三处不是缺口，是裁决。

### 11.7 评估过、但这一轮**不做**的（附理由，避免下一轮重新论证）

| 项 | 为什么不做 |
|---|---|
| `run()` 返回 `?Future`（像 `refetch()` / `ref.onDispose` 那样可 await） | 返回的是**会被后续 `run()` 取消**的那条 Future ⇒ `then` 可能**永不触发**，而"永不触发"正是本仓最痛恨的契约说谎。要做对得给 `Future` 加一个 `cancelled` 终态（现在取消只是"不结算"），代价大于收益：命令层想知道结果，读 `value()` 订阅就够了 |
| 给命令加"键"（`queryKey` 那套） | 一个命令实例**就是**一个键（Riverpod 的 provider 身份）。但本仓的 `carriedFrom()` 是"同一命令内总是保留旧值"—— 对**翻页**是对的（`keepPreviousData`），对**换实体**（用户 A → 用户 B）可能是错的：会把 A 的内容当成 B 的骨架画出来。★ 这条要记住：**换实体请用另一个命令实例**；真要一个实例承载两种语义，再加 `run($arg, keepPrevious: false)`，不提前铺 |
| 错误保留 `\Throwable` | AOT 对可空对象字段会读成 `php::Var`（`MEMORY` 第 41 条）；界面要的是可画的一句话。要"按错误类型重试"就在 `$task` 闭包里判（那里有原始异常），比把异常塞进 UI 值更干净 |
| 自动重试 N 次 / 退避 | 重试策略是业务决定（哪些错误值得重试、幂等性假设），框架默认重试会把假设藏进基础设施 |
| 缓存 / `staleTime` / 失效 | 缓存键策略是 TanStack Query 那一层的课题；本类只保证"最后一次 `run()` 的结果" |
| `ThreadTaskHost` / `SyncTaskHost` 的超时闸 | 线程杀不掉（只能"不交付"，池容量照样掉一格）；同步后端卡住 = UI 线程卡住，任何计时器都叫不醒。**能真停的只有握着进程句柄的那一层** —— 所以这道闸只装在 `ProcessTaskHost` |
| per-job 超时 / 慢日志（FPM 的 `request_slowlog_timeout`） | 池级一个上限够用（FPM 也只有池级）；慢日志要独立通道 + 采样策略，没有需求 |
| `sweepTimeouts` 与帧预算之间的窄窗口竞态 | 现象：回复**已经**在管道里，但本帧超预算没读 ⇒ 下一段把任务判超时并杀 worker。窗口极窄（超时点正好落在超额帧内），且 `startedAt` 用 `hrtime`（不可注入）⇒ **写不出能证伪的判据**。按本仓纪律（未消费的分支 = 未实现；不可证的代码不加），只记录 |

## 12. 第七轮：取消的第三处破口 —— 派生链（顺手把三份交付循环收成一份）

第六轮把"取消要传播"补到了 `all` / `race`（聚合体）。这一轮接着问同一个问题：
**还有哪条路上的 `cancel()` 只是把标记打上、活照旧在跑？** 答案是 `then()` ——
**最常用的那种派生**。而且它不是"理论上会漏"，仓库里就躺着一处绕行代码。

### 12.1 症状：`submit()->then($decode)` 让取消**静默落空**

`UserStore::fetch()` 上一版长这样（注释原文保留了当时的理由）：

```php
// ★ 后台路径：回**根** Future（`submit()` 的返回值），不是 `then()` 的产物
//   —— 取消链下游不回溯上游 ⇒ 取消派生出来的那条对在途任务毫无作用。
return $host->submit(new FetchUsersJob($page, $this->apiBase));
```

"取消派生出来的那条"是什么场合？**应用最自然的写法**：

```php
fn (int $p): Future => $host->submit(new FetchUsersJob($p))->then(fn ($raw) => UserSeed::hydrate($raw));
```

`AsyncCommand` 换参数时取消的正是 `$task` 返回的那条 —— 在这里是**派生节点**。
于是：

| 步 | 上一版实际发生 | 用户看到 |
|---|---|---|
| 翻页（第 1 页 → 第 2 页） | 派生的那条标成 cancelled；**根任务的取消钩子没被调到** | 界面正常 |
| `ProcessTaskHost` | `dropQueued()` 没被调 ⇒ 排队项**照发**给 worker | 无 |
| worker | 白跑一趟（mock 后端 1.2s） | 无 |
| 结果回来 | `resolve()` 撞上取消位 ⇒ 丢弃 | 无 |

四行"无"—— 这正是本仓最不能接受的一类缺陷：**契约说"能停就停"，实现是个空操作，
而症状是完全静默**。上一轮 `Future::cancel()` 的注释里写着"2026-10-30 之前这里是纯
空操作"，这一轮它换了条路又出现了一次。

### 12.2 为什么修在 `chain()`，而不是"把契约写得更严"

三个候选：

| 方案 | 结论 |
|---|---|
| 要求 `$task` **必须**返回根 Future（现状） | **否决**：那是"契约靠人记"。应用只是把解码挪了个位置（`absorb()` → `then()`），语义完全等价，一种能停、一种静默不停 —— 这不叫规矩，叫**坑** |
| 取消时沿 `$links` 反查根 | **否决**：`$links` 是"父 → 子"，方向正好相反；而且一个父可以有多个子，反查要遍历整张图 |
| 新增 `?self $upstream` 字段 | 能行，但 `Future` 上**已经**有一个"怎么停"的钩子（`onCancel`，后端填的那个）。两个钩子 = 两套先后次序 = 迟早不同步 |

⇒ 选**把上游取消组合进已有的 `onCancel`**：一个钩子，语义统一成"**停住我背后那件事**"。
根节点上是后端钩子（摘队列 / 杀 worker），派生节点上是"取消我的上游"。
`cancel()` 本身一行没改 —— 它只是调钩子，钩子链自己会走。

```
$host->submit($job)                    根：onCancel = 摘队列 / 杀 worker
  └─ then($decode)                     派生：onCancel = fn() => 上游->cancel()
       └─ catch($show)                 派生：onCancel = fn() => 上游->cancel()
```

**摊平是第二处赋值**（`forwardTo()`）：`then` 的回调返回另一条 Future 时，真正在跑的
是那条，所以 `$next` 的钩子要**改指内层** —— 漏了这一处，"取 A 再用 A 的 id 取 B"
取消之后 B 照跑（外层已经结算，指着它等于指着空气）。这是两条**互不相干**的赋值，
只测一条会让另一条静默退化 —— 所以判据也分成两条。

### 12.3 落地

| 处 | 改了什么 | 一句话理由 |
|---|---|---|
| `Future::chain()` | 派生的 `$next` 带 `onCancel = fn() => $parent->cancel()` | 派生节点不是任务的持有者，活在上游 |
| `Future::forwardTo()` | 摊平时把 `$next` 的钩子**改指内层** | 外层已结算，指着它等于空转 |
| `Future::cancel()` 注释 | 写明"沿派生链上溯"，以及它带来的边界（见 §12.4） | 契约必须写在被实现的地方 |
| `AsyncCommand::make()` 契约 | 从"必须返回**根** Future"放宽为"**根**必须归本命令独有" | 那条限制本来就只是上一版缺陷的投影 |
| `UserStore::fetch()` | 后台路径改成 `submit()->then($decode)`；删掉"回根 Future"的绕行 | 派生现在真的能停 |
| `UserStore::absorb()` | 不再 hydrate，只做赋值（载荷已经是 `list<User>`） | 解码只在一处（那个 `then()`） |
| `UserSeed::dehydrate()` | **删除** | 它存在的唯一理由是把同步路径"降级成原始数组"再由 `absorb` 升回来 —— 一趟往返。同步源给的就是 `User` |

★ 最后一行是"能替代就只留一套"的直接结果：**归一化发生在边界，不发生在中间**。
后台的边界是 JSON（跨进程只能传数组），同步的边界是 `User` 对象；中间那一层不需要
"统一成某一种再变回来"。

### 12.4 付的代价：取消是**剪枝**，不是"只剪我这一枝"

若同一个根被两处 `then` 扇出、其中一处取消了它，另一处也收不到结果。这条边界写进了
`cancel()` 的注释，理由有两条：

1. **没有本机制时它早就坏了**：根被取消 ⇒ 永不结算 ⇒ 另一处的 `then` 同样不跑。
   本机制只是顺手把"活"也停掉（worker 不再白跑）。
2. 真正的规矩还是那条**独有**契约：一条根 Future 只有一个主人；要复用就复用**结果**
   （自己缓存值），不要复用 `Future`。这句话现在写在 `AsyncCommand::make()` 上，
   而不是"别无选择只能回根"。

### 12.5 顺带的收敛：三份交付循环 → `CompletionQueue`

`TaskHost::drain()` 的契约里写着三条规则（至少交一条 / 剩余算进 `pending()` /
簿记不受预算影响）。改造前 ①② 被**抄在三个后端里**：`SyncTaskHost::$queue`、
`ProcessTaskHost::$failed`、`ThreadTaskHost::$failed` —— 三段几乎逐字相同的
`foreach + hrtime + array_merge`。抄三遍抄出了什么：

| 差异 | 现状 | 后果 |
|---|---|---|
| 超预算之后 | Sync 写 `return`，另外两个写 `break` | 没坏，但"同一句话两种收尾" |
| 回调抛异常 | 只有 `ThreadTaskHost::deliverRows()`（行，不是 Completion）用了 `finally` | 另外两处：被 swap 出去的那几条**永久消失**（`Future` 永不结算 ⇒ 永远转圈，且没有日志） |

⇒ 新建 `src/App/CompletionQueue.php`（`@internal`），三个后端各退化成"结果从哪来"。
规则因此是**结构**，不是三份注释。`DrainBudgetTest` 的五条用例从"测 `SyncTaskHost`
的实现"变成"测**唯一**那份实现"，而此前完全没被测到的 `ThreadTaskHost` /
`ProcessTaskHost` 的失败队列也一并进了同一条路。

★ 写这 40 行时被自己的新用例打了一次：第一版把 `$done = $i + 1` 放在 `$onEach`
**之后**，于是"回调抛异常"那一帧把**已经交付过的那一条**又放回了队列
（`pending=3`、下一帧交 `[1,2,3]`）。裁决是**先记账再交付**：`$onEach` 一旦被调用
就算交出去了（它的第一件事通常是 `Future::resolve()`），此后抛异常也不能重交 ——
否则同一条会结算两次（第二次是空操作，但顺序乱了）。
**一个分支的正确性，只有"专门为它写的那条判据"能证明** —— 这条 40 行的类也一样。

### 12.6 闸门抓到的一次假超时（顺手修）

复跑闸门时 `JobTimeoutTest::testPoolSpawnsReplacementAfterKill` 红了一次：

```
后台任务超时：smoke.sum 超过 300ms 没回来（worker 已终止，池会自动补一个）
```

不是新代码的锅 —— 是那条用例的上限（300ms）与**新 worker 的启动时间**同量级。
超时从 `send()`（派发那一刻）起算，而刚 spawn 的 worker 那一刻还在启动 ⇒ 第一条
任务**替它的启动买单**。默认 30s 无感，300ms 会假阳性（机器一忙就中）。

| 处 | 改了什么 |
|---|---|
| `JobTimeoutTest` | 该用例专用上限 `REPLACE_TERMINATE_MS = 2000`（判的是"补上了、后续跑得通"，与预算宽窄无关） |
| `ProcessTaskHost::send()` | 注释写明这条边界（"第一条任务的预算里含着启动时间"） |

★ **不加"启动宽限"**：宽限值只能猜，而猜出来的数字没有判据能证伪（本仓纪律：不可证
的代码不加）。诚实边界写在计时开始的地方，比一个魔法常量好。

## 13. 第八轮：两种提交语义、一条多步范式、一行预热（2026-10-31）

> 上一轮（§12）修的是"取消在派生链上断掉"。本轮修的是**三处"能写但会写错"**：
> 追加会吃掉旧行（语义错）、多步没有可参照的写法（知识缺）、首条任务白等 275ms
> （兑现承诺）。裁决过程与取舍见 [`ASYNC-ARCH-2026-10-31.md`](ASYNC-ARCH-2026-10-31.md) §10，
> 这里只写**怎么写**。

### 13.1 一张选择表：这次的"拿数据"是替代还是追加？

```php
// ① 翻页 / 刷新 —— 一次只看一份数据，新结果**替代**旧的
$this->rows->run($page);

// ② 加载更多 / 无限滚动 —— 一份数据分几次拿，新结果**接在后面**
$this->rows->append($nextPage);
```

| 业务 | 第 2 次返回后界面上的行 | 动作 |
|---|---|---|
| 翻页（一次一页，页码在工具条上） | 换掉（`[1..20]` → `[21..40]`） | `run()` |
| 刷新（同一份数据重取） | 换掉 | `run()` |
| 加载更多 / 无限滚动 | **接上**（`[1..20]` → `[1..40]`） | `append()` |
| 多步依赖（先 A 再 B） | 换掉，但**一步到位** | `run()` + `$task` 内组合（§13.3） |

★ **为什么不是 `run()` 加一个参数**：这两个动作的差别在**语义**上（"我要新的一份"
vs "我要接着往下看"），而语义差别用动作表达，读代码的人不会看错；用一个 `bool`
表达，读代码的人要去查那个 bool 什么意思，写代码的人会忘记传。
★ 选错的症状**都不报错**：该 `append` 用了 `run` ⇒ 前面的行消失（看起来像翻页）；
该 `run` 用了 `append` ⇒ 列表越翻越长、内容重复（看起来像数据错了）。

### 13.2 范文一：加载更多（`apps/showcase/src/Pages/LoadMorePage.php`）

```php
public function initState(): void
{
    // 第二个参数是**合并规则**：上一次的载荷 + 这一次的载荷 → 新载荷
    $this->rows = $this->asyncCommand(
        $this->fetchRows,
        static function (mixed $old, mixed $new): array {
            return [
                'items' => [...$old['items'], ...$new['items']],
                'total' => $new['total'],        // 计数以最新一次为准
            ];
        },
    );

    $this->rows->run(1);        // 第一页：替代（旧值是 idle，合也无从合）
}

// 「加载更多」按钮
$this->rows->append($nextPage);
```

页面侧要知道的三条：

| 事 | 怎么写 | 为什么 |
|---|---|---|
| "正在加载下一页" | `$v->isRefreshing()`（在 `fold()` 的 **`data` 支**里判） | 追加中旧行还在，`fold()` 路由到 `data` 支；"在忙"必须页面自己说 |
| "失败了但行还在" | `$v->hasError() && $v->hasValue()` ⇒ 画列表 + 错误条 | `fold()` 照旧选 `error` 支（失败要让用户看见），**怎么画由页面定** |
| "下一页是第几页" | 从 `items` 数量推（`intdiv(count, PER_PAGE) + 1`） | 另存一个计数器就一定有第二条路会跟值不同步 |

★ **没有合并规则就别调 `append()`** —— 它当场抛 `LogicException`。静默退化才是要防的
那件事：它会安静地吃掉前面的行，而且看起来像一次正常翻页。

### 13.3 范文二：多步依赖（`tests/Feature/State/MultiStepCommandTest.php`）

```php
// 页面只认一条 Future —— 几步、谁依赖谁，都是 `$task` 内部的事
$this->detail = $this->asyncCommand(
    fn (int $id): Future => $host->submit(new ProfileJob($id))
        ->then(fn (array $profile): Future => $host->submit(new OrdersJob((int) $profile['id']))),
);

$this->detail->run($id);
```

四条性质（都由上面的测试钉着）：

| 性质 | 为什么重要 |
|---|---|
| 界面上只看到**一次** `loading → data` | 中间值漏出去 ⇒ 页面闪两下、可能画出"半个看板" |
| 第二步失败 ⇒ 整条 `error` | 拆成两个命令的话，第一步成功 + 第二步失败 = 半个页面，且没人说得清"加载成功了吗" |
| 取消打到**正在跑的那一步** | `then()` 返回 Future 时会被摊平，`forwardTo()` 把取消钩子改指内层 |
| 仍然只是一个 `AsyncCommand` | 去重 / 重试 / 卸载兜底全部继承，不需要第二套状态 |

★ **不要拆成两次 `run()`**（除非两步各自可独立展示）：那是两个命令 = 两份状态、
两次 `loading`、两次请求之间的状态不确定。

### 13.4 预热：把 worker 的 275ms 挪到应用启动期

```php
// 组合根（apps/users · apps/showcase 的 Bootstrap 都是这么写的）
$host = new ProcessTaskHost([$exe, '--drift-worker'], JobRegistry::make());
$host->prewarm();                       // ← 只这一行；最多起 maxWorkers 个
$scope->setTaskHost($host);
```

| 事 | 答案 |
|---|---|
| 修的是哪段等待 | `spawn` **275ms**（`probes/RESULTS.md` §12 ⑧）—— 首条任务要等执行体出生 |
| 为什么挪得动 | 那 275ms 是**另一个进程**在启动，不占 UI 线程；建窗 / 首帧那段时间正好空着 |
| 保证 0 等待吗 | **不保证**。它只 `proc_open`，不等就绪 —— 等就绪 = 在 UI 线程上阻塞 275ms，正是要躲的事 |
| 代价 | 应用若一直不用异步任务，那个 worker 会闲置占几十 MB（`reap()` 不会杀活着的） |
| 为什么不在 `TaskHost` 端口上 | 只有进程池有这笔启动账；放接口 ⇒ 另外两个后端只能写空方法（ARCH §10.3） |

### 13.5 没做的三件（附理由，避免下一轮重新论证）

| 项 | 理由 |
|---|---|
| `AsyncValue::mergedWith()` | "合并"是**操作**的性质，不是**值**的性质 —— 同一个 `data($x)` 可能是"第 2 页"也可能是"整份重取"。全套论证见 ARCH §10.2 的四行对照 |
| `PagedCommand` / `AsyncList` 独立类 | 与替代共享**七件事**（去重 / 作废 / 真取消 / loading 带旧值 / error 带旧值 / 重试 / 卸载兜底），只差落地一步 |
| `LazyColumn` 的 `onEndReached`（滚到底自动加载） | 那是**触发点**的事，不是状态语义的事；换触发点命令一行不改。等真需求来了再加 |

## 14. 第十轮：慢活该往哪放（`SlicedJob` 删除之后的唯一一张表）

> 2026-10-31 删掉了分片链（`SlicedJob` / `submitSliced()` / `pumpSliced()`）。

### 14.1 一张表（从上往下第一个命中即答案）

| 你的活儿 | 放哪 | 写法 |
|---|---|---|
| 几毫秒以内（一次字符串拼、一次 `<100` 行的排序） | **就写在 `build()` 里** | 不用异步。为它包一层 `Future` 只会多一帧延迟 |
| 会卡帧、但不涉及外部 IO（解析大 JSON、几万行过滤/排序） | **进程池**（`$host->submit(new XxxJob(...))`） | `asyncCommand` + `run()`，见 §13.1 |
| 在等外部（HTTP / 文件 / socket） | **进程池**（最省事）或 `IoPoller`（高频、要复用连接） | `IoPoller` 的接法见 `PumpHost::io()` 的 docblock 与 `DESIGN.md` §17.4.4；高频 HTTP 的正解是 `curl_multi` 接帧循环（ARCH §11.4 方案 D） |
| 多步依赖（先 A 再 B） | 仍是**一个** `asyncCommand`，在 `$task` 内组合 | §13.3 |
| 分页追加 | `asyncCommand` + `append()` | §13.1 |
| "必须在本线程算、且能切成很多小段" | ⚠️ **今天没有 API** | 见 §14.2 |

★ 唯一仍然"在 UI 线程上跑"的异步形态是 **`SyncTaskHost`**（默认后端，`run()` 同步跑完、
回调延到下一帧 `drain()`）。它解决的是"**回调时机**"，不是"**别卡帧**" ——
把 200ms 的计算丢给它，那 200ms 照样卡在 `run()` 里。

### 14.2 为什么"本线程切片"没有 API（以及它该长什么样）

`SlicedJob` 原本就是干这个的：`step(4ms)` 每帧推一小段。它被删是因为两条：

1. **页面调不到**：入口只在 `Application::submitSliced()`，而页面拿的是 `AppScope`，
   `Application` 在它**之上** ⇒ 业务写不出来（真写过的人只会撞到"没有这个方法"）。
2. **它是第二套作业契约**：提交 / 队列 / 预算 / 取消 / 错误五件事与 `TaskHost` 各一套，
   差别只有"在哪跑"。

**成熟 GUI 的做法是"作业一种，预算属于调度器"**（Flutter `scheduleTask(idlePriority)`、
Chromium `TaskPriority::BEST_EFFORT`、WPF `DispatcherPriority.Background`）。
⇒ 如果这个需求真的出现（有页面、有数据），要加的是**帧调度器的一个优先级档**：

```php
// 形状示意（未实现，不要照抄）
$this->requestIdle($fn, budgetMs: 4);   // 帧末有余额才跑，跑不完下次接着跑
```

★ 在此之前，**用进程池**。它多花一次序列化，但不会卡帧、不会崩 UI、也不要求你
把算法改写成可续跑的状态机 —— 那是"没有调度器档位"时最便宜的正确解。

### 14.3 三条"不要"

| 不要 | 为什么 |
|---|---|
| 不要为"几毫秒"的活儿开异步 | 多一帧延迟 + 多一份状态；`asyncCommand` 的价值在"等外部"，不在"算得快" |
| 不要为了"看起来并行"把一条流程拆成两个 `run()` | 两次 `loading`、两份状态、中间那一刻界面不知道该画什么（§13.3） |
| 不要自己起线程 / 用 `Fiber` | AOT 的 lint（`NanoHygiene`）明文禁 `Fiber` / `Generator`；线程要过 Zend 初始化（探针 K 未通） |

## 15. 第十一轮：`cancel()` 到底能停到哪一步（一张必须说清的表）

> 这一轮复审修了七处"注释在说假话"（论证见 [`ASYNC-ARCH-2026-10-31.md`](ASYNC-ARCH-2026-10-31.md) §13）。
> 其中唯一会**改变你对代码的判断**的是这一条：以前文档把"取消"写成"能停就停"，
> 实际上**四个执行体各停在不同深度**，而且其中一个一步都停不了。

| 后端 / 场景 | `cancel()` 之后实际发生什么 | 能不能少干活 |
|---|---|---|
| `ProcessTaskHost`（进程池，**推荐**） | 还在**排队**的：摘掉，那条任务永远不会开始；已发给 worker 的：只"不交付" | **能**（排队那部分） |
| `ThreadTaskHost`（C++ 池） | 只能"不交付"——任务已经交给 C++ worker，摘不出来 | 不能 |
| `SyncTaskHost`（默认后端） | **没有钩子**。`submit()` 里 `Job::run()` 已经跑完，取消只能"别把结果交出去" | 不能 |
| `Future::all()` / `race()` 聚合体 | 自己不干活，把取消**转给全部入参**（最终落到上面某一档） | 取决于入参 |

三条用法结论：

1. **别指望 `cancel()` 省 CPU**（除非任务还在进程池队列里没发出去）。它买到的
   是"迟到的结果不会打到界面上"，那才是它真正保证的事。
2. **`cancel()` 永不产生 `error` 态**。取消不是失败，`catch()` 不会被调到 ——
   所以"用户取消 ⇒ 页面显示错误"这种写法是有 bug 的。
3. **取消是剪枝**：一条根 Future 只该有一个主人（`AsyncCommand::make()` 的契约）。
   同一个根被两处 `then` 扇出时，一处取消，另一处也收不到结果 —— 要复用就复用
   **结果**，不要复用 Future。
