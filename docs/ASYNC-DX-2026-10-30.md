# 异步 API 的开发者手感评估（2026-10-30）

> 问题：**当前异步接口对开发者友好吗？心智负担大吗？对比成熟 GUI 有没有优化空间？**
>
> 这一份的判据是**可数的事实**（要掌握几个概念、要写几行样板、要记住几条隐性纪律），
> 不是"感觉还不错"。凡是"可以更好"的地方，都给出落点与代价。

---

> ★ **2026-10-30 第二轮（同日，接 §5）**：上面两处负担里的"一次请求的生命周期"
> 已经收成 `AsyncCommand`（P1 落地），而且它是**替换不是加法** —— `AsyncCommand`
> 是 `FutureBuilder` 的超集，所以 `FutureBuilder` **已删除**，UI 侧不再有专用异步
> 控件（见 §5.1）。"穿参"那一处经复核**不做**沿树查找（`BuildContext` 三条边界
> 与 §18 已否决），改成组合根打包（§5.3）。
>
> ★★ **2026-10-31 第三轮（收敛到一套）**：`AsyncCommand` 从"只能住 `State`"改成
> **`extends Subject`（宿主无关）** ⇒ 跨页共享那条路用上了同一个类，`apps/users`
> 的 `UserStore` 里那份**手写状态机被删除**（连带 `LoadStatus` 枚举）。
> 页面侧的入口收成 `State::asyncCommand()`（与 `State::cell()` 同一条路），
> 而且**连 `dispose()` 都不用写了** —— 卸载时由框架统一停掉在途任务。

## 0. 一句话结论

**"怎么画"这一层已经和 Flutter 平手；负担全在"Future 从哪来"和"一次请求的生命周期"两处。**

- `FutureBuilder` + `AsyncValue` 的用法与 Flutter `FutureBuilder` + `AsyncSnapshot` **同构**
  —— 一个 future、一个四态 builder，没有额外概念。
- 但 Drift 多出两笔 Flutter 没有的开销：
  ① **依赖靠手写闭包穿参**（同一个能力从组合根递到页面要改 **6 处**）；
  ② **"一次请求"没有任何对象承载**（`?Future` 字段 + `load()` + `dispose()` 取消
     + 去重判断，每页重写约 15 行纯代码 / 50 行含注释）。
- 再加一笔**架构必然的税**：`Job` / `NamedJob` / `args()` —— 进程隔离必须可序列化，
  `await api.fetch()` 这种写法在这里不存在。这笔税**只能付在组合根**，页面不该感知；
  目前恰好是这样（页面只认 `\Closure(int): Future`），这点做对了。

## 1. 换算成开发者的账

### 1.1 一个"进页面就加载、失败可重试、能翻页"的表格页要写什么

`apps/showcase/src/Pages/AsyncTablePage.php`（本仓的真实接入示例，303 行）的构成：

| 段落 | 行数 | 其中纯代码 | 是否"异步特有" |
|---|---|---|---|
| 类注释（讲清数据来源、为什么整页进 builder） | ~30 | 0 | 一次性，可复用为模板 |
| 页面壳：`__construct` / `make` / `createState` | ~20 | ~14 | 否（所有 StatefulWidget 都要） |
| **异步簿记**：`?Future $future` + `load()` 去重 + `dispose(){cancel}` | **~50** | **~15** | **是 —— 每页重写** |
| `build()` + `toolbar()` + `bodyOf()`（四态画法） | ~105 | ~70 | 部分是（四态分支 ~30 行是必要的） |
| `columns()` 等纯业务 | ~27 | ~20 | 否 |

⇒ **异步簿记的纯代码只有 ~15 行，但要理解它得读 ~50 行注释** —— 这正是"心智负担"
的形态：不是打字多，是**每次都要重新确认"我要不要 cancel / 要不要去重"**。

★ 行数按 303 行版本数（2026-10-30 改完后）。"纯代码"= 去掉注释与空行，是估算。

### 1.2 要掌握的概念数（写页面的人必须懂）

| # | 概念 | 不懂会怎样 |
|---|---|---|
| 1 | `Future`（`pending` / `resolved` / `rejected`） | 不知道 `rejected` 没人接会走 Fatal |
| 2 | `AsyncValue` 四态 | 漏一态落进 `else` ⇒ 画空白 |
| 3 | `AsyncCommand`（`run()` / `value()` / `retry()`；`FutureBuilder` 已被它取代，见 §5.1） | 以为还能"把 Future 交给控件去投影" |
| 4 | `State` 生命周期：`initState` 订阅 / `didUpdateWidget` / `dispose` / `setState` 只标脏 | 在 `build()` 里订阅 ⇒ 逐帧增长 |
| 5 | 闭包穿参（同一个能力 6 处） | 加能力时漏改一处 ⇒ 页面拿到旧闭包 |
| 6 | `Job` / `NamedJob::args()`（只有真跑后台才需要） | 忘了 `args()` ⇒ worker 侧重建时参数丢失 |
| 7 | AOT 纪律（`?->`、枚举、外部常量、`parent::__construct()`） | 解释器能跑，AOT 真机 exit=255 |

**Flutter 同等任务是 3 个概念**（`Future`、`AsyncSnapshot`、`FutureBuilder`）+ 1 个依赖查找。
**WPF 是 3 个**（`Task`、`INotifyPropertyChanged`、`IAsyncRelayCommand`）+ DI 容器。

⇒ Drift 多出来的是 **5（穿参）**、**6（Job）**、**7（AOT）**。
其中 6 是架构必然、7 是编译器约束，**只有 5 是框架设计可以改的**。

## 2. 与四家成熟 GUI 的逐项对照

同样是"表格取数 + loading + 错误 + 重试 + 翻页"：

| 维度 | Flutter | WPF | Qt | React Query | **Drift（本轮之前）** |
|---|---|---|---|---|---|
| 异步值类型 | `Future<T>` | `Task<T>` | `QFuture<T>` | `Promise` | `Future` ✅ |
| 状态快照 | `AsyncSnapshot<T>` | 手写 `IsBusy`+`Error` | `QFutureWatcher` 状态 | `{data,isLoading,error}` | `AsyncValue` ✅ |
| UI 绑定 | `FutureBuilder` | `IAsyncRelayCommand` + 绑定 | `finished` 信号 | `useQuery` | `FutureBuilder` ✅ |
| **取消** | 靠 `Future` 无法取消，用 `CancelableOperation` | `CancellationToken` | `QFuture::cancel()` | `AbortSignal` | `Future::cancel()`（两档语义）✅ |
| **去重 / 重入** | 手写 | 手写 | 手写 | **内建**（同 key 共享） | **手写**（本页靠 `$force`）⚠️ |
| **重试** | 手写 | 手写 | 手写 | **内建**（`retry: 3`） | **手写** ⚠️ |
| **超时** | `.timeout()` | `CancellationTokenSource` | `QTimer` | **内建** | **无** ❌ |
| **依赖注入** | `Provider` / `ref.watch(ctx)` | DI 容器 | 手动 / `qApp` | `Context` | **手写穿参 6 处** ❌ |
| **异步值的"从哪来"** | 直接 `await api.x()` | `await api.x()` | `QtConcurrent::run` | `queryFn` | **`Job` + `NamedJob` + `args()`** ⚠️（进程隔离的税） |
| 回调线程保证 | 单 isolate | `Dispatcher` 亲和 | 对象亲和 | JS 单线程 | UI 线程帧内 ✅ |
| **同帧重绘** | 否（下一帧） | 否（`Normal` 优先级在 render 之后） | 否 | 视调度 | **是**（泵在 `settle` 之前）✅ |

**读表要点**：

- ✅ 的四行说明**核心机制不落后**，其中"同帧重绘"和"取消两档语义"比 Flutter 更明确。
- ⚠️/❌ 集中在**"重复劳动"**（去重 / 重试 / 超时 / 注入）—— 这四件恰好是 React Query
  一个 `useQuery` 全包的，而 Drift 要每页手写。
- `Job` 那行是 ⚠️ 而不是 ❌：它不是缺能力，是**换了一种付法**（组合根付一次，页面零感知）。

## 3. 本轮查出的五处真负担

按"会咬人程度"排序。

### Q1 `didUpdateWidget()` 要求覆写者调 `parent::` —— **框架自己能做的事推给了每个开发者**

**证据**：`State::didUpdateWidget()` 原本只有一行 `$this->widget = $widget;`，
而它是 `$widget` 字段（`private`）**唯一**的更新点。于是覆写者必须记得：

```php
public function didUpdateWidget(Widget $widget): void
{
    parent::didUpdateWidget($widget);   // 漏了 ⇒ $this->widget 停在旧值
    ...
}
```

本仓四处覆写**全都老实写了**这一句（`AnimatedOpacityState` 的注释甚至写着"第一句必须"）。
纪律守住了，但**不该让纪律存在**：漏写的症状是"改了筛选条件，结果没变"，
**不报错**、极难归因。

**Flutter 怎么做的**：framework 在调 `State.didUpdateWidget(oldWidget)` 之前就把
`state._widget` 换成新的 —— 覆写者从来不需要 `super.didUpdateWidget()`。

**已修**（见 §4.1）。

### Q2 依赖靠手写闭包穿参 —— **6 跳**

**证据**：`fetchRows` 这个能力从组合根到页面，经过：

```
ShowcaseApplication::buildRoot()        闭包定义          ← 1
  → ShowcaseRoot::__construct()         参数              ← 2
  → ShowcaseRoot::make()                参数              ← 3
  → ShowcaseRoot::createState()         传递              ← 4
  → ShowcaseState::__construct()        参数              ← 5
  → NavEntry 的工厂闭包                  捕获              ← 6
```

`ShowcaseRoot` 的构造器已有 **6 个参数**（`$notify` / `$delay` / `$showModal` /
`$dialog` / `$setCloseConfirm` / `$fetchRows`），**每加一个能力就要动 6 处**。

这是**扩展性上最大的瓶颈**：不是"难写"，是"每加一个功能都要改一条链"。
`BuildContext` 目前只有 `theme()` / `metrics()` / `color()` / `metric()` / `textSize()` /
`textColor()` —— **没有任何依赖查找能力**，也没有 `InheritedWidget` 等价物。

**为什么没在本轮改**：需要 `InheritedWidget`（沿 Element 树查找 + 依赖订阅 + 变更通知），
是**重构级**改动，牵连 `Element` 的生命周期。见 §5 P3。

### Q3 "一次请求的生命周期"没有任何对象承载

每个异步页面都要自己写：

```php
private ?Future $future = null;                  // ① 承载
private function load(int $page, bool $force)    // ② 提交点 + 去重
{
    if (!$force && $this->future !== null && $target === $this->page) return;
    $this->setState(fn() => $this->future = $fetch($target));
}
public function dispose(): void                  // ③ 卸载时取消
{
    $this->future?->cancel();
    parent::dispose();
}
```

**React Query `useQuery` 一行**就给出 `{data, isLoading, error, refetch, isFetching}`，
且同 key 自动共享去重。Drift 这 ~15 行纯代码每页重写（读懂要 50 行注释），且**漏一处就出问题**：
漏 ③ ⇒ 离开页面后 worker 白跑；漏 ② 的去重 ⇒ 转圈时连点排队几条请求。

**为什么没在本轮改**：需要一个新类（`AsyncCommand`），且它天然是"超时 / 重试"的落点
（正好覆盖已记录的 G3 / G4）。单独一轮更稳。见 §5 P1。

### Q4 `AsyncValue::idle()` 在生产代码里**零消费者**

**证据**：`grep AsyncValue::idle()` 只命中 `tests/Unit/Async/AsyncValueTest.php`。
原因：`FutureBuilder` 的 `$future` 不可空、快照恒从 `loading` 起 ⇒ `idle` 永远产生不了
⇒ `isIdle()` 是死判据，`AsyncTablePage` 只能自己写一层
`$future === null ? Center('准备中…') : FutureBuilder(...)`。

四态名义、三态实际 —— **多一个必须理解但没有场景的态**，是纯负担。

**已修**（见 §4.2）：`FutureBuilder::make(?Future $future, ...)`，`null` ⇒ `idle`
（对应 Flutter `FutureBuilder(future: null)` 的 `ConnectionState.none`）。

### Q5 `FutureBuilder` 的 builder 拿不到 `BuildContext`

**证据**：签名是 `\Closure(AsyncValue): Widget`。想在 builder 里读主题
（`$ctx->theme()` / `$ctx->color(...)`），只能在外层 `build($ctx)` 里把 `$ctx`
捕获进闭包。`AsyncTablePage` 恰好没用到主题，所以这处不便**没有暴露**，
但它是隐式要求 —— 而 Flutter 的签名是 `(BuildContext, AsyncSnapshot)`。

**没有本轮改**：破兼容（2 处调用点 + 测试），收益中等。见 §5 P2。

## 4. 本轮落地的

### 4.1 `State::adoptWidget()` —— 覆写 `didUpdateWidget()` 不再需要 `parent::`

`src/Widget/State.php` 新增：

```php
/** @internal 只有 StatefulElement::didUpdateWidget() 调它 */
public function adoptWidget(Widget $widget): void
{
    $this->widget = $widget;
}
```

`src/Widget/StatefulElement.php` **顺序**改成：

```php
$this->state?->adoptWidget($newWidget);   // ① 框架先落新描述
$this->state?->didUpdateWidget($newWidget); // ② 再交用户钩子
```

`State::didUpdateWidget()` 里的赋值**保留作幂等兜底** ⇒ 三件事同时成立：

| 覆写者的写法 | 结果 |
|---|---|
| 调 `parent::didUpdateWidget()` | 无害（重复赋同一个值） |
| **不调** | 无害（框架已落）← **修复点** |
| 不覆写 | 与原来完全一致 |

**零破坏**：没删任何方法、没改签名，四处覆写一行都不用动。

**为什么不干脆把 `$widget` 改 public**：那是用一个封装漏洞换一个纪律问题 ——
封装成本不该转嫁给调用方。

**变异验证**：注释掉 `adoptWidget()` 那行 ⇒ `StateAdoptWidgetTest` 立刻红，
实际读到 `'a'`（旧值）。这是本仓少见的"测**错误写法不再出错**"的用例 ——
既有四处覆写全调了 parent，常规用例永远碰不到这一支。

### 4.2 `AsyncValue::fold()` + `idle` 有了真实语义

**`fold()`**：一次调用写完四支，缺键**当场抛**。

```php
$label = $value->fold([
    'idle'    => static fn(): string => '尚未请求',
    'loading' => fn(): string => '正在加载第 ' . $this->page . ' 页…',
    'error'   => static fn(): string => '加载失败（可重试）',
    'data'    => fn(): string => '第 ' . $this->page . ' 页 / 共 ' . $pages . ' 页',
]);
```

为什么值得：手写 `if/elseif/else` **只有三个出口**，`idle` 会落进 `else` 被当成"有数据"
⇒ 显示「第 1 页 / 共 0 页」。`AsyncTablePage` 的 `toolbar()` 原来就是这个形状 ——
`idle` 一出现，那个 `else` 就成了 bug。

为什么"缺键当场抛"而不是"用到才抛"：后者要等真的走到缺的那一态才炸，而"失败时空白"
正是缺 `error` 的症状 —— 那等于把错误推迟到最难复现的时刻。宁可第一次调用
（几乎必然是 `loading`）就抛，让问题停在开发期。

**`idle` 的真实语义**：`FutureBuilder::make(null, ...)` ⇒ `idle`。
于是 `AsyncTablePage` 少了一层 `$future === null ? 占位 : FutureBuilder(...)`
—— 那层分支只为"首帧前一瞬"存在，属于纯噪音。

> ★ 诚实说明：`AsyncTablePage` 在 `initState()` 里就 `load(1)`，所以它的首帧是
> `loading` —— **`idle` 分支在这个页面上走不到**。`idle` 的价值在"点按钮才加载"
> 的页面（不调 `initState` 加载就是 idle）。本轮验证的是"能力成立"，不是
> "这个页面用到了它"。

### 4.3 `fold()` 原来的混合签名是个 AOT-only 陷阱 —— 已改掉

第一版 `fold()` 是混合签名：`idle` / `loading` 零参、`data` 收值、`error` 收消息。
`toolbar()` 里 write 成：

```php
'data' => fn(): string => '第 N 页 / 共 M 页',   // ← 零参，但 fold 会给它传值
```

- `php -l` ✅ · `phpunit` 932 tests ✅ · `lint` ✅ · `gate` 8 项 ✅
- **AOT 真机**：`Fatal: AsyncTablePageState::{closure}() expects exactly 0 arguments, 1 given`

原因：**PHP 解释器允许"多传实参"（忽略掉），AOT 严格校验参数个数**。
而且它只在**真的走到 `data` 态**才炸 —— 失败态、加载态都正常，所以"点一下就崩"
看起来像随机故障。

**修法不是"文档里写清哪支收什么"，而是让这种错写不出来**：四支签名统一
`\Closure(AsyncValue): mixed`。代价是 `data` 分支多写一次 `->value()`；收益是
**一整类"解释器全绿、真机才崩"的故障从语法层消失**。

⇒ **这条是整份文档里最好的"心智负担"论据**：AOT 的严格性本身就是一笔开发者税，
而它**只在真机暴露** —— 再好的注释也拦不住，只能靠**让错误的写法不成立**。
这也正是为什么"减少必记事项"比"写清必记事项"更值钱。

## 5. 第二轮：收敛（P1–P4 全部处理完，且是替换不是加法）

| 优先级 | 原计划 | 结果 |
|---|---|---|
| **P1** | 新增 `AsyncCommand`，让 `FutureBuilder` 接受它 | **做成"替代"**：`AsyncCommand` 是 `FutureBuilder` 的**超集** ⇒ `FutureBuilder` 删除（§5.1） |
| **P2** | builder 给 `BuildContext` | **消失了**：没有 builder 了，`build()` 本来就有 `$ctx`（§5.2） |
| **P3** | 依赖查找（`InheritedWidget` 等价物） | **否决（有据）**，改做组合根打包（§5.3） |
| **P4** | `Button` 禁用态 | **已做**（§5.4），页面里的 `$force` 兜底随之删除 |

### 5.1 为什么是"删 `FutureBuilder`"而不是"两套并存"

`FutureBuilder` 的入参是一个 **`Future`**，而 `Future` **无主**：谁发起的、还能不能
重跑、旧的那条要不要取消，控件一概不知道 ⇒ 这三件事全摊给页面（每页 ~15 行纯代码、~50 行注释）。
`AsyncCommand` 是它发起的那条 `Future` 的**唯一持有者**，于是：

| 事 | `FutureBuilder` | `AsyncCommand` |
|---|---|---|
| 请求从哪来 | 页面存 `$this->future` + 自己 `load()` | `run($arg)` |
| 旧请求 | 页面记得"换 Future 触发重订阅" | `run()` 内部作废 + **真的 `cancel()`** |
| 迟到的旧结果 | 控件另配"订阅代号"（它不敢取消共享的 Future） | `cancel()` 之后 `Future` **永不结算** |
| 重试 | 页面把提交再写一遍 | `retry()`（记得上次参数） |
| 去重 | 页面自己判"同页且在途" | `run()` 内建（同参数在途 ⇒ 忽略） |

⇒ **凡是 `FutureBuilder` 能表达的，`AsyncCommand` 都能**（"一次性提交" = `run()` 一次；
"投影别人给的 Future" = `fn() => $thatFuture`）。两套并存只会让每个新页面先问一句
"这里该用哪个"。**能替代就只留一套。**

**UI 侧因此不再有专用异步控件**：命令住在页面 `State` 里，值一变就 `markDirty()`
（与 `Cell` 同一条路），`build()` 直接读 `$cmd->value()`。

### 5.2 P2 自然消失

`FutureBuilder` 要 `BuildContext` 是因为它的 builder 在控件内部、拿不到外层的 `$ctx`。
现在画四态的就是页面自己的 `build()` ⇒ `$ctx` 本来就在手上。

### 5.3 P3 否决：不做"沿树查找"，改做组合根打包

复核后的结论比我上一轮写的更硬 —— **不只是"成本高"，是已经被架构否决过**：

- `BuildContext` 的类注释三条边界里第 ②③ 条明写：**无业务数据**、**无向上查找**
  （`of()` / `find()` / `maybeOf()` 一律不开），理由是 §18 已否决 Flutter 的
  provider soup（"`$ctx` 后面藏着读值和订阅 ⇒ `dead-subscription` 的判据被绕过）。
- 而框架**已经有**完整的响应式设施：`Subject` / `Cell` / `State::watch()` /
  `SubjectBuilder`。再开一条"沿树查找"就是第二套依赖传播机制。

**真正做了的替代**：把示例台组合根的那 6 个能力收成一个 `ShowcaseCapabilities`
值对象（`apps/showcase/src/ShowcaseCapabilities.php`）。

- 收益：加第 7 个能力时**只改 1 处**（原为改 3 处签名 + 2 处装配点）；
  "示例台到底要接几样"有了可读的地方。
- **诚实边界**：它降的是噪音（每跳携带的参数个数），**不是跳数** ——
  页面拿到能力仍然由组合根显式递进，跳数一处没少。这是有意的。

### 5.4 P4 已做：`Button::enabled()`

`ToggleBase` 早就有 `enabled()` / `paintsDisabledLook()`，`Button` 只是没接 ——
现在补上（`enabled()` + `activate()` 早退）。框架侧三件事全是现成的：
不激活、外观变淡（`RenderBox` 按 `Modifier::$disabled` 叠 alpha）、不进 Tab 序 +
语义上报 disabled（`FocusManager` / `SemanticsBuilder` 已经读 `mods()->disabled()`）。

⇒ 异步表格页的「上一页 / 重试 / 下一页」现在用**禁用态**表达边界（`isRunning()`
直接就是判据），页面里那段"同页 / 在途就 `return`"的 `$force` 兜底**删除**了 ——
静默拒绝（点了没反应）换成了看得见的"现在不能点"。

### 明确不做（不变 + 一条新增）

- **`async` / `await` 语法糖**：PHP AOT 无法真正挂起调用栈。
- **通用 DI 容器**：见 §5.3。
- **把 `Job` 层藏掉**：进程隔离要求可序列化，税付在组合根是对的。
- **新增：命令内建超时 / 自动重试 N 次** —— 超时需要计时端口，而 `Async` 层只认
  `Errors`（依赖方向），计时端口属于 `App`（`TimerHost`）。要超时就让任务侧管
  （`ProcessTaskHost` 的 worker 超时是后端职责）。重试策略是业务决定（哪些错误值得
  重试），框架默认重试会把"幂等性假设"藏进基础设施。**不做半个。**

## 8. 第三轮：为什么"命令该住哪"这个问题的答案是"都不住"

第二轮结束时有个残留：命令构造收 `State` ⇒ 它**只能服务某一个页面**，于是跨页
共享的异步数据仍然要手写一遍状态机。当时我把它记成"两条路，各管一段"。

复核后那不是两条路，是**同一个状态机被写了两遍**：

| `AsyncCommand::start()` | `UserStore::load()`（旧） |
|---|---|
| `abandon()` 取消旧的 | `$inflight` + `cancel()` |
| `emit(loading())` | `$status = Loading; notifyChanged()` |
| `then/catch` | `then/catch` → `applyPage()` |
| — | `LoadStatus` 枚举 + `$rows` + `$error` 三个字段 |

⇒ 修法不是"给 Store 再造一个命令类"，是把**"值变了 ⇒ 通知谁"从命令里拿掉**。
命令改成 `extends Subject`：它只负责"四态 + 一次请求的生命周期"，通知走本仓既有的
订阅设施（`Subject` / `State::watch()` / `SubjectBuilder` / `Subscription`），
一个字节的新机制都没加。

| 谁持有 | 怎么收到通知 | 生命周期谁收 |
|---|---|---|
| 页面 `State` | `State::asyncCommand()` 内部 `watch()` → `markDirty()` | 框架 `unmount()` → `dropCommands()` |
| 跨页 `Store` | 构造器里 `subscribeFor($this, …)` → `notifyChanged()` | 应用自己 |

成熟 GUI 的同一形状：Riverpod 的 `AsyncNotifier` 在页面内 `autoDispose` 与全局共享
是**同一个类型**的两种寿命；React Query 的 `useQuery` 本地与缓存共用一份机制。
**寿命不是类型的一部分** —— 这正是上一版把 `State` 钉进构造参数所违反的。

### 顺带消失的两条"必记事项"

- **页面不用写 `dispose()` 了**：`State::dispose()` 是**可覆写**的，"忘了
  `parent::dispose()`"正是 A4 点名的失败模式 —— `Subscription` 的注释把这条原则
  写得很清楚（"把兜底放在用户侧就是文档承诺了、机制守不住"）。命令是同一类资源，
  于是同样由框架在 `unmount()` 时统一停掉。
- **`emit()` 里那句"宿主还在树上吗"删了**：卸载时命令已被 `dispose()`，迟到的结算
  根本到不了订阅回调 ⇒ 那是个**不可达分支**，而不可达的分支没有测试能消费
  （本仓纪律：未消费的分支 = 未实现）。留着它，读者还得替它想象一个场景。

### 用户的四态：从枚举换成值对象

`LoadStatus`（`Idle/Loading/Ready/Error`）与 `AsyncValue` 表达的是同一件事，而
`AsyncValue` 多带两样东西：**载荷**（`data` 态的值）与**消息**（`error` 态的原因）。
旧写法把这三样散在三个字段里，"失败时 `rows` 还是上一次的"这种语义只能靠
`applyPage()` 的注释守着。现在它是一条 `if ($value->hasData())`。
| **真机抓到的 bug** | `fold()` 混合签名 ⇒ AOT `expects exactly 0 arguments, 1 given`（解释器/gate 全绿）⇒ 已改为统一签名，见 §4.3 |

## 9. 第四轮：超时 —— 借 PHP-FPM 的形态，落在本仓的进程池上

### 9.1 为什么"客户端超时"是错的落点

前两轮我都把超时记成"待办，落点应是 `TaskHost` 的 per-job 超时"。这一轮做掉它，
先把"为什么不能放在 `AsyncCommand` 里"讲清楚 —— 这是本轮唯一的架构判断：

| 做法 | 谁提供 | 能停掉 worker 吗 | 成熟对照 |
|---|---|---|---|
| **客户端计时**（到点把 `Future` 判失败） | `AsyncCommand` 自己 | **不能** —— 进程还在跑、坑还占着，**且完全不报错** | .NET 6 `Task.WaitAsync(timeout)`：原任务**继续跑** |
| ** cooperative 取消**（带 deadline 的令牌） | 任务自己配合 | 只在任务真的查令牌时 | `CancellationTokenSource.CancelAfter` / gRPC deadline |
| **墙钟上限 + 杀进程**（本轮做的） | 握着进程句柄的那一层 | **能** | PHP-FPM `request_terminate_timeout` |

⇒ 握着 `proc_open` 句柄的只有 `ProcessTaskHost`。**放在别处都是半个。**
（客户端计时的那个"半个"尤其坏：它让 UI 看起来恢复了，实际池的有效容量悄悄掉
一格 —— 没有任何信号。）

### 9.2 从 FPM 借了什么

FPM 那条指令的形态几乎可以逐条照搬，因为两边是同一个形状（一个 master + 一组
PHP 子进程）：

| FPM | 本仓（`ProcessTaskHost`） |
|---|---|
| 池级指令 `request_terminate_timeout`（pool.d） | 构造参数 `$requestTerminateMs` |
| **墙钟**，从 master 把请求交给 worker 那一刻起算 | `hrtime`，从 `send()` 派发那一刻起算 |
| 到点 `SIGTERM`（必要时 `SIGKILL`），master 补一个 | `proc_terminate()`，下一帧 `flush()` 自动补 |
| 失败以 502 回给客户端 | `Completion(error)` ⇒ `Future` 判失败 ⇒ `AsyncCommand` 落 `error` 态 |

三条刻意跟着 FPM 走的决定：

1. **墙钟而不是 CPU 钟**。FPM 的文档把这件事讲得很透：PHP 的
   `max_execution_time` 只对 CPU 时间计时（`setitimer(ITIMER_PROF)`），
   `sleep()` / 慢查询 / 卡住的 curl **一律不计**。本仓的任务同样可能卡在 IO 上。
2. **默认开（30s）而不是默认关**。FPM 的默认值 `0`（关）被运维界叫作
   *the dangerous default*。本仓默认关更糟：worker 卡住 ⇒ `AsyncCommand`
   永远 `isRunning()` ⇒ 翻页 / 重试**全禁用** ⇒ **用户没有任何出路**，只能杀程序。
3. **计时从派发开始，不从提交开始**。排队等空闲 worker 不是"卡住"，是正常等待；
   而卡住的 worker 会被杀、池会补，所以排队不会饿死。

### 9.3 没借什么（诚实边界）

- **per-job 覆盖**：FPM 也只有池级一条。两条取数任务都在 1s 量级，一个池级上限
  足够。真出现"有的任务就是慢"再按需求加 —— 不提前铺。
- **慢日志**（FPM 的 `request_slowlog_timeout`）：需要一条独立的诊断通道与采样
  策略。超时消息里带**任务名**已经够定位。
- **`SyncTaskHost` / `ThreadTaskHost` 不提供这道闸**：同步后端里任务是 inline 跑完
  的，**不存在"卡住的 worker"这个对象**（真慢的话 UI 已经卡了，问题在别处）；
  线程后端杀不掉线程。⇒ 超时是**进程池这个后端的能力**，不是端口契约的一部分
  —— 与 `needsPolling()` 同类：后端声明"我能不能叫醒你"，调用方不猜。
- `State → Platform` 那条边**仍然没人走**：命令因此不需要计时端口。

### 9.4 顺带修掉的三处"说了不该说的话"

- `UserCommands::refresh()`：`load()` 返回后立刻 `say('已刷新')` —— `handle()`
  是**同步**的，它不可能知道异步结果。改成只说"正在刷新…"；"完成了没有"由
  `AsyncValue` 那四态回答（那才是真的状态）。
- `DESIGN.md` §11.5 仍以已删的 `LoadStatus` 手写三态为范例 —— 加了"不要再照它写
  新代码"的更新块 + 当前形态。
- `Spinner` 的类注释仍写 `LoadStatus::Loading => …`。

## 10. 第五轮：界面上的两个谎言 —— "载荷被扔掉" 与 "浇筑时的快照"

第四轮把"超时"落到了进程池上，async 这条线看起来收完了。这一轮**又抓出两个**
问题，它们的形状不同，病根是同一句话：**界面没有如实反映异步状态**。
一个在类型层（载荷活不下来），一个在读法层（会变的值没在订阅里读）。

### 10.1 谎言一：刷新 / 翻页时内容整块消失

`AsyncCommand::start()` 发的是 `AsyncValue::loading()` —— **不带载荷**。于是：

| 动作 | 上一版的画面 | 用户读到的 |
|---|---|---|
| 点「下一页」 | 表格 → 整块转圈 → 新表格 | "卡了一下" |
| 点「刷新」 | 列表 → 一个转圈 → 列表 | "我刚才看的东西呢" |
| 刷新失败 | 列表 → 错误 | 内容丢了（值随 `loading` 一起被扔掉） |

`fold()` 的 `loading` 支被**强制**画成转圈，因为那一态里**没有东西可画**。
这不是页面写错了，是**类型表达不了**"同时有旧数据 + 正在取新的"。

### 10.2 为什么"加一个 `refreshing` 状态"是错的

最直觉的修法是加第五态。但它把两个不同的问题混成一个：

| 问题 | 是"状态"吗 |
|---|---|
| 请求在不在途 | 是（`loading`） |
| 手上有没有值 | **不是**，是载荷的归属 |

"刷新中"= 在途 **且** 有值 —— 它是两个维度的**组合**，不是第三个维度。加成第五态
的直接代价：`fold()` 多一个键，而"漏写一支 ⇒ 静默画空白"的失败模式跟着翻倍
（`fold()` 的注释专门讲这一类）。

成熟 GUI 全都是两维：

| 框架 | 形状 | "刷新中"怎么表达 |
|---|---|---|
| Flutter `AsyncSnapshot` | `(ConnectionState, data, error)` | `waiting` + 有 data |
| Riverpod 2 | `AsyncValue` + `copyWithPrevious()` | `isRefreshing` / `isReloading` |
| React Query / SWR | `status` + `data` | `keepPreviousData` / `isFetching` |

⇒ 本仓选**两维**：四个名字不变，**载荷可以跨状态存活**；`fold()` 的分支选择按
"**现在该画哪一块**"走 —— `loading` **且带旧值** ⇒ 走 `data` 支。这就是 Riverpod
`when(skipLoadingOnRefresh: true)` 的默认行为（默认就对了，页面才不用每处手写）。

### 10.3 落地（替换，不是新增机制）

| 处 | 改了什么 | 一句话理由 |
|---|---|---|
| `AsyncValue` | 新增 `$hasValue` 字段、`carriedFrom()`、`hasValue()`、`isRefreshing()` | 载荷与状态分开；"有没有值"不能用 `$value !== null` 判（`data(null)` 是合法值） |
| `AsyncValue::dataOr()` | 判据从 `state === DATA` 改成 `hasValue` | 刷新中照旧画得出来 —— 消费点不必各写一份 `hasData() ? … : $last` |
| `AsyncValue::fold()` | `loading` **且有值** ⇒ 路由到 `data` 支 | 四支的名字描述"画哪一块"，`loading` 因此被收窄成**首屏** |
| `AsyncCommand::start()` | `loading()->carriedFrom($this->value)` | 一处发出，所有消费点自动受益 |
| `AsyncCommand::land()` | 结算统一 `$next->carriedFrom($this->value)` | `data` 自带载荷（不动），`error` 继承旧值 ⇒ "失败说得出来、旧内容也还在" |
| `AsyncCommand::cancel()` | 有旧值 ⇒ 回 `data`，没有 ⇒ `idle` | 取消是"我不等了"，不是"把看到的东西也扔掉" |
| `AsyncTablePage` | 标题在 `isRefreshing()` 时说"正在加载第 N 页…" | 那时表格里还是**上一页**，写"第 2 页"就是在说没有依据的话 |
| `AsyncTablePage` | `loadingLabel()` 一处 | 两处各写一份 ⇒ 改文案必然只改一处 |
| `UsersPage` | 见 §10.4 | 另一个谎言 |

### 10.4 谎言二：`enabled()` 是浇筑那一刻的快照（真机抓到的）

`UsersPage` 是 `StatelessWidget` —— `build()` 只在这棵子树被造出来时跑一次。而本应用
**进页面就取数**，所以：

```php
Button::primary('刷新')->enabled(!$this->store->page()->isRunning())   // ← 旧写法
```

那一次 `isRunning()` 必然是 `true` ⇒ 按钮**永久灰掉**。真机探针（手动结算的后端）：

```
enabled(loading)=false isRunning=true      ← 首帧：对
enabled(settled)=false isRunning=false rows=1  ← 数据到了，按钮还是灰的（bug）
enabled(reload)=false  isRunning=true
```

上一轮刚把"禁用态"当成边界表达的正解（§5.4），却忘了**它得跟着状态走**。
修法不是"再想个办法刷新按钮"，是把那段包进 `SubjectBuilder`（切片 = `isRunning()`
一个布尔），并顺手把"刷新中"的信号补上（列表不消失之后，界面否则看起来像
"点了没反应"）。

**为什么一个布尔就够**：`AsyncCommand` 维持一条不变式 —— *`isRunning()` 的每次
变化都伴随一次值变化*（`start()` 里先置 `pending` 再 `emit(loading)`；`land()` 里
先清 `pending` 再 `emit(结果)`）。所以"值变了"就是"按钮该重算了"，不需要给
`isRunning()` 单开第二条通知通道 —— 两条通道迟早会不同步。

⇒ 提炼成一条页面层纪律（已写进 `UsersPage` 的类注释）：
**页面里任何读 Store 的地方都必须落在某个 `select` 之内，否则它就是快照。**

### 10.5 没做的（诚实边界）

- **`error` 不路由到 `data`**：带旧值的失败照样进 `error` 支（与 Riverpod
  `skipError: false` 一致）。失败必须被看见 —— 否则就是"静默不刷新"，用户以为
  数据是新的。想在错误条下面继续画旧内容，就在 `error` 支里读 `$v->dataOr()`。
- **不做缓存 / `staleTime`**：与 §9 的边界同 —— 缓存键策略是上层课题。
- **不做每键 debounce**：本仓的搜索是本地过滤（同步），没有真实需求。
- **per-job 超时 / 慢日志**：仍未借（同 §9.3）。
- **"手感"仍无人眼验证**：本轮新增的「刷新中…」提示同样只有断言（文字在树上、
  旧行仍在），**不证明**好看。
