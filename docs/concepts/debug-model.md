# 调试模型：一帧的因果

> 调试器记录的不是"某一刻长什么样"，而是"这一帧为什么变成这样"。本页说明这套记录的四个原语、三个挂点、因果方向，以及它的能力边界。

## 为什么不是快照

GUI 最常被问的三类问题，截面数据都答不了：

| 症状 | 快照能答 | 实际需要 |
|---|---|---|
| 第 37 帧闪了一下 | 不能 | 相邻帧的差异 |
| 这个控件为什么变宽 | 只能看到矩形 | 谁写了状态、约束怎么传下来 |
| 重建风暴 | 只有一个总数 | 哪个 State 每帧写、在哪个调用点写 |

Chrome、Flutter、React Profiler 都在往"时间 + 因果"走，但它们的因果是**估**出来的：采样、启发式、手工埋点。Drift 不一样——声明式重建、布局是纯函数、绘制是显示列表。**因果在这里可以精确记录，不需要推断。**

## 四个原语

| 原语 | 定义 | 作用 |
|---|---|---|
| **Frame** | 一次 `Application::frame()`，帧号单调递增 | 一切观测的时间基准 |
| **Node** | `Element::$debugId`，元素生命周期内稳定 | 跨帧引用同一个节点的唯一地址 |
| **Edge** | `kind` + `from` + `to` + `site` + `detail` | 因果本身 |
| **Record** | 一帧的不可变事实：时间、帧内耗时、各段耗时、重建集合、边 | 环形缓冲的存储单位 |

一帧就是一条因果链的落成：`状态写入 → 重建节点 → 布局 → 绘制`。前两段按因果边记录，后两段按**分段纳秒**记录（见下文），不再只有一个总数。

## 只有三个挂点

全框架只有三处会产生"可归因的变化"，别处都是它们的下游：

| 挂点 | 位置 | 记什么 |
|---|---|---|
| 状态写入 | `State::markDirty()` 的 clean→dirty 跳变 | 谁写的、在哪个文件哪一行写的 |
| 节点重建 | `Element::settlePass()` 真正调 `rebuild()` 之前 | 本帧真正重建了哪些节点 |
| 帧边界 | `Application::frame()` 进出 | 帧号、跑过的段、各段耗时、是否跳过 settle / paint |

"真正调了 rebuild"与"标脏了"是两件事：脏标记可能被父节点重建吸收，也可能因为帧被跳过而没有消费。记录必须落在**执行点**，不能落在标记点。

未安装录制器时，每个挂点只多一次静态判空，热路径可忽略。

### 时间单列，不混进因果

一帧 40ms 与 360 个节点重建同时出现时，"谁写的"回答不了"时间花在哪"。记录因此复用 `Rendering\SurfaceProfile` 这个**全仓唯一的计一段入口**（`settle` / `layout` / `paint` 在 `Frame::run()` 里计时，壳的 `stage()` 拿不到，不能自己抄第二份）。录制器安装时打开量具、帧首清零、帧末把累计纳秒抄进帧记录；关闭时还原。

两条纪律：

- **段账没覆盖的部分单列成"段外"**，不用帧内总数冒充已归因。实测 table 点击帧 40ms：`settle` 30ms、`layout` 8.8ms、`paint` 1.1ms。
- **不接管调用方已经打开的量具**：bench 的跨帧累计账不能被帧首清零冲掉；那种情况下宁可不记段耗时。

## 因果方向由消费端决定

`setState` 多数发生在帧外——输入回调、定时器、异步结算。它标记脏，但要等下一帧 settle 才被消费。

所以边先攒着，帧末统一归到"消费它的那一帧"。方向是 **写入 → 未来某一帧**，不是"本帧写入本帧重建"。反过来记会丢掉绝大多数真实的起因。

`why()` 的 `kind` 只有三种，含义写死：

- `state`——该节点自己的 State 写了，`site` 是调用点；
- `parent`——自己没写，父节点重建带着重建（声明式重建的常规路径）；
- `unknown`——既没写也没找到重建中的父节点（浮层、跨树、计数漂移）。**出现 `unknown` 本身就是线索，不要给它编原因。**

## 节点身份的语义

`debugId` 是元素生命周期内稳定的整数，不回收。它和用于调和的 `key` 是两种身份：

- `key` 回答"这个位置上的新 Widget 是不是原来那个"，位置一变就不稳；
- `debugId` 回答"调试器说的是不是同一个节点"，只在元素销毁时失效。

记录里**只存 id 与父 id，不持有 Element**。环形缓冲裁剪时不能拖住一棵已卸载的树；元素销毁后，它的 id 仍能在历史帧里解释清楚，因为类名与父链在登记时就抄下来了。

## 回放：在不在，由生命周期说

`tree --frame=N` 回答"第 N 帧时这棵树长什么样"。它不复制结构，只做一次集合过滤：

- `f`（出生帧）：节点第一次登记的那一帧，登记时写一次；
- `g`（离开帧）：几何采样的先序遍历里再也看不到它的那一帧；
- 区间 `[f, g)` 就是它在树上的寿命，`f > N` 是"还没出生"，`g <= N` 是"已经走了"。

`f` 不能从"最近见到帧" `s` 反推：静止的容器 `s` 一直不动，拿它当出生帧会让整棵静止的
树在回放早期帧时凭空消失。`g` 也不能拿 `s` 顶替：连续 120 帧没被触达的节点会被回收，
但它其实还在树上（几何采集关着、或连续静止帧）—— 那种情况 `g = 0`，回放时一直算活着，
并计入 `lifecycle.unknownGone`。

已回收节点在 `f <= N < g` 时照样画出来并标 `evicted`。回放的主角恰恰是"后来消失了的
东西"：只列活节点等于把"这个按钮什么时候没的"这个答案删掉。所以回收表里留着父与类型，
`pathOf()` 也认它 —— 否则它们在树里全变空串，而空串看起来跟"这是个根"一模一样。

`rebuilt` 取自该帧的 `FrameRecord`，不从 `s` 倒推：静止节点的 `s` 停在旧帧、刚重建过的
节点 `s` 恰等于目标帧，两个方向都会骗人。帧记录滚出窗口时给 `null`（未知），不是 `false`。

缺口只有一种，而且必须自报：缺 `f` 的旧证据包、缺 `g` 且没开几何采集的会话。两处都让
`coverage.lifecycle.complete = false` 并给出条数 —— 宁可交一张标着"部分靠估计"的图，
也不交一张看起来完整、实际删掉了半个应用的图（A67）。

结构与几何是**两个窗口**（帧 600、几何 60，且几何按"有变化才落记录"跳帧），所以它们各有
默认值：结构取最新帧、几何取几何窗口最新帧。一个默认值不可能同时落在两个窗口里 ——
取几何最新会让回放停在几十帧前的旧树，取帧最新会让几何注解立刻"窗口外"。显式 `--frame`
时两者都听它的；几何帧超出窗口时夹到窗口内并标 `geometryStale`，不假装那一帧采过。

## 查询的形状

查询读的是不可变记录，是纯函数，可以随便重试、缓存、并行：

| 查询 | 回答什么 |
|---|---|
| `frames` | 最近 N 帧的摘要，可按"有重建"过滤；给 `since` 则只取更新的帧（增量游标） |
| `explain` | 单帧展开：耗时、重建节点及路径、按 kind 分组的根因 |
| `why` | 某个节点为什么重建：直接边 + 到根的链路 |
| `cascade` | 单帧**因果森林**：结构根、子树规模、写入点、按类型构成 |
| `tree` | 第 N 帧的**结构树**：按出生 / 离开帧过滤，已回收节点在它活着的帧里照样画出 |
| `hotspots` | 跨帧聚合**根因**：调用点 + State 类，按次数排序 |
| `nodes` | 跨帧聚合节点：重建次数、覆盖子树、自身写入与父传播 |
| `digest` | 记录指纹：节点表 + 逐帧因果哈希（不含时间，可跨进程可跨机器比对） |
| `script` | 本次会话录下的驱动脚本：目标 / 视口 / 环境 / 步骤 |
| `stats` | 录制概览：帧数、节点数、容量、最近帧 |

`hotspots` 只聚合 `kind=state` 的边。`parent` 与 `unknown` 只计数，不参与排序——一个状态写入会让整棵子树逐层产生 `parent` 边，把它们算进根因会让排名全是传播，不是原因。

### 为什么单帧要有森林，而不是排行榜

一次动作帧里常常 300+ 个节点各重建 1 次。"按次数排名"这时没有区分度，排序退化成路径先序，前几行必然是 `PageShell > Card > Column` 这类祖先链——读者会以为根节点是热点。成熟工具（React Profiler、Flutter Widget Rebuild Stats）在单帧里给的是**层级**，次数留到多帧聚合才有意义。

`cascade` 的四个口径：

- **结构根**＝结构父没有重建的节点。森林因此不重叠，`Σ(根.subtree × 根.count) + hidden == rebuilt` 是可判据的。结构父是**元素树上的父**，与"谁让它重建"无关：自己写状态的节点仍然是父的孩子，只是那一行多了个 `←`。
- **写入点不另起根**，只标 `kind` + 调用点。它常常嵌在另一个写入点的子树里（表格页：`PageShell ← TablePage ⊃ Expanded > Table ← TableState`），另起根会把嵌套关系抹平。
- **`byType` 按 Widget 类型聚合**（`SizedBox×88 / Text×69 / …`）：360 行压成十几类，同类控件的重复路径也就不再需要区分。
- **同形兄弟折叠**（`count`）：子树形状相同的兄弟折成一行 `SizedBox ×12`。这是 perf / WPA 折叠相同调用栈、Instruments 折叠递归的同一手法，见 A34。

结构根的旧实现只认 `kind=parent` 的边，于是"自己写了状态"的节点在树里没有父，被画成第二个根——表格页因此看起来是两棵并行的树（`PageShell 18` 与 `Table 342`），而实际上 Table 就在 PageShell 的子树里。看到的两个数都是真的，错的是"并行"这个读法。修法是把结构父记在 `state` 边自己身上：因果链的终点由 `kind` 决定，嵌套由 `from` 决定。

`nodes` 的排序是"次数 → 覆盖子树 → 路径"三级。单帧里次数并列，实际由覆盖决定；报告会明说"次数无区分度"，不让读者把榜首当成重建最多的节点。

`why` 不指定帧时取**最近一次重建它的帧**，不是最后一帧：多动作场景的最后一帧常是静止帧，按最后一帧回答只会得到"它没有重建"，把问题原样退回来。

实测一帧表格点击（360 个重建）：一次页面级写入牵动 **360** 个节点，其中 Table 自己也写了，那一支是 **342** —— 按"次数"口径它们都是 1，这就是只看次数会漏掉的东西。同一帧里 `Column` 底下 12 个 `SizedBox` 同形，折叠后一行讲完 300 个节点；顶部那条"壳 → 卡片 → 列 → 展开"的单链折成一行。一张表格的因果树因此是 8 行，而不是 360 行。

命令行用法见[命令速查](../reference/cli.md)里的 `composer debug`。两条经验来自真页面跑出来的手感：

- **目标是路由 id 时才能跑真实页面**（`--page=async-table`）。依赖页由组合根同款的页面工厂表装配，不必为了看一眼因果另写一个 `Application` 夹具。夹具类名照样可用，但它只覆盖无参构造的那几页。
- **异步要看"数据落地那一帧"**：取数先挂住（`--rows=N`），再 `--resolve` 结算。结算发生在帧外，由下一帧的 settle 消费——这不是工具的将就，正是因果方向本身（写入在帧外，边归入消费它的那一帧）。

## 回放：把记录变成可复现的

记录回答"为什么变成这样"，**脚本**回答"当时是怎么驱动的"。两者必须来自同一次运行，
所以记在同一个挂点上（帧边界、输入派发入口、驱动方声明的副作用），不另起旁路。

| 只有 | 缺 | 后果 |
|---|---|---|
| 帧 | 输入 | 同一串帧，画面永远不动 |
| 帧 + 输入 | 具名副作用（异步结算等） | 页面一直转圈，异步路径一次都没走 |
| 帧 + 输入 + 副作用 | 目标与视口 | 换一页照样跑，报告却是另一个故事 |

**回放是重新执行，不是恢复现场。** 某一帧的 `State` 里可能有关闭、资源、对象图，
存不下也读不回（见下面的边界表）。Drift 的布局是纯函数、重建是声明式，所以
"从第一帧重跑到第 N 帧"必然得到同一份因果 —— 这比快照给得更多：快照只有结果，
重跑能说出"第 3 帧写了状态、第 5 帧才被消费"。

虚拟时钟**不需要新建**，引擎里本来就有：`frame($t)`、`pumpTimers($t)`、
`tickFrameStamped($t)` 全部只认注入的时间戳，不读环境时钟。脚本把每个时间戳记下来，
两次重放喂的是同一串数字。唯一的墙钟残留是 `CompletionQueue` 的每帧交付预算
（4ms）：一帧有多条异步结果在排队时，"这一帧交了几条"取决于机器快慢。
脚本让"一帧结算一条"成为常态，真的撞上多条的场合，摘要会红 —— 那是一个**真实信号**
（这一帧的行为依赖机器速度），不是判据的噪声。

两条纪律：

- **脚本记标注前的输入**。`TapTracker` 会按时间给指针事件标"第几次点击"；记结果会让
  重放再标一次（双击变三击），而那种偏差在报告里看不出来。
- **摘要不覆盖时间**。`t` / 帧内耗时 / 各段纳秒都是这台机器这一秒的运气；摘要只比
  "谁重建了、因为谁、跑了哪些段"。时钟一致性由脚本摘要单独保证。

判据是"同一脚本跑两遍，节点表与逐帧因果逐值相同"。它必须同时有区分度：一次点击帧
要真的重建了节点（否则"两次都是空"也相等），去掉那两条指针事件后摘要要真的变。

## 传输：同一次运行的多次追问

引入传输的**真实理由**不是"跨机器调试"，而是"一次驱动、多次追问"。

没有它时，每个问题都要重跑一遍页面（挂载 + 几百帧），而两次运行的时间戳、异步交付
顺序本来就不保证相同 —— 于是"为什么这一帧慢"和"这棵树为什么重建"取自**两次不同的
运行**，合起来是拼凑的证据。会话留在另一个进程里，十几次查询都对着同一次运行。

| 形态 | 驱动 | 用途 |
|---|---|---|
| headless | 显式 `frame(ts)`，虚拟时钟 | CI 断言、脚本回放 |
| live | 真窗口帧循环 | 开发期人看 |
| attach | 另一个进程读已有会话：宿主子进程，或 dev 壳里正在跑的真窗口（A57，`DRIFT_DEBUG_LIVE=1`） | 一次运行多次追问、将来的面板与崩溃取证；宿主自走时还能叫停与单步 |
| web | 浏览器读同一个会话（`debug web` 起本机 HTTP，页面轮询 `frames(since)`） | 把几何画出来：终端只能印数字，而矩形能被看见 |

三者的查询代码完全相同：`DebugSession` 与 `RemoteSession` 实现同一对接口
（`SessionQueries` / `SessionDriver`），差异只在"谁执行那串步骤"。

### 协议十二个方法，按角色分组

| 角色 | 方法 |
|---|---|
| 会话 | `open` / `close` |
| 驱动 | `frame` / `input` / `effect` |
| 读 | `query` |
| 内省 | `eval`（默认关，不是证据） |
| 干预 | `pause` / `resume` / `highlight` / `pick` |
| 收尾 | `finish` |

`pause` / `resume` 改的是谁推帧，`highlight` 改的是下一帧画什么，`pick` 改的是
下一次输入给谁（A58）—— 三者都不改记录，所以同属干预这一组。活窗口拾取只由
有真窗口的 live 宿主支持，自走宿主回 `not_applicable`。

凡是 `query` 能表达的都不另开动词 —— `script` 与 `digest` 因此是**查询名**。
每多一个动词，对端就多一份"哪个先哪个后"的状态要维护，而状态会漂。

干预是唯一的反向流，它改的是**推进的节奏**而不是记录：`resume` 带 `frames` 就是单步，
推进的仍是脚本自己的下一帧。因此帧仍只由一方给：自走宿主上 `frame` 被拒
（`not_applicable`），从属宿主上 `pause` / `resume` 被拒 —— 一个错误码管两种情形，
因为它们是同一个问题（帧由谁推）的两面。`attach` 回执里的 `driven` 提前回答了它，
客户端不必发一条试试。

消息是一行一条 JSON（NDJSON）。长度前缀更省一次扫描，但人没法直接对着它敲；
调试工具本身的可调试性值这一行代码。`\n` 由 `json_encode` 转义，所以"一行"不会被
内容里的换行劈开。

### 三条边界纪律

- **传脚本，不传记录流**（D2 定下来的）。一份 6 步的脚本能让对端重算出 600 帧的
  全部因果；记录流要把每一帧的边都搬过去，再配上游标、背压、断线续传。
- **游标不是订阅**。`frames(since=N)` 由调用方持游标，服务端无状态 —— 可以重试、
  可以两个消费者各拿一份。订阅漏一条之后每条都是错的，游标只是"再问一次"。
- **数字的类型要过得了边界**。PHP 的 JSON 只有一种数字：`json_encode(40.0)` 写出
  `40`，读回来是 int。编码时带 `JSON_PRESERVE_ZERO_FRACTION`，浮点永远带小数点，
  往返后类型不变。这不是给判据开后门 —— 不带它，读回来的东西**真的**变了类型。
  同理，对象不许过线：`json_encode(new stdClass())` 是 `{}`（不报错，内容没了），
  所以编码前显式走一遍"只有标量 / 数组 / null"。

传输的**实现**只在 `tools/`（stdio、子进程管道与 loopback socket）。`src/` 里只有接口和镜像，
`Debug\Protocol` 不碰任何 I/O —— AOT 面因此不变。

可判的条件是**帧时间 `t` 来自脚本**，不是"宿主从属"。从属只是一种实现方式：宿主
不自推帧、不读时钟，于是墙钟混不进来；但反过来不成立 —— 自走宿主照样可判，只要它
喂进去的 `t` 仍是脚本里的值（`--speed` 改的只是两次 `pump()` 之间等多久）。真正
不可判的是拿 `now()` 当 `t`：动画位置、`after()` 到期判断都会跟着机器速度漂。把
"从属"写成原因，会让后来者以为"宿主自己跑"是个路线问题，而它只是调度问题。

一次失败（参数写错、页面抛异常、副作用返回了对象）回一条错误信封，会话继续；
崩掉宿主的话客户端只看到"管道断了"，真正的原因已经丢了。

判据是"同一份脚本，同进程跑与隔着管道跑，读回来的值逐值相同"。时间列（`cost` /
`wall` / 段耗时）不参与相等 —— 它们是这台机器这一秒的运气，比进去判据会永远红；
但必须证明它们**确实过了管道**且是正数。

## 面板：选择是身份，不是位置

面板是传输的第一个真消费者。在那之前，`--remote` 那类用法是"跑一遍、打印、退出"——
它验证了"隔着管道读回来的值逐值相同"，但没验证"读回来之后还能接着问"。面板做的是
后者：一次驱动，十几次追问，每次追问都对着同一帧。

它把一批新问题摆上桌，全都不在记录里，在**视图状态**里：什么该跟着重算，什么不该。

### 光标挂在行键上，不挂在下标上

树的行表每帧都会重算：展开、折叠、换帧、patch 落地都会变。如果光标存的是"第 7 行"，
行表一变，第 7 行就是另一个节点——用户看起来"选中了自己没点的东西"。Chrome DevTools
与 React DevTools 早期重开面板丢选中，根因都是同一件事：**拿位置当身份**。

所以每行都有一个由记录决定的稳定键：树行 `t:<debugId>`，帧行 `f:<帧号>`。行表怎么重算
都与身份无关。面板拿两个查询接口（`SessionQueries` + `SessionDriver`）时收的是一个合成
接口 `Session`，不是两个参数——分开收会让"本地会话配远端驱动"在类型上合法，读 A 的
记录、推 B 的帧。

键也可能消失（那个节点这一帧没重建）。这时沿记录里的父键往上找最近的还活着的一行，
找不到才退到第一行——并且**写进状态栏**。静默跳走比跳错更糟：用户以为自己还在原处。

### 跟随要有条件

推帧（`n`）不总是让画面往前走。新帧若一个节点都没重建，时间轴多了个数字、树一模一样，
跟着走只会让人以为"我点错了"。所以只有新帧**真有重建**才移动光标，否则明说
"#3 没有重建，仍看 #2"。换帧（`[` `]`）反过来：不重置光标，尽量停在同一个节点上，
消失时由上面那条回退规则说明。

面板不忙着重画整屏也是同一件事的两面：屏幕行数恒定（表头 / 分隔 / 正文 / 分隔 / 页脚），
滚动只改正文里取哪一段。行数变化会让终端里"刚才那一行"的位置漂移，眼睛得重新找。

### 虚拟化在格式化之前

2000 个节点摊平成一屏 24 行，靠的不是"少画一点"，是**顺序**：先摊平成轻量行对象
（键、深度、标签、计数，不含排版），再只格式化视口里那几十行。反过来的话，先格式化
全部再切片，2000 次 `sprintf` 白做，而这一层恰好最容易被写成"反正很快"。

### 单链折叠是排版，不是数据

`A > B` 合并在同一行显示（单孩子、`count` 相同），这件事不进记录、不进查询——记录里
它们是两个节点、两条边。合并只发生在视图层，纯函数 `TreeRows::flatten(roots, collapsed)`，
`tools/debug-report.php` 与面板共用同一份：命令行看到的树和面板里看到的树不是"两套实现
碰巧长得像"，而是同一份排版被钉在判据上。判据钉 `label` / `key` / `parentKey` 三个字段
就够——键取链尾，父键是链尾的父行。

断开条件与 CLI 一致：`kind !== 'parent'`（叶子不并）、`omitted > 0`（有截断边不并，
否则 `… ×N` 会被自己吞掉）、`count !== 1`（折叠组只能当链尾）。

### 表格只有一份列规格

终端报表最容易悄悄坏掉的地方不是数字，是**列边界**：`sprintf('%-22s')` 补的是字节，
中文一进来就少补几列，屏幕上看只是"有点歪"，没人会去查。「耗时分布」那张表就歪了
一整轮 —— `（段外）` 显示 18 列、`settle` 22 列 —— 因为它住在脚本里、没有判据。

所以新表一律走 `View\Table::render($cols, $rows)`：列是显式声明的（定宽截断 / 自适应
不截断 / 右对齐），宽度与补齐只由 `View\Fit` 算。两条口径跟着这张表走：调用点与路径
这类自由文本列**永不截断**（它们就是"该改哪一行"），数字列右对齐（个位要能竖着扫）。
报表的排版是 `View\Report::lines()` 这个纯函数，出口脚本只 `fwrite` 并给退出码——
这样列边界才钉得住判据（A66）。

### 截断参数是给文本报告用的

`cascade` 的 `maxDepth` / `maxChildren` 存在是因为 `debug-report.php` 要控制篇幅。面板要
完整结构，传 `maxDepth: 64, maxChildren: 0`（`0` 表示不丢分支）。把截断当成"性能优化"
直接沿用，用户点开第三层就发现下面没了，而界面上没有任何东西告诉他这是被截的。

## Web：第三个消费者，不是第二套实现

`debug web` 起一个本机 HTTP 服务，页面在浏览器里画。它存在的意义只证明一件事：**投影只有一份**。

### 浏览器说不了 NDJSON

协议传输是"一行进一行出"（`Transport`），三个实现都是本机管道。浏览器只会 HTTP。
`debug web` 因此自己起一个最小 HTTP/1.1（`tools/Debug/HttpServer.php`）：一个连接一条
请求、`Connection: close`、不做 keep-alive / 分块 / 压缩。它不用 `php -S`，因为那些请求
要读的是**本进程里的** `SessionQueries` —— 把几百帧的数组交给另一个进程只能落盘，而落盘
等于每个请求重做一遍采集。

### 轮询，不是 SSE 也不是 WebSocket

当前页面每 1s 轮询 `/api/state`，帧号变化后再取该帧几何；`frames(since)` 本身仍是无状态游标（见上），只是页面暂未用它。SSE 要在服务端存订阅者集合，WS 要多一套帧协议与掩码 —— 两个都要引入
"谁在看"这份状态，而这份状态会与帧推进耦合。

Chrome DevTools 用 WebSocket 是因为 CDP 是**双向命令**通道；这层的控制只有 `pause` /
`resume` 两个低频动作，普通 POST 就够。为了"像成熟工具"而引入 WS，是拿一份会漂的状态
换一个不会用到的能力。

### 页面不许有第二个数字

阈值、顺序、几何、父子关系全部来自响应体：`thresholds` 随 `--slow` 变，`findings` 的顺序
就是数组顺序，盒子用 `rect` 四值。页面的 JS 里不许出现 `16.6`、不许 `sort()`、不许自己
从 `offset` 累加坐标。

可判形式：`/api/brief` 与 `brief --json` 的 `findings` 逐值相同。两份要是各算一遍，那些
数字迟早对不上，而对不上时读者不知道信谁。

### 绝对坐标归查询层

画布要的是绝对矩形，而记录里存的是"相对父内容盒原点的偏移" —— 绝对坐标会"因为祖先挪了
一像素"而整片失效，相对偏移只随自己的父变，几何的签名才稳。

于是 `boxes()` 每行给出 `rect`：**在一处**把父链累加成视口坐标（与 `pick()` 的 `hitTest`
同口径）。这不是判断（"这里不对"），是坐标变换；发给每个消费者自己抄一遍，抄错的表现是
盒子错位，而没有读者会先怀疑自己的遍历。

## 边界

明确不做，以及为什么：

| 不做 | 理由 |
|---|---|
| 活对象引用（`objectId` 那类） | PHP 序列化不了闭包与资源，AOT 也没有稳定地址 |
| 实时属性编辑 | Widget 不可变、AOT 无反射；只能在 dev 形态做，会造成两套行为 |
| 全量历史帧缓存 | 内存不可接受。只留环形窗口，窗口外的帧不再承诺可查 |
| 反射读 State 属性 | 不反射是 AOT 的硬约束。要看的字段由控件显式声明 |
| 某一帧的状态快照 | `State` 里是任意闭包与对象图，存不下也读不回。回放改为"从头重跑到第 N 帧"：布局是纯函数、重建是声明式，重算比快照更准 |
| 跨进程搬记录流 | 传脚本就够：对端从第一步重跑，得到的因果比记录流更全（含中间状态），还不必配背压与断线续传 |
| 实时 attach 一个正在跑的真窗口 | **dev 态已解**（A57）：单线程没有第二线程可读，但 `EventLoop` 每轮本来就要醒来一次，把调试轮询挂在那一轮即可；代价是空闲等待从 `-1` 变成 25ms 上界（只在装桥时）。发布态仍不做：没有可插入的 dev 组合根，暂停真窗口会改用户正在看的事实 |
| 用框架控件写进程内树浏览器 | 循环依赖：拿框架的健康状态去 debug 框架 |

其中两条按**构建态**分开：实时 attach 真窗口、反射读 State 属性，发布态仍不做，dev 形态要做——理由与分期见[证据模型](evidence-model.md)。

## 推进顺序

每期只验证一个假设，前一期不成立就不往下做：

| 期 | 内容 | 要验证的假设 |
|---|---|---|
| D0 | 三挂点 + 稳定 id + 环形缓冲 + `why` | 因果边记得下来，开销可接受 |
| D1 | 查询面（`frames` / `explain` / `hotspots` / `nodes`）+ `DebugSession` | 只用记录能回答"谁在反复重建"，且驱动方式不影响结果 |
| D2 | 回放：可重放脚本（输入 + 帧边界 + 具名效果）+ 摘要判据 | 同一脚本跑两遍，节点表与逐帧因果逐值相同 |
| D3 | 传输：**脚本上行 + 查询下行** + 增量游标 | 跨进程读到的值与同进程逐值相同 |
| D4 | 面板：树 + why + 时间轴，增量 patch + 虚拟化 | 2000 节点首屏可用，折叠与选中不随 patch 丢失 |
| D5 | 像素裁剪 + trace 导出 + CI 基线 | 能红在"帧耗时退化"上，而不是靠肉眼看 |
| D6 | 崩溃自动取证（脚本已存在，只差"死前落盘"） | 进程异常退出后不用重跑就能看现场 |

D3 之前不引入协议层：没有第二个进程时，"域注册表 + 命令回执"只是空壳，而空壳比缺失更贵——它让能力看起来成立。D3 落地时也没有引入域注册表：八个方法（后加的 `pause` / `resume` 仍在同一张表里）、一个下行业务面（`query`），表就没什么可注册的。

D2 排在传输之前，是因为它决定了线上传什么：**传脚本，不传记录流**。一份 6 步的脚本能让对端重算出 600 帧的全部因果，而记录流要把每一帧的边都搬过去，再配上游标、背压、断线续传。Chrome 的 Recorder 与 Redux DevTools 的时间旅行都是这个形状：传小的动作序列，大的状态由对端重新推导。
