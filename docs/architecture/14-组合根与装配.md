# 14 · 组合根与装配

> 回答的问题：**一个应用是怎么从「一行 `Bootstrap::run()`」变成「一棵会刷新的树」的？**
> 以及 `Application` 那 70 多个公共方法分别归谁管、新能力该往哪儿放。
>
> 本册是活文档，引用只给「文件 + 符号」，不写 `file:line`（根 `DESIGN.md` §9）。
> 分册集合与路径真实性由 `tests/Unit/Docs/ArchitectureDocTest.php` 守。

---

## 1. 为什么单列这一册

装配顺序原先散在 `02`（帧内顺序）、`07`（命令 / 作用域）、`10`（平台端口）的碎片里：
每册都讲了自己那一段，但**没有一册回答「谁先造谁、错序会怎样」**。结果是读代码要
从 `Bootstrap` 跳到 `WindowSet`，再跳回 `Application::__construct()` 与 `attach()`，
最后才在 `EventLoop` 里看到主循环 —— 组合根其实是四个文件的接力，不是某一个类。

★ 这册不改任何签名。`Application` 的 public 方法是门面，职责已经拆给
`PumpHost` / `OverlayManager` / `InputRouter` / `FocusManager` / `Frame` /
`TextEditingBridge` / `ScrollInputRouter` 七个部件；**给每个方法补一段分组注释只会
再造一整片新的腐烂面**。所以这里用一张可静态对账的能力索引表代替源码注释：
`tests/Unit/Docs/CompositionRootTest.php` 用 Reflection 保证「每个 public 都被索引、
索引里没有幽灵方法」。

---

## 2. 装配顺序（四个文件的接力）

### 2.1 应用侧组合根：`apps/showcase/bin/win32/Bootstrap.php`

只有这里可以出现具体的平台实现（`Win32Platform`），共享的应用源码零平台引用。
顺序约束都是真机踩出来的：

| 步 | 做什么 | 错序后果 |
|---|---|---|
| ① | `Errors::installFatalBox()` 装中止序列 | 后面任何一步出错都没有错误框 |
| ② | `new WindowSet(...)` 并传**卸载闭包** | 静态钩子捕获整条对象图，AOT 关窗必崩 |
| ③ | `AppScope::make()` 建进程级共享作用域 | 第二个窗口没有可共享的字体 / 任务池 / 主题 |
| ④ | `ThemeData::forAppearance()` 按系统外观取主题 | 运行期切 HC 由 `ThemeChangedEvent` 带快照，`Application` 不再问平台 |
| ⑤ | `AppScope::setTaskHost()`（可含 `prewarm()`） | **必须在 `attach()` 之前**：`PumpHost` 在 attach 时取走并缓存端口 |
| ⑥ | `WindowSet::open()` 每窗一个应用实例 | 多窗共用同一个 `AppScope`、各自的 `Application` 与 `FrameClock` |
| ⑦ | `ResizeHookState::$pump` 按句柄分发 | 副窗拖动会去重排主窗（不报错，只画错窗） |
| ⑧ | `WindowSet::run()` 进主循环 | —— |

### 2.2 窗口级装配：`src/App/WindowSet.php`

`open()` 的顺序：**先造应用 → 再建窗 → 还原几何 → 取表面 → 按实际客户区 resize →
`attach()`**。

★ 标题必须在 `createWindow()` 那一刻就定下（建完再改会先闪默认标题），所以应用要
先造好；而应用不依赖窗口句柄，提前造无副作用。
★ `surface->resize()` 用的是**还原之后读回的**实际客户区，不是 `open()` 传的宽高常量：
照常量排会出现「窗口还原了、画面还按旧尺寸排」的静默拉伸。

### 2.3 应用内部装配：`Application::__construct()` 与 `attach()`

构造器只建**不依赖子类字段**的部件，顺序本身是依赖图：

```
Pipeline → AppScope → CommandRouter(以 scope 的全局表为父)
  → TapTracker / TextEditingBridge / ScrollInputRouter / OverlayManager
  → InputRouter(收前面三片) → OverlayLayout → PumpHost
```

★ `commands()` **不在构造器里调**：PHP 构造链父先子后，那时子类字段还是 `null`；
注册推迟到 `attach()`，且用 `has()` 做可重入保护（重复注册会 Fatal）。

`attach()` 才是真正把树立起来：`Pipeline::enter()` → `setFocusHost()` →
`AppScope::enter(theme())` → `PumpHost::attach()`（取端口）→ 造 `BuildContext` →
注册命令 → `buildRoot()->createElement()` → `mount()` → `new Frame()` → **跑首帧**
→ 建 `FocusManager` 并 `collect()`。

★ 首帧必须走 `frame()` 而不是 `Frame::run()`：后者绕过 `tickAnimations()`，纯动画
应用挂载后没有欠账 ⇒ 帧时钟不上膛 ⇒ 转圈图一辈子不动。
★ `FocusManager` 必须在挂载**之后**建（此刻才有树可走）；宿主提前记在 `Pipeline`
上，所以首帧挂载期间的请求不会丢。

### 2.4 框架侧主循环：`src/App/EventLoop.php`

组合根只剩一句 `EventLoop::run($platform, [$handle => $app])`。循环是
**等 → 派发 → 跑帧**，`Platform::waitEvents()` 负责阻塞等待；每窗一个 `FrameClock`，
`nextWaitMs()` 取最小（`-1` 是不投票的哨兵，不参与取最小）。关闭请求不进命中链，
是窗口级生命周期。`wantsFrame()` 只读 `Pipeline` 的 `frameRequests > frameServed`
一个计数器，变更现场自己 `scheduleFrame()`（`02` §1/§6）。

★ 注入点只认接口：`EventLoop::run()` 与 `WindowSet` 的构造参数类型都是 `Platform`。
`tests/Unit/Platform/PlatformContractTest.php` 用一个最小 `HeadlessPlatform`
（用途对齐 Qt 的 `qminimal` 插件）证明接口可替换、组合根没有硬编码 Win32。
它**不取代** `WindowSetTest` 的「桥可假，策略不可假」：`tools/fakes/win32.php`
替换的是 C 扩展函数层，仍让真的 `Win32Platform` 策略跑。

## 3. 分层与依赖面

`tools/Lint/Rules/DependencyDirection.php` 的 `ALLOWED` 是唯一的分层表，
**key 就是层集合**；未登记的命名空间段默认报红。

★ 2026-11-15 按真实流量收紧：治理前 79 条非自身授权里 37 条零流量（46.8%）。
现在每行只列当前确实有引用的目标层，`DependencyMatrixTest` 守「零流量边不得回潮」
「双向边只有登记过的三对」「文件例外不是死条目」。新增依赖被拦下时，显式加回一行并
写明理由 —— 这是 burn-down，不是撤销设计裁决。

三对**有意**的双向边：`Widget ↔ Layout`、`Widget ↔ State` 是同一棵树的两个视角；
`Theme ↔ Widget` 是「主题控件住 `Theme`、`BuildContext` 住 `Widget`」，反向只走
`src/Widget/BuildContext.php` 一条文件例外。不照搬 Flutter `InheritedWidget` /
`BuildOwner`：那要改公开签名并引入 AOT 生成物风险，收益只是「看起来没有环」。

★ 规则盲区（显式登记，别误读成「没人用」）：`src/Errors.php` 是顶层
`namespace Drift;` 设施，引用 `Drift\Logging` 但整份文件不参与分层检查 ⇒
`Logging` 的层内入边实测为 0 是「看不见」。`Routing` 只被 `apps/` 消费，
`App` 是组合根，两者零入边同理。

## 4. 公共面能力索引

`src/App/Application.php` 的公共面由下表定义，**数量不写死**（手写数字会腐烂，
以 `tests/Unit/Docs/CompositionRootTest.php` 的 Reflection 为准）。下表按「找东西时
你会先想到哪一类」分组，不是按实现文件分（多数只是委托壳）。新增 public 方法必须
补进这张表 —— 判据拿 Reflection 对账，漏一个就红。

| 能力域 | 方法 | 实际落点 / 说明 |
|---|---|---|
| 应用契约与装配 | `__construct()`、`attach()`、`buildRoot()`、`title()`、`theme()`、`scope()`、`root()`、`rootBox()`、`closeRequested()` | 子类只写 `buildRoot()`；`attach()` 顺序见 §2.3 |
| 帧与主循环 | `frame()`、`frameCount()`、`wantsFrame()`、`needsFrameImmediately()`、`nextDeadlineMs()`、`repaintForResize()`、`pipeline()`、`lastTimestampMs()`、`lastInputMs()` | 段顺序真相源是 `src/Rendering/FrameStage.php` |
| 命令 | `commands()`、`commandGates()`、`register()`、`router()`、`dispatch()` | `CommandRouter` 以 `AppScope` 的全局表为父，就近优先；门控与 handler 同一写者、在 `dispatch()` 一处判定 |
| 输入与焦点 | `dispatchInput()`、`accelerators()`、`captureNode()`、`capturePointer()`、`releasePointer()`、`focus()`、`requestFocus()` | `InputRouter` / `FocusManager` |
| 浮层 · 菜单 · 模态 · 快捷消息 | `overlays()`、`dismissOverlay()`、`showMenu()`、`closeMenu()`、`isMenuOpen()`、`showModal()`、`closeModal()`、`isModalOpen()`、`modal()`、`showSnackbar()`、`dismissSnackbar()`、`hasSnackbar()`、`snackbarEntry()`、`snackbarQueueLength()`、`toggleWidgetPanel()` | `OverlayManager` / `OverlayLayout` |
| 拖放 | `beginDrag()`、`updateDrag()`、`cancelDrag()`、`dropDrag()`、`drag()` | `InputRouter` 的手势段 |
| 异步 · 定时器 · IO | `after()`、`cancelAfter()`、`submit()`、`tasks()`、`taskHost()`、`io()` | `PumpHost` / `TaskHost` / `IoPoller` |
| 语义与 IME | `setSemanticsSink()`、`semanticsMode()`、`setSemanticsExpanded()`、`setSemanticsValue()`、`invokeSemanticsNode()`、`imeCaretRect()` | 无 sink ⇒ 不建语义树、零开销 |
| 量具 · 线程守卫 · 端口 | `frameCostMs()`、`worstFrameMs()`、`overBudget()`、`noteFrameCost()`、`zeroViewportFrames()`、`activeAnimationCount()`、`animationVisits()`、`metrics()`、`assertUiThread()`、`uiThreadId()`、`clipboard()` | 诊断 / devtools / 探针，业务代码不该读 |

★ `STAGE_BUDGET_MS` 是**降级用的耗时分组**，不是帧阶段；阶段顺序看
`FrameStage::ORDERED`（九段有序 + 四段只计时），见 `02` §2。

## 5. 扩展点在哪（新能力不要往门面塞）

| 要加的东西 | 落点 | 为什么 |
|---|---|---|
| 进程级共享能力（字体 / 任务池 / IO / 主题 / 全局命令） | `src/App/AppScope.php` | 多窗口共用一份，组合根显式建 |
| 后台执行后端 | `AppScope::setTaskHost()` | 池容量是组合根的决定，不是页面能提的要求 |
| 帧内新泵 / 新段 | `src/App/PumpHost.php` + `FrameStage::ORDERED` | 段名必须进唯一名字表，`FrameStageTest` 守完备性 |
| 输入路由 / 焦点链 / 浮层 | 对应部件类 | `Application` 只留委托壳 |
| 应用自己的命令 | 覆写 `commands()`，或 `register()` | 在 `attach()` 注册，父表是全局命令 |
| 主题外观 | `ThemeData` / `ThemeExtension` + 组合根取系统外观 | `Application` 不持平台（`09`） |
| 要让某个能力对「每一棵渲染树」生效（主题 / 窗口档 / 焦点链 / 动画） | 问 `Application::treeRoots()` | 浮层是第二棵树：各处自己 `foreach` 就是下一次"漏了浮层"的入口（`SecondTreeTest` 守着唯一出口） |
| 存业务状态（表单 / 导航栈 / 滚动 / 选中） | 问 `AppScope::restoration()`，配 `RestorableValue` / `NavigationStack` | 一个 bucket 是唯一真相源；窗口几何仍归 `WindowStateStore`，两者不共用文件（`RestorationTest` 守跨进程冷启动） |
| 新增分层依赖 | 先被 lint 拦 ⇒ 显式加一行 + 写理由 | 见 §3 |

```bash
# 分层表形状对账 + 越界检查

# 帧段表完备性
php vendor/bin/phpunit -c phpunit.xml --filter FrameStageTest

# 活文档引用纪律
php vendor/bin/phpunit -c phpunit.xml --filter ArchitectureDocTest

# 平台接口契约与第二实现自证
php vendor/bin/phpunit -c phpunit.xml --filter PlatformContractTest
```

装配顺序本身没有单元判据可断言（要真窗口），出口证据是真机构建 + 黑盒探针：
`php bin/drift build showcase --full` 与 `python tools/probe-window.py showcase`。
