> 日期：2026-11-16 · 状态：**裁决完成，进入实现**
> 输入：用户诉求「业务只给本地地址或网络地址，控件自动处理异步网络加载与本地加载」；

> 本文先把四个裁决点逐条展开（含一条**推翻上一版推荐**的裁决），再给实现契约与验证口径。

---

## 0. 一句话结论

> **保持 `Image::make()->asset($src)` 唯一入口，`$src` 既收本地路径也收 `http(s)` URL；**
> **框架内部把 Image 改成有态（自驱下载 + 双层缓存 + 三态），业务写法一个字不改。**

撤回上一轮画的 `AsyncImage` + `src()` 新入口：新入口会逼业务自己判断本地/网络，
等于把「开发者不选执行体」的负担转给用户。`asset()` 已是唯一字符串入口，扩展它的语义即可。

## 1. 四个裁决点（多维展开）

### A · 入口形态 → **`asset()` 唯一**（采纳推荐）

| 维度 | 分析 |
|---|---|
| 结构 | `Image` 已是唯一图片叶子；两个源里 `image(ImageHandle)` 收内存句柄、不是字符串。`src()` 会造出**第二个字符串入口**，未来 `data:` / 新 scheme 要改两处 |
| 实现 | 来源判定只需在 `asset()` / `createRenderObjectFromState()` 一处落地；新入口方案要维护两套参数校验与两套 State 分支 |
| 扩展性 | 新 scheme 在 `ImageLoader::classify()` 加一支即可，控件与业务零改动 |
| DX | 业务零改动——现有 `asset('demo/logo.png')` 与新增 `asset('https://…')` 同形；`src()` 方案要改所有调用点或长期维护两个入口 |
| 维护性 | 判据只需钉「一个入口 + 三分类」；双入口要钉「两个入口行为等价」，后者天然会分叉 |
| 成熟框架 | Flutter 用多个命名构造（`Image.network/file/asset`）但统一到 `ImageProvider`；SwiftUI 只有 `AsyncImage(url:)`。本仓没有 Provider 抽象，选**单入口**比造第二个构造函数更接近 SwiftUI 的「不给选择」 |

**裁决：A①**，`asset()` 唯一入口，`image()` 保留为内存句柄通道（不参与来源判定）。

### B · 网络图不给 width → **安全上限 2048 + 诊断**（推翻原推荐）

原推荐是「拒绝 + 诊断」。重新核对后否决：

- 用户诉求是「业务只需要给地址」。把 `width()` 变成网络图的必填项，等于新增一条业务约束——
  这正是蓝图否决 `src()` 时用的同一把尺子（不给业务选择负担）。
- 本仓确实有 OOM 前科（1792×2390 解出 17MB，`Image` 类注释有记录），所以**不能完全放开**。
- Flutter 的 `cacheWidth` 也是可选的，靠全局 `imageCache` 字节上限兜底；本仓没有全局字节预算
  ⇒ 用**保守默认上限**替代「拒绝」，既保住 DX 又不赌内存。

**裁决：B③（新选项）**：

| 情况 | 解码宽度 |
|---|---|
| 给了 `width` | `ceil(width × 2)`（现有 `SUPERSAMPLE`，覆盖 200% DPI） |
| 没给 `width` | `2048`，并记一条 DIAGNOSTIC 建议给 width |

上限是常量、进 cacheKey；不给 width 的网络图两张不同 URL 不会共用缓存条目。

### C · 服务注入 → **AppScope 自动装配 + Rendering 层端口**（推翻原 ThemeExtension 推荐）

上一版推荐 `ThemeExtension`。核对实现后发现一个会让方案失效的坑：

- `ThemeScope::childContext()` 调 `BuildContext::withTheme($this->data)`，**整体替换** `ThemeData`；
- watermark 的 Root 恰好是 `ThemeScope::make(ThemeData::light(), …)`；
- ⇒ 挂在 `AppScope::theme()` 上的 extension 会在第一层 ThemeScope 被冲掉，控件取不到服务。
  要么改 `ThemeScope` 去继承父 extension（跨层语义变更，影响所有主题覆盖点），
  要么每个应用改 Root 接线（又是税）。

更优路径：**复用本仓已有的静态端口形态**。

| 维度 | 分析 |
|---|---|
| 结构 | `ImageLoader` 本来就是「定位 + 解码 + 缓存」中心，且已有静态 `setBaseDir()` / `$cache`。网络获取与磁盘缓存落它这里是**归属正确**，不是新概念 |
| 实现 | `AppScope::setTaskHost()` 是三个应用唯一的后台装配点；在其中把 host 交给 `ImageAssets` ⇒ **业务零改动**，不碰 ThemeData / ThemeScope / BuildContext |
| 扩展性 | 以后换执行体只改 `ImageAssets` 一处；换缓存目录是 `ImageAssets::install()` 的一个参数 |
| DX | 业务只写 `asset($url)`；组合根原有的 `setTaskHost()` 一行不变 |
| 维护性 | 不引入新注入机制；端口静态装配与 `setBaseDir()` 同形，测试用 `install()` / `reset()` 复位 |
| 成熟框架 | Flutter/Coil 的缓存都是**层内单例**而非 Provider 注入——蓝图坑 9 说的是「别做全局可变单例」，但 `ImageLoader` 的静态形态在本仓是既有事实（设计对账第 9 条已决定不照搬），挂端口比新造 ThemeExtension 更少活动件 |

**实现中发现并绕开的一个坑**：最初把端口实现 `ImageAssets` 直接让 `ImageState` 引用，
lint 立刻报红——§4.3 禁止 `Widget → App`，且会在依赖矩阵里新增 `App|Widget` 双向边
（`DependencyMatrixTest` 要求每条双向边先裁决）。最终形态是**端口接口 `ImageSource` 住
`Rendering` 层**（Widget 可依赖），实现 `ImageAssets` 住 `App` 层，组合根 `install()` 时推入
`Image::setSource()`。`Future` 全程留在 App 侧（`fetch()` 收回调、返回类型写 `mixed`），
所以 `Widget → Async` 也仍然禁止。**架构例外一条没加。**

**裁决：C③**。多窗口不串：`AppScope` 每进程一个（多窗口共享），`TaskHost` 也是每进程一个。
保留判死退路：AOT 下端口取不到 ⇒ 网络图降级占位 + 诊断（不崩），本地图完全不受影响。

### D · 水印迁移 → **本轮一起迁**（确认）

只有真实迁移才能验证「业务只给地址」是否成立，也才能量出删掉了多少模板。
产品行为变化（整批百分比 → 每张自治）已在上轮接受。

**裁决：D①**，本轮迁移；`DownloadResultsJob` 与 `DownloadReport` 退出主链路。

## 3. 实现契约

### 3.1 来源三分类（`ImageLoader::classify()`）

| `$src` | 判定 | 行为 |
|---|---|---|
| 相对路径 / `/x` / `C:\x` / `\\server\x` | LOCAL | 沿用 `resolve()` + `load()`，同步解码 |
| `http://` / `https://` | NETWORK | 磁盘缓存命中 ⇒ 同步解码；未命中 ⇒ 提交 `FetchImageJob` |
| `file://` / `data:` / 其它 scheme | REJECT | DIAGNOSTIC + 1×1 占位，**不静默当本地** |

### 3.2 双层缓存

- **磁盘**：URL → 本地文件，`md5(url)` 命名（复用现有策略）；同一 URL 覆盖而非堆积。
- **内存**：`ImageLoader::$cache[resolved@maxWidth]`，命中快路径**同步返回 handle，不提交 Job**。
- 去重键 = `src + targetWidth`。

### 3.3 三态画法

- READY（含两层命中）：`RenderImage(handle, …)`，**不产生 loading 帧**。
- LOADING / IDLE：1×1 透明占位，尺寸由 `width/height` 撑住。
- ERROR：1×1 占位 + `Errors::report(..., DIAGNOSTIC)`，不抛、不弹框。

### 3.4 装配链（C 的落点）

`Bootstrap → AppScope::setTaskHost($host) → ImageAssets::install() → Image::setSource(ImageSource)`
`→ ImageState 取端口 → ImageAssets::fetch()（内部 TaskHost::submit + Future）→ FetchImageJob`

- 核心任务由 `CoreJobs::register()` 在 `ProcessTaskHost` 与 `ProcessWorker` 两侧各自合并
  ⇒ 应用 registry 不用改一行，漏登记也不会静默失败。
- `FetchImageJob` 只依赖构造器参数（`cacheDir` 进 `FIELDS`），不读任何静态服务
  ⇒ worker 进程无需装配。

### 3.5 水印迁移

`ResultCard` 结果图改 `Image::make()->asset($url)->width(PREVIEW_WIDTH)`；
Store 的 `downloads` / `downloadResults()` 与批量 Job 退出主链路。
