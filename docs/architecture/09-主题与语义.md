# 09 · 主题与语义

> 对应 design-v7 [22-国际化与主题](../design-v7/22-国际化与主题.md) 的"主题"部分与无障碍。本文描述**实现**。

## 1. 一句话

颜色 / 字号 / 间距**用 token 不写死**：`ColorToken` / `MetricToken` / `TextRole` 是枚举，控件在
`createRenderObject(ctx)` 里经 `BuildContext` 取主题色，Render 层只收值（"变体 → token → 值只合并一次"，
`src/Widget/ToggleBase.php:183` 注释）。主题切换打 `RenderBoxWidget` 的脏位、整棵重建。无障碍走
`SemanticsBuilder` 建扁平语义快照数组，每帧末推给 UIA（**同时吃推与拉**模型）。

## 2. 主题

- `ThemeData`（`src/Theme/ThemeData.php:22`）：调色板 + 排版 + 间距的令牌值集合。
- `ThemeScope`（`src/Theme/ThemeScope.php:31`）+ `ThemeScopeElement`（`:16`）：覆盖主题的节点，
  覆写 `Widget::childContext()`（`src/Widget/Widget.php:101`）把新 `BuildContext` 递给子树。
- ★ **换主题的唯一入口**：`Element::applyContext()`（`src/Widget/Element.php:239`）——无状态/容器节点
  **立即重建**（它的渲染盒在 `createRenderObject(ctx)` 里算，不重算等于换表不换色）；有状态节点只标脏、
  等帧末 flush（"推迟"不是"丢"）。

## 3. token 纪律（为什么不能写死颜色）

- `BuildContext` 是唯一被允许碰主题的入口（`Widget` 层只在此取色/字号/间距）。
- `ToggleBase::createRenderObject()`（`src/Widget/ToggleBase.php:187`）示范：经 `context->color(ColorToken::Accent)`
  等取色 ⇒ Render 层 `RenderToggle` 只收 `ToggleStyle` 值对象。
- `TextRole`（字号角色）、`MetricToken`（间距）同形。

## 4. 语义（无障碍 / UIA）

- 控件声明：`Widget::semantics(Role, name, value, enabled)`（`src/Widget/Widget.php:378`）—— **字段赋值**
  不是虚方法覆写（去虚化会静默吞掉，见 [11](11-编译器约束与-AOT-坑.md)）。
- 收集：`SemanticsBuilder`（`src/Widget/SemanticsBuilder.php:32`）遍历树，把声明了角色的节点收进
  `SemanticsTree`（`src/Input/SemanticsTree.php:21`）/ `SemanticsNode`（`:22`）。
- 推送：`Application::pumpSemantics()`（`src/App/Application.php`，frame 末段）把扁平语义快照推给 UIA
  sink；**无 sink ⇒ 不建，零开销**。
- `SemanticsRole`（`src/Input/SemanticsRole.php`）：语义角色枚举（注意里面的 `case Switch = 'switch'`
  是 src/ 里**唯一**含 "switch" 记号的地方——不是控制流）。

### 4.1 真机验证：链路两端都走过一次（2026-10-25）

判据不是"窗口能开"，是**从真实 UIA 客户端读回节点**。探针 `_build/uia-probe.php`
（`php _build/uia-probe.php users.exe`）：起 exe → Win32 `EnumWindows` 按 pid 枚举顶层窗
→ `AutomationElement.FromHandle()` → 打印 `ControlType` / `Name` / `BoundingRectangle`。

`users.exe` 实测读回 9 个节点，`ControlType` 与 `SemanticsRole` 一一对上
（`button`→Button / `textfield`→Edit / `scroll`→List / `dialog`→Window）：

```
Button 列表 92,6 60x32    Button 注册 …    Edit 搜索 24,106 80x43
Button 刷新 …             Button 新建用户 …  List （列表） 0,173 983x303
```

★★ **探针必须按 HWND 枚举，不能用 `RootElement.FindFirst(Children, pid)`**：一个进程常有
多个顶层窗（输入法 / IME / 隐藏消息窗），`FindFirst` 抓到的是输入法窗，读回
`ControlType.Pane` + 空 name + `COUNT=0`，看着像"provider 没接上"，实际是量错了对象。

★ **几何必须取 `effectiveBox()`**（`src/Widget/SemanticsBuilder.php:87`），不是
`renderObject()`：语义只声明在控件上，而组合型控件的盒在**子元素**上
（`Button extends BoxWidget` 自己产盒；`TextField` / `ScrollView extends StatefulWidget`
的 `build()` 返回 `TextFieldBox` / `ScrollViewBox`）⇒ 读自己的盒恒为 null ⇒ 几何恒 0
⇒ UIA 侧 `BoundingRectangle` 退化成 `Rect.Empty`（读屏无法高亮，且**不报错**）。

### 4.2 "可操作"半边：已落地（2026-10-25）

`simplePattern()`（`cpp-src/drift_win32.cc`）现在给 `ControlType == Button` 的节点交出
`IInvokeProvider`（tear-off `InvokeAdapter`），其余仍返 `nullptr`。真机闭环
（`php _build/uia-probe.php users.exe`）：Invoke 前读回 **10** 个节点（用户目录：搜索框 /
刷新 / 重试 / 新建用户…），`Invoke()` 之后重读是 **9** 个节点（注册页：姓名 / 邮箱 /
提交 / 清空）—— 页面换了、语义树自动重推了、进程没崩。

★★ **`Invoke()` 里不能跑 PHP**：那是一次跨进程 COM 回调（栈上压着 UIA 的编组状态），
实测重入 PHP 会让进程**静默消失**（无异常、无日志，客户端只看到
`ElementNotAvailable`）。⇒ 只 `PostMessageW(kMsgUiaInvoke)`，立刻返回。

★★ **转投到窗口线程之后仍然不能"在消息派发里跑 PHP"**：消息泵的契约是
"一次调用交一条事件"（`php_drift_win_pump()` 在 `g_queue` 空时阻塞在 `GetMessageW`），
在 `DispatchMessage` 里跑完 PHP 就**没人保证下一帧会跑**。真机现象极具迷惑性：
命令执行了、状态也变了（`PageHost` 都收到 `next=signup` 并 `setState` 了）、
**画面一动不动**，要等下一条用户输入才刷出来。第一次的写法正是这个，卡了两轮。

★ 正解是**把它变成一条输入事件**：`kMsgUiaInvoke` 只往 `g_queue` 塞
`kEvUiaInvoke`（纯 C++，壳里零 PHP 调用）→ `pump()` 交出去 →
`Win32Platform::pump()` 翻成 `SemanticsInvokeEvent`（`src/Input/`）→ 组合根抽完事件
立刻 `FrameClock::tick()` 跑帧。与 `ThemeChangedEvent` / `WindowDeactivatedEvent`
同一个形状，区别只是**带载荷**（节点索引）。

★ 激活语义**不复制**：`Application::dispatchInput()` 收到事件只做一件事 —— 在节点
中心派发一次合成 tap，把"点哪个控件"交回既有的输入路由（`Activatable::activate()`）。
于是"读屏点"与"鼠标点"是同一条路。合成手势必须 **move → down → up 三件**：
"凭空 down"在真机上不激活（`CursorShape` 退默认）。

★ 副产品：`src/Platform/Win32/UiaInvoke.php` + `UiaInvokeState.php`（AOT 全局函数 +
静态槽）整条链删掉，顺带消掉"形参必须是 `php::Int`"与"增量构建不认新增 `.php`"
两个 AOT 坑。

### 4.3 已知缺口：多一层"根作为自己的子节点"

`FromHandle(hwnd)` 之后 `Children` 只有 1 个且就是根自己，
`Descendants` 比真实节点多 1。**不是 `Navigate` 的问题**——`fragNavigate()`
（`cpp-src/drift_win32.cc:384`）的树经 stderr 打点确认为正确（`-1→0→1→…→8`，
`FirstChild` 只被问一次且返回 0）。是 provider **没有和窗口元素合并**的结构性表现：
UIA 为 HWND 造了一层，我们的根又占一层。

四种组合实测（都改过、都不成立，`cpp-src` 已恢复）：

| `get_HostRawElementProvider`（`drift_win32.cc:378`） | `GetRuntimeId`（`:423`） | 结果 |
|---|---|---|
| nullptr（现状） | `{id}` VT_I4 | **9 节点可读**，多一层容器 |
| 每个 fragment 都给宿主 | `{id}` | 全塌成一个（rid 都变 `[42,hwnd]`） |
| 只给根宿主 | `{UiaAppendRuntimeId,id}` | 客户端扫完兄弟后抛 `ArgumentException` |
| nullptr | `{UiaAppendRuntimeId,id}` | provider 被整个忽略（name 退回窗口标题） |

另试：根 `IsControlElement=FALSE` ⇒ 多出的那层消失，但**第一个子节点从枚举里丢了**；
根 `RuntimeId` 返 `NULL` ⇒ 无变化。⇒ 现状（多一层容器）是当前最优，且它只是**外观**问题
（9 个控件都可达、可操作），不影响 4.2。

**下一个 Pattern**：`ValuePattern`（textfield）/ `TogglePattern` / `RangeValuePattern`。
结构上已经有位置 —— 每个都是"新 `kEv*` 入队 + 新 `Semantics*Event`"，与 4.2 同形，
不需要再动泵。按 A15 只在有消费者时补。
