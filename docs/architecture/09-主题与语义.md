# 09 · 主题与语义

## 1. 一句话

颜色 / 字号 / 间距**用 token 不写死**：`ColorToken` / `MetricToken` / `TextRole` 是枚举，控件在
`createRenderObject(ctx)` 里经 `BuildContext` 取主题色，Render 层只收值（"变体 → token → 值只合并一次"，
`src/Widget/ToggleBase.php` 注释）。主题切换打 `RenderBoxWidget` 的脏位、整棵重建。无障碍走
`SemanticsBuilder` 建扁平语义快照数组，每帧末推给 UIA（**同时吃推与拉**模型）。

## 2. 主题

- `ThemeData`（`src/Theme/ThemeData.php`）：调色板 + 排版 + 间距的令牌值集合。
- `ThemeScope`（`src/Theme/ThemeScope.php`）+ `ThemeScopeElement`：覆盖主题的节点，
  覆写 `Widget::childContext()`（`src/Widget/Widget.php`）把新 `BuildContext` 递给子树。
- ★ **换主题的唯一入口**：`Element::applyContext()`（`src/Widget/Element.php`）——无状态/容器节点
  **立即重建**（它的渲染盒在 `createRenderObject(ctx)` 里算，不重算等于换表不换色）；有状态节点只标脏、
  等帧末 flush（"推迟"不是"丢"）。

### 2.1 能力清单（应用侧能做什么）

| 能力 | 入口 | 粒度 |
|---|---|---|
| 选一份基础主题 | `ThemeData::light()` / `dark()` / `forSystem(SystemTheme)` | 全应用 |
| 点覆盖：改一个颜色 | `ThemeData::withColor(ColorToken, Color)` | 一个 token |
| 点覆盖：改一个度量 | `ThemeData::withMetric(MetricToken, float)` | 一个 token |
| 面覆盖：整棵子树换表 | `ThemeScope::make(ThemeData, Widget)` | 子树 |
| 换成框架自带高对比配色 | `ThemeData::withHighContrast()` | 全表 |
| 挂应用侧自定义 token | `ThemeData::withExtension(ThemeExtension)` / `BuildContext::extension(Foo::class)` | 一份主题 |
| 跟随系统明暗 + 高对比度 | `ThemeChangedEvent` → `Application`（事件自带 `SystemAppearance` 快照） | 全应用 |
| 多窗口共享主题 | `AppScope::setTheme()` / `theme()` | 进程 |

- **点覆盖是后写覆盖**：`withColor()` / `withMetric()` 返回新实例、原主题不变；同一
  token 再调一次以本次为准（改 `+` 合并的旧实现会让第二次静默无效，见判据）。
- **面覆盖嵌套时最内层赢**，没有特异性权重：`ThemeScope` 覆写 `childContext()`，
  外层把 `ThemeData` 写进 ctx，内层再覆盖一次。
- **换肤不改调用点**：控件只说角色，`BuildContext::color()` / `metric()` / `textSize()`
  取表里的值；`RenderObject` 只收解析后的值。
- **扩展缝不是字符串注册表**：`ThemeExtension::key()` 由实现写 `return self::class;`，
  取也用 `Foo::class`（编译期常量，拼错不会静默拿到 null）。`ThemeData` 仍是
  `final` + 私有构造器，封闭 token 枚举不变。应用侧建议包一个 `Foo::of($ctx)` 把
  `?ThemeExtension` 的转型收在一处 —— `apps/showcase` 的 `ShowcaseBrand` 是样板。

token 表是**封闭枚举**（拼错是编译错，不用字符串键）：

- `ColorToken`：**10 个** —— `Pane` / `Surface` / `Chrome` / `Text` / `Muted` / `Border` /
  `Accent` / `Danger` / `Hover` / `Pressed`。各有 `lightValue()` / `darkValue()`，部分有
  `highContrastValue()`。
- `MetricToken`：**10 个** —— `Padding` / `Gap` / `Radius` / `BorderWidth` / `FontSize` /
  `FontSizeSmall` / `FontSizeTitle` / `FontSizeHeading` / `RowHeight` / `HeaderHeight`。
  各有一个 `baselineValue()`，与明暗无关（只有一张表）。
- `TextRole`：`ThemeData::textSize()` / `textColor()` 把角色映射到上面两张表。

### 2.2 系统外观跟随（HC 已接线）

`SystemAppearance`（`src/Theme/SystemAppearance.php`）是**明暗 + HC + 系统色**的一次快照。
HC 是独立轴，不塞进 `SystemTheme::Light/Dark` —— 暗色 + HC 是合法组合，对齐 WinUI
`ThemeDictionaries` 的 Light / Dark / HighContrast 三键与 CSS `forced-colors`。

链路四步，全部已落地：

1. `cpp-src/win32/drift_win32.cc`：`WM_SETTINGCHANGE`（`ImmersiveColorSet`）与
   `WM_SYSCOLORCHANGE` 都推 `kEvTheme`；`drift_win_high_contrast()` 读
   `SPI_GETHIGHCONTRAST`，`drift_win_system_color($slot)` 读 `GetSysColor()`。
2. `Screen::appearance()`（`src/Platform/Screen.php`）由 `Win32Screen` 每次现读，不缓存。
3. `Win32Platform::translate()` 把快照塞进 `ThemeChangedEvent`；`Application::dispatchInput()`
   用 `ThemeData::forAppearance()` 换主题、`applyNewContext()` 全树下发。启动时由组合根
   `AppScope::setTheme()` 灌初值（§5.1 纪律 1：`Application` 不持平台）。
4. `ThemeData::forAppearance()` 的 HC 分支用**用户选的系统色**覆盖
   `Pane` / `Surface` / `Text` / `Muted` / `Border` / `Chrome` / `Accent`；
   `withHighContrast()` 的硬编码配色只在系统色拿不到时兜底（Win32 官方口径：HC 下
   不要硬编码颜色，用 `GetSysColor()` 的用户选择色）。

- `ThemeChangedEvent` 的 `appearance` 可为 `null`（旧形态）：框架只调
  `onSystemThemeChanged()` 钩子，由应用自己换主题。
- **真机 HC 信号不在自动链里**：切换要人工按 `Left Alt + Left Shift + PrtScn`。
  自动判据覆盖「外观快照 → 主题映射」这条确定性函数
  （`tests/Unit/Theme/SystemAppearanceTest.php` · `tests/Feature/Theme/ThemeSwitchTest.php`
  · `tools/smoke.php` · 变异自检），
  真机侧靠全量 AOT 编译与 `tools/probe-window.py` 首帧黑盒。
- 系统色槽位见 `src/Platform/SystemColor.php`；C++ 侧把槽号映射到 `GetSysColor()`
  索引，换平台不动 PHP 侧数字。

### 2.3 仍有的边界

- 应用侧**不能新增 `ColorToken` / `MetricToken` 枚举成员**（封闭枚举是刻意的）；
  要自定义语义值走 §2.1 的扩展缝。
- 扩展缝的键是类名 ⇒ 同一份主题里同类扩展只能挂一个（后写覆盖）。
- `Hover` / `Pressed` 没有高对比形态，HC 下保留原值；`Danger` 没有对应的系统色，
  沿用框架 HC 配色。
- **系统跟随写 `AppScope`，不写应用的 `theme()` 覆写**：`applyNewContext()` 读
  `$this->theme()`，默认实现转发到 `AppScope::theme()`。应用仍可覆写 `theme()`
  自带主题源（`AppScopeTest` 守着这条契约），但覆写者收不到框架的外观快照，
  且 `onSystemThemeChanged()` 当前无参 ⇒ **这类应用暂不自动跟随系统外观**。
  `apps/showcase` 不覆写，走默认路径；判据用不覆写的夹具覆盖这条链路。

## 3. token 纪律（为什么不能写死颜色）

- `BuildContext` 是唯一被允许碰主题的入口（`Widget` 层只在此取色/字号/间距）。
- `ToggleBase::createRenderObject()`（`src/Widget/ToggleBase.php`）示范：经 `context->color(ColorToken::Accent)`
  等取色 ⇒ Render 层 `RenderToggle` 只收 `ToggleStyle` 值对象。
- `TextRole`（字号角色）、`MetricToken`（间距）同形。

## 4. 语义（无障碍 / UIA）

- 控件声明：`Widget::semantics(Role, name, value, enabled)`（`src/Widget/Widget.php`）—— **字段赋值**
  不是虚方法覆写（去虚化会静默吞掉，见 [11](11-编译器约束与-AOT-坑.md)）。
- 收集：`SemanticsBuilder`（`src/Widget/SemanticsBuilder.php`）遍历树，把声明了角色的节点收进
  `SemanticsTree`（`src/Input/SemanticsTree.php`）/ `SemanticsNode`。
- 推送：`Application::pumpSemantics()`（`src/App/Application.php`，frame 末段）把扁平语义快照推给 UIA
  sink；**无 sink ⇒ 不建，零开销**。
- `SemanticsRole`（`src/Input/SemanticsRole.php`）：语义角色枚举（注意里面的 `case Switch = 'switch'`
  是 src/ 里**唯一**含 "switch" 记号的地方——不是控制流）。

### 4.1 真机验证：链路两端都走过一次（2026-10-25）

判据不是"窗口能开"，是**从真实 UIA 客户端读回节点**。探针 `_build/uia-probe.php`
（`php _build/uia-probe.php users.exe`）：起 exe → Win32 `EnumWindows` 按 pid 枚举顶层窗
→ `AutomationElement.FromHandle()` → 打印 `ControlType` / `Name` / `BoundingRectangle`。

`users.exe` 实测读回 9 个节点，`ControlType` 与 `SemanticsRole` 一一对上
（`button`→Button / `textfield`→Edit / `scroll`→List / `dialog`→Window）：

```
Button 列表 92,6 60x32    Button 注册 …    Edit 搜索 24,106 80x43
Button 刷新 …             Button 新建用户 …  List （列表） 0,173 983x303
```

★★ **探针必须按 HWND 枚举，不能用 `RootElement.FindFirst(Children, pid)`**：一个进程常有
多个顶层窗（输入法 / IME / 隐藏消息窗），`FindFirst` 抓到的是输入法窗，读回
`ControlType.Pane` + 空 name + `COUNT=0`，看着像"provider 没接上"，实际是量错了对象。

★ **几何必须取 `effectiveBox()`**（`src/Widget/SemanticsBuilder.php`），不是
`renderObject()`：语义只声明在控件上，而组合型控件的盒在**子元素**上
（`Button extends RenderBoxWidget` 自己产盒；`TextField` / `ScrollView extends StatefulWidget`
的 `build()` 返回 `TextFieldBox` / `ScrollViewBox`）⇒ 读自己的盒恒为 null ⇒ 几何恒 0
⇒ UIA 侧 `BoundingRectangle` 退化成 `Rect.Empty`（读屏无法高亮，且**不报错**）。

### 4.2 "可操作"半边：已落地（2026-10-25）

`simplePattern()`（`cpp-src/win32/drift_win32.cc`）现在给 `ControlType == Button` 的节点交出
`IInvokeProvider`（tear-off `InvokeAdapter`），其余仍返 `nullptr`。真机闭环
（`php _build/uia-probe.php users.exe`）：Invoke 前读回 **10** 个节点（用户目录：搜索框 /
刷新 / 重试 / 新建用户…），`Invoke()` 之后重读是 **9** 个节点（注册页：姓名 / 邮箱 /
提交 / 清空）—— 页面换了、语义树自动重推了、进程没崩。

★★ **`Invoke()` 里不能跑 PHP**：那是一次跨进程 COM 回调（栈上压着 UIA 的编组状态），
实测重入 PHP 会让进程**静默消失**（无异常、无日志，客户端只看到
`ElementNotAvailable`）。⇒ 只 `PostMessageW(kMsgUiaInvoke)`，立刻返回。

★★ **转投到窗口线程之后仍然不能"在消息派发里跑 PHP"**：消息泵的契约是
"一次调用交一条事件"（`php_drift_win_pump()` 在 `g_queue` 空时阻塞在 `GetMessageW`），
在 `DispatchMessage` 里跑完 PHP 就**没人保证下一帧会跑**。真机现象极具迷惑性：
命令执行了、状态也变了（`PageHost` 都收到 `next=signup` 并 `setState` 了）、
**画面一动不动**，要等下一条用户输入才刷出来。第一次的写法正是这个，卡了两轮。

★ 正解是**把它变成一条输入事件**：`kMsgUiaInvoke` 只往 `g_queue` 塞
`kEvUiaInvoke`（纯 C++，壳里零 PHP 调用）→ `pump()` 交出去 →
`Win32Platform::pump()` 翻成 `SemanticsInvokeEvent`（`src/Input/`）→ 组合根抽完事件
立刻 `FrameClock::advance()` 跑帧。与 `ThemeChangedEvent` / `WindowDeactivatedEvent`
同一个形状，区别只是**带载荷**（节点索引）。

★ 激活语义**不复制**：`Application::dispatchInput()` 收到事件只做一件事 —— 在节点
中心派发一次合成 tap，把"点哪个控件"交回既有的输入路由（`Activatable::activate()`）。
于是"读屏点"与"鼠标点"是同一条路。合成手势必须 **move → down → up 三件**：
"凭空 down"在真机上不激活（`CursorShape` 退默认）。

★ 副产品：`UiaInvoke` / `UiaInvokeState`（AOT 全局函数 + 静态槽）整条链删掉，顺带
消掉"形参必须是 `php::Int`"与"增量构建不认新增 `.php`"两个 AOT 坑。

### 4.3 已知缺口：多一层"根作为自己的子节点"

`FromHandle(hwnd)` 之后 `Children` 只有 1 个且就是根自己，
`Descendants` 比真实节点多 1。**不是 `Navigate` 的问题**——`fragNavigate()`
（`cpp-src/win32/drift_win32.cc`）的树经 stderr 打点确认为正确（`-1→0→1→…→8`，
`FirstChild` 只被问一次且返回 0）。是 provider **没有和窗口元素合并**的结构性表现：
UIA 为 HWND 造了一层，我们的根又占一层。

四种组合实测（都改过、都不成立，`cpp-src` 已恢复）：

| `get_HostRawElementProvider`（`cpp-src/win32/drift_win32.cc`） | `GetRuntimeId` | 结果 |
|---|---|---|
| nullptr（现状） | `{id}` VT_I4 | **9 节点可读**，多一层容器 |
| 每个 fragment 都给宿主 | `{id}` | 全塌成一个（rid 都变 `[42,hwnd]`） |
| 只给根宿主 | `{UiaAppendRuntimeId,id}` | 客户端扫完兄弟后抛 `ArgumentException` |
| nullptr | `{UiaAppendRuntimeId,id}` | provider 被整个忽略（name 退回窗口标题） |

另试：根 `IsControlElement=FALSE` ⇒ 多出的那层消失，但**第一个子节点从枚举里丢了**；
根 `RuntimeId` 返 `NULL` ⇒ 无变化。⇒ 现状（多一层容器）是当前最优，且它只是**外观**问题
（9 个控件都可达、可操作），不影响 4.2。

**下一个 Pattern**：`ValuePattern`（textfield）/ `TogglePattern` / `RangeValuePattern`。
结构上已经有位置 —— 每个都是"新 `kEv*` 入队 + 新 `Semantics*Event`"，与 4.2 同形，
不需要再动泵。按 A15 只在有消费者时补。

### 4.4 值型 Pattern（Value / Toggle / RangeValue）动工前分析（2026-10-25）

**4.3 末段"结构上已经有位置"只对了一半。** 写侧（`SetValue`）不是"新 `kEv*` +
新 `Semantics*Event`"那么简单：它还要一条**节点 → 控件**的寻址 + 一个"值可被语义
写"的能力接口。更要紧的是，C++ 侧有两处**结构债**必须先还，否则 Pattern 给了也
没人问：

| 债 | 证据 | 后果 |
|---|---|---|
| `UiaNode` **没有 `value` 字段** | `cpp-src/win32/drift_win32.cc` 只有 name/controlType/parent/focused/x/y/w/h；`php_drift_win_uia_push`(:1996) 不读 `value`（PHP `toArrays()` 早就有它） | `IValueProvider.get_Value` / `IToggleProvider` / `IRangeValueProvider` 全部无数据源 |
| `uiaControlTypeFor` **只映射 4 角色** | `:218-224` 只有 button/textfield/scroll/dialog；`checkbox`/`radio`/`switch`/`progress`/`slider` 落 `UIA_CustomControlTypeId` | 客户端认不出"这是复选框/滑块" ⇒ 不会问 `TogglePattern`/`RangeValuePattern` |

**三个 Pattern 的契约与数据需求**（`g_uiaNodes` 里每节点一份）：

| Pattern | 角色 | 读 | 写 | 需要的数据 |
|---|---|---|---|---|
| `IValueProvider` | `textfield` | `get_Value` / `get_IsReadOnly` | `SetValue(string)` | `value`（当前文本） |
| `IToggleProvider` | `checkbox`/`radio`/`switch` | `get_ToggleState`（Off/On/Indeterminate） | `Toggle()` | `value`（`checked`/`unchecked`/radio 值） |
| `IRangeValueProvider` | `slider`（`progress` 只读同形） | `get_Value`/`Minimum`/`Maximum`/`SmallChange`/`LargeChange` | `SetValue(double)` | `value`（读数）+ **`rangeMin`/`rangeMax`** |

**三个候选（结构/实现/扩展性）**

- **方案 1 · 三套独立照抄 `InvokeAdapter`**：每个 Pattern 各自 QI/AddRef/Release
  样板 + 各自消息 + 各自 PHP 事件。四份 IUnknown 样板重复，加第 5 个 Pattern 再抄
  一遍 ⇒ **否决**。
- **方案 2 · 统一值模型 + COM 样板收敛（推荐）**：
  - PHP：`SemanticsNode` 加 `rangeMin`/`rangeMax`（float，加性、默认 0）；
    `Widget::semanticsRange(float $min, float $max): static` 与 `semantics()` **正交**
    （只有 Slider/Progress 调，不膨胀 `semantics()` 的 4 参签名）；`Slider` 在既有
    `semantics()` 处链一个 `->semanticsRange($this->min, $this->max)`。
  - C++：`UiaNode` 加 `value`(wstring)+`rangeMin`/`rangeMax`(double)，push 解析
    多读三个键（**缺键兼容**：老调用方不推 ⇒ 空/0）；`uiaControlTypeFor` 补
    `checkbox`/`radio`/`switch`/`progress`/`slider`；`simplePattern` 按
    `controlType` 分派 `ValueAdapter`/`ToggleAdapter`/`RangeAdapter`。
  - C++ 结构改进：抽 `ComTearOff<TInterface>` 模板基类收敛四份重复的
    `QueryInterface`/`AddRef`/`Release`，每个 adapter 只实现自己的 Pattern 方法
    （`InvokeAdapter` 一并改用它 —— 顺手减少 ≈60 行样板）。
  - 写回：Toggle 的 `Toggle()` **复用 `SemanticsInvokeEvent`**（合成 tap → 既有的
    `Activatable::activate()`，Checkbox 的 activate 就是换值，零新概念）；Value/Range
    的 `SetValue` 走新 `SemanticsSetValueEvent(index, value:string)` + 新接口
    `SemanticsValueEditable::setSemanticsValue(string): bool`（与 `Activatable` 同构），
    `TextField`/`Slider` 实现；寻址复用 `invokeSemanticsNode` 的"节点几何 → hitTest
    → 沿 parent 找能力"。
- **方案 3 · 只读不写**：成本减半，但"读屏能读值、不能改值"是半吊子，且 Invoke 已
  证明"能操作"是硬需求 ⇒ **不作为终点**，只作第一阶段。

**裁决**：取方案 2，**分两个提交**（`A15` 意义上的"有消费者"= 读屏客户端能问
Pattern，故一次做完闭环，但拆成可独立验证的两步）：

1. **提交 1（读侧 + 映射 + 样板收敛）**：`SemanticsNode`/`toArrays` 加 range；
   `Widget::semanticsRange()`；`Slider` 推 range；C++ `UiaNode`/push/controlType 补全
   + `ComTearOff<T>` + 三个**只读** Pattern。真机用 `_build/uia-probe.php` 读
   `CurrentValue`/`CurrentToggleState`/`CurrentValue+Minimum+Maximum`。
2. **提交 2（写侧）**：`SemanticsSetValueEvent` + `SemanticsValueEditable` +
   `TextField`/`Slider` 实现 + `Application` 分发；Toggle 的 write 复用激活。
   真机 `SetValue`/`Toggle` ⇒ 状态变 + 画面变。

**兼容性破坏**：加性（字段/方法/数组键都有默认；C++ push 缺键兼容），无既有 API 变化。

#### 4.4-落地 · 提交 1（读侧，2026-10-25）

**PHP**
- `SemanticsNode` 加 `rangeMin`/`rangeMax`（float，默认 0）；`SemanticsTree::toArrays()`
  多两个键（加性）。
- `Widget::semanticsRange(float, float): static` + `semanticsRangeMin()`/`semanticsRangeMax()`
  两个 `@internal` getter（与 `semantics()` 正交，不动 4 参签名）。
- `SemanticsBuilder::descend()` 填区间的两个字段；`Slider::refreshSemantics()` 链
  `->semanticsRange($this->min, $this->max)`。

**C++（`cpp-src/win32/drift_win32.cc`）**
- `UiaNode` 加 `value`(wstring) + `rangeMin`/`rangeMax`(double)；`php_drift_win_uia_push`
  多解析三个键（缺键 ⇒ 空串 / 0，老调用方安全）。
- `uiaControlTypeFor` 补 `checkbox`/`radio`/`switch`(→CheckBox)/`progress`/`slider` 五个

真机现象：`Toggle()` 正常（`On→Off`），而 `RangeValuePattern.SetValue(77)` 读回仍是

根因：`simpleProperty()` 从没应答 `UIA_IsEnabledPropertyId` ⇒ 客户端默认
`IsEnabled=false` ⇒ `.NET` 的 `RangeValuePattern.SetValue` **在客户端侧**就拒绝，
provider 的 `SetValue` 根本没被调（临时 `fprintf(stderr)` 打点全空是决定性证据）。

教训：
- **`Toggle()` 的 .NET 封装不检查 `IsEnabled`，`SetValue()` 检查** ⇒ "只验证一条
  Pattern 能用"会漏掉两者共用的基础属性。**Pattern 全绿 ≠ 属性齐全。**
- 打点要打在**最靠近嫌疑点**的位置（`SetValue` 入口 + WndProc 入口），且**先看
  客户端自己的错误文本**（`ps` 输出里就有，比加 C++ 打点快得多）。
