# 02 · 帧管线与异步

## 1. 一句话

一帧按顺序跑：`pump(IO/任务/分片) → tickAnimation → settle → layout → paint → present`，
所有"后台结果/动画推进"都必须在 `settle` **之前**，让 `setState()` 标脏被同帧的 settle 消费
（否则 "loading→ready" 闪一帧空）。帧时钟**自适应**：`wantsFrame()` 只在"还有动画/任务在途/
分片没跑完/有流在监听"时返回 true，空闲即停摆、CPU 归零。

## 2. `Application::frame()` 的实际顺序（`src/App/Application.php:701`）

```
pumpIo()        // ① 非阻塞 IO 先到；回调里 setState 的脏标记由本次 settle 消费
pumpTasks()     // ② 后台结果取出；必须在 settle 前 ⇒ 同帧生效
pumpSliced()    // ③ 分片任务完成也在此刻回调 ⇒ 同样在 settle 前
tickAnimations(ts)   // ⓸ 推进动画；返回"还有动画在跑吗"喂 wantsFrame；在 settle 前
placeOverlays(cs)   // 浮层布局段（逐层无界自尺寸 + 钉锚点 + 翻转/夹进客户区）
Frame::run(root, cs, ts, overlays)  // 核心管线：settle → layout → paint → present
tickAnimations(ts)   // ⓹ 迟到挂载补 tick：刚挂上的页 State 在 ⓸ 时还不在树里，补一遍
focus->collect()     // 每帧重建焦点链（settle 可能换了子树 ⇒ 旧链握死节点）
pumpSemantics()      // 语义树推给 UIA（无 sink ⇒ 不建，零开销）
```

★ `Frame::run()` 是 `settle → layout → paint → present` 五段（详见 [01](01-三层树与身份.md) 的 settle、
[03](03-布局与渲染盒.md) 的 layout、[04](04-绘制与双后端.md) 的 paint、[10](10-平台端口与-Win32-壳.md) 的 present）。

### 2.1 零视口帧（最小化 / 桌面临时切走）

`tight(0,0)` **不是**"内容放不下"，而是**"没有像素可画"**。拿它去布局时 `Text` 只能
每字一行（宽 0 ⇒ 换行），而可用高度同样是 0 ⇒ `RenderText 实际 0.0 × 86.4，
最多只能用 0.0 × 0.0`，当场 C6 Fatal（用户 2026-10-25 实测：最小化即崩）。

判据放在 `frame()` 里、**泵全部跑完之后**、`placeOverlays` 之前：

| 段 | 零视口时 | 理由 |
|---|---|---|
| `pumpIo` / `pumpTasks` / `pumpSliced` / `pumpTimers` / `tickAnimations` | **照跑** | 最小化期间动画与 `after()` 必须继续推进，否则还原时一下跳好几秒 |
| `placeOverlays` + `Frame::run` | **跳过** | 布局/绘制/present 都没有意义；表面因此**一帧都不起** |

★ 根盒**保持最后一次有效尺寸**（不被 0 覆盖）—— 这是"还原能正常重排"的前提；
还原时系统必发新的 `WM_SIZE`（带真实尺寸）⇒ 走正常帧。夹具断言的就是这三件事：
帧被**计数跳过**、表面**不起帧**、根盒**保持旧宽**（`Smoke\App\ZeroViewportApplication`）。

★ 为什么不做"缓存上次视口继续画"：画进不可见 surface 纯属浪费，而且会让
`Screen::viewport()` 撒谎 —— 它应当诚实反映客户区（0 就是 0）。判据放在**框架**
而不是平台端口，是因为任何端口都可能给 0（离屏、折叠屏、远程桌面），
框架早退一次就全覆盖；`repaintForResize()` 用同一条判据直接 return（它本来不跑泵）。

## 3. 动画驱动（§17.4.9）

- `State::tickFrame(float $timestampMs): bool`（`src/Widget/State.php:101`）由帧时钟在 settle 前遍历树调用；
  返回"还要下一帧吗"喂 `wantsFrame()`。动画跑完/控件卸载 ⇒ 返回 false ⇒ 时钟停。
- `State::markDirty()`（`src/Widget/State.php:81`）是写入口；`tickFrame()` 里 `setState` 只标脏，由紧随的 settle 消费。
- **同帧幂等**：`tickFrameStamped(ts, serial)`（`src/Widget/State.php:116`）用每帧自增 `frameSerial`
  识别"本帧已推进过的状态"，迟到挂载补 tick 不会把动画快进一帧。
- 原语：`AnimationController`（`src/Widget/AnimationController.php:68`，0..1 单值驱动器）+ `Curve`
  （`src/Widget/Curve.php:27`，`int $kind` + `===` 链分 4 条二次曲线，**不用 `switch`**——见
  `src/Widget/Curve.php:91` 注释：tpc 给 `switch($this->kind)` 生成属性读不加 `php::toInt()` ⇒ C2440）。

## 4. 异步三问（先问"你在等什么"）

- `TaskHost` 接口（`src/App/TaskHost.php:48`）：两条后端——`ProcessTaskHost`（子进程，跨语言/
  防卡帧）与 `SyncTaskHost`（同线程，快路径）。
- 作业：`Job`（`src/App/Job.php:22`）、`NamedJob`（`src/App/NamedJob.php:29`）。
  ★ `SlicedJob`（分片任务）**已于 2026-10-31 删除** —— 它的入口只在 `Application` 上，
  页面（`State`）架构上拿不到，且与 `TaskHost` 重复七件事；见
  `docs/ASYNC-ARCH-2026-10-31.md` §12 与 `DESIGN.md` §17.4.3。
- `IoPoller`（`src/App/Io/IoPoller.php:27`）+ `ProcessWorker`（`src/App/ProcessWorker.php:28`）：非阻塞 IO 与子进程管理。
- ★ 不依赖 `Swoole\Thread`：上游修复实测只到半效。异步结果**回贴**走 `setState` ⇒ 同帧 settle 消费。

## 5. 三条错误通道（先问"这是谁的错"）

`Errors`（判决器，`src/Errors.php:33`）与 `ErrorBoundary`（节点级兜底，`src/Widget/ErrorBoundary.php:39`）
职责分得清，但**入口没有类型**：写应用时没人告诉你什么时候 `throw`、什么时候
`Errors::report()`、什么时候包一层边界。按"错在谁"三行判完：

| 谁错了 | 用什么 | 现场表现 | 为什么不是另外两条 |
|---|---|---|---|
| **框架契约 / 不变式被破坏**（封存后 `mutate()`（`src/Widget/Widget.php:262`）、容器上 `overflow(Overflow::Scroll)`、尺寸超出上界（C6，`src/Layout/RenderBox.php:293`）） | `Errors::report($msg, Errors::FATAL)`（`src/Errors.php:68`，默认就是 FATAL） | 写 `Errors.log`（错误 + 栈 + 最近 100 条 Diagnostic）→ 原生错误框 → `exit(3)` | 继续跑必然得到错误结果 ⇒ 降级没有意义；交给 `ErrorBoundary` 会把"框架坏了"画成一个占位块，**看起来像应用自己的 bug** |
| **用户输入 / 数据让某一子树渲染失败**（一条记录缺字段、插件页面炸了） | `ErrorBoundary::make($subtree)`（`src/Widget/ErrorBoundary.php:46`） | 该子树换成 `ErrorPlaceholder`（消息原文显示给用户），**其余照常** | 这类错不该让整个窗口死；捕获只写 `DIAGNOSTIC`，**不用 `RECOVERABLE`**——它在 debug 下整局中止，与"只坏那一块"直接矛盾 |
| **外部 IO / 慢操作**（读文件、跑子进程、网络） | `Job` + `after()`（真异步 `ProcessTaskHost` / 快路径 `SyncTaskHost`，见 §4） | 结果回贴 UI 线程后 `setState`，同帧 settle 消费 | 既不是契约破坏也不是渲染失败；**在 UI 线程里同步等**才是这里的错（`SyncTaskHost::run()` 就在 UI 线程，卡帧） |

★ 三条纪律：
- **不要用 `throw` 当错误报告**：没人接的异常冒到 `Frame` 走 Fatal 序列 ⇒ 整个窗口中止。
  要么 `Errors::report()`，要么把这段渲染放进 `ErrorBoundary` 子树里。
- **`ErrorBoundary` 不是 `try/catch` 的替代品**：它只兜渲染期三层（`ErrorBoundaryElement::rebuild()`
  / `settle()` / `RenderErrorBoundary::performLayout()/paint()`）；`Job` 回调里的异常**不在**它的
  捕获范围内（那里该自己 `Errors::report()` 或走应用自己的失败态）。
- **占位 UI 本身就是痕迹**（消息原文给用户看）；额外 `Errors::report(DIAGNOSTIC)` 的理由只是
  让 `recentDiagnostics()` 能断言，不是"多记一条更保险"。

## 6. 自适应帧时钟（`FrameClock`，`src/App/FrameClock.php:52`）

- 壳的消息泵是**阻塞**的（`GetMessageW`）：没输入事件就一直睡。所以"后台任务还在跑/分片没跑完/
  有流在监听"必须由框架主动说出口，壳才知道起定时器把循环叫醒——**这是修缺陷，不是优化**。
- `FrameClock::pace(wantsFrame())`（`src/App/FrameClock.php:121`）在 `frame()` 之后调；顺序不可换
  （先 frame 再 pace，wantsFrame 读的是跑完这帧后的状态）。
- 三件事都有界 ⇒ 立刻 `false` ⇒ 帧时钟停摆、CPU 归零。

## 7. 轻量重绘（拖动 resize，`Application::repaintForResize()`）

与 `frame()` 唯一区别：**不碰帧外东西**（不 pump/不推进画/不重建焦点链/不推语义）。平台壳在
`WM_SIZE`（模态循环内）同步调回（C→PHP 重入），能碰的状态越少越安全；松手后主循环恢复跑完整帧收尾。

零视口（最小化时 `WM_SIZE` 的 lp 就是 0×0）与 `frame()` 用**同一条判据**，但它不跑泵 ⇒ 直接
return（§2.1）。不早退的话，最小化瞬间这条重入路径就是第一个撞 C6 的地方。
