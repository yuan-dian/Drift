# 审查：示例应用是不是太多了，能不能整合？

> 2026-11-16 · 只读审查，**未改任何应用代码**。
> 提问：「当前的示例应用比较多，是不是可以整合一下」。
> 相关：[REVIEW-EXAMPLES-TESTING-2026-11-13](REVIEW-EXAMPLES-TESTING-2026-11-13.md)（那次是"测试归属"，本次是"应用整合"）。

---

## 0. 一句话结论

**不建议整合。** 8 个目录里只有 4 个是"能力示例应用"，另 4 个是量具 / 开发壳 / 最小出口判据
—— 它们各自承担**不同的验证职责**，不是同一件事写了八遍。真正的问题不是数量，
是**定位标签缺失**：8 个目录平铺在 `apps/` 下，名字看不出"哪个是给用户看的示例、
哪个是内部尺子"，才产生"是不是太多了"的观感。

真正值得做的不是删应用，是两件低成本的事：
1. **给每个应用补一句定位标签**（在哪一层、给谁看、能不能删）—— 零代码风险；
2. **修一处过时文档**（`docs/tutorial.md` 说 showcase「19 个页面」，实际 35 个）。

## 2. 为什么"整合"是错的（逐项裁决）

### 2.1 量具 / 工具（bench / pacing / dev）—— 不能并，也不该并

三者各自回答一个**唯一的问题**，且有独立的判据、输出文件、运行方式：
- `bench`：三个微基准 + 一个真机分解，输出 `build/bench-out.txt`，判据是 `A/B` 比值；
- `pacing`：帧间隔分布，输出 `build/pacing-out.txt`，判据是 median/p99/max；
- `dev`：热重载开发壳，是工具链一环（`drift-dev.php` 直接读写 `apps/dev/`）。

合并它们等于把三把不同的尺子熔成一把 —— 判据混在一起就没有判据了。且 `drift-build`、
`drift-dev.php`、`dual-mode-fingerprint-entry.php` 都硬编码了这些路径，整合是高成本低收益。

### 2.2 hello / tutorial —— 看着像重复，实则两个不同阶段

- `hello`（1 文件 40 行）：**最小出口判据**，证明"M1 能编出一个窗口程序"，是构建链的最简回归。
- `tutorial`（6 文件 503 行）：**教学**，四段代码对应 `docs/tutorial.md` 四个静默坑
  （帧循环 / 状态 / 浮层 / 异步），配套 smoke 判据（`tools/smoke.php` 的 ㊷ 段）。

把 hello 并进 tutorial 会丢掉"最小可构建单元"这个最快的构建回归；把 tutorial 并进
hello 会让最小判据背上教学代码。两者职责正交，保留。

### 2.3 users / watermark —— 两个业务示例，深度不同

- `users`：命令系统 + 多页 + 表单 + 异步取数 —— **广度**（展示各种缝怎么接）。
- `watermark`：OSS 直传 + 异步任务 + 结果轮询 —— **深度**（一条完整业务流水线）。

二者都有 `JobRegistry`，但结构同构而内容不同（users 1 个 Job、watermark 5 个）。
这是"每个应用各搭一套 scaffold"，属于组合根配置的必要独立性。
`JobRegistry`、`Bootstrap` 看着重复（三个 registry 行数 27/28/43），但每个都装配不同能力，
强行抽公共基类只会把"一眼看全这个应用接了什么"变成到处跳转。判死。

### 2.4 showcase —— 页面多不等于应用多

showcase 的 35 个页面每个对应**一个独立控件能力点**（Align/Aspect/Buttons/Table/Tree…），
是一部控件图鉴。它与 `users`/`watermark` 里出现的异步表格页看着像重复
（`AsyncTablePage` / `LoadMorePage` / `ConcurrentFetchPage` vs `UsersPage`），但：
- showcase 的版本是**控件演示**，断言主语是框架行为（测试在 `tests/Feature/Widget/`）；
- users 的版本是**业务闭环的一环**，断言主语是命令/Store 接线。

这是同一控件在不同上下文的用法，不是两份要合并的实现。且 35 页清单已被
`tools/Bench/ShowcasePages.php`、`tools/Golden/PageScenes.php`、`scene-set-check.php`
当成**显式测试资产**锁定 —— 删页/并页会动判据集合，成本高。

## 3. 真正的痛点与低成本解法

### 3.1 定位标签缺失（这才是"感觉多"的根源）

8 个目录平铺，`bench`/`pacing` 的"我不是示例"只写在各自 README 里 ——
不点进去就不知道。建议在 `apps/` 下加一个**极简总览**（或在 `docs/00-README.md` 补一段），
按"示例 / 量具 / 工具"三类给每个目录一句话定位：

| 分类 | 目录 | 给谁看 |
|---|---|---|
| 能力示例 | showcase（控件图鉴）/ tutorial（教学）/ users（业务广度）/ watermark（业务深度） | 应用开发者 |
| 最小判据 | hello | 构建链回归 |
| 量具 | bench / pacing | 框架维护者 |
| 工具 | dev | 框架维护者 |

零代码风险，直接消除"是不是太多了"的观感 —— 因为看完会明白：给用户看的只有 4 个，
且各解决一个不同的问题。

### 3.2 一处过时文档（建议修）

`docs/tutorial.md` 末尾的"想看全部控件"一行写「`apps/showcase/`（19 个页面）」，
实际 35 个页面（`ls apps/showcase/src/Pages/ | wc -l`）。这是**事实性过时**，建议改为
准确数字或去掉具体数字（"全部控件页"），避免读者按 19 这个数去核对时产生困惑。

### 3.3 不建议动的事（判死汇总）

- 不删任何应用 —— 每个都在 `drift-build` / lint / smoke / 测试里被引用，删一个要动多处判据；
- 不合并 Bootstrap / JobRegistry —— 是组合根配置，独立性是特性；
- 不把 showcase 拆散 —— 35 页是锁定的测试资产；
- 不为"减少数量"新建 meta-应用 —— 用一个应用装所有能力，会让每个能力的演示都带上无关代码。

## 4. 参考：成熟 GUI 框架怎么组织示例

- **Flutter**：`examples/` 下按用途分（catalog / layers / platform_channels），
  每个示例一个独立 pubspec —— 与本项目"每应用一个 project.yml"同构，不合并。
- **Qt**：`examples/` 按模块分组（widgets / quick / charts），量具另放 `tests/benchmarks`。
- **共同点**：示例按"用途"分而非"数量"论；量具与示例物理分开。
  本项目欠的只是**把这层分类写出来**（§3.1），不是删应用。
