## 0. 一句话

**三条路的裁决早就有了，而且是实测出来的，不是偏好 —— 不需要重开。**

但真正的问题不在「选哪条路」，在于**三种完全不同的「并发」被当成了一件事**。
今天框架对「不卡 UI」和「重计算别卡一帧」都给了零件；
唯独**「同时等 5 个接口」这一层没有零件、也没有示例**，
于是它会被自然写成「5 次 `submit()`」，然后撞上 `maxWorkers = 1` 的串行
或者 `maxWorkers = 5` 的五个 AOT 运行时。

**而这一层不需要多进程 —— 单个 worker 里就够了：`curl_multi`（推荐先验）或 worker 内 Swoole 协程。**

★ **关于协程的两次更正**：初稿把「协程」笼统否掉 —— 错在**把 Fiber 与 Swoole 混为一谈**；
二稿说「UI 进程不能开 hook」—— 错在**把「必须开 hook」当成了唯一路径**。
准确的说法是：

- Swoole 协程**不卡 IO**，而且用**原生协程客户端**（`Co\Http\Client`）**根本不需要 hook**
  （实测 [J1] 自证：不开 hook 时 `Co\Client` 照样让出）⇒ 与 `IoPoller` 无冲突；
- 它在 UI 进程被挡住的是**控制权**：`Coroutine\run()` 要吃主线程，
  而 Windows 原生版不提供 `Swoole\Event`，没有「每帧 pump 一次」的粒度（§1.2）；
- **worker 进程没有这个矛盾** —— 那里用 `Co\Http\Client` 并发 N 个接口是最干净的方案（§2.4）。

⇒ 协程在本仓是**可选方案**，不是禁区。

附带的、也是更贵的一个问题：**默认后端是同步的**（`Application::taskHost()`
在 `src/App/Application.php:430` 返回 `new SyncTaskHost()`），而示例台
`apps/showcase` **没有注入过任何 `TaskHost`** ⇒ 示例台演示不了真异步，
而示例台是新人唯一的模板。

## 1. 三条路：裁决与依据

先把它钉死，因为后面所有讨论都建立在这上面。

| 路 | 结论 | 实测依据 | 性质 |
|---|---|---|---|
| **多线程** | ⛔ 当前不可行 | `php_request_cache` 只在模块 RINIT 里建；没跑过 RINIT 的 worker 线程上全是**空指针解引用**，单个 worker 也 SIGSEGV。裸线程、Swoole + FFI 两枪都挂（`probes/RESULTS.md` 第 297–305 行区段有编译期与运行期双重记录） | **能力天花板**，不是设计选择 |
| **Fiber（用户态协程）** | ⛔ 不解决问题 | `Fiber::suspend()` 只切换用户态栈，**它不会让阻塞 IO 变成非阻塞** —— 把 `curl_exec` 塞进 Fiber，切出去的那一刻线程仍然卡在那个 syscall 上 | **语义错配** |
| **Swoole 协程** | ⛔ 在 **UI 进程**里不可用（在 worker 里可用） | 见 §1.1–§1.3：协程**不卡 IO**，且用原生协程客户端（`Co\Http\Client`）**不需要 hook** ⇒ 与 `IoPoller` 不冲突。真正的互斥点是**控制权**：协程调度器（`Coroutine\run()`）要吃掉主线程，而 Windows 原生版**不提供 `Swoole\Event`** ⇒ 没法「每帧 pump 一次」 | **控制权互斥**，不是能力问题 |
| **多进程** | ✅ 唯一可行 | worker 是同一份 AOT 产物 ⇒ 跑的是编译后的代码而不是解释执行；`spawn` 单价 **275ms**（`probes/RESULTS.md:668`）⇒ 必须常驻池，不能每任务一进程 | 已落地 |

### 1.1 Swoole 做协程 IO 有两条路，只有一条污染全局

★ **更正（用户指出）**：本文前两稿都把「协程 = 必须开 hook」当成唯一路径。**那是错的。**

| 路径 | 写法 | 要不要 hook | 全局影响 |
|---|---|---|---|
| **A. hook 遗留同步 API** | `Runtime::enableCoroutine()` 之后直接用 `curl_exec` / `fread` / `PDO` | **要** | ⛔ **全局替换**：任何非协程上下文的 `stream_select` / `fread` 都抛 `API must be called in the coroutine`（实测 [J3-a]） |
| **B. 原生协程客户端** | `Co\Http\Client` / `Co\Client` / `Co\MySQL` / `Co\Redis` | **不要** | ✅ **零污染** —— 它本身就只能在协程里用，不需要改写任何全局函数 |

**B 这条，实测记录本身就自证了**。[J1] 的原文是：

> 不开 hook ⇒ `fread` / `file_get_contents` 仍是阻塞的，**只有 `Co::sleep` / `Co\Client` 会让出**

「不开 hook」和「`Co\Client` 会让出」写在**同一句**里 ⇒ **协程客户端不需要 hook**。

⇒ 于是「hook 会打坏 `IoPoller` 的 `stream_select(..., 0)`」**不构成否决理由**：
走 B 路径根本不开 hook，`IoPoller` 毫发无伤。真正的问题在下一节，与 hook 无关。

### 1.2 真正的障碍：协程调度器要吃掉主线程，而 Windows 版没有手动 pump

协程「不卡 IO」这点没有问题。**问题是谁在驱动它。**

- 协程的挂起 / 恢复由 Swoole 内部的 **IocpLoop** 驱动（Windows 版基于 IOCP，不是 Reactor）；
- 驱动它的**唯一入口**是 `Coroutine\run()` / `Scheduler->start()` ——
  一旦进去，**主线程的控制流就归它了**；
- Linux 版还能靠 `Swoole\Event::dispatch()` 手动「pump 一轮」；
  **但 Windows 原生版明确不提供 `Swoole\Event`**（见 §1.3）。

而 Drift2 的帧循环是 `GetMessageW()`（阻塞等窗口消息）→ `Application::frame()`。
**它必须掌握主线程**，否则窗口消息没人取。

⇒ **两个调度器抢同一根控制流，且协程侧没有「每帧 pump 一次」这个粒度。**
互斥的真正来源是**控制权**，不是 hook，也不是「卡 IO」。

★ 唯一可行的融合方式（**能做，但未验**）：
把 `frame()` 搬进 `Coroutine\run()` 里，消息泵改成 `PeekMessage` 非阻塞 + `Co::sleep(0)` 让出。
代价是空闲时也要按固定间隔轮询（`GetMessageW` 的「没活就睡」没了），
且要重写 C++ 壳的消息泵。**今天不做，但它是「现状」不是「定理」。**

★ 而 **worker 进程**里这个矛盾整个不存在 —— worker 本来就是
`run()` + 阻塞等任务，既没有窗口消息要取，也没有 `IoPoller`。
**那里走 B 路径（`Co\Http\Client`）是最干净的方案**（§2.4）。

### 1.3 Swoole Windows 原生版：官方能力矩阵

2026-05-15 官方发布：基于 **IOCP** 的原生 Windows 移植，不再依赖 WSL / Cygwin / Docker
（`php_swoole.dll` + VS2022 构建）。与本仓相关的几行：

| 能力 | 状态 | 对本仓的意义 |
|---|---|---|
| `Swoole\Coroutine\Http\Client` / `Coroutine\Client` | ✅ 完全支持 | **§2.4 worker 方案的载体**（且不需 hook） |
| `Runtime` 协程 Hook（含 cURL，需 `--enable-swoole-curl`） | ✅ 支持 | 路径 A 可用，但会全局污染 |
| `Swoole\Thread`（需 ZTS + `--enable-swoole-thread`） | ✅ 支持 | 线程能起；**但线程里看不到 tpc 编译的类**（实测 `probes/RESULTS.md:663`） |
| **`Swoole\Event`（事件循环 API）** | ❌ **Windows 不提供** | ⇒ **没有手动 pump**，这正是 §1.2 的硬约束 |
| `Swoole\Process` / `Process\Pool` | ❌ 不支持（依赖 fork） | 本仓多进程走 PHP 原生 `proc_open`，**不受影响** |

★ **一处矛盾，如实记下**：官方矩阵说 Windows「不提供 `Swoole\Event`」，
但本仓 2026-10-18 的探针在 AOT 产物里**确实调到了** `Event::dispatch()`，且实测阻塞 57ms
（环境为 `swoole=6.3.0RC1`，见 `probes/RESULTS.md:661`）。两者对不上，可能是版本差异。

**但这个矛盾不影响结论**：无论它是「不存在」还是「存在但阻塞到下一个事件」，
**都做不到 0 超时 pump** —— 而 §1.2 缺的正是那个粒度。要定论得补一次探针。

★ 官方文章末尾有一句：「配合 Swoole 的 PHP AOT 编译器，利用原生 Windows 线程 / 协程模型，
可以开发异步非阻塞的桌面 GUI」。**这是宣称，不是本仓的实测**，
而且它说的 AOT 与 tpc 是两套东西。按本仓纪律，**宣称不构成可用性证据** ——
要验的是「**tpc 产物 + `Co\Http\Client` + `Coroutine\run()`**」这个具体组合。

### 1.4 为什么 Fiber 也不行（这条与 Swoole 无关）

Fiber 是纯用户态栈切换，**它没有配套的 IO 层**。
`Fiber::suspend()` 之后谁来决定什么时候 `resume()`？必须有人替它盯着 socket。
Swoole 靠 hook 解决了这件事，Fiber 没有 —— 所以 Fiber 只能做「自愿让出」的计算分片
（那正好是 `SlicedJob` 已经在做的），做不了阻塞 IO 的并发。

★ 这一条也正是 `src/App/Io/IoPoller.php:22` 写下「不做通用 Fiber 调度器，
等真有消费者再加」的原因：调度器本身不值钱，值钱的是它背后那个 IO 层。

### 1.5 多线程什么时候可以重开

只有一个前置：**上游给出 `php::thread_init()` 级别的入口**（TSRMLS / `ts_resource` +
EG 初始化），让 worker 线程能拥有自己的 Zend 上下文。

在那之前，任何「多线程」方案在本仓都是 SIGSEGV 制造机。
这条不用每次重新论证 —— 它写在 `src/App/TaskHost.php:39` 起的类注释里，
端口契约**不变**，上游补上即可直接接一个后端实现，**应用代码零改动**。
这正是端口存在的意义。

## 2. 核心：三种「并发」被混成了一件事

用户那句「业务处理慢不能卡 UI，以及需要同时请求多个网络接口」，
其实是**三个不同层次的需求**，需要的工具完全不同：

| 层 | 需求原话 | 要的东西 | 正确工具 | 今天的状况 |
|---|---|---|---|---|
| **L1** | 「业务处理慢，不能卡 UI」 | 把活挪出 UI 线程 | `TaskHost` + `ProcessTaskHost` | ✅ 有，**但默认是同步**（见 §4.1） |
| **L2** | 「一个重计算别占一帧」 | 切帧，不是并行 | `SlicedJob`（每帧 4ms 预算） | ✅ 有（`src/App/SlicedJob.php`） |
| **L2'** | 「多个重计算真并行」 | 真 CPU 并行 | `maxWorkers = N` | ✅ 有，代价是 N 份运行时 |
| **L3** | 「同时请求 5 个接口」 | **并发等待**，总耗时 = max 不是 sum | **单 worker 内 `curl_multi`，或 `Co\Http\Client`（§2.4）** | ⚠️ **没有零件、没有示例** |

### 2.1 L3 是最容易被写错的那一层

今天想「同时请求 5 个接口」，代码会自然地长成这样：

```php
for ($i = 1; $i <= 5; $i++) {
    $host->submit(new FetchUsersJob($i), fn (array $rows) => $this->append($rows));
}
```

然后撞上两种结局：

- **`maxWorkers = 1`（默认）** ⇒ 5 条任务在 worker 里**串行**跑，
  总耗时 = `sum(5 个请求)`。异步白做了 —— 它只保证了不卡 UI，没有并发。
- **`maxWorkers = 5`** ⇒ 起 **5 个 worker 进程**。每个 worker 是一整套 AOT 运行时
  （几十 MB 常驻），只为了同时等 5 个 socket。
  在 8GB 笔记本上这就是「一个页面崩一次内存」的写法。

**两种都不对，因为工具选错了层次。**

L3 要的是「**一个线程同时等 5 条连接**」，这在 libcurl 里是 `curl_multi_*` 的
本职工作：5 条连接一起 non-blocking，事件驱动，总耗时 = 最慢那条。
它**不需要第二个线程**，也就绕开了整张「多线程不可行」的墙。

### 2.2 所以正确的写法是

```php
// 一个 Job，内部并发 5 个请求 —— 1 个 worker 进程就够
final class FetchDashboardJob implements NamedJob
{
    public function run(): mixed
    {
        $mh = curl_multi_init();
        $handles = [];
        foreach ([1, 2, 3, 4, 5] as $page) {
            $ch = curl_init($this->url($page));
            curl_setopt_array($ch, [/* … */]);
            curl_multi_add_handle($mh, $ch);
            $handles[$page] = $ch;
        }

        do {
            $status = curl_multi_exec($mh, $running);
            if ($running) {
                curl_multi_select($mh, 0.05); // 只在这个 worker 里等，与 UI 无关
            }
        } while ($running && $status === CURLM_OK);

        // …收结果、按 page 归位…
    }
}
```

这个写法的性质：
- **1 个 worker 进程**，内存与「请求 1 个接口」相同；
- **总耗时 = 最慢那条**，而不是 5 条相加；
- UI 线程全程不知道（它只看见一次 `submit` 一次 `onDone`）；
- 不需要 Fiber、不需要多线程、不需要 `maxWorkers > 1`。

★ **`maxWorkers` 仍然有用**，但它的适用面窄得多：**互不相关的独立重任务**
（一个导出 Excel、一个全表校验、一个批量上传）。
「一个页面的 5 个数据源」不该用它 —— 那是同一个业务动作的分解，属于 L3。

### 2.3 一条待验项（必须验，不能假设）

`curl_multi_*` 在 tpc AOT 产物下**没有历史记录**。

已验证的是 `curl_init` / `curl_exec` / `curl_setopt_array`（`tools/drift-build.php:447`
的记录：AOT 产物里全部可用、`code=200`）。`curl_multi_init` / `curl_multi_exec` /
`curl_multi_select` 属于同一扩展的另一半 API，**理论上可用，但没有实测**。

按本仓纪律（「没验过的不许写成事实」），这是 **A1 台阶的第一件事**：
一个最小探针，5 条并发请求打到慢 mock，断言「总耗时 ≈ max 而非 sum」。
**验不过就不要写进文档当推荐做法** —— 那时 L3 只能退回多 worker，代价要如实写出来。

> **★ 2026-10-30 已验（`probes/RESULTS.md` §13.2，探针 `probes/eventloop_design/`）**：
> `[E2] n=5 ok=5 elapsedMs=623 serialWouldBe=3000ms verdict=CONCURRENT`
> —— **通过**，且是**真并发**。附带一条更有用的：切成「每帧 `exec` + `select(0)`
> 推进」后单轮 **12.2µs**、最坏 **2.1ms**（`[E2b] verdict=UI-SAFE`）⇒
> **它可以在 UI 线程做，不必进 worker**。设计落点见
> [`EVENT-LOOP-DESIGN-2026-10-30.md`](EVENT-LOOP-DESIGN-2026-10-30.md) §3.2 的 A1。

### 2.4 第三条路：**worker 进程**里用 Swoole 协程（`Co\Http\Client`，**不开 hook**）

§1.2–§1.3 否掉协程的理由是**控制权**：`Coroutine\run()` 要吃主线程，
而 Windows 版没有 `Swoole\Event` 可以手动 pump。**这条在 worker 进程里不成立**：

| 矛盾 | UI 进程 | worker 进程 |
|---|---|---|
| `Coroutine\run()` 抢主线程控制流 | ⛔ 致命（`GetMessageW` 没人取） | ✅ **worker 没有窗口消息**，控制流本来就归它 |
| 没有 0 超时 pump | ⛔ 帧循环要那个粒度 | ✅ **worker 不需要**：它一次只服务一条请求 |
| hook 全局污染 | ⛔ 打坏 `IoPoller` 的 `stream_select(0)` | ✅ **根本不开 hook**（走 `Co\Http\Client`） |

worker 是纯后台进程：全部工作就是**读一行请求、跑、写一行回复**
（`src/App/ProcessWorker.php`）。没有窗口、没有输入、没有绘制、没有 `IoPoller`。
⇒ 它可以整个跑在 `Coroutine\run()` 里，**写顺序代码并发 5 个请求，一行 hook 都不开**：

```php
// worker 侧：不开 hook。用原生协程客户端 —— 它本身就会让出
$pages = [1, 2, 3, 4, 5];

\Swoole\Coroutine\run(function () use ($pages): void {
    $chan = new \Swoole\Coroutine\Channel(count($pages));

    foreach ($pages as $page) {
        \Swoole\Coroutine::create(function () use ($page, $chan): void {
            $cli = new \Swoole\Coroutine\Http\Client('127.0.0.1', 8099);
            $cli->set(['timeout' => 10]);            // connect 与 request 各 10s
            $cli->get('/api/users?page=' . $page);   // ← 这里挂起，不占线程
            $chan->push([$page, $cli->statusCode, $cli->body]);
            $cli->close();
        });
    }

    $results = [];
    for ($i = 0; $i < count($pages); $i++) {
        [$page, $status, $body] = $chan->pop();
        $results[$page] = ['status' => $status, 'body' => $body];
    }
});
// 总耗时 = max(5 条)，写起来是顺序的，getHookFlags 仍为 0
```

**三个 L3 方案的诚实对照**（同一件事，三种写法）：

| 方案 | 进程数 | 写法 | 代价 | 未验项 |
|---|---|---|---|---|
| **单 worker + `curl_multi`** | 1 | 回调 / 状态机（自己管 multi handle 生命周期） | Job 内部变复杂 | `curl_multi_*` 在 AOT 下 |
| **单 worker + `Co\Http\Client`** | 1 | **顺序代码**（最好读），**不开 hook** | ① 每 worker 多一份 swoole 运行时；② AOT 构建要带 `extension=swoole`，且 **swoole 依赖 curl，ini 顺序不能反**（`probes/RESULTS.md:661`）；③ `ProcessWorker::serve()` 要改写成 `Coroutine\run()` 形态 | **整个组合完全未验** |
| **N 个 worker** | N | 最简单（一行 `maxWorkers`） | N 份 AOT 运行时常驻内存 | 无 |

★ **为什么仍然推荐 `curl_multi` 打头阵**：它不引入扩展依赖、不改 `ProcessWorker`、
不让 AOT 构建链多带一个 DLL、也不要求部署机装 swoole。
协程方案在「写法」上明显更优（顺序代码 + `Co\Http\Client` 自带连接复用 / 超时 / TLS），
但**验证成本高一个量级** —— 要验的不是一个 API，是
「`extension=swoole` + `Coroutine\run()` + `Co\Http\Client` + tpc 编译的类 + `ProcessWorker` 循环」
五者的组合。

★ **这条推翻了「协程在本仓完全不可用」这个过强结论**。准确的说法是：
**协程在 UI 进程被控制权挡住，在 worker 进程可用（且不必 hook）但未验。**

★ **一个仍然悬着的关键未知**：协程里调 **tpc 编译的类**能不能跑？
按原理能（协程与线程不同 —— 它在同一线程、同一 `php_request_cache`、同一类表），
但探针只测过 `Swoole\Thread`（线程，实测 `Class "SwooleProbe\Counter" not found`，
`probes/RESULTS.md:663`）—— **线程的结论不能搬到协程上，这是两回事**。
这条是 §2.4 能否成立的唯一硬前提，要先验。

> **★ 2026-10-30 已验（`probes/RESULTS.md` §13.2，探针 `probes/eventloop_design/`）：可行。**
> 四项全对：`[M5] tpc-fn=42`（全局函数）/ `[M6] tpc-class=7`（`new` 类）/
> `[M7] inner=12 total=12`（子协程 + 闭包捕获对象）/
> `[M8] wallet=650`（**跨实例读 private**，AOT 老坑的同类形态）。
> ⇒ 协程与 tpc 编译产物共处同一类表、同一堆，**这条硬前提解除**。
>
> ★ 同轮还发现一条**工程约束**：`curl_multi` 与 `swoole` **不能共存于同一 AOT 产物**
> —— 运行期全部正常，崩在**退出阶段**（`swoole=6.3.0RC1`；换顺序崩得更早）。
> ⇒ 「UI 线程用 `curl_multi` 切片」与「用协程」**互斥，一个产物只能选一个**。
> 设计上如何取舍见 [`EVENT-LOOP-DESIGN-2026-10-30.md`](EVENT-LOOP-DESIGN-2026-10-30.md) §3.2。

★ **顺带一条收益**：worker 里用 `Co\Http\Client` 还免掉了一个 `curl_multi` 的坑 ——
连接复用与 keep-alive 由客户端自己管，不用在 `curl_multi_*` 里手工维护
handle 池与 `curl_multi_remove_handle` 的时机。

### 2.5 `Co\Http\Client` 到底是什么（能力边界）

★ 先把最容易误判的一点说清：**它不是 libcurl**。
`Swoole\Coroutine\Http\Client` 是 Swoole **自研**的 HTTP 客户端，
底层走 `Coroutine\Socket`（Windows 上即 IOCP）。这决定了它的边界 ——
既没有 curl 那么全，也不吃 curl 的那些坑。

**能力（官方文档口径；本仓未验，仅供选型参考）**

| 项 | 支持 | 备注 |
|---|---|---|
| HTTP 版本 | **HTTP/1.1** | HTTP/2 要另用 `Co\Http2\Client`（**另一个类**，不是同一个） |
| 连接复用 | ✅ Keep-Alive | 同一个 Client 实例内持续复用 |
| 分块 / 压缩 | ✅ Chunked；✅ gzip（依赖 zlib） | |
| 表单 | ✅ `setData()` / `addFile()`（form-data，底层 sendfile） | 大文件上传不必先读进内存 |
| Cookie | ✅ `setCookies()`，且自动合并服务端下发的 | |
| 重定向 / 代理 | ⚠️ `set()` 有相关选项（`follow_location` / `max_redirects` / `http_proxy` 等） | **能力不如 curl 完整**，复杂代理别指望 |
| TLS | ✅ 构造器第三参数 `$ssl = true` | |
| 超时 | ✅ `set(['timeout' => 秒])` —— **默认 500ms** | 默认偏激进：内网接口够用，公网务必显式放宽 |
| WebSocket | ✅ 同一个类可 `upgrade()` | |

**它没有的**：curl 的协议族（FTP / SMTP…）、`CURLOPT_*` 那套细粒度控制、
HTTP/2（在 Http 客户端内）、curl 的 DNS 缓存策略。
⇒ 对「请求内部 / 公网 REST API」够用；对「要精确复刻 curl 行为」不够。

★ **一条反直觉的发现，也是这份评估里最有价值的一条** ——
文章「cURL 协程 Hook 桥接」那节，把 Swoole **Windows 版 hook 的实现**写明了：

> 通过零字节的 `WSARecv()` / `WSASend()` 投递到 `IOCP`；完成通知到达后，
> 回调 **`curl_multi_socket_action()`**；`libcurl` 仍然控制着实际的传输状态机和 IO 操作；
> `Swoole` 只负责「这个 Socket 可以读了 / 可以写了」的信号传递。

**换句话说：Swoole 的 cURL 协程化 = `curl_multi` + IOCP 就绪桥接。**

| 维度 | 本册建议的 `curl_multi` 方案 | Swoole 的 cURL 协程方案 |
|---|---|---|
| 传输内核 | **libcurl multi** | **libcurl multi**（同一个） |
| 事件源 | `curl_multi_select()`（Winsock `select`，**就绪通知**） | IOCP（**完成通知**）+ 零字节 WSARecv/WSASend |
| 写法 | 回调 / 状态机 | 顺序代码（协程挂起） |
| 依赖 | 只要 curl 扩展 | curl + swoole，且需 `--enable-swoole-curl` |
| 规模上限 | `select()` 受 FD_SETSIZE(1024) 与 O(n) 限制 | IOCP 无此限制 |

⇒ **`curl_multi` 不是「退而求其次」——它就是 Swoole 方案的内核**，
只差 IOCP 与协程包装。这让 A1 的排序更站得住：**先用最低成本拿到同一内核的并发能力**，
将来真要上规模（几百上千连接）再换 IOCP。

★ **一个更干净的长期方向（不在本轮范围，但值得记）**：
IOCP 的 handle 是**可等待对象**，能被 `MsgWaitForMultipleObjectsEx` 与窗口消息**一起等**。
也就是说，理论上可以把「窗口消息」和「IO 完成」放进**同一个等待集合**，
做到**零轮询、零协程** —— 这是 Chromium / Electron 这类桌面壳的正解，
比「在 UI 线程塞协程调度器」干净得多。
代价是要在 C++ 壳里做，且 Swoole 不暴露它的 IOCP handle（除非走 FFI）。
**它是「协程之外的第三条路」，而且比协程更贴合本仓的帧模型。**

（`src/App/ProcessTaskHost.php:228` 起）：Windows 上 `pipe + select(0)` 是
**13.6ms/次**，非阻塞 `fread` 在 pipe 上等于没用（411ms/次）；
`socket + select(0)` 是 **0.008ms**。用 pipe 的版本每帧 29ms —— 界面上就是稳定掉帧，
而且**看不出是谁的错**。

### 3.2 两处断桥

**断桥一：`apps/showcase` 没有注入任何 `TaskHost`。**

| 应用 | 是否注入 | 结果 |
|---|---|---|
| `apps/users` | ✅ `apps/users/bin/win32/Bootstrap.php:78` 注入 `ProcessTaskHost`（`maxWorkers` 默认 1） | 真异步演示的唯一载体 |

## 4. 六个真缺口（按「现在就会咬人」排序）

### 4.1 默认后端是同步的，且没有消费者纠正它

`src/App/Application.php:430`：

```php
public function taskHost(): ?TaskHost
{
    return new SyncTaskHost();
}
```

`SyncTaskHost::submit()` **在调用者线程上把 `run()` 跑完**。
它的诚实边界写得很清楚（「大响应时会短暂停顿，`loading` 那一态对用户不可见」），
问题不在它，在**没人换掉它**：示例台没换 ⇒ 模板有毒。

★ 这一条的修法不是「改默认值」（框架不能替应用决定起不起进程池，
那涉及内存与生命周期），而是**让示例台显式注入 + 文档写明确**。
两者都是纯加法。

### 4.2 L3 没有零件也没有范式（§2 全部）

见上文。这是用户当前问题最直接的落点。

### 4.3 没有取消

`TaskHost` 的接口只有 `submit` / `pending` / `drain`，**没有 `cancel`**。

典型场景：用户在列表页点了「加载第 2 页」，1.2 秒内切到了别的页。
任务仍在 worker 里跑完，回调仍然会在某一帧被执行，去改一个**已经不该更新的 State**。
它不会崩（闭包持有 State 引用），但会：
- 白白占着 worker / 带宽；
- 若那个 State 还被复用（比如分页 Store 是单例），会**把旧页数据写进新页**。

`SlicedJob` 同理：`step()` 返回 `true` 就一直排队，没有「终止」通道。
（`IoPoller` 反倒有 `unwatch()` —— 最小的那个零件做得最完整。）

### 4.4 没有框架级超时 —— 代价是**电池**

`pending()` 是帧时钟的判据：`> 0` ⇒ 平台按 15ms 跳，`= 0` ⇒ 可以无限期阻塞。
设计是对的（「有活才跳，没活就睡」）。

但**没有超时**意味着：worker 卡在一个不响应的远端上（TCP 连上了但对面不回），
`pending()` 永远 `> 0` ⇒ UI 线程**每 15ms 被唤醒一次、什么都不做**，
一直持续到那个请求自己超时（或者永不超时）。

用户看到的是：风扇转、电池掉，界面却没有任何变化。
这不是性能问题，是**能耗问题**，而且极难归因 —— 帧耗时里只有「空转」。

今天的超时只存在于**业务代码自己**（`apps/users/src/Jobs/FetchUsersJob.php`
的 `CONNECT_TIMEOUT_S` / `TIMEOUT_S`）。框架层没有兜底 = 忘设一次就中招。

### 4.5 没有进度

长任务（导出、批量上传）只能「转圈到结束」。
表达进度的现有手段只有两个，都不合用：
- `SlicedJob`：那是**切帧**，进度是副作用，且它跑在 UI 线程上（重活不能用）；
- 多次 `submit`：会打破「一次业务动作 = 一个任务」的语义。

真要做，正确形状是 `Job` 侧能往回推一条事件（单向、无阻塞），
`TaskHost` 转发成 UI 线程回调。但**今天没有消费者**，按纪律不发明。

### 4.6 `shutdown()` 不优雅

`ProcessTaskHost::shutdown()` 直接 `fclose` 三根管道再 `proc_close`。
worker 的 `fgets` 返回 `false` ⇒ 正常收工 —— 但**在途任务静默丢失**，
不会触发 `onError`，UI 侧永远等不到回调。

单窗口、退出即销毁时无所谓（反正要死了）。多窗口一旦立项（关一个窗口不收工），
这条会立刻变成「关掉窗口 = 悄悄丢一次保存」。

## 5. 被否掉的方案

### 5.1 上 Fiber 调度器（写「顺序代码」的异步）

**否。** 理由见 §1.4：Fiber 只提供 `suspend()` 这个手动让出点，**没有配套的 IO 层** ——
「什么时候该 `resume()`」还得有人盯着 socket。本仓的「事件循环」是**帧**，
不是独立 `run()` 循环，所以这个调度器无处安放。塞进来只会多出一层
「谁在什么时候恢复哪个协程」，而收益只是少写几个闭包。

★ 而且 `src/App/Io/IoPoller.php:22` 已经写了这条裁决：
「不做通用 Fiber 调度器 —— `Awaitable::read()` 那种'顺序代码'包装**等真有消费者再加**」。
今天依然**没有消费者**。

★ **注意别把这条和 §2.4 混淆**：否的是「自建 Fiber 调度器」，
不是「Swoole 协程」。后者自带 IocpLoop 与 `Co\Http\Client`，
在 worker 进程里是可行方案。

### 5.2 提前攻坚多线程

**否。** 缺的是上游 `php::thread_init()`，不是本仓的工作量。
在本仓做任何「绕过」都是拿 SIGSEGV 换一个看起来并行的假象。
端口契约已经留好（`TaskHost` 换后端是组合根一行），上游一通即可接。

### 5.3 每任务一进程

**否。** `spawn` 单价 275ms（`probes/RESULTS.md:668`）。
按任务起进程在任何交互场景都不可用。所以是**懒启动 + 常驻池**。

### 5.4 Swoole **线程**

**否。** 线程侧两枪都试过：裸线程与 Swoole + FFI 都 SIGSEGV（缺 Zend 上下文）。
而且 `Swoole\Thread` 里**只能 `require` 源码解释执行**（慢 55–95×），
看不到 tpc 编译的类 —— 等于把 AOT 的收益全丢掉。

### 5.5 Swoole **协程在 UI 进程**

**否，但理由是「控制权互斥」，不是「会卡 IO」，也不是「必须开 hook」。**

- 「卡 IO」不成立：协程不卡（§1.1）。
- 「必须开 hook」不成立：`Co\Http\Client` 不需要 hook（§1.1 路径 B）。
- **成立的是**：`Coroutine\run()` 一旦进去就接管主线程，
  而 UI 线程必须去 `GetMessageW` 取窗口消息；Windows 版又不提供 `Swoole\Event`，
  没有「0 超时 pump 一次」的粒度（§1.2 / §1.3）。

★ **这条不适用于 worker 进程** —— 那里没有窗口消息，控制流本来就归它。
**在 worker 里不否**，见 §2.4。

### 5.6 给 `SlicedJob` 加并行

**否。** `SlicedJob` 的定义就是「切帧，不是并行」——
它的价值恰恰在于**它没有第二个线程**（`src/App/SlicedJob.php` 的类注释写明
「分片不是后端，它没有第二个线程可谈」）。要并行是另一个工具的事。

## 6. 路径：三个台阶

按「先做零风险的、直接回答需求的」排序。

### A1 · 并发 IO 零件与范式（**零真机**，最高性价比）

1. **探针**：`curl_multi_*` 在 AOT 产物下是否可用（5 条并发打慢 mock，
   断言总耗时 ≈ max 而非 sum）。**验不过就走 1b**。
1b. **探针（备选）**：`curl_multi` 不通则验 §2.4 的 worker 协程组合 ——
   `extension=swoole` 加载 + `Coroutine\run()` + `Co\Http\Client` 并发 5 条
   + **协程里调 tpc 编译的类**（这条是硬前提）。**不要开 hook**（走原生协程客户端）。
   验证成本高一个量级，只在 1 失败时启动。
2. **示例**：`apps/users` 增加一个 `FetchDashboardJob`（`curl_multi` 版），
   与现有 `FetchUsersJob`（单请求 curl）并列 —— 两个范式并排，对比才有教学价值。
3. **文档**：`docs/tutorial.md` 的异步节补「什么时候该 `curl_multi`、什么时候该
   `maxWorkers`」的判据（§2.2 那张表）。

★ 这一台阶**不碰 `src/`**，全部在 `apps/` + `docs/`。
它直接回答「同时请求多个网络接口」，且不需要任何并发机制。

### A2 · 让示例台说真话（**零真机**，但要 AOT 重建）

`apps/showcase` 注入 `ProcessTaskHost`（自 spawn `--drift-worker`），
加一页演示「真异步」（`loading` 态可见、连点两次不出错、worker 崩溃只丢一个任务）。

风险不在真机，在**构建**：`showcase.exe` 需要 `--drift-worker` 分支，
且 worker 注册表要与 UI 侧一致。做完要跑一次 AOT + 手工点一次。

★ 替代的更小版本：不改 showcase，只在 `docs/tutorial.md` 明确写
「示例台用同步后端，真异步见 `apps/users`」。这是零成本止损，
但示例台的模板毒性问题**依然在**（新人不会读到那句）。

### A3 · 取消与超时（**有真机风险**）

`TaskHost` 加 `cancel(int $id)` 与 `deadline`：
- 取消：队列里未发的直接丢弃；已发到 worker 的，**当前 worker 无法中断**
  （它是串行 `fgets` + 同步 `run()`）⇒ 现实做法是「**丢弃结果 + 该 worker 标记脏**」，
  或者干脆 `proc_terminate` 掉再补一个新的（进程池的价值就在这里）。
- 超时：由 `ProcessTaskHost::drain()` 侧计时，到点转 `onError`，
  **并且必须让 `pending()` 归零** —— 否则 §4.4 的电池问题还在。

这一台阶要改 `src/`，要真机验证「取消后 UI 不再被回调写入」，
是本轮唯一有真机成分的一件。**按当前授权，可以排到最后，或者等有真实消费者再做。**

## 7. 代价与风险（诚实账）

| 项 | 代价 | 风险 |
|---|---|---|
| `curl_multi` 方案 | 一个 Job 内部复杂度上升（要管 multi handle 生命周期） | **AOT 未验**（§2.3）；验不过则整个 L3 退回多 worker |
| 示例台注入 `ProcessTaskHost` | 示例台多起一个进程（几十 MB 常驻） | AOT 重建 + 手工点一次；`--drift-worker` 分支要在 app 侧写对 |
| `maxWorkers > 1` | N 份 AOT 运行时内存 | 无界起 = 内存炸弹；已有 `maxWorkers` 上限兜住 |
| 取消 / 超时 | 要改 `TaskHost` 契约（`@api` 面扩张） | 真机验证；且「中断在跑的 worker」只能靠杀进程 |

★ 一条不该被忽略的账：**同步后端不是 bug，是基线**。
它保证「换后端语义不变」（结果一律经队列回贴，不在 `submit()` 栈上）。
任何时候都不要为了「看起来快」把它改成直调 —— `SyncTaskHost` 的类注释里
记着 2026-10-18 那次裁决的理由。

这一节的结论被用户纠正过**两次**，两次都是对的。留在这里，因为它比结论本身更有用。

| 轮次 | 用户质疑 | 初稿错在哪 | 改成了什么 |
|---|---|---|---|
| **一** | 「Swoole 的协程呢，这个不会卡 IO」 | 把 **Fiber 与 Swoole 混为一谈** —— 拿「Fiber 不会让出阻塞 IO」去否 Swoole 协程 | 拆成 §1.4（Fiber）与 §1.1–§1.3（Swoole）；承认 Swoole 协程**确实不卡 IO** |
| **二** | 「Swoole 有协程客户端，这个不需要 hook」 | 把「**必须开 hook**」当成唯一路径 | §1.1 补上路径 B（`Co\Http\Client`，零污染）；否决理由从「hook 打坏 `IoPoller`」换成**控制权互斥**（§1.2） |

**结论的最终形态**：

- **UI 进程**：协程仍不可用，但**理由已换过两次** —— 不是「卡 IO」、不是「hook」，
  而是 `Coroutine\run()` 要主线程 + Windows 原生版不提供 `Swoole\Event`（§1.2）；
- **worker 进程**：**可用**，且**不必 hook**，`Co\Http\Client` 就是对的东西（§2.4）。

★ 两次错误的共同形状：**把一个前提当成必要条件，然后整条论断都建在它上面。**
第一次的前提是「协程 = 一种机制」，第二次是「协程 IO = hook」。
两次的单条理由拆开看**都成立** —— 这正是它们难以被发现的原因。

★ 还有一条元教训：**用户两次都只说了半句**（「不会卡 IO」「不需要 hook」），
没有给出方案。而正确反应不是辩护，是**去查「有没有另一种形态」**：
第一次查出了「Fiber ≠ Swoole」，第二次查出了「hook ≠ 协程 IO 的全部」。
**遇到「X 不行」的论断，先问「X 的另一种形态呢」。**

### 11.1 §4.2 补上了：`AsyncValue` + `FutureBuilder`

> **⚠️ 更新（2026-10-31）**：本章起至 §11.x 描述的 `src/Widget/FutureBuilder.php`
> **已删除** —— 它是 `AsyncCommand` 的子集，按"能替代就只留一套"被替换掉
> （见 `ASYNC-DX-2026-10-30.md` §5.1）。`AsyncValue` 也已从"四态互斥"改成
> **状态 × 载荷两维**（载荷可跨状态存活，见同文 §10）。
> 下面这段保留为**当时的推理记录**，不要再照着它写新代码。

§2.1 说 L3 是最容易写错的那一层，当时只给了「应该怎么写」的散文。现在是零件：

| 文件 | 是什么 | 关键约束 |
|---|---|---|
| `src/Async/AsyncValue.php` | 四态值对象（`idle`/`loading`/`data`/`error`），**不可变** | 用 **int 常量**而非 enum —— AOT 下枚举 case 不存在也**不报错** |
| `src/Widget/FutureBuilder.php` | `StatefulWidget`，把 `Future` 订阅成三态 | 三件事必须做对，见下表 |
| `Application::submit()` | 应用侧**唯一**提交入口（`@api`） | 没有后端时返回 `Future::rejected()`，**不抛异常** |

**为什么 `FutureBuilder` 住在 `Widget` 层而不是 `App`**：它只碰 `Future` / `AsyncValue`
两个**纯值类型** —— 不碰 `TaskHost`、不碰泵、不往帧上注册回调。放 `Widget` 层，
页面就能「零依赖地等一个 Future」，不必知道背后是子进程池还是静态数据。
为此给 `DependencyDirection` 的 `Widget` 行补了 `Async`（`Async` 只依赖
`Errors`/`Logging`，比 `Widget` 更低 ⇒ 方向向下、无环）。

`FutureBuilder` 有三个必守点，各自对应一类**只在真机上才看得见**的故障：

| 必守点 | 漏了会怎样 | 怎么做的 |
|---|---|---|
| 卸载后迟到回调要丢弃 | 页面已销毁，回调去 `setState` 一个死 State | `$generation` 自增 + 回调里比对 |
| `didUpdateWidget` 每次都换 builder | 页面每帧 `make()` 新闭包 ⇒ 冻结旧闭包 ⇒ 数据到了画旧内容 | 无条件 `$this->builder = $widget->builder()` |
| 换 `future` 要重置回 `loading` | 刷新时看不到转圈（旧的 data 挂在那儿） | `future !== $old` ⇒ `snapshot = loading` + 重订阅 |

**`AsyncValue` 收掉的是三类静默故障**（手写三态必然会踩到的那三个）：

| 手写时漏了什么 | 症状 | 收口后怎么挡 |
|---|---|---|
| 漏 `setState` | 数据到了界面不动（白屏，但日志一切正常） | 回调里必 `setState` |
| 漏 `catch` | 一次失败打断整条渲染管线（窗口还在、内容没了） | `catch` 落到 `error` 态 + 重试按钮 |
| 漏防陈旧 | 旧页数据覆盖新页（错得最隐蔽） | `generation` 比对，迟到的直接丢 |

### 11.4 超时：这一轮没做，以及它到底缺在哪

§4.4 把超时写成「电池问题」。核实后，它在**进程后端上是正确性问题**：

`ProcessTaskHost` 已有崩溃回收 —— `readReplies()` 发现管道 EOF 就给所有在途任务
`onError`（那条路径的注释写得很清楚）。但 **worker 活着却不返回**时没有任何兜底：

- 管道没断 ⇒ 不走 EOF 那条路；
- `pending()` 永远 `> 0` ⇒ 帧时钟每 15ms 空转（就是 §4.4 的能耗）；
- 页面永远 `loading`，用户除了关窗口没有别的出路。

**为什么不在 `Future` 上加 `.timeout()`**：定时器住在 `PumpHost`（`App` 层），
`Async` 依赖 `App` 立刻成环 —— 这在 `DependencyDirection` 里是硬错误，不是风格问题。

**正确落点是 `ProcessTaskHost`**：每个在途任务记 `submittedAtMs`（**墙钟**
`microtime(true)`，不依赖帧时间 —— 帧在空闲时本来就不跑），`poll()` 里比阈值 ⇒
超时就 kill worker、重拉、给在途任务 `reject()`。

但它有三件必须先裁决的事，都不是能顺手拍的：

1. **超时后「丢弃结果」还是「杀进程」** —— 对**有副作用**的任务（删到一半）哪个更安全？
2. **阈值默认多少**：`FetchRowsJob` 自己设 10s，框架兜底设 30s？谁来配？
3. **一个 worker 上挂着多条任务时**，杀掉它，**别人的任务**怎么交代？

★ 所以本轮的选择是：把 §4.4 改写成这条更具体的形态并留在这里，
**而不是塞一个 `timeout` 参数进去假装解决了**。

### 11.5 接入示例：`AsyncTablePage`

用户要的真实场景（表格数据要走网络、且慢）落在
`apps/showcase/src/Pages/AsyncTablePage.php`，链路：

```
initState() → load(1)
                │
                ├─ $fetch($page)   ← 组合根注入的 \Closure(int): Future
                │                     （背后是 ProcessTaskHost 还是静态数据，页面不知道）
                ▼
           FutureBuilder  ── loading ──> Spinner + 「正在加载第 N 页…」
                          ── error   ──> ErrorPlaceholder + 重试按钮
                          ── data    ──> Table（+ 分页工具条）
```

**两个后端，同一个页面，零改动**：

| 后端 | 什么在慢 | 怎么开 |
|---|---|---|
| `FetchRowsJob::MODE_LOCAL`（默认） | worker 进程里 `usleep(1.2s)` | 什么都不用做 |
| `FetchRowsJob::MODE_HTTP` | 真 `curl` 打 mock（也慢 1.2s） | `php -S 127.0.0.1:8098 tools/app-workers/showcase-mock.php` + `DRIFT_SHOWCASE_HTTP=1` |

★ `local` **不是假异步**：`usleep` 在**子进程**里，UI 线程同帧照跑 60fps。
★ 两种模式共用 `RowsSeed` 的行形状 —— 否则会出现「一边能画表、一边画空白」，
而症状看起来像「异步坏了」（排查方向会完全跑偏）。

**页面为什么只认 `\Closure(int): Future`，不直接拿 `Application`**：
`Widget` 层不许依赖 `App`（分层硬约束）。闭包就是那条边界上的形态 ——
页面说「我要第 N 页」，谁去取、在哪取，是组合根的事。

### 11.7 golden 的一张漏网（本轮补上）

`tools/golden-raster.php` 会**自动发现** `apps/showcase/src/Pages/*.php`，

`AsyncTablePage::__construct(\Closure $fetchRows)` 有 1 个必填参数 ⇒ **它没有任何

**但这个数字本身不包含它** —— 这正是「绿着但少了一张网」。

★ 变异自检（做完就还原）：把 `initState()` 里的 `$this->load(1)` 注释掉 ⇒
