## 0. 结论页（先读这一段）

**短答案：在设计不变量这一层，Drift3 确实更好；但在「已经验证过的工程架构」这一层，
它还不是一套架构，而是一份规格。把兼容性可破坏加回来，不足以让它成为本仓的可选升级。**

| 问法 | 答案 | 依据 |
|---|---|---|
| 设计不变量更干净吗？ | **是**，差距真实 | 四条类型边界是 lint 可判的机械事实；本仓靠注释纪律 + 事后判据，且 `dead-subscription` 对构造器属性提升假绿（S1） |
| 已经验证过的架构更好吗？ | **无法判定** | Drift3 六道闸门 **0/6**、M1–M6 真机 NOT RUN、默认 `NullRenderer` 不出真像素、git 零提交；`Cell` 已删、`src/Core/` 空、`View::buildInto()` 是未追认的工作假设 |
| 扩展性更好吗？ | **分场景，不是一边倒** | 赢在「正确性可机检 / 状态粒度 / 依赖可解释」；输在「加一个字段的书写成本 / 控件组合自由度」 |
| 兼容性可破坏能翻案吗？ | **不能** | 它只免掉「迁移旧调用点」这一项成本；另外三项成本与兼容性无关，见 §7.2 |
| 主推方案要改吗？ | **不改** | 视图模型切片（V0–V3）仍是最小可实施改动，见 §8 |

一句话：**Drift3 的领先来自「先付了一整套类型基础设施的税」，而这套税本身在 Drift3 里
还没验完。兼容性可破坏能降低迁移成本，不能降低验证成本 —— 后者才是这里的主要成本。**

## 1. 先把「架构更好」拆成三个可证伪的问法

前面几轮反复出现「判据全绿但能力是假的」，本轮先把「更好」这个形容词拆开，
否则三个不同层面的答案会互相打架：

| 层 | 问的是 | 怎么证伪 |
|---|---|---|
| **A 设计不变量** | 规则是否由类型/lint 机械保证，而不是靠人记得 | 找出一条「违反它但能编译、能跑、无声」的写法 |
| **B 已验证工程** | 这套规则有没有在真机上跑通 | 找闸门/回归/产物证据；规格文字不算 |
| **C 扩展性单位成本** | 一次典型变更要改几处、几层 | 列 5 个变更场景逐项数 |

三问的答案**不一致**，所以「是否更好」不能一句话回答。下面按 A / B / C 顺序推。

## 3. A 层：Drift3 真实领先的四条，本仓真实领先的三条

### 3.1 领先：类型边界 vs 注释纪律

`22` §2 把隔离写成两栏表（禁止构建签名出现业务实体 / Repository / Store、禁止 UI 内 IO、
禁止 UI 写业务状态、禁止闭包回调），并配 `U-J1`（签名类型白名单）/`U-J2`（代码体零
`use App\Domain\`、零 `curl`/`AsyncRuntime`、零 `fn(`）两条可机检判据，注入 `BizUser`
必须转红。

本仓对应的是**注释纪律**：`UsersPage` 类注释写「页面里任何读 Store 的地方都必须在某个
`select` 之内，否则它就是快照」。这条纪律是对的，但它是给人看的；守它的判据
`dead-subscription` 对构造器属性提升是 0 条（S1，最小仓库对照：提升 0 / 传统 1）。
**规则写在注释里 + 判据空转 = 事实上没有边界。** 这是本仓架构层最实在的欠债，
而且与选哪条订阅路线无关。

### 3.2 领先：一读一写两条单向通道 + 唯一写侧

`22` §3 / `04` §2：读通道 `UI 读 ← 投影 ← 业务`，写通道 `UI 写 → 命令 → 用例 →
业务写 Cell → 下一帧读`，`Cell::set()` 调用点只在编排层，`AsyncRuntime::deliver()`
是唯一回注入口，`(status, revision)` 判变。写侧唯一 ⇒ 「点了没反应 / 数据错乱」有
唯一排查落点。

本仓**部分做到了**：组合根注入 Store、页面零 HTTP（`40` §1.2 第 3 条明写这条
「接线形态值得学」）、`AsyncCommand` / `AsyncValue::fold()` 四态、命令走 `CommandRouter`。
差在：UI 写点没有 lint（`State::markDirty()` 的 `E-FLUSH-CYCLE` 是运行期兜底），
且 `select` 闭包内允许夹带写调用（上一轮补的投影纯度判据就是补这里）。

### 3.3 领先：静默失败零容忍的密度

`22` §10 R1–R10 + `40` §2.3 `U-J1…U-J6`：`match` 无 default、命令差集 lint、
四态无 default、**U-J6 字段集 vs 读取集差集为空**（`40` §1.3 P4 说的「修饰多落点 =
死字段」）、重复命令 id 报错、lint 必须配注入用例。
共同特征写在 `40` §1.3 结尾：**「编译通过、运行无异常、效果就是不生效」要变成编译期可检的差集。**

本仓同款零件其实不少：`dead-command` 双向对账 + selftest 2 条夹具、
`CommandRouter::on()` 重复注册当场 `Errors::report`、`dispatch()` 无人接报 DIAGNOSTIC、
`select-purity` 12 条夹具、`Widget::mutate()/seal()` 的单一守卫。
⇒ **差距不是「有没有」，是「有没有连成一张网」**：Drift3 把这些收进一套
「差集」判据族，本仓是各守一摊。这也解释了为什么 S1 那种洞能一路全绿。

### 3.4 领先：可解释性有静态落点

`dep-table` 的设计目标是 `drift inspect deps` 回答「为什么没更新 / 为什么重组」。
本仓回答同一问题只能打开 `select` 闭包读代码 —— 但反过来说，**闭包本身就是依赖表**，
人能直接看见，不需要额外仪器。这是「显式映射族」的固有便宜，前几轮已确认。

### 3.5 本仓领先的三条（不能只算一边）

| 项 | 本仓 | Drift3 |
|---|---|---|
| 保留模式 Widget 树 | `build(): Widget` + `Element` 树 + `updateChildren` diff + `mutate()/seal()`，控件可任意组合、`children([...])` 一次给全 | `interface View { buildInto(NodeArena, int): int }`，立即模式 + 节点句柄；类注释明写「不能改成 `build(): View`，返回 View 再递归会退化成闭包式递归，违反 N4」 |
| 变更的书写成本 | 加字段改 2 处（Store 方法 + `select` 一行） | 加字段穿 5–6 层，见 §4 |
| 验证体系 | T0/T1/T2 + 25 项 gate + 真机 probe-window，产物可跑 | 0/6 闸门、真机 NOT RUN、默认不出像素 |

★ 第 1 条是**范式差异，不是版本差异**：换过去不是「重构状态层」，是连渲染模型一起换。

## 4. C 层：扩展性按变更场景算「要动几处」

「扩展性」不比口号，比一次典型变更的落点数。

| 变更 | Drift3 目标态 | 本仓现状 | 本仓 + 视图模型切片 |
|---|---|---|---|
| 加一个展示字段 | 实体 → `UserProjection::rows()` → `UserRows::add()` + 平行标量数组 + `idAt()/nameAt()` → `buildUserPage` 形参 → 节点树；**5–6 处**，每处还要过 `U-J1` 白名单 | Store 加读方法 + `select` 加一行：**2 处** | 同左（2 处） |
| 加一条命令 | `const CMD_*` → `UserActions::dispatch()` `match` → `U-J4` 差集 lint → 编排层用例：**4 处**，零容忍 | `Button::command('x')` → `XxxCommands::handle()` `match` → `dead-command` 双向对账：**2–3 处** | 同左 |
| 加一类控件 | 命名类 + `AsyncStateView` 四方法 + 节点 tag + `buildInto` + 标量读取器：重 | `Widget` 子类 + `build()`：轻 | 同左 |
| 状态粒度 | `Cell` 字段级 + `(status, revision)` 判变：天然精确到字段 | `Subject` 粗广播（全量通知）+ 每个 `SubjectBuilder` 自己 `sameValue()` 门控：O(订阅者数) | 整页（更粗，已量化承认） |
| 加一个数据源/后端 | 编排层唯一 IO 点，UI 零感知 | 组合根注入 Store、页面零 HTTP —— **Drift3 自己说这条值得学** | 同左 |
| 依赖可机检 | `U-J1/U-J2` + `dep-table` 差集（设计态） | 注释纪律 + 假绿的 `dead-subscription` | `builder` 里读不到 Store ⇒ 结构性防漏，比判据更强 |

**读数**：Drift3 在「正确性能不能机检」「状态粒度」「依赖可解释」三项赢；本仓在
「变更落点数」「控件组合自由度」两项赢，且差距是 2 处 vs 5–6 处。

**这不是偶然，是刚性的两面。** Drift3 的强来自三件硬约束：类型白名单、零闭包、
全标量 DTO。它们把「写错」变成编译期差集，代价是每个业务字段都要显式穿一层投影。
适合「框架稳定、业务多变、多人协作、出错代价极高」的场景；本仓是「一个应用框架 +
3 个 app + 快速迭代」，落在另一侧。

⇒ **架构评级要分场景给，不能给一个总分。** 用户问的是架构/扩展性，若把权重放在
「出错可检 + 状态粒度」，Drift3 赢；若放在「变更成本 + 迭代速度」，本仓赢。

## 5. ★ 一条此前没评估过的第三形态：生成元数据（`dep-table`）

前几轮把「生成」整族否决了，否决理由是：生成 **PHP trait** ⇒ 开发者要先写
`use XxxView;`，而 trait 还不存在 ⇒ `php -l` / IDE 当场红。这是 PHP 语言边界。

但 Drift3 的 `dep-table` **生成的不是源码**：

```text
tpc --dry → 扫 C++ 生成物里的 php_cell__get(count) → 产出 dep-table.json / .md
```

产物是元数据，不进开发者要写的文件，不需要 `use`，**不受那条否决约束**。
`RESULT.md` 第 12–13 行把这个和解写得很清楚：「编译期订阅不必在编译器里插桩」。
所以它是「生成源码 / 运行期追踪 / 显式映射」之外的**第四族**，本轮必须单独判。

### 5.1 三条判死理由

1. **前提在本仓不成立**。探针靠固定调用 `php_cell__get(count)` 恢复依赖名，前提是
   「状态以**静态类型形参**进入构建函数」（`RESULT.md` 结论 1）。本仓是
   `build(BuildContext $ctx): Widget`，读的是实例属性 `$this->store`，
   生成物里是方法调用 —— 正是 `RESULT.md` 第 39–40 行判为「编译期断裂」、
   「lint 应报 error 而不是静默降级」的形态。要让它成立，得先改所有 `build()` 签名，
   即 §3.5 的范式重写。
   另外探针 `main.php` 里的 `Cell` / `Store` **是探针替身**；`40` §6 明写 `Cell` 已删。
2. **没有失效路由消费者**。`tools/drift` 确实读 `dep-table.json`，但只用来算
   `depSha` 做 **CI 结构漂移门禁**（`depDrift ⇒ E-GOLDEN-DRIFT`）。
   「`Cell → 待重跑构建函数` 的失效路由表」与 `drift inspect deps` 是
   `RESULT.md` 第 44–45 行的**工程建议**，未接线。按 Drift3 自己 `00` §5 纪律 10
   「每加一个组件必须给出谁调用它的可执行路径，否则视为未实现」，
   已实现的是**漂移检测**，自动订阅未实现。
3. **本仓不缺它解的那个问题**。`dep-table` 解「漏订阅」；本仓刚用视图模型切片
   结构性解掉（`builder` 里读不到 Store），成本是 1 处 `src/` 改动 + app 改写。
   用整套 `Cell` + 命名构建函数 + 扫描器换同一收益，是把 3 处改动换成 3 层架构。

⇒ **列为观察项，不实施。** 重启条件写死在 §7.3。

### 5.2 顺带澄清一个容易误引的点

`22` §5 说「业务类型进构建签名 ⇒ `dep-table` 退化成全量重绘」。本仓
`select(static fn(UserStore $s) ...)` 确实把业务类型放进了闭包签名，但本仓
**没有 dep-table**，依赖是显式写出的，不存在「扫描器遇到动态分派」。
这条因果不能拿来给本仓的方案加分或减分 —— 上一轮 §8.2 已记，本轮复核不变。
反过来，`dep-table` 这个名字本身就是刚否决的生成层的另一个马甲，只是产物换成了
元数据；它绕开了 PHP 语言边界，却绕不开「没有消费者」和「前提不成立」。

## 6. ★ 编译器版本差：Drift3 的刚性有多少是旧 tpc 的 workaround

这是本轮最容易被漏掉、也最能改变评级的一条。

Drift3 的 AOT 读数都标着 **tpc 0.10.0**（`40` §2.1 / §9 证据域）。本仓
`AOT-CONSTRAINTS.md` §9.4 的现行台账写的是另一个版本的上游修复
（#183 / #184 / #185 / #186，`bff46481`）：

| Drift3 的约束理由（0.10.0 探针） | 本仓 §9.4 现行结论 | 是否仍成立 |
|---|---|---|
| `40` §3.3「数据放实例字段 1 动 / 11 Var ⇒ 必须走形参」 | typed property→局部、链式/临时对象接收者、`?Obj` 形参**均已解禁**；§9.2 有 `$this->focus->collect()` ⇒ 静态直调证据 | **大概率已不成立**（未对本仓跑同款 A/B，不能断言，需重测） |
| `40` §2.2 第 2 条「接口跳不去虚拟化 ⇒ 命令不用 `CommandHandler` 注册表，用 `match`」 | **单实现 interface 已解禁**（#184）；但 `interface contract` 那一跳、声明不可访问 / 子类覆盖 / `__call` **仍回退动态分派**（§9.4.1 及同文档关于「接口特化只对同文件单实现者」的注记） | **部分仍成立**：本仓 `CommandHandler` 是多实现注册表 ⇒ 这一跳仍动态，Drift3 用 `match` 的理由在本仓依然有效 |
| `00` §4「禁 `?T` 属性 / 可空标量」 | `?Obj` **字段**用「非空 + bool」**不变**（§9.4），`?->` 静默坑仍在 | **仍成立** |
| `40` §2.2 第 1 条 `N4 零闭包` | 闭包相关退化 **#184 已解禁**；§9.4「真实混合联合 / 引用 / 可覆写调用仍保留运行时表示」 | **AOT 理由已削弱**，但 N4 在 Drift3 还有「依赖可收集 / 可枚举」的非 AOT 理由，不能整体推翻 |
| `C-42` 无自定义注解 / codegen 扩展点 | 本仓同族（AOT 未验属性解析），前几轮已确认 | **仍成立** |

**结论**：Drift3 的一部分刚性是**被旧编译器的缺陷逼出来的**，不是架构优越。
本仓的编译器已经跨过其中几道坎。破坏兼容性去照搬这些约束，等于把已解禁的能力
重新锁回去 —— 而且用户的前提一直是「性能后续编译器可优化，不改代码即可享受」，
照搬刚性恰好与该前提相反。

⚠️ 口径纪律（两仓都写死了）：Drift3 `40` §9「绝对 µs 不可跨会话对照，
只有倍率是结构量」；本仓 §9.3「`drift-codegen.php` 走 `lib` 口径，拿它的产物
断言应用性能会看反」。**0.10.0 的 `1 动 / 11 Var` 不能直接当本仓证据。**

## 7. 「兼容性可破坏」的真实作用域

### 7.1 它确实解锁了什么

- 删/改 `SubjectBuilder::select()` / `builder()` 公共签名，不必留兼容层；
- 批量改 7 个文件 23 处订阅点、3 个 Store，不必做双轨灰度；
- 换 `Subject::notifyChanged()` 语义、`CommandRouter` 分派方式、`Widget` 基类契约；
- 重排 `src/` 分层、`api-surface` 台账一次性重写。

这些在「已发布」语境下确实是大成本；现在免费。

### 7.2 它不能解锁的四条（这才是答案）

| # | 成本 | 为什么与兼容性无关 |
|---|---|---|
| 1 | **PHP 语言边界** | 生成 PHP trait 仍需开发者先写 `use`，写的时候 trait 不存在 ⇒ `php -l` 红。用户否决的是语言能力，不是迁移成本。破坏兼容性救不了它（§5 是唯一绕开的形态，但另判死） |
| 2 | **渲染范式** | `build(): Widget` + Element diff vs `buildInto(NodeArena, int): int` + 节点句柄，是两套渲染模型。重写与「旧 API 能不能删」无关 |
| 3 | **验证重做** | 换架构要重跑 T0/T1/T2 + 真机 + C++ 桥接校验；本仓 25 项 gate / probe-window 全绿是长期积累，Drift3 0/6。**主要成本在验证，不在迁移** |
| 4 | **状态原语** | 本仓没有细粒度 `Cell`（`src/State/` 只有 `Subject` / `SubjectBuilder` / `Computed`），`Subject::notifyChanged()` 是全量广播，`UserStore` 注释明写「依赖取整个 Store（粗依赖）」是**有意为之**。要细粒度得从零造一套并给每个字段拆订阅 |

★ 第 4 条带出一个能把整篇串起来的观察：
**粗广播与 dep-table 是同一枚硬币的两面。** 本仓选粗广播 ⇒ 不需要依赖表，
代价是每个切片自己 `sameValue()` 门控、O(订阅者)；Drift3 选细粒度 Cell ⇒
必须有依赖表才能知道哪个 Cell 变了要重跑哪棵子树，而它没落地。
两边各自自洽，不是「先进 vs 落后」。

### 7.3 三档清单

| 档 | 内容 | 裁决 |
|---|---|---|
| **A 该做（与破坏无关）** | V0 修 S1 + 夹具补等价属性写法；V1 `sameList()` 逐元素门控；V2 `UsersPage` 单文件灰度并量重建节点数；V3 `vm-key` + 投影纯度判据 | **不变**，仍是最短路径。破坏兼容性不加速它们 |
| **B 只有「可破坏」才划算，但按用户前提登记不实施** | **细粒度状态原语**：给每个字段一个可订阅槽，`notifyChanged()` 带上槽，Builder 只重算含该槽的切片 ⇒ O(变化字段) 而非 O(订阅者) | 这是**唯一编译器补不了的架构差距**（调用开销能后置，通知粒度不能）。但：① 要重做 `SubjectBuilder::make(Subject)` 的单源契约成多源；② 每个 Store 字段拆槽，apps 3 个 Store 全改；③ 用户前提是「性能后置」⇒ **登记，不做**。重启条件：Store 字段数 > 20 且订阅者 > 20，或 T2 量出粗广播成为帧预算主因 |
| **C 明确不做** | 整套 Drift3 架构（换渲染模型 + 类型白名单 + 零闭包 + 全标量 DTO）；生成 PHP 源码；`dep-table` 自动订阅 | §7.2 三条；`dep-table` 重启条件：本仓引入字段级状态原语 **且** 命名构建函数成为主流 **且** T1 产物能稳定扫出依赖名 —— 三条同时满足才重评 |
