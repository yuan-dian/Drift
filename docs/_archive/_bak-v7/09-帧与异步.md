# 09 帧与异步

> 本册回答：**一帧花在哪、什么时候可以不做、慢活怎么挪走。**

---

## 1. 一帧的五个阶段

```
┌────────────────────────────────────────────────────────────┐
│ ① input    壳已归一化的事件 → 命令 ID                        │  微秒级
│ ② settle   消费 DIRTY_STRUCT，跑命令，清脏位                 │  通常 < 2ms
│ ③ layout   内部两遍：measure(LAYOUT) → place(LAYOUT|PLACE)  │  通常 < 4ms
│ ④ paint    只处理 DIRTY_PAINT 的节点 → op 段                 │  通常 < 3ms
│ ⑤ present  op 流 → 合成(COMPOSE) → 后端 → 像素 → 上屏        │  唯一副作用
└────────────────────────────────────────────────────────────┘
```

★ **仍是五阶段，不是六阶段**：`measure` / `place` 是 ③ 内部的**两遍**，`compose` 是 ⑤ 内部的一步。
I4（一条时间线）不变——变的只是每一遍**各自有独立的脏位与跳过条件**。

★ **五段都有明确的跳过条件，且跳过原因可观测**：

| 阶段 | 跳过条件 | 记录到 FrameStats |
|---|---|---|
| input | 队列空 | `skipped: input(empty)` |
| settle | 无脏位 且 无待处理命令 | `skipped: settle(clean)` |
| layout | 工作集无 `DIRTY_LAYOUT` 且无 `DIRTY_PLACE` | `skipped: layout(clean)`（只 measure 干净、place 仍跑时记 `layout(place-only)`） |
| paint | 工作集无 `DIRTY_PAINT` | `skipped: paint(clean)` |
| present | 不可能跳（除非整帧都跳了） | — |

★★ **"为什么这一帧没重绘"必须能回答**。
Compose/SwiftUI 的更新时机不可观测是它们最大的抱怨；我们的答案就是这行日志。

## 2. 帧预算

以 60Hz 为例：**16.7ms/帧**。分配：

| 用途 | 预算 | 超了怎么办 |
|---|---|---|
| 五阶段（必做） | 12ms | **不能跳**——跳了就是画面错。只能优化 |
| 任务分片（chunk） | 3ms | 下一帧继续 |
| 语义推送 | 0.5ms | 降档（full → delta → coalesce） |
| 清理（缓存/回收） | 0.5ms | 延后 |

★ **必做段不做时间片**：把 layout 切成两半会让中间状态可见（半个界面）。
**只有"可延后"的活才能切片。**

★ **掉帧是可以接受的，"错帧"不可以**：宁可少画一帧，不可画一半。

### 2.1 自适应帧钟

```
FrameClock:
  · 目标间隔由 Surface 的刷新率给出（60/120/144）
  · 连续 3 帧提前完成 ⇒ 允许降频（省电）；持续紧张 ⇒ 保持满帧
  · 请求间隔会被系统量化（Win32 定时器 ~15.6ms 粒度）⇒ 记录"实际间隔"
```

★ **动画相位 = f(帧时间戳)**，时间戳由 `Platform::now()`（单调时钟）注入。
**框架不读环境时钟**——这是确定性的物质基础，也是 golden 可复现的前提。

★ **时间戳只做减法**：`GetTickCount64` 的更新粒度就是系统时钟中断（~15.6ms），
短段会被量化成 0。所以"两帧间隔"必须用相邻两次采样相减，不能假设精度。

## 3. 什么会让 `wantsFrame()` 返回 true

| 原因 | 说明 |
|---|---|
| 有脏位 | 常规重绘 |
| 有动画在跑 | `State::tickFrame(timestamp)` 推进相位 |
| 有任务待处理 | `TaskHost::pending()` |
| **有挂起的 IO** | `Io` 注册表非空 ⇒ `waitEvents` 用 4ms 超时（§4.2） |
| 有滚动动画 | 平滑滚动（若启用） |
| 有 IME 组字中 | 光标闪烁 |

★ **漏一个就是"动画卡住"或"帧钟睡死"**。所以 `wantsFrame()` 是**唯一入口**，
不允许别处直接 `sleep()` 或 `postMessage` 唤醒——一处漏了就是难查的卡顿。

## 4. 异步：先问"你在等什么"

> ⚠️ **本节是重写**。v7 第一版这里是"异步四问"，按**耗时**分档（<1ms / 1–16ms / >16ms 等 IO / >16ms 在算）。
> 那个分法有三个洞：
> ① 档与档会重叠（"HTTP 请求 200ms"既在算又在等，按耗时归不了类）；
> ② "在算"的落点写的是 `Swoole\Thread` —— **上游修复实测只到半效（`class_full` 仍 SIGSEGV），已放弃**；
> ③ 它把"IO 一律主线程非阻塞"当铁律，而那对协议栈不成立。
> 本节按 v6 第 28 轮的重设计改写：**先问"你在等什么"，再选手段。**

### 4.0 更强的不变式：整个进程只有一个线程持有 PHP 运行时

★★ 这比"Fiber 全在主线程"更根本，它是下面所有分类的前提，也是"线程里跑的东西碰不碰 Zend"这条判据的来源。

| 线程里跑什么 | 手段 | 状态 |
|---|---|---|
| **C++ 库**（不碰 Zend） | 自建 `std::thread` / 常驻库宿主 | ✅ **今天可落地，NTS 构建也行** |
| AOT 编译出的 PHP 函数（不碰 Zend） | 自建线程 | ⚠️ 探针成功但脆弱，**框架不提供** |
| PHP 任意代码 · 同进程多线程 | `Swoole\Thread` | ❌ 需 ZTS + 上游 `php::thread_init()` 未落地 |
| PHP 任意代码 · 跨进程 | 子进程池 | ✅ 已实测（`proc_open` + socket） |

★ **判据是"这段编译产物碰不碰 Zend"**，不是"这是不是 PHP 代码"。

★★ 探针铁结论：能不能上线程取决于**调用形态**，不是"PHP 代码能不能上线程"：
自由函数裸线程 `match=YES`，而**纯标量闭包裸线程直接 SIGSEGV(139)**（`php::call()` 碰 EG / request cache）。
应用层无从判断自己那段代码编译成哪种形态 ⇒ **一律禁止**，只留 C++ 库通道。

★ **推论（很重要）**：并发模型**不依赖上游修复**。
`Swoole\Thread` 从"必选路径"降级为"我们不走的支线"，风险表里"等官方修复"不再是阻塞项。
代价：切 NTS 构建则 `Swoole\Thread` 彻底不可用 —— 但我们的设计本来就不用它。

### 4.1 三问：先问等什么，再选手段

```
你在做什么？
  │
  ├─ ① 在算（CPU 时间）
  │    ├─ 有 C++ 库能干 ───────────→ 通道（常驻库宿主；投递**数据**，不投递闭包）
  │    ├─ 能切块 ──────────────────→ chunk（每帧 ≤ 4ms，块间让出，可取消）
  │    └─ 又慢又重、且必须 PHP ────→ 子进程池（常驻，不是每任务 spawn）
  │
  ├─ ② 在等（IO）
  │    ├─ 裸 fd，且一次就绪后处理 ≤ 4ms → 主线程 `Io::await`
  │    └─ 有协议栈（HTTP / TLS / JSON）→ 通道（解析是 CPU 活）
  │
  └─ ③ 稍后做（收尾 / 非关键）
       └────────────────────────────→ defer（帧末空闲期）
```

★★ **两个机械判据**（可被 lint 检查，不需要判断力）：

1. **有没有 C++ 库能干这件事？** 有 ⇒ 通道。
2. **一次就绪之后，处理成本是否 > 4ms？** 是 ⇒ 不能留在主线程。

★ **本方案推翻了一条从 Drift 继承的纪律**："IO 一律主线程非阻塞"。
- 对**裸 fd** 成立：`select(0)` 空转 0.006–0.02ms，每帧 poll 完全可接受。
- 对**协议栈**不成立：HTTP 头解析、TLS 握手、JSON 解码都是 CPU 活，
  主线程 poll 等于"把重活搬回主线程"，只是换了个地方卡。

⇒ **轻量归主线程，协议栈归通道。** 这条判据替代了原来的"是不是 IO"。

★ 探针数据（决定上面的阈值，不是估算）：

| 测什么 | 结果 | 用来定 |
|---|---|---|
| Fiber suspend / resume | 0.04ms / 0.17ms | 切片粒度 4ms 划算（切片开销 < 5%） |
| `select(0)` 空转 | 0.006–0.02ms | 每帧 poll 可接受 |
| `pipe` select | **2.37ms**（≈ socket 的 375 倍） | **不要用 pipe 当事件源** |
| `socket` select | 0.006ms | 用 socket |
| spawn-self | 123.5ms | 子进程池必须常驻，不能每任务 spawn |

### 4.2 `Io::await`：注册与挂起一步完成

```php
// 唯一的 IO 挂起原语。高层 Http / socket / 子进程 drain 全部走它。
Io::await(int $fd, int $events, int $timeoutMs = 0): int;   // 返回就绪事件位
```

```
注册表：map<fd, FIFO list<Fiber*>>   +   反向索引 map<fiberId, fd>
① 调用即"登记 + 让出"，不给"先注册后等待"两步（两步必然有人漏第二步）
② 同一 fd 多个 Fiber 等待 ⇒ 队首唤醒，**不惊群**
③ 摘除三条路径：完成 / 超时 / 取消（三者都要摘，漏一条就是 E-IO-LEAK）
④ 帧首 sweep：反向索引里 Fiber 已死 ⇒ 摘除并记 `E-IO-LEAK`
```

★★ **有挂起时 `waitEvents` 必须带 4ms 超时**（无挂起才 `∞`）。
否则：IO 挂起中的 Fiber 既不算"就绪"也不产生窗口消息 ⇒ 按 §3 的 idle 判据循环会
`waitEvents(∞)` **睡死**。这条是 v6 的 G1（两册机制没合流）暴露出来的真洞。

★ 平台上限：Windows `select` 的 `FD_SETSIZE = 64`。
- 挂起 > 64 ⇒ 报 `E-IO-FDSET`（明确失败，不静默截断）；
- 挂起 > 256 ⇒ **强制走通道**（这是能力判据，不是可调参数）。

★ `pipe` 不要当事件源（2.37ms/次），用 socket pair。这条来自实测，不是偏好。

### 4.3 错误传播树：入口或 `Guard`，二选一

```
Fiber 内未捕获异常
   │
   ├─① 发起处有 Guard（页面 / 列表项）→ 走 Guard 的 fallback，记 E-*
   ├─② 没有 → Owner 的页面级 Guard（ErrorBox）
   ├─③ 还没有 → App::onUncaught
   └─④ 最终兜底 → 帧循环捕获 → 记 fatal + 退出码 4
```

★★ **"每个 `await` 恢复点都 try/catch"是物理上做不到的**（v7 第一版的写法）：
`throw` 发生在**帧循环的 resume 栈**上，那里的 catch 点根本不存在。
所以只能是上面这条树 —— **入口写 Guard，或者交给默认树，二选一**。

★ 这条把三处本来断开的机制接上了：`17-诊断` 的退出码 4、`16-应用分层` 的页面 `Guard`、`09` 的帧循环。

### 4.4 三级取消与超时

| 级 | 状态 | 手段 |
|---|---|---|
| 1 | 未调度 | 直接从队列移除（无成本） |
| 2 | 运行中 | 打"放弃"标记，下一个挂起点收到 `Cancelled` |
| 3 | 已完成 | 结果丢弃 + 记 `I-TASK-CANCELLED` |

★ `await($timeoutMs)` 的超时与取消**不是一回事**：
超时是"我不想再等了"，取消是"这件事不该做了"。
超时抛 `AsyncTimeout`（走 §4.3 的树），**不自动取消任务**——任务可能还有别人在等。

★ 取消不是失败：不记 `Error`、不触发 `Guard`、不弹框（同 [18](18-生命周期与所有权.md) §4）。

### 4.5 帧预算仲裁：`ms:4` 是全局的，不是每任务的

★★ v7 第一版把"每帧 4ms"写成了**每个任务**的配额 ⇒ N 个并发任务 = N × 4ms，直接爆预算且无告警。

正确形状：

```
每帧业务预算 = 4ms（全局剩余计数器）
就绪任务按注册序取，每个实际片长 = min(声明片长, 剩余预算)
每帧最多处理 16 个完成结果（避免"完成风暴"占满一帧）
连续 10 帧预算耗尽 ⇒ W-ASYNC-BUDGET（要能统计，不是只在心里知道）
```

★ 判据：**任何"每 X 毫秒"的配额，都必须问一句"这是每个还是一个"。** 这一条挡掉过两次同类错误。

### 4.6 数据处理：结果只有四形态

| 形态 | 过界方式 | 落点 |
|---|---|---|
| 标量（int/float/string/bool） | 直接返回 | 直接 `set` 进 Cell |
| 大集合（万行） | **句柄（int）** | Cell 存句柄，节点按需取窗口（[04](04-布局.md) §10.6） |
| 二进制（图/字节） | **int 句柄** | 后端槽位（[15](15-资源.md) §4） |
| 流式 | 进度与数据**分离** | 进度 ≥100ms 节流一次 |

★★ **万行不能进 Cell**：Cell 变化会触发所有读者重算，一万行进去 = 一次交互一次全量。
进 Cell 的必须是"句柄 + 计数"，不是数据本身。

四条硬规则：
1. **事务性**：一次异步结果要么全写，要么不写（不能写一半）。
2. **取消后不写**：已取消的任务返回的结果必须丢弃（否则"取消了的导入又回来了"）。
3. **失败不改状态**：失败只进诊断，不动业务状态（否则界面显示"部分成功"的假象）。
4. **背压传导到源头**：pending 满了 ⇒ 降级（暂停投递 / 丢最旧 / 报错），三选一，**不能静默堆积**。

### 4.7 子进程池的最小协议

```
帧格式：4 字节长度前缀 + JSON 体
体：    {"id": 7, "job": "index", "args": {...}}
心跳：  15s 无心跳判死（重启 worker）
上限：  in-flight ≤ 32（超过即背压）
```

★ **必须是常驻 worker**（spawn-self 123.5ms，每任务 spawn 等于把 123ms 加到每次操作上）。
★ 只允许标量 / 数组过界（同 [08](08-平台与能力矩阵.md) §9.6 第 1 条）。

### 4.8 反模式

| 反模式 | 症状 | 正解 |
|---|---|---|
| 把 < 1ms 的活异步化 | 延迟变大、复杂度上升 | 当场做（异步本身有成本） |
| 用 `pipe` 当事件源 | 每次 2.37ms，帧预算被吃掉 | socket pair |
| 万行数据进 Cell | 一次交互一次全量重算 | 句柄 + 计数（§4.6） |
| 每个任务各 4ms | N 并发 = N×4ms，静默爆预算 | 全局剩余计数器（§4.5） |
| 每片写一次进度 | 一帧几十次 Cell 写 | ≥100ms 节流（§4.6） |
| pending 满还继续投递 | 内存涨到崩，且无告警 | 背压三选一（§4.6 规则 4） |
| 在 flush 里 `await` | 帧循环被自己的 flush 挂住 | lint `E-AWAIT-IN-FLUSH` |
| 用 `Swoole\Thread` 做并行 | 需 ZTS + 上游未修；且无崩溃隔离 | 通道 / 子进程池（§4.0） |
| 把 AOT 函数送进裸线程 | 探针"成功"过，但形态一变就 SIGSEGV | 一律禁止（§4.0） |

## 5. 动画

```php
final class Anim
{
    public float $from = 0.0, $to = 0.0;
    public float $startMs = 0.0;
    public int   $durationMs = 200;
    public int   $easing = Easing::OUT_CUBIC;

    public function valueAt(float $nowMs): float;   // ★ 纯函数
}
```

★ **动画是纯函数 `f(时间戳)`，不是"每帧累加"**：
累加会因掉帧而漂移，纯函数不会。掉帧时相位跳过，但终点一定对。

★ **判据是"帧间变化像素数"**，不是"有没有动画对象"：
`FrameStats` 记录每帧变化像素数，连续两帧为 0 ⇒ 说明动画已经结束但还在请求帧（空转）。

## 6. 帧统计（`FrameStats`）

```
Frame #142  16.8ms  (budget 16.7)  ⚠ over
  input    0.02ms
  settle   1.84ms   dirty: struct 3, layout 12, paint 40
  layout   6.21ms   节点 486 / 重排 41
  paint    3.10ms   op 812 (命中缓存 771)
  present  5.60ms   1920x1080 @1.0
  任务      0.00ms
  语义      0.03ms   delta(12)
```

★ **这个格式是设计的一部分**：它让"慢"变成可定位的数字，而不是"感觉卡"。
每次超预算都要能指到**具体阶段 + 具体数字**。

★ `--trace-frame` 可以导出单帧的完整 op 流 + 语义树 + 订阅表（JSON）。
**这是给测试、给 agent、也给人看的同一个产物。**

## 7. 首次启动与退出

| 阶段 | 必须做 | 不能做 |
|---|---|---|
| 启动 | 加载字体、建根节点、首帧全量布局+绘制 | 在启动时做网络/磁盘重活（会白屏） |
| 运行 | 增量 | — |
| 退出 | 保存窗口几何（**用壳侧缓存**，§08 4.1）、flush 待写数据 | 依赖窗口句柄（已死） |

★ **退出路径是最容易漏的分支**：它只在"用户点关闭"时走，
开发时几乎不经过，所以 bug 会一直活到用户手上。
**P1 就要写一个"启动 → 立刻退出"的夹具**，跑 100 次，验证几何每次都存对。
