# 13 决策与风险

> 本册是**问责表**：每条决策写清"否了什么、为什么、什么情况下该推翻"。
> 目的不是记录正确，是**让后来者知道哪里可以改、哪里改了就塌**。

---

## 1. 关键决策

| # | 决策 | 被否方案 | 理由 | 推翻条件 |
|---|---|---|---|---|
| **D1** | 一棵树（无 View / 无 Element / 无 Render） | Flutter 三棵树；WPF 逻辑/视觉双树 | 普通类的类型化属性已是 `Z_LVAL_P(o + offset)`（与 C struct 同量级）⇒ 节点本身就是便宜的固定布局对象，Element 层"隔离廉价配置与昂贵渲染"的收益消失；`runtimeType` 配对**能写但不该写** | 出现"同一份 UI 要在两个渲染后端上复用同一棵树"的强需求（那时才需要中间层） |
| **D2** | 写即置脏（不做 diff / 不做稳定性推断） | React `memo`；Compose 稳定性推断；Vue Proxy | 前两者的代价都是**框架层比较**，成本随树规模增长且位置不明确；写入口比较是 O(1) 且可指到行 | 出现"外部状态直接改对象字段、绕过 setter"的合法场景（那时只能加 diff 兜底） |
| **D3** | **双路径**：常规交互用闭包，可回放路径用命令 ID（int + array） | ① 一律命令 ID（v7 第一版）② 一律闭包（v6） | ① 是重税：每个按钮一个常量 + 一个 switch 分支；② 丢了可序列化 ⇒ 撤销栈/夹具/AI 驱动全没。判据 = **这条交互要不要进"重放即复现"的日志** | 若命令侧退化为"每个控件都不得不写一个常量"，说明判据切错了，应改按"是否跨进程"切 |
| **D4** | `int $kind` + `switch` 分派 | 虚方法覆写 | 静态类型已知时虚方法被编译成直接调用，**静默吞掉子类覆写**（C6）——本项目踩过 | 编译器修好去虚化语义（需实测确认），那时可回到虚方法 |
| **D5** | 19 op 分三层（Core 10 / Extended 4 / Optional 5） | 只做 7 op；一次做全 19 | 跨平台下 Raster 后端不可能全量；分层让"新平台知道底线" | 只剩一个后端时（如只做 Skia），分层退化为无意义的标签 |
| **D6** | `Painter`（PHP 追加 op）与 `Canvas`（后端消费）分离，**一帧一次跨界** | Drift2 的每 op 过桥 | 一帧一次跨界把 N 次 C++ 调用压成 1 次；`CustomPaint` 可随便追加几百 op 不产生桥开销 | 后端需要"流式"绘制（边算边画，不能整帧缓冲）——GPU 直通时可能出现 |
| **D7** | op 段属于节点，`DRAW_CHILD` 是唯一结构 op | 单一全局显示列表 | 全局列表要"重排整段"，局部重绘要 memmove；段属于节点则兄弟节点连 memcpy 都不用 | 树极深（>1000）时引用链过长，那时需要扁平化 |
| **D8** | **布局拆 `measure` / `place`；`offset` 是 `Scroll` 节点字段，只进 `place`** | ① offset 进 `ScrollConstraints`（v7 第一版）② 单方法 `layout()` | "定位是 O(子数) 的加法，重量是 O(子树)"。分离后：滚动只跑 place 链（`DIRTY_PLACE`），`measure` 完全不读 offset ⇒ 尺寸缓存永不因滚动失效 | 若 `place` 里出现了"需要重新量孩子"的需求（如按可用空间换行），说明该逻辑放错了阶段——那属于 `measure` |
| **D9** | 文本度量归自己（读字体表） | 平台 shaper / `SkParagraph` | 三平台三套度量 ⇒ 断行/光标/命中全错，golden 无法跨平台 | 需要 RTL/连字/复杂脚本（阿拉伯语、天城文）——那时必须引 HarfBuzz，且要接受度量分叉 |
| **D10** | **读即订阅**（运行期 `Tracker` 栈） | ① 建树期手写 `subscribe()`（v7 第一版）② Compose 编译期推断 ③ Vue Proxy | 手写方案的唯一防线 `assertTracked` 只在 debug 生效 ⇒ **release 漏订阅仍静默**；读即订阅从根上消灭该错误，且依赖集是**运行期带类型静态数组**，可 dump 可断言 | 若 `Tracker::track()` 在热路径上被证明有可观开销（>1ms/帧），那时改成"构建期生成 getter 的依赖常量" |
| **D11** | 语义 = 扁平快照数组，不加新端口 | 第二棵语义树；独立 `Accessibility` 端口 | 扁平快照同时满足"推"（UIA）与"拉"（NSAccessibility/AT-SPI）；语义天然属于每窗口 | Linux AT-SPI 需要独立事件循环时，可能要单独开一条通道（但仍复用同一快照） |
| **D12** | 能力用 `SupportLevel` 三态 + reason | 返回 `null` / 抛异常 / 布尔 | `null` 表达不了"有但打折"，而跨平台最真实的状态就是这个 | 某能力在所有目标平台都是 Full（如"单调时钟"）——那时不必三态，直接进主接口 |
| **D13** | 列表主路径是数据驱动 `CellSpec` | `Each(items, fn)` 闭包构建器 | 闭包捕获变量不受订阅表管理；不可序列化 ⇒ 不可测试/不可给 agent | 出现"每行结构差异极大"的强需求，那时 `CellBuilder` 对象逃生舱 |
| **D14** | **异步三问（先问等什么）+ 不依赖 `Swoole\Thread`** | ① "真并行必须走 C++"（旧结论）② "用 `Swoole\Thread` 做并行"（v7 第一版） | 上游修复实测**只到半效**（`class_full` 仍 SIGSEGV）；且能不能上线程取决于**调用形态**（纯标量闭包裸线程 139，自由函数裸线程 OK）⇒ 三条路：C++ 库走通道 / 裸 fd 走 `Io::await` / 必须 PHP 走子进程池 | 上游 `php::thread_init()` 真正落地且 ZTS 三平台稳定后，可把"必须 PHP 的多线程"接回来；但**通道与子进程池仍保留**（崩溃隔离是它们的独立价值） |
| **D15** | P0 = 无头管线，先于任何窗口代码 | 先建窗跑通再说 | 90% 的 bug 与窗口无关；无头迭代快 40 倍；golden 需要确定性入口 | 无（这条没有推翻条件） |

## 2. 风险登记

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| **R1** | V1–V8 八个编译器未知数，某个不成立会动摇性能模型 | 中 | 高 | P0 第一周全部实测；每条都已写退路（见 [11](11-编译器约束映射.md) §3） |
| **R2** | 5000 节点的 Native 对象树实际内存/GC 停顿未测 | 中 | 高 | P1 用生成器造 5000 节点压测；不行就降目标到 2000 + 虚拟化 |
| **R3** | 文本自研成本被低估（UAX#14 子集可能不够） | 高 | 中 | 首版明确只做中英文 + 三条断点规则；不够就承认"不支持某语言"，不硬撑 |
| **R4** | 只取 IME 提交串 ⇒ 组字过程框架不可见 | 中 | 中 | 平台原生组字框负责显示（用户看到的是系统画的那个）；风险在"自绘内联组字"场景，首版明确不做 |
| **R5** | macOS/Linux 无障碍成本（NSAccessibility / AT-SPI） | 高 | 中 | 首版只做 Win32；Linux 无障碍标 `Unsupported` 并写进能力矩阵（诚实声明优于假装支持） |
| **R6** | 性能目标全是估算 | 高 | 中 | 所有数字标"待实测"；P1 结束前不改设计，只改预算 |
| **R7** | 命令 ID 不如闭包直观，上手成本高 | 高 | 低 | 常量类 + 命名规范；错误消息打印"命令名"而不是数字 |
| **R8** | 一棵树在"局部高频更新"场景不如分层方案 | 低 | 中 | `LayoutBoundary` + `RepaintBoundary` 已经覆盖；实测不行再加"脏子树隔离" |
| **R9** | 零实现起步，第一个月没有任何可见成果 | 高 | 中 | P0 结束就能"JSON → PNG"，这是可见成果；用它做 demo |
| **R10** | 与 Drift2 并存造成维护分叉 | 中 | 高 | 明确二选一：要么回植 Drift2，要么新仓。**不允许"边改旧边写新"**（见 §4） |

## 3. 分期

| 期 | 交付 | 闸门（不过不进下一期） | 估时 |
|---|---|---|---|
| **P0** | 无头管线 + L1/L2 测试 + lint 8 条 + V1–V9 实测报告 | JSON → PNG 跑通；九个未知数有结论 | 2–3 周 |
| **P1** | 布局 26 节点 + `RasterCanvas` + op golden + 5000 节点压测 | 静态页 < 8ms；golden 稳定 | 3–4 周 |
| **P2** | Win32 壳（8 关注点）+ 首帧上屏 + 拖动 resize + 退出几何 | 真机能开窗、能拖、退出不丢几何 | 3–4 周 |
| **P3** | 文本（度量/整形/编辑/IME/`GLYPH_RUN`） | 中文输入法能打字、候选框位置对 | 4–6 周 |
| **P4** | 输入/焦点/手势/滚动/列表虚拟化 | 滚动条可拖、Tab 可走、拖拽不卡 | 3–4 周 |
| **P5** | 无障碍（UIA 全链路 + 三档推送） | 探针能枚举树 + 焦点事件计数 > 0 | 2–3 周 |
| **P6** | macOS 端口（验证"抽象真的可移植"） | 框架零改动，只写壳 + 适配器 | 3–5 周 |
| **P7** | 性能调优 + Optional op（路径/图像/阴影/图层） | 达到预算表 | 3–4 周 |

★ **MVP = P0–P4（约 15–21 周）**：能跑真应用、能打字、能滚动、能拖动窗口。
**P5 之后才是"产品级"**。

★ **P6 的位置是有意的**：**第二个平台越早接，抽象漏洞越早暴露**。
等 P7 做完再移植，等于拿一整套没验证过的抽象去撞一个新平台。

## 4. 与 Drift2 的关系（必须现在就定）

| 选项 | 含义 | 代价 |
|---|---|---|
| **A. 新仓新写** | Drift2 冻结，只作参考 | 已实现的 26 个能力要重做（但可搬运设计与测试） |
| **B. 回植 Drift2** | 在 Drift2 上按本册重构 | 要边跑边换引擎（飞机空中换发动机） |
| **C. 并存** | 两条线都活 | ❌ **明确否掉**：维护分叉，两边都做不好 |

★ **建议 A**，但**把 Drift2 的真机结论当资产搬运**（那 20 多条坑是花钱买的，见 [00](00-README.md) §4）。
判据：**本册的"一棵树 + 命令 ID + kind 分派"三条与 Drift2 的三棵树 + 闭包 + 虚方法是不兼容的**，
回植等于重写，那不如在新仓里重写（至少不用背着旧结构的包袱）。
