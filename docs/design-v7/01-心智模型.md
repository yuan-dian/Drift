# 01 心智模型

> 本册只回答一个问题：**一棵树怎么同时装下状态、结构、布局、绘制、语义这五件事，而不互相污染？**

---

## 1. 节点是什么

一个节点 = **一个普通 PHP 类**（**不是** `#[Native]`，理由见 §3.1），它有五组字段，对应五件事：

```php
abstract class Node
{
    // ① 身份（结构）
    public int    $kind  = 0;      // 节点类型标签（行为分派靠它，不靠 get_class）
    public string $key   = '';     // 同位置复用锚点
    public int    $id    = 0;      // 帧内唯一序号（调试 / 语义 / 命令目标）

    // ② 脏位（时序）
    public int    $flags = 0;      // STRUCT|LAYOUT|PLACE|COMPOSE|PAINT|SEMANTICS

    // ③ 几何（布局的产出）
    public float  $x = 0.0, $y = 0.0, $w = 0.0, $h = 0.0;

    // ④ 结构（唯一容器）
    public array $children = [];   // ★ packed PHP array（Node 是普通对象，可以进数组）

    // ⑤ 语义（无障碍 / 测试 / agent）
    public string $label = '';
    public int    $role  = 0;
}
```

★ **没有 `?Node $child`**。可空在 TypePHP 里退化成 `php::Var`，热路径不能有（见 L1）。
"没有孩子"= `$children === []`；"没有父"= 用 `parentIndex = -1` 哨兵。

★ **没有 `parent` 指针字段**。反向引用会造环、会被 tracing GC 追（能追，但没必要），
更重要的是：**父指针一旦可写，就会有人绕过 `children()` 改结构**（I3 的唯一入口原则）。

---

## 2. 五个正交面

一棵树，但**每次只沿一个面走**。这是"一棵树"不等于"一坨"的关键：

| 面 | 谁走 | 走法 | 走的结果 |
|---|---|---|---|
| **结构面** | `settle` | 从脏结构节点向下，按位置 + key 配对 | 新孩子列表 |
| **布局面** | `layout` | 约束向下、尺寸向上 | 几何 |
| **绘制面** | `paint` | 前序遍历，产出 op 段 | op 流 |
| **语义面** | `pumpSemantics` | 前序遍历，只取 `role != 0` 的节点 | 扁平快照 |
| **输入面** | `dispatch` | 从命中节点向上找声明者 | 命令 ID |

★ **五个面互不调用**。`layout` 里不能读语义，`paint` 里不能改结构。
违反这一条的后果不是"慢"，而是**帧内状态不确定**——同一份输入两次跑出不同像素，golden 就废了。

## 3. 为什么不是三棵树

Flutter 的三棵树不是设计偏好，是**成本权衡**：

> Widget 便宜（可随意新建丢弃）· RenderObject 贵（持久、有布局状态）
> ⇒ 中间必须有 Element 层做"配对复用"

在 TypePHP 里这个前提**大幅弱化**：

| 事实 | 后果 |
|---|---|
| 普通类的**类型化属性访问已是固定偏移**（`Z_LVAL_P(o + offset)`，官方 `performance.md`：与访问 C struct 几乎一致） | "节点"本身就是便宜的固定布局对象，不需要一个廉价配置层去保护它 |
| 建节点仍要分配 ZendVM 对象（有 refcount / 对象头），改字段不用 | 每帧发生的是**改字段**，建节点只在结构变化时发生 ⇒ Element 层"隔离昂贵渲染"的收益消失 |
| `get_class()` 能用，但热路径上是一次动态查找 | Flutter 的 `canUpdate(runtimeType)` **能写，但不该写**：它把身份判断从整数比较变成类型查找 |

⇒ **一棵树是成本权衡的结论，不是编译器的强制。** 这一点要诚实——
它与 design-v6 的说法不同（v6 称"唯一可行解"），但**结论一致**：一棵树仍然对。

★ **但另有一条是编译器强制的**（见 §3.1）：**`#[Native]` 不能做节点**。那不是取舍。

### 3.1 为什么节点必须是普通 class（这条是强制的）

`#[Native]` 看起来更适合节点（固定字段、属性近 C struct），但**它装不下孩子列表**：

| 事实 | 出处 | 后果 |
|---|---|---|
| Std 容器**不能嵌入原生类属性** | `native-class.md` §属性 | 不能 `private StdVector $children` |
| **普通 PHP array 不能保存 Native Object** | 同上 | 不能 `private array $children` |
| Std 容器赋给属性会被 **`toArray()` 拷贝成 PHP 数组** | design-v6 探针（`probe/p5.php` + `tpc --dry`） | 以为建了持久结构，实际每次赋值都拷贝 |
| Native Object 不能进**普通对象属性** | 同上 | 退一步"用普通类包一层"也不成立 |

⇒ **一个 Native 节点无法拥有孩子。** 四条事实叠加，这是"不可能"，不是"不推荐"。

| 用 `#[Native]` | 不用 |
|---|---|
| `BoxConstraints` / `Color` / `TextStyle` —— 不进数组、不持容器、整帧复用、访问极频繁 | `Node`（要装 children）、`EditState`（要装撤销快照栈）、`Paragraph`（要装行表与字形表） |

★ **判断标准只有一条：它要不要进容器？** 要 ⇒ 普通类。不要 ⇒ 可以 Native，且**先用 profiling 证明值得**。

## 4. 为什么不是 TEA / 不是 MVVM

| 方案 | 好在哪 | 在 TypePHP 里贵在哪 |
|---|---|---|
| **TEA**（Model + Msg + update） | Model 是纯数据 ⇒ 可序列化、可回放、agent 可操作 | 每个交互要定义 Msg 类型 + `update` 分支；TypePHP 无 sealed class / 无模式匹配 ⇒ 分支变 `switch` 长链，样板税翻倍 |
| **MVVM**（ViewModel + 绑定） | 逻辑与视图分离干净 | 绑定靠**字符串路径**解析（WPF 教训：静默失败）或**反射**（TypePHP 没有）⇒ 只能编译期生成，等于自己写个 codegen |
| **TEA 的精华** | **状态机可编程** | 我们用**命令 ID**拿到这一半：`dispatch(1001, ['id' => 7])` 可序列化、可回放、可给 AI 调用 |

★ 结论：**不引入 Msg 类型系统，但保留"可编程"**。
交互 = 一个整数 + 一个数组。整数在编译期就是常量，数组在边界处才存在（不在热路径）。

## 5. 一次变更的完整路径

```
用户点了一个按钮
  │
  ├─[壳] OS 消息 → 归一化 PointerEvent(device, x, y, phase)     ← 唯一翻译点
  │
  ├─[input] 命中测试（走结构面）→ 找到最内层 Node
  │          向上找最近的「命令声明者」→ (commandId = 1001, target = nodeId)
  │
  ├─[settle] dispatch(1001, args)
  │          → 路由表查出方法名 → 执行
  │          → 方法里写字段：$this->count = 5   ← ★ 写入口自动置 DIRTY_PAINT
  │
  ├─[settle 末] 清脏位、结算（flip）
  │
  ├─[layout] 两遍：measure(LAYOUT) → place(LAYOUT|PLACE)（脏集合按深度升序）
  │          ★ 只有 PLACE 脏 ⇒ **跳过 measure，只跑 place 链**（滚动走这条，O(可见孩子数)）
  │          ★ 只有 COMPOSE 脏 ⇒ 连 place 都不跑，只改合成矩阵（O(1)，见 20）
  │
  ├─[paint]  只有 DIRTY_PAINT 的节点重录 op 段；其余段从缓存取
  │
  └─[present] op 流 → 后端 → 像素 → 上屏（唯一副作用）
```

★ **"写即置脏"怎么实现**：字段不是 `public`，而是 `private` + `#[Getter]` + 一个 `set` 方法。
TypePHP 的 Property Hook 支持直接 get/set，但**间接写入不支持**，且 Hook 比普通字段慢；
所以走**显式 setter**（`setText()`），setter 里 `$this->flags |= DIRTY_PAINT`。

代价：写起来比 `$this->text = 'x'` 多几个字符。
收益：**不需要 `equals`、不需要 diff、不需要稳定性推断**——三个最大吐槽源一次消失。

## 6. 节点的生命周期

**七个态，只有 `active` 是稳态**：`create → mount → attach → active → deactivate → detach → dispose`。
完整表（每个态"必须做 / 不能做"）见 [18](18-生命周期与所有权.md) §1 —— 本册不重复它，只记三个必踩点：

| 必踩点 | 后果 |
|---|---|
| **`deactivate` ≠ `detach`**（离树先"暂离"，帧末才"真死"） | 列表移动 = remove + insert，直接 dispose ⇒ **移动一次丢一次状态** |
| **`dispose` 推迟到帧末** | 帧内仍可被后续 settle 复用；释放也集中在一个点，可批量 |
| **`detach` 必须显式 `close()`** | tracing GC 只在两个安全点回收，`unset` 不保证析构 ⇒ **帧间泄漏、几小时后爆** |

## 7. 三条会被违反的纪律（写在这里，是为了能在 review 时引用）

1. **`layout` 里禁止读 `flags` 以外的状态** —— 否则布局不再是 `f(约束)` 的纯函数。
2. **`paint` 里禁止改任何字段** —— 否则一帧内两次 paint 结果不同。
3. **`settle` 之外禁止 `dispatch`** —— 否则一帧内状态被改多次，脏位结算点漂移。

违反第 3 条的现实诱因：**在 paint 里根据可见性触发懒加载**。
正解：懒加载在 `settle` 里按"上次布局的可见范围"触发（滞后一帧，但确定）。
