# 15 资源

> 本册回答：**图片/字体/图标/图层这些东西，谁解码、多大、什么时候放、放不掉会怎样。**
> 来源：v6 §09 全册。v7 第一版完全没有这一册——这是最大的单点缺口。

---

## 0. 一句话

**资源的所有权在 C++，PHP 只持 `int` 槽位；资源的体积由"目标尺寸"决定，不由"源文件"决定。**

两条都反直觉，两条都是血账：

- 第一条反直觉在**不能靠析构**。TypePHP 的 tracing GC 只在两个安全点回收，`unset` 不保证时机
  （Drift2 的 `adoptBoxes()` 就是这件事的前身）。靠析构释放句柄的症状是**帧间泄漏**——每次重建列表漏一点，几小时后爆。
- 第二条反直觉在**一张 4000×3000 的原图不该被完整解码**。列表里 40×40 的缩略图，解码原图 = 48MB，
  按目标尺寸解码 = 25KB，**差 1900 倍**。不这么做，滚动长列表直接 OOM。

## 1. 资源分四类，生命周期不同

| 类 | 例子 | 谁创建 | 何时释放 | 是否进 golden |
|---|---|---|---|---|
| **内建表** | 图标矢量路径、默认字体度量表 | 编译期常量（`const` 表） | **永不释放** | 是（参与 op 哈希） |
| **文件资源** | 字体文件、图片文件 | 运行时按需解码 | 引用计数归零 + 预算淘汰 | 是（走随包 `fonts/` 与 `assets/`） |
| **后端资源** | 纹理、字形图集页、图层缓存 | 后端（`SurfaceProvider` 之后） | 显式 `close()`，帧末统一 | 否（像素 golden 间接覆盖） |
| **平台资源** | 光标、托盘图标、文件句柄 | 平台壳 | 应用退出 | 否 |

★ **只有"内建表"可以进框架核心**。其余三类一律经端口或后端，框架不直接 `fopen` / 不碰系统 API
（见 [08](08-平台与能力矩阵.md) §7）。

★ 判据：**这段资源的存在会不会让 golden 在不同机器上不同？** 会 ⇒ 它必须是内建表或随包分发。

## 2. 图片：三个决定

### 2.1 按目标尺寸解码（v6-R1）

```php
// ✅ 解码时就给目标尺寸
$tex = $surface->decodeImage($bytes, $targetW, $targetH);
```

| 场景 | 源尺寸 | 目标 | 全量解码内存 | 按目标解码 |
|---|---|---|---|---|
| 列表缩略图 | 4000×3000 | 40×40 @2x = 80×80 | 48 MB | **25 KB** |
| 详情页大图 | 4000×3000 | 1200×900 | 48 MB | 4.3 MB |
| 图标 | 512×512 | 24×24 @2x = 48×48 | 1 MB | 9 KB |

★ **`targetW/H` 是"逻辑尺寸 × DPR"**，由布局给出（节点已经知道自己的尺寸），不是图片自己猜。
所以 `Image` 节点的 `measure` 必须先定尺寸、再请求解码——**顺序不能反**。

★ **DPI 变化 = 目标尺寸变化 = 重新解码**。这是 `perMonitorDpi` 能力的直接后果（见 08 C8）：
把窗口拖到另一块屏，所有图片要按新 DPR 重解码。**首版接受这一次重解码**，不做多分辨率缓存。

### 2.2 三态占位，布局尺寸永远按声明值（v6-R2）

```php
final class ImageNode extends Node
{
    private int $declW = 0;         // ★ 声明的逻辑宽（布局用这个，不用解码结果）
    private int $declH = 0;
    private int $state = 0;         // 0=解码中 1=成功 2=失败
    private int $handle = 0;        // C++ 槽位，0 = 无
}
```

★ **布局尺寸永不依赖解码结果**。否则"图片加载完成后布局跳动"——这是所有 UI 框架的共同伤，
而且**它只在慢网/大图上出现**，本地测不出来。

| 状态 | 画什么 | 语义 |
|---|---|---|
| 解码中 | 占位（底色 + 可选骨架） | `role=img`, `name=图片加载中` |
| 成功 | 纹理 | 正常 |
| 失败 | 占位 + 明确的失败标记 | `name=图片加载失败`（**不是静默空白**） |

★ 失败必须**可见**：静默空白会让用户以为是布局 bug，排查从"看图"变成"猜布局"。

### 2.3 字节预算 + LRU + 两层计数（v6-R3）

```
预算（默认 64MB）：
  · 已解码字节总数 > 预算 ⇒ 按 LRU 淘汰**引用计数为 0** 的条目
  · 淘汰后仍超 ⇒ ★ 允许超，记一条 W-RES-OVER-BUDGET 警告，绝不拒绝加载
```

★★ **"绝不拒绝加载"是刻意的**：拒绝加载的后果是"图片不显示"，比内存高**更难查**——
用户看到空白，开发者看到无异常。宁可超预算 + 一条可统计的警告。

★ **两层计数**：
1. **引用计数**（refcount）：多少个节点在用这个纹理。归零才能淘汰。
2. **字节预算**（LRU）：全局字节上限，只管"淘汰顺序"。

只有一层是不够的：只看 refcount ⇒ 已不用但未归零的条目永远占着；只看 LRU ⇒ 会淘汰正在显示的纹理（画面闪白）。

★ 淘汰时机：**帧末**（与 `dispose` 同一个队列，见 [18](18-生命周期与所有权.md) §3）。
不在 `paint` 里淘汰——那会在帧中间把正在用的纹理释放掉。

## 3. 图标：矢量路径表，不是字体也不是位图（v6-R4）

```php
final class Icons
{
    public const SAVE  = 0;
    public const OPEN  = 1;
    // 路径数据是编译期 const 表（归一化到 0..1 的坐标）
    public static function path(int $id): array { /* const 表 */ }
}
```

| 方案 | 改色 | 改尺寸 | 清晰度 | 判据 |
|---|---|---|---|---|
| 图标字体 | 靠文字颜色（能用） | 靠字号（能用） | 好 | 需要"图标当字排版"（如与文字基线对齐） |
| 位图（SVG/PNG） | **不能** | 要备多套 | 取决于资源 | 需要多色/复杂插画 |
| **矢量路径表（本方案）** | **`fill` 颜色即可** | 任意 | 任意 | **图标要跟主题色变** |

★ 判据就是最后一行：**图标要跟主题色变** ⇒ 必须是矢量路径，且路径在框架内、颜色是 op 参数。
位图改不了色（除非做遮罩，那等于多一次合成层，见 [05](05-绘制.md) §9.1）。

★ 路径表用 `const` 数组：**不进 golden 的变量部分**，且 AOT 编译期就能固化。
图标是 op 流里的 `PATH` op（Optional 层），后端不支持时降级为"画一个占位方块 + 语义名"（不是静默不画）。

## 4. 句柄：PHP 只持 `int`，槽位表在 C++（v6-R5）

```
PHP 侧：  $node->handle = 7        ← 一个 int，可进数组、可序列化、可比较
C++ 侧：  g_slots[7] = {tex, refcount=2, generation=3}
```

★ **为什么不用对象/资源句柄**：Native 对象不能进 PHP 数组（v6-L1）⇒ 槽位表必须在 C++。
PHP 侧只留 `int`，这样"节点持有一张纹理"这件事**不违反任何编译期约束**。

★ **tombstone（墓碑）**：槽位释放后**不立即复用**，先标 `dead` 并 `generation++`；
新分配优先用全新槽位，只有槽位耗尽才回收墓碑。
判据：**`(index, generation)` 才是完整句柄**。只用 index 的话，一个过期句柄会静默指到别人的纹理——
症状是"图片串了"，比崩溃难查一百倍。

★ 三层防护，缺一不可：

| 防护 | 挡住什么 |
|---|---|
| `handle = 0` 表示"无" | 空指针 |
| `generation` 校验 | 过期句柄指到复用槽位 |
| `close()` 幂等 | 重复释放（Reconciler 与 Owner 都调一次） |

★ **释放顺序**（与 [18](18-生命周期与所有权.md) §3 一致）：取消 Fiber → 退订 → 释放资源 → 标记节点 dead。
顺序反了 ⇒ Fiber 在资源释放后恢复执行，撞悬空句柄。

## 5. 解码在哪个线程（接 [09](09-帧与异步.md) 的异步三问）

| 资源 | 典型耗时 | 归类 | 做法 |
|---|---|---|---|
| 图标路径表 | 0 | 内建 | 编译期 |
| 小图标纹理（48×48） | < 0.1ms | **当场** | `paint` 前同步解码 |
| 列表缩略图（80×80） | 0.5–2ms | **切片** | 每帧解 2–4 张，超出留到下一帧（`TaskHost` 分片） |
| 大图（1200×900） | 5–40ms | **等 IO / 线程** | 异步解码 → 完成后置 `DIRTY_PAINT` 并**标记需要一帧** |
| 字体文件加载 | 3–20ms | 等 IO | 启动期预加载，运行期不加载 |

★ **异步完成必须能唤醒帧**：解码线程完成后要 `wantsFrame()`（见 [09](09-帧与异步.md) §3），
否则图片解完了但界面不动，直到用户碰一下鼠标。

★ 首版默认 `SyncTaskHost`（全同步，缩略图走切片）；异步解码是 per-app opt-in。
理由：异步引入"同一张图两帧内可能两种状态"，会让 golden 不稳——**先保证可测，再谈流畅**。

## 6. 反模式

| 反模式 | 症状 | 正解 |
|---|---|---|
| 全量解码再缩放 | 滚动长列表 OOM / 卡顿 | 按目标尺寸解码（§2.1） |
| 布局等解码结果 | 图片加载完成后布局跳动 | 布局按声明尺寸（§2.2） |
| 靠析构释放纹理 | 帧间泄漏，几小时后爆 | 显式 `close()` + 帧末队列（§4） |
| 只用 index 当句柄 | 图片串了（显示成别的图） | `(index, generation)`（§4） |
| 预算超了就拒绝加载 | 图片不显示，且无报错 | 允许超 + 警告（§2.3） |
| 图标用位图再染色 | 主题切换后图标颜色不对 | 矢量路径 + `fill` 参数（§3） |
| 在 `paint` 里淘汰纹理 | 帧中间纹理被释放，画面闪白 | 淘汰只在帧末（§2.3） |
