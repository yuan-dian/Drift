## 2. 决策树

```
M3 每阶段耗时  ──┬─ layout < 20%（PHP 侧）⇒ measure/place 收益上限 20% ⇒ 推后
                 └─ layout > 40%（PHP 侧）⇒ **先补 M4**，别直接拆：
                        present > 80% ⇒ 不碰 src/Layout/，转去查 present
                        present < 50% ⇒ measure/place 优先

M1 toObject    ──┬─ > 1.5× 一次动态分派 ⇒ 一棵树比现状更贵，写进 24 册 + 13 册 D1
                 └─ ≤ 1.0× 动态分派    ⇒ 一棵树反而更便宜（现状是 N 次动态分派）

M2 mixed 装箱  ──┬─ > 5× int      ⇒ Cell 分裂优先（1 周见效）
                 └─ ≈ int         ⇒ Cell 分裂降级为"顺手做"
```

**三个数互相独立**，同一批脚本一次测完。

★★ **M3 的分母是"PHP 侧"（`settle + layout + paint`），不含 present。**
M4 已测（[`26`](26-bench-结果.md) §5）：真机端到端 **9.2 ms**，表面链占 **61.2%**、layout 占 **9.5%**。
所以"layout 占 66%"与"该拆布局"之间隔着一次 present 测量 —— 测完的答案是**不拆**。

## 3. 阶段 0：三个微基准（3 天，零代码风险）

### 通用纪律

★★ **必须用 AOT 产物跑**，不能只在 `php.exe` 下测。
解释执行与 AOT 的开销分布不同（项目踩过"解释模式过了不算完"）。

做法：`apps/bench/` 下写三个 `main.php` → `drift-build bench` 编成 exe → `--no-console` → 结果写文件
（无 stdout，见 `11` §5.4）。

★ 每个基准都带**对照组**，且对照组代码形状尽量一致——
否则测的是"代码写得不一样"，不是"机制不一样"。

### M1：`toObject` 的成本（V3）

★★ **这一节的对照组改过一次**（见 [`24`](24-v7-vs-实现.md) §2.2）：
实现的 `RenderFlex::$kids` 与 `Element::$children` 都是**裸 array**，
`foreach` 出来是 `php::Var`，`$kid->layout()` 每次都是**动态方法分派**。
所以"一棵树"要对比的不是类型化引用，而是**一次动态分派**。

```
夹具：5000 个真实 Node（含 children），packed array
A 组：foreach + toObject(Node::class) + 读 $n->w + 静态调用
B 组：foreach + $kid->layout() —— 实现今天的形状（动态分派）
C 组：父持类型化引用 —— 零装箱理想上界（只作信息量，不作判据）
各跑 1000 轮，取中位数
```

**判据只看 `A / B`**：

| `A / B` | 结论 |
|---|---|
| `≤ 1.0` | 一棵树**比现状便宜**（1 次定型换掉 N 次动态分派）⇒ I1 有实测支撑 |
| `1.0 – 1.5` | 同量级 ⇒ 不构成推翻理由，按其它维度（可读性 / 可调试性）决策 |
| `> 1.5` | 遍历成本高于现状 ⇒ **关掉 I1**（`24` 加结论、`13` 的 D1 加推翻条件） |

★ `A / C` 只记录、不作判据：它衡量的是"PHP 层相对 C struct 的差距"，
而**那个差距现在也存在**（现状同样是裸 array + 动态分派）。
拿 `C` 当基线会把"PHP 的固有成本"误判成"一棵树的成本"。

### M2：`mixed` 装箱的成本（`Cell`）

```
夹具：一个 mixed 属性 + 一个 int 属性
A 组：读 mixed 属性 10 万次（⇒ php::Var）
B 组：读 int 属性 10 万次
判据：A / B > 5 ⇒ Cell 分裂优先
```

### M3：每阶段耗时分解

```
在 Frame.php 的三个阶段边界插 hrtime（受 DRIFT_PROFILE=1 控制）
跑 showcase + users 各 300 帧，输出中位数
阶段：flush / layout / paint+record / present
```

★★ **M3 是三个里最重要的**：它直接回答"v7 的增量布局值不值得"。
如果 layout 只占 15%，measure/place 的收益上限就是 15%——而改动是 23 个文件。
**这个数字出来之前，不该动 `src/Layout/`。**

## 4. 阶段 1：按结果分支（1–3 周）

| 分支条件 | 做什么 | 周期 |
|---|---|---|
| **M4 已测：表面链 61.2%**（`toRgba` 30% + `present` 20.5% + `beginFrame` 10.3%） | **不碰 `src/Layout/`**：C 侧直接贴 Skia 表面 / 复用表面 / 直接产 BGRA | 3–5 天 |
| **M1 已测：`toObject` 比动态分派便宜**（0.72–0.83） | 给 Render 层加定型 —— **独立优化，与重写无关** | 2–3 天 |
| **M2 已测：装箱与 int 同阶**（0.89–0.93） | `Cell` 分裂**不做**，除非出现"每帧万次读"的实测热点 | — |
| **都不差** | 壳拆分（`drift_win32.cc` 21 桥 → 9 端口），服务"多端"目标 | 2–3 周 |

★★ **measure/place 先只拆两个容器**，不是 23 个。
滚动是唯一能立刻量出收益的场景；拆完量一次再决定剩下的。
这是"用最小改动验证最大假设"——**拆两个之后滚动帧时间没降，拆 23 个也不会降。**

★ 分支可以叠加：M2 差就做 Cell（1 周），同时 M3 也可能差——
但按 §7 的纪律，**串行做**，一次只动一条线。

## 7. 一条纪律

★★ **一次只动一条线。**

项目踩过"边改旧边写新"（`13` R10）。上面每条线都会碰 `src/`，
两条并行会让"帧时间变了"**归因不清** —— 而阶段 1 的全部价值就是归因。

★ 推论：每个分支做完，**先跑一遍完整量具**（smoke + golden-raster + 真机 probe），再开下一条。
