## 1. M1：`toObject` 不贵，反而更便宜

| 组 | 第 1 次 | 第 2 次 | 含义 |
|---|---|---|---|
| A `toObject` + 静态调用 | 49 ns/节点 | 54 ns/节点 | v7 的形状 |
| B 动态分派 `$v->layout()` | 68 | 65 | **实现的形状** |
| C 父持类型化引用（8 度） | 54 | — | 理想下界（形状不同，只作信息量） |
| D 纯 `foreach` | 12 | — | 迭代本身的成本 |

**净成本**（扣掉迭代）：A = 37 ns，B = 56 ns。

### 1.1 这推翻了什么

[`24`](24-v7-vs-实现.md) §2.2 的原稿说"V3 能推翻一棵树"，后来自我修正为
"V3 只决定要不要显式 `toObject`"。**现在实测把后半句也否掉了**：

- `toObject(Node::class)` 的运行时成本 ≈ **一次动态方法分派的三分之二**；
- 原因已核实（`typephp/src/CompilerBase.php:2618`）：带 `X::class` 的 `toObject`
  被编译器**收窄为 `X`** ⇒ 后续 `$n->w` 是偏移访问、`$n->layout()` 是静态调用；
  代价只剩 `php::toObject($v, ce)` 那一次**类校验**。
- 而动态分派要"取方法名 → 查方法表 → 绑定 → 调用"，比一次类校验贵。

⇒ **`toObject` 不是"为了架构纯净付的税"，它本身就是一条优化。**
实现现在每次 `$kid->layout()` 都在动态分派 —— 那是**没人量过的热点**，
而且它的修法（给 Render 层加定型）**与是否重写无关**。

### 1.2 判据的边界（别过度外推）

- 测的是"**每个孩子每帧调用一次方法**"。真实 layout 里每个孩子要调
  `measure` + `place` + `paint` **三次** ⇒ 1 次定型摊到 3 次调用，v7 的优势只会更大。
- C 组（类型化引用）**没有**比 A 快：54 vs 49。原因是它的形状不同（`layoutAll`
  一次处理 8 个孩子，方法调用与属性读的开销摊在 8 个节点上），且 `foreach` 的
  迭代次数只有 1/8（迭代成本被低估）⇒ **C 只能当"量级参考"，不能当基线**。
- 这只测了**遍历成本**。一棵树的结构复杂度（`adoptBoxes` 协议、加控件改几层）
  一个字都没测 —— 那才是重写的主要代价。

## 2. M2：`Cell` 分裂的收益比预期小一个数量级

| 组 | 第 1 次 | 第 2 次 |
|---|---|---|
| A `mixed`（值 int）+ `toInt()` | 25 ns/读 | — |
| B `int` 直读 | 27 | — |
| C `float` 直读 | 38 | — |
| D `mixed`（值 **string**）+ `toInt()` | 35 | 31 |

`A / B = 0.89 ~ 0.93` ⇒ **统一 `Cell` 与分裂 `Cell` 同价**。
反例 D 是 1.4×A，但绝对差只有 **10 ns/读** —— 一次读多 10ns，一万次读才 0.1ms。

⇒ `Cell` 类型分裂（1 周）**换不到可观测的帧时间**。降级为"顺手做"，
且只在"某个 cell 确实每帧被读上万次"时才值得。

★ **反例自检是必要的**：第一版只有 A/B/C，测出 `A / B = 1.00`。两种解释都成立
（`toInt()` 内联成 tag 检查 / 值恰好是 int 被优化成 int 存储），分不清时判据不成立。
加了 D（值 string）才确认：**开销与值的类型有关，但量级不足以驱动重构**。

## 3. M3：layout 是 PHP 侧大头 —— 但这**不能**推出"该拆布局"

### 3.1 数据

| 夹具 | 节点 | settle | layout | paint(record) | total | layout 占比 |
|---|---|---|---|---|---|---|
| showcase（真实根） | 70 | 0.082 | **0.866** | 0.357 | 1.313 ms | **66.4%** |
| 参数化 20×3 | 83 | 0.072 | 0.460 | 0.317 | 0.854 | 54.2% |
| 参数化 50×8 | 453 | 0.388 | 2.695 | 2.027 | 5.220 | 52.7% |
| 参数化 100×14 | 1503 | 1.271 | 8.813 | 6.681 | 16.866 | 52.6% |

- 每节点 layout ≈ **5.5–6 µs**（showcase 12.4 µs —— 控件更复杂）。
- `settle` 是下界：夹具树是静态的，没有 `setState`。真实交互帧的 settle 会更贵。
- `present` ≈ 0：无头 `RecordingCanvas` 的 `endFrame()` 只是计数，**这一列不可用**。

### 3.2 ★★ 分母的陷阱

`layout 占 66%` 的分母是 **`settle + layout + paint`** —— 这是"PHP 侧可优化部分"。
端到端不是这个分母：

```
端到端一帧（真机 Skia）≈ PHP 侧 1.3ms + Skia 光栅/GPU/present 28.6ms ≈ 29.9ms
⇒ layout 占端到端 ≈ 2.9%
```

如果 29.9ms 这个数成立，**把 layout 从 0.87ms 优化到 0.4ms，只省 1.3% 的帧时间**。

★ 29.9ms 这个数字来自早先的端到端口径实测，**本轮没有复测**（需要窗口）。
所以 §3.2 是**推论**，不是本轮数据 —— 但它足以说明：**不能拿 §3.1 的 66% 直接
决定拆布局**。

★★ **§5 已把这段推翻**：真机实测端到端是 **9.2 ms**（不是 29.9），layout 占 **9.5%**。
推论的方向对、量级错三倍 —— 记在这里是为了让"引用过 29.9 的地方"能追到更正。

### 3.3 这推翻了路线里的判据

[`25`](25-推进路线.md) §2 写的是：

```
M3 layout > 40%  ⇒ measure/place 优先
```

**这条判据缺一个前置条件。** 它默认"PHP 侧 = 端到端"，而真机上 present 可能占
96%。按原判据，本轮会直接进"拆 23 个文件"—— 而收益上限只有 2.9%。

⇒ 判据必须改成"**先量 present**"（见 [`25`](25-推进路线.md) §2 的修正版）。

## 5. M4：真机每帧分解（2026-10-20 已测）

> 量具：`apps/bench` 的 M4（`touch build/m4.on` → `./bench.exe` → `build/bench-m4.txt`）
> 配置：1280×800 逻辑，dpr 1.00，showcase 真实根，300 帧（预热 20），不开消息泵

### 5.1 数据（两次运行）

| 段 | 第 1 次 | 第 2 次 | 占比 |
|---|---|---|---|
| **端到端** | 9.115 ms | 9.357 ms | 100% |
| `beginFrame`（Skia 表面分配 + 清白） | 0.935 | 0.951 | **10.3%** |
| `toRgba`（Skia → PHP 字符串 4 MB） | 2.724 | 2.863 | **30.0%** |
| `present`（swizzle + GDI 贴屏） | 1.919 | 1.911 | **20.5%** |
| 其余（PHP：settle / layout / paint 记录 / pump / focus / semantics） | 3.537 | 3.632 | 38.8% |

### 5.2 ★★ 先更正一个数

`25` §1 与本文 §3.2 都引用过"端到端 29.9 ms"。**在本轮配置下它不成立** —— 实测 9.1–9.4 ms。
29.9 ms 大概是更早的、不同窗口尺寸或不同后端的测量，本轮没有复现。

⇒ §3.2 里"layout 占端到端 2.9%"的**推论作废**，正确的数是 **9.5%**（0.87 / 9.2）。
结论方向不变（layout 不是大头），但量级差三倍 —— 而"差三倍"足以改变优先级判断。

### 5.3 真正的账

```
端到端 9.2 ms
├─ 表面链 5.7 ms（61.2%）  ← beginFrame 0.94 + toRgba 2.86 + present 1.91
└─ PHP 逻辑 3.6 ms（38.8%）← 其中 layout 0.87（9.5%）、settle 0.08、paint 记录 0.36，
                             剩下 ~2.3 ms 是 Skia 绘制调用 + pump + focus + semantics
```

**表面链占六成，而它的全部工作是"把已经画好的像素搬出去"** —— 它一次都没参与绘制。

### 5.4 三个具体修法（按收益排）

| # | 修法 | 省 | 改动面 |
|---|---|---|---|
| 1 | **`drift_skia_present(hwnd, skiaHandle, w, h)`** —— C 侧直接读 Skia 表面贴屏，不让像素进 PHP | **2.86 ms（30%）** | `cpp-src` +1 函数；`Win32SkiaSurface::endFrame()` 少一次 `toRgba` |
| 2 | **Skia 直接产 BGRA**（`kN32_SkColorType` 在 Windows 本就是 BGRA）⇒ `present` 里的逐像素 swizzle 可省 | present 的一部分（≤1.9 ms） | `cpp-src` 一个循环 |
| 3 | **复用 Skia 表面**（尺寸不变就不 new/destroy） | **0.94 ms（10%）** | `Win32SkiaSurface` 一个字段 + 尺寸判断 |

★ 三条互不冲突，合计上限 **5.7 ms ⇒ 端到端 9.2 → 3.5 ms（腰斩）**。

### 5.5 所以：**不拆布局**

- 拆 measure/place：23 个文件，收益上限 = layout 的 **9.5%**，实际能拿到的更少（`place` 也要跑）。
- 修表面链：2–3 个文件，收益 **61%**。

**十倍收益、十分之一改动面。** `25` §4 的判据在这里给出同一个答案，不需要纠结那 51% 落在灰区。

### 5.6 下一步（重排后）

| 顺序 | 做什么 | 依据 |
|---|---|---|
| **1** | **修法 1**：C 侧直接贴 Skia 表面（省 `toRgba`） | §5.4，30% |
| 2 | 修法 3：复用 Skia 表面 | §5.4，10% |
| 3 | 修法 2：Skia 直接产 BGRA | §5.4，≤20% |
| 4 | 修完重跑 M4 验证（应降到 4–5 ms） | §5.4 |
| 5 | 再看 layout 占**新**端到端的比例 —— 那时才决定拆不拆 | — |
| — | `Cell` 分裂：不做（本文 §2） | — |

## 6. 修法 1 + 3 已落地（2026-10-20 续）

`php_drift_win_present_skia(hwnd, canvas)`：C 侧直接读 Skia 表面像素，
BGRA→BGRA **零 swizzle** 纯 memcpy（`kN32` 在 Windows 本就是 BGRA）⇒

## 7. RenderFlex 白排修复（2026-10-20 续）

> 依据：GUI 上游十二轮的同类实测（`layout()` 本就位置无关 ⇒ measure/arrange 改名是
> no-op；真正的债是**第一遍把弹性子树整棵量一遍、结果被第二遍完全覆盖**，实测
> layout 620→310µs，且它从结构上消掉了「非破坏性夹紧」的成因）。

Drift2 的 `RenderFlex::performLayout` 正是旧形态：第一遍连 `flex > 0` 的子节点
一起量（拿无界主轴），而 `$mains` 在第二遍回填、`mainSize` 在第二遍之后才求和
⇒ 第一遍对弹性子的量**零消费者**。showcase 的外层
`Row[导航, Expanded(ScrollView(页))]` 每帧白排整个右栏。

**改法**（一个文件）：第一遍跳过弹性子（**仅主轴有界时**；无界时第二遍不跑，
弹性子仍在这里拿自然尺寸），只累计权重；第二遍照旧按份额重排并回填 `$mains`。

| 段 | 修复前 | 修复后（三次连跑 3.101/3.197/3.120） |
|---|---|---|
| 端到端 | 3.284 ms | **≈3.14 ms（-4~6%）** |
| surface 链 | 0.81 | 0.81（不变） |

★ 收益比 GUI 小：M4 的树（showcase）弹性内容是**轻**演示页；users 那种
`Expanded(右栏 + 长列表)` 的收益应更大（待该应用可离线取数后补测）。

**契约变化**（smoke 同步改）：C4 旧口径"弹性子第一遍拿无界主轴"作废 ——
它的前提（"分母是自然尺寸"）已被 2026-10-17 的分母修复取代。新口径：
弹性子**只在份额定下后量一次**，拿紧主轴。原用例改为断
`firstSeen === lastSeen && maxHeight === 份额`（780→781 全绿）。

**正确性**：selftest 781/0；T1 781/0；showcase 静态渲染 md5 与改前逐像素一致
（`ab1519f5`）；真机滚轮探针：列表页滚 5 下后首项滚出视口、滚动条滑块下移
（滚动路径 = `ScrollView → Column/Each` 全过）。

## 8. ★★ 2026-10-21 复评更正：§6.4 / §7 的"下一步"作废

§6.4 结尾与 §7 结尾都写着"**下一步轮到 `25` §4 判据的 measure/place 分支：
先只拆两个容器（滚动场景）**"。**这条行动项已作废，不要执行。**

理由（完整推导见 [`docs/EVAL-design-v7-2026-10-21.md`](../EVAL-design-v7-2026-10-21.md) §3.1）：

1. `layout()` 本就**位置无关**（`14` §14.1 规则 1）⇒ `measure`/`place` 分离**本身不产生收益**，
   只是把一次遍历拆成两次。
2. 要收益就必须有**尺寸缓存**（place 复用上次 measure）⇒ 需要一整套失效逻辑；
   GUI 上游对同一问题已裁决**布局缓存层不做**（为个位数百分比预算造失效逻辑，不划算）。
3. ⇒ 分离 = no-op、缓存 = 不做 ⇒ **整条线关闭**。

★★ 更硬的一条：D8 的动机（"定位是 O(子数) 的加法，重量是 O(子树)"）**已经被虚拟化达成，而且更彻底** ——
`LazyColumn` + `RenderScrollView` 的 `virtualExtent`/`sliceOrigin` 让不可见孩子**根本没被建**，
比 place-only（仍遍历整棵已建树）少一整层；10000 行单帧 96 ms → 0.2 ms，已有消费者 `BigListPage`。

★ 附带更正 `13` 册 D8 的**推翻条件写错了方向**：它只写"若 `place` 里出现需要重新量孩子的需求"，
真正发生的推翻理由是"**分离本身是 no-op**" —— 后者应补进 D8。

★ 本册不再新增章节；后续结论记入 `docs/EVAL-design-v7-2026-10-21.md` 与 `DESIGN.md` §13.5。
