# 24 v7 与现有实现的对比

> 对象：`design-v7`（24 册 / 5719 行 / 零代码） vs Drift2 实现（198 文件 / 22081 行 + DESIGN 5758 行）。
>
> ★ 本册写于 2026-10-20 上午，册数/行数是**当时的快照**。现在 v7 已是 **27 册 / 6380 行**
> （后续加了 `22`/`23`/`25`/`26`），但下文的对比结论不受影响 —— 新增的都是"补齐"，
> 没有改动本册比较的那四条架构判据。
> 目的：**不是评优劣，是回答"哪条判据该搬、哪条该扔"**。
> 所有对比都指到具体文件/签名，不给印象分。

## 0. 事实对照

| 维度 | Drift2 实现 | design-v7 |
|---|---|---|
| 代码 | **22081 行 / 198 文件** | 0 |
| 设计文档 | DESIGN 5758 + DECISIONS 886 + HISTORY 722 = **7366 行** | 5719 行 / 24 册 |
| 能跑的应用 | **3 个**（hello / showcase / users） | 0 |
| 量具 | smoke（418 探针）/ golden-raster（md5）/ probe-grab（真机像素）/ lint 18 条 | 设计里有，零实现 |
| 布局 | `RenderBox::layout(BoxConstraints): Size` —— **一步，每帧全量** | `measure` + `place` 两步 + 6 脏位增量 |
| 绘制 | `DisplayList` 7 op / 5 槽；**每节点持有**（`RenderText::$list` 缓存） | 19 op 三层 / 8 槽；段属于节点 |
| 命令 | `CommandRouter`：`array<string, CommandHandler>` | `int` + 静态路由表 |
| 共享态 | `Cell::$value` 是 **`mixed`** | 按存储类型分裂成 5 个类 |
| 异步 | `TaskHost` / `SlicedJob` / `ProcessTaskHost` / `Io/` 目录 | 三问判据树 + `Io::await` + 子进程池 |
| 跨平台 | `drift_win32.cc` 21 桥混 8 关注点 | 9 端口 + `SupportLevel` 三态 |

★ **第一个反直觉的结论**：v7 不是"想得更多"，它与实现的设计文档**厚度相当**（5719 vs 7366 行）。
差别在**证据性质**：实现那 7366 行是踩坑后写下的，v7 这 5719 行是推导出来的。
**同样的行数，证据强度差一个数量级。**

★ **第二个**：v7 以为的"净增量"里有三条实现已经做了雏形——
`DisplayList` 就是 op 流且**已经每节点持有**（I5 的"段属于节点"已落地，只是只在 Text/TextField 上用）；
`Platform/{Clipboard,Dialog,Tray}.php` 三个端口**已存在**（`23` 册的设计对象）；
`Commands/` 目录**已有** `CommandRouter` + `CommandHandler` + `CommandArg`。

## 1. v7 相对实现的优点

### 1.1 布局拆两步 —— **最实在的一条**

实现：`RenderBox::layout(BoxConstraints): Size`，`Frame.php` 每帧 `$box->layout()` 全树跑一遍。
v7：`measure(LAYOUT)` → `place(LAYOUT|PLACE)`，滚动只跑 place 链。

**收益可算**：滚动时实现的成本 = O(整棵子树 measure)；v7 = O(可见孩子数) 的加法。
判据是 v7 那句「**定位是 O(子数) 的加法，重量是 O(子树)**」——
这句话实现里没有，而它解释了"为什么滚动不该重排"。

★ 这是唯一一条**既有理论判据、又能量出差距、改动还集中在 `src/Layout/`** 的增量。

### 1.2 6 个脏位（实现是 0 个）

实现里 `grep DIRTY_` 零命中 —— `Frame.php` 每帧无条件 `layout()` + `paint()`。
v7：STRUCT / LAYOUT / PLACE / COMPOSE / PAINT / SEMANTICS。

**收益**：动画分档。`DIRTY_COMPOSE` 只改合成矩阵（~3µs），`DIRTY_LAYOUT` 要重排（~300µs）——
**差 100 倍**，所以"这个动画能不能 60fps"在设计时就能回答。
实现里所有动画只能走"重排 + 重画"那条路。

### 1.3 `Cell` 按类型分裂（实现是 `mixed`）

```php
// 实现
final class Cell { private mixed $value; }
```
`mixed` 在 AOT 下是 `php::Var` ⇒ **每次读一次装箱**。
v7：`IntCell` / `StrCell` / `FloatCell` / `BoolCell` / `ObjCell` + 共享 `trait CellCore`。

**这是全对比里最容易验证的一条**：改一个类，跑一次 profiling，看帧时间。
★ 判据：`Cell` 是热路径（每次读状态都要走它），而实现的 `mixed` 是"能跑但每次多一次装箱"的典型。

### 1.4 命令 ID 是 int（实现是字符串）

实现 `CommandRouter` 用 `array<string, CommandHandler>`：
- 拼错要**运行时**才发现（`'nav.user'` vs `'nav.users'`）；
- 不可序列化 ⇒ 撤销栈 / 回归夹具 / AI 驱动三条路都断（v7 的 I6）；
- 每次派发一次字符串哈希。

v7：int 常量 + 静态路由表 ⇒ 编译期可查、可序列化、O(1) 跳转。
**代价**：每个命令一个常量。实现里命令字符串出现 300+ 处，**改造成本要按实际命令数算**（v7 没算这个数）。

### 1.5 19 op 分三层能力（实现是 7 op 平铺）

实现 `DisplayList` 只有 7 个 opcode（SAVE/RESTORE/TRANSLATE/PUSH_CLIP/POP_CLIP/DRAW_RECT/DRAW_PARAGRAPH）。
v7：Core 10 / Extended 4 / Optional 5，**缺 Core 即启动 Fatal**。

**收益在跨平台**：现在"这个后端支持什么"没有地方表达；
v7 的 `build/capabilities.php` 让它可查询、可断言。
★ 而且"Core 缺一个就 Fatal"这个判据很硬：宁可启动炸，不要跑到一半缺块。

### 1.6 能力三态 `SupportLevel`（实现没有）

v7 的 `FULL / PARTIAL(必带 reason) / UNSUPPORTED`。
实现里"不支持"只有两种表达：抛异常，或返回 null。
**跨平台最真实的状态恰恰是"有但打折"**（托盘在 Linux、无障碍在 AT-SPI），`null` 表达不了。

### 1.7 一棵树：删掉 Element 层

实现：`Widget` → `Element`（`Element.php` / `ProxyElement.php`）→ `RenderObject`（`adoptBoxes()` 协议）。
v7：一棵树，节点自己就是状态 + 行为 + 结构。

**收益**：`Element::adoptBoxes()` 那套"父挂接孩子盒"的协议消失；加一个控件不用改三层。
**代价见 §2.1** —— 这条是双刃的。

### 1.8 五件"框架外的事"有判据了

实现的 `Platform/Dialog.php` / `Tray.php` / `Clipboard.php` 只有端口定义（大概率返回 null/未实现）。
v7 的 `23` 册给了落地姿势：**帧边界进出**（先 present → 阻塞 → 回来重置帧钟）。
这条判据实现里没有，而 Drift2 已经踩过"模态循环挂起 PHP"这个坑（写在 `08` v6-C1）。

## 2. v7 的缺点（诚实版）

### 2.1 ★★ 一棵树的隐藏代价：用户建树成本暴露

实现的三层换来一件事：**用户写 Widget 可以随便 `new`**（Widget 便宜、Element 做配对、Render 持久）。
v7 的模型里**用户写的就是节点** —— 建一个节点 = 分配 Zend 对象 + 改所有字段。

v7 §3 用"普通类属性是 `Z_LVAL_P(o+offset)`"论证"节点不贵"，但它没回答：
**"每帧重建 500 个节点"和"每帧改 500 个节点的字段"差多少？**
实现的 Element 层正是为了让前者便宜（配对复用）。v7 把这条路堵了 ——
用户一旦在 `build()` 里 `new`，就是真的 new。

★ 这不是说 v7 错，而是说：**v7 必须明确"禁止在每帧路径上 new 节点"**，而它现在只说了"结构变化才建节点"，
没说"用户违反时怎么发现"。实现里这条由 Element 配对兜住。

### 2.2 ★★ V3 是**两边都没解决**的问题（原稿此处写错了，已修正）

v7 的孩子遍历是：
```php
$child = $c->toObject(Node::class);   // 每帧每孩子一次定型，之后是静态调用
$child->measure($c);
```

**我原先写"实现是 Element 持类型化引用、零运行时检查"——查代码后确认这是错的。**
事实是：`RenderFlex::$kids` 是**裸 array**（`private array $kids = []`），
`Element::$children` 同样是裸 array，每帧 `foreach` 出来是 `Var`：

```php
foreach ($this->kids as $kid) {     // $kid 是 Var
    $kid->layout($sub);             // ← 动态方法分派，每个孩子每次调用一次
}
```

所以真实对比不是"v7 有开销 / 实现没开销"，而是：

| | 每帧每孩子的开销 |
|---|---|
| **实现** | **N 次动态分派**（`$kid->layout()` 每次查方法表） |
| **v7** | **1 次 `toObject` + N 次静态调用** |

⇒ **V3 的正确问法不是"`toObject` 贵不贵"，而是"它比一次动态分派便宜吗"。**
- 若便宜 ⇒ v7 的遍历**比实现更快**（一次定型摊到 N 次静态调用上）；
- 若不便宜 ⇒ v7 不如实现，但那意味着"定型比查方法表还贵"，不太可能。

★ 机制已核实（`typephp/src/CompilerBase.php:2618`）：`toObject(X::class)` 的返回类型
被编译器**收窄为 `X`**（`resolveClassNameArg($args[0]->value)`）⇒ 拿到的是**静态类型**，
后续 `$child->measure()` 是静态调用、`$child->w` 是偏移访问。
所以 v7 的写法确实"只付一次定型"，代价全在 `php::toObject($v, ce)` 那一次
**运行期类校验**上 —— 这正是 `apps/bench` 的 M1 A 组要量的东西。

★★ **更要紧的推论**：无论 V3 结果如何，**"一棵树 vs 三棵树"的差异都不在遍历成本上**，
在结构复杂度上（要不要 `adoptBoxes` 协议、加控件改几层）。
⇒ **我原稿说"V3 能推翻一棵树"，收回。** V3 只决定"要不要显式 `toObject`"，
它既不支持也不否定一棵树。

★ 这同时说明：实现现在**每次 `$kid->layout()` 都在动态分派**，这可能是一个**没人量过的热点**。
M1 的第一个对照组就是它 —— 如果 A/B 差 2 倍以上，"给 Render 层加定型"本身就是一条独立的优化，
**与是否重写无关**。

★★ **实测结果（2026-10-20，[`26`](26-bench-结果.md) §1）**：`A / B = 0.72 ~ 0.83`
（`toObject` + 静态调用 49–54 ns/节点 vs 动态分派 65–68 ns/节点，扣掉迭代后 37 vs 56）。
⇒ **`toObject` 比一次动态分派便宜约三分之一**，V3 不构成"一棵树"的任何障碍；
反过来说，**实现现在每个孩子一次动态分派，是一处真实可优化点**（修法与重写无关）。

### 2.3 迁移成本被低估

v7 §4 写"已实现的 26 个能力要重做"——实际数字是：
- `src/Widget/` **59 文件 / 5570 行**（全部要重写）
- `src/Text/` **31 文件 / 3604 行**（度量 / 整形 / 编辑 / IME / 确定性字体）
- `src/Layout/` **23 文件 / 2705 行**（全部要重写）

而 v7 的 `06-文本.md` 只有 242 行，**覆盖不了 3604 行的实现细节**。
最典型的是确定性字体：实现有 `DeterministicFontCollection` / `BitmapFontFace` / `CjkGlyphData` /
`font-gen-glyphs.py`（生成位图字形的工具链），v7 的 `06` §3 只说"随包目录、不查系统"。
**这条链重做的风险被完全低估了** —— 没有它，golden 就不能跨机器。

### 2.4 v7 丢失了实现里已经验证过的机制

| 实现里有 | v7 里的对应 |
|---|---|
| `LayoutTolerance::$previewing`（拖动期降级为裁剪） | `08` §4.3 只有 5 行，没给"三处校验点"的具体位置 |
| `Element::findBox(callable)`（穿过包装层找指定类型的盒） | 无（`01` 只说"一棵树"，没提"包装层"这个现实） |
| `probe-grab --mdrag=x1,y1,x2,y2`（客户区拖拽探针） | `12` 只说"真机探针"，没给工具形状 |
| 418 条 smoke 探针 | `12` 说"四层验证"，零条现成 |
| 手势 arena 的 `Tap` 必须居首 | `07` §3 有（✓ 这条搬对了） |

★ 这些不是"设计缺陷"，是"设计的**分辨率**不够"：
v7 停在"该做什么"，实现已经到了"具体哪个函数、哪个像素"。

### 2.5 文档厚度不等于可执行度

7366 行实现文档 vs 5719 行 v7 文档 —— **数量相当，但可执行度差很远**：
- 实现的每节后面都跟着一段"实测结论"或"踩坑记录"；
- v7 的每节后面都跟着一句"否则会怎样"（推导），**没有一条被跑过**。

★ 判据：**"否则会怎样"能说服人，但不能验证。** v7 的 24 册里，
只有 §4「借来的东西」那一张表是实证，其余全是推理。

### 2.6 一棵树的收益在"当前规模"下可能不显著

实现的每帧成本是 **9.2ms（Skia / 1280×800 / 实测）** —— 其中**表面链 61.2%**
（`toRgba` 30% + `present` 20.5% + `beginFrame` 10.3%），layout 只占 **9.5%**。
v7 的增量布局省的是 layout（~300µs 量级），**省 300µs 解决不了 5.7ms 的搬运问题**。
★ 所以 v7 的性能收益**只在"局部高频变化 + 大树"场景成立**（编辑器、表格），
而那正是实现还没做的场景。**在 showcase/users 这个规模上，v7 的性能优势量不出来。**

## 3. 实现的优点（对照着看）

### 3.1 真机结论是资产，且不可复制

`00` §4 列了 20+ 条"花钱买的坑"：退出路径窗口已死、拖动 resize 模态循环、
IME 候选框贴左上角、滚轮取负、滚动条 thumb 必须在派发里先接管、溢出降级……
**这些结论 v7 全搬了，但搬的是结论，不是验证。**
一旦 v7 重写，这些坑会以"新代码里的新形态"再踩一遍（因为触发条件变了）。

### 3.2 三层协议换来了"用户随便 new"

见 §2.1 —— 这是实现最被低估的优点。

### 3.3 量具是现成的

smoke 418 条 / golden-raster / probe-grab / lint 18 条 —— v7 的 P0/P1 要把这些**重做一遍**，
而"重做量具"是最容易做成"量具本身有 bug"的环节（项目里已经踩过：探针统计没对 y 去重 ⇒ 假报 thumb 碎了）。

## 5. 判断

### 5.1 不要现在从零重写

三条理由，按分量排：

1. **证据不对称**：实现的每条判据都咬过人，v7 的每条判据都是推导。重写等于把 22k 行的验证清零。
2. **重写要清零 22k 行的真机验证**，而 v7 的方案里没有一条被真机验证过。
   （原稿这里写"V3 未测且能推翻架构"——见 §2.2 的修正：**V3 不决定树的层数**，只决定要不要显式定型。）
3. **文本系统覆盖不足**：3604 行实现 vs 242 行设计，确定性字体链（含生成工具）没有对应设计。

### 5.2 该搬的四条（按性价比排）

| 顺序 | 搬什么 | 为什么排这个位置 | 改动面 |
|---|---|---|---|
| **①** | **`measure`/`place` 拆分** | 唯一"有理论 + 能量出差距 + 改动集中"的增量 | `src/Layout/`（23 文件） |
| **②** | **`Cell` 类型分裂** | 一个类，跑一次 profiling 就能验证 | `src/State/Cell.php` + 调用点 |
| **③** | **19 op 分层 + `SupportLevel`** | 纯增量，不动现有结构；为跨平台铺路 | `src/Rendering/` + `src/Platform/` |
| **④** | **6 脏位（先加 PLACE/COMPOSE 两位）** | 依赖 ① 落地；先只加位、不做增量，观察成本 | `src/Layout/` + `Frame.php` |

★ ① 和 ④ 必须一起做（`04` 与 `05` 那组"必须一起读"的理由）。
★ ③ 可以独立做，不阻塞任何东西。

### 5.3 该扔的三条

| 扔什么 | 理由 |
|---|---|
| **一棵树**（重写全部 59 个控件） | 收益在"当前规模量不出来"（§2.6），代价是全量重写 + 失去 Element 的"随便 new" |
| **int 命令**（改 300+ 处调用点） | 收益真实，但**要先数命令数**：30 个以内不值得，300 个以上值得。现在没人算过 |
| **读即订阅**（改全部订阅点） | 实现的 `SubscribingWidget` 已能跑；v7 的收益是"消灭漏订阅"，但那是**新代码**的问题，不是存量代码的问题 |

### 5.4 一个被 v7 漏掉的判据

★★ **"每帧能不能 new 节点"必须写成硬规则**（见 §2.1）。
实现里这条由 Element 配对兜住；一棵树的模型里**没有东西兜**。
如果回植一棵树，这条要先写进 `03` 册并配 lint —— 否则用户会在 `build()` 里 new 出 500 个节点，
然后发现"一棵树怎么比三棵树还慢"。

## 6. 一句话

**v7 的价值不在"另一套架构"，在它把实现里"靠经验撑着"的地方换成了"靠判据撑着"** ——
`measure`/`place`、6 脏位、`Cell` 分裂、op 分层这四条是**判据级的增量**；
而"一棵树 / int 命令 / 读即订阅"是**架构级的改动**，收益要么量不出来（§2.6）、要么要先数命令数。
**先搬判据，别急着搬架构。**
