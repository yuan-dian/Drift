# 02 状态与命令

> 本册回答两件事：**状态怎么改才不需要 diff**，**交互怎么表达才不需要闭包**。

---

## 1. 三种状态，三条规则

| 类型 | 载体 | 生命周期 | 改动方式 | 典型用途 |
|---|---|---|---|---|
| **本地态** | 节点自己的 `private` 字段 | 跟节点 | 节点 setter | 展开/折叠、输入框文本、滚动位置 |
| **共享态** | 普通类（如 `AppState`） | 跟应用 | 状态 setter | 当前用户、选中项、筛选条件 |
| **派生态** | `Computed` 对象 | 跟应用 | 只读，惰性 | 过滤后的列表、计数、格式化文本 |

★ **没有第四种**。没有全局可变单例（`global` 在 TypePHP 里会擦除类型 ⇒ L1 违规），
没有隐式上下文（`InheritedWidget` 那种查找式注入要沿祖先链找 + 运行期类型查找，而它天然是"第二棵树"）。

## 2. 写即置脏

### 2.1 字段不是 public

```php
final class TextNode extends Node
{
    private string $text = '';

    #[Getter]                       // 编译期生成 text(): string，零成本
    public function text(): string { return $this->text; }

    public function setText(string $v): void
    {
        if ($this->text === $v) { return; }   // ★ 唯一的"比较"，且是廉价的串比较
        $this->text = $v;
        $this->flags |= Node::DIRTY_LAYOUT | Node::DIRTY_PAINT | Node::DIRTY_SEMANTICS;
    }
}
```

**为什么允许 `=== $v` 这一次比较**：
它不是"diff"，是**写入口的幂等保护**。没有它，每帧重设同一个值会永久置脏 ⇒ 永远重排。
有了它，**重复写同值 = 零成本**，且不需要框架层做任何相等性判断。

★ 这是与 React/Compose 的根本分野：
它们**在框架层比较**（`memo` / 稳定性推断），我们**在写入口比较**（一个字符串比较）。
前者的成本随组件树规模增长，后者恒为 O(1) 且**位置明确**（性能问题永远能指到某一行 setter）。

### 2.2 脏位是位域，一帧只清一次

| 位 | 含义 | 谁消费 | 量级 |
|---|---|---|---|
| `DIRTY_STRUCT` | 孩子列表要重算 | `settle` | 最贵（重建节点 + 配对） |
| `DIRTY_LAYOUT` | 尺寸可能变 ⇒ `measure` + `place` | `measure` 阶段 | ~300µs / 500 节点 |
| `DIRTY_PLACE` | **尺寸不变、只有位置变** ⇒ 只跑 `place` 链 | `place` 阶段 | ~5µs / 可见孩子 |
| `DIRTY_COMPOSE` | **只有变换 / 不透明度变** ⇒ 只改合成矩阵 | 合成 | ~3µs |
| `DIRTY_PAINT` | 自身的 op 段要重录 | `paint` | ~60µs |
| `DIRTY_SEMANTICS` | 语义快照要重建 | `pumpSemantics` | 一次全树遍历 |

★★ **`DIRTY_PLACE` 与 `DIRTY_COMPOSE` 是 v7 第一版漏掉的两级，也是"动画能不能 60fps"的分水岭**：
一个 200ms 的位移动画跑 60 帧 —— 走 `DIRTY_COMPOSE` 约 3µs/帧，走 `DIRTY_LAYOUT` 约 300µs/帧，**差 100 倍**。

★ **蕴含关系**：`DIRTY_LAYOUT` ⇒ 必然也要 `place`；`DIRTY_PLACE` 不蕴含 `LAYOUT`。
`DIRTY_COMPOSE` 是最便宜的一级：**不重排、不重录 op、不光栅**，只改一个矩阵。
★ 这两级不是"优化"，是**让三条不同性质的变化各走各的路**（见 [04](04-布局.md) §1、[05](05-绘制.md) §9.4）。

**时序**（一帧内）：

```
settle  前：flags 累积（可能被多次写）
settle  中：消费 DIRTY_STRUCT（可能产生新的脏）
settle  末：★ 一次性把整棵脏树的 flags 快照成"本帧工作集"，然后清位
measure  ：只处理工作集里的 DIRTY_LAYOUT
place    ：处理 DIRTY_LAYOUT | DIRTY_PLACE（place 是纯加法，几乎总是跑）
paint    ：只处理工作集里的 DIRTY_PAINT
compose  ：只处理工作集里的 DIRTY_COMPOSE（改矩阵，不出新 op）
```

★ **"清位在 settle 末，不在各阶段末"**：因为 `layout` 可能触发新的 `DIRTY_PAINT`（尺寸变了要重画），
若 `paint` 阶段前才清位，这些新脏位会被误清。**清位点必须早于所有消费点，且只有一个。**

### 2.3 脏集合按深度升序

父必须先于子处理（父的约束决定子的输入）。做法：节点维护 `depth` 字段（创建时由父 +1），
脏集合插入时按 `depth` 排序（桶排序，深度通常 < 32）。

Flutter 的 `BuildOwner` 也这么做——这是**唯一被三个主流框架共同验证的调度细节**。

## 3. 共享态：类型化 + 变更日志

### 3.1 状态就是普通类，不是动态 map

```php
final class AppState
{
    public const F_USER   = 0;
    public const F_FILTER = 1;
    public const F_ITEMS  = 2;

    private string $user   = '';
    private string $filter = '';
    private array  $items  = [];

    #[Getter] public function user(): string   { return $this->user; }
    #[Getter] public function filter(): string { return $this->filter; }
    #[Getter] public function items(): array   { return $this->items; }

    public function setFilter(string $v): void
    {
        if ($this->filter === $v) { return; }
        $this->filter = $v;
        StateHub::touch($this, self::F_FILTER);      // ★ 记变更，不扫订阅者
    }
}
```

★ **为什么不是 `Store::get('filter')`**：字符串键 ⇒ 动态查找 + `mixed` 返回 ⇒ 退化 `php::Var`（L1 违规）。
**字段索引是编译期常量**，`touch()` 收到的是 int。

### 3.2 订阅：读即订阅

```php
#[Getter] public function filter(): string
{
    Tracker::track($this, self::F_FILTER);   // ★ 读的时候登记依赖，不手写 subscribe
    return $this->filter;
}
```

`Tracker::$stack` 是**带类型的静态数组**（栈顶 = 当前正在 `settle` 的节点 id）；
`set()` 只置脏、不回调；`settle` 结束时把这一层收集到的依赖集写进 `StateHub`。
一次交互里读同一字段 N 次，只在第一次记一条（按 `(nodeId, field)` 去重）。

| 方案 | 代表 | 代价 |
|---|---|---|
| **读即订阅（运行期栈）** | **本方案**；SolidJS | 每个 getter 一个 `track()` 调用；依赖集在**运行期**生成 ⇒ 可 dump、可断言 |
| 建树期手写 `subscribe()` | v7 第一版（已否） | 要写一行；漏写就是"界面偶尔不刷新"，而且**只有 debug 构建抓得住** |
| 编译期推断 | Compose 稳定性 | 黑盒，跨模块失效，**社区第一性能问题** |
| 运行期 Proxy | Vue | 解构丢响应；TypePHP 无动态属性，压根不可行 |

★ **为什么改掉手写方案**（这是 v7 第一版与本册的实质差异）：
手写 subscribe 的唯一防线是 `assertTracked`，而它只在 debug 构建里生效 ⇒ **release 里漏订阅依然静默**。
读即订阅把"漏订阅"这个错误**从根上消灭**：读过就一定有依赖，不存在第二条路径。
（`assertTracked` 作为可选的自检保留，但不再是正确性的依据。）

★ **它不是黑盒**：`Tracker::$stack` 与依赖表都是带类型的静态数组，
`StateHub::dumpSubscriptions()` 能一行一条打出来（§3.3）。
"自动推断 = 不可观测"这个指控在这里不成立——不成立的原因是**推断发生在运行期、用显式栈，而不是在编译期做类型分析**。

★ 唯一的纪律：**共享态只能在 `settle` 里读**。在 `place` / `paint` 里读会让依赖集漏登记（那时栈已空）
⇒ `Tracker::track()` 在非 settle 期直接 Fatal：`共享态 AppState::F_FILTER 在 paint 阶段被读取`。
这条同时挡住"在绘制里偷偷读状态"——那会让帧内容不再由脏位决定，增量就失效了。

### 3.3 订阅表是一等公民，可 dump

```
StateHub::dumpSubscriptions()   // 谁订阅了谁的哪个字段，一行一条
```

★ 这是对 SwiftUI 黑盒的正面回答：**订阅关系不是编译期推断出来的，是运行期记录下来的，所以能打印**。
★ 这也是对「读即订阅 = 黑盒」这一指控的反驳：黑盒的定义是「看不见依赖边」，而这里有边、有表、有 dump。

## 4. 派生态：版本号 + 惰性

```php
final class VisibleItems
{
    private int $version = -1;      // 上次计算的输入版本
    private array $cache = [];
    private AppState $state;

    public function get(): array
    {
        $v = StateHub::versionOf($this->state, AppState::F_ITEMS)
           ^ StateHub::versionOf($this->state, AppState::F_FILTER);
        if ($v === $this->version) { return $this->cache; }   // ★ 未变不重算
        $this->version = $v;
        $this->cache   = self::compute($this->state);
        return $this->cache;
    }
}
```

版本号用 **XOR 合并**（不是加法）：任一输入变则变，且不需要维护依赖计数。
碰撞概率极低，且碰撞的后果只是"少算一次"——为消除它加一次全量比较反而更贵（Vue `computed` 也是这个取舍）。

## 5. 命令：int + array

> ★ **先澄清一件事：本册不禁止闭包。**
> v7 第一版写的是"交互一律命令 ID"，那是重税 —— 每个按钮都要一个常量 + 一个 `switch` 分支。
> 正确的分工是按**"要不要可回放"**切，不是按"是不是交互"切：

| 路径 | 形态 | 用于 | 可序列化 | 成本 |
|---|---|---|---|---|
| **常规交互** | `->onTap(callable)` | 按钮 / 开关 / 菜单项 / 输入提交 —— **用户速度**（≤10 次/秒） | 否 | 一次动态调用 |
| **可回放路径** | `->command(int, array)` | 菜单、快捷键、AI 驱动、撤销栈、跨进程 worker | 是 | 一次跳转表 |

★ 判据一句话：**这条交互要不要出现在"重放一遍就能复现"的日志里？** 要 ⇒ 命令；不要 ⇒ 闭包。

★ 闭包不进热路径（`layout` / `paint` 里永远不调闭包），所以 `callable` 退化成 `php::Var` 的那点装箱
**不构成问题**。L2 要挡的是"把闭包存进每帧都要读的属性"，不是"用了闭包"。

以下各节讲的是**命令那条路径**。

### 5.1 形状

```php
// 声明（建树时，编译期常量）
$node->command = Command::SAVE;          // int

// 派发（运行时）
$app->dispatch(Command::SAVE, ['force' => true]);
```

| 组成 | 类型 | 为什么 |
|---|---|---|
| 命令 ID | `int` | 编译期常量；可进 `switch`（跳转表）；可序列化；日志一行一个数字 |
| 参数 | `array` | 只在派发边界存在，不进任何属性；**不进热路径** |
| 目标 | 节点 `id`（int） | 允许"同一个命令在不同节点上有不同含义"（如 `DELETE`） |

★ **命令 ID 不是枚举类**：TypePHP 的类常量可以，但枚举（`enum`）在 AOT 下行为未验证（V8）。
用 `final class Command { public const SAVE = 1001; }` —— 纯常量，零运行时。

### 5.2 两条分派路径

| 路径 | 用于 | 机制 | 成本 |
|---|---|---|---|
| **内建 switch** | 框架自带 ~30 种节点 | 一个大 `switch ($node->kind)` 直接调具体类的方法 | 跳转表，零动态分派 |
| **自定义表** | 第三方节点 | `kind => handler 对象`，`$table[$kind]->handle($node, $id, $args)` | 一次数组查找 + 一次动态调用 |

★ **为什么不用虚方法**：类支持覆写，但**静态类型已知时会被编译成直接调用，静默走基类实现**（L3）。
一个"看起来能跑、偶尔不生效"的分派机制是灾难。用 `kind` + `switch`，**分派点是唯一且可读的**。

★ **命令频率是用户速度**（点击、按键、滚动 60/s），不是帧速度。自定义表那点开销可以忽略；
真正每帧跑的是 `measure` / `place` / `paint`，那里不碰命令。

### 5.3 命令路径比闭包多的是什么

| 维度 | 闭包 | 命令 ID |
|---|---|---|
| 序列化 | 不能 | 能（`[1001, {"force":true}]`） |
| 回归测试 | 要跑整个界面 | 喂一串命令即可 |
| 撤销/重做 | 要额外设计 | **命令日志即撤销栈** |
| AI / 自动化 | 要截图理解 | 直接读状态 + 发命令 |
| 跨进程（子进程 worker） | 不能 | 能（JSON Lines） |
| 调用开销 | 一次动态调用（用户速度，可忽略） | 一次跳转表（同样可忽略） |

★★ **中间三条是同一个东西**：命令日志同时是**撤销栈**、**回归夹具**、**AI 驱动脚本**。
这是 TEA 的全部好处，去掉了 Msg 类型系统的样板税。

★ 注意最后一行：**两边开销都可忽略**。选命令不是因为"快"，是因为"可回放"。
v7 第一版把"闭包退化 `php::Var`"当成性能理由，是错位的——那条只对**热路径**成立，而交互不在热路径上。

### 5.4 命令作用域

```
dispatch(id, args)
  │
  ├─ 1. 应用级路由（菜单 / 快捷键 / 全局动作）  ← App::command()
  ├─ 2. 焦点节点链（从焦点节点向上找 handler）
  └─ 3. 目标节点链（从事件命中的节点向上找）
```

★ **优先级顺序固定，且可观测**：`FrameStats` 记录每条命令被哪一层吃掉。
"我按了 Ctrl+S 没反应" 这类问题，答案在日志里，不在猜测里。

### 5.5 命令必须幂等或显式可逆

撤销栈要求"每条命令都能被反向执行"。两条纪律：
1. **命令不得依赖不可回读的隐式状态**（如"当前时间"必须作为参数传入）；
2. 不可逆命令（删除文件、发网络请求）必须显式标 `Command::IRREVERSIBLE`，撤销栈遇到它就清空。

## 6. 一帧内多次写怎么办

```php
public function handleSave(): void
{
    $this->state->setFilter('');       // touch F_FILTER
    $this->state->setUser('alice');    // touch F_USER
    $this->state->setItems($items);    // touch F_ITEMS
}
```

三次 `touch` ⇒ 三个字段的订阅者各置脏 ⇒ **一次 settle 合并处理**。
不存在"三次重绘"，因为置脏只改位域，重绘发生在帧边界。

★ 这就是 Qt `update()` 延迟合并、Vue `nextTick`、React 批处理在做的事。
我们的优势是：**不需要调度器**——脏位天然是累积的，帧边界天然是合并点。

## 7. `Cell` 与 `local`（v6 补齐）

### 7.1 `Cell` 按存储类型分裂（S1）

```php
final class StrCell   { use CellCore; private string $v = '';    }
final class IntCell   { use CellCore; private int    $v = 0;     }
final class FloatCell { use CellCore; private float  $v = 0.0;   }
final class BoolCell  { use CellCore; private bool   $v = false; }
final class ObjCell   { use CellCore; private object $v;         }
```

★ **为什么不一个 `Cell` + `mixed`**：`mixed` ⇒ `Var` ⇒ 每次读一次装箱、每次写一次拆箱。
分裂后读是原生类型（`Z_LVAL_P`）。
★ 五个类共享 `trait CellCore`（版本号、订阅表、`touch`），**只分裂存储，不复制逻辑**。

★ 与 §3 的"类型化状态类 + 字段索引"是**两种粒度，都保留**：
- 应用状态用**一个类 + 多个字段**（`AppState`）：字段索引是编译期常量，一次 `touch` 只脏相关节点。
- 单独可传递的值用 **`Cell`**：能被当参数传、能被放进 `CellSpec`。

★ 判据：**这个值需要被"传递"吗？** 需要 ⇒ `Cell`；只是"某对象的某个属性" ⇒ 字段。

### 7.2 `Computed` 为什么不需要拓扑排序（S2）

★ 因为是**拉取式**：`Computed::get()` 在调用时才检查版本号。
- 推模式（依赖变了就重算）需要拓扑排序保证上游先算，还要处理环。
- 拉模式（用到才算）天然按调用顺序求值，**环会直接栈溢出**（比死循环好查）。

★ 版本号 XOR（§4）保证"输入变则版本变"，所以拉取时能判断缓存是否有效。
**代价是"没人读就不算"**——这正是我们要的（[16](16-应用分层.md) §6 反模式 5）。

### 7.3 `batch`（S3）

```php
StateHub::batch(function () {
    $state->setFilter('');
    $state->setUser('alice');
});
```

★ 与 §6 的"脏位累积"是同一件事的**显式版本**：帧边界天然是合并点，
所以 `batch` 在**帧内**是空操作；它真正的作用域是**帧外**（启动期批量初始化、命令处理里连续写）。

★ 判据：**在一次交互里写了 3 个字段，不需要 `batch`**（帧边界已经合并了）。
需要 `batch` 的只有一种情况：**在 `settle` 之外批量改状态**（那时没有帧边界兜着）。

### 7.4 `local` 判据（S4）

> **写它的时候，需要通知别人吗？** 需要 ⇒ `Cell`；不需要 ⇒ `local`。

★ 一句话挡住最高频的误用（"选中项放 local"）。完整四家判决见 [16](16-应用分层.md) §2。

★ `local` 的机制差异：变化只打自己 + 祖先链的脏位，**不进 `Tracker`、不产生依赖边**。
所以它便宜，但**别处看不见**——这正是它的定义。
