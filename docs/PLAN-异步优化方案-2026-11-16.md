## 0. 一句话结论

`?Obj` 解禁是**真的**，但它对本轮 review 的优化方案**几乎不产生成本变化** ——
因为报告里被它"卡住"的两条方案（声明式资源控件、缓存端口）实际卡点都不是 `?Obj`，
而是**回调 arity**和**架构纪律（Widget 不依赖 App/Async）**。
唯一被解禁实质性改变的是：**报告 §5 把 `?Obj` 列进"不该照搬 SwiftUI phase"的理由是过期的，
已订正**；方案层面新增的只有一条低价值清理项（§4 方案 9）。

**所以：有可优化方案，但驱动力不是 `?Obj` 解禁。** 按收益/成本排序，最值得做的仍是
「加载态→界面声明式收口」和「取消可见性」，这两条与编译器无关，是产品 DX 差距本身。

## 3. 优化方案（按推荐顺序，与编译器解禁无关的部分为主）

### 方案 A · 声明式资源加载收口（对应报告 §4-1）

**问题**：`ImageState` 为一张图写 5 个方法（`initState`/`didUpdateWidget`/`resolve`/`apply`/`handle`），
加上 `SubjectBuilder::select()` + `AsyncValue::fold()` 四支，加载态→界面全是手写接线。

**形态**：一个 `AsyncResourceState` 基类（或 trait，遵守 PITFALLS「能不新建类就不新建」），
统一持有 `AsyncCommand` + `AsyncValue` 四态，把「来源判定 → 缓存命中 → 提交 → 三态 → 诊断」
收进框架；子类只覆写一个 `buildFor(AsyncValue $v): Widget` 或 `applyResource($handle): void`。

**收益**：DX 主战场。业务从「5 方法 + 100 行」降到「1 覆写 ≈ 10 行」。
**成本**：中高 —— 改 `ImageState` 及消费侧 Store/Page，需全套回归 + AOT 双形态。
**风险与判死**：
- ★ 真卡点是**回调 arity**：调用 `buildFor()` 时固定传 1 个 `AsyncValue`，覆写必须完整声明 1 参；
  靠现有 `callback-arity` lint + 判据守，不能只看解释器绿灯。
- `Widget → App/Async` 禁令仍在：`buildFor` 收 `AsyncValue`（State 层）不收 `Future`（Async 层），
  下载仍在 App 层经 `ImageSource` 端口回调，架构例外一条不加。
- 不照搬 SwiftUI 的 `@unknown default` / phase 闭包语法（那是 Swift 编译器特性，PHP 无等价物）。

### 方案 B · 取消可见性：lint 化优先于作用域树（对应报告 §4-2）

**问题**：`Future::cancel()` 沿派生链上溯剪枝，「一根 Future 只能有一个主人」靠纪律，
两处扇出会互相剪掉，且症状静默（另一处不再更新）。

**推荐两步**：
1. **先做 lint（低成本高收益）**：静态判「同一条 `submit()`/`task()` 返回的 Future 被两个
   `AsyncCommand`/`AsyncScope` 持有」→ 当场报。这与既有的 `dispose` 判据同族，改动小。
2. **再做显式批次作用域容器（高成本，择机）**：给 `AsyncScope` 外再加一层
   `CancelGroup`，让「同批任务的取消」有确定边界，替代"复用结果不复用 Future"的口传纪律。

**收益**：把本仓**唯一一处「纪律靠人」的取消风险**变成可观测或结构化。
**成本**：lint 低、容器高。**判死**：容器不要动 Fiber 语义（用户态跨帧、无父子 Job 树），
只建在 `AsyncScope`/`AsyncCommand` 层；否则会引入 Kotlin 式作用域树与现有调度器打架。

### 方案 C · 图片缓存两级防线（对应报告 §4-3）

**问题**：`ImageLoader::$cache` 只增不减；2048 单图上限挡住单图 OOM，挡不住同屏 N 张累积。
**形态**：给内存缓存加条目数/字节上限 + LRU 淘汰，与单图 2048 上限形成两级防线。
**收益**：中（真机内存稳定性）。**成本**：中（纯 PHP 数组，无 AOT 风险）。
**判死**：淘汰策略要有判据（第二次加载同一张不应重新解码）、与 `cacheKey` 保持一致。

### 方案 D · `asset()` 加可选 `cacheKey()`（对应报告 §4-4）

**问题**：`md5(url)` 对签名 URL / 带 token 的 URL 每次 miss（Flutter `cached_network_image`
用独立 `cacheKey` 正对此）。
**形态**：`asset($src)->cacheKey($stableKey)`，key 进 `FIELDS` 传给 worker，
`FetchImageJob::cachePath()` 优先用它；不给时仍用 url。
**收益**：中（签名 URL 场景）。**成本**：中（改 FIELDS 契约，UI/worker 两侧算法须一致，
由 `NamedJobContractTest` 守）。**判死**：`cachePath()` 算法两侧共用一份，不能各算一遍。

### 方案 E · 来源解析器注册表（对应报告 §4-5）

**问题**：`ImageLoader::classify()` 是封闭 if 链，加 `data:`/`blob:` 要改框架核心。
**形态**：升级为来源解析器注册表，内置 local/network/reject 三项为默认注册项，
允许注入新 scheme 的 resolver。
**收益**：中（扩展性，对齐 Flutter `ImageProvider`）。**成本**：中。
**★ 解禁相关边界**：单实现 interface 形参已解禁（静态直调有利），
但**注册表是多实现查表，那一跳仍动态分派**（#184 明确"interface contract 多实现跳仍动态"，
这是设计不是缺陷）。⇒ 性能上不吃亏（本来就要查表），但别指望它变静态直调。

### 方案 F/G/H · 低优先级（对应报告 §4-6/7/8）

可选 placeholder/errorBuilder、NamedJob 业务 code 命名空间、进度一等流 —— 均维持报告判断，
本轮不展开。**其中进度一等流**：短期靠 `await($future, $onProgress)` 收口已够用，
`?Obj` 解禁不改变其成本。

### 方案 9 · 过期注释清理（解禁**唯一**新增项，低价值）

`docs/REVIEW-异步DX对照成熟GUI-2026-11-16.md` 已订正三处过期 `?Obj` 引用（本轮完成）。
`PITFALLS.md` 顶条前半句过期、后半句结论对字段层仍成立 —— 该文件是 append-only 战史全文，
本轮**不动**，以 `AOT-CONSTRAINTS.md` §2.2/§9 为现行口径。
源码注释里凡写「AOT 下 `?Obj` 退化」且指的是**形参/返回值**的，理论上可清理，
但扫描未发现异步面有此类误导性注释（`Image`/`RenderImage` 的占位理由属字段层，成立）。

## 6. 落地裁决（2026-11-16 同日，已实现）

上面是"方案分析"，本节是"实际动手时的裁决" —— 逐条多维复核后推翻了两项推荐的具体形态。

### 6.1 方案 B：推翻"lint 化"，落地"运行时扇出诊断"（**已实现**）

**推翻理由**：lint 是构建期静态文本分析，追踪不了"两个闭包在运行时返回同一个 Future 对象"。
把 lint 规则写进 `tools/Lint/Rules/` 无法命中这个模式 —— 它不是源码形状问题，是对象图问题。

**风险实测**（`Future::pending()` 两根 + 两处 `then()`，取消一处）：
```
取消 A 后：后端钩子 stopped=1, root.cancelled=yes, b.cancelled=no
结算 root 后：a.done=no, b.done=no        ← B 既不 cancelled 也不 done，永久静默
```
证明"一处取消剪掉另一处"真实、且另一处消费者毫不知情。

**落地形态**：`Future::cancel()` 在被取消节点检测 `links > 1`（>1 条独立派生链 =
一根多主的可靠信号），报 `Diagnostics::degraded('future/fanout-cancel')`。
- 零误报依据：合法接线根恒为 1 条链 —— `then()->catch()` 串行成 1 条、
  `all()/race()` 给每条入参只挂 1 条、进度订阅走 `progressSinks` 不计入 links。
- 改诊断不改语义：后端停活是刚需，取消仍沿链上溯剪枝，只把静默剪枝变红。
- **借鉴 Kotlin**：取消要有明确归属；**排坑**：不建父子 Job 树（会与 Fiber 跨帧调度打架）。
- 判据：`tests/Unit/Async/FutureTest.php` 的 `testFanoutCancelIsReported` +
  `testSingleChainCancelDoesNotReportFanout`；变异自检（去掉诊断）前者立刻变红。

### 6.2 方案 A：否决"声明式资源基类"（**不实现**）

**否决理由**（结构与 DX 多维复核）：
1. **描述失实**：方案假设 `ImageState` 里有 `AsyncValue::fold()` 四态样板。实际 `ImageState`
   是回调式 `fetch(url, width, onReady)` + 一个 `handle` 字段 + `apply()` 换 handle，
   根本没有四态 fold。全仓 `->fold(` 零命中（四态穷尽写法在页面层 `bodyOf()`，不在资源控件）。
2. **负优化**：`AsyncValue::fold()` 缺一支当场抛，是本仓**优于** RTK Query 四布尔的设计
   （review §2.3、§3）。把它改成"可覆写的 `buildFor(AsyncValue)`"会把编译期穷尽
   退化成运行期漏态 —— 用优势换样板，方向反了。
3. **YAGNI**：全仓 `ImageSource` 只有 `Image` 一个消费者，没有第二个异步资源控件要收口。
   为单一用例建基类是过早抽象。
4. **业务 DX 已领先**：`Image::make()->asset($url)` 一行拿到下载 + 双层缓存 + 三态，
   比 Flutter/SwiftUI 都省（review §2.4），没有"用户写代码多"的痛点要解决。

**结论**：A 的核心痛点（页面层四态接线）不在资源控件层，且现有 `fold()` 已是最优解。
保留现状，不建基类。
