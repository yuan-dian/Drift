# 18 诊断与错误边界

> 本册回答：**"为什么没刷新"和"为什么慢"怎么答；一个节点坏了怎么不拖垮整页；出问题怎么被自动化区分。**
> 来源：v6 §08 §4 + Drift2 的真机坑。v7 第一版只有 `FrameStats`——它只答"哪帧慢"，**不答"谁改的"**。

---

## 0. 一句话

**诊断要能回答三个不同的问题，而它们需要三套不同的数据结构，不能混。**

| 问题 | 数据结构 | 时机 |
|---|---|---|
| **谁改的**（为什么没刷新 / 为什么刷新了） | **写入链**（D1） | 每次写状态 |
| **哪帧慢** | `FrameStats`（[09](09-帧与异步.md) §5） | 每帧一次 |
| **崩之前发生了什么** | 环形缓冲（D2） | 常开 + dev |

★ 把三者塞进一个日志，后果是**一次滚动就把崩溃前的诊断冲掉**。这不是理论——环形缓冲的大小是固定的。

---

## 1. 写入链（D1）

```
#42.color ← binding#7 ← Cell#3.set ← event#881(pointerDown)
```

| 段 | 含义 |
|---|---|
| `#42.color` | 哪个节点的哪个字段被置脏 |
| `binding#7` | 该节点是第 7 个绑定到这条状态的读者 |
| `Cell#3.set` | 哪个共享态被写 |
| `event#881(pointerDown)` | 触发这次写的**根事件** |

★★ **这是"为什么没刷新"的唯一答案**。没有它，你只能猜；有了它，答案是**一行可读的链**。

★ **实现方式是"一帧一个写者栈"，不是全局历史**：
`settle` 开始时压一个栈帧，每次 `Cell::set` 压一条记录，`settle` 结束时把整棵树读到的
依赖集与写记录一起快照成 `FrameStats` 的一部分。**只保留本帧**——上一帧的写入链几乎永远用不上。

★ **置脏也要记**：链的第二段是关键。用户问的往往是"我明明改了，为什么这块没变"，
答案是"这块没绑定到那条状态"——**没有 `binding#7` 这一段，就答不了**。

★ 与 [02](02-状态与命令.md) §3.2 的读即订阅是同一个机制的两面：
`Tracker` 记"谁读了"，写入链记"谁写了"。两边都是带类型的静态数组，都能 dump。

## 2. 两条环形缓冲，分开（D2）

| 缓冲 | 容量 | 何时开 | 内容 | 用途 |
|---|---|---|---|---|
| `diagRing` | 256 条 | **常开** | 警告/错误 + code + 节点路径 | 崩溃后回溯 |
| `traceRing` | 每节点 8 条 | dev（`--trace`） | 该节点的写入/脏位/绘制摘要 | 定位单个控件 |

★ **分开的理由**：`traceRing` 的量是节点数 × 8（5000 节点 = 4 万条），常开不可能；
而 `diagRing` 必须常开，否则**线上出了问题没有现场**。

★ **`traceRing` 按节点分片**，不是全局环形：查"这个输入框为什么闪"时，要的是它自己的历史，
不是"最近 8 条全局事件"（那大概率是别的节点的滚动）。

## 3. 帧内不写盘（D3）

```
paint/present 期间：只入队（grow-only array，预分配）
帧末（present 之后）：把队列移交给写线程 / 空闲期批量 fwrite
```

★ **一次 `fwrite` 是 1–20ms**。在 16.7ms 的预算里，一次日志就能把 60fps 打到 30fps——
而且症状是"偶发卡顿"，最难查。

★ 判据：**任何在帧内可能阻塞的系统调用都是禁止的**（文件、网络、锁、`OutputDebugString` 大量输出）。
这条与 [05](05-绘制.md) §9.5 第 4 条的"帧内不分配"是同一族纪律。

★ **崩溃时例外**：`fatal` 路径允许同步写盘（那时已经没有下一帧了），
但必须先 `fflush` 已入队的诊断，**否则崩溃前的最后几条全丢**——而那几条恰恰是答案。

## 4. 五级 + 必须带 code（D4）

| 级 | 例子 code | 行为 |
|---|---|---|
| `Fatal` | `F-LAYOUT-OVERFLOW` | 弹错误框 + 退出码 3 |
| `Error` | `E-RES-DECODE` | 记 + 该节点降级为占位 |
| `Warn` | `W-RES-OVER-BUDGET` | 记 + 继续（允许超预算） |
| `Info` | `I-PERF-FRAME-BUDGET` | 仅 dev |
| `Trace` | `T-WRITE-CHAIN` | 仅 `--trace` |

★★ **没有 code 就无法回答"这个版本这个警告出现了多少次"**。
自由文本日志能读不能统计；`W-RES-OVER-BUDGET` 能统计、能设阈值、能进 CI 断言。

★ **code 登记在 `diag-codes.json`**（数据文件，不是散文）：

```json
{ "W-RES-OVER-BUDGET": { "level": "warn", "msg": "资源占用超过预算 {used}MB（预算 {budget}MB）", "since": "0.1" } }
```

★ 好处：消息文本可以改，code 不变；测试断言 code 而不是文本（文本会改）。

★ **脱敏默认开**：诊断里出现的字符串参数（输入框内容、路径、用户名）默认替换为 `<str:12>`（长度保留）。
理由：诊断会被贴进 issue，**用户不该为了报 bug 泄露输入内容**。
`--no-redact` 只在本地调试用。

## 5. 退出码（D5）

| 码 | 含义 | 谁产生 |
|---|---|---|
| `0` | 正常退出 | 应用 |
| `3` | **框架致命**（布局失败 / 不变量违反） | 框架 |
| `4` | 应用未捕获异常 | 框架兜底 |
| `5` | 平台初始化失败（无窗口 / 无 DPI / 无字体） | 壳 |

★ 判据：**自动化必须能区分"我的代码错了"和"框架/环境错了"**。
全部返回 1 的话，CI 只能报"失败了"，人得看日志才知道该找谁。

★ 退出码与 [08](08-平台与能力矩阵.md) §4.1 的"最后已知几何"配合：
`3`/`4`/`5` 时**仍要尝试保存几何与状态快照**（那时窗口可能已死，靠缓存）。

## 6. 错误边界 `Guard`（D6）

```php
$list->child(
    Guard::of(
        fn() => $this->rowNode($item),      // 可能抛（数据坏了、资源缺了）
        fn() => $this->rowFallback($item)   // fallback：按父给的约束**填满**
    )
);
```

| 规则 | 说明 |
|---|---|
| **粒度到节点** | "列表里第 7 行数据坏了"不该拖垮整页 |
| **fallback 按父约束填满** | 否则布局塌陷，坏一行导致整页错位 |
| **同节点连续失败 3 次不再重试** | 否则每帧抛一次，帧预算全被吃掉 + 日志刷爆 |
| **失败信息进语义树** | 屏幕阅读器要能读到"这一项加载失败" |

★★ **`Guard` 是"局部降级"，不是"吞异常"**：
它必须记一条 `E-*` 级诊断（带节点路径），并且**在 dev 构建里直接 Fatal**——
否则"某一行永远是 fallback"会变成一个没人发现的长期 bug。

★ 与 [08](08-平台与能力矩阵.md) §4.3 的 `LayoutTolerance::$previewing` 是两件事：
- `previewing`：**预期内**的临时越界（拖动窗口），降级为裁剪，松手恢复严格。
- `Guard`：**非预期**的节点级失败，降级为 fallback，并永久记录。

两者都会"让错误不响亮"，所以**都必须有配套的可观测出口**，否则就是在埋雷。

## 7. 检视工具（D7）

| 工具 | 回答 | 输出 |
|---|---|---|
| `Inspect::pick(x, y)` | "这个像素是谁画的" | 节点路径 + op 列表 + 该 op 的来源段 |
| `Inspect::overlay('dirty')` | "这块为什么在闪" | 脏区高亮（本帧 damage 矩形） |
| `Inspect::overlay('layout')` | "为什么位置不对" | 每个节点的盒 + 约束 + 溢出标记 |
| `Inspect::overlay('frame')` | "哪帧慢" | 五阶段耗时条 + 脏节点数 |
| `Inspect::dumpSubscriptions()` | "谁在看这条状态" | 依赖表（[02](02-状态与命令.md) §3.3） |

★ **overlay 是 op 流的普通消费者**：它自己也是一段 op，走同一条 `Painter` → `Canvas` 路径。
所以"检视工具"不需要任何特殊通道，也不会因为"调试模式"改变绘制行为。

★ 判据：**任何"只在调试下才画"的东西，都必须能画出与生产完全相同的帧**（overlay 叠加在其上）。
否则你调的是另一个程序。

## 8. 与错误消息纪律的关系

[04](04-布局.md) §6 定的是**面向使用者**的消息（现象 + 数值 + 两条修法，不写内部编号）；
本册定的是**面向开发者/自动化**的通道（code + 写入链 + 退出码）。

★ 两者不冲突，分工明确：

| 读者 | 通道 | 形态 |
|---|---|---|
| 用户 | 错误框 / 控制台 | 人话，无编号 |
| 开发者 | `diagRing` + `--trace` | code + 节点路径 + 写入链 |
| CI | 退出码 + `diag-codes.json` | 可断言的数字 |

★ **同一个失败要同时进两个通道**：用户看到"Row 的横向空间不够，超出 48.5"，日志里是
`F-LAYOUT-OVERFLOW node=#42 path=App>Dock>Row`。缺任何一个，都有一类人没法干活。
