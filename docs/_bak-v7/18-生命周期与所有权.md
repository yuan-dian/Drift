# 19 生命周期与所有权

> 本册回答：**节点从生到死经过哪几个态、每个态能做什么、谁负责释放、异步任务活多久。**
> 来源：v6 §02 §6–7。v7 第一版只有 `create/update/move/destroy` 四个词——**不够**，而且有一个必踩的坑。

---

## 0. 一句话

**`deactivate` 与 `detach` 必须分开，`dispose` 必须推迟到帧末。**

不分开的后果很具体：`Repeater` 的一项"移动"在实现上是 remove + insert，
节点**短暂离树**。如果离树就 `dispose`，那么**移动一次丢一次状态**——
输入框内容清空、展开态收起、滚动位置归零。这个 bug 只在"列表可排序"时出现。

---

## 1. 六个阶段（T1）

```
 create ──→ mount ──→ attach ──→ active
              ↑                    │
              │                    ↓
           (复用)            deactivate ──→ detach ──→ dispose
              ↑                    │           │
              └────────────────────┘           └──→ (帧末统一)
                 同一帧内回来了 ⇒ 不 dispose
```

| 阶段 | 何时 | **必须做** | **不能做** |
|---|---|---|---|
| `create` | 构造 | 设 `kind` / `key` / 默认字段 | 读父、读状态、申请资源 |
| `mount` | 进入孩子列表 | 建子节点、`depth = 父+1` | 测量（父的约束还不知道） |
| `attach` | 收到第一次约束 | 登记依赖（`Tracker`）、申请后端资源 | 假设自己尺寸已定 |
| `active` | 在树中且可见 | 响应命令、写状态 | 假设每帧都会被调用 |
| `deactivate` | 被移除或隐藏 | 停止接收命令、保留状态 | 释放资源 |
| `detach` | 确定不再复用 | 退订、释放资源 | 假设还能回来 |
| `dispose` | **帧末** | 标记 dead、清空引用 | 被任何布局/绘制路径访问 |

★ **`create` 里不能读状态**：那时 `Tracker` 栈是空的，读了也登记不上 ⇒ 静默漏订阅。
这也解释了为什么 `CellSpec`（数据）比闭包构建器好：数据可以在任何阶段构造，闭包不行。

★ **`attach` 的时机是"收到第一次约束"**，不是"进入孩子列表"。
资源申请要按目标尺寸做（[15](15-资源.md) §2.1），所以必须等约束到了。

## 2. `deactivate` ≠ `detach`（T2）

| 动作 | 语义 | 状态 | 资源 | 依赖 |
|---|---|---|---|---|
| `deactivate` | "暂时不在了" | **保留** | **保留** | 保留（可能马上回来） |
| `detach` | "确定不再用" | 保留到帧末 | 立即释放 | 立即退订 |
| `dispose` | "真的没了" | 丢弃 | 已释放 | 已退订 |

★ **判定"会不会回来"的唯一依据是帧末的复用结果**：

```
一帧内：
  ① settle 跑 Reconciler，得到"old 里未被复用的节点集合" U
  ② U 里的节点全部 deactivate（不是 dispose！）
  ③ 本帧后续的 settle 若又复用了其中某个 ⇒ 直接 attach 回来（状态还在）
  ④ 帧末：仍在 U 里的 ⇒ detach → dispose
```

★★ **`dispose` 推迟到帧末是这一册的核心机制**。它同时解决三件事：
- `Each` 的移动（remove + insert 在同一帧）不丢状态；
- `dispose` 里可以安全地"回头看"本帧的结构（树还没拆完）；
- 释放动作集中在一个点，可以批量（纹理淘汰、句柄回收都在这里，见 [15](15-资源.md) §2.3）。

★ **代价**：一帧内被 `deactivate` 的节点仍占内存，且**不能参与布局**（尺寸未定）。
所以 `deactivate` 的节点必须从布局遍历里排除——判据是"`attach` 过但本帧没收到约束"。

## 3. `Owner`：谁负责释放（T3）

```php
final class Owner
{
    private array $fibers  = [];    // 结构化并发的子任务
    private array $subs    = [];    // 依赖订阅
    private array $handles = [];    // 后端资源句柄（int）
}
```

三样东西挂在 `Owner` 上，**释放顺序固定**：

```
dispose(owner):
  ① 取消所有 Fiber（发 Cancelled，不等待完成）
  ② 退订所有依赖（Tracker 的依赖边）
  ③ 释放所有资源句柄（close()，幂等）
  ④ 标记节点 dead
```

★★ **顺序反了会撞悬空句柄**：Fiber 在资源释放后恢复执行，访问已 `close()` 的纹理 ⇒ 崩在 C++ 侧，
栈里看不到任何 PHP 代码。这类崩溃最难查，因为它发生在"页面已经销毁之后"。

★ **`close()` 必须幂等**：Reconciler 与 `Owner` 都会调一次（防御性），重复调用不能出错。

★ **`Owner` 是节点的一个字段，不是全局**：`Owner` 树与节点树同构，
所以"销毁一个子树"= 按后序遍历 dispose 每个 `Owner`。不需要单独的所有权图。

## 4. 结构化取消（T4）

```
页面 A 的 Owner
  ├─ Fiber#1（加载列表）
  └─ Fiber#2（加载详情）
        └─ 页面 A 出栈 ⇒ Owner 取消 ⇒ 两个 Fiber 在下一个挂起点收到 Cancelled
```

★ **判据：一个异步任务的生命周期不能超过它的发起者**。
"后台任务活过页面"是泄漏之源——它持有 `Owner` 的引用 ⇒ 整个子树无法回收。

★ **取消是协作式的**：Fiber 只在**挂起点**（`await` / `sleep` / IO 等待）收到 `Cancelled`。
所以纪律是：**长循环里必须有挂起点**，否则取消失效（这与"帧内切片"是同一个要求，见 [09](09-帧与异步.md) §4）。

★ **取消不是失败**：`Cancelled` 不记 `Error` 级诊断、不触发 `Guard`、不弹错误框。
它记一条 `Info`（`I-TASK-CANCELLED`），因为"任务被取消"在排查"为什么数据没加载"时是关键信息。

## 5. `Cell` 不属于任何 `Owner`（T5）

| 东西 | 归谁 | 理由 |
|---|---|---|
| 节点、Fiber、后端资源 | **`Owner`（框架拥有）** | 它们的生命周期由树决定 |
| **共享态 `Cell`** | **应用（框架不拥有）** | 框架只拥有"谁在看它"，不拥有它本身 |

★★ **边界不清的后果**：页面销毁顺手把 store 也退了 ⇒ 别的页面（或下一次进入）读到空状态。
这个 bug 的症状是"返回上一页后数据没了"，而它看起来像"页面没保存状态"。

★ 所以 `dispose(owner)` **只退订，不销毁 `Cell`**。`Cell` 的销毁由应用自己决定（通常跟应用同生命周期）。

★ 一条推论：**`Cell` 可以活得比任何节点都长**，所以它里面**不能存 `Node` 引用**——
否则一个已 `dispose` 的节点被 `Cell` 拖着，内存泄漏且访问即崩。

## 6. 与 Reconciler 的接口

`Reconciler`（[03](03-树与身份.md) §3）只做三件事，其余交给生命周期：

```
① 配对（key / 位置 + kind）       ⇒ 复用的节点：update（不重建）
② 未被复用的 ⇒ deactivate         ⇒ 放进本帧的 U 集合
③ 新增的 ⇒ create → mount → （等约束）attach
帧末：U 里剩下的 ⇒ detach → dispose
```

★ **`Reconciler` 不知道资源、不知道 Fiber**。它只知道"谁被复用了"。
释放的全部知识在 `Owner` 里——这是"结构"与"所有权"的分工。

★ **`update` 不是 `create`**：复用节点的字段要重置为新的声明值，但**`local` 状态保留**
（这就是复用 vs 重建的全部区别，也是 key 存在的唯一理由）。
判据：**哪些字段属于"父给的配置"（重置），哪些属于"节点自己的状态"（保留）**。
`local` 一律保留；`fields` 一律重置。

## 7. 反模式

| 反模式 | 症状 | 正解 |
|---|---|---|
| 离树即 `dispose` | 列表移动一次丢一次状态 | `deactivate` / `detach` 分开（§2） |
| `dispose` 里访问树 | 崩溃或读到半拆的树 | 推迟到帧末（§2） |
| 先释放资源再取消 Fiber | C++ 侧崩溃，栈里没有 PHP | 顺序固定（§3） |
| 靠析构释放 | 帧间泄漏 | 显式 `close()` + `Owner`（§3） |
| 长循环无挂起点 | 取消失效，任务继续跑 | 循环里插入挂起点（§4） |
| 页面销毁顺手清 store | 返回上一页数据没了 | `Cell` 不归 `Owner`（§5） |
| `Cell` 里存 `Node` | 已销毁节点被拖着 + 访问即崩 | `Cell` 只存数据（§5） |
