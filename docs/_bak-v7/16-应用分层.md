# 17 应用分层

> 本册回答：**业务逻辑放哪、状态放哪、页面什么时候还活着、什么值该由谁持有。**
> 来源：v6 §16 §1–4。v7 第一版完全没写——于是"框架对了，应用层全是坑"。

---

## 0. 一句话

**框架管一棵树，应用管三层。三层之间只有一条依赖方向，且框架不认识上面两层。**

这条不写清楚，出现的第一个问题一定是"业务判断写进 `onTap` 里，于是没法无头测"。

---

## 1. 三层与依赖方向（A1）

```
  Domain（纯数据 + 纯函数）        ← 不认识 Node、不认识 StateHub、不认识平台
      ↑
  Store（应用状态 + 命令处理）      ← 认识 Domain 与 StateHub，不认识 Node
      ↑
  Ui（建树 + 声明命令 + 读状态）    ← 三层里唯一认识 Node 的
```

★ **依赖只能向上，不能向下**。`Domain` 里出现 `use Drift\Node` ⇒ 编译能过、测试不能过（无头跑不起来）。

★ **判据一句话**：**这段逻辑会不会因为"改需求"而变？**
会 ⇒ 它属于 `Domain`（要能单独测）；不会、只是因为"界面长这样" ⇒ 属于 `Ui`。

| 逻辑 | 归属 | 为什么 |
|---|---|---|
| "折扣 = 满 300 减 50" | Domain | 改需求就变；要能单测 |
| "列表按名称排序" | Domain（或 Store） | 与界面无关 |
| "筛选条件变了要重算列表" | Store | 认识状态，不认识控件 |
| "这一行显示标题还是副标题" | Ui | 纯展示决定 |
| "按钮点击后禁用 200ms" | Ui（本地态） | 渲染态，不是业务 |

★ **框架不提供"应用框架"**：不提供路由、不提供 DI 容器、不提供全局单例。
它只提供"一棵树 + 一条命令通道 + 一份共享态"，其余由应用自己组织——**但组织方式必须遵守本节**。

## 2. 状态四家（A2）

每个值只有四个可能的家，选错的症状都很典型：

| 家 | 是什么 | 判据 | 选错的症状 |
|---|---|---|---|
| **`Cell`（共享态）** | 普通类 + 字段索引（[02](02-状态与命令.md) §3） | **写它的时候，需要通知别人吗？** 需要 ⇒ Cell | 放 local ⇒ 别处不刷新（最难查） |
| **`local`（节点本地态）** | 节点自己的 `private` 字段 | 只影响**本节点渲染**（展开/折叠、光标位置） | 放 Cell ⇒ 每次交互一次全树依赖检查 |
| **`fields`（父配置）** | 父节点传给子的构造参数 | 由父决定、子不改 | 放 local ⇒ 父改不了；放 Cell ⇒ 过度共享 |
| **局部变量** | 函数内，生命周期 = 一次 `settle` | 只在这次构建里用 | 放 local ⇒ 泄漏成永久状态 |

★★ **最高频的误用：把"选中项"放进 `local`**。
症状：列表选中了，工具栏的"删除"按钮不变灰——因为工具栏读不到那个 local。
判据：**这个值有没有第二个读者？** 有 ⇒ 一律 `Cell`。

★ 反向的误用：**把"输入框光标位置"放进 `Cell`**。
症状：每次移动光标触发一次全树依赖检查。光标只有编辑器和它自己读 ⇒ `local`。

★ **`local` 不是"私有 Cell"**：`local` 变化只打自己（和祖先链）的脏位，不经过 `Tracker`，
不产生依赖边，不参与 `dumpSubscriptions()`。它便宜，代价是**别处看不见**。

## 3. 页面三态（A3）

```
        ┌──────────┐   被盖住   ┌───────────┐   出栈   ┌─────────┐
        │  active  │ ────────→ │  offstage │ ──────→ │ dispose │
        └──────────┘ ←──────── └───────────┘         └─────────┘
              ↑       回到栈顶
              └── 仍在帧里参与结构维护（但不是 active）
```

| 态 | 在树上？ | 参与 `settle`？ | 参与 `layout`/`paint`？ | 语义树里？ |
|---|---|---|---|---|
| `active` | 是 | 是 | 是 | 是 |
| `offstage` | 是 | **是** | 否（跳过） | 否 |
| `dispose` | 否 | 否 | 否 | 否 |

★★ **`offstage` 仍在 `settle`，是这一节唯一反直觉的点**：
被盖住的页面如果完全不参与 `settle`，它上面的 `Cell` 订阅就断了 ⇒ 切回来时状态是旧的。
但如果让它参与 `layout`/`paint`，就白算。

★ **隐藏成本必须说清**：10 层页面栈 ⇒ 每帧 10 页的结构维护（`settle` + 脏位清点）。
这是"切回来状态还在"与"内存/CPU 爆炸"的分界线。
判据：**栈深 > 3 时，非栈顶页面必须能被显式冻结**（`freeze()`：退订 + 保留最后一份快照，
`thaw()` 时重放快照并重新登记依赖）。首版不自动冻结，但接口留好。

★ **`offstage` 不是 `visible: false`**：后者是绘制属性（还占布局），前者是生命周期状态。

## 4. 跨页数据：共享 Store，不传对象（A4）

```php
// ❌ 传对象：页面可能在栈里躺很久，对象早被替换
$router->push(new DetailPage($user));

// ✅ 传 id：页面自己从 Store 取当前值
$router->push(new DetailPage($userId));
```

★ 理由不是"解耦"这种空话，是**时间**：详情页可能在栈里躺 10 分钟，期间那条记录被别处改了或删了。
传对象 ⇒ 页面显示的是 10 分钟前的快照，且**用户以为是当前的**。

★ 传 id ⇒ 页面每次 `settle` 从 Store 读当前值，自动跟随。
删除的情况也要显式处理：**id 查不到 ⇒ 页面显示"该项已删除"并自动出栈**，不是空白页。

★ **页面之间不直接调用**。要影响别的页面 ⇒ 改 Store（它自然会刷新）。
"页面 A 调页面 B 的方法"是事件总线的变种，见 §5 反模式。

## 5. 受控 / 非受控（A5）

| 形态 | 值在哪 | 判据 | 代价 |
|---|---|---|---|
| **受控** | `Cell`（外部持有） | **这个值别人还要用吗？** 要 ⇒ 受控 | 每次输入一次 flush 往返 |
| **非受控** | 节点 `local` | 只在提交时取一次 | 无法外部设值/校验 |

```php
// 受控：值在 Cell，每次输入写回
$field->value($state, AppState::F_QUERY)->command(Command::SEARCH);

// 非受控：值在节点里，提交时才读
$field->defaultValue('')->onSubmit(fn($v) => $this->search($v));
```

★ **选错的症状**：
- 该受控却非受控 ⇒ 程序改不了输入框内容（"清空筛选"按钮无效）。
- 该非受控却受控 ⇒ 每次按键一次 Store 写入 + 一次依赖检查 + 一次布局，**打字发涩**。

★ 判据的准确版本：**这个值在"输入过程中"有没有第二个读者？**
搜索框的每次按键都要触发搜索 ⇒ 受控；表单里的备注只在提交时读 ⇒ 非受控。

## 6. 六条反模式（A6）

| # | 反模式 | 症状 | 正解 |
|---|---|---|---|
| 1 | **`Ui` 里写业务判断** | 无法无头测；改需求要改界面代码 | 判断搬 `Domain`，`Ui` 只读结果 |
| 2 | **`Store` 里 `new Node`** | 依赖倒置；`Store` 无法在无头测试里构造 | `Store` 只改状态，`Ui` 读状态建树 |
| 3 | **全局单例** | `global` 在 TypePHP 里擦除类型（L1）；且测试间互相污染 | 显式传入（`App` 持有 `Store`，构造时给） |
| 4 | **事件总线** | 发布者不知道谁在听 ⇒ "改一处，三处莫名其妙刷新" | 改共享 `Cell`（依赖边可 dump） |
| 5 | **在 `of(fn)` 里做重活** | 每次读都重算；且在 `settle` 里，直接吃掉帧预算 | 用 `Computed`（版本号 + 惰性，见 [02](02-状态与命令.md) §4） |
| 6 | **选中项放 `local`** | 别处读不到（§2） | 放 `Cell` |

★ 六条里 1、2、4 三条**都指向同一个东西**：**依赖必须是显式的、可枚举的**。
反模式不是"风格不好"，是"让依赖变得不可枚举"，而不可枚举的依赖无法诊断（见 [17](17-诊断与错误边界.md) §2）。

## 7. 与框架的接口面（应用只碰这些）

| 应用要做的事 | 用的东西 | 不用的东西 |
|---|---|---|
| 建树 | `Node` 子类 + 工厂函数 | 不继承框架的"控件基类"（没有这种东西） |
| 声明交互 | 闭包（常规）/ 命令 ID（可回放） | 不注册全局回调表 |
| 存状态 | 普通类 + `Cell` 字段索引 | 不用动态 map（`mixed` ⇒ `Var`） |
| 起应用 | 组合根五步（[12](12-工程与工具.md) §5） | 不碰 `Platform` 实现类 |
| 页面栈 | 应用自己的 `Router`（框架不提供） | 不在框架里加"页面"概念 |

★ **最后一行是刻意的**：框架只有"节点"，没有"页面"。页面是应用层的组织方式（三态、冻结、传 id），
把它塞进框架会让框架必须懂路由——那是另一个产品。
