## 1. 摘要（结论先行）

**Drift2 当前处于「可交付真实业务 app 的早期生产阶段」，整体成熟度已领先于 2026-10-13 的调研资料假设。** 调研资料当时把 Drift2 判为「画界面够、跑业务缺底座、异步未排期」，但 10-30～11-01 的收口把其中大部分缺口已补齐甚至超出资料预期：业务底座五项里四项（全局错误出口 / 校验 / 设置持久化 / 列表身份）已落地，异步从「未排期」变成「三后端 + Future + AsyncValue + allSettled 已实装」，多窗口 M0–M3 全绿，`Offstage`、`ScrollLane` 收敛、`BoxStyle` 单字段收口均已落地。真正仍落在调研资料口径之下的，主要是**异步「流/stream」维度缺失**、**通用裁剪/变换控件缺失**、**UIA 真机验证与跨 DPI 双屏拖动未覆盖**三件，外加若干去重收尾。

一句话定调：**表现层与控件广度已对齐 Flutter/Compose 同级，业务底座已跨过门槛，当前的主要风险从「缺能力」转为「已建能力的真机验证覆盖」与「个别维度尚未定性」。** 这恰好印证了调研资料《Optimization-Plan》的核心判断：本仓的瓶颈从来不在表现力，而在真机/业务侧的验证与少数列表/异步语义。

## 3. 能力缺失清单（P0 / P1 / P2）

### P0（阻塞真实交付 / 高优先级）
> 说明：相对调研资料，P0 缺口已大幅收敛。剩余 P0 实为「已建能力的真机验证」而非「缺实现」。

- **P0-1　`ElementProviderFromPoint` 真机验证 —— ✅ 2026-11-01 已闭环**
  - 结论：`tools/probe-uia.py --verify-hit-test` 真机 5/5 命中正确（点叶子中心返回该叶子），不再恒返回窗口根。
  - 根因（曾误判为「需 C++ 消息泵客户端」）：ctypes 把参数传成两个 double，实际签名是 `POINT`（`UIAutomationClient.h:18869`）⇒ x64 下整数寄存器 `rdx` 是垃圾坐标。修 `element_from_point` 后即通。
  - 仍待：`drift_win32.cc:823` parent 链成环防护的**变异证伪**（造一个环，确认上溯有界不挂死）——当前只有代码界的静态存在，未做变异验证。
  - 出处：`tools/probe-uia.py`；提交 `94b8537`。

- **P0-2　跨 DPI 双屏拖动边缘项**
  - 现象：`docs/MULTI-WINDOW-2026-10-30.md` §6 末列为 pending，需双屏硬件；`nodeScreenRect` 已用 `dpiOfWindow()` 现查规避跨屏拖动后 `WM_DPICHANGED` 滞后（`drift_win32.cc:990`），但未实测双屏场景。
  - 影响：双屏不同 DPI 拖动窗口时边缘项可能错位。
  - 建议：有双屏硬件后补端到端用例；先确认 `GetDpiForWindow` 在跨屏拖动中途返回值正确。
  - 出处：`docs/MULTI-WINDOW-2026-10-30.md:741`。

### P1（重要，应排入近期）
- **P1-1　异步「流 / stream」维度缺失（整维未定性）**
  - 现象：`src/Async/` 仅 `Future.php` + `AsyncValue.php`；grep `stream|Stream` 命中均为 I/O 流（`IoPoller`/`ProcessTaskHost`），**无异步流组合器**（无 `Stream`/`onEach`/进度流）。`Future::all`/`allSettled` 覆盖「一次性多任务」，但不覆盖「单任务渐进产出」（下载进度、SSE、大结果分块）。
  - 影响：需要「渐进更新 UI」的真实场景（如大文件下载进度条、流式日志、分页增量）只能用轮询或多次 `Future`，无类型化承载。
  - 建议方向：**先按项目教条「等真实需求逼出来」**（与 `Async-Evaluation` 的「暂不实现」纪律一致），但要在 `ASYNC-ARCH` 里把「流」显式定性为「待引入维度」而非「被删的声明」——当前代码里没有任何误导性遗留声明，属单纯空缺。
  - 出处：`src/Async/` 目录核查；`docs/ASYNC-2026-10-30.md` 仅谈一次性任务；Flutter `Stream`/`StreamBuilder` 为成熟对照。

- **P1-2　通用裁剪 / 变换控件缺失**
  - 现象：无 `ClipRect`/`ClipRRect`/`Transform` 控件；裁剪只在 `RenderScrollView`/`RenderTable` 内联（`RenderScrollView.php:18`、`RenderTable.php:547`）。
  - 影响：业务要做「圆角裁图」「旋转卡片」「局部遮罩」必须改渲染盒，违反「组合不新写盒」的纪律（`TimeView`/`DateTimePicker` 注释反复强调）。
  - 建议：新增 `ClipRect`/`ClipRRect`（修饰型 `SingleChildRenderObjectWidget`，复用已有裁剪几何）与 `Transform`（矩阵修饰）；与 `BoxStyle`/`ControlStyle` 同款「一套口径」。
  - 出处：本册 §2 差距表（🔴）；调研资料《Global-Review》把「样式/修饰」列为第二梯队差距来源。

- **P1-3　运行中开窗的「帧边界执行」钩子落地**
  - 现象：`N4 Inbox` 在 `docs/EVENT-LOOP-DESIGN-2026-10-30.md:873` 已二次改判为「**不建**」（唤醒由 N5 内建、跨上下文投递 PHP 闭包结构上不可能）；运行中开窗改为 `EventLoop` 的**帧间钩子**（`EVENT-LOOP-DESIGN:1182`），但尚未见实现落点。
  - 影响：`WindowSet::open()` 必须在帧边界执行，否则在某事件回调中间跑一整帧 = 重入崩溃。
  - 建议：确认帧间钩子已实现并覆盖「点按钮弹新窗」示例（`MULTI-WINDOW:573` 提到的 `InspectorApplication` 演示）。
  - 出处：`docs/EVENT-LOOP-DESIGN-2026-10-30.md:873`、`:1182`；`docs/MULTI-WINDOW-2026-10-30.md:740`。

### P2（治理 / 收尾，成本低）

## 4. 可优化项（重点：能替代只留一套）

用户明确偏好：**同一件事只保留一套实现**。核查发现 Drift2 已 aggressively 执行了这一纪律，应作为正向资产保留；仅余少量可进一步合并的机会。

### 已做（正向，保留）
- **滚动三实现 → `ScrollLane`**：`ScrollViewState`/`LazyListState`/`TableState` 共用的「偏移夹取 + 动画收口 + 条淡出」收成 `ScrollLane` + `ScrollMotion` + `ScrollBarFade`，三 State 经 `$push`/`$apply` 回调保留策略（`src/Widget/ScrollLane.php:25`、`ScrollMotion.php`）。→ 同一件事一套契约。
- **HTTP 两份手写 → 单一 `Http`**：基于 `curl_multi`，两份手写 curl 合并（`4035b16`）。
- **`BoxStyle` 单字段收口**：视觉四维收成一个字段、底色只剩一份实现（`85f94e8`）。
- **`TableGeometry` 收口**：七个散字段 + 三种「空」⇒ 一个快照（`063500b`）。
- **格级矩形选区**：`list<TableRange>` 取代点法语义多份（`b0ccee4`）。
- **`Card` 归位**：包装器不再自持样式（`5f38be8`）。
- **异步 `all/race/allSettled` 共享**：`collect()`/`cancelAll()`/`orderedByInput()` 抽出（`Future.php:275`、`:299`、`:319`），消灭「两处各写一遍必然漂」。

### 可进一步合并（候选，待核实）
- **视口渲染盒的裁剪 + 滚动条 paint**：`ScrollBarHost`/`ScrollBarFade`/`ScrollBarGeometry` 已共享几何与动画，但 `RenderScrollView` 与各虚拟列表/表格盒仍各自内联「夹裁剪矩形 + 画 thumb」。建议核实后把这段收成 `RenderBox` 共享 helper（P2-1）。
- **DPI 读取口径**：`nodeScreenRect` 用 `dpiOfWindow()`（优先 `GetDpiForWindow`），注释声明与 `php_drift_win_dpi()` 同源（`drift_win32.cc:993`）。已是一套，但建议显式 grep 确认全仓无第二处直接 `GetDpiForWindow`/`WM_DPICHANGED` 缓存读，避免「两处真相源」。

> 总体评价：**Drift2 在「去重/单一口径」上显著优于调研资料对早期项目的担忧**（资料《Redesign-Review》曾警告「机制沉积成多套」）。当前没有发现「同一件事两套并存且互相漂移」的硬伤。

## 5. 可借鉴的成熟 GUI 做法 + 排坑提醒

### 已经踩过并修好的坑（本仓已对齐成熟做法）
1. **UIA 几何单一转换函数**：`nodeScreenRect` 把「逻辑→物理（×dpi/96，现查）」+「客户区→屏幕（ClientToScreen）」收在一处，服务 `BoundingRectangle`/`IsOffscreen`/`ElementProviderFromPoint` 三消费方（`drift_win32.cc:985`）。这正是成熟 provider（WPF `AutomationPeer`/Chromium `ViewAccessibility`）「成对提供」的做法。**坑**：旧版返回客户区坐标（注释写「近似」）是错误的——UIA 契约没有近似（`drift_win32.cc:1000`）。
2. **订阅句柄 + 相等门控 + 绝不静默**：`SubjectBuilder` + `setIfChanged` + `Errors::report` 覆盖 Aria 对比里最值钱的 P0-1/P0-2/P1-4（`Aria-Comparison` §三）。**坑**：「忘了订阅 ⇒ UI 不动、不报错」正是 Aria 直呼的「黑洞」；`AsyncValue::fold()` 缺键即抛、四支统一签名规避 AOT 静默崩（`AsyncValue.php:313`）都是同一类防御。
3. **批量操作计数语义**：`Future::all`/`allSettled` 的 `$left` 计数漏减 ⇒ 聚合体永不结算 ⇒ 页面一直转圈（`Future.php:451`）。成熟框架 `Promise.all`/`Future.wait` 同源风险。
4. **取消沿派生链上溯到根**：`then/catch` 造的派生 Future 取消钩子指向上游（`Future.php:617`），否则 `submit()->then()` 被取消时只标本节点、根任务静默不停。这是上一版漏掉的半边。

### 正在踩 / 可能踩的坑（排坑提醒）
1. **🔴 `ElementProviderFromPoint` 的 parent 链成环防护必须保留**：`drift_win32.cc:823` 上溯最多 `nodes.size()` 步，因 `parent` 是 PHP 推来的裸整数无校验，成环即死循环且跑在读屏软件回调里 = 整个窗口挂死。**真机验证时优先打这一个断言**。
2. **🟡 异步「流」未定性**：不要因为 `Future` 已做就默认「异步齐了」。Flutter/Web 的「渐进产出」是独立维度；若未来用轮询模拟流，会出现「每帧 setState + 永远转圈」类故障（同 `Future` 计数坑同源）。建议先在 `ASYNC-ARCH` 显式定性。
3. **🟡 跨 DPI 双屏拖动**：`nodeScreenRect` 用 `dpiOfWindow()` 现查已规避 `WM_DPICHANGED` 滞后，但双屏场景的真机值仍待验证；这是「看起来对、跨屏才炸」类坑。
4. **🟡 视口渲染盒裁剪/滚动条内联**：若新增第三种视口盒而不走 `ScrollBarHost`/`ScrollBarGeometry`，会重新引入「三处漂移」。任何新滚动容器必须实现 `ScrollBarHost` + 复用 `ScrollLane`。
5. **🟡 通用裁剪/变换缺失的副作用**：业务若绕过「组合不新写盒」纪律去改渲染盒做圆角/旋转，会制造「又一套几何口径」，与 `BoxStyle`/`ControlStyle` 单一口径原则冲突（§4）。

### 成熟框架可借鉴但本仓已正确否决的
- **自动依赖追踪（Aria `Computed`）**：前提不成立（换 C 轴 + AOT 无全局 build 栈），本仓判死——价值在「脏边界收紧」已由 `SubjectBuilder` 订阅点下移覆盖（`Aria-Comparison` §四）。
- **`Subscription` RAII 句柄**：PHP 无确定性析构 ⇒ 假安全；本仓用 `SubjectBuilder` 覆盖（`Optimization-Plan` §七）。
- **N4 `Inbox`**：跨上下文投递 PHP 闭包结构上不可能，且唤醒已由 N5 内建 ⇒ 判为不建（`EVENT-LOOP-DESIGN:873`、`:1153`）。这是**少建一套机制**的正确决策，与用户「只留一套」偏好一致。
