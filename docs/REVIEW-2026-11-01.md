## 1. 摘要（结论先行）

**Drift2 已经不是「早期框架」，而是一个架构对齐成熟 GUI 的声明式自绘框架。** 资料里的 9 个主题，Drift2 在 6 个上已落地、在 3 个上有明确差距：

- **已对齐甚至超出**：④ 布局（一遍式约束）、⑥ 平台抽象（命令流 + Skia/Raster 双后端 + `CanvasCapabilities` 三层能力位掩码，比 UDA 的 SupportLevel 更细）、⑧ 扩展性（Modifier 值对象 + 主题）、③ 视图树（`(type,key)` diff + `Key` 桶配对）；⑤ 事件（`GestureArena` 竞技场 + 焦点行为层）大部分对齐；⑦ 文本（`TextEditingHost`/`TextInputClient` 子系统）存在但结构弱。
- **真实差距（按影响排序）**：
  1. **① 渲染管线缺「脏矩形/脏边界」**——`RenderObject` §13.3 明说 `relayout()` 永远全树，只有 `paintEpoch` 的整帧门控；无「按深度排序的脏集」（资料主题 1 的推荐）。这是当前唯一的**结构性**管线欠缺（M5 待办）。
  2. **⑨ 工程化工具链欠账**——缺 `drift doctor`（环境自检）、CLI 全量 `--json`、`--script 交互→截图`、双后端/跨平台像素一致测试、脏集/依赖可 dump。
  3. **② 状态 / ⑦ 文本两个维度是「有意取舍」而非遗漏**——显式 `Subject` 订阅（AOT 无全局 build 栈 ⇒ 不做编译期自动依赖收集）、文本无 `Rope`（字符串拼接）——前者是正确取舍，后者是真实欠账。

一句话定调：**表现层与管线已对齐 Flutter/Compose 同级，当前瓶颈从「缺能力」转为「脏矩形未做 + 工程化验证工具不足 + 个别数据结构（文本）欠账」。**

## 3. 能力缺失清单（P0 / P1 / P2）

### P0（结构性 / 影响扩展性）
- **P0-1　布局脏矩形 / 脏边界（M5）缺失**
  - 现象：`RenderObject` §13.3 明写「Render 层没有脏边界，`relayout()` 永远全树」；`Frame` 只有「要不要重排」的粗门控，一旦重排即全树。
  - 影响：大列表 / 深树页面每次交互全树重排；资料主题 1 的「三 pass 各管脏集、按深度排序」未兑现。**这是当前唯一的结构性管线缺口**。
  - 建议：按资料 M5 口径做「脏矩形 + 脏边界成对」——单独做任一个反而把瓶颈搬到对面（本仓 §13.3 已自述该陷阱，勿只做半边）。
  - 出处：`src/Layout/RenderObject.php:18`；`src/App/Frame.php:265`。

- **P0-2　「只改像素」的通道不给帧时钟信号 —— 死锁（2026-11-01 已修，1f924c3）**
  - 现象：`wantsFrame()` 只认结构 / 动画 / 定时器 / 焦点环；`setHovered()` / `setBarOpacity()` /
    `applyCompose()` 三条刻意不 `setState`（为了不重建），于是**没有任何判据看得见它们**。
    后果是死锁：`没脏 ⇒ 不上膛 ⇒ 不跑帧 ⇒ tickAnimations 不跑 ⇒ 永远不脏`。
  - 已修：`Frame::hasPendingPaint()`（复用 paint 门控那个序号）接进 `Application::needsFrameNow()`；
    `setHovered()` 补 `markNeedsPaint()`。`PaintArmsFrameTest` 3 例 + 三轮变异。

- **P0-3　悬停浮起 / 滚动条淡出真机都不出画面（两条均已收口，2026-11-01）**
  - **悬停：已修 + 真机验收绿**。两个独立成因，各有一条能红的断言
    （`tests/Feature/App/HoverPixelTest.php`）：
    ① **盒换代清零瞬态** —— `Element::update()` 必调 `syncBox()`（§13.2），悬停态住
       盒字段上 ⇒ 任何一次 `setState()` 都清零。修法：同类型盒之间
       `inheritRuntimeState()`（`Element::syncBox()` 里调）。
    ② **重绘边界吞命令** —— `LayerCache` 按 `layoutEpoch + 尺寸` 命中，而 hover 叠色
       是**录进命令流**的 ⇒ 只推全局 `paintEpoch` 时边界整段重放旧命令。真机 trace：
       进度 0→1 推了 43 帧，`paint` 记录里从来没有那个盒的 id。修法：就地写点统一走
       `markPaintChanged()`（`RenderBox` 覆写 = 失效**从自己开始**最近的边界）。
  - **上一轮那批红有一半是探针造成的**：`probe-motion.py` 的 `move/click/wheel` 用了
    `PostMessage` 伪造消息（`PITFALLS` 第 37 条早就禁止这么做）。改真实光标后同样的
    exe 立刻绿：盒内 1910 px、环带 202 px 变化。⇒ 以后"探针说没反应"先换真实输入复测。
  - **滚动条淡出：不是产品缺陷，是探针采错了列（2026-11-01 晚订正）**。
    上一版写"插桩后日志 0 行、右侧一条都没有"，据此判"视口盒没进绘制树"。
    **那个结论是假的**：两个探针都在**窗口右缘**（`x ∈ [w-40, w)`）采样 ——
    那里是**页面底色**，整列恒 238.9 ⇒ "滚动前后完全一样"必然成立。
    用逐列扫描重新定位后，条在 **x=1370..1375**（离窗口右缘 39px）：画着，
    且淡出正常（滚后 luma **119.3** → 静止 **207.7**，与解释器逐位相同）。
    ⇒ 处置不在产品侧，在量具侧：
    ① 新增 `tests/Feature/App/ScrollBarFadePixelTest.php`（解释器级像素判据，
       5 条断言：全亮 / 900ms 前不许淡 / 淡到 0.35 / 淡完仍看得见 / 淡出期间内容不动）；
    ② 定位逻辑收成 `tools/probe_pixels.py::find_scrollbar()`，两个探针共用；
       采不到目标时打 **SKIP（退出码 2）**，不再报"没变"。
  - 已排除（免得重跑）：`TrackMouseEvent(TME_LEAVE)`；探针取点（并排按钮粘成一块）；
    动画不推进（`p` 确实到 1）；帧时钟判据（P0-2 已补）；盒换代（已修并验证）；
    **懒列表视口盒是否进绘制树**（进了 —— 见上一条）。


### P1（重要，应排期）
- **P1-1　双后端 / 跨平台像素一致测试缺失**（资料 13-nanoui §3.6，明确「Drift 缺，值得抄」）
  - ✅ **已改判并落地（2026-11-01 夜，见 §9）**。原建议「同一 golden 在 Raster/Skia 逐字节
    一致」**是恒假命题** —— `SkiaCanvas` 类注释早写明抗锯齿/描边是**有意**差异，
    「像素级 golden 不能跨后端比」。改判为 **"一份换算，两个观察者"**：
    ① `Scale::deviceRect/deviceX/deviceY` 成为唯一的"加偏移 + 量化"（此前两后端各抄一遍，
    共 6 处）；② `BackendDeviceSpaceTest` 用同一个 `DisplayList` 回放给两个后端，
    桥参数与墨迹盒各自对齐**同一份规格**（规格在测试里用定义重算，不调实现）。
  - 仍未做：真机 Skia 光栅基线（`php.exe` 里跑不到真 Skia）、跨平台互比（各平台各自基线）。
- **P1-2　字形图集（glyph atlas）缺失**（资料 13-nanoui §3.5）
  - 现象：逐字形 `face->rasterize()` 到画布（`RasterCanvas.php:247` 附近），无图集。
  - 影响：CJK / 大字号场景重复栅格化；若将来上 GPU 后端，图集是实例化合批的前置。
  - 建议：字形一次栅格进图集 + 按字形引用；上 GPU 前必须做。
- **P1-3　动效模型弱：controller + 每帧全树 tick**（资料 13-nanoui §3.4）
  - 现象：`AnimationController` + `tickAnimations()` 逐节点推进（`RenderObject::tickAnimations`），无「活跃动效集合」。
  - 影响：每帧全树 tick 的固定成本；「中途改目标保留速度」这类体验细节容易写成「重置」。
  - 建议：改「声明目标 + 弹簧 + 活跃动效登记表」（资料 13-nanoui §3.4，且印证 `analysis/20` P1-5）。
- **P1-4　事件隧道（Preview / 隧道阶段）缺失**（资料主题 5：WPF 冒泡+隧道双路径）
  - 现象：grep 无 `Preview`/`tunnel`/「隧道」；只有「命中即目标 → 冒泡到祖先」。
  - 影响：祖先「先拦截再下传」（如全局快捷键、权限拦截、手势预处理）无法在事件下行阶段统一处理，只能在冒泡阶段补救。
  - 建议：在 `InputRouter` 命中后加「隧道下行」一遍（祖先先处理，`Preview*` 语义），与冒泡对称；先只给键盘/指针两个高频路径。
- **P1-5　文本无 `Rope`**（资料主题 7：GPUI 的 Rope + Tree-sitter + LSP 三件套）
  - 现象：`TextDraft`/`TextInputClient` 在，但无 Rope 数据结构；插入/删除大概率字符串拼接（`O(n)`）。
  - 影响：大文本编辑时每次输入整串拷贝；与文本状态机（选区/组合区/撤销栈）耦合后更贵。
  - 建议：文本编辑数据结构改 Rope（或 rope-like 的块链），插入 `O(log n)`；与选区/撤销栈一起设计。

### P2（治理 / 可优化，成本低）
- **P2-1　`Modifier` 的「父意图」族该升为 `ParentData` 值对象**——`Modifier.php:168` 已自述：「再加第三族（Dock 槽名 / Table 列提示）就该引入独立 `ParentData` 值对象，而不是第 28 个字段」。当前字段数接近该阈值，建议提前拆。
- **P2-2　视口渲染盒「夹裁剪矩形 + 画 thumb」去重**——`ScrollBarHost`/`ScrollBarFade`/`ScrollBarGeometry` 已共享几何/动画，但 `RenderScrollView` 与各虚拟列表/表格盒仍各自内联 paint（待核实 `RenderTable` 与虚拟列表盒是否同源）。
- **P2-3　`Modifier` 四类正交化（Compose Modifier.Node 思想）**——当前是一大值对象；若字段继续膨胀，可考虑「布局/绘制/输入/语义」四组子结构（不一定要链式节点树，但分组可内省）。
- **P2-4　编译期 `PatchFlag` 标注**——`Element` 运行期全量 diff；AOT 编译期已知结构，可标注「哪里会变」减少 diff 面（资料主题 3）。
- **P2-5　编译期依赖表 + 惰性 `computed`**——资料主题 2 的「自动订阅」Drift2 有意不采用（AOT 无 build 栈），但 `computed` 惰性派生可单独补（Vue 式，与显式订阅不冲突）。
- **P2-6　DPI 单源确认** —— ✅ **已做（2026-11-01）**。原判断（"`nodeScreenRect` 已用 `dpiOfWindow()`，只需查有没有第二处缓存"）**是错的**：`nodeScreenRect()` 是 **C++ 侧** UIA 的方法，PHP 侧根本没有 `dpiOfWindow` / `nodeScreenRect` 这两个名字。真实形态是**同一段换算被手写了六遍**（`Win32Platform::dprOf()` ×1 + `Win32WindowHost` ×4 + `Win32Screen::scale()` ×1），且六份的兜底**不一致** —— 五份写了 `<= 0 ⇒ 1.0`，`Win32Screen::scale()` 漏了 ⇒ 桥给 0 时它把 `0.0` 交给消费者做除数。已收成唯一入口 `Drift\Platform\Win32\Dpr::of()`，`Win32Platform::dprOf()` 删除。

## 4. 可优化：能替代只留一套（用户明确偏好）

**仍可合并（待核实）**：

## 5. 可借鉴 + 排坑（资料明确结论）

### 可借鉴（按可落地性，来自 13-nanoui §3）
1. **`drift doctor` 环境自检**（最高性价比）：把「人脑里的约束」变成断言——`PHPRC`、`opcache.enable=0`、`cl.exe` 在 PATH、`PHPX_HOME`、tpc 版本（源码树 vs 发行版）、Per-Monitor V2 DPI、`-m lib` 需源码树。
2. **CLI 全量 `--json`**：agent 驱动「构建→测试→快照」的前提；否则只能正则刮 stdout。
3. **`--script` 交互脚本 → 截图**：补「交互序列→视觉回归」空白（现有 golden 只测静态帧），一次投入同时服务 CI 与文档配图。
4. **动效改「声明目标 + 弹簧 + 活跃集合」**（P1-3）。
5. **字形图集**（P1-2）。
6. **双后端 / 跨平台像素一致测试**（P1-1）。
7. **DrawOp IR 按「可合批」组织**：同 pipeline/同纹理的连续 op 可并，而非纯顺序命令流（设计期输入，上 GPU 前定）。
8. **`drift new` 脚手架：AGENTS.md + 锁三版本**（Drift / tpc / phpx）。

### 排坑（资料明确「不该借鉴」+ 各框架教训）
- **不抄 immediate mode 主体**：会丢 reconcile 复用、Element 生命周期、1000+ smoke 断言面；nanoui 的 `Context.state` 本质是「在 immediate 上重建迷你 retained」。
- **不抄 0.7MB 单文件体积**：Drift 分发带 `libphp.so`+`libphpx.so`，下界由 PHP 运行时决定，当目标会逼出「砍功能换体积」。
- **不用 `layer`/`fixed` 替代 OverlayStack**：OverlayStack 有焦点陷阱/模态/scrim/锚点自动关，属性式撑不起；可吸收为语法糖。
- **不指望增量编译**：与 tpc 同病；改「双档验证」（解释器跑逻辑 + AOT 跑真机/像素）。
- **文本/IME 是自绘最大坑**（Flutter 十年未清）：选区/IME/放大镜/工具栏/撤销栈是一期工程，不是控件附属。
- **声明式连接静默失败**（WPF 字符串绑定 / Vue 解构丢响应）：任何绑定/订阅/能力查询失败要编译期错误或显式日志，不做「Output 窗口一行警告」。
- **编译期魔法必须可 inspect**（Compose 稳定性黑盒）：依赖表/脏集要能导出，否则「为什么没更新/为什么重组」无解。
- **事件隧道不要做成第二套分发**：与冒泡共用语义动作出口。

### 6.1 进展：先做了「每帧固定税」，不是脏矩形（2026-11-01 16:40）

**结论：上表里 M5 的顺位被一条更便宜的路抢走了。** 新增量具 `tools/frame-tax-probe.php` 量出：

| 规模 | 稳态帧（layout/paint 均跳过） | 同树全量 layout |
|---|---|---|
| 50 行 ≈ 200 节点 | 320µs | 841µs |
| 500 行 ≈ 2000 节点 | **3484µs** | 7192µs |

已落地（见 `FocusManager.php` 的注）：

- `walk()` 只在真的有人声明 `focusOrder` 时才收集+排序（无 order 时比较器恒 0 ⇒ 等价变换）；

- 稳态帧 **3484 → 850µs（-76%）**，`focus` 段 2.46ms → 0.002ms。5 条新测试钉住两条判据，两轮变异各红 2 条。

**M5 的触发条件因此写实**：它只在"**重建帧**已经掉帧"时才值得做（当前 2000 节点重建帧 ≈ settle + 7.2ms layout + paint，仍在 16.7ms 内）。判据是 `frame-tax-probe` 的 `layout(us)` 列 × 重建频率，不是"资料里有这一项"。同理，`tickAnimations` 的 926µs 仍是动画期的固定税，但它要重设计"帧时钟上膛"判据链（漏登记 = 动画静默停住），单独一轮。

## 9. 2026-11-01 夜：P1-1 改口径 —— 从"逐像素一致"到"一份换算，两个观察者"

### 9.1 原口径为什么是错的（不是"难做"，是"恒假"）

`SkiaCanvas` 的类注释早就写死了两条**有意**差异：抗锯齿（软光栅只对圆角/字形做覆盖度，
Skia 对所有边做）、描边（软光栅"外圈减内圈"，Skia 居中 `kStroke`），结论原话是
「**像素级 golden 不能跨后端比**，只能各自与自己的基线比」。

⇒ 「同一 golden 在 Raster/Skia 逐字节一致」在**设计上**就是个恒假命题。写成测试只有两个
结局：永远红（然后被 skip 掉），或者把容差调到没有牙。**两个都不是判据。**

### 9.2 成熟框架怎么做的（同一个思路：分层，不在像素上硬碰）

| 框架 | 做法 | 结论 |
|---|---|---|
| Chromium | pixel test 带 `fuzzy`（max pixels diff / avg error）+ 按平台分别 rebaseline | 承认平台差异，只钉"没变坏" |
| Skia `dm` | 同一 corpus 跑多 config，config 之间**不**逐像素比，各比各的 baseline | 同上 |
| Servo / WebRender | 参考测带 YAML `fuzzy` 注解 | 同上 |
| Qt `lancelot` | 按 paint engine 分基线 + 容差 | 同上 |
| Flutter | `matchesGoldenFile` 按平台分 golden，iOS/Android 互不比 | 同上 |

共性：**像素是后端私有的**。跨后端能共享的是它上面那一层 —— 命令流 / `DisplayList` /
设备几何。本仓本来就是这个形状（一份 `DisplayList`，两个回放器），所以口径该往上抬一层。

### 9.3 顺带查出来的结构病：同一个公式抄了六处

`toDevice()` 在两个后端里**逐字重复**（`SkiaCanvas:758` / `RasterCanvas:1560`），
另有三处更散的拷贝：`SkiaCanvas::drawLine` 四个标量、`packPath()` 六个标量、
`applyPaintSource()` 四个渐变端点；软光栅侧 `deviceX/deviceY` 各一份。

`Scale` 的类注释写着「全框架**只有这一个量化函数**……别处一律不许取整」——
**这句话当时是假的**：取整在 `Scale` 里，而"加偏移"在它外面，抄了六遍。

处置：`Scale` 新增 `deviceRect()` / `deviceX()` / `deviceY()`，**顺序写死为"先加偏移、
再一次量化"**；两后端的 6 处拷贝全部改走它。软光栅的私有 `deviceX/deviceY`（矩阵感知
那一层）改名 `transformedX/Y`，免得与 `Scale::deviceX()` 混读。

### 9.4 判据：同一个 `DisplayList`，两个观察者

`tests/Feature/Rendering/BackendDeviceSpaceTest.php`（5 个方法 / 30 条断言）

| 观察者 | 能观察到什么 | 读法 |
|---|---|---|
| `SkiaCanvas` | 桥收到的参数（**就是设备坐标**） | 假桥记录 |
| `RasterCanvas` | 像素 | `inkBounds()` 取墨迹盒 |

两边都必须等于**同一个规格**：`round((逻辑值 + 偏移) × dpr)`；规格在测试里**用定义重算**
（`self::dev()`），**不调** `Scale::deviceRect()` —— 调了就是"测试与实现共用一份错"。

覆盖：填充矩形（无偏移 / 整偏移 / 半像素偏移 / dpr=2 / 圆角）、椭圆、描边（+**内部是空的**）、
线段（4 个端点 + 宽度不乘 dpr）、路径（解包桥收到的 float32 顶点）。

容差：矩形族**精确相等**（实测椭圆 `[13,13,32,24]` 与规格逐位相同，不留余量）；
路径 ±1，理由算得出来 —— 三角形最右是**一个顶点**（设备 x=23），中心采样在 y=7.5 时
右端只到 22.47 ⇒ **最后一列没有像素中心落入**，墨迹到 21 是对的，不是缺陷。

### 9.5 变异自检（4/4 有牙）

| 变异 | 结果 |
|---|---|
| `Scale::deviceX()` 漏掉偏移 | 红 2 条 |
| `Scale::deviceRect()` 先取整再加（顺序反了） | 红 1 条（半像素那行） |
| `RasterCanvas::toDevice()` 漏偏移 | 红 2 条 |
| `packPath()` 丢掉偏移（命中 2 处） | 红 1 条 |

外加一个"量具自检"方法：证明**规格本身不恒真**（漏偏移 / 顺序反了都会算出不同的盒子）。
第一版这条自检是假绿 —— 挑的 `1.5 + 0.5 = 2.0` 恰好与 `round(1.5) = 2` 撞上；
换成 `1.2 + 0.4 = 1.6 ⇒ 2` vs `round(1.2) = 1` 才有牙。

### 9.6 这一轮**没**做的

- **真机 Skia 基线**：真 Skia 光栅在 `php.exe` 里跑不到，所以本判据的 Skia 侧观察的是
  **桥参数**而非像素。要真比像素只能走 exe + 截图（`probe-*` 那条路），成本高一个量级
  ⇒ 按"不提前投资"留到有第二个平台后端时再说。
- **跨平台（Win/Linux/mac）**：同 9.1 的理由，各平台各自基线，不互比。
- **没动** `tools/smoke.php` 里 P3 那批 Skia 参数断言：它们是硬编码元组、全是
  dpr=1 / 偏移 0，但那是"某个具体 bug 的现场记录"，改成表驱动会丢掉那层信息。

### 9.7 P1-1 的最终结论

**不是"补一个测试"，是"改一个口径 + 收一处重复"**：结构上没了重复实现（漂移不可能），
判据上同一份规格被两个后端各验一次（漂移一发生就红）。原口径那个"逐字节一致"从
待办里删掉 —— 它永远不会被做对，只会被调宽容差。

## 10. 2026-11-01 深夜：探针骨架收成三件 —— "不许有第二条输入通道"

### 10.1 这一节要解决的问题不是"代码重复"，是"探针会说谎"

上一节（§8）的结论是"量具坏了，不是管线坏了"。这一节把**为什么量具会坏**修掉。

盘出来的是这样一张表（`tools/probe-*.py` 9 个文件 / 2645 行）：

| 同一件事 | 有几份实现 | 漂成了什么样 |
|---|---|---|
| 输入通道 | **5** | 真的 `SetCursorPos`+`mouse_event` / 纯 `PostMessage` / 混合 |
| 截图 | **4** | `bytes` / `bytearray` / 类 / 少一次 `SelectObject` 还原 |
| 启动（`PHPRC`） | **9** | 两份写 `encoding="ascii"`、七份 `utf-8` |
| 结论 | **4** | 全是 `ok`/`FAIL` 两态 —— **"没测到"无处可写** |

这张表里没有一条是风格问题。**输入通道**那 5 份里，3 份走的是已证伪两次的路
（`PostMessage` 只让应用"知道"指针在哪，`TME_LEAVE` 与 `ScrollBarFade::noteScroll()`
认的是真实光标/真实消息）⇒ 应用照常推进状态、动画也跑满，画面不变，探针报
"一像素不动"，产品是好的。**结论**那 4 份两态 ⇒ 采不到目标时只能写 `FAIL`，
于是"我没采到"被读成"产品坏了" —— §8 白追的 90 分钟就是这么来的。

### 10.2 成熟框架怎么处理这件事（同一个答案：通道只有一个）

| 框架 | 做法 |
|---|---|
| Playwright / Puppeteer | 只有一个 `Input` domain（CDP `Input.dispatchMouseEvent`），测试作者**选不了**"真发还是假发" |
| FlaUI / WinAppDriver | 只有一个 `Mouse` 类（`SendInput`），`MoveTo`/`Click`/`Wheel` |
| pyautogui | 整个生态共用它当唯一输入层 |
| pytest / Playwright | `skip()` 是**一等结论**，与 `fail()` 分开：没条件测 != 测坏了 |

共性两条：**① 输入是能力，不是每个测试自己的帮手；② "没测成"必须是一等结论。**

### 10.3 落地：三件共享 + 一条会红的判据

| 件 | 管什么 | 关键设计 |
|---|---|---|
| `tools/probe_win.py` | 启动 / 找窗 / 抢前台 / 截图 / **真实输入** / 收尾 / 用户状态隔离 | **假的那条路根本不导出**（连 `PostMessage` 包装都不给）；`move/click/wheel` **每次调用前**都验 `GetForegroundWindow() == hwnd` |
| `tools/probe_check.py` | 三态结论：PASS / FAIL / **没测到（SKIP，退出码 2）** | `need(value, why)` 是"采不到 ⇒ SKIP"的唯一写法；`run()` 收尾，**失败优先** |
| `tools/probe_pixels.py` | 像素定位（§8 已有） | 本轮补 `near()` / `nonwhite_ratio()`，收掉两份 `near` |

三个决定值得单独记：

1. **假通道不可表达**，不是"文档说不许"。探针想再造一条假路，得自己重新
   `ctypes` 一遍 —— 那时 `probe-audit` 会红。**约定挡不住，闸门挡得住。**
2. **输入前逐次验前台**。不是启动时验一次就够：中途被别的窗口抢走，
   后面每一次点击都会落到那个窗口上。宁可中途 SKIP，也不要量出一组假的数。
3. **三种"没前台"分开报**（这是本轮最实用的改进）：
   `GetForegroundWindow() == 0` ⇒ 会话里**没有**前台窗口（桌面锁定 / 非交互会话，
   `SetForegroundWindow` 实测 `GetLastError = 1400`）；`!= hwnd` ⇒ 被别的进程占着。
   合并成一句"抢不到前台"，下次还得重查一遍。

## 11. 2026-11-02 晨：桌面解锁后的真机复核 —— 抓到一个"共享件语义漂移"

### 11.1 昨晚留下的四件 SKIP，现在四件全绿 —— 但过程里发现了一件更要紧的事

桌面锁定时（§10）四个输入类探针只能报 SKIP。桌面解锁后逐个真跑：

| 探针 | 结果 |
|---|---|
| `probe-scroll-diag.py` | **0 FAIL（3 条）** —— 条在 `x=921..926`，luma **119.3 → 207.7** |
| `probe-motion.py` | **0 FAIL（7 条）** —— 悬停 ring 202px / 盒内 1910px / 移开回 0；条 119.3 → 207.7 → 120.3 |
| `probe-modal.py` | **0 FAIL（10 条）** —— 遮罩 −35.3%、面板 49525px、X 墨迹 30px、反例无 X |
| `probe-scrollbar.py` | **0 FAIL（7 条）**（换了目标页，见 11.4） |

与解释器级判据（`ScrollBarFadePixelTest`）**逐位相同**：119.3 / 207.7。产品侧没有任何变化。

### 11.2 但 `probe-motion` 第 1 条先红了：`blocks=[]`

「找不到墨绿按钮块」。追下去发现 **`px()` 的通道顺序在上一轮迁移时被悄悄换掉了**：

| | 迁移前（`probe-motion.py` 自己的 `px`） | 迁移后（`probe_pixels.px`） |
|---|---|---|
| 返回 | `data[i+2], data[i+1], data[i]` = **RGB** | `data[i], data[i+1], data[i+2]` = **BGR** |
| `PRIMARY = (0x00,0x96,0x88)` | 对得上 | 实测拿到 `(136,150,0)` ⇒ **永远不等** |

`(136,150,0)` 正是 `(0,150,136)` 的 R/B 对调 —— **同一个颜色，翻个序依然是合法颜色**，
所以肉眼看截图完全正常，只有"跟常量比"才会失败。

★ 为什么它能活过一整轮：**灰度判据对翻序不敏感。** 亮度 `(r+g+b)/3`、低饱和
`max-min` 都不在乎谁在前，于是滚动条那 3 条一直是绿的，把整个迁移期盖住了；
而唯一会红的第 1 条，昨晚恰好因为"没有前台窗口"被 SKIP 掉。
⇒ **「SKIP 不等于迁移通过」**，这是这一轮最贵的一句话。

★★ 同一份字节流在**同一个文件里本来就有两种语义**：`nonwhite_ratio()` 一直按
`data[i+2], data[i+1], data[i]` 读（RGB），而 `px()` 读 BGR。这种"一个文件两套约定"
正是当初"9 个探针各抄一份"造成的，只是抄的时候两份**恰好不同**。

### 11.3 处置：让共享件语义正确，并自己证明一次

1. **`px()` 改为返回 `(r, g, b)`** —— 与主题色常量 / `Color::fromRgb` / CSS 同一顺序，
   BGRA 的翻序**只在这一个函数里**发生。调用方零改动（它们本来就是按 RGB 写的）。
2. **`probe_pixels.selftest()`（新，11 条）** —— 量具的契约必须自己证：
   * 合成一块已知 BGRA 缓冲 ⇒ `px()` 必须给回 RGB；**并且**必须不等于对调值
     （对调后仍是合法颜色，只能靠这条抓）；
   * `find_scrollbar` 四个方向：白底 ⇒ None、**页面底色** ⇒ None（假红原形）、
     6 宽段 ⇒ 定位到、3 宽窄带 ⇒ 不算条；
   * `column_luma` / `nonwhite_ratio` 的灰度口径。
3. **闸门加第 11 项 `pixels`**，并给闸门补上**三态**：只有显式声明为
   `$may_skip` 的检查（现在是"依赖本机装了 python"这一项）才允许退出码 2 / 命令缺失，
   跳过**单列在总结里**，绝不折算成通过。

变异自检：把 `px()` 改回 BGR ⇒ `selftest` **红 4 条**（`got=(136,150,0)` 那组）。

### 11.4 顺手救活了一个"只会 SKIP"的探针

`probe-scrollbar.py` 原本验 `users.exe` 列表页，理由是"种子 15 用户溢出 `maxScroll≈64`"。
实测：滚轮不动、右 80px 内**零个** Muted 墨点 ⇒ 这页根本不溢出、按设计不画条
（§10.6 记的"整屏只有 4 个 Muted"其实也是通道对调造成的假数，修好后同一页量到 269 个）。 

一个只会 SKIP 的探针等于没有探针。改成验**确实溢出**的 showcase「长列表 Big」，并补两条
一直没人做的判据：

| 判据 | 值 | 意义 |
|---|---|---|
| ④ 条离客户区右缘有留白 | 33px | **条在视口右缘、不在窗口右缘** —— §8 两次假红的那个假设，现在会直接红 |
| ⑤ 滚 200 格 ⇒ thumb 下移 ≥ 4px | 7px | 跟手 |
| ⑥ 滚回顶部 ⇒ 回到原位 | 0px | 位移是双向的 |

两个"看起来像产品缺陷、实际是量法欠账"的坑也在这一节里被记下：

* **条长被量成 22px（< `MIN_THUMB` 24）**：条的上下端是抗锯齿边 `(123,131,140)`，
  与 `Muted` 差 13/14 ⇒ 任何 `tol < 15` 的精确匹配都会两端各吃掉一行。
  改按**墨迹**量（`luma < 222`）后量到 **24**，与常量逐位对上。
* **"滚 1 格 thumb 不动"**：10000 行 × 44px ⇒ 内容高 44 万，一格只该动
  `360 × 48 / 439600 ≈ 0.04px`。**那是比例滚动条的正确行为。** 判据改成 200 格。
* **⑥ 一度报 -221px**：墨迹阈值取 200 时，**淡出后**的条（208）不算墨 ⇒ `thumb_shape`
  退化成把顶栏那 2 行边框当 thumb。阈值改成 222（区间必须同时 > 208 且 < 236）。

### 11.5 这一轮的结论

三轮下来，"探针骨架收成三件"（§10）只解决了一半：**共享件的结构统一了，语义没被证明。**
现在补上的是后半句 —— **共享件必须自带契约自检，SKIP 不能当作迁移通过。**

## 12. 2026-11-02 上午：量具自己会说谎 —— 1000× 的单位、过期的注释、进闸门的判据

### 12.1 起点：上一棒说"下一格只有异步流"，先证了一遍"不该做"

上一轮的交接是「M5 未到触发条件 · 异步"流"是唯一整维缺口」。按本仓纪律
（**未被消费的分支 = 未实现**）先把"流"证伪了一遍：

| 问 | 答 |
|---|---|
| `src/Async/` 真的只有 2 个类？ | 是（`Future` / `AsyncValue`）。但**"流"的零件到处都是**：`Subject`（订阅即推送）、`IoPoller::watch`（回调流）、`completionQueue`（先记账再交付）、`Future::all`（多值并发） |
| 缺的是状态层类型？ | 不是。`AsyncCommand::append()`（追加语义）**已经有真实消费者**（`showcase` 的「加载更多」页 + App\`LoadMorePageTest`），`Future::all` 也有 `ConcurrentFetchPage` |
| 那"进度 / 日志 / WebSocket"呢？ | **零消费者**。`apps/users`、`showcase` 里没有一个"已知长度的长任务" |

⇒ `StreamValue` / `AsyncStream` 仍然**不做**（`ASYNC-ARCH-2026-10-31.md` §7.3 的裁决
继续有效）。再造一个没有消费者的类型，违反的是本仓自己的第一条账：*未被消费的分支 =
未实现*，而且这次连"将来会有人用"都说不出口。

### 12.2 于是回到唯一有实测数的那一项 —— 一上手就发现量具在说谎

排期里唯一带数字的是「每帧固定税」（§6.1：稳态帧 3484 → 850µs）。重跑
`tools/frame-tax-probe.php`，输出是这样：

```text
   500          985.7       7251.4       0     50
       分段: pumpIo=0.98ms  pumpTasks=0.88ms  anim=972.92ms  ...
```

**稳态帧 985.7µs，而 `anim` 段 972.92ms** —— 同一份输出里两个数差了三个数量级，
却从来没有人在三轮里多看一眼。追下去是**三个独立的假**：

| # | 假话 | 真相 | 为什么它能活下来 |
|---|---|---|---|
| ① | `SurfaceProfile::perCall()` 按 ms 打印 | 它返回**纳秒**；探针写了 `round($v/1000).'ms'` ⇒ 每段被印成 **1000 倍** | 读者会"自动校正"（心里知道是 µs），于是错误被读懂了、没被修 |
| ② | 注释写"每次调用**中位**纳秒" | 算式是 `累计/次数` = **平均** | 两种都合理，只差一个词；用它做决策时口径不同 |
| ③ | `gate.php` 头写"合计 **63.4s**、smoke **448** 条" | 实际 **120s 量级**、smoke **460** 条 | 数字没有判据 ⇒ 必烂，且烂了没人发现（`MEMORY` 里记的是对的，代码注释里是错的） |

★ 这一轮的判断：**①②③ 是同一个病 —— "量具的说明书/输出"没有判据。**
上一轮（§11）刚学会"共享件要自带契约自检"，这一轮把同一条纪律推到**人读的那一面**：
单位换算、聚合语义、耗时数字，只要写在人眼前，就必须能被证伪。

### 12.3 处置一：ns→文本的换算收成一份，并让契约自己证一次

`SurfaceProfile` 新增 `formatNs()`（`<1µs → ns`、`<1ms → µs`、否则 `ms`），
探针不再自己算；新增 `selfTest()` 两条：

* **单位**：`formatNs(1000)=='1µs'`、`(972920)=='972.92µs'`、`(1500000)=='1.5ms'`…七档；
* **聚合**：同一段两次 2000ns ⇒ `perCall()` 必须给 **2000**（平均），给 4000 就是
  "累计冒充每次"。

这与 `Scale::deviceX()` 是同一条纪律：**同一件事写两遍必然漂移**。差别是这次漂的是
人眼读的那一侧，代价是"拿错三个数量级的数去判断要不要重构管线"。

### 12.4 处置二：把"报告"变成判据（`--check` 六条）

原来这个文件头写着「**别拿它当门禁**：墙钟数随机器浮动，`gate` 里放它只会变成一台
随机失败的机器」。那句话对**绝对耗时**成立，对**自洽性**不成立 —— 六条判据里
**没有一条是墙钟阈值**：

| # | 判据 | 能红的真实事故 |
|---|---|---|
| ① | `SurfaceProfile::selfTest()` | 单位换算写错（就是今天这个 1000×） |
| ② | 每个分段 ≤ 整帧 × 1.25 | 量具自相矛盾：单位错 / 同一段重复计时 |
| ③ | 分段里必须出现 `anim` | **"没扫到"冒充"没有"**（否定结论要自证扫到了东西） |
| ④ | 稳态帧 paint 全跳过（run=0 && skip=帧数） | paint 门控退化 ⇒ 每帧整树重画 |
| ⑤ | `layout` 段 ≤ 全量重排的 5% | layout 门控退化 ⇒ 稳态帧变成全树重排 |
| ⑥ | 三个版本号全 `+0` | "稳态"前提不成立（帧在自激）⇒ 后面所有数字不可信 |

★ ⑤ 是**比值**不是毫秒：分子分母是同一棵树上的**同一种操作**，机器慢了两边一起慢
⇒ 比值稳。这是它敢进闸门的唯一理由（`Scale` 那条"只比同量纲"的同类）。
★ 闸门第 **12** 项 `tick`（`~0.6s`，非慢项）。

### 12.5 变异自检（3/3 有牙，且第一次运行抓到了自己的绿壳）

| 变异 | 结果 |
|---|---|
| `formatNs` 的 µs 分支除数 1000 → 100 | ①红，**exit 1** |
| 探针里伪造一个 200ms 的分段 | ②红，exit 1 |
| `Frame::run()` 的 layout 门控改成 `if (true)` | ④红（run=30/skip=0）**且** ⑤红（92.2%），exit 1 |

★ 同一份契约在**测试**一侧也钉了一遍（`tests/Feature/Rendering/SurfaceProfileContractTest.php`，
3 个方法 / 16 条断言）：单位八档边界 + `perCall()` 是平均不是累计 + `selfTest()`
只读不污染现场。变异：`formatNs` 除数 1000→100 ⇒ 红 2 条；`perCall()` 改成返回累计
⇒ 红 2 条。

★★ **第一版判据自己是绿壳**：它先无条件印 `ok ②`，再在末尾补一行 ✗ —— 同一份输出里

下面紧跟着 `✗ ② …超过整帧`）。改成"**先算结论，再选 ok / FAIL 打印**"之后，
每条只有一个说法。⇒ 判据的形状也要被变异检验，不是只有判据的内容。

### 12.6 用修好的量具重读 §6.1：那条"两个全树遍历各占一半"已经过期

| 段 | 2026-11-01（§6.1） | 2026-11-02 实测（500 行 / 2000 节点） |
|---|---|---|
| 稳态帧 | 3484 → **850µs** | **993.5µs** |
| `focus`（`FocusManager::collect`） | 2462µs → **0.002ms** | **1.52µs** |
| `anim`（`tickAnimations` 全树） | 995µs | **980.71µs（98.7%）** |

⇒ 固定税的**结构变了**：focus 已经降到噪声，稳态帧现在**几乎全是**全树 tick。
§6.1 里"两者各占一半"的框架不再成立；要再动这一项，目标只剩动效表。

**但仍然不做**，理由有数：① 2000 节点是**合成**最坏树（`Column` 全量，不是
`LazyColumn`）——真实页面的可见节点是十几到几十；② 这笔税只在**帧已经在跑**时付
（空闲时 `wantsFrame()` 为假，根本不进 `frame()`），而帧在跑时本来就是要推进动画。
⇒ 收益是"动画帧的 6% 预算"，风险却是"漏登记 = 动画静默停住"（`MEMORY` 已记：登记表版

- **上限 = 最重页的全量重排 ≈ 1.5–2.0ms = 帧预算的 9–12%**；
- 而且这 9–12% 只在"**整页重排、且大部分子树没变**"这一种形态下才拿得到。实测的两种
  真实形态都不属于它：整页重建（盒子全新，M5 一个都跳不过）与单点交互（本来就只重排

⇒ 投入产出比明确不成立。**M5 的判据因此写实并可复查**：最重页全量重排 > 16.7ms 时再做，

冷 2.2ms / 暖 0.09ms）。这是**文字 shaping 的首次成本**（`DeterministicMetricsProvider`

## 14. 2026-11-02 中午：用户截图里的 `class ... is undefined` —— 一个漏 `use` 活过了四道闸门

### 14.1 症状

任务跑完、结果出来了，点"下载结果图"：

```text
下载结果图失败：class 'App\Watermark\Store\DownloadResultsJob' is undefined
```

`DownloadResultsJob` 住在 `App\Watermark\Jobs`，而报错里的命名空间是 `Store` ——
这是 **PHP 的"短名回退"**：文件里没 `use` 的短名一律解析到**当前命名空间**。

### 14.2 根因（一行）

`WatermarkStore` 顶部有四个 `use App\Watermark\Jobs\*Job`，唯独漏了第五个：

```php
return $host->submit(new DownloadResultsJob($urls));   // ← 解析到 App\Watermark\Store\DownloadResultsJob
```

**为什么四道闸门全绿**（这一段才是重点）：

| 闸门 | 为什么没拦住 |
|---|---|
| `php -l` | 只查语法。未导入的类名是**合法语法** |
| lint（当时 23 条） | 有一条 `instanceof-missing-use`，但只认 `instanceof` 这一处语境 |
| smoke / phpunit | 全走 `$host === null` 的**同步降级路径**；`$host->submit(...)` 那一行**只在真机可达** |
| AOT 编译 | 那行是**可达**的，编译照样过 —— 它失败在运行期，不在构建期 |

⇒ 本仓写过很多次的那句话在这里又成立一次：**未被消费的分支 = 未实现**。
"真机唯一走的那一半"此前**没有任何一条判据落在上面**。

### 14.3 处置一：补 `use`（1 行）

### 14.4 处置二：把判据补成规则（`class-missing-use`，lint 第 24 条）

不新增解析能力，只把 `instanceof-missing-use` 的判据**推到另外三处同样"加载时不报错"的语境**：

| 语境 | 不修会怎样 |
|---|---|
| `new X` | 运行期 `class not found`（本次事故） |
| `X::` / `X::class` | 运行期 `class not found`；**`::class` 更糟 —— 静默返回字符串，连错都不抛** |
| `catch (X $e)` | **连错都不抛**，这条 catch 永远不命中（与 `instanceof` 同一种静默） |

复用而不是复制：

- `Project::symbolFqcn()` / `Project::symbolsByShortName()` —— 两条规则共用同一份符号索引
  （大小写不敏感，PHP 类名本来就大小写不敏感）；
- `SourceQuery::classNames()` —— 三处语境的 token 遍历只此一份；`extends`/`implements`
  **故意不收**（漏 use 在类加载时就 fatal，任何一次挂载都会红，静态规则只是重复已有的保险）。

夹具双向：`ClassMissingUseBad.php`（new / `::` / catch 各一条 = 3 个 error）+
`ClassMissingUseGood.php`（use 过、全限定、内建类 catch、`self::` 与变量左侧 —— 一条都不该响）。
★ 反例里**故意不放匿名类**：本仓 `nano-hygiene` 直接禁匿名类，拿它当反例只会让两条规则打架
（第一版就这么撞了，自检当场报出来）。

### 14.5 规则落地当天就抓出第二处（同样是真 bug）

```text
apps/bench/src/M0Nullable.php:50  error  class-missing-use  静态访问 Errors ...解析落到 Drift\Bench\Errors
```

`Errors::report()` 漏 `use Drift\Errors` —— 那个夹具的用途是"自检失败时给出诊断"，

### 14.6 处置三：给"真机那一半"写判据（这才是根治）

规则只管"类名看不看得见"，管不了"这条分支有没有被执行过"。所以补了
`tests/Feature/Watermark/StoreHostChainTest.php` + `tests/Support/RecordingTaskHost.php`：

- `RecordingTaskHost` —— 按任务类名回一个**已结算**的 `Future`（`then()` 在已结算的
  Future 上立刻跑 ⇒ 整条链在一个调用栈里走完，不用推帧）；未配置的任务类返回

- 判据 ③：每个提交过的任务都能被 `JobRegistry` 用 `args()` **原样重建**
  —— 这是 `NamedJob` 的跨进程契约（worker 侧只有名字 + 参数），
  也顺带钉住"注册表没漏登记"。

### 14.7 写判据的过程里抓到第二个真 bug：接力标志被 `loading` 通知吃掉

给 `upload()` 写判据时链路只走到 `FetchSignJob` 就停了。追下去：

```php
$relay = $this->uploadAfterSign;   // 无条件消费
$this->uploadAfterSign = false;
```

`AsyncCommand::start()` 会先 `emit(loading)` **再**落地，而 `absorbSign()` 对**每一次**
通知都跑 ⇒ **那一趟 loading 就把接力标志清掉了**，等签名真到手时 `$relay` 已是 `false`：
**签名取回来了，却永远不接力上传**，界面停在"正在获取上传凭证…"，不报错。

真机上这条路径被"启动预热"掩盖：预热先拿到签名 ⇒ 点上传走的是 `upload()` 里
"签名还有效"那条直路 ⇒ 接力分支从没被走到过。修法：只在**终结态**（`hasData()` /
`hasError()`）消费标志。

★ 这是本仓"**中间态通知**"这一类坑的又一张脸：**订阅者对每一次通知都跑，
但只有终结态才该改变"接下来干什么"**。

## 15. 2026-11-02 下午：真机崩溃零日志 —— 先造"崩溃的量具"，再说根因

### 15.1 症状

用户报"任务完成后崩溃了"。机器上能拿到的**全部**证据只有一条 Windows 事件日志：

```text
错误应用程序名称: watermark.exe      错误模块名称: php8ts.dll
异常代码: 0xc0000005                 错误偏移量: 0x0000000000024b30
```

没有栈、没有 dump、没有日志文件。`%APPDATA%\Drift` 下只有 `.window` 状态文件，
WER 的 `ReportArchive` 是空的。

★ 这本身就是缺陷，而且是本仓最熟悉的那种：**崩溃这条路径此前一条判据都没有**。
上一轮（§12）刚收口"量具的说明书会撒谎"，这一轮遇到的是它的对偶 ——
**没有量具**。用户说"崩了"，我们只有一行 `php8ts.dll+0x24b30`。

### 15.2 先把手上的一个数榨干：`0x24b30` 落在哪个运行时函数

没有调试器也能定位 —— `php8ts.dll` 有**导出表**，读它就能得到"哪些 RVA 是函数入口"。
按 RVA 排序后取崩点的前后邻居：

| 相对位置 | RVA | 符号 |
|---|---|---|
| 前一个导出 | `0x24870` | `zend_object_std_dtor`（崩点在它 **+0x2c0**） |
| **崩点** | **`0x24b30`** | **夹在两者之间 —— 一个未导出的内部函数** |
| 后一个导出 | `0x24ed0` | `zend_memnstr_ex` |

⇒ 崩点不在业务代码、不在 AOT 生成的代码，而在 **PHP 运行时的"对象释放"族**
（`zend_object_std_dtor` / `zend_objects_store_del` / `zend_object_release` 这一带）。
它们是 `static` 的、不进导出表，所以只能给到"区间"。

★ 这条结论的方法是可复用的：**导出表就是最便宜的符号表**。`dumpbin /exports` 能干的事，
二十行 Python 读 PE 头也能干，而且不用装任何工具（本机没有 cdb / windbg / procdump）。

### 15.3 但"对象释放时崩"这句话有两个截然不同的含义

| 含义 | 现场长什么样 | 怎么证 |
|---|---|---|
| **A. 释放路径自己写错** | 每次走到都会崩，可稳定复现 | 一复现就崩在同一 RVA |
| **B. 堆早被踩坏，释放只是第一个受害者** | 崩点会漂（这次 `+0x24b30`，下次别处）、崩的时机看起来"毫无关系" | 崩点不稳定 ⇒ 回头找**写坏堆的那一次** |

两种处置完全不同（A 改那段代码，B 要抓"谁越界写"），而**只看一条事件日志分不出来**。
⇒ 必须先有栈。这就是下一节那三件东西存在的唯一理由。

### 15.4 处置一：崩溃捕获（`cpp-src/win32/crash_report.cc`）

`SetUnhandledExceptionFilter` + `CaptureStackBackTrace`，写
`%APPDATA%\Drift\crash-latest.log`（固定名，找最近一次不必翻目录）+ `crash-<pid>-<tick>.log`（留现场）。

内容全部是 **模块名 + RVA**：ASLR 每次换基址、换机器更不一样，RVA 在同一份产物上稳定。

红线（写在头文件里，因为它就是这套东西的全部难点）：

- **不碰 CRT 堆**：不用 `std::string` / `new`。崩的时候堆可能已经坏了，再分配是二次伤害。
  缓冲全是栈上定长数组 + `CreateFileW`/`WriteFile`。
- **过滤器自己崩了不能套娃**：`InterlockedExchange` 守卫，重入直接放行。
- **不尝试继续执行**：返回 `EXCEPTION_EXECUTE_HANDLER` ⇒ 进程照常终止。堆已坏时"继续跑"只会让
  下一个崩溃点漂移，把现场冲掉。
- **日志只写 ASCII**：本文件是 UTF-8，而 MSVC 对窄字符串字面量按 ACP 解释
  ⇒ 中文会写成 GBK 字节。崩溃日志是要被各种工具读的，别赌编码（第一版写了"崩点"，
  改成了 `crash point`）。

挂载点选 `php_drift_win_create()` 开头，不是 `main()`：后者由 tpc 生成、改不了；
而**任何** GUI 进程都必然先建窗 ⇒ 覆盖面与本仓的应用形态一致。

### 15.5 处置二：`/MAP`（`build/base.yml`）

日志给 `watermark.exe+0x1a2b3c`，但 exe 没有 pdb、没有 `/DEBUG` —— 那个数是**没法读**的。
`/MAP` 是链接期顺手生成的纯文本对照表（27.9 MB），比 pdb（要 `/DEBUG` + `/Zi`，
拖慢构建、放大 exe）划算得多。产物与 exe 同目录、已在 `.gitignore`。

### 15.6 处置三：`tools/rva2sym.php`（把这个数变成函数名）

```bash
php tools/rva2sym.php watermark.map --log "$APPDATA/Drift/crash-latest.log"
```

解析 map 的 `Preferred load address` 与符号行（**严格要求第 4 列是 16 位十六进制地址**
⇒ 段表行 `0001:00000000 00331f70H .text CODE` 自然被排除，不需要另写一条"跳过段表"分支
—— 那种分支就是漏判的来源），二分找 `<= rva` 的最近符号并给出偏移，再反修饰。

反修饰认两种名字：

| 输入 | 输出 | 规则 |
|---|---|---|
| `?seek@Foo@@UEAA_N_K@Z` | `Foo::seek` | MSVC 修饰名：`@` 前是函数，后面倒序是类 |
| `php_drift__app__bar__run` | `drift\app\bar::run` | AOT 的 PHP 函数：`php_` + `__` 分段的命名空间/类/方法 |
| `php_drift__app__store____construct` | `drift\app\store::__construct` | ★ `____` = 分隔符 `__` **加上**名字自己的 `__` |

★ 第三条是 `--selftest` 抓出来的：第一版用 `array_filter` 把 `explode` 出的空串当噪声滤掉，
于是 `__construct` 变成了 `construct`。**空段不是噪声，是魔术方法的标记**。

### 15.7 三件的自证（谁也没被放过）

| 件 | 自证方式 | 结果 |
|---|---|---|
| `crash_report.cc` | `_build/crash-selftest/` 里一个独立小程序：装过滤器 → 写空指针 → 真崩 | `access=write target=0x0`、`addr=selftest.exe+0x100b`、9 帧栈；`#5 … <== crash point` |
| `/MAP` | 同一程序用 `/link /MAP` 重编 | 生成 `selftest.map`（★ cl 不认裸 `/MAP:`，必须 `/link /MAP:`） |
| `rva2sym.php` | `--selftest` 六条（合成 map，不依赖构建产物）+ **端到端跑一次真实崩溃日志** | `selftest.exe+0x100b ⇒ +0xb main`、`#6 +0x10f __scrt_common_main_seh` |

端到端那一跑是关键：**三件串起来**才有意义（日志 → map → 函数名），
分开各自"看起来对"没有说服力。

闸门新增第 **13** 项 `sym`（0.3s，纯 PHP、无构建前置）。

★ 顺带修了一处自己的绿壳：`--selftest` 加了第 ⑥ 条判据之后，总结行还印着"5 项判据全过"
—— 改成 `count($items)`。**判据数量与文案不一致，就是一份会说谎的输出**（§12.5 的同一条病）。

### 15.8 顺带确证的一条结构事实：`?Obj` 在 AOT 里真的退化成 `php::Variant`

map 里的符号名是修饰名，反修饰就能看到真实签名：

```text
?php_drift__rendering__imagedecoder__decode@@YA?AVVariant@php@@AEAVObject@2@VString@2@@Z
  ⇒ class php::Variant __cdecl php_drift__rendering__imagedecoder__decode(class php::Object &, class php::String)

?php_drift__rendering__imageloader__load@@YA?AVVariant@php@@AEAVObject@2@VString@2@@Z
  ⇒ class php::Variant __cdecl php_drift__rendering__imageloader__load(class php::Object &, class php::String)
```

两者都声明为 `?ImageHandle`，AOT 里都成了返回 `php::Variant`。本仓 `ImageLoader` 的注释
早就写过这件事（"`RenderImage` 的字段永远是非空 `ImageHandle`，不必引 `?ImageHandle`"），
但**没有判据**，所以它一直只是注释。

★ 这一条**不是**本次崩溃的证据 —— 只是"释放路径崩溃"的一个候选方向（Variant ↔ Object
的引用计数如果少加一次，对象就会被提前释放）。**没有栈之前不动它**：改返回类型会波及
`ImageLoader` 的缓存与 `RenderImage` 的字段，属于"用猜测换大改"。

### 15.9 这一轮没做的

- **根因**：等真机复现的栈。现在能确定的只有"崩在对象释放族"。
- **`?Obj` 收口**：见 §15.8，要证据不要直觉。
- **`crash_report.cc` 进闸门**：它要 MSVC 才能自证，而闸门必须能在纯 PHP 环境跑完；
  自证过程记在 §15.7，靠"改这个文件就跑一次"的人工纪律。

## 16. 2026-11-02 下午：颜色不对 —— 六条判据全绿，因为"错得很整齐"

用户报「图片的颜色不对」，附一张结果图预览的截图：照片整体发蓝，白墙是冷蓝的。
上一棒（§15.9 之后）刚把解码从纯 PHP 换成 WIC 并按显示尺寸缩放，所以嫌疑面很窄。

### 16.1 先给"颜色对不对"造一把尺

不能靠眼睛判"偏蓝了 5%"。**文件本身**才是基准：`tools/png-ref-dump.py` 用纯 Python
按文件字面字节解（zlib + 五种滤波重建，16 位取高字节），跟 WIC 走的是两条完全
不同的代码路径。同坐标一比，事情就没了余地：

```text
原尺寸 (1792x2390)  896,239  ->  (223 216 210)  暖白
缩放后 (1120x1494)  560,149  ->  (210 216 223)  冷蓝      ← R/B 互换

原尺寸 1075,717 -> (255  23  86)  红
缩放后  672,448 -> ( 85  22 253)  蓝

均值  原尺寸 R=172.21 G=155.30 B=144.22
      缩放后 R=144.22 G=155.30 B=172.21    ← 三个数被整整齐齐地置换
```

**R↔B 互换、G 不动**。这解释了两件事：为什么白墙变冷蓝（暖白 `#DFD8D2` 反过来是
`#D2D8DF`），以及为什么这类 bug 特别难自查 —— 绿色落在中间通道，怎么换都不变；
只有冷暖对比（暖白 / 橙色 / 肤色）才暴露。用户截图里"整张发蓝"就是这一处。

★ 顺带一个可验证的推断（**不作为证据**）：截图里那只手套是蓝的。若原图是橙色
（暖色），互换后正好变蓝 —— 与上面的数字同一方向。要不要认这条，看用户手上有
没有原图；判据不依赖它。

### 16.2 根因：`IWICBitmapScaler` 不接受 `32bppRGBA`

```text
frame → IWICFormatConverter(→ 32bppRGBA) → IWICBitmapScaler → CopyPixels
                                              ↑ 它只认 BGRA 那一族，于是自己
                                                又转成 32bppBGRA 再缩
```

缩放器不报错、`CopyPixels` 成功、长度也正好是 `w*h*4`，只是通道顺序变了。
**上一棒的这行改动就是全部原因**：加缩放之前没有 scaler，颜色一直是对的。

### 16.3 判据当时为什么全绿

原来的六条是：原尺寸能解 / 目标宽生效 / 等比 / 长度自洽 / 真的变小 / 不是全黑。
它们比的是**同一张图的两个尺寸互相一致**。"错得整齐"完全满足一致性 ——
两个尺寸都错，或者只有缩放那个错但没人拿它跟"真值"比，六条照样全绿。

★ 这是 §12 那条病的变种：不是量具坏了，是**量具没有真值**。判据里必须至少有一条
**期望值写死**的断言，否则"一致"只是一种自洽，不是正确。

### 16.4 修法：取像素之前，复核事实

```cpp
if (FAILED(source->GetPixelFormat(&actual))
    || !::IsEqualGUID(actual, GUID_WICPixelFormat32bppRGBA)) {
    // 再套一层 converter 转回 RGBA；转不出来就 return false
}
```

★ 判的是**事实**（当前源的像素格式）而不是"我有没有缩放"：WIC 将来改了这块、
或换了另一族格式，这里照样自适应。
★ 转不出来就 `return false`（调用方走占位图）。**错色比没图更难发现** ——
这次它就是被当成"下载失败"报上来的（§15 也是）。

### 16.5 判据：一张期望值手写的色带图

`tools/decode-selftest/make-fixture.py` 生成 `fixtures/rgb-bands.png`（64×64、16 位 RGB）：
红 / 绿 / 蓝 / 中灰四条带。期望值是**手写**的（红带必须是 `255,0,0`），
由 `selftest.cc` 断言，与任何解码器无关：

```text
原尺寸四条带       —— 钉 16 位→8 位 与通道序
缩到一半四条带     —— 钉 scaler 的通道序（也就是这次的 bug）
```

**先红后绿自证**（在修复前跑）：

```text
ok    color at original size   (32,8)  want 255,0,0     got 255,0,0      red
FAIL  color after scaling      (16,4)  want 255,0,0     got 0,0,255      red     ← 抓到了
FAIL  color after scaling      (16,20) want 0,0,255     got 255,0,0      blue
ok    color after scaling      (16,12) want 0,255,0     got 0,255,0      green   ← 对称，看不出
ok    color after scaling      (16,28) want 128,128,128 got 128,128,128  grey    ← 对称，看不出
2 of 10 check(s) failed
```

修复后 `0 of 10 check(s) failed`。另外真图那条加了第 ⑨ 检查：两个尺寸的**通道均值**
差 < 3.0（插值误差是零点几个色阶，R/B 互换是几十个色阶，差三个数量级）。

### 16.6 进闸门：第 14 项 `decode`

`tools/decode-selftest/run.php` 负责编译 + 运行（mtime 判断要不要重编，源码没动就
复用 exe，实测 0.5s）。**退出码三态**：0 过 / 1 失败 / 2 没测到（没 MSVC 或没 WIC）。
`decode` 加进 `$may_skip`，与 `pixels` 同一口径 —— 跳过不是通过。

★ 踩到一个 Windows 坑，顺手记下：`proc_open(bypass_shell)` 找可执行文件用的是
**父进程**的 PATH，`Environment::prepare()` 塞进子 env 的 PATH 对它无效 ⇒
`cl.exe` 报"系统找不到指定的文件"。解决办法是用绝对路径，于是把
`Environment::msvcRoot()` 从 `private` 提成 `public`（"MSVC 装在哪"只留一份来源），
而不是在调用方自己拼一遍路径。

### 16.7 一次自己的失误（记录在案）

清 `touch` 造成的时间戳时顺手 `git checkout cpp-src/win32/image_decode.cc`，
**把还没提交的修复一起回退了**。发现方式是真图复测时颜色又变了。
★ 教训：`git checkout -- <file>` 的语义是"回到 HEAD"，不是"撤销我刚才那个 touch"；

### 16.8 这一轮没做的

- **其它 WIC 产物的通道序**：目前只有这一处 `CopyPixels`（`image_decode.cc`），已覆盖。
  `drawImage` 落地后如果新增了 surface→bitmap 的路径，要重新看这条契约。
- **`ImageLoader::$cache` 的上限**：仍是无上限。解码尺寸已经不是问题（§15 之后
  按显示宽度解），但"用户连开 20 张图"时仍会线性涨。留着不动，因为加淘汰策略要
  先有"缓存命中率"的量具。

## 17. 2026-11-02 下午：exe 为什么 13 MB —— 分账到库，再实测两个开关

`watermark.exe` 13.2 MB。问题先要问对：**是应用大，还是框架大？**

```text
hello.exe      13,220,864     ← 只有一个 Hello World 的控件目录
bench.exe      12,961,280
users.exe      13,498,368
watermark.exe  13,880,320
showcase.exe   14,773,760
```

hello 与 watermark 差 **660 KB**。所以 13 MB 是**地板价**：和"应用写了多少"关系很小，
是"整个框架 + Skia 全静态链进来"的价格。下面把地板拆开。

### 17.1 分账（`tools/map-size.py`，按相邻符号偏移差）

| 来源 | 体积 | 占比 | 对象数 |
|---|---|---|---|
| Drift 框架（AOT 出来的 PHP） | 6.83 MB | 52.3% | 358 |
| Skia / 三方渲染 | 3.56 MB | 27.3% | 570 |
| 应用代码（watermark） | 2.62 MB | 20.1% | 14 |
| 静态 CRT | 0.04 MB | 0.3% | 92 |

段布局：`.text` 11.19 MB（80.6%）· `.rdata` 1.98 MB · `.data` 0.49 MB ·
`.pdata` 0.35 MB · `.reloc` 0.05 MB。**是代码，不是数据。**

Skia 内部：core 2.01 MB · freetype 0.60 · libwebp 0.28 · libjpeg 0.26 ·
skcms 0.12 · libpng 0.11 · wuffs 0.07 · codec 0.06 · zlib 0.05。

### 17.2 那 2.62 MB 的"应用代码"其实也不是应用写的

`extension-watermark.obj` 一个对象就 2.02 MB，里面 **30,102 个符号**，最大的几个是：

```text
219.2 KB  ??__E_literal_strings@typephp_project_watermark      静态初始化器
121.0 KB  ?_literal_strings@…                                  字面量字符串表（15,488 条）
 37.8 KB  $stateUnwindMap$??__E_literal_strings…               上面那个函数的展开表
 22.6 KB  $ip2state$??__E_literal_strings…                     同上
 53.8 KB  ?zm_startup_typephp_watermark                         模块启动
 13.2 KB  ?module_init                                         模块注册
  7.0 KB  ?php_register_class_Drift_App_Application            每个类一个注册函数
```

加上 `Text\CjkGlyphData` 的类常量表 0.53 MB（单个符号 330 KB）。
**这个应用的 PHP 源码只有 132 KB** —— 那 2.62 MB 是"把整个框架的类和字面量登记一遍"
的固定开销，谁编译都一样。全仓 `literal_strings` 相关合计 **642 KB / 15,488 个符号**，
其中 219 KB 是**启动时执行的代码**（不是数据）→ 这也是启动成本，不只是体积。

### 17.3 转译比：3.1 MB PHP → 8.5 MB C++ → 13 MB 机器码

```text
PHP 源码        3.14 MB（374 框架 + 24 应用）
生成的 C++      8.5 MB / 159,793 行 / 342 个 .cc      ≈ 2.7×
机器码          13.0 MB                              ≈ 4.1×（对 PHP 源码）
AOT 方法数      2,629 个 ⇒ 平均 1.5 KB 机器码/方法
```

每个方法 1.5 KB 不是"编译器低效"，是**语义代价**：方法签名是 `php::Variant`，
每个临时值都是一个**引用计数对象**（`php::Var tmp_var_N`，全仓 **11,084 个**），
每个都要析构 ⇒ 每个函数都带 C++ 异常展开表：

```text
$stateUnwindMap / $ip2state 等   653 KB（44,615 个符号）
.text$x（展开代码）              606 KB
合计                            ≈ 1.26 MB = 9.6%
```

（顺带解释了 `/STACK:8388608` 那条注释：这么多临时变量 ⇒ 栈帧巨大。）

### 17.4 实测：链接开关**一点都省不下来**（这是最有信息量的负结果）

`tpc` 的 `/Gy /Gw /Zc:inline` 与 `/OPT:REF /OPT:ICF` 只在 **nano 模式**下打开
（`NativeCommandOptionsTrait.php:71`），Drift 不是 nano ⇒ 这些全关。看起来是块肥肉。
于是实测一遍（改 `build/base.yml` 的 `cxx-flags` / `ld-flags`，全量重建 198s）：

```text
开 /Gy /Gw /Zc:inline + /OPT:REF /OPT:ICF  →  13,882,880 B（+2,560 B，+0.02%）
```

**结论：链接器没有死代码可丢。** 原因是 `zm_startup` 里那 229 个
`php_register_class_*`：每个类的方法都写进 `zend_function_entry` 数组
（函数指针），于是**每个方法都被"引用"**。可达性在链接期已经全部成立，
`/OPT:REF` 无事可做。配置已还原（留着零收益的开关只会增加链接时间与风险）。

### 17.5 未被使用的控件：1.86 MB（上界，14.3%）

131 个 `src/Widget/*.php` 里，watermark 只 `use` 了 28 个。剩下的 103 个
（CalendarView 69 KB、ComboBox 58 KB、DataGrid 一族、TreeView、TimeView…）
照样在 exe 里 —— 它们被**编译**（`sources: - ../../src` 是整目录）也被**注册**。

按 object 名把它们加起来是 **1.86 MB（14.3%）**，但这是**上界**：`iconset`（424 KB）
就属于"没有 import 但被 `Icon` 间接用到"。真做可达性分析，可减的会比这个小。

### 17.6 结论与三条真正的路

现在这个体积是**架构决定的**：整个框架全编译 + 全注册 + Skia 全静态。想显著变小，
只能动 AOT/tpc，动不了链接器：

1. **注册表按可达性裁剪**（tpc 侧：只注册真的被引用到的类/方法）—— 唯一能动那 6.83 MB
   的杠杆，估算 1–2 MB。代价是"动态字符串 new 类"这条路会被砍掉或要保守兜底。
2. **字面量字符串改成一个 blob + 偏移表**（tpc 侧）—— 省 ~340 KB，附带更快启动。
3. **Skia 重编关掉用不到的 codec** —— 最多 ~0.4 MB（webp/zlib/wuffs），风险是
   某类用户图突然解不出，收益/风险不划算。

**明确不做**：链接开关（实测 0）、`/MT` 换免 CRT（换不到，仍导入 VCRUNTIME140）、
UPX 之类压缩壳（杀软误报 + 每次启动解压，且拿不到任何真实收益）。

### 17.7 校准：这算大吗

| 方案 | 体积 |
|---|---|
| WPF 自包含 | ~70–150 MB（含运行时） |
| Flutter Windows | ~20 MB（`flutter_windows.dll` 独立） |
| Qt Widgets 静态 | 15–30 MB |
| **Drift2** | **13.2 MB exe + 14.5 MB 运行时 DLL** |

其中 3.56 MB 是 Skia —— 自绘引擎的入场费。真正要打包分发的是
`watermark.exe`(13.2) + `phpx.dll`(1.0) + `php8ts.dll`(13.5) + `cacert.pem`(0.19) ≈ **28 MB**。

## 18. 2026-11-02 傍晚：还能小多少 —— 八个方案的实测与取舍

§17 把 13 MB 的来源分完了。这一节回答"那能不能小"，并给出**每个杠杆的实测数字**。

### 18.1 先把"大"拆成三种，它们的最优解不一样

| 诉求 | 真正的指标 | 有效手段 |
|---|---|---|
| 下载/分发 | **压缩后的字节** | 打包压缩（§18.6） |
| 安装后占磁盘 | 解压后的字节 | 裁代码（§18.3） |
| 启动快 | 初始化工作量 | 字面量延迟（§18.5） |

★ 混在一起谈"exe 太大"会得出错的结论：**为下载省 1 MB 而去裁代码，是在用最贵的方式
拿最小的收益**。

### 18.2 优化级别：/O2 一直在用，MSVC 没有 /O3

`tpc` 的默认是 `optimize => 2` ⇒ `/O2`（`Msvc.php:63-65`）。所以"改用 O2"不是优化，
是现状；"改用 O3"这条路在 MSVC 上不存在 —— `/Ox` 是"最大优化**子集**"，
不含 `/Os`/`/Ot` 的取向，既不是"更快的 O2"也不是"更小的 O2"。

体积方向只有 `/O1`（最小体积）和 `/Os`（偏向尺寸）。实测 `/O1`（全量重建 184s）：

```text
/O2  13,880,320
/O1  13,156,352    -5.2%  (-0.69 MB)
```

★ 代价是**全程序降速**，而 Drift 有帧预算判据（真机最重的页面 1.5–2.0 ms，占帧预算
9–12%）。体量 5% 换掉这部分余量，不划算。**已还原配置**，exe 回到 `/O2`。

#### 更正：`optimize:` **是**合法键，之前那条结论是错的

原先这里写着"`optimize:` 不是 tpc 的合法 yml 键、写进去被静默忽略"。**这是误判**，
证据链（2026-11-02 复核）：

```text
typephp/src/Metadata/Constants.php:138   'optimize' => ['prefix' => 'O', 'castTo' => 'int', ...]
                                         ⇒ 它是正经的 `-O` / `--optimize` 选项
typephp/src/Config/ProjectYamlLoader.php 全文 219 行只做 include 递归合并 + 版本/OS 条件求值，
                                         **没有任何键白名单** ⇒ yml 顶层键原样进 `$cfg`
typephp/src/Translator.php:512-513       CLI 的 -O 写 `$this->optimizeLevel`
typephp/src/Translator.php:4572-4573     yml 的 optimize 再写一次 —— **在后面** ⇒ **yml 赢**
typephp/src/Backend/Msvc.php:63-65       最终映射 $config['optimize'] ?? 2 → /Od /O1 /O2 /Ox
```

⇒ 合法、默认 `2`、且**优先级高于命令行**。`drift-build.php:307` 虽然硬编码了
`-O2`，但那是"默认值"，被 yml 覆盖 —— 所以 yml 里写 `optimize:` 是**会生效**的。

那次"+0 字节"的真实原因是**我选的取值换不出体积差**：`optimize: 3` → `/Ox`，
而 `/Ox` 是"最大优化**子集**"，与 `/O2` 的产物体积本来就接近（MSVC 没有 /O3）。
想证伪"键被忽略"必须选一个必然改变体积的取值（如 `0` → `/Od`），否则实验两边都绿。
**这是量具问题，不是 tpc 问题** —— 与 §16.3"六条判据全绿却错色"同一个病：判据不咬人。

★ 待补：`optimize: 0`（`/Od`）的体积实测。曾用 `probes/optprobe` 跑全量构建，
四分钟后被中断（便宜的路已经走完，这条只为把一个已定性的结论钉成数字）。
**不影响任何决策**：`/O2` 是现状、`/O1` 的 -5.2% 已实测且因降速被否。

### 18.3 自动裁剪：算得出来，难在"怎么证明没算错"

结论先给：**98 个生成文件可裁，1.48 MB，占 exe 的 11.8%**。依据与过程如下。

#### 为什么"没 import 就能删"是错的

第一个直觉是"131 个控件里应用只用了 28 个，删掉剩下的"。但这条判据在 AOT 之后会
给你一个荒谬的答案：

```text
按"类名是否被引用"统计，非注册表代码里 399 / 402 个类都被引用了
```

不是它们被用，是**它们自己引用了自己** —— `$this`、`self`、`instanceof self` 都会落成
自己的类名引用，而所有 `.cc` 都被 `sources: - .` 全目录编译。

#### 正确的算法：不动点迭代

从 `main.cc` 出发，**只沿可达文件的引用**往外扩；一个类被拉进来之后再看它引用了谁；
迭代到稳定。不可达类的 `.cc` 不参与统计，它们的"自引用"才会消失。

跨文件引用有四族，**漏任何一族都会把活代码判死**：

```text
php_<ns>__<class>__<method>              方法
class_const__<ns>__<class>__NAME         类常量（没有括号，是变量引用）
typephp_request_init_class_constant_<h>  常量的构造函数
get_persistent_class(id, "A\\B")         按名引用一个类（`new X` / `instanceof` 走这条）
```

★ 第四族是 AOT 最容易看漏的：`new X` **不产生符号引用**，所以链接器的图上根本没有
类与类之间的依赖 —— 它只看到注册表把它们全串起来了。这也解释了 §17.4 那个负结果
（`/OPT:REF` 只增 2.5 KB）：不是链接器不干活，是**它看不到可以丢的东西**。

#### 我在这上面算错了三版（记在案，这是本节的重点）

```text
第 1 版：只算静态符号边          ⇒ 可达 181 / 341，明显偏低
第 2 版：补 class_const 边        ⇒ 字形数据 CjkGlyphData(519 KB) 仍被判死
          （它在 DeterministicFontData.cc 里是 `tmp = class_const__..._GLYPHS;`
            —— **没有括号**，函数调用正则一条也抓不到）
第 3 版：补 PHP 的 `use` 边       ⇒ 仍剩 25 个"被 import 却判死"
          （反向验证的口径本身写错了：我比的是"全局 use"，
            而不可达类 use 的东西当然可以不可达。正确方向是
            **可达文件的 use 目标必须可达**）
```

最终自证：**可达文件 239 个，其 `use` 目标未覆盖 0 条**。此时 101 个文件不可达，
剔除 `init/`（那 13 个由注册表无条件调用，不算数）后 **98 个、1.48 MB**。

最大的几块：

```text
287.8 KB  TableState        66.9 KB  RenderTable     61.3 KB  CalendarView
 51.9 KB  LazyListState     51.6 KB  ComboBox        45.2 KB  RenderToggle
 39.1 KB  DateTimePicker    36.7 KB  TreeView        35.7 KB  TableColumn
```

#### 真正的实施难点不在算法，在 PersistentClassId

`PersistentClassId{N}` 是**编译期分配的序号**，`get_persistent_class(id, 名字)` 两参数
互相校验。所以：

- **不能事后剪 PE 或用链接器开关** —— 删一个类会让所有 id 错位
- 只能在 **tpc 生成阶段**决定"注册哪些、分配哪些 id"，然后整份重编
- 也就是：**这是 AOT 编译器的事，不是构建配置的事**

#### 工具

`tools/reach.py`（不动点闭包 + 5 条 `--self-test` 判据 + `--json` 给下游用）。
它是分析工具，不进闸门；真要实施裁剪时，它输出的集合就是那份"应当裁掉"的清单，
而**上面那条自证（use 闭包）必须变成编译期判据**。

### 18.4 Skia 的 codec：0.61 MB 纯死重

§17.1 里 Skia 占 3.56 MB，其中 `libwebp 0.28 + libjpeg 0.26 + wuffs 0.07`。而 Drift
**根本不调 Skia 的解码器**：

```text
cpp-src/skia/drift_skia.cc:601   SkImages::RasterFromPixmapCopy(pixmap)   ← 喂已有像素
                            没有 SkCodec / MakeFromEncoded 的任何调用
```

图片解码走 WIC（§15）。这 0.61 MB 是被 `SkCodec` 的静态 decoder 注册表拖进来的：
任何一个 SkCodec 符号被引用，整张 decoder 表就可达。

★ 收益 0.61 MB / 4.6%，**零运行时风险**（我们从不走那条路）。代价是要重编 Skia
（GN 参数关掉 webp/jpeg/wuffs 解码）。这是性价比最高的一条。

### 18.5 字面量：0.34 MB，附带更快启动

全仓 15,488 条字面量，生成为**静态初始化的 `php::Str` 数组**：

```cpp
static php::Str _literal_strings[] = {
php::Str{ZEND_STRL("http://..."), true}, // [0]
```

- 初始化器 219 KB —— 是**代码**，而且**启动时执行**（15488 次 interned string 构造）
- 表本身 121 KB

改成"一个大 `const char[]` blob + 偏移表 + 惰性构造"，省 ~340 KB 且把这段启动开销
变成按需。★ 这条独立于裁剪，可以先做。

### 18.6 如果目的是"下载体积"，压缩是 11.6 倍

**先更正口径**：下面第一张表只算了 4 个文件，**漏了运行时真正必须带的另外 8 个**
（2 个字体 + 6 个依赖 DLL）⇒ "27.87 MiB" 不是分发集。真实分发集是 **49.87 MiB**，
压缩收益也应按这个口径算。两张表都留在这里，因为后者改变了结论的**形状**（见末尾）。

当时的口径（zlib level 9，逐文件，**只有 4 个文件**）：

```text
watermark.exe      13.24 MB  ->   4.86 MB   36.7%
phpx.dll            0.97 MB  ->   0.22 MB   22.8%
php8ts.dll         13.49 MB  ->   5.44 MB   40.4%
cacert.pem          0.18 MB  ->   0.10 MB   57.6%
--------------------------------------------------
合计               27.87 MB  ->  10.63 MB   38.1%
```

#### 分发集是"依赖闭包"，不是"exe + 两个 dll"

清单不该手写。`watermark.exe` 的 PE 导入表（56 行 Python 读字节，不用 pdb）：

```text
watermark.exe → phpx.dll php8ts.dll VCRUNTIME140.dll VCRUNTIME140_1.dll
                + api-ms-win-crt-*（Win10+ 系统自带）+ 系统库（USER32/GDI32/...）
phpx.dll      → php8ts.dll gmp-10.dll mpfr-6.dll libmpdec++-4.0.1.dll libmpdec-4.0.1.dll MSVCP140.dll
php8ts.dll    → 系统库（WS2_32/CRYPT32/...）
运行期还要     cacert.pem（HTTPS）+ cpp/fonts/NotoSansSC-{Regular,Bold}.ttf
```

★ 这条链顺带说明**"零依赖分发"不成立**：exe 直接导入 `VCRUNTIME140(_1).dll` 与
`MSVCP140.dll`，目标机没装 VC++ 2015–2022 运行库就起不来（症状是缺 dll 弹窗，
不是崩溃日志）。

#### 完整集合实测（2026-11-02 复核）

| 形态 | 体积 | 占原始 |
|---|---|---|
| 原始（exe + 2 运行时 + 6 依赖 + cacert + 2 字体） | **49.87 MiB** | 100% |
| zip / deflate level 9（逐文件） | **23.48 MiB** | 47.1% |
| 7z / LZMA2（`lzma preset 9e`，逐文件） | **17.34 MiB** | 34.8% |
| RAR5 固实（`-m5 -s`，仅 4 个非字体文件，实测归档） | 7.62 MiB | 对照 lzma 的 7.73 |

两个数字值得记：

- **lzma 比 deflate 再省 6.1 MiB（26%）**，而两者都几乎零成本 —— 差别只在"用哪个格式"。
- **字体占 lzma 后体积的 51%**（20.13 MiB → 8.91 MiB）。去掉字体，其余 29.74 MiB
  压完只剩 8.43 MiB。⇒ **压缩之后最大的那一块不再是代码，是字体**。

#### "分发压缩"具体怎么做（三条路，按交付形态选）

1. **zip**（`ZipArchive` / 资源管理器右键）：接收方双击即可解，零依赖。
   23.48 MiB。适合"发给同事 / 内测"。
2. **7z 或 RAR5**：`7z a -mx=9 -ms=on dist.7z <dir>` / `Rar a -m5 -s dist.rar <dir>`。
   17.34 MiB。适合"挂官网下载"，代价是要求对方装解压工具。
3. **自解压 / 安装器**：`Default64.SFX` + `Rar a -sfx`，或 Inno Setup / NSIS。
   体积同 2，但双击即装、可带开始菜单与卸载项 —— **面向最终用户时这条才是正解**，
   因为第 2 条把"装个解压软件"的成本转嫁给了用户。

工程化要点（真要落地时）：

- 清单**从 PE 导入表递归求闭包**，白名单排除系统 DLL（`api-ms-win-*` / `KERNEL32` 等），
  而不是在脚本里手写 —— 手写的那份一定会和 `base.yml` 的 `link-libs` 漂移。
- 打包前校验：exe 的 `file-version` 与包名一致；`cacert.pem` 在；字体在。
- 打包后**解压到干净目录双击验一次**（验的是"缺 DLL 会不会当场炸"，不是压缩率）。

★ **压缩的边界**：它只解决"传"。装完磁盘仍是 49.87 MiB，内存与启动一分不省。
**不要**为了"看起来小"去用 UPX 这类 PE 壳：杀软误报率、每次启动多一次解压，
换来的只是磁盘数字。真正能同时降"传"与"装"的是 §18.3 的裁剪 + **字体子集化**
（20.13 MiB 这一项，比压缩后的全部代码还大）。

★ 这不否定裁剪：两条腿各走各的（传 / 装）。但如果只来得及做一件事，先做压缩 ——
它零风险、零工期，而且现在知道了：**做完压缩，下一个该动的是字体，不是 exe**。

### 18.7 方案总表与推荐顺序

> 收益口径：1–3 行按 §18.6 复核后的**分发集**（49.87 MiB）算，4–9 行按 **exe** 算。
> 两组不能相加 —— 前者是"传"，后者是"装"。

| # | 方案 | 收益 | 工期/风险 | 结论 |
|---|---|---|---|---|
| 1 | 分发时压缩（lzma/7z） | **32.5 MiB**（49.87→17.34） | 零 | **先做** |
| 1b | 同上，改用 zip | 26.4 MiB（→23.48） | 零 | 对方不装解压工具时用它 |
| 2 | **字体子集化** | 最多 **~18 MiB**（压缩后仍占 8.91） | 中 / 低 | **紧随其后** |
| 3 | Skia 关 codec 重编 | 0.61 MB (4.6%) | 中 / 低 | 值得 |
| 4 | 字面量 blob 化 | 0.34 MB + 启动 | 中 / 低 | 值得 |
| 5 | 类级可达性裁剪 | 1.48 MB (11.8%) | **大 / 中高** | 中期 |
| 6 | `/O1` | 0.69 MB (5.2%) | 小 / **高**（降速） | 不做 |
| 7 | 链接开关 `/Gy /OPT:REF` | +2.5 KB | —— | 已实测，不做 |
| 8 | Skia 改 DLL | exe −3.5 MB | 中高 / 中 | 多应用才划算 |
