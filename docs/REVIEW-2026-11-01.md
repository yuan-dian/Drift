## 1. 摘要（结论先行）

**Drift2 已经不是「早期框架」，而是一个架构对齐成熟 GUI 的声明式自绘框架。** 资料里的 9 个主题，Drift2 在 6 个上已落地、在 3 个上有明确差距：

- **已对齐甚至超出**：④ 布局（一遍式约束）、⑥ 平台抽象（命令流 + Skia/Raster 双后端 + `CanvasCapabilities` 三层能力位掩码，比 UDA 的 SupportLevel 更细）、⑧ 扩展性（Modifier 值对象 + 主题）、③ 视图树（`(type,key)` diff + `Key` 桶配对）；⑤ 事件（`GestureArena` 竞技场 + 焦点行为层）大部分对齐；⑦ 文本（`TextEditingHost`/`TextInputClient` 子系统）存在但结构弱。
- **真实差距（按影响排序）**：
  1. **① 渲染管线缺「脏矩形/脏边界」**——`RenderObject` §13.3 明说 `relayout()` 永远全树，只有 `paintEpoch` 的整帧门控；无「按深度排序的脏集」（资料主题 1 的推荐）。这是当前唯一的**结构性**管线欠缺（M5 待办）。
  2. **⑨ 工程化工具链欠账**——缺 `drift doctor`（环境自检）、CLI 全量 `--json`、`--script 交互→截图`、双后端/跨平台像素一致测试、脏集/依赖可 dump。
  3. **② 状态 / ⑦ 文本两个维度是「有意取舍」而非遗漏**——显式 `Subject` 订阅（AOT 无全局 build 栈 ⇒ 不做编译期自动依赖收集）、文本无 `Rope`（字符串拼接）——前者是正确取舍，后者是真实欠账。

一句话定调：**表现层与管线已对齐 Flutter/Compose 同级，当前瓶颈从「缺能力」转为「脏矩形未做 + 工程化验证工具不足 + 个别数据结构（文本）欠账」。**

## 3. 能力缺失清单（P0 / P1 / P2）

### P0（结构性 / 影响扩展性）
- **P0-1　布局脏矩形 / 脏边界（M5）缺失**
  - 现象：`RenderObject` §13.3 明写「Render 层没有脏边界，`relayout()` 永远全树」；`Frame` 只有「要不要重排」的粗门控，一旦重排即全树。
  - 影响：大列表 / 深树页面每次交互全树重排；资料主题 1 的「三 pass 各管脏集、按深度排序」未兑现。**这是当前唯一的结构性管线缺口**。
  - 建议：按资料 M5 口径做「脏矩形 + 脏边界成对」——单独做任一个反而把瓶颈搬到对面（本仓 §13.3 已自述该陷阱，勿只做半边）。
  - 出处：`src/Layout/RenderObject.php:18`；`src/App/Frame.php:265`。

- **P0-2　「只改像素」的通道不给帧时钟信号 —— 死锁（2026-11-01 已修，1f924c3）**
  - 现象：`wantsFrame()` 只认结构 / 动画 / 定时器 / 焦点环；`setHovered()` / `setBarOpacity()` /
    `applyCompose()` 三条刻意不 `setState`（为了不重建），于是**没有任何判据看得见它们**。
    后果是死锁：`没脏 ⇒ 不上膛 ⇒ 不跑帧 ⇒ tickAnimations 不跑 ⇒ 永远不脏`。
  - 已修：`Frame::hasPendingPaint()`（复用 paint 门控那个序号）接进 `Application::needsFrameNow()`；
    `setHovered()` 补 `markNeedsPaint()`。`PaintArmsFrameTest` 3 例 + 三轮变异。

- **P0-3　悬停浮起 / 滚动条淡出真机都不出画面（两条均已收口，2026-11-01）**
  - **悬停：已修 + 真机验收绿**。两个独立成因，各有一条能红的断言
    （`tests/Feature/App/HoverPixelTest.php`）：
    ① **盒换代清零瞬态** —— `Element::update()` 必调 `syncBox()`（§13.2），悬停态住
       盒字段上 ⇒ 任何一次 `setState()` 都清零。修法：同类型盒之间
       `inheritRuntimeState()`（`Element::syncBox()` 里调）。
    ② **重绘边界吞命令** —— `LayerCache` 按 `layoutEpoch + 尺寸` 命中，而 hover 叠色
       是**录进命令流**的 ⇒ 只推全局 `paintEpoch` 时边界整段重放旧命令。真机 trace：
       进度 0→1 推了 43 帧，`paint` 记录里从来没有那个盒的 id。修法：就地写点统一走
       `markPaintChanged()`（`RenderBox` 覆写 = 失效**从自己开始**最近的边界）。
  - **上一轮那批红有一半是探针造成的**：`probe-motion.py` 的 `move/click/wheel` 用了
    `PostMessage` 伪造消息（`PITFALLS` 第 37 条早就禁止这么做）。改真实光标后同样的
    exe 立刻绿：盒内 1910 px、环带 202 px 变化。⇒ 以后"探针说没反应"先换真实输入复测。
  - **滚动条淡出：不是产品缺陷，是探针采错了列（2026-11-01 晚订正）**。
    上一版写"插桩后日志 0 行、右侧一条都没有"，据此判"视口盒没进绘制树"。
    **那个结论是假的**：两个探针都在**窗口右缘**（`x ∈ [w-40, w)`）采样 ——
    那里是**页面底色**，整列恒 238.9 ⇒ "滚动前后完全一样"必然成立。
    用逐列扫描重新定位后，条在 **x=1370..1375**（离窗口右缘 39px）：画着，
    且淡出正常（滚后 luma **119.3** → 静止 **207.7**，与解释器逐位相同）。
    ⇒ 处置不在产品侧，在量具侧：
    ① 新增 `tests/Feature/App/ScrollBarFadePixelTest.php`（解释器级像素判据，
       5 条断言：全亮 / 900ms 前不许淡 / 淡到 0.35 / 淡完仍看得见 / 淡出期间内容不动）；
    ② 定位逻辑收成 `tools/probe_pixels.py::find_scrollbar()`，两个探针共用；
       采不到目标时打 **SKIP（退出码 2）**，不再报"没变"。
  - 已排除（免得重跑）：`TrackMouseEvent(TME_LEAVE)`；探针取点（并排按钮粘成一块）；
    动画不推进（`p` 确实到 1）；帧时钟判据（P0-2 已补）；盒换代（已修并验证）；
    **懒列表视口盒是否进绘制树**（进了 —— 见上一条）。


### P1（重要，应排期）
- **P1-1　双后端 / 跨平台像素一致测试缺失**（资料 13-nanoui §3.6，明确「Drift 缺，值得抄」）
  - ✅ **已改判并落地（2026-11-01 夜，见 §9）**。原建议「同一 golden 在 Raster/Skia 逐字节
    一致」**是恒假命题** —— `SkiaCanvas` 类注释早写明抗锯齿/描边是**有意**差异，
    「像素级 golden 不能跨后端比」。改判为 **"一份换算，两个观察者"**：
    ① `Scale::deviceRect/deviceX/deviceY` 成为唯一的"加偏移 + 量化"（此前两后端各抄一遍，
    共 6 处）；② `BackendDeviceSpaceTest` 用同一个 `DisplayList` 回放给两个后端，
    桥参数与墨迹盒各自对齐**同一份规格**（规格在测试里用定义重算，不调实现）。
  - 仍未做：真机 Skia 光栅基线（`php.exe` 里跑不到真 Skia）、跨平台互比（各平台各自基线）。
- **P1-2　字形图集（glyph atlas）缺失**（资料 13-nanoui §3.5）
  - 现象：逐字形 `face->rasterize()` 到画布（`RasterCanvas.php:247` 附近），无图集。
  - 影响：CJK / 大字号场景重复栅格化；若将来上 GPU 后端，图集是实例化合批的前置。
  - 建议：字形一次栅格进图集 + 按字形引用；上 GPU 前必须做。
- **P1-3　动效模型弱：controller + 每帧全树 tick**（资料 13-nanoui §3.4）
  - 现象：`AnimationController` + `tickAnimations()` 逐节点推进（`RenderObject::tickAnimations`），无「活跃动效集合」。
  - 影响：每帧全树 tick 的固定成本；「中途改目标保留速度」这类体验细节容易写成「重置」。
  - 建议：改「声明目标 + 弹簧 + 活跃动效登记表」（资料 13-nanoui §3.4，且印证 `analysis/20` P1-5）。
- **P1-4　事件隧道（Preview / 隧道阶段）缺失**（资料主题 5：WPF 冒泡+隧道双路径）
  - 现象：grep 无 `Preview`/`tunnel`/「隧道」；只有「命中即目标 → 冒泡到祖先」。
  - 影响：祖先「先拦截再下传」（如全局快捷键、权限拦截、手势预处理）无法在事件下行阶段统一处理，只能在冒泡阶段补救。
  - 建议：在 `InputRouter` 命中后加「隧道下行」一遍（祖先先处理，`Preview*` 语义），与冒泡对称；先只给键盘/指针两个高频路径。
- **P1-5　文本无 `Rope`**（资料主题 7：GPUI 的 Rope + Tree-sitter + LSP 三件套）
  - 现象：`TextDraft`/`TextInputClient` 在，但无 Rope 数据结构；插入/删除大概率字符串拼接（`O(n)`）。
  - 影响：大文本编辑时每次输入整串拷贝；与文本状态机（选区/组合区/撤销栈）耦合后更贵。
  - 建议：文本编辑数据结构改 Rope（或 rope-like 的块链），插入 `O(log n)`；与选区/撤销栈一起设计。

### P2（治理 / 可优化，成本低）
- **P2-1　`Modifier` 的「父意图」族该升为 `ParentData` 值对象**——`Modifier.php:168` 已自述：「再加第三族（Dock 槽名 / Table 列提示）就该引入独立 `ParentData` 值对象，而不是第 28 个字段」。当前字段数接近该阈值，建议提前拆。
- **P2-2　视口渲染盒「夹裁剪矩形 + 画 thumb」去重**——`ScrollBarHost`/`ScrollBarFade`/`ScrollBarGeometry` 已共享几何/动画，但 `RenderScrollView` 与各虚拟列表/表格盒仍各自内联 paint（待核实 `RenderTable` 与虚拟列表盒是否同源）。
- **P2-3　`Modifier` 四类正交化（Compose Modifier.Node 思想）**——当前是一大值对象；若字段继续膨胀，可考虑「布局/绘制/输入/语义」四组子结构（不一定要链式节点树，但分组可内省）。
- **P2-4　编译期 `PatchFlag` 标注**——`Element` 运行期全量 diff；AOT 编译期已知结构，可标注「哪里会变」减少 diff 面（资料主题 3）。
- **P2-5　编译期依赖表 + 惰性 `computed`**——资料主题 2 的「自动订阅」Drift2 有意不采用（AOT 无 build 栈），但 `computed` 惰性派生可单独补（Vue 式，与显式订阅不冲突）。
- **P2-6　DPI 单源确认** —— ✅ **已做（2026-11-01）**。原判断（"`nodeScreenRect` 已用 `dpiOfWindow()`，只需查有没有第二处缓存"）**是错的**：`nodeScreenRect()` 是 **C++ 侧** UIA 的方法，PHP 侧根本没有 `dpiOfWindow` / `nodeScreenRect` 这两个名字。真实形态是**同一段换算被手写了六遍**（`Win32Platform::dprOf()` ×1 + `Win32WindowHost` ×4 + `Win32Screen::scale()` ×1），且六份的兜底**不一致** —— 五份写了 `<= 0 ⇒ 1.0`，`Win32Screen::scale()` 漏了 ⇒ 桥给 0 时它把 `0.0` 交给消费者做除数。已收成唯一入口 `Drift\Platform\Win32\Dpr::of()`，`Win32Platform::dprOf()` 删除。

## 4. 可优化：能替代只留一套（用户明确偏好）

## 5. 可借鉴 + 排坑（资料明确结论）

### 可借鉴（按可落地性，来自 13-nanoui §3）
1. **`drift doctor` 环境自检**（最高性价比）：把「人脑里的约束」变成断言——`PHPRC`、`opcache.enable=0`、`cl.exe` 在 PATH、`PHPX_HOME`、tpc 版本（源码树 vs 发行版）、Per-Monitor V2 DPI、`-m lib` 需源码树。
2. **CLI 全量 `--json`**：agent 驱动「构建→测试→快照」的前提；否则只能正则刮 stdout。
3. **`--script` 交互脚本 → 截图**：补「交互序列→视觉回归」空白（现有 golden 只测静态帧），一次投入同时服务 CI 与文档配图。
4. **动效改「声明目标 + 弹簧 + 活跃集合」**（P1-3）。
5. **字形图集**（P1-2）。
6. **双后端 / 跨平台像素一致测试**（P1-1）。
7. **DrawOp IR 按「可合批」组织**：同 pipeline/同纹理的连续 op 可并，而非纯顺序命令流（设计期输入，上 GPU 前定）。
8. **`drift new` 脚手架：AGENTS.md + 锁三版本**（Drift / tpc / phpx）。

### 排坑（资料明确「不该借鉴」+ 各框架教训）
- **不抄 immediate mode 主体**：会丢 reconcile 复用、Element 生命周期、1000+ smoke 断言面；nanoui 的 `Context.state` 本质是「在 immediate 上重建迷你 retained」。
- **不抄 0.7MB 单文件体积**：Drift 分发带 `libphp.so`+`libphpx.so`，下界由 PHP 运行时决定，当目标会逼出「砍功能换体积」。
- **不用 `layer`/`fixed` 替代 OverlayStack**：OverlayStack 有焦点陷阱/模态/scrim/锚点自动关，属性式撑不起；可吸收为语法糖。
- **不指望增量编译**：与 tpc 同病；改「双档验证」（解释器跑逻辑 + AOT 跑真机/像素）。
- **文本/IME 是自绘最大坑**（Flutter 十年未清）：选区/IME/放大镜/工具栏/撤销栈是一期工程，不是控件附属。
- **声明式连接静默失败**（WPF 字符串绑定 / Vue 解构丢响应）：任何绑定/订阅/能力查询失败要编译期错误或显式日志，不做「Output 窗口一行警告」。
- **编译期魔法必须可 inspect**（Compose 稳定性黑盒）：依赖表/脏集要能导出，否则「为什么没更新/为什么重组」无解。
- **事件隧道不要做成第二套分发**：与冒泡共用语义动作出口。

### 6.1 进展：先做了「每帧固定税」，不是脏矩形（2026-11-01 16:40）

**结论：上表里 M5 的顺位被一条更便宜的路抢走了。** 新增量具 `tools/frame-tax-probe.php` 量出：

| 规模 | 稳态帧（layout/paint 均跳过） | 同树全量 layout |
|---|---|---|
| 50 行 ≈ 200 节点 | 320µs | 841µs |
| 500 行 ≈ 2000 节点 | **3484µs** | 7192µs |

已落地（见 `FocusManager.php` 的注）：

- `walk()` 只在真的有人声明 `focusOrder` 时才收集+排序（无 order 时比较器恒 0 ⇒ 等价变换）；

- 稳态帧 **3484 → 850µs（-76%）**，`focus` 段 2.46ms → 0.002ms。5 条新测试钉住两条判据，两轮变异各红 2 条。

**M5 的触发条件因此写实**：它只在"**重建帧**已经掉帧"时才值得做（当前 2000 节点重建帧 ≈ settle + 7.2ms layout + paint，仍在 16.7ms 内）。判据是 `frame-tax-probe` 的 `layout(us)` 列 × 重建频率，不是"资料里有这一项"。同理，`tickAnimations` 的 926µs 仍是动画期的固定税，但它要重设计"帧时钟上膛"判据链（漏登记 = 动画静默停住），单独一轮。

## 9. 2026-11-01 夜：P1-1 改口径 —— 从"逐像素一致"到"一份换算，两个观察者"

### 9.1 原口径为什么是错的（不是"难做"，是"恒假"）

`SkiaCanvas` 的类注释早就写死了两条**有意**差异：抗锯齿（软光栅只对圆角/字形做覆盖度，
Skia 对所有边做）、描边（软光栅"外圈减内圈"，Skia 居中 `kStroke`），结论原话是
「**像素级 golden 不能跨后端比**，只能各自与自己的基线比」。

⇒ 「同一 golden 在 Raster/Skia 逐字节一致」在**设计上**就是个恒假命题。写成测试只有两个
结局：永远红（然后被 skip 掉），或者把容差调到没有牙。**两个都不是判据。**

### 9.2 成熟框架怎么做的（同一个思路：分层，不在像素上硬碰）

| 框架 | 做法 | 结论 |
|---|---|---|
| Chromium | pixel test 带 `fuzzy`（max pixels diff / avg error）+ 按平台分别 rebaseline | 承认平台差异，只钉"没变坏" |
| Skia `dm` | 同一 corpus 跑多 config，config 之间**不**逐像素比，各比各的 baseline | 同上 |
| Servo / WebRender | 参考测带 YAML `fuzzy` 注解 | 同上 |
| Qt `lancelot` | 按 paint engine 分基线 + 容差 | 同上 |
| Flutter | `matchesGoldenFile` 按平台分 golden，iOS/Android 互不比 | 同上 |

共性：**像素是后端私有的**。跨后端能共享的是它上面那一层 —— 命令流 / `DisplayList` /
设备几何。本仓本来就是这个形状（一份 `DisplayList`，两个回放器），所以口径该往上抬一层。

### 9.3 顺带查出来的结构病：同一个公式抄了六处

`toDevice()` 在两个后端里**逐字重复**（`SkiaCanvas:758` / `RasterCanvas:1560`），
另有三处更散的拷贝：`SkiaCanvas::drawLine` 四个标量、`packPath()` 六个标量、
`applyPaintSource()` 四个渐变端点；软光栅侧 `deviceX/deviceY` 各一份。

`Scale` 的类注释写着「全框架**只有这一个量化函数**……别处一律不许取整」——
**这句话当时是假的**：取整在 `Scale` 里，而"加偏移"在它外面，抄了六遍。

处置：`Scale` 新增 `deviceRect()` / `deviceX()` / `deviceY()`，**顺序写死为"先加偏移、
再一次量化"**；两后端的 6 处拷贝全部改走它。软光栅的私有 `deviceX/deviceY`（矩阵感知
那一层）改名 `transformedX/Y`，免得与 `Scale::deviceX()` 混读。

### 9.4 判据：同一个 `DisplayList`，两个观察者

`tests/Feature/Rendering/BackendDeviceSpaceTest.php`（5 个方法 / 30 条断言）

| 观察者 | 能观察到什么 | 读法 |
|---|---|---|
| `SkiaCanvas` | 桥收到的参数（**就是设备坐标**） | 假桥记录 |
| `RasterCanvas` | 像素 | `inkBounds()` 取墨迹盒 |

两边都必须等于**同一个规格**：`round((逻辑值 + 偏移) × dpr)`；规格在测试里**用定义重算**
（`self::dev()`），**不调** `Scale::deviceRect()` —— 调了就是"测试与实现共用一份错"。

覆盖：填充矩形（无偏移 / 整偏移 / 半像素偏移 / dpr=2 / 圆角）、椭圆、描边（+**内部是空的**）、
线段（4 个端点 + 宽度不乘 dpr）、路径（解包桥收到的 float32 顶点）。

容差：矩形族**精确相等**（实测椭圆 `[13,13,32,24]` 与规格逐位相同，不留余量）；
路径 ±1，理由算得出来 —— 三角形最右是**一个顶点**（设备 x=23），中心采样在 y=7.5 时
右端只到 22.47 ⇒ **最后一列没有像素中心落入**，墨迹到 21 是对的，不是缺陷。

### 9.5 变异自检（4/4 有牙）

| 变异 | 结果 |
|---|---|
| `Scale::deviceX()` 漏掉偏移 | 红 2 条 |
| `Scale::deviceRect()` 先取整再加（顺序反了） | 红 1 条（半像素那行） |
| `RasterCanvas::toDevice()` 漏偏移 | 红 2 条 |
| `packPath()` 丢掉偏移（命中 2 处） | 红 1 条 |

外加一个"量具自检"方法：证明**规格本身不恒真**（漏偏移 / 顺序反了都会算出不同的盒子）。
第一版这条自检是假绿 —— 挑的 `1.5 + 0.5 = 2.0` 恰好与 `round(1.5) = 2` 撞上；
换成 `1.2 + 0.4 = 1.6 ⇒ 2` vs `round(1.2) = 1` 才有牙。

### 9.6 这一轮**没**做的

- **真机 Skia 基线**：真 Skia 光栅在 `php.exe` 里跑不到，所以本判据的 Skia 侧观察的是
  **桥参数**而非像素。要真比像素只能走 exe + 截图（`probe-*` 那条路），成本高一个量级
  ⇒ 按"不提前投资"留到有第二个平台后端时再说。
- **跨平台（Win/Linux/mac）**：同 9.1 的理由，各平台各自基线，不互比。
- **没动** `tools/smoke.php` 里 P3 那批 Skia 参数断言：它们是硬编码元组、全是
  dpr=1 / 偏移 0，但那是"某个具体 bug 的现场记录"，改成表驱动会丢掉那层信息。

### 9.7 P1-1 的最终结论

**不是"补一个测试"，是"改一个口径 + 收一处重复"**：结构上没了重复实现（漂移不可能），
判据上同一份规格被两个后端各验一次（漂移一发生就红）。原口径那个"逐字节一致"从
待办里删掉 —— 它永远不会被做对，只会被调宽容差。

## 10. 2026-11-01 深夜：探针骨架收成三件 —— "不许有第二条输入通道"

### 10.1 这一节要解决的问题不是"代码重复"，是"探针会说谎"

上一节（§8）的结论是"量具坏了，不是管线坏了"。这一节把**为什么量具会坏**修掉。

盘出来的是这样一张表（`tools/probe-*.py` 9 个文件 / 2645 行）：

| 同一件事 | 有几份实现 | 漂成了什么样 |
|---|---|---|
| 输入通道 | **5** | 真的 `SetCursorPos`+`mouse_event` / 纯 `PostMessage` / 混合 |
| 截图 | **4** | `bytes` / `bytearray` / 类 / 少一次 `SelectObject` 还原 |
| 启动（`PHPRC`） | **9** | 两份写 `encoding="ascii"`、七份 `utf-8` |
| 结论 | **4** | 全是 `ok`/`FAIL` 两态 —— **"没测到"无处可写** |

这张表里没有一条是风格问题。**输入通道**那 5 份里，3 份走的是已证伪两次的路
（`PostMessage` 只让应用"知道"指针在哪，`TME_LEAVE` 与 `ScrollBarFade::noteScroll()`
认的是真实光标/真实消息）⇒ 应用照常推进状态、动画也跑满，画面不变，探针报
"一像素不动"，产品是好的。**结论**那 4 份两态 ⇒ 采不到目标时只能写 `FAIL`，
于是"我没采到"被读成"产品坏了" —— §8 白追的 90 分钟就是这么来的。

### 10.2 成熟框架怎么处理这件事（同一个答案：通道只有一个）

| 框架 | 做法 |
|---|---|
| Playwright / Puppeteer | 只有一个 `Input` domain（CDP `Input.dispatchMouseEvent`），测试作者**选不了**"真发还是假发" |
| FlaUI / WinAppDriver | 只有一个 `Mouse` 类（`SendInput`），`MoveTo`/`Click`/`Wheel` |
| pyautogui | 整个生态共用它当唯一输入层 |
| pytest / Playwright | `skip()` 是**一等结论**，与 `fail()` 分开：没条件测 != 测坏了 |

共性两条：**① 输入是能力，不是每个测试自己的帮手；② "没测成"必须是一等结论。**

### 10.3 落地：三件共享 + 一条会红的判据

| 件 | 管什么 | 关键设计 |
|---|---|---|
| `tools/probe_win.py` | 启动 / 找窗 / 抢前台 / 截图 / **真实输入** / 收尾 / 用户状态隔离 | **假的那条路根本不导出**（连 `PostMessage` 包装都不给）；`move/click/wheel` **每次调用前**都验 `GetForegroundWindow() == hwnd` |
| `tools/probe_check.py` | 三态结论：PASS / FAIL / **没测到（SKIP，退出码 2）** | `need(value, why)` 是"采不到 ⇒ SKIP"的唯一写法；`run()` 收尾，**失败优先** |
| `tools/probe_pixels.py` | 像素定位（§8 已有） | 本轮补 `near()` / `nonwhite_ratio()`，收掉两份 `near` |

三个决定值得单独记：

1. **假通道不可表达**，不是"文档说不许"。探针想再造一条假路，得自己重新
   `ctypes` 一遍 —— 那时 `probe-audit` 会红。**约定挡不住，闸门挡得住。**
2. **输入前逐次验前台**。不是启动时验一次就够：中途被别的窗口抢走，
   后面每一次点击都会落到那个窗口上。宁可中途 SKIP，也不要量出一组假的数。
3. **三种"没前台"分开报**（这是本轮最实用的改进）：
   `GetForegroundWindow() == 0` ⇒ 会话里**没有**前台窗口（桌面锁定 / 非交互会话，
   `SetForegroundWindow` 实测 `GetLastError = 1400`）；`!= hwnd` ⇒ 被别的进程占着。
   合并成一句"抢不到前台"，下次还得重查一遍。

## 11. 2026-11-02 晨：桌面解锁后的真机复核 —— 抓到一个"共享件语义漂移"

### 11.1 昨晚留下的四件 SKIP，现在四件全绿 —— 但过程里发现了一件更要紧的事

桌面锁定时（§10）四个输入类探针只能报 SKIP。桌面解锁后逐个真跑：

| 探针 | 结果 |
|---|---|
| `probe-scroll-diag.py` | **0 FAIL（3 条）** —— 条在 `x=921..926`，luma **119.3 → 207.7** |
| `probe-motion.py` | **0 FAIL（7 条）** —— 悬停 ring 202px / 盒内 1910px / 移开回 0；条 119.3 → 207.7 → 120.3 |
| `probe-modal.py` | **0 FAIL（10 条）** —— 遮罩 −35.3%、面板 49525px、X 墨迹 30px、反例无 X |
| `probe-scrollbar.py` | **0 FAIL（7 条）**（换了目标页，见 11.4） |

与解释器级判据（`ScrollBarFadePixelTest`）**逐位相同**：119.3 / 207.7。产品侧没有任何变化。

### 11.2 但 `probe-motion` 第 1 条先红了：`blocks=[]`

「找不到墨绿按钮块」。追下去发现 **`px()` 的通道顺序在上一轮迁移时被悄悄换掉了**：

| | 迁移前（`probe-motion.py` 自己的 `px`） | 迁移后（`probe_pixels.px`） |
|---|---|---|
| 返回 | `data[i+2], data[i+1], data[i]` = **RGB** | `data[i], data[i+1], data[i+2]` = **BGR** |
| `PRIMARY = (0x00,0x96,0x88)` | 对得上 | 实测拿到 `(136,150,0)` ⇒ **永远不等** |

`(136,150,0)` 正是 `(0,150,136)` 的 R/B 对调 —— **同一个颜色，翻个序依然是合法颜色**，
所以肉眼看截图完全正常，只有"跟常量比"才会失败。

★ 为什么它能活过一整轮：**灰度判据对翻序不敏感。** 亮度 `(r+g+b)/3`、低饱和
`max-min` 都不在乎谁在前，于是滚动条那 3 条一直是绿的，把整个迁移期盖住了；
而唯一会红的第 1 条，昨晚恰好因为"没有前台窗口"被 SKIP 掉。
⇒ **「SKIP 不等于迁移通过」**，这是这一轮最贵的一句话。

★★ 同一份字节流在**同一个文件里本来就有两种语义**：`nonwhite_ratio()` 一直按
`data[i+2], data[i+1], data[i]` 读（RGB），而 `px()` 读 BGR。这种"一个文件两套约定"
正是当初"9 个探针各抄一份"造成的，只是抄的时候两份**恰好不同**。

### 11.3 处置：让共享件语义正确，并自己证明一次

1. **`px()` 改为返回 `(r, g, b)`** —— 与主题色常量 / `Color::fromRgb` / CSS 同一顺序，
   BGRA 的翻序**只在这一个函数里**发生。调用方零改动（它们本来就是按 RGB 写的）。
2. **`probe_pixels.selftest()`（新，11 条）** —— 量具的契约必须自己证：
   * 合成一块已知 BGRA 缓冲 ⇒ `px()` 必须给回 RGB；**并且**必须不等于对调值
     （对调后仍是合法颜色，只能靠这条抓）；
   * `find_scrollbar` 四个方向：白底 ⇒ None、**页面底色** ⇒ None（假红原形）、
     6 宽段 ⇒ 定位到、3 宽窄带 ⇒ 不算条；
   * `column_luma` / `nonwhite_ratio` 的灰度口径。
3. **闸门加第 11 项 `pixels`**，并给闸门补上**三态**：只有显式声明为
   `$may_skip` 的检查（现在是"依赖本机装了 python"这一项）才允许退出码 2 / 命令缺失，
   跳过**单列在总结里**，绝不折算成通过。

变异自检：把 `px()` 改回 BGR ⇒ `selftest` **红 4 条**（`got=(136,150,0)` 那组）。

### 11.4 顺手救活了一个"只会 SKIP"的探针

`probe-scrollbar.py` 原本验 `users.exe` 列表页，理由是"种子 15 用户溢出 `maxScroll≈64`"。
实测：滚轮不动、右 80px 内**零个** Muted 墨点 ⇒ 这页根本不溢出、按设计不画条
（§10.6 记的"整屏只有 4 个 Muted"其实也是通道对调造成的假数，修好后同一页量到 269 个）。 

一个只会 SKIP 的探针等于没有探针。改成验**确实溢出**的 showcase「长列表 Big」，并补两条
一直没人做的判据：

| 判据 | 值 | 意义 |
|---|---|---|
| ④ 条离客户区右缘有留白 | 33px | **条在视口右缘、不在窗口右缘** —— §8 两次假红的那个假设，现在会直接红 |
| ⑤ 滚 200 格 ⇒ thumb 下移 ≥ 4px | 7px | 跟手 |
| ⑥ 滚回顶部 ⇒ 回到原位 | 0px | 位移是双向的 |

两个"看起来像产品缺陷、实际是量法欠账"的坑也在这一节里被记下：

* **条长被量成 22px（< `MIN_THUMB` 24）**：条的上下端是抗锯齿边 `(123,131,140)`，
  与 `Muted` 差 13/14 ⇒ 任何 `tol < 15` 的精确匹配都会两端各吃掉一行。
  改按**墨迹**量（`luma < 222`）后量到 **24**，与常量逐位对上。
* **"滚 1 格 thumb 不动"**：10000 行 × 44px ⇒ 内容高 44 万，一格只该动
  `360 × 48 / 439600 ≈ 0.04px`。**那是比例滚动条的正确行为。** 判据改成 200 格。
* **⑥ 一度报 -221px**：墨迹阈值取 200 时，**淡出后**的条（208）不算墨 ⇒ `thumb_shape`
  退化成把顶栏那 2 行边框当 thumb。阈值改成 222（区间必须同时 > 208 且 < 236）。

### 11.5 这一轮的结论

三轮下来，"探针骨架收成三件"（§10）只解决了一半：**共享件的结构统一了，语义没被证明。**
现在补上的是后半句 —— **共享件必须自带契约自检，SKIP 不能当作迁移通过。**

## 12. 2026-11-02 上午：量具自己会说谎 —— 1000× 的单位、过期的注释、进闸门的判据

### 12.1 起点：上一棒说"下一格只有异步流"，先证了一遍"不该做"

上一轮的交接是「M5 未到触发条件 · 异步"流"是唯一整维缺口」。按本仓纪律
（**未被消费的分支 = 未实现**）先把"流"证伪了一遍：

| 问 | 答 |
|---|---|
| `src/Async/` 真的只有 2 个类？ | 是（`Future` / `AsyncValue`）。但**"流"的零件到处都是**：`Subject`（订阅即推送）、`IoPoller::watch`（回调流）、`completionQueue`（先记账再交付）、`Future::all`（多值并发） |
| 缺的是状态层类型？ | 不是。`AsyncCommand::append()`（追加语义）**已经有真实消费者**（`showcase` 的「加载更多」页 + App\`LoadMorePageTest`），`Future::all` 也有 `ConcurrentFetchPage` |
| 那"进度 / 日志 / WebSocket"呢？ | **零消费者**。`apps/users`、`showcase` 里没有一个"已知长度的长任务" |

⇒ `StreamValue` / `AsyncStream` 仍然**不做**（`ASYNC-ARCH-2026-10-31.md` §7.3 的裁决
继续有效）。再造一个没有消费者的类型，违反的是本仓自己的第一条账：*未被消费的分支 =
未实现*，而且这次连"将来会有人用"都说不出口。

### 12.2 于是回到唯一有实测数的那一项 —— 一上手就发现量具在说谎

排期里唯一带数字的是「每帧固定税」（§6.1：稳态帧 3484 → 850µs）。重跑
`tools/frame-tax-probe.php`，输出是这样：

```text
   500          985.7       7251.4       0     50
       分段: pumpIo=0.98ms  pumpTasks=0.88ms  anim=972.92ms  ...
```

**稳态帧 985.7µs，而 `anim` 段 972.92ms** —— 同一份输出里两个数差了三个数量级，
却从来没有人在三轮里多看一眼。追下去是**三个独立的假**：

| # | 假话 | 真相 | 为什么它能活下来 |
|---|---|---|---|
| ① | `SurfaceProfile::perCall()` 按 ms 打印 | 它返回**纳秒**；探针写了 `round($v/1000).'ms'` ⇒ 每段被印成 **1000 倍** | 读者会"自动校正"（心里知道是 µs），于是错误被读懂了、没被修 |
| ② | 注释写"每次调用**中位**纳秒" | 算式是 `累计/次数` = **平均** | 两种都合理，只差一个词；用它做决策时口径不同 |
| ③ | `gate.php` 头写"合计 **63.4s**、smoke **448** 条" | 实际 **120s 量级**、smoke **460** 条 | 数字没有判据 ⇒ 必烂，且烂了没人发现（`MEMORY` 里记的是对的，代码注释里是错的） |

★ 这一轮的判断：**①②③ 是同一个病 —— "量具的说明书/输出"没有判据。**
上一轮（§11）刚学会"共享件要自带契约自检"，这一轮把同一条纪律推到**人读的那一面**：
单位换算、聚合语义、耗时数字，只要写在人眼前，就必须能被证伪。

### 12.3 处置一：ns→文本的换算收成一份，并让契约自己证一次

`SurfaceProfile` 新增 `formatNs()`（`<1µs → ns`、`<1ms → µs`、否则 `ms`），
探针不再自己算；新增 `selfTest()` 两条：

* **单位**：`formatNs(1000)=='1µs'`、`(972920)=='972.92µs'`、`(1500000)=='1.5ms'`…七档；
* **聚合**：同一段两次 2000ns ⇒ `perCall()` 必须给 **2000**（平均），给 4000 就是
  "累计冒充每次"。

这与 `Scale::deviceX()` 是同一条纪律：**同一件事写两遍必然漂移**。差别是这次漂的是
人眼读的那一侧，代价是"拿错三个数量级的数去判断要不要重构管线"。

### 12.4 处置二：把"报告"变成判据（`--check` 六条）

原来这个文件头写着「**别拿它当门禁**：墙钟数随机器浮动，`gate` 里放它只会变成一台
随机失败的机器」。那句话对**绝对耗时**成立，对**自洽性**不成立 —— 六条判据里
**没有一条是墙钟阈值**：

| # | 判据 | 能红的真实事故 |
|---|---|---|
| ① | `SurfaceProfile::selfTest()` | 单位换算写错（就是今天这个 1000×） |
| ② | 每个分段 ≤ 整帧 × 1.25 | 量具自相矛盾：单位错 / 同一段重复计时 |
| ③ | 分段里必须出现 `anim` | **"没扫到"冒充"没有"**（否定结论要自证扫到了东西） |
| ④ | 稳态帧 paint 全跳过（run=0 && skip=帧数） | paint 门控退化 ⇒ 每帧整树重画 |
| ⑤ | `layout` 段 ≤ 全量重排的 5% | layout 门控退化 ⇒ 稳态帧变成全树重排 |
| ⑥ | 三个版本号全 `+0` | "稳态"前提不成立（帧在自激）⇒ 后面所有数字不可信 |

★ ⑤ 是**比值**不是毫秒：分子分母是同一棵树上的**同一种操作**，机器慢了两边一起慢
⇒ 比值稳。这是它敢进闸门的唯一理由（`Scale` 那条"只比同量纲"的同类）。
★ 闸门第 **12** 项 `tick`（`~0.6s`，非慢项）。

### 12.5 变异自检（3/3 有牙，且第一次运行抓到了自己的绿壳）

| 变异 | 结果 |
|---|---|
| `formatNs` 的 µs 分支除数 1000 → 100 | ①红，**exit 1** |
| 探针里伪造一个 200ms 的分段 | ②红，exit 1 |
| `Frame::run()` 的 layout 门控改成 `if (true)` | ④红（run=30/skip=0）**且** ⑤红（92.2%），exit 1 |

★ 同一份契约在**测试**一侧也钉了一遍（`tests/Feature/Rendering/SurfaceProfileContractTest.php`，
3 个方法 / 16 条断言）：单位八档边界 + `perCall()` 是平均不是累计 + `selfTest()`
只读不污染现场。变异：`formatNs` 除数 1000→100 ⇒ 红 2 条；`perCall()` 改成返回累计
⇒ 红 2 条。

★★ **第一版判据自己是绿壳**：它先无条件印 `ok ②`，再在末尾补一行 ✗ —— 同一份输出里

下面紧跟着 `✗ ② …超过整帧`）。改成"**先算结论，再选 ok / FAIL 打印**"之后，
每条只有一个说法。⇒ 判据的形状也要被变异检验，不是只有判据的内容。

### 12.6 用修好的量具重读 §6.1：那条"两个全树遍历各占一半"已经过期

| 段 | 2026-11-01（§6.1） | 2026-11-02 实测（500 行 / 2000 节点） |
|---|---|---|
| 稳态帧 | 3484 → **850µs** | **993.5µs** |
| `focus`（`FocusManager::collect`） | 2462µs → **0.002ms** | **1.52µs** |
| `anim`（`tickAnimations` 全树） | 995µs | **980.71µs（98.7%）** |

⇒ 固定税的**结构变了**：focus 已经降到噪声，稳态帧现在**几乎全是**全树 tick。
§6.1 里"两者各占一半"的框架不再成立；要再动这一项，目标只剩动效表。

**但仍然不做**，理由有数：① 2000 节点是**合成**最坏树（`Column` 全量，不是
`LazyColumn`）——真实页面的可见节点是十几到几十；② 这笔税只在**帧已经在跑**时付
（空闲时 `wantsFrame()` 为假，根本不进 `frame()`），而帧在跑时本来就是要推进动画。
⇒ 收益是"动画帧的 6% 预算"，风险却是"漏登记 = 动画静默停住"（`MEMORY` 已记：登记表版
在 AOT 下失效过一次）。**按"不提前投资"留到有掉帧证据时再说** —— 而那个证据现在
有判据了（`tick` 项每次闸门都跑，稳态帧/全量重排两个数一直摆在 CI 眼前）。

## 13. 2026-11-02 上午：给 M5 一个**真实页面**的分母 —— 结论是"不做，而且上限只有 10%"

### 13.1 起点：上一棒的交接是"只剩两条正路"，其中一条是错的

§12.8 把"下一格"写成两条：① `Application` 门面拆分（S4，纯搬砖）② 给 M5 一个真实页面
的分母。选 ②，理由是**信息价值不对等**：S4 用户零感知且早被判过"多窗口不依赖它"；
而 M5 是唯一开着的结构性问题，却一直用**合成树**当分母。

对账时发现分母错得更彻底：M5 的触发条件写作"**重建帧**掉帧"，而 §6.1 引用的
`frame-tax-probe` 四档**全是合成树**（`Column` 全量 2000 节点），真实页面根本不会那么搭。
**拿合成树判"真实页面要不要 M5"，等于拿错分母。**

### 13.2 做法：不新建量具，给已有的那一件加一档

`apps/bench` 已有 `showcase（真实应用根）`，但它是"整个应用 + 默认页"，不分页、也不给
`layout/paint` 三段；而 `M3::runTree` 住在 `apps/bench`（`Drift\Bench\` 不在 composer
自动加载里）⇒ `tools/` 用不了它。

所以落在 **`frame-tax-probe.php --pages`**：同一个量具、同一套词汇（`perFrame` / `layout` /
分段 / 版本），只把**工作负载**从合成树换成 `apps/showcase` 的 27 个真实页（发现规则与
`golden-raster --pages` 逐条相同：构造器无必填参数；跳过的 7 页**点名**）。

★★ 为什么不新建 `page-tax-probe.php`：本仓刚花三天收拾"9 个探针各抄一份"的遗产
（§10）。量具的**机械部分**（挂载 / 预热 / 计时 / 报告）只能有一份，换的只是工作负载。

### 13.3 三个口径坑（都踩了，都进了文件头）

| # | 坑 | 症状 | 真相 |
|---|---|---|---|
| ① | `attach()` **自己就跑一帧** | 冷帧 37.9ms，比同页第二次的 14.2ms 还怪 | 我又补了一次 `frame(0)` ⇒ **双计**，且两帧缓存状态不同，加起来没有意义 |
| ② | 重建帧造的垃圾污染后面的 layout 测量 | 500 行 `layout(us)` 从 8.0ms 变 11.6ms（+45%） | 重建每帧造一整棵新树 ⇒ GC 压力 ⇒ **全量重排必须排在重建帧之前** |
| ③ | 分段是**纳秒**，表头印 us | 重建帧 "1814130us" | 换算是 `formatNs()` 那件事的老账（1000×），这次是分段没除 1000 |

### 13.4 数字（27 页，1200×800，解释器）

| 列 | 最重页 | 典型页 | 说明 |
|---|---|---|---|
| **打开**（`attach` 自带那帧，冷 shaping） | **TablePage 21.7–26.1ms** | 1.4–11.7ms | **超 16.7ms 预算**，但一次性（每串只 shaping 一次） |
| **重建帧**（每帧整页 `update`） | TablePage 4.1–4.4ms（settle 0.29 / layout 1.9 / paint 2.0） | 0.2–1.5ms | 真实"整页 setState"的形状 |
| **稳态帧** | TablePage 0.29ms · CustomPaintPage 1.54ms | 0.015–0.1ms | CustomPaintPage 每帧都在推进动画 |
| **全量重排**（暖缓存） | **TablePage 1.5–2.0ms** | 0.06–0.8ms | **M5 的上限** |

### 13.5 结论：M5 不做，理由是**上限**不是"没时间"

M5（脏矩形 / 脏边界）能省的**只有 `layout`** —— 它省不掉 `settle`（build + diff），也省不掉
`paint`。而在真实页面上：

- **上限 = 最重页的全量重排 ≈ 1.5–2.0ms = 帧预算的 9–12%**；
- 而且这 9–12% 只在"**整页重排、且大部分子树没变**"这一种形态下才拿得到。实测的两种
  真实形态都不属于它：整页重建（盒子全新，M5 一个都跳不过）与单点交互（本来就只重排
  那一小棵子树）。

⇒ 投入产出比明确不成立。**M5 的判据因此写实并可复查**：最重页全量重排 > 16.7ms 时再做，
当前余量 **10×**，每次跑 `--pages --check` 都会打印这个数。

### 13.6 顺带挖出的真问题：**页面首次打开 21.7ms**

比 M5 更值得看的是"打开"那一列。TablePage 首次打开 **21.7–26.1ms**（`SelectPage` 20.9ms、
`AlignPage` 18.4ms），大头是 `layout` —— 而 `layout` 冷热差 3–13×（`LogPage` 20 个元素：
冷 2.2ms / 暖 0.09ms）。这是**文字 shaping 的首次成本**（`DeterministicMetricsProvider`
按 `(text, style, maxWidth)` 缓存，命中后几乎免费）。

它一次性、且只在新串首次出现时付，所以**不是每帧税**；但它确实会**让第一次打开掉一帧**。
本轮**不做**（要先有"哪一页真的卡"的体感证据），只把它记成 P1-2（字形图集）旁边的
一个已知数。

### 13.7 判据（4 条）与变异（4/4 有牙）

| # | 判据 | 能红的真实事故 |
|---|---|---|
| ① | 扫到 ≥20 页 | 路径写错 ⇒ 0 页 ⇒ 后面三条恒绿 |
| ② | 最重页全量重排 ≤ 16.7ms 预算 | 真实页面变慢（当前余量 10×，不会因机器抖动误红） |
| ③ | 每页**暖态**全量重排 ≤ 页面打开 | 缓存没生效 / 两次量的不是同一棵树 |
| ④ | 整页重建的 layout 与全量重排**同量级** | **layout 哪天变成增量了** ⇒ "M5 的上限 = 全量重排"这句话失效，结论要重新论证 |

★ **故意没有**"稳态帧 paint 必须全跳过"这条：`CustomPaintPage` 每帧都在推进动画，它的
稳态帧本来就该画；而"动画在跑"与"门控退化"从这几个数上**长得一模一样**，判据分不开
⇒ 硬判只会误伤，误伤的判据下一棒只会被关掉。门控完整性交给合成档的 ④⑤（那里树是静止的）。

变异：①门槛提到 100 页 ②预算改成 1µs ③③比较方向反过来 ④④门槛放到 100 倍 —— **四条全红**，
还原后 `md5` 逐字节相同。
