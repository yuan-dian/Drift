## 0. 一页纸

**规模**：`src/` 320 文件 / 50,012 行；`apps/` 77 / 9,350；smoke 18,492 行 / **1663 断言**；
lint **570 文件 · 22 条规则**；docref 70；selftest 双向自检。

**没变的判断**：三层树 + 三 pass 帧管线 + `TextDraft`（文本状态机唯一实现）+ 四档闸门，
骨架成熟度高于多数自研框架。这一条本轮复核仍成立。

**本轮新增的三条结论**：

1. **第一条硬上限出现了（实测）**：1503 节点一帧 **18.0ms**（PHP 侧，不含光栅）⇒ 60fps 的
   可承载规模约 **1400 节点**；453 节点 6.6ms 仍有余量。瓶颈不是「某一段慢」，而是
   **settle / layout / paint 三段都是 O(N)，且对「只有一个控件在动」没有任何减免**。
2. **业务刚需还有三处完全空白**：文件对话框（`IFileDialog` 0 处）、滚动惯性（velocity 0 处）、
   undo/redo（0 处）。它们不是「框架能力」，是用户第一天就会去找的东西。
3. **量具自己坏了没人发现**：`bench` 的 M3（唯一的布局/绘制规模基准）已停摆 ——
   `new ShowcaseRoot()` 参数缺失 + 用例尺寸 1280×800 装不下 showcase。本轮已修，
   §1 的数字是修复后第一次跑出来的。

## 1. 实测：帧成本 vs 规模（bench M3，AOT 产物）

`RecordingCanvas`（只记录命令、不做光栅），`present≈0`。逐帧 **全量** settle + layout + paint
（基准刻意不跳过，测的是最坏情形）。

| 用例 | 节点 | settle | layout | paint | total | layout/节点 |
|---|---|---|---|---|---|---|
| showcase（真实应用根） | 104 | 0.145 ms | 1.103 ms | 0.844 ms | **2.143 ms** | 10.6 µs |
| 参数化 20×3 | 83 | 0.099 | 0.698 | 0.455 | **1.265 ms** | 8.4 µs |
| 参数化 50×8 | 453 | 0.496 | 3.750 | 2.300 | **6.586 ms** | 8.3 µs |
| 参数化 100×14 | 1503 | 1.345 | 10.274 | 6.138 | **18.014 ms** | 6.8 µs |

**四条解读**：

1. **三段都是 O(N)**：layout 6.8–10.6 µs/节点、paint 4.1–8.1 µs/节点、settle 0.9–1.4 µs/节点。
   PHP AOT 的每节点成本比 C++ 框架高两个数量级，这不是可优化项，是**语言税**——
   结构上的答案只能是「每帧少走节点」，不是「把每节点做快」。
2. **settle 没有「干净帧」快路径**：`Element::settle()` 第一遍**无条件全树**
   （`src/Widget/Element.php` 的 `settle()` 注释写明：这一遍还负责 `adoptBoxes()`，
   跳过会让容器握空盒 ⇒ 首屏全白且不报错）。⇒ 一个 Spinner 在转，全树每帧付一次 0.9 µs/节点。
3. **paint 永远全量**：`Frame::run()` 的 ③ 段无条件 `paintComposed()`；Render 层**没有脏边界**
   （`src/Layout/RenderObject.php` 类注释：「`relayout()` 永远全树，要等 M5 与脏矩形成对做」）。
4. **只有 layout 有跳过判据**（`didRebuild || boxEpoch 变 || 约束变`，`src/App/Frame.php`）。

**由此得到两种真实帧型**：

| 帧型 | 走哪几段 | 1503 节点 | 外推 60fps 上限 |
|---|---|---|---|
| 纯 hover / 光标移动（不重建） | settle + paint | 7.4 ms | ≈ 2200 节点 |
| 滚动 / 动画（每帧重建） | settle + layout + paint | 18.0 ms | ≈ **1400 节点** |

> 结论：**「几千节点的企业表格」在当前结构下不可达**。而 1400 节点大约是「30 行 × 8 列
> 带图标的表格」的量级 —— 正好是 `Table` 的目标场景。这是下一阶段最该先解决的结构问题。

### 2.1 `settle()` 的无条件全遍

**证据**：`src/Widget/Element.php::settle()` 的注释 —— 第一遍「**无条件**跑，不能因
`pendingDirty() === 0` 整遍跳过」，因为这一遍还做 `adoptBoxes()`（把子盒挂进父盒），
挂载路径不调它。实测代价 0.9–1.4 µs/节点。

**为什么现在这样是对的**：这是真机抓出来的（首屏全白、smoke 全绿），注释里留着原委。
不是疏忽。

**方案**：把「待挂接」变成**显式队列**——`Element::syncBox()` 是唯一盒创建点，那里把
`(parent, child)` 入队；`settle()` 只处理队列 + 重建脏节点。全遍保留为 `--verify` 模式的
对照实现（selftest 里两者结果必须一致）。

**判据**：① `adoptBoxes()` 调用次数 == 新盒数（加计数器断言）；② smoke 全绿；
③ bench 1503 节点 settle 从 1.345ms 降到 **<0.3ms**；④ 真机首屏有墨（沿用既有探针）。

### 2.2 `updateChildren()` 的 O(n²) 配对

**证据**：`src/Widget/Element.php::updateChildren()` —— 对每个新子，从头扫整张旧表找
`get_class` 相同且 `Key::same()` 的槽位。⇒ 单个容器 O(k²)，k = 该容器子数。
100 子 = 5,000 次配对；1000 子 = 500,000 次。

**为什么现在没炸**：树是宽而浅的（每个容器子数不大），且 `453 节点 settle 0.496ms` 说明
当前规模无感。**但它是"每帧 rebuild"路径上的固定税**，与 2.1 叠加就是 settle 的全部成本。

**方案**（Flutter 的 `updateChildren` 三扫）：① 从头同步，直到类型/键不匹配；② 从尾同步，
直到不匹配；③ 中间段建 `(class, key) → 索引队列` 的 map，O(1) 取；取不到的新建。
无 key 的子走位置配对（与现状语义一致）。

**判据**：① 同序重建 1000 子，配对次数从 ~500k 降到 ~1k（加计数器）；② key/复用相关
smoke 全绿；③ 乱序 + key 的用例行为不变（现有用例已覆盖）。

### 2.3 paint 无脏边界 / 无层缓存

**证据**：`Frame::run()` ③ 段无条件 `paintComposed()`；`RenderObject` 类注释写死
「Render 层没有脏边界」。

**为什么现在没做**：注释的理由是「单独做脏矩形，瓶颈只是搬到对面」——正确。所以顺序是：
**先做层缓存（RepaintBoundary），不做脏矩形**。

**方案**：`RepaintBoundary` 显式声明（`Widget::repaintBoundary()`），盒持有上一次的
`DisplayList` + 一份「本帧是否变化」判据（重建过 / 盒 epoch 变 / 约束变 / 子边界变）。
未变则重放命令列表，跳过整棵子树的 `paint()`。滚动容器、`LazyColumn` 的行、`Table` 的
表头与行区是天然边界。

**判据**：① 1503 节点滚动帧 paint 从 6.1ms → **<1ms**；② golden 逐像素不变
（层缓存只能等价替换，不能改像素）；③ 缓存命中率可断言（计数器：`replayed / painted`）。

### 2.4 `tickAnimations()` 全树

**证据**：`Application::tickAnimations()` → `tickSubtree()` 递归全树；只要有一个动画在跑，
**每帧**访问所有节点（注释还写明「不许短路」——那是对的，但代价是 O(N)）。

**方案**：活跃集合。`AnimationController` / `AnimatedValue` 启动时注册、结束/取消时注销；
`tickAnimations()` 只遍历集合。全树遍历保留为兜底开关（`DRIFT_TICK_ALL=1`），
用于「漏注册」这类 bug 的排查。

**判据**：① 1 个 Spinner 时 tick 访问节点数 == 1（计数器）；② 多个动画都推进
（现有 smoke「多个 Spinner 只有一个转」的反例用例必须仍绿）；③ `wantsFrame()` 语义不变。

### 2.5 `Application` 门面

**证据**：62 个 `public function`、1885 行，横跨：生命周期 / 主题 / 任务 / 剪贴板 / 度量 /
路由 / 挂载 / 帧 / 定时器 / 帧预算 / 语义 / 动画 / 分片 / IO / 指针捕获 / 输入派发 /
命令 / 拖放 / 浮层 / 模态 / 面板。

**现状**：`docs/arch-v2/12-Application拆分.md` 已拆 5 片（`TextEditingBridge` /
`ScrollInputRouter` / `InputRouter` / `OverlayLayout` / `OverlayManager`），**剩 `FrameEngine`**
（`frame()` 285 行九段 + `wantsFrame()` + `after()` + 帧预算）未拆。

**建议**：按原计划拆 `FrameEngine`；顺带把散在 Application 的 `overlays()` / `snackbar*`
收进已存在的 `OverlayHost` 片。目标：Application < 1200 行，只留装配与 `@api` 观察面。

**判据**：smoke 全绿 + `api-surface` diff 有记录（公开面不变是硬要求）。

### 2.6 `TableState` 2118 行

**证据**：61 个方法，混居七件事：滚动偏移与节律 / 行虚拟化 / 选择与行态 / 三态排序 /
列宽拖拽与分割线 / 编辑会话（`TextDraft` + 提交）/ 指针落点（`pointerContentX` /
`columnAtX` / `pointerCaretOffset`）。

**为什么值得拆**：本阶段（7a/7b）每次改动都要在同一个文件里同时碰「几何」「会话」「指针」，
而这三者的失效模式完全不同（几何错了是画偏、会话错了是数据丢、指针错了是点不中）。
拆开才能让每类有独立的夹具与断言。

**方案**：`TableGeometry`（列宽 + `columnAtX` + `cellRect`）、`TableEditSession`
（draft / origin / commit / caret）、`TablePointer`（`pointerContentX` / `pointerCaretOffset`）。
`TableState` 只留「这一帧造哪几行 + 把三片接起来」。

**判据**：每片 < 400 行；表格相关 40+ 条 smoke 全绿；7b 余项（拖动框选 / Tab / 选词）
在新结构上各加 2 条断言。

### 2.7 `ScrollBarFade` 接线三处重复

**证据**：`ScrollViewState` / `LazyListState` / `TableState` 各自持一个
`private ?ScrollBarFade $barFade` + 私有 `bar()` 懒建 + `opacity()` 转发，三份同形代码。

**方案**：抽一个 `ScrollChrome`（或 trait）收「懒建 + `noteScroll()` + `opacity()`」。
量小，但它是「同一纪律写三遍就会漂」的典型。

### 2.8 `Tray` / `Dialog` 声明了却 `return null`

**证据**：`src/Platform/Tray.php` / `Dialog.php` 是完整接口（含 `install()` 返回 bool 的时序理由），
但 `Win32Platform::tray()` / `dialog()` 都 `return null; // M2+`。

**问题不在"没实现"**（诚实标注是对的），在于**调用方无从区分「平台不支持」与「还没做」**，
也无法在构建期知道自己拿到的是空。这正是 UDA `SupportLevel` 要解决的：查询时明确、
降级可解释。

**方案**：平台层统一 `capabilities(): int`（已有 `materialCapabilities()` 的雏形）+
`support(能力): Support` 三态（`Full` / `Partial{reason}` / `Unsupported`）。
`tray()` 保留（返回 `?Tray`），但**先问 `support()`** 成为纪律。

**判据**：① 每个平台实现都回答同一张能力表（漏答 ⇒ 编译期/自检报错）；
② 应用侧拿不到能力时有可读原因（不是 `null`）。

### 2.9 量具坏了：`bench` M3 停摆（已修）

两个 bug，都不报错、都表现为「M3 什么都没写」：

1. `new ShowcaseRoot()` —— `ShowcaseRoot` 的构造器要 `(notify, delay, showModal)` 三个闭包，
   0 参调用在 AOT 下是 `ArgumentCountError` ⇒ 进程 `exit=255`，`bench-out.txt` 停在 M2 末尾。
2. 用例尺寸 1280×800 —— showcase 首页横向 Flex 共需 826、只有 706 ⇒ C5 Fatal。

修法：`Trees::showcase()` 统一构造（三个空闭包 + 注释说明为什么不接真线），
尺寸改 1600×1000（与真机窗口同量级）。**教训**：基准是量具，量具坏了不会有人报错，
只会「结论静默消失」。⇒ 量具也要有自检（`bench` 跑完必须出现 4 个 `──` 段落）。

### 2.10 文档漂移：`docs/architecture/06` 缺点击链（已补）

`TapTracker` / `PointerEvent::clickCount` 落地后，输入章没有同步。已补 §2.1（四条规则表 +
否决 `CS_DBLCLKS` 的理由 + 验证口径 grep）。**这类漂移的根因**是「代码改了、写实文档没人提醒」——
`docref` 只查「引用的文件/行号是否存在」，查不出「新类没被任何文档提及」。

## 4. 可借鉴的八条（含落点）

| # | 来源 | 做法 | 落点 | 判据 |
|---|---|---|---|---|
| 1 | Flutter | `updateChildren` 三扫（头/尾同步 + 中间 keyed map） | `Element::updateChildren()` | 配对次数 500k → 1k |
| 2 | Flutter | `RepaintBoundary` 层缓存（显式边界 + 命令列表重放） | `Widget::repaintBoundary()` + `RenderProxyBox` 家族 | 滚动帧 paint <1ms、golden 不变 |

## 5. 建议路线

### A 批 —— 每帧成本（结构，先做，有实测支撑）

1. **settle 的 adoption 队列**（§2.1）：1503 节点 settle 1.345ms → <0.3ms。
2. **`updateChildren` 三扫**（§2.2）：去掉大容器的 O(k²)。
3. **动画活跃集合**（§2.4）：1 个动画不再全树 tick。
4. **`RepaintBoundary` 层缓存**（§2.3）：滚动帧 paint <1ms。

> 四件事做完，1503 节点滚动帧的估计值：1.3→0.3 + 10.3 + 6.1→1.0 ≈ **11.6ms**，
> 回到 60fps 预算内；再往上就该动脏矩形与布局脏边界了。
> **每件都单独可验证**（计数器断言 + bench 前后对比），不要求一次做完。

### B 批 —— 手感与业务刚需

5. 滚动惯性 + 平滑（`ScrollPhysics`：velocity → fling 衰减，纯策略层）。
6. 文件对话框（`IFileDialog`）+ 剪贴板多格式 + 文件拖放（「数据进出」一批做）。
7. 手势族：`long-press` / `double-tap`（`TapTracker` 已给时间与次数）；拖动框选
   （`capturePointer()` 已在，注意**元素跨帧换新**的捕获失效）。
8. undo / redo（命令栈 + `TextDraft`）。
9. `TableState` 拆分（§2.6）+ 7b 余项（拖动框选 / `Tab` 格间走 / 双击选词）。

### C 批 —— 平台与工具链

10. 平台能力表（`SupportLevel`）+ 托盘/通知/任务栏。
11. 多窗口（`map<HWND,…>` + `attach()` 收表面数组）。
12. `drift doctor` / `--json` / `--script` 截图 / 双后端像素一致 golden。
13. i18n / RTL、字形图集、脏矩形（按真实瓶颈出现顺序）。
