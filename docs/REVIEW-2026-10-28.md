### 五条判断

**三条强项（复核仍成立，且是真正的差异化）**

1. **分层与不变量守得住**。`Widget → Element → Render` 三树 + 三 pass 帧管线 +
   「全仓唯一的盒创建点」(`Element::syncBox()`)。依赖方向干净：`src/Widget/` 里
   **0 处** `use Drift\App\`（实测），`Geometry` 是最底层被 import 169 次。
2. **判据文化**。430 + 670 条断言几乎条条能证伪，变异自检是常规动作。
   这套"先问这条断言能不能红"的纪律，比多数商业框架的测试质量高。
3. **工具链**。四档闸门 + AOT 构建 + golden 像素基线 + `inspect`/`probe` 真机链。
   自研框架里罕见。

**三条弱项（本轮新增/修正）**

1. **表现力的"最后一公里"仍未通**：渐变原语在 `Rendering/Gradient.php` 写好三天了，
   `src/Widget/` 与 `BoxStyle` **0 消费者**；没有变换（rotate/scale）、没有隐式动画
   （`Animated*` 0 个）、没有页面转场。**这不是"不会做"，是"做完了没接线"**。
2. **API 门面形状在恶化**：`Widget` 1265 行 / **66 个 public 方法**，`Application`
   1885 行 / **67 个**。新控件作者无法从类形状判断"我该覆写谁"，只能读 18 万字节的注释。
3. **文档自身开始腐坏**：`docs/arch-v2/00-总纲.md` 的"自检命令"四条已失效（它说
   Stack/Align/Wrap/Grid 全零，实际有 4 个；说 lint 15 条，实际 22 条）；
   `apps/showcase` 的"诚实边界"段说"框架没有 SizedBox"——SizedBox 早就有，showcase 自己
   用了 20 次。**闸门只查 `file:line` 引用，不查这类叙述**。

## 1. 架构

### 1.1 骨架（复核仍成立）

| 决策 | 落点 | 为什么它是对的 |
|---|---|---|
| 三层树 | `Widget`(不可变描述) / `Element`(身份+生命周期) / `RenderBox`(布局绘制) | 与 Flutter 同构，且**没有**引入 `InheritedWidget` 那种隐式依赖魔法 |
| 三 pass | flush → layout → paint → present（`App/Frame.php`） | 顺序固定、可跳过，「跳过」本身有判据（`needsBuild` / `needsLayout`） |
| 单一盒创建点 | `Element::syncBox()`（唯一 `State::noteBoxReplaced()` 调用处） | 「换盒 ⇒ 必须重排」这个事实只记一次，帧外路径也覆盖 |
| 值对象化 | `Modifier` / `BoxStyle` / `EdgeInsets` / `Rect` 全 `final` + `clone` 换新 | 无就地修改 ⇒ 无"谁改了我的状态"类 bug |
| 响应式 | `Cell` / `Subject` / `SubjectBuilder`（细粒度，非依赖注入） | 比 WPF 绑定简单一个数量级，够用 |
| 命令 + 快捷键 | `CommandRouter` + `AcceleratorTable`（含冲突检测、启用禁用） | 菜单/按钮/快捷键同一条出口 |

**结论**：骨架不需要重画。真正的问题都在"骨架之上长出来的第二层"（见 1.2）。

### 1.2 五个结构性负债（按"还在变贵"排序）

| # | 症状 | 证据 | 为什么现在处理比以后便宜 |
|---|---|---|---|
| **L1** | `Widget` 是**上帝基类**：布局意图、视觉修饰、裁剪、合成、光标、身份、hover、键盘、语义、调试全挂在它身上 | `1265` 行 / `66` 个 public 方法；子类要 `padding()` 就得**自己覆写**（`6` 个控件覆写 `padding()`、`4` 个覆写 `background()`） | 每加一个控件（这批加了 6 个）都要重新判断"哪些方法落 `Modifier`、哪些落自有字段"。方法数只增不减 |
| **L2** | **修饰双轨制**：`Modifier`（任意控件贴一层）与 `BoxStyle`（控件自带样式）各管一半 | `Modifier.php` 619 行 vs `BoxStyle.php` 74 行；`Modifier` 有 `isDefault()` 守卫、`BoxStyle` 没有；两者字段重叠（背景/边框/圆角） | 越晚收敛，两边的字段越难对齐。今天的 `repaintBoundary` 漏进 `isDefault()` 就是这条的副产物 |
| **L3** | `Application` **门面过大**：窗口、表面、帧循环、浮层、命令、任务、主题、焦点、输入路由全在 | `1885` 行 / `67` 个 public 方法；`OverlayManager`(724) / `InputRouter`(927) 已外提，但门面仍转发 60+ 项 | 它被 5 个 `apps/*` 直接依赖；再长出"多窗口"就会变成 3000 行 |
| **L4** | `TableState` **2528 行**（阶段 8 抽出 `ColumnWidths`/`TableRowPicker` 后仍 2528） | 22 个 public 方法；编辑会话、列宽、选择、键盘、build 编排仍在一处 | 下一步"格级矩形选区"会再堆 300 行 |
| **L5** | `RasterCanvas` **1862 行**是**测试与预览的唯一像素源**，也是性能上限 | 它是纯 PHP 逐像素；今天实测 1920×1017 一帧 1.5s | 加后端（D2D）或做并发都要碰它；且它同时承担"参考实现"与"测试夹具"两个角色 |

**建议的处理顺序**：L2 → L1 → L5 → L3 → L4。
理由：L2 是**语义**问题（两套话术），先定；L1 是 L2 的上游（方法落在哪取决于口径统一）；
L5 是"要不要给测试换引擎"的独立决策，与 UI 架构无关；L3/L4 是纯搬砖，随时可做。

### 1.3 依赖方向

```
Geometry ← Rendering ← Layout ← Widget ← App ← Platform
                                     ↑
                                   State / Text / Input / Theme / Commands / Routing
```
- `Widget` 不 import `App`：**0 处**（实测）✓
- `App` 被 import 2 次（`apps/*` 之外只有 `PageHost` 相关）⇒ 门面没有被框架内部反向依赖 ✓
- 22 条 lint 规则里 `DependencyDirection` 在守这条线。

**唯一的气味**：`Widget/` 里有 6 个 `*Element` / `*State`（`DockElement`、`StackElement`、
`TableElement`、`TableBox`、`TextFieldBox`…）—— Element 层与 Widget 层同目录。逻辑上
Element 是框架内部，与"给应用用的控件"混在一起会让 `113 个文件`的目录失去可读性。

## 2. 实现质量（可维护性）

### 2.1 判据文化是最大资产（复核仍成立）

- 变异自检是常规动作：今天两次改动共 11 组变异，10 红 1 绿（绿的立刻导致删死代码）。
- 判据的**形状**在被持续改进：从"有墨就行"→"数命令"；从"`!== 3`"→"`=== 0` + 走到末尾"。
- `PITFALLS.md` 1813 行记录"踩过的坑 + 判据为什么这么写"，这是新人的最快入口。

### 2.2 ★ 但判据会反噬：今天两个自伤案例（本轮新增）

| 案例 | 形态 | 代价 |
|---|---|---|
| `㊷b` showcase 段 | 用**真光栅**（195 万像素）+ `inkCount()` 断"有墨" | **12.19s 换 10 条断言**，占 smoke 的 32%，而判据本身是弱判据 |

**共性**：两例都**不是实现错**，而是"测量方式本身选错了"。这类问题的检测成本极高

## 3. 性能（实测）

### 3.1 已知上限（`REVIEW-2026-10-27` 实测，复核仍成立）

- **干净帧**（无脏节点）1503 节点 **18.0ms**；**每帧重建** 453 节点 **16.1ms** / 1503 节点 **52.0ms**
  ⇒ 60fps 下**每帧被重建的 widget ≈ 400**。这条上限来自"PHP 建树"本身，不是布局算法。
- 已落地：滚动**零重建零重排**（A 批①②③）、Table 列虚拟化（−34% 节点 / −35% paint）。
- **余项**：`RepaintBoundary` 接线、adoption 队列、动画活跃集（A 批③④）。

### 3.2 量化取舍

滚动帧现在 **≈2–3.7ms**（Table 1000×20 列裁列后 3.66ms）。**60fps 预算 16.7ms**，
即还剩 4–5 倍余量 ⇒ 「框架自身性能」不再是瓶颈；下一阶段的性能问题会来自
**应用写法**（每帧重建、大列表未虚拟化），而不是框架。

### 3.3 测试面成本（今天已有结论）

gate 63.0s = feature 21.6 + smoke 17.0 + unit 5.2 + pages 5.2 + lint 4.6 + 其余。
smoke 从 32.4 降到 17.0 靠的是"假表面只录命令"。**再快只有并行**（→ ~28s），
或把 B 桶 app 级样板拆成独立项。

## 4. 易用性（DX）

### 4.1 好的地方

- **fluent 链式，无注解魔法**：`Text::make('hi')->paddingAll(8)->background($c)` 一眼能懂。
  刻意不用 `#[\Getter]` 这类编译期注解（`php.exe` 不认 ⇒ 闸门跑不起来），这是拿"少一点糖"
  换"工具链可信"。
- **一个 import 前缀**：`Drift\Widget\*`，不需要记 15 个命名空间。
- **示例台是活的规格**：23 页，每页对应一个能力，且**如实暴露缺口**（虽然有几处过期）。

### 4.2 摩擦点

| # | 摩擦 | 证据 | 影响 |
|---|---|---|---|
| U1 | **写一个状态页要两段**（`StatefulWidget` + `State`），且必须记得 `parent::__construct()`（忘就 255） | `ChainPage`/`InnerPage` 两个夹具今天才发现漏调 | 新手第一小时必踩；lint 只覆盖 `apps/**`（`AppSubclassCtorParent`） |
| U2 | **66 个方法没有分层**：IDE 提示是一堵墙，且不知道哪些该覆写 | `Widget.php` | 学习曲线陡 |
| U3 | **错误信息虽好，但发现晚**：控件不可用的地方（如给 `TextField` 套 `padding`）是运行期 Fatal，不是静态检查 | `Modifier::isDefault()` 守卫 | 写法错要到跑起来才知道 |
| U4 | **无 IDE/静态分析生态**：PHP 有 Psalm/PHPStan，本仓用的是自研 lint（22 条） | `tools/lint.php` | 拿不到"跳转定义/参数提示"之外的深度检查，且新人要学自研规则 |

### 4.3 一个具体的易用性判断

**这个框架今天的"最佳用户"是写示例台的人**（有 430+670 条闸门兜着、有 `inspect`/`probe`）。
**而"第一次写自己应用的人"缺三样**：
① 文件对话框（选不了文件等于做不了导入导出）；
② 滚动惯性（手感不对，第一天就会被用户抱怨）；
③ 撤销/重做（文本编辑之外完全没有）。

## 5. 扩展性

### 5.1 加一个控件要改几处？（实测流程）

| 步骤 | 是否必改 | 说明 |
|---|---|---|
| 1. `Widget` 子类 | ✓ | 覆写 `createRenderObject()` 或走 `createRenderObjectFromState()` |
| 2. `RenderBox` 子类 | ✓ | 布局 + 绘制 |
| 3. `padding()/background()` 等修饰 | **看情况** | 若不覆写则落 `Modifier`，若覆写则落自有 `BoxStyle` —— **这就是 L1/L2 的双轨制，新人无法判断** |
| 4. 主题取色 | ✓ | `ColorToken` 只有 10 个槽，`MetricToken` 9 个（缺 success/warning/focus/disabled/scrim） |
| 5. 语义/UIA | 半强制 | `SemanticsRole` 10 个；不声明则无障碍不可见 |
| 6. 测试 | ✓ | 至少 smoke 或 PHPUnit 一条 + 变异 |
| 7. lint 白名单 | **有时** | 部分规则按类名白名单（`Activatable` 那类已改结构性扫描，但仍有几处名单） |

**结论**：加控件的**成本主要在"3 与 4"**，而这两处正是 L1/L2 与主题 token 面窄的直接后果。

### 5.2 加一个渲染后端

现状：`Canvas` 接口 + `RecordingCanvas` / `RasterCanvas` / `SkiaCanvas`（桥）。
新增 D2D 需要实现 `Canvas` 全部 op，并用 `golden` 的 20 页 + 9 个原语场景做等价性验证 ——
**判据已经就位**（`backend-resolve`、`paintBoth` 的雏形）。这一层扩展性**好**。

### 5.3 加一个平台

`Platform/` 已有 `WindowHost` 接口按"多句柄"设计（`createWindow(hwnd)`），但
`Application::attach(RenderSurface)` 收**单数表面** ⇒ **一个 Application 一个窗口**。
这是当前最硬的结构上限：多窗口/多文档应用现在写不出来。

### 5.4 主题扩展性（偏弱）

- `ThemeData` 128 行，`ColorToken` 10 个、`MetricToken` 9 个、`TextRole` 若干。
- **没有控件级 token 槽**：`Button` 的底色、`Card` 的边框是从 `BoxStyle` + 少量 token 推的，
  第三方想"只改按钮圆角"没有落点（只能每次传 `radius()`）。
- 与 Flutter 的 `Theme.of(context).buttonTheme` / SwiftUI 的 `EnvironmentValues` 相比，
  **缺少"控件粒度的主题覆盖"**。

### 6.1 三个"必须承认"的判断

1. **表现力不是画不出来，是画不出来"声明式地"**：阴影/圆角/毛玻璃都能画，
   但只有一半能"在控件上声明"。`Gradient` 是唯一彻底断线的那个。
2. **业务控件面差的不是数量，是"企业应用那三件"**：TabView（多页签）、
   TreeView（层级数据）、DatePicker（时间输入）。表格已经有了，这三件补完，
   "能不能写企业应用"这个问题的答案就变成"能"。
3. **平台集成是"从框架到产品"的门槛**：文件对话框、拖文件、托盘、原生菜单 —— 四项全空。
   任何真实桌面应用第一周就会要它们。

## 7. 优化方案（三档，按"越拖越贵"排序）

### S 档 · 结构性（先做，做完 A 档才不返工）

| # | 动作 | 判据（怎么算做完） | 为什么排这里 |
|---|---|---|---|
| **S1** | **修饰口径统一**：`Modifier` 与 `BoxStyle` 收敛为一个 `BoxPainter`，或明确「`BoxWidget` 子类**不接** `mods`」并由 lint 拦住 | 新控件只有**一条**设置背景/圆角/边框的路；`isDefault()` 之类守卫只剩一处 | L2 是语义分裂，越晚越贵；今天 `repaintBoundary` 的坑就是它生的 |
| **S2** | **`Widget` 门面分层**：把 66 个方法按维度拆成 `LayoutIntent` / `Visual` / `Focusable` / `Semantic` 四个 trait（**API 不变**，只是声明位置变），基类只留 `build/createRenderObject/identity` | 新控件作者能在 30 秒内找到"我该覆写谁"；`Widget.php` < 400 行 | 它是 L1/S1 的上游；不拆，S1 无处落 |
| **S3** | **`RasterCanvas` 与测试解耦**：把"参考光栅"与"测试像素源"分开，后者可以用更小的视口/降采样 | smoke 里读像素的次数不再随视口面积线性增长 | 决定"以后还要不要为测试付 195 万像素" |
| **S4** | **`Application` 拆门面**：`WindowHost` / `OverlayHost` / `TaskHost` / `FrameDriver` 四个小门面，`Application` 只做组合 | 单文件 < 900 行；多窗口落地时不用再改 1885 行的类 | 纯搬砖，但多窗口/S 档都要先拆 |
| **S5** | **`TableState` 继续外提**：编辑会话（~380 行）与 build 编排分离 | 格级选区能加在**新类**上而不是旧类里 | 与 S4 同性质 |

### A 档 · 能力（感知最强，S 档之后做）

| # | 动作 | 说明 | 依赖 |
|---|---|---|---|
| **A1** | **接上"表现力三件套"**：`Gradient` 消费者（`BoxStyle`/`Modifier` 各一条）· `Transform` 控件（rotate/scale/translate）· `AnimatedValue` 上层的 `Animated*` 隐式动画 | 这是"两座桥断了"的正面修复；`Gradient` 已经写好三天没人用 | S1 |

| # | 动作 | 说明 |
|---|---|---|
| **B1** | **`docref` 升级**：把 `00-总纲.md` 那类"自检命令 + 期望值"接进闸门，跑一遍比对 | 今天已有 4 条失效；这是唯一能自动发现"文档说谎"的办法 |

## 10. 落地记录 · S2：`Widget` 拆分（2026-10-28 当天）

### 10.1 结果

| | 前 | 后 |
|---|---|---|
| `Widget.php` | **1265 行** | **420 行** |
| 基类自有 public 方法 | 66 | **10**（+ `mutate()` 一个 protected） |
| 方法声明位置 | 一个类 | 基类 11 + 四个能力面 57 |
| 解出新文件 | — | `Traits/WidgetModifiers`(375) · `WidgetFocus`(126) · `WidgetInteraction`(396) · `WidgetSemantics`(125) |
| 五行合计 | 1265 | 1442（**多了 177 行**：4 个 trait 的类头 docblock + 基类里那段拆分说明）|

**API 一个字节没变**：拆分前用反射快照了 68 个方法（public+protected）的
「名字 + 参数类型 + 默认值 + 返回类型」，拆完逐行比对——**完全一致**。

**真机逐像素一致**：`showcase.exe` 在 1920×1017 下的截图 md5 与拆分前**完全相同**
（`b85ad4b4…`，ink 41.7%）⇒ 这次重构对行为是透明的，不是"看起来没坏"。

### 10.2 ★ 顺手推翻了一条旧纪律（有实测）

`lint` 原本有一条 `orphan-trait`：**「trait 必须与一个具体类同文件」**，理由是
GUI 仓的坑「只有 trait 的文件不产出翻译单元，`cl` 收到空文件名」。
`docs/_archive/design-proposals.md` 还记着据此做的决定：**「不用 trait —— 未验证」**。

实测三件事：
1. 4 个只含 trait 的文件一起走 `drift-build showcase` ⇒ **构建通过**（12.2 MB，135s）；
2. `_codegen/build/src/Widget/Widget.cc` 里能找到内联进去的 trait 方法，
   **没有**为空文件产出翻译单元；
3. 真机截图 md5 与拆分前完全一致。

⇒ 那条坑在今天的 tpc 上**不复现**，规则的前提消失了。但它想防的事还在
（没人 `use` 的 trait 是死代码 + 白跑一个空文件），所以**把判据改成表达本意**：

> `orphan-trait`：trait 必须被某个类 `use`（判定用类体内的短名 `use X;`）。

★ 顺带记一次自己的假判据：第一版正则 `(^|[\s;{])use\s+X;` 会把**注释掉的**
`// use X;` 也算成"被使用"——反例自检（注释掉 `use WidgetSemantics;`）时它
**0 error**，等于没牙齿。改成行首锚定 `^[ \t]*use[ \t]+X[ \t]*;` 才红。

### 10.3 落地时踩到的两个坑

1. **自动搬方法要处理单行 docblock**：`/** @internal … */` 与 `/** 一句话 */` 这种
   一行 docblock，用"上一行是 `*/`"去回溯会漏判 ⇒ 方法搬走了、注释留在原地，
   基类出现一排孤儿 docblock（第一次拆完 415 行的版本就是这样）。
   判据：搬完数一遍"孤儿 docblock"（`*/` 之后下一个非空行不是声明）。
2. **多遍拆分不可重入**：按组跑三次（modifiers → focus → semantics），每次重新解析
   行号已经漂移 ⇒ 第二次起 docblock 归属判错。改成**单遍解析、单遍删除**。

### 10.4 新增的结构判据（`tests/Unit/Widget/WidgetSurfaceTest.php`）

| 断言 | 防的是什么 |
|---|---|
| 四个能力面必须还在（trait 集合相等） | 有人把 trait 又合回基类 |
| 能力面承载 **≥ 50** 个 public 方法 | **量具自证** —— `getTraits()` 返回空时"基类很小"会恒真 |
| 基类自有 public 方法 **≤ 12** | 新 setter 又往基类加 ⇒ 养肥 |
| `mods()` 声明在基类上 | 它一搬走，`Element::syncBox()` 的注释就与实现脱节 |

变异：把上限压到 5 ⇒ 该条立刻红（有牙）。

### 10.5 这一档没做的事

- **`@overridePoint` 标记 + lint**（"哪些方法子类不该覆写"）留到 **S1**：它要连带裁决
  `BoxWidget` 那 6 个控件为什么覆写 `padding()`——那是双轨制（L2）的正面，不能只加标记。
- `Application` / `TableState` / `RasterCanvas`（S3–S5）未动。

## 11. 落地记录 · S1：修饰口径统一（2026-10-28 当天）

### 11.1 先量了一遍"双轨"到底是几条轨

| 落点 | 谁在用 | 存储 | 判定 |
|---|---|---|---|
| `$mods`（`Modifier`） | 所有控件 | `fill` / `stroke` / `radius` / `padding` / … | **通用装饰层**，`RenderBox::paint()` ① 画 |
| `BoxWidget::$box`（`BoxStyle`） | `Button` / `PopupPanel` | 只有 `background` / `border` / `radius` | **完全是 `Modifier` 的子集** ⇒ 纯冗余 |
| `Card::$box` + `$padding` + `$shadow` | `Card` | 同上 + 内距 + 阴影 | 包装器参数，`build()` 翻给子控件 |
| `Span::background()`（ARGB int） | `Span` | 文本 span 的底 | 不是 Widget，不同层 |

★ 关键测量：`src/` 里 **`instanceof BoxWidget` 零消费者**（只有测试里两条"结构节点不该
继承它"的断言）。⇒ `BoxWidget` 剩下的作用只有"提供三个重复方法与一份重复存储"。

### 11.2 做的是"删掉第二份存储"，不是"合并两个值对象"

`BoxStyle` **留在 Layout 层**（它是 `RenderButton` / `RenderAppBar` / `RenderTable` /
`RenderTextField` 的构造参数，24 个文件在用 —— 那是渲染参数，不是 Widget 修饰）。
删掉的是 **Widget 层的第二个写入口**：

| | 前 | 后 |
|---|---|---|
| Widget 层样式存储 | `$mods` + `BoxWidget::$box` | **只有 `$mods`** |
| `BoxWidget` | 抽象基类（3 方法 + 1 字段） | **已删**（`git rm`） |
| `->background()` 落点 | 看类决定（`BoxWidget` 子类写 `$box`、其余写 `$mods`） | **一律 `$mods`** |
| `BoxStyle` 从哪来 | 存着 | 需要时 `Modifier::boxStyle()` **派生** |
| 守卫覆盖 | 只看 `$mods`（另一半静默） | **看全部**（只有一个存储） |

`Card` **不动**：它是 `StatelessWidget`（不产盒），自己的样式写 `$mods` 正好撞
`Element::syncBox()` 的守卫（"声明了修饰但不产盒"）⇒ 它必须自持一份再翻给子控件。
这条边界是**语义必需**，不是债务 —— 已写进 `Card` 的类注释。

### 11.3 ★★ golden 抓到了双画，而它只在描边上可见

改完第一版：`$mods` 里还留着用户设的 fill/stroke，`RenderBox::paint()` ① 画一遍、
`RenderButton::paintOwnChrome()` 再画一遍。我当时判断"同色同矩形 ⇒ 幂等"，并写进了注释。

**`golden/page` 立刻红了 2 页**：

| 页 | 差异 | 位置 |
|---|---|---|
| `ButtonsPage` | 32 像素（max Δ=13） | `y=260..263` / `288..291` —— **上下边框条带** |
| `ListPage` | 322 像素（max Δ=25） | `x=808..867` —— **按钮右边缘** |

**底色幂等（不透明矩形全覆盖），描边不幂等**（`Paint::stroke` 带抗锯齿，同色叠两次
≠ 一次）。恰好是最容易靠"看起来一样"漏掉的那一半。

修法：`RenderBoxWidget::paintsBoxChrome()`（默认 `false`），声明 `true` 的控件在
`Element::syncBox()` 里把交给盒的 `$mods` **剥掉**视觉三字段
（`Modifier::withoutBoxVisual()`）——**保留 `shadow`**（`Button` 的浮起影子走
`ShadowPainter`，用户显式 `->shadow()` 走 `paintBehind`，剥了就静默吞掉）。

剥完之后立刻跑 golden：**20 页全绿**（逐像素回到改动前）。

### 11.4 顺手补上 `isDefault()` 漏的 `repaintBoundary`

这是上一轮挂着的"待裁决"。判据：`isDefault()` 的注释写的是"没有任何修饰"，那它就必须
覆盖**全部**字段；"重绘边界丢了只是慢"是**后果**的辩解，不是"它不算修饰"的理由 ——
而静默失效的检测成本远高于一次多画的代价。`ModifierTest` 里那一行的期望从 `true`
改回 `false`，**表里再没有例外**。

### 11.5 顺带修好的两处静默失效

- **`AppBar` 的 `->background()` / `->border()` / `->radius()` 一直是死字段**：
  `BoxWidget` 把值存进 `$box`，而 `AppBar::createRenderObject()` 直接
  `new BoxStyle(主题…)`，**存了但没人读**。现在合并写在 `createRenderObject()` 里
  （与 `Button` / `PopupPanel` 同口径）。
- **`withoutBoxVisual()` 被前缀判据误判**：`ModifierTest` 的完整性自检用
  `str_starts_with($name, 'with')` 收集方法名，于是 `withoutBoxVisual` 被算成
  "漏了一行"。改成排除 `without` 前缀 —— **前缀判据要连"否定前缀"一起想**。

### 11.7 新判据：`tests/Unit/Widget/BoxChromeTest.php`（3 条）

| 断言 | 防的是什么 |
|---|---|
| 自绘控件把用户样式**合并进** `Render*` | "只剥不合并" ⇒ 用户设置变死字段（比双画更糟）|
| 交给**盒**的 `$mods` 已剥视觉三字段，且 `shadow` 保留 | 双画；以及剥过头 |
| `paintsBoxChrome()` 取值表（表驱动）| 新控件忘了声明 ⇒ 走默认 `false` 但实际自绘 ⇒ 双画 |

判据 2 读的是**挂载后盒上的 `mods()`**（`findBoxOf()`），不是 Widget 上的声明 —— 那才
是 `RenderBox::paint()` 每帧真正读的那一份。

### 11.8 这一档没做的事

- **`padding` 的双语义没有合并**，也不该合并：`Flex` / `LazyList` / `LazyGrid` /
  `PopupPanel` 覆写的 `padding()` 写自己的字段，因为**容器要拿 padding 参与排布数学**
  （`RenderFlex` 在 `deflate` 后直接用 `padding->left` 算 pen）。塞进 `$mods` 会让
  `RenderBox::layout()` ②⑤ 也做一次 ⇒ **双份内距**。这条边界已写进
  `WidgetModifiers::padding()` 的注。
- **`@overridePoint` 标记 + lint** 仍未做。今天它要裁决的对象少了一个（`BoxWidget`
  那三个覆写没了），剩下的 `padding` 覆写是**语义必需**而非需要拦的东西 ⇒ 这条
  标记的收益进一步下降，建议降级为"文档表"而不是 lint 规则。
- `Application` / `TableState` / `RasterCanvas`（S3–S5）未动。
