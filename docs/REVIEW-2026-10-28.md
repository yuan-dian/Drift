### 五条判断

**三条强项（复核仍成立，且是真正的差异化）**

1. **分层与不变量守得住**。`Widget → Element → Render` 三树 + 三 pass 帧管线 +
   「全仓唯一的盒创建点」(`Element::syncBox()`)。依赖方向干净：`src/Widget/` 里
   **0 处** `use Drift\App\`（实测），`Geometry` 是最底层被 import 169 次。
2. **判据文化**。430 + 670 条断言几乎条条能证伪，变异自检是常规动作。
   这套"先问这条断言能不能红"的纪律，比多数商业框架的测试质量高。
3. **工具链**。四档闸门 + AOT 构建 + golden 像素基线 + `inspect`/`probe` 真机链。
   自研框架里罕见。

**三条弱项（本轮新增/修正）**

1. **表现力的"最后一公里"仍未通**：渐变原语在 `Rendering/Gradient.php` 写好三天了，
   `src/Widget/` 与 `BoxStyle` **0 消费者**；没有变换（rotate/scale）、没有隐式动画
   （`Animated*` 0 个）、没有页面转场。**这不是"不会做"，是"做完了没接线"**。
2. **API 门面形状在恶化**：`Widget` 1265 行 / **66 个 public 方法**，`Application`
   1885 行 / **67 个**。新控件作者无法从类形状判断"我该覆写谁"，只能读 18 万字节的注释。
3. **文档自身开始腐坏**：`docs/arch-v2/00-总纲.md` 的"自检命令"四条已失效（它说
   Stack/Align/Wrap/Grid 全零，实际有 4 个；说 lint 15 条，实际 22 条）；
   `apps/showcase` 的"诚实边界"段说"框架没有 SizedBox"——SizedBox 早就有，showcase 自己
   用了 20 次。**闸门只查 `file:line` 引用，不查这类叙述**。

## 1. 架构

### 1.1 骨架（复核仍成立）

| 决策 | 落点 | 为什么它是对的 |
|---|---|---|
| 三层树 | `Widget`(不可变描述) / `Element`(身份+生命周期) / `RenderBox`(布局绘制) | 与 Flutter 同构，且**没有**引入 `InheritedWidget` 那种隐式依赖魔法 |
| 三 pass | flush → layout → paint → present（`App/Frame.php`） | 顺序固定、可跳过，「跳过」本身有判据（`needsBuild` / `needsLayout`） |
| 单一盒创建点 | `Element::syncBox()`（唯一 `State::noteBoxReplaced()` 调用处） | 「换盒 ⇒ 必须重排」这个事实只记一次，帧外路径也覆盖 |
| 值对象化 | `Modifier` / `BoxStyle` / `EdgeInsets` / `Rect` 全 `final` + `clone` 换新 | 无就地修改 ⇒ 无"谁改了我的状态"类 bug |
| 响应式 | `Cell` / `Subject` / `SubjectBuilder`（细粒度，非依赖注入） | 比 WPF 绑定简单一个数量级，够用 |
| 命令 + 快捷键 | `CommandRouter` + `AcceleratorTable`（含冲突检测、启用禁用） | 菜单/按钮/快捷键同一条出口 |

**结论**：骨架不需要重画。真正的问题都在"骨架之上长出来的第二层"（见 1.2）。

### 1.2 五个结构性负债（按"还在变贵"排序）

| # | 症状 | 证据 | 为什么现在处理比以后便宜 |
|---|---|---|---|
| **L1** | `Widget` 是**上帝基类**：布局意图、视觉修饰、裁剪、合成、光标、身份、hover、键盘、语义、调试全挂在它身上 | `1265` 行 / `66` 个 public 方法；子类要 `padding()` 就得**自己覆写**（`6` 个控件覆写 `padding()`、`4` 个覆写 `background()`） | 每加一个控件（这批加了 6 个）都要重新判断"哪些方法落 `Modifier`、哪些落自有字段"。方法数只增不减 |
| **L2** | **修饰双轨制**：`Modifier`（任意控件贴一层）与 `BoxStyle`（控件自带样式）各管一半 | `Modifier.php` 619 行 vs `BoxStyle.php` 74 行；`Modifier` 有 `isDefault()` 守卫、`BoxStyle` 没有；两者字段重叠（背景/边框/圆角） | 越晚收敛，两边的字段越难对齐。今天的 `repaintBoundary` 漏进 `isDefault()` 就是这条的副产物 |
| **L3** | `Application` **门面过大**：窗口、表面、帧循环、浮层、命令、任务、主题、焦点、输入路由全在 | `1885` 行 / `67` 个 public 方法；`OverlayManager`(724) / `InputRouter`(927) 已外提，但门面仍转发 60+ 项 | 它被 5 个 `apps/*` 直接依赖；再长出"多窗口"就会变成 3000 行 |
| **L4** | `TableState` **2528 行**（阶段 8 抽出 `ColumnWidths`/`TableRowPicker` 后仍 2528） | 22 个 public 方法；编辑会话、列宽、选择、键盘、build 编排仍在一处 | 下一步"格级矩形选区"会再堆 300 行 |
| **L5** | `RasterCanvas` **1862 行**是**测试与预览的唯一像素源**，也是性能上限 | 它是纯 PHP 逐像素；今天实测 1920×1017 一帧 1.5s | 加后端（D2D）或做并发都要碰它；且它同时承担"参考实现"与"测试夹具"两个角色 |

**建议的处理顺序**：L2 → L1 → L5 → L3 → L4。
理由：L2 是**语义**问题（两套话术），先定；L1 是 L2 的上游（方法落在哪取决于口径统一）；
L5 是"要不要给测试换引擎"的独立决策，与 UI 架构无关；L3/L4 是纯搬砖，随时可做。

### 1.3 依赖方向

```
Geometry ← Rendering ← Layout ← Widget ← App ← Platform
                                     ↑
                                   State / Text / Input / Theme / Commands / Routing
```
- `Widget` 不 import `App`：**0 处**（实测）✓
- `App` 被 import 2 次（`apps/*` 之外只有 `PageHost` 相关）⇒ 门面没有被框架内部反向依赖 ✓
- 22 条 lint 规则里 `DependencyDirection` 在守这条线。

**唯一的气味**：`Widget/` 里有 6 个 `*Element` / `*State`（`DockElement`、`StackElement`、
`TableElement`、`TableBox`、`TextFieldBox`…）—— Element 层与 Widget 层同目录。逻辑上
Element 是框架内部，与"给应用用的控件"混在一起会让 `113 个文件`的目录失去可读性。

## 2. 实现质量（可维护性）

### 2.1 判据文化是最大资产（复核仍成立）

- 变异自检是常规动作：今天两次改动共 11 组变异，10 红 1 绿（绿的立刻导致删死代码）。
- 判据的**形状**在被持续改进：从"有墨就行"→"数命令"；从"`!== 3`"→"`=== 0` + 走到末尾"。
- `PITFALLS.md` 1813 行记录"踩过的坑 + 判据为什么这么写"，这是新人的最快入口。

### 2.2 ★ 但判据会反噬：今天两个自伤案例（本轮新增）

| 案例 | 形态 | 代价 |
|---|---|---|
| `㊷b` showcase 段 | 用**真光栅**（195 万像素）+ `inkCount()` 断"有墨" | **12.19s 换 10 条断言**，占 smoke 的 32%，而判据本身是弱判据 |

## 3. 性能（实测）

### 3.1 已知上限（`REVIEW-2026-10-27` 实测，复核仍成立）

- **干净帧**（无脏节点）1503 节点 **18.0ms**；**每帧重建** 453 节点 **16.1ms** / 1503 节点 **52.0ms**
  ⇒ 60fps 下**每帧被重建的 widget ≈ 400**。这条上限来自"PHP 建树"本身，不是布局算法。
- 已落地：滚动**零重建零重排**（A 批①②③）、Table 列虚拟化（−34% 节点 / −35% paint）。
- **余项**：`RepaintBoundary` 接线、adoption 队列、动画活跃集（A 批③④）。

### 3.2 量化取舍

滚动帧现在 **≈2–3.7ms**（Table 1000×20 列裁列后 3.66ms）。**60fps 预算 16.7ms**，
即还剩 4–5 倍余量 ⇒ 「框架自身性能」不再是瓶颈；下一阶段的性能问题会来自
**应用写法**（每帧重建、大列表未虚拟化），而不是框架。

### 3.3 测试面成本（今天已有结论）

gate 63.0s = feature 21.6 + smoke 17.0 + unit 5.2 + pages 5.2 + lint 4.6 + 其余。
smoke 从 32.4 降到 17.0 靠的是"假表面只录命令"。**再快只有并行**（→ ~28s），
或把 B 桶 app 级样板拆成独立项。

## 4. 易用性（DX）

### 4.1 好的地方

- **fluent 链式，无注解魔法**：`Text::make('hi')->paddingAll(8)->background($c)` 一眼能懂。
  刻意不用 `#[\Getter]` 这类编译期注解（`php.exe` 不认 ⇒ 闸门跑不起来），这是拿"少一点糖"
  换"工具链可信"。
- **一个 import 前缀**：`Drift\Widget\*`，不需要记 15 个命名空间。
- **示例台是活的规格**：23 页，每页对应一个能力，且**如实暴露缺口**（虽然有几处过期）。

### 4.2 摩擦点

| # | 摩擦 | 证据 | 影响 |
|---|---|---|---|
| U1 | **写一个状态页要两段**（`StatefulWidget` + `State`），且必须记得 `parent::__construct()`（忘就 255） | `ChainPage`/`InnerPage` 两个夹具今天才发现漏调 | 新手第一小时必踩；lint 只覆盖 `apps/**`（`AppSubclassCtorParent`） |
| U2 | **66 个方法没有分层**：IDE 提示是一堵墙，且不知道哪些该覆写 | `Widget.php` | 学习曲线陡 |
| U3 | **错误信息虽好，但发现晚**：控件不可用的地方（如给 `TextField` 套 `padding`）是运行期 Fatal，不是静态检查 | `Modifier::isDefault()` 守卫 | 写法错要到跑起来才知道 |
| U4 | **无 IDE/静态分析生态**：PHP 有 Psalm/PHPStan，本仓用的是自研 lint（22 条） | `tools/lint.php` | 拿不到"跳转定义/参数提示"之外的深度检查，且新人要学自研规则 |

### 4.3 一个具体的易用性判断

**这个框架今天的"最佳用户"是写示例台的人**（有 430+670 条闸门兜着、有 `inspect`/`probe`）。
**而"第一次写自己应用的人"缺三样**：
① 文件对话框（选不了文件等于做不了导入导出）；
② 滚动惯性（手感不对，第一天就会被用户抱怨）；
③ 撤销/重做（文本编辑之外完全没有）。

## 5. 扩展性

### 5.1 加一个控件要改几处？（实测流程）

| 步骤 | 是否必改 | 说明 |
|---|---|---|
| 1. `Widget` 子类 | ✓ | 覆写 `createRenderObject()` 或走 `createRenderObjectFromState()` |
| 2. `RenderBox` 子类 | ✓ | 布局 + 绘制 |
| 3. `padding()/background()` 等修饰 | **看情况** | 若不覆写则落 `Modifier`，若覆写则落自有 `BoxStyle` —— **这就是 L1/L2 的双轨制，新人无法判断** |
| 4. 主题取色 | ✓ | `ColorToken` 只有 10 个槽，`MetricToken` 9 个（缺 success/warning/focus/disabled/scrim） |
| 5. 语义/UIA | 半强制 | `SemanticsRole` 10 个；不声明则无障碍不可见 |
| 6. 测试 | ✓ | 至少 smoke 或 PHPUnit 一条 + 变异 |
| 7. lint 白名单 | **有时** | 部分规则按类名白名单（`Activatable` 那类已改结构性扫描，但仍有几处名单） |

**结论**：加控件的**成本主要在"3 与 4"**，而这两处正是 L1/L2 与主题 token 面窄的直接后果。

### 5.2 加一个渲染后端

现状：`Canvas` 接口 + `RecordingCanvas` / `RasterCanvas` / `SkiaCanvas`（桥）。
新增 D2D 需要实现 `Canvas` 全部 op，并用 `golden` 的 20 页 + 9 个原语场景做等价性验证 ——
**判据已经就位**（`backend-resolve`、`paintBoth` 的雏形）。这一层扩展性**好**。

### 5.3 加一个平台

`Platform/` 已有 `WindowHost` 接口按"多句柄"设计（`createWindow(hwnd)`），但
`Application::attach(RenderSurface)` 收**单数表面** ⇒ **一个 Application 一个窗口**。
这是当前最硬的结构上限：多窗口/多文档应用现在写不出来。

### 5.4 主题扩展性（偏弱）

- `ThemeData` 128 行，`ColorToken` 10 个、`MetricToken` 9 个、`TextRole` 若干。
- **没有控件级 token 槽**：`Button` 的底色、`Card` 的边框是从 `BoxStyle` + 少量 token 推的，
  第三方想"只改按钮圆角"没有落点（只能每次传 `radius()`）。
- 与 Flutter 的 `Theme.of(context).buttonTheme` / SwiftUI 的 `EnvironmentValues` 相比，
  **缺少"控件粒度的主题覆盖"**。

### 6.1 三个"必须承认"的判断

1. **表现力不是画不出来，是画不出来"声明式地"**：阴影/圆角/毛玻璃都能画，
   但只有一半能"在控件上声明"。`Gradient` 是唯一彻底断线的那个。
2. **业务控件面差的不是数量，是"企业应用那三件"**：TabView（多页签）、
   TreeView（层级数据）、DatePicker（时间输入）。表格已经有了，这三件补完，
   "能不能写企业应用"这个问题的答案就变成"能"。
3. **平台集成是"从框架到产品"的门槛**：文件对话框、拖文件、托盘、原生菜单 —— 四项全空。
   任何真实桌面应用第一周就会要它们。

## 7. 优化方案（三档，按"越拖越贵"排序）

### S 档 · 结构性（先做，做完 A 档才不返工）

| # | 动作 | 判据（怎么算做完） | 为什么排这里 |
|---|---|---|---|
| **S1** | **修饰口径统一**：`Modifier` 与 `BoxStyle` 收敛为一个 `BoxPainter`，或明确「`BoxWidget` 子类**不接** `mods`」并由 lint 拦住 | 新控件只有**一条**设置背景/圆角/边框的路；`isDefault()` 之类守卫只剩一处 | L2 是语义分裂，越晚越贵；今天 `repaintBoundary` 的坑就是它生的 |

## 10. 落地记录 · S2：`Widget` 拆分（2026-10-28 当天）

### 10.1 结果

| | 前 | 后 |
|---|---|---|
| `Widget.php` | **1265 行** | **420 行** |
| 基类自有 public 方法 | 66 | **10**（+ `mutate()` 一个 protected） |
| 方法声明位置 | 一个类 | 基类 11 + 四个能力面 57 |
| 解出新文件 | — | `Traits/WidgetModifiers`(375) · `WidgetFocus`(126) · `WidgetInteraction`(396) · `WidgetSemantics`(125) |
| 五行合计 | 1265 | 1442（**多了 177 行**：4 个 trait 的类头 docblock + 基类里那段拆分说明）|

**API 一个字节没变**：拆分前用反射快照了 68 个方法（public+protected）的
「名字 + 参数类型 + 默认值 + 返回类型」，拆完逐行比对——**完全一致**。

**真机逐像素一致**：`showcase.exe` 在 1920×1017 下的截图 md5 与拆分前**完全相同**
（`b85ad4b4…`，ink 41.7%）⇒ 这次重构对行为是透明的，不是"看起来没坏"。

### 10.2 ★ 顺手推翻了一条旧纪律（有实测）

`lint` 原本有一条 `orphan-trait`：**「trait 必须与一个具体类同文件」**，理由是
GUI 仓的坑「只有 trait 的文件不产出翻译单元，`cl` 收到空文件名」。
`docs/_archive/design-proposals.md` 还记着据此做的决定：**「不用 trait —— 未验证」**。

实测三件事：
1. 4 个只含 trait 的文件一起走 `drift-build showcase` ⇒ **构建通过**（12.2 MB，135s）；
2. `_codegen/build/src/Widget/Widget.cc` 里能找到内联进去的 trait 方法，
   **没有**为空文件产出翻译单元；
3. 真机截图 md5 与拆分前完全一致。

⇒ 那条坑在今天的 tpc 上**不复现**，规则的前提消失了。但它想防的事还在
（没人 `use` 的 trait 是死代码 + 白跑一个空文件），所以**把判据改成表达本意**：

> `orphan-trait`：trait 必须被某个类 `use`（判定用类体内的短名 `use X;`）。

★ 顺带记一次自己的假判据：第一版正则 `(^|[\s;{])use\s+X;` 会把**注释掉的**
`// use X;` 也算成"被使用"——反例自检（注释掉 `use WidgetSemantics;`）时它
**0 error**，等于没牙齿。改成行首锚定 `^[ \t]*use[ \t]+X[ \t]*;` 才红。

### 10.3 落地时踩到的两个坑

1. **自动搬方法要处理单行 docblock**：`/** @internal … */` 与 `/** 一句话 */` 这种
   一行 docblock，用"上一行是 `*/`"去回溯会漏判 ⇒ 方法搬走了、注释留在原地，
   基类出现一排孤儿 docblock（第一次拆完 415 行的版本就是这样）。
   判据：搬完数一遍"孤儿 docblock"（`*/` 之后下一个非空行不是声明）。
2. **多遍拆分不可重入**：按组跑三次（modifiers → focus → semantics），每次重新解析
   行号已经漂移 ⇒ 第二次起 docblock 归属判错。改成**单遍解析、单遍删除**。

### 10.4 新增的结构判据（`tests/Unit/Widget/WidgetSurfaceTest.php`）

| 断言 | 防的是什么 |
|---|---|
| 四个能力面必须还在（trait 集合相等） | 有人把 trait 又合回基类 |
| 能力面承载 **≥ 50** 个 public 方法 | **量具自证** —— `getTraits()` 返回空时"基类很小"会恒真 |
| 基类自有 public 方法 **≤ 12** | 新 setter 又往基类加 ⇒ 养肥 |
| `mods()` 声明在基类上 | 它一搬走，`Element::syncBox()` 的注释就与实现脱节 |

变异：把上限压到 5 ⇒ 该条立刻红（有牙）。

### 10.5 这一档没做的事

- **`@overridePoint` 标记 + lint**（"哪些方法子类不该覆写"）留到 **S1**：它要连带裁决

## 11. 落地记录 · S1：修饰口径统一（2026-10-28 当天）

### 11.1 先量了一遍"双轨"到底是几条轨

| 落点 | 谁在用 | 存储 | 判定 |
|---|---|---|---|
| `$mods`（`Modifier`） | 所有控件 | `fill` / `stroke` / `radius` / `padding` / … | **通用装饰层**，`RenderBox::paint()` ① 画 |
| `BoxWidget::$box`（`BoxStyle`） | `Button` / `PopupPanel` | 只有 `background` / `border` / `radius` | **完全是 `Modifier` 的子集** ⇒ 纯冗余 |
| `Card::$box` + `$padding` + `$shadow` | `Card` | 同上 + 内距 + 阴影 | 包装器参数，`build()` 翻给子控件 |
| `Span::background()`（ARGB int） | `Span` | 文本 span 的底 | 不是 Widget，不同层 |

★ 关键测量：`src/` 里 **`instanceof BoxWidget` 零消费者**（只有测试里两条"结构节点不该
继承它"的断言）。⇒ `BoxWidget` 剩下的作用只有"提供三个重复方法与一份重复存储"。

### 11.2 做的是"删掉第二份存储"，不是"合并两个值对象"

`BoxStyle` **留在 Layout 层**（它是 `RenderButton` / `RenderAppBar` / `RenderTable` /
`RenderTextField` 的构造参数，24 个文件在用 —— 那是渲染参数，不是 Widget 修饰）。
删掉的是 **Widget 层的第二个写入口**：

| | 前 | 后 |
|---|---|---|
| Widget 层样式存储 | `$mods` + `BoxWidget::$box` | **只有 `$mods`** |
| `BoxWidget` | 抽象基类（3 方法 + 1 字段） | **已删**（`git rm`） |
| `->background()` 落点 | 看类决定（`BoxWidget` 子类写 `$box`、其余写 `$mods`） | **一律 `$mods`** |
| `BoxStyle` 从哪来 | 存着 | 需要时 `Modifier::boxStyle()` **派生** |
| 守卫覆盖 | 只看 `$mods`（另一半静默） | **看全部**（只有一个存储） |

`Card` **不动**：它是 `StatelessWidget`（不产盒），自己的样式写 `$mods` 正好撞
`Element::syncBox()` 的守卫（"声明了修饰但不产盒"）⇒ 它必须自持一份再翻给子控件。
这条边界是**语义必需**，不是债务 —— 已写进 `Card` 的类注释。

### 11.3 ★★ golden 抓到了双画，而它只在描边上可见

改完第一版：`$mods` 里还留着用户设的 fill/stroke，`RenderBox::paint()` ① 画一遍、
`RenderButton::paintOwnChrome()` 再画一遍。我当时判断"同色同矩形 ⇒ 幂等"，并写进了注释。

**`golden/page` 立刻红了 2 页**：

| 页 | 差异 | 位置 |
|---|---|---|
| `ButtonsPage` | 32 像素（max Δ=13） | `y=260..263` / `288..291` —— **上下边框条带** |
| `ListPage` | 322 像素（max Δ=25） | `x=808..867` —— **按钮右边缘** |

**底色幂等（不透明矩形全覆盖），描边不幂等**（`Paint::stroke` 带抗锯齿，同色叠两次
≠ 一次）。恰好是最容易靠"看起来一样"漏掉的那一半。

修法：`RenderBoxWidget::paintsBoxChrome()`（默认 `false`），声明 `true` 的控件在
`Element::syncBox()` 里把交给盒的 `$mods` **剥掉**视觉三字段
（`Modifier::withoutBoxVisual()`）——**保留 `shadow`**（`Button` 的浮起影子走
`ShadowPainter`，用户显式 `->shadow()` 走 `paintBehind`，剥了就静默吞掉）。

剥完之后立刻跑 golden：**20 页全绿**（逐像素回到改动前）。

### 11.4 顺手补上 `isDefault()` 漏的 `repaintBoundary`

这是上一轮挂着的"待裁决"。判据：`isDefault()` 的注释写的是"没有任何修饰"，那它就必须
覆盖**全部**字段；"重绘边界丢了只是慢"是**后果**的辩解，不是"它不算修饰"的理由 ——
而静默失效的检测成本远高于一次多画的代价。`ModifierTest` 里那一行的期望从 `true`
改回 `false`，**表里再没有例外**。

### 11.5 顺带修好的两处静默失效

- **`AppBar` 的 `->background()` / `->border()` / `->radius()` 一直是死字段**：
  `BoxWidget` 把值存进 `$box`，而 `AppBar::createRenderObject()` 直接
  `new BoxStyle(主题…)`，**存了但没人读**。现在合并写在 `createRenderObject()` 里
  （与 `Button` / `PopupPanel` 同口径）。
- **`withoutBoxVisual()` 被前缀判据误判**：`ModifierTest` 的完整性自检用
  `str_starts_with($name, 'with')` 收集方法名，于是 `withoutBoxVisual` 被算成
  "漏了一行"。改成排除 `without` 前缀 —— **前缀判据要连"否定前缀"一起想**。

### 11.7 新判据：`tests/Unit/Widget/BoxChromeTest.php`（3 条）

| `paintsBoxChrome()` 取值表（表驱动）| 新控件忘了声明 ⇒ 走默认 `false` 但实际自绘 ⇒ 双画 |

是 `RenderBox::paint()` 每帧真正读的那一份。

### 11.8 这一档没做的事

- **`padding` 的双语义没有合并**，也不该合并：`Flex` / `LazyList` / `LazyGrid` /
  `PopupPanel` 覆写的 `padding()` 写自己的字段，因为**容器要拿 padding 参与排布数学**
  （`RenderFlex` 在 `deflate` 后直接用 `padding->left` 算 pen）。塞进 `$mods` 会让
  `RenderBox::layout()` ②⑤ 也做一次 ⇒ **双份内距**。这条边界已写进
  `WidgetModifiers::padding()` 的注。
- **`@overridePoint` 标记 + lint** 仍未做。今天它要裁决的对象少了一个（`BoxWidget`
  那三个覆写没了），剩下的 `padding` 覆写是**语义必需**而非需要拦的东西 ⇒ 这条
  标记的收益进一步下降，建议降级为"文档表"而不是 lint 规则。
- `Application` / `TableState` / `RasterCanvas`（S3–S5）未动。

## 12. 落地记录 · A1（前半）：渐变接线（2026-10-28 当天）

### 12.1 ★ A1 不能一次做完 —— 三件的成本差一个数量级

评审把 A1 写成"`Gradient` 消费者 · `Transform` 控件 · `Animated*` 隐式动画"，理由是
"原语都在，只差接线"。**逐项核过之后，这句话只对第一件成立**：

| 件 | 原语状态 | 真实成本 |
|---|---|---|
| **渐变消费者** | `Paint::withGradient()` / `RasterCanvas::fillSpanGrad()` / `SkiaCanvas::packGradient()` 全通，golden 已有 linear+radial 两个**画布级**场景 | **真·接线**：只缺 Widget 层的字段与一个坐标空间约定 |
| **`Transform`（rotate/scale）** | `Canvas` **只有 `translate`**，且 `RasterCanvas::translate()` 就是 `$offsetX += $dx` —— 没有矩阵 | **重写光栅器**：`rasterize()` 按扫描线填、`fillEdges()` 多边形容差全按轴对齐写；`pushClip(Rect)` 在旋转下不再是矩形。三后端 + op 表 + golden 全动 |
| **`Animated*` 隐式动画** | `AnimationController` / `Curve` / `AnimatedValue` 齐全 | **要层合成语义** —— `AnimationController` 自己的类注释就写着：*"`Opacity` / `Transform` 这类'整棵子树一起动'的包装暂不做（前提：要先有层合成语义）"* |

⇒ A1 拆成 **A1a（渐变，本轮完成）/ A1b（隐式动画，前置=层合成）/
A1c（Transform，前置=仿射光栅器）**。后两项各是独立立项，不是"接线"。

### 12.2 接线时真正的问题：**渐变没有坐标系**

`Gradient` 的坐标原来是**绝对像素**（`linear(20,20,180,20,...)`）。这对"直接画在一块
已知矩形上"（golden 场景、`CustomPainter`）是对的，但 `Card::make()->gradient(...)` 的
人**不知道自己的盒多大** —— 这个 API 等于没用。

落法：`Gradient` 加一个显式的**坐标空间**标记（`relative`），并提供四个"盒内比例"工厂：

| 工厂 | 语义 | 内部坐标 |
|---|---|---|
| `Gradient::vertical($colors)` | 上 → 下 | `(0,0) → (0,1)` + relative |
| `Gradient::horizontal($colors)` | 左 → 右 | `(0,0) → (1,0)` + relative |
| `Gradient::diagonal($colors)` | 左上 → 右下 | `(0,0) → (1,1)` + relative |
| `Gradient::radialBox($colors)` | 中心 → 内切圆 | 圆心 `.5,.5`、半径 `.5` + relative |

换算只有一个函数 `Gradient::resolvedTo($w, $h)`：比例 ⇒ 乘；绝对 ⇒ **原样返回同一实例**
（不新建对象，也保证 `CustomPainter` 里写死的绝对坐标不会被缩成 1/100）。

★ **为什么必须显式标记、不能靠"看起来像 0..1"**：`linear(0,0,1,0)` 是合法的绝对坐标
渐变。隐式猜会把这类用法画成一条 1 像素的线，而画面只是"看不清渐变"，不像错误。

### 12.3 落点：三层各一处，没有第二份

| 层 | 改动 | 为什么在这里 |
|---|---|---|
| `Gradient` | `relative` 标记 + 4 个比例工厂 + `resolvedTo()` | 坐标换算是**纯函数**，与宿主无关（同 `TextBoundary` 的判据） |
| `Modifier` | `gradient` 字段（**占位对象 + bool**，不是 `?Gradient`）+ `withGradient/withoutGradient/gradient()` | AOT 约束：可空对象退化成 `php::Var`（与 `$background` 同一条账） |
| `BoxStyle` | `backgroundGradient` 字段 + `backgroundPaint($w,$h)` | 三个自绘 chrome 的渲染盒共用一次换算，各自写就会漏一处 |
| `Widget::gradient()`（trait） | 一行转发 | 与 `->background()` 同一层 |
| `Card::gradient()` | 写自己的 `$box`（包装器参数） | 它不产盒，写 `$mods` 撞守卫 |
| `RenderButton` / `RenderAppBar` / `RenderTextField` / `RenderPopupPanel` | 改用 `backgroundPaint()` | 原来各写"有底就 `Paint::fill`"，加 paint source 要各改一遍 |

**并集语义统一为"渐变赢"**：`->background($c)` 与 `->gradient($g)` 并存时画渐变；
`->gradient(null)` 清掉它、实色回来。三处（`Modifier` / `BoxStyle` / `Card`）用**同一条**规则。

### 12.4 过程中撞到的两个坑

1. **`Card::gradient(Gradient)` 是不兼容覆写** —— `Widget::gradient(?Gradient)` 可空，
   子类收窄成非空 ⇒ 装载期 Fatal（`php -l` 查不出，`golden-raster` 一跑就炸）。
   与 `padding(EdgeInsets)` 那条是同一类：**覆写必须保持参数可空性**。
2. **`ModifierTest` 的完整性自检立刻抓到 `withGradient` 漏行**（20 个 `with*()` / 表 19 行）
   —— 这正是它存在的意义，补一行即可。

## 13. A4 第一件：`Stack` 的层叠定位（`->positioned()`）

`A4` 原计划是三件（`Wrap` / `Positioned` / `Align`）。先做 `Positioned`：它是另外两件里
"缺了就写不出东西"的那一件 —— `Stack` 有了却不能定位 ⇒ 叠层布局是半残的。

### 13.1 三个岔口与裁决

| 岔口 | 选项 | 裁决 | 理由 |
|---|---|---|---|
| 意图住哪 | `Positioned` 包装节点 vs `Modifier` 字段 | **字段** | W5 的判据是"修饰是字段不是节点"，`Expanded → grow()` 已经这么退过一次 |
| 盒怎么读 | `RenderStack` 直接读 `$kid->mods()` vs 落盒字段 | **落盒字段**（`setStackIntent()`） | 与 `setFlexIntent()` 同构。第二个读法会让下一个人问"为什么 inset 读 mods、grow 读字段" |
| 定位子撑不撑大 `Stack` | 撑大 vs 不撑大 | **不撑大** | 唯一能解开循环依赖的走法（见下） |

### 13.2 关键裁决：定位子不撑大 `Stack`

"定位子多大"要减"本盒多宽"（`left`+`right` ⇒ 宽 = 盒宽 − 左 − 右），而"本盒多宽"来自
`max(子)` ⇒ **互为前提**。两条出路：

1. 两遍 layout —— 本盒类注明令不是（`StackTest::testEachChildLaidOutOnce` 盯着）；
2. **断开依赖**：定位子不参与 `max` ⇒ 顺序变成
   `量非定位子 → 定本盒尺寸 → 排定位子`。

选 ②。它让这一遍仍是**单遍**（定位子只是被**挪后**量，不是被量两次），且白送了 CSS 的
拉伸语义。上游（Flutter）是同一条裁决。

**代价（写进判据，不掩饰）**：只有定位子的 `Stack` 尺寸是 `0×0` ⇒ 那个子被夹到 0、
画面上什么都没有、也不报错 ⇒ 修法是自己套 `SizedBox`。这条钉成**契约**
（`StackPositionedTest::testStackOfOnlyPositionedChildrenIsZero`）。

★ 这一条是**跑出来才看清的**：最初用 `SolidBox` 当那个子，撞了 C6 Fatal
（"尺寸超出可用空间"）—— 因为 `SolidBox` **故意无视约束**（它是 C6 的正向夹具）。
真控件会被夹到 0 ⇒ 静默消失。两种后果同源，判据取真控件那条。

### 13.3 落点（每层一处，无第二份）

| 层 | 改动 |
|---|---|
| `Modifier` | 4 个 `inset*` 字段（`NAN` = 未声明）+ `hasInset()` + `withInset(边序, 值)` + `isDefault()` 加一项 |
| `RenderBox` | 镜像 4 字段 + `setStackIntent()` + `hasInset()` / `inset*()`；`setMods()` 多派发一行 |
| `RenderStack` | `performLayout()` 分两趟 + `layoutPositioned()`；内禀值跳过定位子 |
| `WidgetModifiers` | `positioned(?left, ?top, ?right, ?bottom)`（`null` = 不动这一边，可多次叠加） |

★ `withInset(边序, 值)` 是**一个方法 + 4 个常量**，不是四个 `withInsetLeft()`：四条边是
同一个概念的四个分量，分成四个方法会让"设了哪几条边"在 `ModifierTest` 的完整性表里
占四行、而它们永远一起变。

### 13.4 收口判据：`ParentIntentTest`（不许再扩族）

加 `inset` 时 `Modifier` 已经是第 27 个字段。再往下，`Dock` 槽名、`Table` 列提示都会
想走同一条通道 —— **每加一族就要在 `Modifier` 加字段、在 `RenderBox` 加镜像与 setter、
在 `isDefault()` 加一行**，漏任何一处都是"这个修饰静默失效"。

所以钉的不是"现在几个字段"，而是**族的数目**：`set*Intent()` 的方法数 ≤ 2
（现状 `setFlexIntent` / `setStackIntent`）。**第三族 ⇒ 红 ⇒ 逼一次设计决定**
（引入 `ParentData` 值对象），而不是第 3 个 `set*Intent()`。

★ 为什么数方法而不是数字段：加族必然加方法（否则没法派发），而数字段要区分
"父意图"与"自己就用"（`width` / `clip`…）⇒ 得维护一份硬编码名单，那份名单本身会腐坏。
★ 配对第二条：每一族**都被 `setMods()` 派发**（声明了却不派发 ⇒ 整族死字段）。

## 14. A4 第二件：`Wrap`（顺带挖出"响亮失败路径自己是坏的"）

### 14.1 推翻 `04` §4.4：那条否决的**前提不成立**

`04` §4.4 判"不做 `Wrap`"，原话：`Wrap` 需要两遍布局 —— 先量所有子的自然尺寸 → 按可用宽
分行 → **而分几行决定容器高度，容器高度又可能改变子的宽度** ⇒ 需要 `layout` 迭代。

那个环在本实现里**构造性地不存在**：子拿到的约束是 `主轴 0..mainLimit、交叉轴 0..crossLimit`，
两个数**都直接来自父**，与"最后分了几行"无关 ⇒ 子的尺寸不依赖容器高度。

⇒ **每个子只 `layout()` 一次**。这与 §13 那次是同一类误判的形状：
把"我没想到单遍算法"写成了"这个问题需要两遍"（`04` §4.1 的"`Expand` 需要第二遍"同款）。

★ 判据把这条钉死了：`WrapTest::testEveryChildIsLaidOutOnce` —— 它红 = 实现里长出了迭代。

### 14.2 保留的两个边界（**没**假装都解决了）

| 边界 | 裁决 |
|---|---|
| **内禀值** | `Wrap` 的"自然宽"有两个合法答案（Σ子 / max子），本仓每轴只有一个内禀 ⇒ 按**一行**给（max-content）。偏宽但会被父 `constrain()` 夹回、不 C6。真要 min-content 需第二套内禀（= `04` §2 的 S3 仲裁），本轮不做 |
| **`Stretch`** | 同一行取该行最高值 ⇒ **正是** `04` §4.4 担心的那个迭代 ⇒ **响亮失败**（写明理由 + 修法），不静默退化成 `Start` |

⇒ 换句话说：`04` §4.4 真正担心的东西，只剩 `Stretch` 这一种形态，而它被**显式拒绝**了。

### 14.3 顺带挖出：`WidgetModifiers` 的响亮失败路径一直是坏的

给 `Wrap` 写"接收 `Stretch` 就 Fatal"时，第一次跑出来的是
`Error: Class "Drift\Widget\Traits\Errors" not found` —— 不是"退出码 3 + 人话 + 修法"。

顺着查到：**上一轮 S2 把方法搬进 trait 时，没把 `use Drift\Errors;` 一起搬过去**
⇒ `grow(-1)` / `shrink(-1)` / `opacity(1.5)` 三条校验路径**一直是坏的**
（用户看到的是 PHP 的类找不到：没有日志、没有修法、退出码也不是 3）。
同一次扫描又抓到 `ProcessTaskHost` / `ProcessWorker` 两处同类。

★ 这是最坏的一类静默：**失败路径自己失败，而没人会去测失败路径**。

修法与两道闸（新文件 `tests/Unit/Widget/LoudFailurePathTest.php`，3 tests）：
① **表驱动子进程判据** —— Widget 层的每个响亮失败入口都验"退出码 3 + 日志里那段人话"；
② **静态扫描** —— 出现裸 `Errors::`（**代码行**，不是注释）的文件必须 `use Drift\Errors;`。
★ ② 的第一版用 `str_contains($src, 'Errors::')` ⇒ 7 个命中里 4 个只是 docblock 文字
⇒ 改成逐行跳过注释。误报比漏报贵，这条当场就教育了我一次。

### 14.4 落点

`src/Layout/RenderWrap.php`（单遍：分行 + 定位两个标量平行数组 / 内禀按一行）·
`src/Widget/Wrap.php`（`direction` / `spacing` / `runSpacing` / `alignment` / `runAlignment`）·
`src/Widget/WrapElement.php`（与 `FlexElement` 同构）· 3 处补 `use Drift\Errors;`。

★ 行用 **三张标量平行数组**（`runMain` / `runCross` / `runFrom`）而不是
`list<array{float,float,list<RenderBox>}>`：后者在 AOT 下会被推成 `php::Var`，而行是热路径。

## 15. A3 第一件：`TabView`（多页签容器）

### 15.1 关键发现：框架里**已经有一个同构的东西** —— `PageHost`

动手前探出 `src/Routing/PageHostState.php:87`：

```php
$hosted[] = Offstage::make($this->pageFor($name), $name === $current);
```

和我原本打算写的 `TabView` 是**同一套机制**。这必须先判，否则就是造第二个轮子：

| | `PageHost`（路由）| `TabView`（本轮）|
|---|---|---|
| 键 | 页名 `string`（来自 `RouteTable`）| 序号 `int`（来自 `->tab()` 顺序）|
| 谁来选 | 订阅 `Subject`（外部 Store 驱动）| **受控** `selected()` + `onChanged()` |
| 谁来造页 | 工厂 + **在 State 里缓存** | 应用直接给 |
| 有没有可见的选择器 | 没有 | 有（页签条）|

**裁决：不共用代码，共用契约。** 共同部分只是那个三行的 `Offstage` 循环，抽出来只会
更难读（一边是 Stateful + 订阅，一边是 Stateless + 受控）。但契约必须一致，本轮把它
写进两边的类头 + 判据。

### 15.2 顺带澄清一条：`PageHost` 的"页面 Widget 只造一次"是**工厂**带来的，不是通用纪律

`PageHost` 类头写着"★ 每页的 Widget 只造一次……否则'保留状态'直接没了 —— 这是本节
最容易错的一处"。照抄会给 `TabView` 平白加一个 `State` + 缓存表。

那条只对**工厂**成立：`RouteTable::build($name)` 每次调用都可能返回一个带新参数的新实例。
`TabView` 没有工厂 —— 页面是应用当作**描述**给的，新实例只是"重新描述一遍"；
`OffstageElement::rebuild()` 对停着的 Element 做 `update()`，而 **State 挂在 Element 上，
不随 Widget 走**。⇒ `TabView` 可以是 `StatelessWidget`，零新增 Element / RenderBox。

### 15.3 三个岔口的裁决

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 受控 vs 自持 | **受控** | 与 `SegmentedControl` / `ToggleBase` 同纪律（"自持 ⇒ 两份真相"）。自持的写法看着更好用（点一下就切、应用不用接），破起来也最安静 |
| 自己当容器 vs 组合 | **`StatelessWidget`**，不新增 Element / RenderBox | 没有局部 UI 态；它只是"条 + 保活内容区"这个组合 |
| 页签条 | 复用 `SegmentedControl`（v1） | 单选 + 每段一个焦点 + `activate()` 三件事现成且已测；真 TabBar 是**另一个视觉契约**（见 §15.8）|

**有意的边界**：越界 `selected` ⇒ **全不选**（不夹到 0，与 `SegmentedControl` 同裁决）；
内容区**吃掉条以外全部高度**（每页套 `Expanded`，否则切页签时面板会跳）。

## 16. A3 第二件：`TreeView`（层级树）+ 两个框架级缺陷

### 16.1 三个岔口的裁决

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 展开集合：受控 vs 自持 | **受控**（`expanded()` + `onToggle()`） | 与 `TabView::selected` / `Table::selection` 同族。自持的话"展开全部 / 搜索时自动展开命中路径 / 跨会话记住展开态"应用一件也做不到，只能再补一套反向同步 API |
| 自己当容器 vs 组合 | **`StatelessWidget` + `LazyColumn`** | 零新增 Element / RenderBox，与 `LazyGrid` 同一条路。行构建器闭包**不捕获 `$this`**（同 `LazyGrid::build()` 纪律：捕获了就把整棵树留在渲染树上） |
| 数据形状 | 新值对象 `TreeNode`（`id`/`label`/`children`） | 与 `Option` 同族：`id` 是身份。展开集合与选中值都按 `id` 认，不按下标 —— 过滤 / 重排后下标会漂 |

**锚点按身份 key**（`keyOf(行 id)`）：展开一行会让它后面所有行的序号 +N，
按序号恢复会把视口甩到别的节点上（"展开一下，列表跳走了"）。实测 4200 → 4284
且顶部仍是同一个节点。

### 16.4 ★★ AOT 真机取证挖出两个缺陷（PHP 测试全绿时也看不见）

这一件最大的收获不是控件本身，而是**golden + 22 条判据都过的情况下**，
把窗口真的画出来看，立刻露出两个问题：

**① 标签被撑满后居中** —— 行里的标签按钮套 `Expanded`（点行的空白也算点这一行），
`Button` 默认内容居中 ⇒ 整棵树的标题全飘到窗口中间，缩进层级只能靠箭头位置读出来，
"看着像一段居中的文字"。修法不是给 `Button` 加参数而是加**公共能力**
`Button::alignLeft()`：借 `NavButton`（"这类按钮天生左对齐"）会把"树行"和
"导航项"焊在一起，改侧栏对齐会波及树。判据补了一条 `RenderButton::centersContent()`
为 `false`（`centersContent()` 是 `@internal` 夹具访问器，同 `hasIcon()`）。
—— 原有那条"叶子行与有子行标签起点相同"测的是 **Button 盒**的起点：盒看着对、
字却在中间，所以它一直是绿的。

**② `skipFocus()` 让按钮彻底点不动** —— 树行箭头（`IconButton` + `skipFocus()`，
目的是每行只留一个 Tab 站）点了毫无反应，画面、日志、退出码都没有任何线索。
A/B 一次（只删 `->skipFocus()`）就复现/消失，然后顺着 `focusHit()` 找到根因：

```php
// FocusManager::walk()（修前）
if ($node !== null && $node->skip) { return; }      // 整棵子树直接跳过
if (isFocusable()) { $order[] = $el; $byId[id] = $el; }   // 两张表一起填
```

`byId` 是"**可聚焦**元素表"，`focusHit()` 靠它回答"点到的这个东西能不能拿焦点"；
`order` 才是 Tab 序。两者共用一张表 ⇒ **"跳过 Tab 序"顺手把"点得动"也取消了**。
修法：`byId` 无条件登记可聚焦元素，`skip` 只挡 `order`（并沿子树传递）。

这是个**语义陷阱**：`skipFocus()` 的文档从头到尾写的是"不进 Tab 序"，
没有任何地方暗示"也就不响应指针"—— AppBar 工具组是它的典型用法，
只是那组按钮当时另有路径可达，没暴露。

## 17. A3 第三件（前半）：`CalendarView` + 两个值对象

`DatePicker` 拆成两半做：**月历本体**（这一件）+ **触发框与浮层**（下一件）。
理由：月历是"日期的全部规则"（闰年 / 月长 / 一号周几 / 前导格 / 行数），
它自己就能嵌进页面单独验；浮层那层是 `Select` 已经走过的老路（`overlayPanel` +
第二棵根树 + `dismiss`），混在一起做会让"日期算错"和"面板没关"两类问题互相掩盖。

### 17.1 三个岔口

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 日期用什么类型 | **自建 `YearMonth` / `LocalDate`** | ① 日历只要"这月几天 / 一号周几"，`\DateTimeImmutable` 反而要先钉时区（忘了就跨时区漂一天）；② 翻月是点击级操作，值对象比"构造 + 一串方法过 `php::Var`"便宜；③ `Option` / `TreeNode` 同族，纯值对象、`public readonly` 即终态 |
| 月份受控还是自持 | **受控**（`month()` + `onMonthChange()`） | "打开时跳到本月 / 记住上个月看的月份 / 搜索命中后跳到那个月"——自持的话三件都要补反向 API |
| 自己当渲染盒还是组合 | **`StatelessWidget` + `Column`/`Row`/`Button`** | 零新增 Element / RenderBox。日历是"一堆按钮排成网格"，没有需要盒级才知道的东西 |

★ `YearMonth` 与 `LocalDate` **分开**（而不是"day 恒为 1 的月"）：日历标题要"月"、
选中值要"天"，一个类型兼两职时 `day` 就成了"永远是 1 的占位符"，而 `plusMonths()`
之后它还是不是 1 只能靠口头约定。

### 17.2 判据 18 条（`CalendarDateTest` 9 + `CalendarViewTest` 9 / 91 断言）

| 组 | 防的是什么 |
|---|---|
| 月长 12 条 + 闰年 7 条 | 闰年四条规则各一个锚点（普通闰 / 百年非闰 / 400 年闰 / 平年） |
| 周几 6 个锚点 + `firstWeekday` | 用**已知日期**验，不拿 Sakamoto 自己验自己 |
| 翻月 8 条（含**反向跨年**） | 反向借位是唯一会暴露"月基写错"的方向 |
| ISO 往返 / 补零 / 比较 | `2026-10-09` 不补零会排到 `2026-10-10` 后面 |
| 行数 5/6 与 `MIN_ROWS` 兜底 | 28 天且 1 号周一的月份只需 4 行，太扁 |
| 只有本月是格子（31 / 29 / 28） | 别月留白，不是灰色按钮 |
| **首日列位**（前导 3 ⇒ 第一行 4 格、x ≈ 128） | ★ 前导算错一位整月都错位，而肉眼看"还是像日历" |
| 列等宽 40（`Expanded` 等分 + `compact()`） | 按钮最小宽超过格宽 ⇒ 布局超界 |
| 受控 3 条（点 15 号 / 两个月号 / 上报后画面不动） | 与 `TreeView` / `TabView` 同款正向判据 |
| 选中态（只一格 Primary、跨月不亮） | 跨月不亮是受控的**必然结果**，不是 bug —— 写成判据免得下次被"修" |
| 不占 Tab 站（走 `FocusManager::order()`） | ★ 初版用 `focusNode() === null` 判，**恒真**（节点只在声明过 focusOrder 时才建）⇒ 无牙；改成数 `order()` 才有 |

### 17.3 变异 14 组全红，其中两组暴露**真缺陷**

- **7 列等分的浮点溢出**：`344 / 7 × 7 = 344.00000000000006`，而 `RenderFlex` 的
  溢出判定是裸 `>` ⇒ 报"子项共需 344.0，可用只有 344.0（差 0.0）"的 Fatal。
  这不是我的宽度算错，是**任何等分 N 份都会撞上**的框架缺陷：`LayoutTolerance::EPSILON`
  （0.01px）+ `RenderFlex` / `RenderBox` 两处比较都带上它。真溢出（≥ 0.5px）照样报。
- **`Button` 没有紧凑档**：常规横向内边距是 `2×gap`，7 列各 40 宽装不下 ⇒ 同样超界。
  补 `Button::compact()`（内边距 `1×gap`，与 `alignLeft()` 同族："**这一个**按钮的
  布局微调"，不是新控件）。
  反例对照：借 `IconButton` 的 `all(gap*1.5)` 不行 —— 那是"纯图标正方形"的语义。

另一组不是"变红"而是**死规则**：`YearMonth::plusMonths()` 原本有个"负数走手工地板除"

## 18. A3 第三件（后半）：日 / 月 / 年三档视图

### 18.1 四个岔口（两个新裁决、两个继承 §17）

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 月/年网格**做成嵌套浮层**（laydate 那样弹一层） | **不做，原地换内容** | 浮层里再开浮层，`OverlayManager` 的属主清扫要变成两层；而收益只是"同一块区域的另一种画法"。原地换内容的还有一个好处：`DatePicker` 把它塞进浮层时，**里面不会再开第二个浮层** |

# §19 DatePicker / DateTimePicker / TimeView（2026-10-29）

## 19.1 一个入口、两个实现件

用户问的是"这个时间控件能不能选时分秒，是一个控件还是两个"。layui `laydate` 的事实：
**一个组件、五套面板**（`type: year|month|date|time|datetime`），而 `time` 面板里**没有日历**，
`datetime` 就是"左日历 + 右时分秒列"并排。所以它的"一个"是**调用形态**，不是实现形态。

我们的切法：

| 层 | 物件 | 值 |
|---|---|---|
| 面板件 | `CalendarView`（已有，**一字未改**） | `LocalDate` |
| 面板件 | `TimeView`（新） | `LocalTime` |
| 值 | `LocalDateTime`（新，只做组合 + ISO） | — |
| 入口 | `DatePicker` / `DateTimePicker`（新） | `LocalDate` / `LocalDateTime` |

**为什么不合成一个带 `type` 的类**（三条硬理由）：

1. `time-only` 的表单（"每天 02:00 跑批"）会被迫带一张用不上的 7×6 月历；合成后只能靠
   `type` 分支写两套布局，等于内部照样两块，只是少了一个类名。
2. `CalendarView::onSelected(LocalDate)` 的签名会被污染成"一天 + 也许还带个时间"
   （旁挂 `?LocalTime` 字段），而"选值"和"选值 + 可能有个附属值"是两种语义。
3. 组合是本仓既有纪律：`TreeView` 组合 `LazyColumn`、`CalendarView` 组合 `Row`/`Button`，
   都零新增 Element / RenderBox。`Row[CalendarView, TimeView]` 同理。

**为什么也不拆成两个彼此独立的输入控件**：表单里"选日期时间"是一个字段，两个不相干的框
还要应用自己保证它们属于同一条数据。所以 `DateTimePicker` 是**一个入口**。

## 19.2 顺带补的三条框架缝（都是被真机逼出来的）

| 缝 | 起因 | 修法 |
|---|---|---|
| `Widget::overlayPanel($f, ?float $maxWidth)` | 浮层面板宽上限写死 320（"一列选项"的口径），并排两块要 416 ⇒ `RenderFlex 放不下：共需 416，可用 304`，进程直接 exit 3 | 控件自报上限；`OverlayManager` 读它，缺省仍 320 |
| `LazyList::viewportExtent($px)` | 浮层里 `BuildContext` 的主轴**无界** ⇒ `viewportEstimate()` 退到它 ⇒ 60 格全造出来（虚拟化静默失效） | 允许列表自己声明视口；优先级排在"盒实测"之后、`ctx` 之前 |
| `OptionPanel::make(..., bool $scrollable = true)` | 外壳无条件套 `ScrollView`，而 `TimeView` 自带 `LazyColumn` ⇒ 嵌套滚动，布局期直接崩 | 内容自己滚时传 `false`，超限由 `PopupPanel` 裁剪 |

★ 三条都不是"为这个功能开的口子"：①是**内容语义**（面板多宽该由内容说），②是
**虚拟化的前提**（视口是窗口换算的除数），③是**职责不重叠**（`ScrollView` 的类注释早就写着
"别塞进外层滚动视口"）。

## 19.3 一处结构性教训：`PickerPanelSignal` 必须独立成文件

第一版把 `PickerPanelSignal` 和 `SelectPanelSignal` 一样顺手定义在 `DatePicker.php` 里
（"省一个文件"）。测试夹具里先 `new PickerPanelSignal()` 就 `Class not found` ——
autoload 是"类名 → 同名文件"，同文件第二个类只有在第一个先被加载时才存在。
`SelectPanelSignal` 至今靠"`Select` 总会被先用"这条**偶然**成立。

## 19.4 真机才看得见的两处视觉缺陷（PHP 测试全绿时）

放大 `_build/crop-time.png` 才看出来的，都**不影响点击、不报错**：

| 缺陷 | 根因 | 修法 |
|---|---|---|
| 相邻两列的 Primary 色块**贴成一片** | 列间没有间隔 | `COLUMN_GAP = 4`（列起点 0 / 72 / 144）|
| 滚动条**切在色块右边缘**上 | 条是画在视口里的（`thumbRect()` 按**渲染盒**宽定位，`MARGIN` 是它离盒边的距离）| 见下 |

第二处第一版是**错的**：给 `LazyColumn` 加 `->padding(right: 5)`。padding 只把内容挤窄、
挪不动条 —— 而且让 56 宽的按钮塞进 51 宽的视口，净效果是色块被裁一条边，条还在原地。

正确做法是把条的宽度算进**盒宽**：

```php
private const BAR_GUTTER  = ScrollBarGeometry::THICKNESS + 2.0 * ScrollBarGeometry::MARGIN; // 12
private const COLUMN_EXTENT = self::COLUMN_WIDTH + self::BAR_GUTTER;                        // 68
```

连带的两个后果（都写进了文档与常量注释）：

- 并排宽度不能再用 `COLUMN_WIDTH × 列数` 估 ⇒ 加 `TimeView::widthOf(bool $withSeconds)`；
- `DateTimePicker::PANEL_MIN_WIDTH`（常量）变成 `panelMinWidth(bool $withSeconds)`（方法）——
  时刻列随 `withSeconds()` 从两列变三列，写死一个数时两列模式白空一截、三列模式够不着。

★ 这条补了一个**几何判据**（`testScrollbarSitsRightOfCells`）：拿每列的 `thumbRect()` 与色块
右边界比，条必须落在外面。理由同"初始偏移"那条 —— 它不报错、只难看，不定住就会回归。

# §20 `disabled()` 禁用态（2026-10-29）

## 20.1 为什么是这一件，而不是 A1 后半（Transform / 隐式动画）

按 §7 的排序，S1/S2 已落地（§10/§11）、A1 只做了"渐变"一半（§12）、A3 三件已收口（§15/§16/§19）
⇒ 纸面上下一件是 **A1 后半**。我没有照做，理由是三处**代码事实**而不是喜好：

| 事实 | 证据 |
|---|---|
| 框架**没有** `disabled` | `grep -rn "function disabled\|isDisabled\|enabledValue" src/Widget/` ⇒ **0 处**；而 §17.5 与 §19.6 两次写着"要先有禁用态" |
| 但**四处局部实现**已经有了 | `ToggleBase::enabled()` / `Slider::enabled()` / `Segment::enabled()` / `SegmentedControl::enabled()`，各自"形状色降级 + 不响应激活 + 仍留 Tab 序" |
| 消费端**全部就绪、只缺最后一根线** | `RenderBox::hitTest()` 的注释里写着"禁用 ≠ 穿透的基础"；`SemanticsNode::$enabled` 字段在、注释写着"声明面"；C++ 桥 `drift_win32.cc:2894` 已经解析 PHP 传来的 `enabled`；`FocusManager` 的 `byId`/`order` 刚刚（TreeView 那轮）拆成两张表 |

也就是说：这不是"加一个能力"，是**一处概念漂移（四份实现）+ 一根断掉的线（消费端都在等）**。
A1 后半的两个东西要新建 `RenderTransform`（含命中逆变换，是新不变量）与"隐式动画"的帧驱动模式，
是**从零开始**；disabled 是**接线**。同样的工时，接线先做的边际收益高得多。

## 20.2 四处消费（以及一处画错的判断）

| 消费方 | 改在哪 | 结果 |
|---|---|---|
| 绘制 | `RenderBox::setMods()` | `composeOpacity = opacity × 0.38`，`paintComposed()` 在 `< 1` 时开层 ⇒ 整棵子树变淡，**零新增绘制代码** |
| 命中 | `RenderBox::hitTest()` + `RenderTable::hitTest()` | 返回**自己**；`InputRouter` 的 down 分支见 `isDisabled()` 直接 `return null` |
| 焦点 | `FocusManager::walk($el, $skip, $disabled)` | 子树既不进 `byId` 也不进 `order`；失焦是 `collect()` 末尾既有那条逻辑**免费**给的 |
| 语义 | `SemanticsBuilder::descend(..., bool $disabled)` | `enabled = semanticsEnabled() && !$off`（子树级） |

**★★ 画错的那一处**：第一版 `hitTest()` 里 `if ($this->disabled) { return null; }`。

看着很对 —— 注释第 ③ 条明明写着"子节点都不中 ⇒ 返回自己 ⇒ 容器吞掉事件"。但那条讲的是
**容器兜底**：`Stack[under, over(禁用)]` 里 `over` 返回 `null`，`RenderStack` 的循环于是**继续问
`under`** ⇒ `under` 命中 ⇒ **事件穿透到了被盖住的那一层**。夹具立刻给出 `pressed = ["under"]`。

正确语义是"**这一层还在，只是不响应**" ⇒ 返回 `$this`，把"不响应"交给激活入口判断
（`focusHit()` 本来就会拦住它 —— 它不在可聚焦表里；只有 `pointer(ownsPress)` 与 `Draggable`
这两条在 `focusHit()` **之前**接管按下的路要显式挡，所以 `InputRouter` 那道判断必须有，
不能指望可聚焦表兜住）。

## 20.3 与既有 `enabled()` 的关系：**没有收敛，这是欠债**

四处 `enabled()` 的语义是"形状色降级 + 不响应激活 + **仍在 Tab 序里**"。本轮**不动它们**，原因：

1. 收敛要先裁决"**禁用该不该进 Tab 序**"。本仓那四处的注释写"仍在 Tab 序里 —— 与 Win32 一致"，
   但 Win32 的 `WS_DISABLED` 控件**不能**获得焦点，HTML 的 `disabled` 也跳过 Tab ⇒ **原注释是错的**，
   而"改注释"和"改行为"是两件事。
2. 真收敛要动四个类的渲染（它们用各自的灰化，与 `DISABLED_ALPHA` 叠加会**双重变淡**）、
   示例台两处调用、以及四条 golden 基线。这是一个独立件的工作量。

⇒ 本轮只做**新契约**：`disabled()` 是唯一推荐入口，新控件不必再各写一份。示例台 `DisabledPage`
把这笔账写在页面上（诚实边界），`08-控件面.md` §5.2 记录收敛方案与代价。

## 20.5 这一件没做的事

- **四处 `enabled()` 的收敛**（见 20.3）—— 排在下一件，前置裁决是 Tab 序。
- **`ColorToken::disabled` 槽**：现在统一乘 alpha，够用但不精细；加槽要动主题契约与全部 golden。
- **`readOnly`**：只读 ≠ 禁用（能选中、能复制、不接受编辑）。`TextField` 需要它是另一件。
- **hover / 光标**：禁用的控件仍然会显示手型光标与 hover 高亮（`move` 分支没拦）——
  属外观细节，等 token 槽一起做更合适。
- **`DatePicker` 的 `min/max` / 禁用某些天**：禁用态刚到位，这件现在**解锁了**，但本身是独立一件。
