### 五条判断

**三条强项（复核仍成立，且是真正的差异化）**

1. **分层与不变量守得住**。`Widget → Element → Render` 三树 + 三 pass 帧管线 +
   「全仓唯一的盒创建点」(`Element::syncBox()`)。依赖方向干净：`src/Widget/` 里
   **0 处** `use Drift\App\`（实测），`Geometry` 是最底层被 import 169 次。
2. **判据文化**。430 + 670 条断言几乎条条能证伪，变异自检是常规动作。
   这套"先问这条断言能不能红"的纪律，比多数商业框架的测试质量高。
3. **工具链**。四档闸门 + AOT 构建 + golden 像素基线 + `inspect`/`probe` 真机链。
   自研框架里罕见。

**三条弱项（本轮新增/修正）**

1. **表现力的"最后一公里"仍未通**：渐变原语在 `Rendering/Gradient.php` 写好三天了，
   `src/Widget/` 与 `BoxStyle` **0 消费者**；没有变换（rotate/scale）、没有隐式动画
   （`Animated*` 0 个）、没有页面转场。**这不是"不会做"，是"做完了没接线"**。
2. **API 门面形状在恶化**：`Widget` 1265 行 / **66 个 public 方法**，`Application`
   1885 行 / **67 个**。新控件作者无法从类形状判断"我该覆写谁"，只能读 18 万字节的注释。
3. **文档自身开始腐坏**：`docs/arch-v2/00-总纲.md` 的"自检命令"四条已失效（它说
   Stack/Align/Wrap/Grid 全零，实际有 4 个；说 lint 15 条，实际 22 条）；
   `apps/showcase` 的"诚实边界"段说"框架没有 SizedBox"——SizedBox 早就有，showcase 自己
   用了 20 次。**闸门只查 `file:line` 引用，不查这类叙述**。

## 1. 架构

### 1.1 骨架（复核仍成立）

| 决策 | 落点 | 为什么它是对的 |
|---|---|---|
| 三层树 | `Widget`(不可变描述) / `Element`(身份+生命周期) / `RenderBox`(布局绘制) | 与 Flutter 同构，且**没有**引入 `InheritedWidget` 那种隐式依赖魔法 |
| 三 pass | flush → layout → paint → present（`App/Frame.php`） | 顺序固定、可跳过，「跳过」本身有判据（`needsBuild` / `needsLayout`） |
| 单一盒创建点 | `Element::syncBox()`（唯一 `State::noteBoxReplaced()` 调用处） | 「换盒 ⇒ 必须重排」这个事实只记一次，帧外路径也覆盖 |
| 值对象化 | `Modifier` / `BoxStyle` / `EdgeInsets` / `Rect` 全 `final` + `clone` 换新 | 无就地修改 ⇒ 无"谁改了我的状态"类 bug |
| 响应式 | `Cell` / `Subject` / `SubjectBuilder`（细粒度，非依赖注入） | 比 WPF 绑定简单一个数量级，够用 |
| 命令 + 快捷键 | `CommandRouter` + `AcceleratorTable`（含冲突检测、启用禁用） | 菜单/按钮/快捷键同一条出口 |

**结论**：骨架不需要重画。真正的问题都在"骨架之上长出来的第二层"（见 1.2）。

### 1.2 五个结构性负债（按"还在变贵"排序）

| # | 症状 | 证据 | 为什么现在处理比以后便宜 |
|---|---|---|---|
| **L1** | `Widget` 是**上帝基类**：布局意图、视觉修饰、裁剪、合成、光标、身份、hover、键盘、语义、调试全挂在它身上 | `1265` 行 / `66` 个 public 方法；子类要 `padding()` 就得**自己覆写**（`6` 个控件覆写 `padding()`、`4` 个覆写 `background()`） | 每加一个控件（这批加了 6 个）都要重新判断"哪些方法落 `Modifier`、哪些落自有字段"。方法数只增不减 |
| **L2** | **修饰双轨制**：`Modifier`（任意控件贴一层）与 `BoxStyle`（控件自带样式）各管一半 | `Modifier.php` 619 行 vs `BoxStyle.php` 74 行；`Modifier` 有 `isDefault()` 守卫、`BoxStyle` 没有；两者字段重叠（背景/边框/圆角） | 越晚收敛，两边的字段越难对齐。今天的 `repaintBoundary` 漏进 `isDefault()` 就是这条的副产物 |
| **L3** | `Application` **门面过大**：窗口、表面、帧循环、浮层、命令、任务、主题、焦点、输入路由全在 | `1885` 行 / `67` 个 public 方法；`OverlayManager`(724) / `InputRouter`(927) 已外提，但门面仍转发 60+ 项 | 它被 5 个 `apps/*` 直接依赖；再长出"多窗口"就会变成 3000 行 |
| **L4** | `TableState` **2528 行**（阶段 8 抽出 `ColumnWidths`/`TableRowPicker` 后仍 2528） | 22 个 public 方法；编辑会话、列宽、选择、键盘、build 编排仍在一处 | 下一步"格级矩形选区"会再堆 300 行 |
| **L5** | `RasterCanvas` **1862 行**是**测试与预览的唯一像素源**，也是性能上限 | 它是纯 PHP 逐像素；今天实测 1920×1017 一帧 1.5s | 加后端（D2D）或做并发都要碰它；且它同时承担"参考实现"与"测试夹具"两个角色 |

**建议的处理顺序**：L2 → L1 → L5 → L3 → L4。
理由：L2 是**语义**问题（两套话术），先定；L1 是 L2 的上游（方法落在哪取决于口径统一）；
L5 是"要不要给测试换引擎"的独立决策，与 UI 架构无关；L3/L4 是纯搬砖，随时可做。

### 1.3 依赖方向

```
Geometry ← Rendering ← Layout ← Widget ← App ← Platform
                                     ↑
                                   State / Text / Input / Theme / Commands / Routing
```
- `Widget` 不 import `App`：**0 处**（实测）✓
- `App` 被 import 2 次（`apps/*` 之外只有 `PageHost` 相关）⇒ 门面没有被框架内部反向依赖 ✓
- 22 条 lint 规则里 `DependencyDirection` 在守这条线。

**唯一的气味**：`Widget/` 里有 6 个 `*Element` / `*State`（`DockElement`、`StackElement`、
`TableElement`、`TableBox`、`TextFieldBox`…）—— Element 层与 Widget 层同目录。逻辑上
Element 是框架内部，与"给应用用的控件"混在一起会让 `113 个文件`的目录失去可读性。

## 2. 实现质量（可维护性）

### 2.1 判据文化是最大资产（复核仍成立）

- 变异自检是常规动作：今天两次改动共 11 组变异，10 红 1 绿（绿的立刻导致删死代码）。
- 判据的**形状**在被持续改进：从"有墨就行"→"数命令"；从"`!== 3`"→"`=== 0` + 走到末尾"。
- `PITFALLS.md` 1813 行记录"踩过的坑 + 判据为什么这么写"，这是新人的最快入口。

### 2.2 ★ 但判据会反噬：今天两个自伤案例（本轮新增）

| 案例 | 形态 | 代价 |
|---|---|---|
| `㊷b` showcase 段 | 用**真光栅**（195 万像素）+ `inkCount()` 断"有墨" | **12.19s 换 10 条断言**，占 smoke 的 32%，而判据本身是弱判据 |

## 3. 性能（实测）

### 3.1 已知上限（`REVIEW-2026-10-27` 实测，复核仍成立）

- **干净帧**（无脏节点）1503 节点 **18.0ms**；**每帧重建** 453 节点 **16.1ms** / 1503 节点 **52.0ms**
  ⇒ 60fps 下**每帧被重建的 widget ≈ 400**。这条上限来自"PHP 建树"本身，不是布局算法。
- 已落地：滚动**零重建零重排**（A 批①②③）、Table 列虚拟化（−34% 节点 / −35% paint）。
- **余项**：`RepaintBoundary` 接线、adoption 队列、动画活跃集（A 批③④）。

### 3.2 量化取舍

滚动帧现在 **≈2–3.7ms**（Table 1000×20 列裁列后 3.66ms）。**60fps 预算 16.7ms**，
即还剩 4–5 倍余量 ⇒ 「框架自身性能」不再是瓶颈；下一阶段的性能问题会来自
**应用写法**（每帧重建、大列表未虚拟化），而不是框架。

### 3.3 测试面成本（今天已有结论）

gate 63.0s = feature 21.6 + smoke 17.0 + unit 5.2 + pages 5.2 + lint 4.6 + 其余。
smoke 从 32.4 降到 17.0 靠的是"假表面只录命令"。**再快只有并行**（→ ~28s），
或把 B 桶 app 级样板拆成独立项。

## 4. 易用性（DX）

### 4.1 好的地方

- **fluent 链式，无注解魔法**：`Text::make('hi')->paddingAll(8)->background($c)` 一眼能懂。
  刻意不用 `#[\Getter]` 这类编译期注解（`php.exe` 不认 ⇒ 闸门跑不起来），这是拿"少一点糖"
  换"工具链可信"。
- **一个 import 前缀**：`Drift\Widget\*`，不需要记 15 个命名空间。
- **示例台是活的规格**：23 页，每页对应一个能力，且**如实暴露缺口**（虽然有几处过期）。

### 4.2 摩擦点

| # | 摩擦 | 证据 | 影响 |
|---|---|---|---|
| U1 | **写一个状态页要两段**（`StatefulWidget` + `State`），且必须记得 `parent::__construct()`（忘就 255） | `ChainPage`/`InnerPage` 两个夹具今天才发现漏调 | 新手第一小时必踩；lint 只覆盖 `apps/**`（`AppSubclassCtorParent`） |
| U2 | **66 个方法没有分层**：IDE 提示是一堵墙，且不知道哪些该覆写 | `Widget.php` | 学习曲线陡 |
| U3 | **错误信息虽好，但发现晚**：控件不可用的地方（如给 `TextField` 套 `padding`）是运行期 Fatal，不是静态检查 | `Modifier::isDefault()` 守卫 | 写法错要到跑起来才知道 |
| U4 | **无 IDE/静态分析生态**：PHP 有 Psalm/PHPStan，本仓用的是自研 lint（22 条） | `tools/lint.php` | 拿不到"跳转定义/参数提示"之外的深度检查，且新人要学自研规则 |

### 4.3 一个具体的易用性判断

**这个框架今天的"最佳用户"是写示例台的人**（有 430+670 条闸门兜着、有 `inspect`/`probe`）。
**而"第一次写自己应用的人"缺三样**：
① 文件对话框（选不了文件等于做不了导入导出）；
② 滚动惯性（手感不对，第一天就会被用户抱怨）；
③ 撤销/重做（文本编辑之外完全没有）。

## 5. 扩展性

### 5.1 加一个控件要改几处？（实测流程）

| 步骤 | 是否必改 | 说明 |
|---|---|---|
| 1. `Widget` 子类 | ✓ | 覆写 `createRenderObject()` 或走 `createRenderObjectFromState()` |
| 2. `RenderBox` 子类 | ✓ | 布局 + 绘制 |
| 3. `padding()/background()` 等修饰 | **看情况** | 若不覆写则落 `Modifier`，若覆写则落自有 `BoxStyle` —— **这就是 L1/L2 的双轨制，新人无法判断** |
| 4. 主题取色 | ✓ | `ColorToken` 只有 10 个槽，`MetricToken` 9 个（缺 success/warning/focus/disabled/scrim） |
| 5. 语义/UIA | 半强制 | `SemanticsRole` 10 个；不声明则无障碍不可见 |
| 6. 测试 | ✓ | 至少 smoke 或 PHPUnit 一条 + 变异 |
| 7. lint 白名单 | **有时** | 部分规则按类名白名单（`Activatable` 那类已改结构性扫描，但仍有几处名单） |

**结论**：加控件的**成本主要在"3 与 4"**，而这两处正是 L1/L2 与主题 token 面窄的直接后果。

### 5.2 加一个渲染后端

现状：`Canvas` 接口 + `RecordingCanvas` / `RasterCanvas` / `SkiaCanvas`（桥）。
新增 D2D 需要实现 `Canvas` 全部 op，并用 `golden` 的 20 页 + 9 个原语场景做等价性验证 ——
**判据已经就位**（`backend-resolve`、`paintBoth` 的雏形）。这一层扩展性**好**。

### 5.3 加一个平台

`Platform/` 已有 `WindowHost` 接口按"多句柄"设计（`createWindow(hwnd)`），但
`Application::attach(RenderSurface)` 收**单数表面** ⇒ **一个 Application 一个窗口**。
这是当前最硬的结构上限：多窗口/多文档应用现在写不出来。

### 5.4 主题扩展性（偏弱）

- `ThemeData` 128 行，`ColorToken` 10 个、`MetricToken` 9 个、`TextRole` 若干。
- **没有控件级 token 槽**：`Button` 的底色、`Card` 的边框是从 `BoxStyle` + 少量 token 推的，
  第三方想"只改按钮圆角"没有落点（只能每次传 `radius()`）。
- 与 Flutter 的 `Theme.of(context).buttonTheme` / SwiftUI 的 `EnvironmentValues` 相比，
  **缺少"控件粒度的主题覆盖"**。

### 6.1 三个"必须承认"的判断

1. **表现力不是画不出来，是画不出来"声明式地"**：阴影/圆角/毛玻璃都能画，
   但只有一半能"在控件上声明"。`Gradient` 是唯一彻底断线的那个。
2. **业务控件面差的不是数量，是"企业应用那三件"**：TabView（多页签）、
   TreeView（层级数据）、DatePicker（时间输入）。表格已经有了，这三件补完，
   "能不能写企业应用"这个问题的答案就变成"能"。
3. **平台集成是"从框架到产品"的门槛**：文件对话框、拖文件、托盘、原生菜单 —— 四项全空。
   任何真实桌面应用第一周就会要它们。

## 7. 优化方案（三档，按"越拖越贵"排序）

> **2026-10-30 补记**：本表是 10-28 的快照，已有**四处**另行评估，读表前先看这里。
> ① **多窗口**：S4 行原判据「多窗口落地时不用再改 1885 行的类」的前提不成立 ——
>    障碍在 C++ 壳的进程级全局与 `Platform` 的窗口身份缺位，
>    见 [`MULTI-WINDOW-2026-10-30.md`](MULTI-WINDOW-2026-10-30.md) §1。
> ② **异步 / 并发**：本表**原本没有这一档**。多线程 / 协程 / 多进程三条路已有实测裁决
>    （前两条否决），真缺口不在「选哪条路」，而在「并发 IO 等待」这一层没有零件、
>    没有示例，见 [`ASYNC-2026-10-30.md`](ASYNC-2026-10-30.md) §2。
> ③ **事件循环 / IO 等待**：本表也**没有这一档**，但它是 ② 的底座。
>    实测结论反直觉：瓶颈不是「怎么等」，而是**等的时候还在画** ——
>    有 IO watcher 时 `wantsFrame()` 恒真 ⇒ 15.6ms 定时器常驻 ⇒ 每帧无条件
>    `paint` + `present`（`Frame::run` 三段里唯一没有跳过判据的一段）⇒ 约 22% 空转。
>    跨平台三种形态（fd 循环 / 消息队列 / run loop）与 IOCP 裁决见
>    [`EVENT-LOOP-2026-10-30.md`](EVENT-LOOP-2026-10-30.md) §2。
> ④ **重设计方案**：②③ 只诊断，不给终局。已按「七个成熟框架对照 + 五个探针实测」
>    出一份**可破坏兼容性**的设计 ——
>    [`EVENT-LOOP-DESIGN-2026-10-30.md`](EVENT-LOOP-DESIGN-2026-10-30.md)。
>    两条结论修正了 ②③ 的口径：**协程与消息泵不互斥**（把泵写成协程即可，
>    实测 1.2s 慢 IO 期间 maxGap 59ms）；**`curl_multi` 可以留在 UI 线程**
>    （每帧推进单轮 12.2µs）。下一步建议 **N1 泵帧分离**（零真机）。

## 10. 落地记录 · S2：`Widget` 拆分（2026-10-28 当天）

### 10.1 结果

| | 前 | 后 |
|---|---|---|
| `Widget.php` | **1265 行** | **420 行** |
| 基类自有 public 方法 | 66 | **10**（+ `mutate()` 一个 protected） |

**API 一个字节没变**：拆分前用反射快照了 68 个方法（public+protected）的
「名字 + 参数类型 + 默认值 + 返回类型」，拆完逐行比对——**完全一致**。

**真机逐像素一致**：`showcase.exe` 在 1920×1017 下的截图 md5 与拆分前**完全相同**
（`b85ad4b4…`，ink 41.7%）⇒ 这次重构对行为是透明的，不是"看起来没坏"。

### 10.2 ★ 顺手推翻了一条旧纪律（有实测）

`lint` 原本有一条 `orphan-trait`：**「trait 必须与一个具体类同文件」**，理由是
GUI 仓的坑「只有 trait 的文件不产出翻译单元，`cl` 收到空文件名」。
`docs/_archive/design-proposals.md` 还记着据此做的决定：**「不用 trait —— 未验证」**。

实测三件事：
1. 4 个只含 trait 的文件一起走 `drift-build showcase` ⇒ **构建通过**（12.2 MB，135s）；
2. `_codegen/build/src/Widget/Widget.cc` 里能找到内联进去的 trait 方法，
   **没有**为空文件产出翻译单元；
3. 真机截图 md5 与拆分前完全一致。

⇒ 那条坑在今天的 tpc 上**不复现**，规则的前提消失了。但它想防的事还在
（没人 `use` 的 trait 是死代码 + 白跑一个空文件），所以**把判据改成表达本意**：

> `orphan-trait`：trait 必须被某个类 `use`（判定用类体内的短名 `use X;`）。

★ 顺带记一次自己的假判据：第一版正则 `(^|[\s;{])use\s+X;` 会把**注释掉的**
`// use X;` 也算成"被使用"——反例自检（注释掉 `use WidgetSemantics;`）时它
**0 error**，等于没牙齿。改成行首锚定 `^[ \t]*use[ \t]+X[ \t]*;` 才红。

### 10.3 落地时踩到的两个坑

1. **自动搬方法要处理单行 docblock**：`/** @internal … */` 与 `/** 一句话 */` 这种
   一行 docblock，用"上一行是 `*/`"去回溯会漏判 ⇒ 方法搬走了、注释留在原地，
   基类出现一排孤儿 docblock（第一次拆完 415 行的版本就是这样）。
   判据：搬完数一遍"孤儿 docblock"（`*/` 之后下一个非空行不是声明）。
2. **多遍拆分不可重入**：按组跑三次（modifiers → focus → semantics），每次重新解析
   行号已经漂移 ⇒ 第二次起 docblock 归属判错。改成**单遍解析、单遍删除**。

## 11. 落地记录 · S1：修饰口径统一（2026-10-28 当天）

### 11.1 先量了一遍"双轨"到底是几条轨

| 落点 | 谁在用 | 存储 | 判定 |
|---|---|---|---|
| `$mods`（`Modifier`） | 所有控件 | `fill` / `stroke` / `radius` / `padding` / … | **通用装饰层**，`RenderBox::paint()` ① 画 |
| `BoxWidget::$box`（`BoxStyle`） | `Button` / `PopupPanel` | 只有 `background` / `border` / `radius` | **完全是 `Modifier` 的子集** ⇒ 纯冗余 |
| `Card::$box` + `$padding` + `$shadow` | `Card` | 同上 + 内距 + 阴影 | 包装器参数，`build()` 翻给子控件 |
| `Span::background()`（ARGB int） | `Span` | 文本 span 的底 | 不是 Widget，不同层 |

★ 关键测量：`src/` 里 **`instanceof BoxWidget` 零消费者**（只有测试里两条"结构节点不该
继承它"的断言）。⇒ `BoxWidget` 剩下的作用只有"提供三个重复方法与一份重复存储"。

### 11.2 做的是"删掉第二份存储"，不是"合并两个值对象"

`BoxStyle` **留在 Layout 层**（它是 `RenderButton` / `RenderAppBar` / `RenderTable` /
`RenderTextField` 的构造参数，24 个文件在用 —— 那是渲染参数，不是 Widget 修饰）。
删掉的是 **Widget 层的第二个写入口**：

| | 前 | 后 |
|---|---|---|
| Widget 层样式存储 | `$mods` + `BoxWidget::$box` | **只有 `$mods`** |
| `BoxWidget` | 抽象基类（3 方法 + 1 字段） | **已删**（`git rm`） |
| `->background()` 落点 | 看类决定（`BoxWidget` 子类写 `$box`、其余写 `$mods`） | **一律 `$mods`** |
| `BoxStyle` 从哪来 | 存着 | 需要时 `Modifier::boxStyle()` **派生** |
| 守卫覆盖 | 只看 `$mods`（另一半静默） | **看全部**（只有一个存储） |

`Card` **不动**：它是 `StatelessWidget`（不产盒），自己的样式写 `$mods` 正好撞
`Element::syncBox()` 的守卫（"声明了修饰但不产盒"）⇒ 它必须自持一份再翻给子控件。
这条边界是**语义必需**，不是债务 —— 已写进 `Card` 的类注释。

### 11.3 ★★ golden 抓到了双画，而它只在描边上可见

改完第一版：`$mods` 里还留着用户设的 fill/stroke，`RenderBox::paint()` ① 画一遍、
`RenderButton::paintOwnChrome()` 再画一遍。我当时判断"同色同矩形 ⇒ 幂等"，并写进了注释。

**`golden/page` 立刻红了 2 页**：

| 页 | 差异 | 位置 |
|---|---|---|
| `ButtonsPage` | 32 像素（max Δ=13） | `y=260..263` / `288..291` —— **上下边框条带** |
| `ListPage` | 322 像素（max Δ=25） | `x=808..867` —— **按钮右边缘** |

**底色幂等（不透明矩形全覆盖），描边不幂等**（`Paint::stroke` 带抗锯齿，同色叠两次
≠ 一次）。恰好是最容易靠"看起来一样"漏掉的那一半。

修法：`RenderBoxWidget::paintsBoxChrome()`（默认 `false`），声明 `true` 的控件在
`Element::syncBox()` 里把交给盒的 `$mods` **剥掉**视觉三字段
（`Modifier::withoutBoxVisual()`）——**保留 `shadow`**（`Button` 的浮起影子走
`ShadowPainter`，用户显式 `->shadow()` 走 `paintBehind`，剥了就静默吞掉）。

剥完之后立刻跑 golden：**20 页全绿**（逐像素回到改动前）。

### 11.4 顺手补上 `isDefault()` 漏的 `repaintBoundary`

这是上一轮挂着的"待裁决"。判据：`isDefault()` 的注释写的是"没有任何修饰"，那它就必须
覆盖**全部**字段；"重绘边界丢了只是慢"是**后果**的辩解，不是"它不算修饰"的理由 ——
而静默失效的检测成本远高于一次多画的代价。`ModifierTest` 里那一行的期望从 `true`
改回 `false`，**表里再没有例外**。

### 11.5 顺带修好的两处静默失效

- **`AppBar` 的 `->background()` / `->border()` / `->radius()` 一直是死字段**：
  `BoxWidget` 把值存进 `$box`，而 `AppBar::createRenderObject()` 直接
  `new BoxStyle(主题…)`，**存了但没人读**。现在合并写在 `createRenderObject()` 里
  （与 `Button` / `PopupPanel` 同口径）。
- **`withoutBoxVisual()` 被前缀判据误判**：`ModifierTest` 的完整性自检用
  `str_starts_with($name, 'with')` 收集方法名，于是 `withoutBoxVisual` 被算成
  "漏了一行"。改成排除 `without` 前缀 —— **前缀判据要连"否定前缀"一起想**。

| 自绘控件把用户样式**合并进** `Render*` | "只剥不合并" ⇒ 用户设置变死字段（比双画更糟）|
| 交给**盒**的 `$mods` 已剥视觉三字段，且 `shadow` 保留 | 双画；以及剥过头 |
| `paintsBoxChrome()` 取值表（表驱动）| 新控件忘了声明 ⇒ 走默认 `false` 但实际自绘 ⇒ 双画 |

判据 2 读的是**挂载后盒上的 `mods()`**（`findBoxOf()`），不是 Widget 上的声明 —— 那才
是 `RenderBox::paint()` 每帧真正读的那一份。

### 11.8 这一档没做的事

- **`padding` 的双语义没有合并**，也不该合并：`Flex` / `LazyList` / `LazyGrid` /

  `WidgetModifiers::padding()` 的注。
- **`@overridePoint` 标记 + lint** 仍未做。今天它要裁决的对象少了一个（`BoxWidget`
  那三个覆写没了），剩下的 `padding` 覆写是**语义必需**而非需要拦的东西 ⇒ 这条
  标记的收益进一步下降，建议降级为"文档表"而不是 lint 规则。
- `Application` / `TableState` / `RasterCanvas`（S3–S5）未动。

## 12. 落地记录 · A1（前半）：渐变接线（2026-10-28 当天）

### 12.1 ★ A1 不能一次做完 —— 三件的成本差一个数量级

评审把 A1 写成"`Gradient` 消费者 · `Transform` 控件 · `Animated*` 隐式动画"，理由是
"原语都在，只差接线"。**逐项核过之后，这句话只对第一件成立**：

| 件 | 原语状态 | 真实成本 |
|---|---|---|
| **渐变消费者** | `Paint::withGradient()` / `RasterCanvas::fillSpanGrad()` / `SkiaCanvas::packGradient()` 全通，golden 已有 linear+radial 两个**画布级**场景 | **真·接线**：只缺 Widget 层的字段与一个坐标空间约定 |
| **`Transform`（rotate/scale）** | `Canvas` **只有 `translate`**，且 `RasterCanvas::translate()` 就是 `$offsetX += $dx` —— 没有矩阵 | **重写光栅器**：`rasterize()` 按扫描线填、`fillEdges()` 多边形容差全按轴对齐写；`pushClip(Rect)` 在旋转下不再是矩形。三后端 + op 表 + golden 全动 |
| **`Animated*` 隐式动画** | `AnimationController` / `Curve` / `AnimatedValue` 齐全 | **要层合成语义** —— `AnimationController` 自己的类注释就写着：*"`Opacity` / `Transform` 这类'整棵子树一起动'的包装暂不做（前提：要先有层合成语义）"* |

⇒ A1 拆成 **A1a（渐变，本轮完成）/ A1b（隐式动画，前置=层合成）/
A1c（Transform，前置=仿射光栅器）**。后两项各是独立立项，不是"接线"。

### 12.2 接线时真正的问题：**渐变没有坐标系**

`Gradient` 的坐标原来是**绝对像素**（`linear(20,20,180,20,...)`）。这对"直接画在一块
已知矩形上"（golden 场景、`CustomPainter`）是对的，但 `Card::make()->gradient(...)` 的
人**不知道自己的盒多大** —— 这个 API 等于没用。

落法：`Gradient` 加一个显式的**坐标空间**标记（`relative`），并提供四个"盒内比例"工厂：

| 工厂 | 语义 | 内部坐标 |
|---|---|---|
| `Gradient::vertical($colors)` | 上 → 下 | `(0,0) → (0,1)` + relative |
| `Gradient::horizontal($colors)` | 左 → 右 | `(0,0) → (1,0)` + relative |
| `Gradient::diagonal($colors)` | 左上 → 右下 | `(0,0) → (1,1)` + relative |
| `Gradient::radialBox($colors)` | 中心 → 内切圆 | 圆心 `.5,.5`、半径 `.5` + relative |

换算只有一个函数 `Gradient::resolvedTo($w, $h)`：比例 ⇒ 乘；绝对 ⇒ **原样返回同一实例**
（不新建对象，也保证 `CustomPainter` 里写死的绝对坐标不会被缩成 1/100）。

★ **为什么必须显式标记、不能靠"看起来像 0..1"**：`linear(0,0,1,0)` 是合法的绝对坐标
渐变。隐式猜会把这类用法画成一条 1 像素的线，而画面只是"看不清渐变"，不像错误。

### 12.3 落点：三层各一处，没有第二份

| 层 | 改动 | 为什么在这里 |
|---|---|---|
| `Gradient` | `relative` 标记 + 4 个比例工厂 + `resolvedTo()` | 坐标换算是**纯函数**，与宿主无关（同 `TextBoundary` 的判据） |
| `Modifier` | `gradient` 字段（**占位对象 + bool**，不是 `?Gradient`）+ `withGradient/withoutGradient/gradient()` | AOT 约束：可空对象退化成 `php::Var`（与 `$background` 同一条账） |
| `BoxStyle` | `backgroundGradient` 字段 + `backgroundPaint($w,$h)` | 三个自绘 chrome 的渲染盒共用一次换算，各自写就会漏一处 |
| `Widget::gradient()`（trait） | 一行转发 | 与 `->background()` 同一层 |
| `Card::gradient()` | 写自己的 `$box`（包装器参数） | 它不产盒，写 `$mods` 撞守卫 |
| `RenderButton` / `RenderAppBar` / `RenderTextField` / `RenderPopupPanel` | 改用 `backgroundPaint()` | 原来各写"有底就 `Paint::fill`"，加 paint source 要各改一遍 |

**并集语义统一为"渐变赢"**：`->background($c)` 与 `->gradient($g)` 并存时画渐变；
`->gradient(null)` 清掉它、实色回来。三处（`Modifier` / `BoxStyle` / `Card`）用**同一条**规则。

### 12.4 过程中撞到的两个坑

1. **`Card::gradient(Gradient)` 是不兼容覆写** —— `Widget::gradient(?Gradient)` 可空，
   子类收窄成非空 ⇒ 装载期 Fatal（`php -l` 查不出，`golden-raster` 一跑就炸）。
   与 `padding(EdgeInsets)` 那条是同一类：**覆写必须保持参数可空性**。
2. **`ModifierTest` 的完整性自检立刻抓到 `withGradient` 漏行**（20 个 `with*()` / 表 19 行）
   —— 这正是它存在的意义，补一行即可。

## 13. A4 第一件：`Stack` 的层叠定位（`->positioned()`）

`A4` 原计划是三件（`Wrap` / `Positioned` / `Align`）。先做 `Positioned`：它是另外两件里
"缺了就写不出东西"的那一件 —— `Stack` 有了却不能定位 ⇒ 叠层布局是半残的。

### 13.1 三个岔口与裁决

| 岔口 | 选项 | 裁决 | 理由 |
|---|---|---|---|
| 意图住哪 | `Positioned` 包装节点 vs `Modifier` 字段 | **字段** | W5 的判据是"修饰是字段不是节点"，`Expanded → grow()` 已经这么退过一次 |
| 盒怎么读 | `RenderStack` 直接读 `$kid->mods()` vs 落盒字段 | **落盒字段**（`setStackIntent()`） | 与 `setFlexIntent()` 同构。第二个读法会让下一个人问"为什么 inset 读 mods、grow 读字段" |
| 定位子撑不撑大 `Stack` | 撑大 vs 不撑大 | **不撑大** | 唯一能解开循环依赖的走法（见下） |

### 13.2 关键裁决：定位子不撑大 `Stack`

"定位子多大"要减"本盒多宽"（`left`+`right` ⇒ 宽 = 盒宽 − 左 − 右），而"本盒多宽"来自
`max(子)` ⇒ **互为前提**。两条出路：

1. 两遍 layout —— 本盒类注明令不是（`StackTest::testEachChildLaidOutOnce` 盯着）；
2. **断开依赖**：定位子不参与 `max` ⇒ 顺序变成
   `量非定位子 → 定本盒尺寸 → 排定位子`。

选 ②。它让这一遍仍是**单遍**（定位子只是被**挪后**量，不是被量两次），且白送了 CSS 的
拉伸语义。上游（Flutter）是同一条裁决。

**代价（写进判据，不掩饰）**：只有定位子的 `Stack` 尺寸是 `0×0` ⇒ 那个子被夹到 0、
画面上什么都没有、也不报错 ⇒ 修法是自己套 `SizedBox`。这条钉成**契约**
（`StackPositionedTest::testStackOfOnlyPositionedChildrenIsZero`）。

★ 这一条是**跑出来才看清的**：最初用 `SolidBox` 当那个子，撞了 C6 Fatal
（"尺寸超出可用空间"）—— 因为 `SolidBox` **故意无视约束**（它是 C6 的正向夹具）。
真控件会被夹到 0 ⇒ 静默消失。两种后果同源，判据取真控件那条。

### 13.3 落点（每层一处，无第二份）

| 层 | 改动 |
|---|---|
| `Modifier` | 4 个 `inset*` 字段（`NAN` = 未声明）+ `hasInset()` + `withInset(边序, 值)` + `isDefault()` 加一项 |
| `RenderBox` | 镜像 4 字段 + `setStackIntent()` + `hasInset()` / `inset*()`；`setMods()` 多派发一行 |
| `RenderStack` | `performLayout()` 分两趟 + `layoutPositioned()`；内禀值跳过定位子 |
| `WidgetModifiers` | `positioned(?left, ?top, ?right, ?bottom)`（`null` = 不动这一边，可多次叠加） |

★ `withInset(边序, 值)` 是**一个方法 + 4 个常量**，不是四个 `withInsetLeft()`：四条边是
同一个概念的四个分量，分成四个方法会让"设了哪几条边"在 `ModifierTest` 的完整性表里
占四行、而它们永远一起变。

### 13.4 收口判据：`ParentIntentTest`（不许再扩族）

加 `inset` 时 `Modifier` 已经是第 27 个字段。再往下，`Dock` 槽名、`Table` 列提示都会
想走同一条通道 —— **每加一族就要在 `Modifier` 加字段、在 `RenderBox` 加镜像与 setter、
在 `isDefault()` 加一行**，漏任何一处都是"这个修饰静默失效"。

所以钉的不是"现在几个字段"，而是**族的数目**：`set*Intent()` 的方法数 ≤ 2
（现状 `setFlexIntent` / `setStackIntent`）。**第三族 ⇒ 红 ⇒ 逼一次设计决定**
（引入 `ParentData` 值对象），而不是第 3 个 `set*Intent()`。

★ 为什么数方法而不是数字段：加族必然加方法（否则没法派发），而数字段要区分
"父意图"与"自己就用"（`width` / `clip`…）⇒ 得维护一份硬编码名单，那份名单本身会腐坏。
★ 配对第二条：每一族**都被 `setMods()` 派发**（声明了却不派发 ⇒ 整族死字段）。

### 13.5 新判据 `tests/Unit/Layout/StackPositionedTest.php`（8 tests / 21 断言）

| 四条边 ⇒ 拉伸成 90×75（+ 对照：不声明 ⇒ 0×0） | "90×75 是盒子本来就这么大" |

| 未声明的轴退回 `StackAlign`（`TopRight` ⇒ x=80，y 仍是 8） | 两个来源必须**各管一轴** |

## 14. A4 第二件：`Wrap`（顺带挖出"响亮失败路径自己是坏的"）

### 14.1 推翻 `04` §4.4：那条否决的**前提不成立**

`04` §4.4 判"不做 `Wrap`"，原话：`Wrap` 需要两遍布局 —— 先量所有子的自然尺寸 → 按可用宽
分行 → **而分几行决定容器高度，容器高度又可能改变子的宽度** ⇒ 需要 `layout` 迭代。

那个环在本实现里**构造性地不存在**：子拿到的约束是 `主轴 0..mainLimit、交叉轴 0..crossLimit`，
两个数**都直接来自父**，与"最后分了几行"无关 ⇒ 子的尺寸不依赖容器高度。

⇒ **每个子只 `layout()` 一次**。这与 §13 那次是同一类误判的形状：
把"我没想到单遍算法"写成了"这个问题需要两遍"（`04` §4.1 的"`Expand` 需要第二遍"同款）。

★ 判据把这条钉死了：`WrapTest::testEveryChildIsLaidOutOnce` —— 它红 = 实现里长出了迭代。

### 14.2 保留的两个边界（**没**假装都解决了）

| 边界 | 裁决 |
|---|---|
| **内禀值** | `Wrap` 的"自然宽"有两个合法答案（Σ子 / max子），本仓每轴只有一个内禀 ⇒ 按**一行**给（max-content）。偏宽但会被父 `constrain()` 夹回、不 C6。真要 min-content 需第二套内禀（= `04` §2 的 S3 仲裁），本轮不做 |
| **`Stretch`** | 同一行取该行最高值 ⇒ **正是** `04` §4.4 担心的那个迭代 ⇒ **响亮失败**（写明理由 + 修法），不静默退化成 `Start` |

⇒ 换句话说：`04` §4.4 真正担心的东西，只剩 `Stretch` 这一种形态，而它被**显式拒绝**了。

### 14.3 顺带挖出：`WidgetModifiers` 的响亮失败路径一直是坏的

给 `Wrap` 写"接收 `Stretch` 就 Fatal"时，第一次跑出来的是
`Error: Class "Drift\Widget\Traits\Errors" not found` —— 不是"退出码 3 + 人话 + 修法"。

顺着查到：**上一轮 S2 把方法搬进 trait 时，没把 `use Drift\Errors;` 一起搬过去**
⇒ `grow(-1)` / `shrink(-1)` / `opacity(1.5)` 三条校验路径**一直是坏的**
（用户看到的是 PHP 的类找不到：没有日志、没有修法、退出码也不是 3）。
同一次扫描又抓到 `ProcessTaskHost` / `ProcessWorker` 两处同类。

★ 这是最坏的一类静默：**失败路径自己失败，而没人会去测失败路径**。

修法与两道闸（新文件 `tests/Unit/Widget/LoudFailurePathTest.php`，3 tests）：
① **表驱动子进程判据** —— Widget 层的每个响亮失败入口都验"退出码 3 + 日志里那段人话"；
② **静态扫描** —— 出现裸 `Errors::`（**代码行**，不是注释）的文件必须 `use Drift\Errors;`。
★ ② 的第一版用 `str_contains($src, 'Errors::')` ⇒ 7 个命中里 4 个只是 docblock 文字
⇒ 改成逐行跳过注释。误报比漏报贵，这条当场就教育了我一次。

### 14.4 落点

`src/Layout/RenderWrap.php`（单遍：分行 + 定位两个标量平行数组 / 内禀按一行）·
`src/Widget/Wrap.php`（`direction` / `spacing` / `runSpacing` / `alignment` / `runAlignment`）·
`src/Widget/WrapElement.php`（与 `FlexElement` 同构）· 3 处补 `use Drift\Errors;`。

## 15. A3 第一件：`TabView`（多页签容器）

### 15.1 关键发现：框架里**已经有一个同构的东西** —— `PageHost`

动手前探出 `src/Routing/PageHostState.php:87`：

```php
$hosted[] = Offstage::make($this->pageFor($name), $name === $current);
```

和我原本打算写的 `TabView` 是**同一套机制**。这必须先判，否则就是造第二个轮子：

| | `PageHost`（路由）| `TabView`（本轮）|
|---|---|---|
| 键 | 页名 `string`（来自 `RouteTable`）| 序号 `int`（来自 `->tab()` 顺序）|
| 谁来选 | 订阅 `Subject`（外部 Store 驱动）| **受控** `selected()` + `onChanged()` |
| 谁来造页 | 工厂 + **在 State 里缓存** | 应用直接给 |
| 有没有可见的选择器 | 没有 | 有（页签条）|

**裁决：不共用代码，共用契约。** 共同部分只是那个三行的 `Offstage` 循环，抽出来只会
更难读（一边是 Stateful + 订阅，一边是 Stateless + 受控）。但契约必须一致，本轮把它
写进两边的类头 + 判据。

### 15.2 顺带澄清一条：`PageHost` 的"页面 Widget 只造一次"是**工厂**带来的，不是通用纪律

`PageHost` 类头写着"★ 每页的 Widget 只造一次……否则'保留状态'直接没了 —— 这是本节
最容易错的一处"。照抄会给 `TabView` 平白加一个 `State` + 缓存表。

那条只对**工厂**成立：`RouteTable::build($name)` 每次调用都可能返回一个带新参数的新实例。
`TabView` 没有工厂 —— 页面是应用当作**描述**给的，新实例只是"重新描述一遍"；
`OffstageElement::rebuild()` 对停着的 Element 做 `update()`，而 **State 挂在 Element 上，
不随 Widget 走**。⇒ `TabView` 可以是 `StatelessWidget`，零新增 Element / RenderBox。

### 15.3 三个岔口的裁决

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 受控 vs 自持 | **受控** | 与 `SegmentedControl` / `ToggleBase` 同纪律（"自持 ⇒ 两份真相"）。自持的写法看着更好用（点一下就切、应用不用接），破起来也最安静 |
| 自己当容器 vs 组合 | **`StatelessWidget`**，不新增 Element / RenderBox | 没有局部 UI 态；它只是"条 + 保活内容区"这个组合 |
| 页签条 | 复用 `SegmentedControl`（v1） | 单选 + 每段一个焦点 + `activate()` 三件事现成且已测；真 TabBar 是**另一个视觉契约**（见 §15.8）|

**有意的边界**：越界 `selected` ⇒ **全不选**（不夹到 0，与 `SegmentedControl` 同裁决）；
内容区**吃掉条以外全部高度**（每页套 `Expanded`，否则切页签时面板会跳）。

### 15.4 判据 `tests/Feature/Widget/TabViewTest.php`（7 tests / 34 断言）

钉的是**保活**，不是"画对"（页签条是复用件，它的判据在 `SegmentedControlTest`）。

## 16. A3 第二件：`TreeView`（层级树）+ 两个框架级缺陷

### 16.1 三个岔口的裁决

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 展开集合：受控 vs 自持 | **受控**（`expanded()` + `onToggle()`） | 与 `TabView::selected` / `Table::selection` 同族。自持的话"展开全部 / 搜索时自动展开命中路径 / 跨会话记住展开态"应用一件也做不到，只能再补一套反向同步 API |
| 自己当容器 vs 组合 | **`StatelessWidget` + `LazyColumn`** | 零新增 Element / RenderBox，与 `LazyGrid` 同一条路。行构建器闭包**不捕获 `$this`**（同 `LazyGrid::build()` 纪律：捕获了就把整棵树留在渲染树上） |
| 数据形状 | 新值对象 `TreeNode`（`id`/`label`/`children`） | 与 `Option` 同族：`id` 是身份。展开集合与选中值都按 `id` 认，不按下标 —— 过滤 / 重排后下标会漂 |

**锚点按身份 key**（`keyOf(行 id)`）：展开一行会让它后面所有行的序号 +N，
按序号恢复会把视口甩到别的节点上（"展开一下，列表跳走了"）。实测 4200 → 4284
且顶部仍是同一个节点。

### 16.4 ★★ AOT 真机取证挖出两个缺陷（PHP 测试全绿时也看不见）

这一件最大的收获不是控件本身，而是**golden + 22 条判据都过的情况下**，
把窗口真的画出来看，立刻露出两个问题：

**① 标签被撑满后居中** —— 行里的标签按钮套 `Expanded`（点行的空白也算点这一行），
`Button` 默认内容居中 ⇒ 整棵树的标题全飘到窗口中间，缩进层级只能靠箭头位置读出来，
"看着像一段居中的文字"。修法不是给 `Button` 加参数而是加**公共能力**
`Button::alignLeft()`：借 `NavButton`（"这类按钮天生左对齐"）会把"树行"和
"导航项"焊在一起，改侧栏对齐会波及树。判据补了一条 `RenderButton::centersContent()`
为 `false`（`centersContent()` 是 `@internal` 夹具访问器，同 `hasIcon()`）。
—— 原有那条"叶子行与有子行标签起点相同"测的是 **Button 盒**的起点：盒看着对、
字却在中间，所以它一直是绿的。

**② `skipFocus()` 让按钮彻底点不动** —— 树行箭头（`IconButton` + `skipFocus()`，
目的是每行只留一个 Tab 站）点了毫无反应，画面、日志、退出码都没有任何线索。
A/B 一次（只删 `->skipFocus()`）就复现/消失，然后顺着 `focusHit()` 找到根因：

```php
// FocusManager::walk()（修前）
if ($node !== null && $node->skip) { return; }      // 整棵子树直接跳过
if (isFocusable()) { $order[] = $el; $byId[id] = $el; }   // 两张表一起填
```

`byId` 是"**可聚焦**元素表"，`focusHit()` 靠它回答"点到的这个东西能不能拿焦点"；
`order` 才是 Tab 序。两者共用一张表 ⇒ **"跳过 Tab 序"顺手把"点得动"也取消了**。
修法：`byId` 无条件登记可聚焦元素，`skip` 只挡 `order`（并沿子树传递）。

这是个**语义陷阱**：`skipFocus()` 的文档从头到尾写的是"不进 Tab 序"，
没有任何地方暗示"也就不响应指针"—— AppBar 工具组是它的典型用法，
只是那组按钮当时另有路径可达，没暴露。

## 17. A3 第三件（前半）：`CalendarView` + 两个值对象

`DatePicker` 拆成两半做：**月历本体**（这一件）+ **触发框与浮层**（下一件）。
理由：月历是"日期的全部规则"（闰年 / 月长 / 一号周几 / 前导格 / 行数），
它自己就能嵌进页面单独验；浮层那层是 `Select` 已经走过的老路（`overlayPanel` +
第二棵根树 + `dismiss`），混在一起做会让"日期算错"和"面板没关"两类问题互相掩盖。

### 17.1 三个岔口

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 日期用什么类型 | **自建 `YearMonth` / `LocalDate`** | ① 日历只要"这月几天 / 一号周几"，`\DateTimeImmutable` 反而要先钉时区（忘了就跨时区漂一天）；② 翻月是点击级操作，值对象比"构造 + 一串方法过 `php::Var`"便宜；③ `Option` / `TreeNode` 同族，纯值对象、`public readonly` 即终态 |
| 月份受控还是自持 | **受控**（`month()` + `onMonthChange()`） | "打开时跳到本月 / 记住上个月看的月份 / 搜索命中后跳到那个月"——自持的话三件都要补反向 API |
| 自己当渲染盒还是组合 | **`StatelessWidget` + `Column`/`Row`/`Button`** | 零新增 Element / RenderBox。日历是"一堆按钮排成网格"，没有需要盒级才知道的东西 |

★ `YearMonth` 与 `LocalDate` **分开**（而不是"day 恒为 1 的月"）：日历标题要"月"、
选中值要"天"，一个类型兼两职时 `day` 就成了"永远是 1 的占位符"，而 `plusMonths()`
之后它还是不是 1 只能靠口头约定。

### 17.2 判据 18 条（`CalendarDateTest` 9 + `CalendarViewTest` 9 / 91 断言）

| 组 | 防的是什么 |
|---|---|
| 月长 12 条 + 闰年 7 条 | 闰年四条规则各一个锚点（普通闰 / 百年非闰 / 400 年闰 / 平年） |
| 周几 6 个锚点 + `firstWeekday` | 用**已知日期**验，不拿 Sakamoto 自己验自己 |
| 翻月 8 条（含**反向跨年**） | 反向借位是唯一会暴露"月基写错"的方向 |
| ISO 往返 / 补零 / 比较 | `2026-10-09` 不补零会排到 `2026-10-10` 后面 |
| 行数 5/6 与 `MIN_ROWS` 兜底 | 28 天且 1 号周一的月份只需 4 行，太扁 |
| 只有本月是格子（31 / 29 / 28） | 别月留白，不是灰色按钮 |
| **首日列位**（前导 3 ⇒ 第一行 4 格、x ≈ 128） | ★ 前导算错一位整月都错位，而肉眼看"还是像日历" |
| 列等宽 40（`Expanded` 等分 + `compact()`） | 按钮最小宽超过格宽 ⇒ 布局超界 |
| 受控 3 条（点 15 号 / 两个月号 / 上报后画面不动） | 与 `TreeView` / `TabView` 同款正向判据 |
| 选中态（只一格 Primary、跨月不亮） | 跨月不亮是受控的**必然结果**，不是 bug —— 写成判据免得下次被"修" |
| 不占 Tab 站（走 `FocusManager::order()`） | ★ 初版用 `focusNode() === null` 判，**恒真**（节点只在声明过 focusOrder 时才建）⇒ 无牙；改成数 `order()` 才有 |

### 17.3 变异 14 组全红，其中两组暴露**真缺陷**

- **7 列等分的浮点溢出**：`344 / 7 × 7 = 344.00000000000006`，而 `RenderFlex` 的
  溢出判定是裸 `>` ⇒ 报"子项共需 344.0，可用只有 344.0（差 0.0）"的 Fatal。
  这不是我的宽度算错，是**任何等分 N 份都会撞上**的框架缺陷：`LayoutTolerance::EPSILON`
  （0.01px）+ `RenderFlex` / `RenderBox` 两处比较都带上它。真溢出（≥ 0.5px）照样报。
- **`Button` 没有紧凑档**：常规横向内边距是 `2×gap`，7 列各 40 宽装不下 ⇒ 同样超界。
  补 `Button::compact()`（内边距 `1×gap`，与 `alignLeft()` 同族："**这一个**按钮的
  布局微调"，不是新控件）。
  反例对照：借 `IconButton` 的 `all(gap*1.5)` 不行 —— 那是"纯图标正方形"的语义。

另一组不是"变红"而是**死规则**：`YearMonth::plusMonths()` 原本有个"负数走手工地板除"
的分支，删掉它仍全绿 —— 因为年份下限是 1 ⇒ `$total` 恒为正 ⇒ 那支是死代码。已删。

## 18. A3 第三件（后半）：日 / 月 / 年三档视图

### 18.1 四个岔口（两个新裁决、两个继承 §17）

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 月/年网格**做成嵌套浮层**（laydate 那样弹一层） | **不做，原地换内容** | 浮层里再开浮层，`OverlayManager` 的属主清扫要变成两层；而收益只是"同一块区域的另一种画法"。原地换内容的还有一个好处：`DatePicker` 把它塞进浮层时，**里面不会再开第二个浮层** |

| 翻页越界（年视图到 1 年还往前） | **`YearMonth::tryPlusMonths()` 返回 `null`，那侧箭头不挂回调** | 用 `plusMonths()` 会 FATAL，用户多点两下就把进程打死；而"上报一个跟当前一样的月份"又会让应用白跑一次 `setState`。**到头了就点了没反应**，才是"到头了"的诚实表达 |

月份"，直接落到 10 月反而要多点一次标题。

# §19 DatePicker / DateTimePicker / TimeView（2026-10-29）

## 19.1 一个入口、两个实现件

用户问的是"这个时间控件能不能选时分秒，是一个控件还是两个"。layui `laydate` 的事实：
**一个组件、五套面板**（`type: year|month|date|time|datetime`），而 `time` 面板里**没有日历**，
`datetime` 就是"左日历 + 右时分秒列"并排。所以它的"一个"是**调用形态**，不是实现形态。

我们的切法：

| 层 | 物件 | 值 |
|---|---|---|
| 面板件 | `CalendarView`（已有，**一字未改**） | `LocalDate` |
| 面板件 | `TimeView`（新） | `LocalTime` |
| 值 | `LocalDateTime`（新，只做组合 + ISO） | — |
| 入口 | `DatePicker` / `DateTimePicker`（新） | `LocalDate` / `LocalDateTime` |

**为什么不合成一个带 `type` 的类**（三条硬理由）：

1. `time-only` 的表单（"每天 02:00 跑批"）会被迫带一张用不上的 7×6 月历；合成后只能靠
   `type` 分支写两套布局，等于内部照样两块，只是少了一个类名。
2. `CalendarView::onSelected(LocalDate)` 的签名会被污染成"一天 + 也许还带个时间"
   （旁挂 `?LocalTime` 字段），而"选值"和"选值 + 可能有个附属值"是两种语义。
3. 组合是本仓既有纪律：`TreeView` 组合 `LazyColumn`、`CalendarView` 组合 `Row`/`Button`，
   都零新增 Element / RenderBox。`Row[CalendarView, TimeView]` 同理。

**为什么也不拆成两个彼此独立的输入控件**：表单里"选日期时间"是一个字段，两个不相干的框
还要应用自己保证它们属于同一条数据。所以 `DateTimePicker` 是**一个入口**。

## 19.2 顺带补的三条框架缝（都是被真机逼出来的）

| 缝 | 起因 | 修法 |
|---|---|---|
| `Widget::overlayPanel($f, ?float $maxWidth)` | 浮层面板宽上限写死 320（"一列选项"的口径），并排两块要 416 ⇒ `RenderFlex 放不下：共需 416，可用 304`，进程直接 exit 3 | 控件自报上限；`OverlayManager` 读它，缺省仍 320 |
| `LazyList::viewportExtent($px)` | 浮层里 `BuildContext` 的主轴**无界** ⇒ `viewportEstimate()` 退到它 ⇒ 60 格全造出来（虚拟化静默失效） | 允许列表自己声明视口；优先级排在"盒实测"之后、`ctx` 之前 |
| `OptionPanel::make(..., bool $scrollable = true)` | 外壳无条件套 `ScrollView`，而 `TimeView` 自带 `LazyColumn` ⇒ 嵌套滚动，布局期直接崩 | 内容自己滚时传 `false`，超限由 `PopupPanel` 裁剪 |

★ 三条都不是"为这个功能开的口子"：①是**内容语义**（面板多宽该由内容说），②是
**虚拟化的前提**（视口是窗口换算的除数），③是**职责不重叠**（`ScrollView` 的类注释早就写着
"别塞进外层滚动视口"）。

## 19.3 一处结构性教训：`PickerPanelSignal` 必须独立成文件

第一版把 `PickerPanelSignal` 和 `SelectPanelSignal` 一样顺手定义在 `DatePicker.php` 里
（"省一个文件"）。测试夹具里先 `new PickerPanelSignal()` 就 `Class not found` ——
autoload 是"类名 → 同名文件"，同文件第二个类只有在第一个先被加载时才存在。
`SelectPanelSignal` 至今靠"`Select` 总会被先用"这条**偶然**成立。

## 19.4 真机才看得见的两处视觉缺陷（PHP 测试全绿时）

放大 `_build/crop-time.png` 才看出来的，都**不影响点击、不报错**：

| 缺陷 | 根因 | 修法 |
|---|---|---|
| 相邻两列的 Primary 色块**贴成一片** | 列间没有间隔 | `COLUMN_GAP = 4`（列起点 0 / 72 / 144）|
| 滚动条**切在色块右边缘**上 | 条是画在视口里的（`thumbRect()` 按**渲染盒**宽定位，`MARGIN` 是它离盒边的距离）| 见下 |

第二处第一版是**错的**：给 `LazyColumn` 加 `->padding(right: 5)`。padding 只把内容挤窄、
挪不动条 —— 而且让 56 宽的按钮塞进 51 宽的视口，净效果是色块被裁一条边，条还在原地。

正确做法是把条的宽度算进**盒宽**：

```php
private const BAR_GUTTER  = ScrollBarGeometry::THICKNESS + 2.0 * ScrollBarGeometry::MARGIN; // 12
private const COLUMN_EXTENT = self::COLUMN_WIDTH + self::BAR_GUTTER;                        // 68
```

连带的两个后果（都写进了文档与常量注释）：

- 并排宽度不能再用 `COLUMN_WIDTH × 列数` 估 ⇒ 加 `TimeView::widthOf(bool $withSeconds)`；
- `DateTimePicker::PANEL_MIN_WIDTH`（常量）变成 `panelMinWidth(bool $withSeconds)`（方法）——
  时刻列随 `withSeconds()` 从两列变三列，写死一个数时两列模式白空一截、三列模式够不着。

★ 这条补了一个**几何判据**（`testScrollbarSitsRightOfCells`）：拿每列的 `thumbRect()` 与色块
右边界比，条必须落在外面。理由同"初始偏移"那条 —— 它不报错、只难看，不定住就会回归。

# §20 `disabled()` 禁用态（2026-10-29）

## 20.1 为什么是这一件，而不是 A1 后半（Transform / 隐式动画）

按 §7 的排序，S1/S2 已落地（§10/§11）、A1 只做了"渐变"一半（§12）、A3 三件已收口（§15/§16/§19）
⇒ 纸面上下一件是 **A1 后半**。我没有照做，理由是三处**代码事实**而不是喜好：

| 事实 | 证据 |
|---|---|
| 框架**没有** `disabled` | `grep -rn "function disabled\|isDisabled\|enabledValue" src/Widget/` ⇒ **0 处**；而 §17.5 与 §19.6 两次写着"要先有禁用态" |
| 但**四处局部实现**已经有了 | `ToggleBase::enabled()` / `Slider::enabled()` / `Segment::enabled()` / `SegmentedControl::enabled()`，各自"形状色降级 + 不响应激活 + 仍留 Tab 序" |
| 消费端**全部就绪、只缺最后一根线** | `RenderBox::hitTest()` 的注释里写着"禁用 ≠ 穿透的基础"；`SemanticsNode::$enabled` 字段在、注释写着"声明面"；C++ 桥 `drift_win32.cc:2894` 已经解析 PHP 传来的 `enabled`；`FocusManager` 的 `byId`/`order` 刚刚（TreeView 那轮）拆成两张表 |

也就是说：这不是"加一个能力"，是**一处概念漂移（四份实现）+ 一根断掉的线（消费端都在等）**。
A1 后半的两个东西要新建 `RenderTransform`（含命中逆变换，是新不变量）与"隐式动画"的帧驱动模式，
是**从零开始**；disabled 是**接线**。同样的工时，接线先做的边际收益高得多。

## 20.2 四处消费（以及一处画错的判断）

| 消费方 | 改在哪 | 结果 |
|---|---|---|
| 绘制 | `RenderBox::setMods()` | `composeOpacity = opacity × 0.38`，`paintComposed()` 在 `< 1` 时开层 ⇒ 整棵子树变淡，**零新增绘制代码** |
| 命中 | `RenderBox::hitTest()` + `RenderTable::hitTest()` | 返回**自己**；`InputRouter` 的 down 分支见 `isDisabled()` 直接 `return null` |
| 焦点 | `FocusManager::walk($el, $skip, $disabled)` | 子树既不进 `byId` 也不进 `order`；失焦是 `collect()` 末尾既有那条逻辑**免费**给的 |
| 语义 | `SemanticsBuilder::descend(..., bool $disabled)` | `enabled = semanticsEnabled() && !$off`（子树级） |

**★★ 画错的那一处**：第一版 `hitTest()` 里 `if ($this->disabled) { return null; }`。

看着很对 —— 注释第 ③ 条明明写着"子节点都不中 ⇒ 返回自己 ⇒ 容器吞掉事件"。但那条讲的是
**容器兜底**：`Stack[under, over(禁用)]` 里 `over` 返回 `null`，`RenderStack` 的循环于是**继续问
`under`** ⇒ `under` 命中 ⇒ **事件穿透到了被盖住的那一层**。夹具立刻给出 `pressed = ["under"]`。

正确语义是"**这一层还在，只是不响应**" ⇒ 返回 `$this`，把"不响应"交给激活入口判断
（`focusHit()` 本来就会拦住它 —— 它不在可聚焦表里；只有 `pointer(ownsPress)` 与 `Draggable`
这两条在 `focusHit()` **之前**接管按下的路要显式挡，所以 `InputRouter` 那道判断必须有，
不能指望可聚焦表兜住）。

## 20.3 与既有 `enabled()` 的关系：**当时没有收敛，是欠债（2026-10-29 已还，见 §21）**

四处 `enabled()` 的语义是"形状色降级 + 不响应激活 + **仍在 Tab 序里**"。本轮**不动它们**，原因：

1. 收敛要先裁决"**禁用该不该进 Tab 序**"。本仓那四处的注释写"仍在 Tab 序里 —— 与 Win32 一致"，
   但 Win32 的 `WS_DISABLED` 控件**不能**获得焦点，HTML 的 `disabled` 也跳过 Tab ⇒ **原注释是错的**，
   而"改注释"和"改行为"是两件事。
2. 真收敛要动四个类的渲染（它们用各自的灰化，与 `DISABLED_ALPHA` 叠加会**双重变淡**）、
   示例台两处调用、以及四条 golden 基线。这是一个独立件的工作量。

⇒ 本轮只做**新契约**：`disabled()` 是唯一推荐入口，新控件不必再各写一份。示例台 `DisabledPage`
把这笔账写在页面上（诚实边界），`08-控件面.md` §5.2 记录收敛方案与代价。

# §21 四处 `enabled()` 的收敛（2026-10-29，还 §20.3 的债）

一句结论：`enabled(bool)` 现在只是 `disabled(!$enabled)` 的**别名**，`$enabled` 字段从四个类里
全部删掉；这不只是删代码，它把"禁用"的**唯一真相**钉回了 `Modifier`。

## 21.1 先裁决的那件事：禁用**不进** Tab 序

四处旧注释都写"仍在 Tab 序里 —— 与 Win32 一致"。**这句是错的**，而且错在事实层：

| 平台 | 禁用控件的焦点行为 |
|---|---|
| Win32 | `WS_DISABLED` ⇒ `SetFocus()` 直接失败，`GetNextDlgTabItem` 跳过它 |
| HTML | `<button disabled>` / `<input disabled>` ⇒ 不在 Tab 序、鼠标事件不派发、不触发 `:hover` |
| 旧本仓（四处 `enabled()`） | **仍在 `order` 里**，只在 `activate()` 里 `return` ⇒ Tab 要空走一格 |

裁决：与平台一致 ⇒ 不进 `order`、不进 `byId`、不吃指针。这直接改掉了三条既有测试的**隐含期望**
（它们靠"多走一格 Tab"来证明"禁用不响应"）：

| 测试 | 旧 | 新 |
|---|---|---|
| `ToggleTest::testTabSpaceActivationChain` | 5 步 Tab+Space ⇒ 3 事件（第 5 步空走禁用项） | 4 步 ⇒ 3 事件；**另加**一条"5 次 Tab 的落点 = 同意→小→中→通知→通知" |
| `SegmentedControlTest::testKeyboardTabSpaceActivationChain` | 8 步 ⇒ 4 事件（后 2 步空走禁用组） | 6 步 ⇒ 4 事件；**另加**一条 8 次 Tab 的落点序列 |
| `SliderTest::testPointerDragAndKeyboardChain` | "禁用仍吞掉按下"⇒ `captureNode() === $elC` | `captureNode() === null`（吞掉发生在 `InputRouter`，widget 层收不到）；"禁用不吃方向键"⇒ 改测"点它**不夺焦**，方向键落在原聚焦的 B 栏" |

★★ **不写"改测试就是改契约"**：这三条断言的**意图**（禁用不响应）没变，变的是"不响应发生在哪一层"
（widget 回调层 → 焦点层 / 路由层）与"要不要占一个 Tab 位"。新断言比旧的更强：旧断言只能证明
"按了没反应"，新断言还锁住了"根本不给你按"。

★ 顺带发现的一个既有事实（不是本轮引入）：**Tab 到末尾不循环**，停在最后一个可聚焦元素上
（`FocusManager` 的顺序推进是 clamp 而不是 wrap）。三条新断言都建立在这个事实上，写进了测试描述。

## 21.2 结构：状态归一 + 灰化归属

删掉的字段：`ToggleBase::$enabled`、`Slider::$enabled`、`Segment::$enabled`、
`SegmentedControl::$enabled`；连同 `RenderToggle` 的 `bool $enabled` 构造参数（它只用来选
`ToggleStyle::$disabled`）。取而代之：

| 旧 | 新 |
|---|---|
| `$this->enabled`（每个类一份） | `!$this->mods()->disabled()`（唯一来源） |
| `enabled(bool)` 各自 mutate + 赋值 + 刷语义 | `return $this->disabled(!$enabled);` |
| `isEnabled()` 读字段 | `return !$this->mods()->disabled();` |
| `RenderToggle` 收 `$enabled` 选色 | `!$this->isDisabled()`（`RenderBox` 在 `setMods()` 里落的） |

★ **为什么读 `mods()->disabled()` 而不是直接读盒的 `$this->disabled`**：两处场景不同 ——
widget 层（`activate()` / 语义 / `createRenderObject()`）跑在盒还没建/还没 `setMods()` 的时机，
只有 `Modifier` 是稳的；`RenderToggle::paintContent()` 跑在帧里，`setMods()` 早已发生，
读盒的字段省掉一次 `?Obj` 解引用。

★★ **本轮唯一的新机制：`paintsDisabledLook()`** —— 解决"两个灰化来源叠加"。

框架默认的禁用外观是"整棵子树乘 0.38"（通用、零新增绘制代码，适合任意控件）。但这四个控件
有更好的表达：标签/轨道/填充换 `ColorToken::Muted`（**灰**），而 0.38 是（**淡**）。两者叠加
⇒ 已经变灰的字再乘 0.38，深灰字在浅底上几乎看不见 —— 是**二次衰减**，不是"更明显的禁用"。

裁决方式与既有的 `paintsBoxChrome()` **逐字同构**（声明在控件 → 落实在 `Element::syncBox()` →
消费在盒），这是本仓已经验证过的形状，不发明第三套：

```php
// 1) 控件声明（ToggleBase / Slider / Segment / SegmentedControl）
public function paintsDisabledLook(): bool { return true; }

// 2) Element::syncBox() 落实 —— 与 withoutBoxVisual() 并排
if ($this->widget->paintsDisabledLook()) { $mods = $mods->withoutDim(); }

// 3) RenderBox::setMods() 消费
$dim = $this->disabled && $mods->dimsWhenDisabled();
$this->composeOpacity = $dim ? $mods->composeOpacity() * self::DISABLED_ALPHA : $mods->composeOpacity();
```

★ `Modifier` 里存的是 `bool $dim = true`（**默认开**），`isDefault()` 追加 `&& $this->dim` ——
默认路径 `Modifier` 不分配，与既有"默认值不进堆"的纪律一致。

★ **`SegmentedControl` 自己不画任何禁用外观，却也要声明**：禁用要下发给每个 `Segment`
（各段换 `Muted`），若容器再乘一层 0.38，段里的灰字照样被二次衰减。声明为真在这里的含义是
"这一层的禁用由**子树**表达，别在容器上叠 alpha"—— 所以这个开关的语义是"**谁负责变淡**"，
不是"我画了灰色的东西"。

## 21.3 三处连带修正

1. **`ToggleBase::refreshSemantics()` 里四处 `$this->enabled`** —— 语义的 `enabled` 字段是
   "控件自报"，最终值由 `SemanticsBuilder` 的**子树级** `$off` 裁定。收敛后自报也读
   `mods()->disabled()`，两条路同源；`enabled()` 别名里补一次 `refreshSemantics()`
   （`->disabled()` 直调路径不刷自报值，但 builder 会覆盖 ⇒ 语义树正确）。
2. **`Slider::wireInput()` 的两处早退** —— `if (!$this->enabled) return null;` 保留，
   改成 `if ($this->mods()->disabled())`。它在收敛后已是**冗余保险**（`InputRouter` 根本
   不会把事件送进来），但留着成本为零，且挡住"将来有人绕过 `InputRouter` 直接调 `pointer()`"。
   `nudge()` 里那句同理。
3. **`Segment` / `SegmentedControl` 注释里的"与 Win32 一致"** 全部改写 —— 错误的注释比没有注释
   更贵，它会让下一个人照着错的做。

# §22 A2 重新定义：滚动**平滑**（不是惯性）（2026-10-29）

一句结论：滚轮一格不再"闪现 48px"，而是**滑过去**（半衰期 55ms）。做法是给
`Scrollable` 加**第三条**入口 `glideByAxis()`，而不是把既有的 `scrollByAxis()`
改成动画 —— 后者会让 **81 处**调用（21 个测试文件）语义翻车。

## 22.1 先纠一个事实错误：A2 的前提是假的

§7 的 A2 原文写"`ScrollEvent` 已带 velocity 的位置"。**这是错的**：

```php
final class ScrollEvent {           // src/Input/ScrollEvent.php
    // x, y, delta, axis —— 没有 velocity，没有 timestamp 速度
}
```

而且本仓**没有拖拽滚动**（`ScrollInputRouter` 只有滚轮与 thumb 拖动两条路）。
所以：

| 方案 | 消费者 | 裁决 |
|---|---|---|
| 惯性（fling）：松手后按 v 衰减继续滑 | **无** —— 滚轮是离散事件（一格就是一格，没有"松手"），触控板惯性由 Win32 折进连续的 `WM_MOUSEHWHEEL` | **不做** |
| 平滑：一格 48px 摊成若干帧 | 每个用滚轮的人，每滚一格 | **做** |

**没有消费者的物理不是特性。** `arch-v2/04` §6.4 当年"惯性不做"的结论仍然成立，
这次改的只是它下面那句"`scrollBy()` 是纯位移"。

## 22.2 结构：新开一条入口，不改老的那条

`Scrollable` 的三条入口分工是**语义**，不是"快慢"：

| 入口 | 语义 | 调用点 |
|---|---|---|
| `scrollBy(Δ)` | **立即**改偏移（原语，夹取在这里） | `ensureVisible()`、State 内部 |
| `scrollByAxis(轴, Δ)` | **立即** + 轴判定 | `ScrollInputRouter::dragThumb()`（thumb 必须 1:1 跟手） |
| `glideByAxis(轴, Δ)` | **摊成若干帧** | `ScrollInputRouter::scrollAt()`（滚轮） |

★★ **核心裁决**：**动画 = 把一次大增量拆成多次小增量**，每帧仍交给现成的
`scrollBy()`。于是夹取（`maxScroll`）、换窗（`markDirty`）、锚点
（`rememberAnchor`）、提交编辑（`commitIfUserScrolled`）**一条都没被重写** ——
这是本件唯一的新语义，也是它只有 ~120 行新代码的原因。

★ 节律独立成 `ScrollMotion`（`src/Widget/ScrollMotion.php`）：`ScrollViewState` /
`LazyListState` / `TableState` 是**三份实现**（全量 / 虚拟化 / 表格），但曲线一样。
写在 State 里就要抄三遍，一旦漂移，现象是"长列表滑得比短列表快一点"——没人会去查。
理由与 `ScrollBarFade` 同源，**不住盒上**也一样：盒每帧重造（`scrollOffset` 是
readonly 构造参数）⇒ 住盒上的进度每帧清零、动画永远走不完。

## 22.3 三处静默坑（都靠变异自检才钉住）

| # | 坑 | 现象 | 判据 |
|---|---|---|---|
| 1 | **收口帧不交付** | `AnimatedValue::tick()` 收敛那帧把值精确落到 target，但返回 `false`；跟着不交付 ⇒ 停在 `-47.9896` 而不是 `-48.0` | `childOffset === -48.0`（`===`，不是 `≈`） |
| 2 | **动画中再滚一格做了 `snapTo(当前偏移)`** | 丢掉第一格没走完的距离 ⇒ "快滚时越滚越慢"，**单格测试全绿** | 半路再滚一格 ⇒ 收口 `-96.0`（错误实现给 `-69.79`） |
| 3 | **到边界不收口** | 指数衰减保证终会停，但要多转一百多帧（实测 **81 vs 190**）⇒ 每帧白跑 `tickFrame` + 全量 paint，滚动条多亮一百多帧 | 120 帧内 `wantsFrame() === false` |

★ 坑 3 的判据**改过一次**：第一版写"240 帧后 `wantsFrame()` false"，结果**变异不红** ——
因为指数衰减本来就会在 190 帧内落闸，"永不停摆"这个描述本身就是错的。
教训：**先量清楚真实差异，再决定断言写"会不会"还是"多久"**。

★ 坑 3 的注释在三个 State 里都写错过（"帧时钟永不停止"），已按实测改成
"多转一百多帧（81 vs 190）"。

## 22.4 连带修正

滚轮从"立即"变成"带动画"，凡是"dispatch 一帧就断言 48px"的用例都必须跑够帧。
**9 处**，分两类改法：

| 类 | 位置 | 改法 |
|---|---|---|
| 要"收口后的最终值" | `ScrollWheelTest`（4 处）、`LazyListTest`（3 处）、`SelectTest`（1 处）、`PopupPanelTest`（2 处） | 新增 `pumpScroll()` 助手（`tests/Support/functions.php`）跑到收口 |
| 要"**某一帧**的语义" | `SemanticsPushTest::testLazyScrollIsStructural` | 逐帧推进，**锚在"结构变的那一帧"**（`$deltaAtChange === 1`）。一口气 pump 60 帧不行 —— 动画期间 `animating=true` ⇒ 语义走 `coalesce` 节流会多推，`pushes === 1` 变成假红 |

★ smoke 的声明式 DSL 也受影响（`TestApp::scroll()` 之后 `pump(1)` 不够）。新增
`TestApp::settle()`：一直跑到 `wantsFrame()` 说停。**不写死帧数** —— 那个数字是从
半衰期推出来的，曲线一调就烂。
★★ `settle()` 第一版写错：`wantsFrame()` 反映的是**上一帧**的结果（`animating` 在
`frame()` 里才赋值），`scroll()` 刚 dispatch 完还没跑帧时它一律 `false` ⇒ 先问就立刻
收工、偏移停在 0。**必须先跑一帧再问。**

★ 顺手修掉一个消息精度缺陷：`ScrollWheelTest` 里 8 处 `sprintf('%.1f')` 改成 `%.6g`。
变异 3 时真踩到 —— 实际值 `47.9896` 被打成 `48.0`，失败消息与结论自相矛盾
（"显示 48.0 却判红"）。

# §23 A1b 隐式动画：`Opacity` / `AnimatedOpacity`（2026-10-29）

一句结论：应用侧只写**目标值**，控件自己追过去 —— 每帧只写盒的合成槽，
**不重建、不重排**。真正的发现不是"新控件"，而是**两处框架洞**（§23.3）。

## 23.1 先纠一个事实错误：A1b 不是"造层合成"，是"接线"

§7 的 A1b 原文写"`Opacity` / `Transform` 的前置是层合成语义"。**这句话是过时的**：

| 原语 | 位置 | 状态 |
|---|---|---|
| `Canvas::pushLayer()/popLayer()` | `src/Rendering/Canvas.php:137,139` | 已有、已有消费者（`RenderBox::paintComposed()`） |
| `RasterCanvas::pushLayer()` | 同上实现 | alpha 乘数栈（不是真离屏；层内重叠子各乘一次，Skia 是真离屏） |
| `DisplayList::OP_LAYER_PUSH` + 录制侧配对校验 | `src/Rendering/DisplayList.php` | 已有 |
| `RenderBox::setCompose()` / `paintComposed()` | `src/Layout/RenderBox.php:830,858` | 已有；`opacity>=1 && dx==dy==0` 走零开销快路 |
| `LayerCache` / `setRepaintBoundary()` | `src/Rendering/LayerCache.php` | 已有 |
| "纯动画帧不重排" | `tests/Unit/Frame/ComposeSkipLayoutTest.php` | 已有测试 |

⇒ 这一件**没有一行新的层合成代码**。`AnimationController` 类注释里那句"前提：要先有
层合成语义"已按此更正（`Transform` 仍缺，前置是仿射光栅器 —— 那条是对的）。

## 23.2 结构：两个控件，一条纪律

| 控件 | 语义 | 盒 |
|---|---|---|
| `Opacity::make($a, $kid)` | **静态**不透明度包装 | 自己的 `RenderProxy` |
| `AnimatedOpacity::make($target, $kid)` | 只写目标值，自己追过去 | 内部 `Opacity` 的盒 |

★★ **为什么 `Opacity` 必须是控件，不能只靠 `->opacity()` 修饰符**：修饰写的是
**盒上的合成槽**，一个盒只有一个槽 ⇒ `->opacity(0.5)->opacity(0.5)` 是**后写覆盖先写**
（效果 0.5，不是 0.25）。`Opacity` 每次包装产自己的盒 ⇒ 嵌套时相乘。判据落在
**命令流**上：两层各一条 `OP_LAYER_PUSH`（肉眼看"都是半透明"，只有数命令能分）。

★★ **`tickFrame()` 只写合成槽**：不 `setState`、不 `markNeedsLayout`。判据是
**计数器**（`LayoutCountBox`）：整段动画 `layoutCalls` 一次不涨、`paintCalls` 每帧都涨。
画面上"每帧全量重建"与"只改合成槽"**逐像素一样** —— 这条只能靠计数，不能靠看图。

★★ **`build()` 交"当前动画值"而不是目标值**：`Element::update()` 的顺序是
`syncBox()`（`setMods()` 重置合成槽）**先于** `rebuild()` ⇒ 声明目标值的话，
"动画跑到一半时父控件重建"会让画面**瞬间跳到终点**再被拉回中间值。一次肉眼可见的
闪烁，**没有任何报错**。

★ **曲线与收口帧交付下沉到 `AnimatedScalar`**：`ScrollMotion` / `ScrollBarFade` /
`AnimatedOpacity` 三处都要"指数趋近 + 值变了才交付"。各写一份迟早漂成"这个控件比
那个慢一点"（不报错，也没人会查）。与 `AnimationController` 的分工是**语义**：
本类追目标（无总时长、可随时改向），那个放定时动画（0..1 + `Curve` + 可反向）。

## 23.3 ★★ 两处框架洞（都是真机才暴露的）

### 洞 ①：`wantsFrame()` 漏了"settle 期间起飞的动画"

```text
Application::frame()
  ⓸ tickAnimations()   ← 目标还是旧的 ⇒ 看不到"刚起飞" ⇒ animating = false
  Frame::run() → settle → didUpdateWidget() → toward(新目标)   ← 动画在这里才开始
  ⇒ wantsFrame() === false ⇒ 帧时钟落闸 ⇒ 动画停在起点（不报错）
```

真机现象：点「淡入」**画面一动不动**，再点一次才动（第二次点击时 ⓸ 才看到
"上一帧已经起飞了"）。所以症状是"**要点两次**"，不是"完全没反应" —— 这也是它
一直没被当成 bug 的原因。

**修法**：`State::requestFrame()` → 静态计数器 `frameWantedCount()` →
`Application::frame()` 在 `Frame::run()` **之后**比对计数器前后差，差就 `animating = true`。
只上膛不推进（同帧再 tick 一次就是"一帧走两步"）。

★ **第一版写的是 `list<State>` 登记表**（与 `$mountedThisFrame` 同构），真机**不生效**；
改成计数器后仍待真机复核。登记表要在 `Application` 侧再问 `element()` / `isMounted()`，
那两跳任何一跳失手都静默退化成"什么都没发生" —— 计数器只有一次 `!==`，没有可以
失手的中间环节（与 `needsSettle()` 读 `markedCount` 同一个理由）。

### 洞 ②：夹具拿到的盒是**上一代**

`Element::update()` 走 `syncBox()` ⇒ **新盒**、`boxEpoch` 变。第一版测试把
`effectiveBox()` 存在变量里跨 `update()` 用 ⇒ `setCompose()` 写在新盒上、断言读旧盒，
表现为"compose 一直等于初值"（看起来像产品代码没生效，实际是夹具拿了尸体）。
**每次断言前重新取盒。**

## 23.8 ★★★ 真因：合成槽 + **重绘边界缓存**（2026-10-29，用户两张截图钉住的）

§23.7.1 的解释（"太快所以看不出"）**只对了一半**。用户随后发来两张截图：

| 截图 | 页面上的字 | 卡片 |
|---|---|---|
| 点一次后 | `点击 1 次 · 目标 0.25` | **完全不透明** |
| 点两次后 | `点击 2 次 · 目标 0.25` | 已经很淡 |

★ 那行计数就是为这一刻加的（§23.7.2）：**事件到了**（数字变了），但**画面没动**。
所以不是"没点中"，也不是"太快"—— 是**值在滑、屏是死的**。

### 23.8.1 根因链（三层，缺一层都不成立）

```text
① pushLayer(alpha) 是录进 DisplayList 的一条命令 —— alpha 是录制那一刻的值
② LayerCache::beginRecord() 的命中判据只有 layoutEpoch + 宽高
   ⇒ 只改合成槽时两者都不变 ⇒ 命中缓存 ⇒ 重放旧 alpha
③ 于是 paintComposed() 根本没被调用（整棵子树一次 paint() 都不跑）
   ⇒ setCompose() 写进去的新值没有消费者
   ⇒ 直到下一次 rebuild 顶掉 layoutEpoch，缓存失效，才"突然"画成新值
```

为什么只在真机上：`AnimatedOpacityTest` 的夹具里**没有外层重绘边界**，每帧都
真画 ⇒ 全绿。而真机上它在 `ScrollView` 的内容区里，那是重绘边界。

### 23.8.2 修法

`RenderBox::applyCompose()` 收成 `setMods()` / `setCompose()` 的**唯一落点**，
值真变时 `invalidateEnclosingLayer()`：从 `parent()` 往上找**最近的外层**边界，
`LayerCache::invalidate()`。

- **必须是外层**：本盒若是边界，`paintComposed()` 在 `paintOrReplay()` **之外**
  现算 `pushLayer` ⇒ 自己的缓存不含 alpha、没脏。
- **值没变必须早退**：动画收口后每帧仍写同值，无条件失效会让静止画面一直重录。
- **代价**：淡入淡出期间外层边界每帧重录（≈ 一帧正常 paint）。这是"把 alpha 烤进
  命令流"的必然代价，不是实现缺陷。滚动路径不受影响（滚动改的是 offset，不是合成槽）。

### 23.8.3 判据

`AnimatedOpacityTest::testComposeChangeInvalidatesEnclosingRepaintBoundary`：

| 判据 | 挡的退化 |
|---|---|
| 动画期间（在外层边界下）叶子 `paintCalls` **每帧涨** | 缓存命中 ⇒ 重放旧 alpha（本件的病灶） |
| **反例**：每帧写**同值** ⇒ `paintCalls` 不涨 | 为让上一条绿而写成无条件失效（静止画面白烧） |

变异自检：摘掉 `invalidateEnclosingLayer()` ⇒ 红，报 `base=2 now=2（不涨 ⇒ 重放了旧 alpha）`；
摘掉"同值早退" ⇒ 反例红，报 `base=1 now=6（涨了 ⇒ 每帧无条件失效）`。

★ 这条也纠正了一条**看起来对、其实错**的设计注释：`setCompose()` 原来写着
"不置任何脏位"。对**布局**是必须的（置了就每帧全树重排），对**重绘缓存**是错的。

## 23.9 ★★★ §23.8 的修复在 AOT 上是**空操作**（可见性与 `?->`）

都属"解释器合法、编译后不报错、只是不生效"：

| # | 写法 | 解释器 | AOT |
|---|---|---|---|
| ① | `$p->repaintBoundary` / `$p->layer`（`$p` 是 `RenderFlex` 等子类实例） | 合法 | 父类 `private` **不进子类属性表** ⇒ 查表失败、读成 `null` |
| ② | `$this->layer?->invalidate()`（修法第一版） | 合法 | `?->` 降级成"按运行时类名查表"⇒ **`$this` 也走跨实例路径** |

后果不是崩溃而是**静默失效**：`invalidateEnclosingLayer()` 永远找不到边界 ⇒ 外层
缓存不失效 ⇒ 重放旧 alpha ⇒ 画面不动，直到下一次 rebuild 顶掉 `layoutEpoch` 才"突然"
到位 —— 与 §23.8 要修的症状一模一样。

### 23.9.1 修法

- 两字段 `private` → **`protected`**（不是 `public`：`protected` 才是"子类共用一片属性表"
  的正确表达，也保住了封装边界）。
- 新增 `isRepaintBoundary()` / `invalidateLayerCache()`，循环里**只走公开成员**。
- `invalidateLayerCache()` 内不用 `?->`，拆 `$layer = $this->layer; if ($layer !== null)`。

### 23.9.2 判据：只有 AOT 真机能证伪

A/B 各构建一次（其余代码相同，只差这一个文件）：

| 版本 | 点「淡出」一次 | 卡片区最暗 5% 亮度 | stdout |
|---|---|---|---|
| 旧 `9134dc3` | **画面不变**（ink 13.6 → 13.6） | 66.5（全不透明） | **46200 字节**警告 |

对照淡入（207.6 → 66.5，Δ141.1）三次独立配对结论相同，连点 4 次进程始终存活。

★ **phpunit 802 条全绿、gate 431 全过、旧版照样不动** —— 因为夹具里没有跨实例读

### 23.9.3 未解

用户同时报「点击淡出直接崩溃」。**旧版与新版都复现不出崩溃**（各点 4 次、进程存活）；

> **2026-10-30 结案（关窗时的 `exit=139` 那一半）**：根因找到了，而且不是"玄学"。
>
> - **症状**：关窗后进程以 `0xC0000005` 退出，崩溃点固定是 `php8ts.dll+0x24b30`
>   （Windows 事件日志「应用程序错误」里能看到；`hello.exe` 在 **2026-10-27** 就有
>   完全相同的偏移 ⇒ 确实早就存在）。
> - **根因**：组合根把**应用对象图留到了 PHP shutdown**。两处静态属性各持一半 ——
>   `Errors::installFatalBox()` 的闭包捕获 `$platform`，`ResizeHookState::$pump` 的
>   闭包捕获 `$windows`（应用 / 表面 / 状态）。AOT 产物在 shutdown 段释放这些对象时，
>   类元数据已被销毁 ⇒ 解引用已释放内存。
> - **修法**：组合根在 `EventLoop::run()` 返回后**主动卸下两个钩子**
>   （`ResizeHookState::$pump = null` + `Errors::installFatalBox(null)`），让对象图在
>   引擎还健康时释放。
> - **实测**（单窗关窗 8 次）：两个都不卸 8/8 崩；只卸 `$pump` 7/8；只卸 fatalBox 6/8；
>   **两个都卸 0/8**。`showcase` 同样从 6/8 降到 0/8。⇒ **两个都必须卸**，
>   留一个就足以让整条对象图活到 shutdown。
> - **判据也收紧了**：`tools/probe-two-windows.py` 的 ⑤ 与 `tools/probe-window.py`
>   新增的第 ⑤ 条都改成"退出码必须 0"。此前因为"早就存在"而放水成"进程没了就算过"——
>   那和"崩溃也算通过"是同一类静默失败。
>
> → 用户报的「点击淡出崩溃」仍未被复现，这一条继续挂着。

## 24. 落地记录 · A1c：`Transform`（2026-10-29）

§7 的推荐是"A1b 之后接 A1c（`Transform`，前置=仿射光栅器）"。**这句"前置"写错了**——
不是"先造一个仿射光栅器再用它"，见 24.1。

### 24.1 ★ 先纠一个前提：为什么"变换全在 PHP 侧算"这条路走不通

第一版设计想省掉矩阵栈：`RasterCanvas` 本来就把坐标换算收在两个函数里
（`$offsetX/$offsetY`），那就再加两个 `applyX/applyY`，把矩形四个角、椭圆中心、
折线顶点、路径段全部过一遍矩阵 —— **Skia 后端不动，golden 不变，成本看起来最低**。
逐类点过之后被一条堵死：

| 图元 | PHP 侧能不能自己变换 |
|---|---|
| `drawRect` / `drawOval` / `drawLine` / `drawPath` | 能（顶点过矩阵；椭圆退化成旋转后的路径） |
| `drawParagraph` | **不能** |

理由是硬的：`drift_skia_draw_paragraph` 的 ABI 只有 `(handle, paragraph, x, y)` ——
**字形位图、字号、字距、基线全在 C++ 侧**。PHP 手里只有一个 `Paragraph` 对象和一个
原点，改不了"字长什么样、朝哪个方向画"。旋转 30° 的标题，PHP 无论怎么算 `x,y`，
出来的永远是水平的一行字。

⇒ **真变换必须下推 CTM**（`SkiaCanvas` 走 `drift_skia_concat`，`RasterCanvas` 走自己的
仿射求值）。而文字恰好是唯一不可替代的理由 —— 只要承认"文字要能转"，矩阵栈就躲不掉。

### 24.2 结构：两种变换段**互斥**，谁也不迁就谁

真下推 CTM 的代价是"既有 golden 可能逐字节漂移"（Skia 的 CTM 会改亚像素落点）。
为了不动任何既有画面，做成**两种段**，同一时刻只有一种：

| 段 | 触发 | 落法 | 成本 |
|---|---|---|---|
| **纯平移段** | 只有 `translate()` / 纯平移矩阵 | PHP 侧累加 `$offsetX/Y`（老路，**一行没改**） | 0 |
| **真变换段** | 出现非平移矩阵 | `SkiaCanvas::$devMode` / `RasterCanvas::$transform`，坐标交给矩阵/CTM | 一次 save + 一次 concat |

- 决定点在 **`RecordingCanvas::transform()`**（录制侧），不是在三个回放后端各判一次：
  `isTranslationOnly()` ⇒ 降级录成 `OP_TRANSLATE`；否则录 `OP_TRANSFORM`。**流里分好，
  回放侧与后端都不用再想这件事。**
- `SkiaCanvas::enterDeviceMode()`：进入时先 `drift_skia_save()`（**撤销锚点**），把已累加
  的逻辑偏移换成设备像素下推下去再归零，之后 `translate()` 一律走 `drift_skia_translate`。
  不压这一层 save，这个盒的旋转会漏给后面所有兄弟 —— 而且 W8（save 深度守恒）**查不出来**，
  因为 `transform()` 本身不改变 save 深度。
- `RasterCanvas` 同理：`translate()` 在矩阵模式下不再是 `+=`，而是折进
  `$transform = $transform->translated($dx,$dy)`（**内层**平移）。

### 24.3 `Matrix2D`：一个 335 行的值对象，三条踩过的坑

`src/Geometry/Matrix2D.php`，2×3 仿射，`@api`。工厂 `identity/translation/scaling/
scalingAround/rotation/rotationAround`，运算 `then/translated/applyX/applyY/applyPoint/
applyRect/inverted`，查询 `isTranslationOnly/isIdentity/isAxisAligned/isInvertible`。
可逆性判据用 `inverted() === null`（`|det| < EPSILON`）。

| # | 坑 | 表现 | 修法 |
|---|---|---|---|
| ① | 名字叫 `multiply()` 表达"先 this 后 next" | 与线性代数直觉**恰好相反**（要左乘），必错 | 改名 **`then()`**，让名字承担语义；`multiply` 只留在注释里解释"为什么不叫这个" |
| ② | `translated()` 只写 `tx + dx` | `rotate(90); translate(10,0)` 画到 `(0,10)` 而不是 `(10,0)`，判据红 | 内层平移必须**过线性部分**：`tx' = a·dx + c·dy + tx` |
| ③ | `DEG_TO_RAD` 用 `M_PI / 180.0` | AOT 常量折叠不认除法 | 写成字面量 `0.017453292519943295` |

★ ②的语义区分值得单记：`Canvas::transform()` 的约定是 `CTM' = CTM · m`（**外层**，新矩阵
在世界坐标之后作用），而 `Matrix2D::translated()` 是 `m · T`（**内层**，在已有变换的
坐标系里平移）。两者都叫"平移"，差一个乘侧，结果差一个数量级。这条已写进
`Canvas::transform()` 的 docblock，明确写"与 `Matrix2D::then()` 不是一回事"。

### 24.4 合成槽与命中：反变换必须**在边界检查之前**

- `Modifier` 加 `?Matrix2D $transform` + `bool $transformCentered`；`isDefault()` 同步加两条。
  `withTransform()` 遇到 identity **视为未声明**（不写字段）—— 否则 `->rotate(0)` 会让
  每个盒都进真变换段，白烧一次 save/concat。
- `RenderBox::effectiveTransform()` 绕中心展开成 `T(-c) → M → T(c)`；
  `applyTransform()` 用**结构相等**判断值真变才失效外层缓存（沿用 §23.8 的纪律）。
- **`hitTest()` 里反变换放在 AABB 检查之前**，退化矩阵直接 `return null`：
  - 放在之后 ⇒ 旋转 45° 时角伸出 `[0,w]×[0,h]`，**画得出来但点不动**；
  - 退化矩阵返回 `null` 而不是恒等 ⇒ "点不中看不见的东西" 比 "点得中但位置错" 好排查。
- Widget 层只暴露三个：`transform(Matrix2D, bool $aroundCenter = false)` / `rotate(float $degrees)`
  / `scale(float $factor)`。**没有 `translate()`** —— 平移在 Widget 层已有 `offset`，再开一个
  会让人以为两者不同。

### 24.5 判据（+21 条 / +71 断言）

| 文件 | 挡的退化 |
|---|---|
| `Matrix2DTest`（11） | 顺时针方向、绕中心不动、`then` 次序（**必须用平移+旋转两种形状**，同形状换序测不出来）、逆矩阵往返、退化无逆、`applyRect` 取 AABB、`translated` 内层语义 |
| `CanvasTransformTest`（5） | 录制侧纯平移**必须**降级成 `OP_TRANSLATE`；光栅落点（`scaling 2×` / `save-restore` / `rotate+translate` 内层 / 退化零像素） |

| # | 写法 | 解释器 | AOT |

- **`pushClip(Rect)` 在旋转下仍是矩形**：`SkiaCanvas` 交给 CTM 处理（Skia 内部会做），
  `RasterCanvas` 取 AABB ⇒ **光栅后端在旋转裁剪下偏保守**（裁多了）。要精确得给裁剪
  加路径支持，属独立立项。
- **渐变坐标在变换下不跟随**：`Gradient` 的解析仍按盒的未变换矩形算，旋转后渐变方向
  不变。真修要让渐变也过矩阵（`SkiaCanvas` 可以靠 CTM 免费拿到，`RasterCanvas` 要改
  `gradientColorAt`），与本件耦合但可分离。
- **`drawParagraph` 在 `RasterCanvas` 下只变换原点，不转动字形**。这是光栅后端的
  既有限制（它没有字形旋转能力），**只影响测试后端**，AOT 真机走 Skia 是正确的。
  ⇒ 任何"文字要转"的视觉判据**不能**用 `RasterCanvas` golden 断言。
- 没有 `skew` 工厂，没有 3D 透视（`Matrix2D` 是 2×3，透视要 3×3）。

### 24.9 否掉的方案

**"给 `DisplayList` 的 `OP_TRANSFORM` 拆 6 个 float"**：`SLOTS = 6`，5 个操作数位放不下
6 个 float；而扩槽会让**所有**命令变宽（`Rect`/`Path`/`Paint` 是对象进引用槽才没爆）。
⇒ 矩阵整体走引用槽 `[matrix]`，与 `Rect`/`Paint` 同一档。代价是回放端多一次对象读，
一次性开销，不影响逐帧预算。

## 25. 落地记录 · A4c：`Align`（2026-10-29，A4 三件的收尾）

§7 的 A4 是"布局补三件：`Wrap` / `Positioned` / `Align`"。前两件在 §13/§14 落地，
`Align` 当时被判"有替代品（`Stack` + `StackAlign`、`Center`），价值低于 `Wrap`"。
**这个判断对了一半**：替代品确实存在，但它们是**两套词汇表**，而这一件的真正产出
不是"多一个控件"，是把那两套并成一套。

### 25.1 ★★ 裁决一：`Align` 不需要自己的布局代码

动手前先问：Drift 已经有 `bool $center`（`Modifier` 的字段，由基类 `layout()` 的 ③⑦
两步施加）。`Align` 要的是什么？**九个锚点 + 中间任意值**。而九宫格只是"自由空间的
哪一段"：

```
offset = free * (x + 1) / 2      // x ∈ -1..1
```

`-1 ⇒ 0`、`0 ⇒ free/2`、`+1 ⇒ free`。**`bool $center` 就是 `x = y = 0` 这一个点**。
⇒ 把 `bool $center` 换成 `?Alignment $align`，对齐就推广完了，`Align` 控件只需
写一次 `alignContent($a)`，**不持有任何布局逻辑**。

三条入口因此**同解**（`AlignTest::testCenterIsJustAnAnchor` 逐像素比对）：

| 写法 | 落点 |
|---|---|
| `Center::make($x)->boxSize(100,100)` | (40, 45) |
| `Align::make($x, Alignment::center())->boxSize(100,100)` | (40, 45) |
| `SizedBox::make($x)->size(100,100)->centerContent()` | (40, 45) |

副产品：`Center` 从"独立类"收敛为 `Align` 的子类，两者原本把 `kid` 那套管线
（`make`/`child`/`kid`/`expandChildren`/`createRenderObject`/`createElement`）各抄
一遍，现在只有一份。

### 25.2 ★★★ 裁决二：`StackAlign` 退役（本件唯一的破坏性改动）

`StackAlign` 是九宫格枚举（9 个 case），`Alignment` 是同一概念的**连续**形态。
两者并存意味着：两套词汇、两套默认值、以及"`Stack` 里能不能用 `Align`"这类
永远要解释的问题。**同一概念不留两套词汇** ⇒ 删掉枚举，`Stack::alignment()`
直接收 `Alignment`。

收益不只是"少一个类"，`RenderStack` 的两段 `match` 塌成一次乘法：

| | 改前 | 改后 |
|---|---|---|
| `alignX()` | 9 分支 `match`（含 `default`） | `$this->align->resolveX($free)` |
| `alignY()` | 9 分支 `match` | `$this->align->resolveY($free)` |
| 表达力 | 只有 9 个位置 | 9 个 + 中间任意值（`Alignment(0.5, 0)` = 起点与中心之间） |

★ **默认值刻意不一致，别顺手统一**：`Align` 默认 `center`（与 Flutter 同名类一致），
而 `RenderStack` 默认 **`topLeft`**（自 2026-10-26 起的行为）。把 `Stack` 的默认改成
center 会让所有既有 `Stack` 的静态内容整体偏移 —— 那是一次全域视觉回归，而收益为零。
这条写进了 `RenderStack::__construct()` 的注释。

**破坏面**（已全量替换，`0` 处遗留）：

| 种类 | 处数 | 处理 |
|---|---|---|
| `StackAlign::Xxx` 枚举引用 | 48 | ⇒ `Alignment::xxx()` |
| `RenderStack` / `Stack::alignment()` 形参类型 | 3 | ⇒ `?Alignment` / `Alignment` |
| `use Drift\Layout\StackAlign;` | 6 文件 | ⇒ `use Drift\Geometry\Alignment;` |
| 枚举文件本身 | 1 | **删除** `src/Layout/StackAlign.php` |

### 25.3 裁决三：值对象**不夹取**，夹在调用点

`Alignment` 允许 `|x| > 1`（滑入/滑出动效需要把内容推出去）。要不要把负偏移夹掉，
是**布局策略**不是数学 ⇒ `resolveX/Y` 只做乘法，`RenderBox` 与 `RenderStack`
各自决定，且**都选了"内容比盒大就贴起点"**：

```php
$free = $contentW - $content->width;
if ($free < 0.0) { $free = 0.0; }     // 贴起点，不产生负偏移
```

这条同时是**逐字节兼容的证明**：旧代码是 `max(0, free/2)`，
新代码是 `max(0, free) * (0+1)/2` —— 代数恒等。

### 25.4 踩到的三件事

| # | 事 | 处理 |
|---|---|---|
| ① | **`Modifier::withAlign()` 名字已被占**（flex 的 `alignSelf` 用它） | 两边都改成与 Widget 层同名：`withAlignSelf(int)` / `withContentAlign(?Alignment)`。撞名是类声明期 Fatal，不是运行时 |
| ② | **子类不能比父类少参数**（`Center::make` 想省掉 `$alignment`） | 已实测 `PHP Fatal: Declaration must be compatible` ⇒ 保留两参、第二个忽略并注明"要换锚点请用 `Align`" |
| ③ | `new static` / 默认参数里 `new` 在 `src/` **零先例** | 不赌 tpc：一律 `?Alignment = null` + 方法体里 `?? Alignment::center()`，工厂用 `new self()`（子类各自覆写 `make`，靠**协变返回类型**保证类型正确） |

## 26. 落地记录 · A5-①：文件对话框（2026-10-30）

### 26.1 先裁决：为什么是 A5 而不是 S4

§7 的表把 A5 标成"依赖 S4"，那条依赖是**软的**：S4 拆的是 `Application`
（1911 行 / 67 个公开方法），而 A5-① 在 `Application` 上一行都不加 ——
端口从组合根直接递给页面，绕开了门面。真正的触发点是"多窗口"，不是"文件对话框"。

而 A 档只剩这一件，且它是 §6.1 第 3 条（"从框架到产品"的门槛）的第一项。
S4 是纯搬砖、用户零感知、且没有任何一个消费者在等它 ⇒ **先给能力，S4 等
多窗口立项时再拆**（拆的理由到时候是硬的）。

### 26.2 缺口不在端口，在"端口 + 没人用"

`Drift\Platform\Dialog` 的四个方法**一个月前就写好了**（`@api platform`，
含"取消 ⇒ `null` 不是空串"、"`confirm` 关框 ⇒ false"、筛选表形状三条契约），
`Win32Platform::dialog()` 一直 `return null; // M2+`。

★ 这次补的是三样，一样都不能省：

| # | 缺的 | 落点 |
|---|---|---|
| ① | 原生实现 | `Win32Dialog` + 四个桥函数（`drift_win_open_file` / `save_file` / `alert` / `confirm`） |
| ② | **消费者** | 示例台页 30「对话框 Dialog」 |
| ③ | 平台装配 | `Win32Platform::dialog()` 返回真件（`clipboard()` 同款） |

★ **只做 ① 等于没做**：§16 那条纪律（"未被消费的分支 = 未实现"）在这里是字面意思
—— 没有页面调用它，就没人能说清"取消返回什么、UI 怎么显示"。②是 ① 的判据。

### 26.3 四个方法的返回值语义**不一样**，所以是四个按钮

`openFile`/`saveFile` ⇒ `?string`；`alert` ⇒ `void`；`confirm` ⇒ `bool`。
合成一个"对话框演示"会把三种语义糊成一团，页面上的**可见状态**也就无法分开断言。
页面上因此有三态：`拿到路径` / `取消` / `还没选过` —— 前两态必须分开显示，
否则"取消"会退化成"什么都没发生"，那正是这一页要否定的形态。

### 26.4 编码留在 PHP：`filterText()` 是这条链上唯一有分支的地方

`OPENFILENAMEW::lpstrFilter` 要的是**双 NUL 结尾**的宽字符表
（`名\0通配\0名\0通配\0\0`）。三个岔口：

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 双 NUL 在 PHP 侧拼？ | **不** | NUL 穿过 ABI 之后在调试器里全是一样的点，出了错看不出来 |
| 用 `\t` / `\n` 做中间形态 | **是** | 可读、可断言（`Win32DialogTest` 5 条），C 侧只做"分隔符→双 NUL"一次机械转换 |
| 空表怎么办 | **PHP 兜一行"所有文件"** | `lpstrFilter = NULL` 时 Win32 对话框**不显示筛选行**，用户以为坏了；而兜底文案里有中文，`drift_win32.cc` 不声明 `/utf-8`（源码里的中文字面量会成乱码）⇒ 文案只能放 PHP |

★ 坏项**跳过**而不是 Fatal：筛选表是文案，为它中止整个应用与 §1.2 的中止序列不成比例。

### 26.5 一个诚实的边界：端口表达不了"失败"

`CommDlgExtendedError()` 非 0 是**真失败**（内存不足 / 参数非法），而
`Dialog::openFile(): ?string` 只有"取消 / 成功"两态。**没有加第三态** ——
今天没有调用方会为它写分支，"多一态"只会变成永远不走的 `if`。
取舍是让壳自己弹框报出来（`runFileDialog()` 里那一处 `MessageBoxW`），
不静默装成用户点了取消。这条写进了 `Dialog` 的接口注释。

### 26.6 owner 必须每次现取

`Win32Dialog` 收的是 **`Win32WindowHost` 对象**，不是句柄：句柄在建窗之前是
`null`，而组合根完全可能在建窗之前就把端口递出去。缓存句柄的后果是 owner 恒 0
——`MB_TASKMODAL` 只挡本进程，弹框会跑到别的程序窗口后面去（**不报错**）。

★ `Win32Platform::dialog()` 里直接 `new Win32WindowHost()` 再塞字段，
**不写** `new Win32Dialog($this->window())`：`window()` 的返回类型是接口
`WindowHost`，AOT 对"接口值喂进类类型形参"不做静态判断 —— 别给它机会在运行期失败。

## 27. 落地记录 · A5-②：拖文件进窗（2026-10-30）

### 27.1 先裁决：为什么是这一件，而不是 S 档 / 托盘

§7 把 A5 标成"依赖 S4"，但 §26.1 已经裁决那条依赖是**软的**：A5-① 在
`Application` 上一行都没加，端口直接从组合根递给页面；S4 真正的触发点是
"多窗口"，不是"文件对话框"。A5 内部顺序是「文件对话框 → 拖文件 → 托盘 →

不转 S 档、也不先做托盘，两条硬理由：

- **S4 没有消费者在等**：纯搬砖、用户零感知。上一轮刚裁决"等多窗口立项时再拆"，
  现在转头做等于自我推翻（§26.1）。
- **托盘零消费者**：`Tray` 端口今天一个调用点都没有，先实现等于让"支持"变成
  一句无法验证的话（§26.9）—— §16 那条纪律（未被消费的分支 = 未实现）是字面意思。

★ 而 §26.9 自己承认拖文件"够一件单独的量"。它是 A5 里唯一现在就成立的一件。

★ 更贴用户这轮强调的"多从结构、扩展性角度"：这一件的本质**不是加个按钮，是
建立一条新的正交通道** —— OS 系统消息 → 事件对象 → 输入路由 → 控件接收。
这条通道立起来后，托盘消息、其它 shell 事件都能复用同一条路。

`WM_DROPFILES` 之前是 **0**：`DragAcceptFiles` 没调、`WndProc` 没有分支、

### 27.3 三个岔口的裁决（即"有没有更好的方案"）

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 载荷怎么过 ABI | **多路径用 `'\n'` 分隔塞进现成 `text` 字段**，不新增 `std::vector<std::string>` 跨数组 | 数组字段跨实例读在 AOT 上是 C2679/`php::Var` 高发区（§24 踩过 `Float += Var`）；`'\n'`(U+000A) 在 Win32 文件名里**非法** ⇒ 分隔无损；中间形态可单测（同 A5-① `filterText` 思路：可读、可断言、C 侧只做最后一次机械转换） |
| 谁来接收 | **命中测试 + 父链冒泡**找最近 `onFilesDropped` 声明者 | 应用级单一 handler 会让"多个控件分别接收"退化成在 handler 里再分发一遍（扩展性差）；命中是框架既有模型（`draggableOwner`/`pointerOwner`/`windowDragOwner`/ScrollEvent 分支都是同款 `xxxOwner()` + `hitTest`） |
| 能力怎么声明 | Widget fluent `onFilesDropped(\Closure)` + `filesDropHandlerValue()` | 与 `windowDrag()`/`pointer()` 同构（写侧 + 读侧成对、`@api`/`@internal` 各归其位）；`implements` 接口会让 StatefulWidget 的状态无处安放（状态在 `State` 里，接口挂 `Widget` 上），而闭包在 `build()` 里捕获 `$this`（State）即可 `setState()` |

★ 落点坐标复用 `PendingEvent.a/b`，坐标除 dpr 转逻辑单位放在
`Win32Platform::pump()`（与 pointer/wheel 同口径，§6.1 量化只在平台侧做一次）。

### 27.4 两个被否掉的"更激进"方案

- **OLE `IDropTarget`/`RegisterDragDrop`**：现代、能给悬停反馈与非文件数据。

- **把 `InputRouter::dispatch` 的 if-else 类型分发重构成注册表**：结构性更漂亮，

  用不上用户给的"可以破坏兼容性"授权 —— 兼容性破坏该留给真正需要它的 S 档。

### 27.5 ★★ 一个被"照抄既有写法"差点带进去的坑：`Errors` 默认级会 `exit()`

`deliverFilesDropped` 的异常兜底初版照抄 `beginWindowDrag` 的

Fatal 在 debug 与 release **都中止**，末尾是 `exit()` —— 一次拖放回调抛异常就让
**整个进程退出**，与"兜住异常、不吞消息泵"的注释完全相反。

修：改用 `Errors::RECOVERABLE`（同 `Subject::notifyChanged()` 对订阅者异常的
隔离口径）。release 下只 `appendLog` + return；debug 下仍会中止（这是框架既定
语义，测试里以 `setDebug(false)` 显式降级测量，配方抄 `SubscriptionIsolationTest`）。

★ 这条记进 `PITFALLS`：以后在回调兜底里写 `Errors::report`，**不要照抄默认级**，
先看清楚要的是"隔离"还是"中止"。

### 27.8 ★ 真机取证方法：SendInput 模拟不了 shell 拖放，改注入 HDROP

`probe-grab` 的 SendInput 只能造鼠标/键盘消息，**造不出 `WM_DROPFILES`** ——
它由系统 shell 在真实拖放结束时发出，带一个 `HDROP`（`GlobalAlloc` 来的
`DROPFILES` 结构 + 双 NUL 结尾宽字符路径表）。所以这一段的 C++ 桥（`DragQueryFileW`
→ `toUtf8` → `'\n'` 拼接）**没有任何 PHP 测试覆盖得到**（feature 测试是从
`FilesDroppedEvent` 往下派的，够不到桥）。

取证办法：`_build/inject-drop.ps1` 用 P/Invoke 亲手构造合规 HDROP，`PostMessage`
`WM_DROPFILES` 到 showcase 主窗。这覆盖了整条真实链路（消息进 WndProc → 入队 →
pump 翻译 → 命中冒泡 → 页面重建）。踩到并记进 `PITFALLS` 的两个坑：

- **`FindWindowW("DriftWindowClass")` 找不到窗口**，而 `probe-grab` 按 pid 枚举能
  拿到 `hwnd` ⇒ 注入脚本不再自己找窗口，改由探针解析 `probe-grab` 输出的
  `hwnd=0x…` 直接递进去。
- **PS 5.1 两个语法坑**：`.ToInt64()` 方法解析失败（`[IntPtr]::new()` 的产物）⇒
  用朴素类型转换；`.ps1` 按 ANSI(GBK) 读无 BOM 文件 ⇒ 中文路径用 `[char]0x62A5`
  码点拼，脚本本身保持纯 ASCII，却能验证 UTF-16→UTF-8。
- **前台跑 GUI 探针仍会 SIGTERM**（STDOUT 缓冲全丢）⇒ 输出重定向 `/dev/null` +
  日志落文件，才拿得到"跑到哪一步"。

### 27.9 这一件没做的事

### 28.2 缺口本质：不是"扫中文"，是"给显式标记做过期守卫"

B2 字面写的是"让 `docref` 红"。复核后换了落点，两条硬理由：

- **`docref` 扫不到示例页注释**：`DocSet::collectDocs()` 只收 `docs/** + DESIGN.md`，
  而"诚实边界"住在 `apps/showcase/src/Pages/*.php` 的**代码注释**里。改 `docref`
  让它扫 `apps/` 等于把职责从"文档引用校验"扩成"全仓注释扫描"，破坏面大。
- **自由中文扫不得**：中文"没有 / 缺席 / 做不到"里混着大量**主动取舍**
  （Slider 不做垂直、Snackbar 不做动画…），词法扫会把"有意不为"和"能力真缺"
  一锅端 ⇒ 误报。G2 的"响亮"要打在真违约上，不能变成噪音。

裁决落地为 **lint 第 24 条 `stale-capability-claim`**：作者用一行显式标记声明
"这个能力现在缺，补上请提醒我"，规则只做机械核对——符号一旦存在就 ERROR。
"值不值得被守"的判断交还给人，规则不猜中文。

### 28.3 三个岔口的裁决

| 岔口 | 裁决 | 理由 |
|---|---|---|
| 标记语法 | `@capability-gap:` + `\|` 分节紧凑 probe（`class\|FQN` / `method\|FQN\|name` / `const\|FQN\|NAME`），行内空白后接可选理由 | 用空格/冒号分节会与 `Class::method` 的 `::`、中文理由里的空格撞车；`\|` 段内不含空白 ⇒ 正则 `\S+` 一抓一个准，理由天然被隔开 |
| 符号查询 | 复用 `ClassTable`，方法/常量沿 `extends` 链查；宿主类不存在一律判绿 | 不新造第二套符号解析（§16.6.3 的教训）；宿主类都没有 ⇒ 能力必然仍缺，不为难未来的重构 |
| `const` 探针 | 给 `SourceQuery::readBody()` **加一张类常量表**（纯增量字段 `constants`） | 原 info 只有 `properties`/`methods`，查不了常量；常量是编译期可见的类结构事实，本就该由 `SourceQuery` 抽，顺手补齐让后续规则可复用（结构收益，非局部 hack） |

★ `method` 只查类自身 + `extends` 链声明，**不追 trait**；常量一条声明只记首名
（`const A=1,B=2;` 会漏 B）。都写进规则 docblock 的"诚实边界"——漏报可接受，
误报不可接受。FQN 需写全限定名（注释不是代码，没有 use 上下文可解析）。

### 28.4 两个被否掉的"更激进"方案

- **让 `docref` 扫 `apps/**` 注释**：职责从文档引用校验扩成全仓注释扫描，
  且 `DocSet` 的目录模型要动，破坏面与收益不成比例。
- **正则扫自由中文"框架没有 X"并自动解析 X**：X 的形态无边界（类名/方法/op/
  一整句能力描述），无法可靠符号化，且主动取舍文案会被误伤。A15：判断交还给人。

### 28.5 判据与变异自检

lint 双向自检（§20 纪律 1）新增 `stale-capability-claim` 一组：

- **反例** `StaleCapabilityClaimBad.php` ⇒ **5 条 ERROR**：`class`/`method`/`const`
  三种"符号已存在"（自包含夹具：被 probe 的类就在同文件）+ 未知探针类型
  `widget\|…` + 分节数不足 `class`。后两条守"拼写错了必须响、不静默忽略"。
- **正例** `StaleCapabilityClaimGood.php` ⇒ **0 条**：符号确实还缺（`method`/`const`
  查不到）、宿主类不存在（`class\|Drift\Never\Exists`）、自由中文写"框架从来没有
  XXX 能力"但没打标记——三件"看着像但绿"。

首跑自检时规则产出了 5 条但 `$expected` 未接 ⇒ 自检如实 FAIL 并打印实际产出，
接线后全绿（`该响 5 / 不该响 0`）。★ 这就是双向自检的价值：先证明"有牙"，
再证明"不误伤"。

真实消费者首批两个（都 Grep 双确认当前确实缺 ⇒ 判绿，规则不是空转）：
`LogPage` 的 `@capability-gap: method|Drift\Widget\Text|mono`（`function mono` 全仓
0 命中）、`CustomPaintPage` 的 `@capability-gap: const|Drift\Rendering\DisplayList|OP_ARC`
（`OP_ARC` 全仓 0 命中）。
