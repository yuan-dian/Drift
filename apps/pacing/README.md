# apps/pacing —— 帧节奏量具

**这里只有两个问题：真窗口上，`waitEvents()` 的帧间隔是多少、短等待会不会被量化？**

它不是能力示例，是尺子（与 `apps/bench` 同一条理由：`drift-build` 只认
`apps/<name>/project.yml`）。

## 怎么跑

```bash
# 从仓库根
php tools/drift-build.php pacing
./pacing.exe
cat build/pacing-out.txt
```

★ **必须跑 AOT 产物**：`drift_win_*` 是原生桥，解释器里没有这些函数。

## 判据

| 项 | 阈值 | 为什么 |
|---|---|---|
| `median` | 16.667ms ± 0.63ms（±3.8%） | 60fps 的帧间隔 |
| `p99` | ≤ 20ms | 尾部不能掉帧 |
| `max` | ≤ 33ms | 最多容忍丢一帧 |
| `over25` | 0 | 25ms 已肉眼可见 |
| `short` | 每个请求的 `err_max` ≤ 4ms | 短等待不许被量化到系统 tick（15.6ms） |

只统计**连续 `Timeout`** 的间隔：消息/IO 打断会重置基线（那些帧不是"按节奏等"）。

## 实测（本机，300 帧 × 3 轮取中位）

| 实现 | median | p99 | max | >25ms |
|---|---:|---:|---:|---:|
| `SetTimer(16)` 系统 tick（旧） | 15.78 | 31.59 | 32.71 | 21 |
| 高精度定时器 + 相对排程（中间态） | 17.98 | 18.80 | 19.06 | 0 |
| 高精度定时器 + 绝对排程（现行） | **16.81** | **17.63** | **17.88** | **0** |

两处都必要：高精度定时器去掉系统 tick 的 15.6ms 量化；绝对排程去掉每帧
`~1ms` 唤醒延迟的逐帧叠加（相对排程会稳定偏成 18ms）。

### 短等待（`after(N)` 的 deadline 路径最终落在这里）

| 请求 | 现行 `err_max` | 退回系统 tick 的 `err_max` |
|---|---:|---:|
| 1ms | 2.22 | **15.35** |
| 4ms | 2.62 | **12.83** |
| 15ms | 2.12 | **15.95** |
| 50ms | 1.73 | **14.51** |

现行实现是**常数 ~1ms 唤醒开销**（不随请求放大）；退回系统 tick 则一律被拉到
15.6ms 的整数倍 —— 这就是 `short` 档判据要挡的形态。

## 边界

- 窗口必须**空闲**（无动画/无持续消息）。有消息时 `waitEvents` 返回 `Message`，不计入。
- `vsync` 是另一条路（`DwmFlush`），帧率上限 = 刷新率；本仓不用它做默认（会锁死刷新率，且远程桌面下不可靠）。
- **这个量具解释不了应用层**：`after(N)` 的真实延迟 = 等待误差（上表）+ 一帧（帧边界回调）。
  N < 16.667 时 `after` 仍要等下一帧，那是「定时器在帧边界交付」的语义，不是量化。
